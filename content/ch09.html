9.1 OOP pillars as design tools

Why?

In simple words: The four OOP pillars are not definitions to recite. They are questions you ask while designing. If your design skips one, the interviewer will notice and ask about it.

Interviewers will not ask you to define encapsulation. Instead, they watch whether your design actually uses it.

Each pillar answers one design question. If you forget a pillar, the design shows a clear warning sign. This warning sign is called a smell. Interviewers know these smells well, and they will dig into them.

What is happening internally?

The table shows the question each pillar answers, and the smell you see when it is missing.

Pillar Design question it answers Smell when missing
Encapsulation Who owns this data, and who checks its rules? Public setters everywhere; logic sits in "manager" classes that change other objects' fields directly
Abstraction What does the caller really need to know? Callers depend on concrete classes and their inner details
Inheritance Is this truly an "is-a" relationship, with shared behaviour that rarely changes? Very deep class trees; subclasses override methods just to throw UnsupportedOperationException
Polymorphism How do I add a new type without editing old code? if/else or switch on type codes copied all over the codebase

Rich vs anaemic domain model

  • In a rich model, behaviour lives next to the data it protects. For example, account.debit(points) itself refuses to let the balance go negative.
  • In an anaemic model, entities are just bags of data. Services read the fields, do the calculation and write the values back. So every service must remember every rule. If one service forgets, the rule is broken.

Think of a bank locker. In a rich model, the locker has its own lock and checks your key. In an anaemic model, the locker is an open box, and every staff member must remember to check your key.

How does it work?

While designing, ask three questions for each class:

  1. What rules (invariants — things that must always be true, like "balance is never negative") does this class own?
  2. What is the smallest public API that still lets callers do their job?
  3. Where will change come from? New types, new rules, new channels?

Put an interface exactly at the place where change will come from — and nowhere else.

Example

// Anaemic: the rule "can't redeem more than balance" lives in some service — or nowhere
class Wallet { public long balance; }

// Rich: the object protects its own invariant
final class Wallet {
    private long balance;
    void credit(long pts) { if (pts <= 0) throw new IllegalArgumentException(); balance += pts; }
    void debit(long pts)  { if (pts > balance) throw new InsufficientPointsException(pts, balance); balance -= pts; }
    long balance() { return balance; }
}

// Polymorphism instead of type switches
interface RewardRule { long points(Order o); }          // a new rule type = a new class, no edits elsewhere

When would I use it?

In every LLD answer. Say these things out loud:

  • which class owns which rule,
  • where the abstraction boundary is (what callers can and cannot see), and
  • how a new variant plugs in without editing old code.

What can go wrong?

  • Over-abstraction: making an interface for every class "just in case".
  • Fake encapsulation: thinking that private fields with getters and setters is encapsulation. It is not, if anyone can still set any value.
  • Inheritance only to reuse code: using extends just to borrow methods, when there is no real "is-a" relationship.

Interview questions

Q1. How do OOP principles show up in your design? Encapsulation: each entity checks and protects its own rules (invariants). Abstraction: callers depend on interfaces such as PaymentGateway, not on concrete classes. Polymorphism: a new variant is just a new class. Inheritance: I use it only for a real is-a relationship; otherwise I use composition (one object holding another).

Q2. What's an anaemic domain model and why is it a smell? It is a model where entities have only data plus getters and setters, and all the logic sits in services. It is a smell because no class owns the rules. So rules get copied into many services, or someone forgets them.

9.2 Class relationships and UML in interviews

Why?

In simple words: Draw a quick box-and-arrow picture of your classes before you code. It gets you and the interviewer on the same page, and the arrows show who owns what.

A quick class diagram takes about five minutes. It makes sure you and the interviewer agree on the design before you write code.

The relationship types are association, aggregation, composition, inheritance and dependency. Using them correctly tells the interviewer you understand ownership and lifecycles. Ownership means "who is in charge of this object". Lifecycle means "when it is created and when it is deleted". These two things decide which class creates and deletes which object.

What is happening internally?

Relationship Meaning Java shape UML
Dependency Uses another class for a short time A method parameter or a local variable dashed arrow
Association Knows about another object A field that points to another object plain line
Aggregation Has-a; the part can live on its own A field holding objects created somewhere else (Team → Player) hollow diamond at the whole
Composition Owns; the part dies when the whole dies The whole creates and manages its parts (Order → OrderLine) filled diamond at the whole
Inheritance Is-a extends hollow triangle
Realisation Implements an interface implements dashed line + hollow triangle

Multiplicity means "how many objects are on each side of the link". You write it as 1, 0..1, * (any number) or 1..* (one or more).

A simple way to remember aggregation vs composition: a cricket team has players, but if the team is dissolved, the players still exist (aggregation). A tiffin box has compartments, and if you throw away the box, the compartments go with it (composition).

How does it work?

  1. Draw a box for each class.
  2. In the box, write the class name, 2–4 key fields and the key methods.
  3. Draw the arrows between boxes.
  4. Mark interfaces with «interface».
  5. Do not draw getters, setters or every field.
  6. Spend five to eight minutes at most.

Example

+----------------------+ 1        1..* +----------------------+
| ParkingLot           |◆──────────────| ParkingFloor         |
| - floors             |               | - spots by type      |
| + park(Vehicle)      |               | + findSpot(type)     |
| + exit(ticketId)     |               +----------------------+
+----------------------+                         ◆ 1..*
          │ uses                       +----------------------+
          ▼                            | ParkingSpot          |
 «interface» FeeStrategy               | - id, type, free     |
 + fee(type, duration)                 +----------------------+
    △            △
 HourlyFee   FlatDailyFee

When would I use it?

  • At the start of every LLD round, right after you clarify the requirements.
  • In behavioural rounds, when you explain the design of a system you built.

What can go wrong?

  • Spending 20 minutes making a perfect diagram.
  • Drawing implementation details instead of the main structure.
  • Forgetting multiplicities. These matter because they decide your data structures. For example, "1..* spots" means you need a collection of spots, keyed by spot type.

Interview questions

Q1. Aggregation vs composition? Both are has-a relationships. In composition, the whole owns the part's lifecycle — an order's lines are deleted with the order. In aggregation, the part lives independently — players still exist after a team is broken up.

Q2. Association vs dependency? Association is a lasting link in the structure, usually a field. Dependency is short-term use, usually a method parameter or a local variable.

9.3 Single Responsibility Principle (SRP)

Why?

In simple words: A class should do one kind of job, for one kind of person. Then a change asked by one team touches only that team's class.

Suppose one class does many jobs. Then it changes for many reasons. A tax rule change, a database change and an email template change all edit the same file.

Because of this:

  • Different people's changes clash in code reviews.
  • A change for one reason can break something unrelated.

SRP keeps each class focused on one job. So changes stay local, and testing is simple.

What is happening internally?

The rule is: "A class should have one reason to change."

"One reason" means one actor — one person, team or concern that asks for changes. Examples: finance rules, saving to the database (persistence), or how things look on screen (presentation).

So you split responsibilities by who asks for changes. You do not split them by counting methods.

How does it work?

  1. Look at a class.
  2. List everyone who could ask for a change to it.
  3. If there is more than one such stakeholder, split the class along those lines.
  4. Add a small coordinator class that calls the pieces in the right order.

Example

// Before: calculation + persistence + rendering + email in one class
class InvoiceService {
    Invoice create(Order o) { /* tax + discount rules */ return null; }
    void save(Invoice i)    { /* SQL */ }
    byte[] pdf(Invoice i)   { /* layout */ return null; }
    void email(Invoice i)   { /* SMTP */ }
}

// After: each piece changes for one reason
class InvoiceCalculator { Invoice create(Order o) { return null; } }        // finance rules
interface InvoiceRepository { void save(Invoice i); }                       // persistence
class InvoicePdfRenderer { byte[] render(Invoice i) { return null; } }      // presentation
class InvoiceMailer { void send(Invoice i, byte[] pdf) { } }                // delivery
class InvoiceWorkflow {                                                     // coordinator
    private final InvoiceCalculator calc; private final InvoiceRepository repo;
    private final InvoicePdfRenderer pdf; private final InvoiceMailer mailer;
    InvoiceWorkflow(InvoiceCalculator c, InvoiceRepository r, InvoicePdfRenderer p, InvoiceMailer m) { calc = c; repo = r; pdf = p; mailer = m; }
    void issue(Order o) { Invoice i = calc.create(o); repo.save(i); mailer.send(i, pdf.render(i)); }
}
record Order() {} record Invoice() {}

When would I use it?

Split a class when you see any of these signs:

  • It has grown beyond about 200–300 lines.
  • It has unrelated dependencies — for example a repository and an SMTP (email) client and a PDF library.
  • Its tests need many unrelated mocks.

What can go wrong?

You can over-split. Dozens of one-method classes are hard to find your way around.

Group by cohesion instead: things that change together should stay together.

Interview questions

Q1. Explain SRP with an example. Each class should have one reason to change. For invoices, I keep calculation (finance rules), persistence (database), PDF rendering and delivery (email) in separate classes. A workflow class coordinates them.

9.4 Open/Closed Principle (OCP)

Why?

In simple words: When you need a new type of something, you should add a new class — not edit an old, tested switch. Old code stays safe; new code plugs in.

Imagine every new reward type, payment method or notification channel means editing one central switch. Each edit can break the cases that already work. So you must retest all of them every time.

OCP says code should be open for extension, closed for modification. In plain words: add new behaviour by adding new code, not by editing code that is already tested.

What is happening internally?

  1. Each place where behaviour varies (a variation point) becomes an abstraction — an interface.
  2. Each variant becomes one class that implements this interface.
  3. The core logic depends only on the interface.
  4. The core logic receives the variants from outside — through dependency injection or a registry (a lookup map).

So polymorphism replaces the if/else chains.

Think of a mobile charger socket. The socket stays the same. To support a new phone, you buy a new cable that fits the socket — you do not rewire the wall.

How does it work?

  1. Find a switch or if-else on a type code that keeps growing.
  2. Pull out an interface with the operation that varies.
  3. Move each branch into its own class.
  4. Pick the right class at runtime from a map or a factory.

Example

// Before: every new reward type edits this method
long points(Order o, String type) {
    switch (type) {
        case "FLAT": return 100;
        case "PERCENT": return o.amount() / 10;
        default: throw new IllegalArgumentException(type);
    }
}

// After: new types are new classes; the engine never changes
interface RewardStrategy { String type(); long points(Order o); }
class FlatReward implements RewardStrategy { public String type() { return "FLAT"; } public long points(Order o) { return 100; } }
class PercentReward implements RewardStrategy { public String type() { return "PERCENT"; } public long points(Order o) { return o.amount() / 10; } }

class RewardEngine {
    private final Map<String, RewardStrategy> byType;
    RewardEngine(List<RewardStrategy> strategies) {                  // Spring injects all implementations (6.4)
        byType = strategies.stream().collect(Collectors.toMap(RewardStrategy::type, s -> s));
    }
    long points(Order o, String type) { return Optional.ofNullable(byType.get(type)).orElseThrow().points(o); }
}
record Order(long amount) {}

When would I use it?

Wherever you expect new variants to keep coming: pricing, fees, rule types, channels, export formats, payment providers.

What can go wrong?

You may predict change that never comes. This is speculative abstraction. It breaks YAGNI — "You Aren't Gonna Need It".

So apply OCP where change has already happened, or is clearly planned.

Interview questions

Q1. Explain OCP with an example from your work. In our incentive and reward system, each new rule type is a new Strategy class, registered by its type name. The evaluation engine does not change when we add a type.

9.5 Liskov Substitution Principle (LSP)

Why?

In simple words: A child class must behave the way its parent promised. If code works with the parent, it must still work when you pass in the child.

Polymorphism only works if every subtype can replace its base type without surprising the caller.

Suppose a subclass breaks the base class's promise (its contract). For example, it throws where the base does not, ignores an input, or gives a weaker guarantee. Then bugs appear in other code — code that was correct — far away from the subclass. These bugs are hard to trace.

What is happening internally?

A subtype must keep the base type's contract. This means four things:

  1. No stronger preconditions. A precondition is what the method needs before it runs. The subtype must accept at least everything the base accepts.
  2. No weaker postconditions. A postcondition is what the method promises after it runs. The subtype must promise at least what the base promises.
  3. Keep the invariants. Rules that are always true for the base must stay true.
  4. No new surprise exceptions. Do not throw exceptions that callers of the base would not expect.

Think of a substitute driver for your office cab. You don't care who drives, as long as he follows the same route and reaches on time. If the substitute refuses to take the highway, the "substitute" has broken the deal.

How does it work?

Test it with this question: "Can every caller of the base type use this subtype correctly, without knowing it is a subtype?"

If callers need instanceof checks or special cases, LSP is broken.

To fix it, redesign the hierarchy. Use separate interfaces for separate capabilities.

Example

// Violation 1: the classic Square/Rectangle
class Rectangle { protected int w, h; void setWidth(int w) { this.w = w; } void setHeight(int h) { this.h = h; } int area() { return w * h; } }
class Square extends Rectangle {
    @Override void setWidth(int w) { this.w = w; this.h = w; }      // breaks the caller's expectation
    @Override void setHeight(int h) { this.w = h; this.h = h; }
}
// Caller: r.setWidth(5); r.setHeight(4); assert r.area() == 20  → fails for Square (16)

// Violation 2: capability not supported
class ReadOnlyAccount extends Account { @Override void debit(long p) { throw new UnsupportedOperationException(); } }

// Fix: model capabilities separately
interface Shape { int area(); }
record Rect(int w, int h) implements Shape { public int area() { return w * h; } }
record Sq(int side) implements Shape { public int area() { return side * side; } }

interface Readable { long balance(); }
interface Debitable extends Readable { void debit(long p); }
class Account { void debit(long p) {} }

When would I use it?

  • When you design class hierarchies.
  • When you review subclasses that override a method only to throw or to do nothing.

What can go wrong?

Using inheritance because something is "is-a" in English. A square is a rectangle in maths class. But in code, a Square cannot behave like a Rectangle, because its width and height cannot change separately. What matters is whether one can safely replace the other in code — this is called behavioural substitutability.

Interview questions

Q1. What is LSP and give a violation? You must be able to use a subtype anywhere the base type is expected, without breaking correctness. Two classic violations: Square overriding Rectangle's setters so width and height change together, and a subclass that throws UnsupportedOperationException for a base-class method.

9.6 Interface Segregation Principle (ISP)

Why?

In simple words: Don't make one giant interface for everything. Make small interfaces, so each class implements only what it can really do, and each caller sees only what it really uses.

A "fat" interface has too many methods. This causes two problems:

  1. Every class that implements it must provide methods it cannot support. Usually it just throws for them.
  2. Every client depends on methods it never calls. So a change to an unrelated method still affects it.

What is happening internally?

Split a large interface into small role interfaces. Each role interface covers one need of one kind of client.

  • One class can implement several roles.
  • A client depends only on the role it uses.

Think of a restaurant menu. A tea stall does not need to print the full five-star menu and then write "not available" next to most items. It prints only what it serves.

How does it work?

  1. Group the methods by which client calls them.
  2. Turn each group into its own interface.

Example

// Fat interface: a simple printer must "implement" fax
interface Machine { void print(Doc d); void scan(Doc d); void fax(Doc d); }

// Segregated
interface Printer { void print(Doc d); }
interface Scanner { void scan(Doc d); }
interface Fax { void fax(Doc d); }
class SimplePrinter implements Printer { public void print(Doc d) { } }
class OfficeMachine implements Printer, Scanner, Fax { public void print(Doc d) { } public void scan(Doc d) { } public void fax(Doc d) { } }
record Doc() {}

// Domain example: readers of a ledger shouldn't depend on posting
interface LedgerReader { long balance(String accountId); List<String> statement(String accountId); }
interface LedgerWriter { void post(String accountId, long points, String idemKey); }

When would I use it?

  • When an interface has many methods, and some implementations leave methods empty or make them throw.
  • When read clients and write clients are different. This read/write split is also the basis of CQRS (Command Query Responsibility Segregation — separate models for writes and reads).

What can go wrong?

Splitting into one method per interface with no reason. Keep each interface cohesive — its methods should belong together.

Interview questions

Q1. What is ISP? Clients should not depend on methods they don't use. So I prefer small, role-specific interfaces over one fat interface.

9.7 Dependency Inversion Principle (DIP)

Why?

In simple words: Your business logic should not know which SMS company or which database you use. It talks to an interface it owns; the SMS or database code plugs into that interface from outside.

Suppose business logic directly creates infrastructure objects, like new TwilioClient() or new PostgresRepo(). Then two problems follow:

  • Every infrastructure change ripples into business code.
  • You cannot test the business logic without the real infrastructure.

DIP fixes this. It makes both sides depend on an abstraction (an interface), and the business side owns that interface.

What is happening internally?

  1. The high-level policy (for example, the redemption rules) defines ports. A port is an interface the business needs, such as NotificationSender or LedgerRepository.
  2. The low-level details (Twilio, Postgres) implement these ports. These implementations are called adapters.
  3. Now the source-code dependency points from the detail to the abstraction. Normally the business code would point to the detail. This direction is now flipped — that is the "inversion".

This idea is the core of hexagonal architecture (also called ports and adapters) and of clean architecture. DI containers like Spring connect the adapters to the ports for you (6.2).

Think of a wall plug socket. The socket's shape is fixed by the house, not by the appliance. Any appliance — a fan, a mixer, a phone charger — makes its plug fit the socket.

How does it work?

The diagram shows the dependency before and after.

Before:  RedemptionService ──► TwilioClient        (policy depends on detail)
After:   RedemptionService ──► «interface» NotificationSender ◄── TwilioSender
                                                             ◄── WhatsAppSender
                                                             ◄── FakeSender (tests)

Example

// Port owned by the domain
public interface NotificationSender { void send(String to, String message); }

// Policy depends only on the port
public class RedemptionService {
    private final NotificationSender notifier;
    public RedemptionService(NotificationSender notifier) { this.notifier = notifier; }
    public void redeem(String phone, long pts) { /* rules */ notifier.send(phone, "Redeemed " + pts + " points"); }
}

// Adapters at the edge
class TwilioSender implements NotificationSender { public void send(String to, String msg) { /* Twilio SDK */ } }
class RecordingSender implements NotificationSender {                     // for tests
    final List<String> sent = new ArrayList<>();
    public void send(String to, String msg) { sent.add(to + ":" + msg); }
}

When would I use it?

At every boundary with infrastructure or outside systems: the database, messaging, HTTP partners, clocks, file storage.

What can go wrong?

  • Leaky interfaces: the interface copies one vendor's API exactly. Then the abstraction leaks that vendor's concepts into your business code.
  • Needless interfaces: making interfaces for internal classes that will never have a second version.

Interview questions

Q1. Explain DIP. Both high-level and low-level modules depend on abstractions. The high-level (business) side owns these abstractions. The low-level details implement them and are injected from outside.

Q2. DIP vs DI? DIP is a design principle — it is about which direction dependencies point. DI (dependency injection) is a technique — you pass dependencies in from outside instead of creating them inside. Containers like Spring automate DI.

9.8 Singleton

Why?

In simple words: Some objects should exist only once in the whole program. A Singleton makes sure only one is ever created, and everyone shares it.

Some things must exist exactly once per process. Examples: a configuration registry, an ID generator, a metrics registry.

If you create many of them, you waste resources. Worse, each copy may hold different data, so the state becomes inconsistent. For example, two ID generators could hand out the same ID.

What is happening internally?

The class hides its constructor, so nobody else can call new. It gives out one shared instance instead.

In Java, the safe versions depend on guarantees from the JVM:

  • Holder idiom: the JVM loads a class only when it is first used (lazy), and it does this in a thread-safe way. So a static field inside a nested holder class is created once, safely, on first use.
  • Enum: each enum constant is created exactly once. Java also protects enums from the two common attacks on singletons — creating a second copy using reflection, or by serialising and deserialising.

How does it work?

public enum IdGenerator {                          // 1. Enum: simplest, safest
    INSTANCE;
    private final AtomicLong seq = new AtomicLong();
    public long next() { return seq.incrementAndGet(); }
}

public final class AppConfig {                     // 2. Holder idiom: lazy, thread-safe, no locks
    private AppConfig() { }
    private static final class Holder { static final AppConfig INSTANCE = new AppConfig(); }
    public static AppConfig get() { return Holder.INSTANCE; }
}
// 3. Double-checked locking with volatile — see 4.6

Example

long id = IdGenerator.INSTANCE.next();.

In Spring, you rarely write singletons yourself. Every bean is already a singleton per container by default. Spring injects it wherever it is needed, and you can replace it with a fake in tests.

When would I use it?

  • In plain Java (LLD rounds without Spring): for stateless utilities or truly global resources.
  • In Spring apps: prefer singleton-scoped beans instead.

What can go wrong?

  • Hidden global state: tests share the same instance, so one test can affect another.
  • Tight coupling: calls like X.getInstance() all over the code cannot be mocked easily.
  • Thread safety: if the singleton holds data that changes (mutable), you must make it thread-safe.
  • Bad lazy initialisation: if you create it lazily without proper synchronisation, two threads can create two instances. Or one thread can see a half-built object.

Interview questions

Q1. How do you implement a thread-safe singleton? Use an enum singleton, or the holder idiom. Another option is double-checked locking with a volatile field.

Q2. Why are singletons criticised? They create global state that can change, hide dependencies, make testing hard and couple code tightly. A single instance supplied through dependency injection avoids these problems.

9.9 Factory patterns: simple factory, factory method, abstract factory

Why?

In simple words: A factory is one place that decides which class to create and how to set it up. The rest of the code just asks the factory and gets an object.

Suppose new ConcreteClass() is written all over the code. Two problems follow:

  • Callers are tied to concrete types.
  • The creation logic is copied everywhere — which class to pick for which input, and how to configure it.

A factory puts this in one place. It decides which class to create and how.

Think of a railway reservation counter. You say "Sleeper, Delhi to Varanasi". The clerk decides which coach and berth to give you. You don't walk into the train and pick a seat yourself.

What is happening internally?

There are three kinds of factory:

  • Simple factory. It is not an official GoF ("Gang of Four" design patterns book) pattern, but it is the most common. A static method picks the class based on a parameter.
  • Factory Method (GoF). An abstract creator class declares a create() method. Subclasses decide which concrete product to return. The creator's other logic works only with the product interface.
  • Abstract Factory (GoF). An interface that produces a family of related products that must be used together. For example, all the components for one payment provider.

How does it work?

// Simple factory
enum VehicleType { BIKE, CAR, TRUCK }
sealed interface Vehicle permits Bike, Car, Truck { VehicleType type(); }
record Bike(String plate) implements Vehicle { public VehicleType type() { return VehicleType.BIKE; } }
record Car(String plate) implements Vehicle { public VehicleType type() { return VehicleType.CAR; } }
record Truck(String plate) implements Vehicle { public VehicleType type() { return VehicleType.TRUCK; } }
final class VehicleFactory {
    static Vehicle create(VehicleType t, String plate) {
        return switch (t) { case BIKE -> new Bike(plate); case CAR -> new Car(plate); case TRUCK -> new Truck(plate); };
    }
}

// Factory Method: the report job's skeleton is fixed; subclasses choose the exporter
abstract class ReportJob {
    final void run(List<String> rows) { Exporter e = createExporter(); e.write(rows); }
    protected abstract Exporter createExporter();               // the factory method
}
interface Exporter { void write(List<String> rows); }
class CsvReportJob extends ReportJob { protected Exporter createExporter() { return rows -> System.out.println(String.join(",", rows)); } }

Example

// Abstract Factory: one provider's components must match each other
interface PaymentProviderFactory {
    PaymentGateway gateway();
    RefundClient refunds();
    WebhookVerifier webhookVerifier();
}
class RazorpayFactory implements PaymentProviderFactory {
    public PaymentGateway gateway() { return new RazorpayGateway(); }
    public RefundClient refunds() { return new RazorpayRefunds(); }
    public WebhookVerifier webhookVerifier() { return new RazorpayWebhookVerifier(); }
}
// Checkout code receives a PaymentProviderFactory and never mixes Razorpay's verifier with Stripe's gateway.

When would I use it?

  • When the concrete type depends on input or configuration — vehicle type, file format, provider.
  • When creating the object is complex.
  • When a family of objects must match each other.

In Spring, a Map<String, Bean> registry often replaces a hand-written factory (6.4).

What can go wrong?

  • Factories that grow a giant switch. Combine the factory with a registry (a map from key to implementation) instead.
  • Abstract factories for families that never actually change.

Interview questions

Q1. Factory Method vs Abstract Factory? Factory Method lets subclasses decide one product type. Abstract Factory creates a whole family of related products through one interface.

Q2. Factory vs Builder? A factory decides which class to create, usually in one step. A builder constructs one complex object step by step.

9.10 Builder

Why?

In simple words: When an object has many optional settings, a Builder lets you set them one by one, by name, and then gives you a finished object that cannot be changed.

Objects with many optional parameters usually end up in one of two bad shapes:

  1. Telescoping constructors — long constructors like new Notification(to, null, body, null, 5, true, null). You cannot tell which argument is which.
  2. Setter-based objects that can change. These can be left half-configured.

A builder fixes both. It gives readable, named, step-by-step construction, with validation. The end result is an immutable object — one that cannot change after it is built.

Think of ordering a dosa at a counter. You say "masala, extra butter, no onion". The cook checks the order makes sense, then hands you the finished plate. You don't get a half-made dosa.

What is happening internally?

  1. A static nested Builder class holds the settings while you configure them. These settings can change.
  2. Each setter-like method returns this. So you can chain calls one after another. This is called a fluent interface.
  3. build() checks rules that involve more than one field (cross-field rules).
  4. Then build() calls the private constructor of the immutable target class.

How does it work?

public final class Notification {
    enum Channel { SMS, EMAIL, PUSH }
    private final String to, subject, body; private final Channel channel; private final int priority; private final List<String> tags;

    private Notification(Builder b) {
        to = b.to; subject = b.subject; body = b.body; channel = b.channel; priority = b.priority; tags = List.copyOf(b.tags);
    }
    public static Builder to(String to) { return new Builder(to); }          // required field up front

    public static final class Builder {
        private final String to; private String subject = "", body = ""; private Channel channel = Channel.SMS;
        private int priority = 5; private final List<String> tags = new ArrayList<>();
        private Builder(String to) { this.to = Objects.requireNonNull(to); }
        public Builder subject(String s) { subject = s; return this; }
        public Builder body(String b) { body = b; return this; }
        public Builder channel(Channel c) { channel = c; return this; }
        public Builder priority(int p) { if (p < 1 || p > 10) throw new IllegalArgumentException("priority 1-10"); priority = p; return this; }
        public Builder tag(String t) { tags.add(t); return this; }
        public Notification build() {
            if (channel == Channel.EMAIL && subject.isBlank()) throw new IllegalStateException("email needs a subject");
            return new Notification(this);
        }
    }
}

Example

Notification n = Notification.to("+919876543210")
        .body("500 points credited")
        .channel(Notification.Channel.SMS)
        .priority(8)
        .tag("loyalty")
        .build();

(Lombok's @Builder generates this same pattern for you. Records with only a few fields usually don't need a builder.)

When would I use it?

  • Objects with 4 or more parameters, where several are optional.
  • Immutable configuration objects and request objects.
  • Test data builders.

What can go wrong?

  • No validation in build() — so invalid objects can be created again.
  • Builders for 2-field objects — just noise.
  • build() returning an object that can still change (mutable).

Interview questions

Q1. When do you use a Builder? For complex objects with many optional parameters. It gives readable construction, validation inside build(), and an immutable result.

9.11 Prototype

Why?

In simple words: Instead of building a complex object from zero each time, keep one ready-made sample and make copies of it, changing only what is different.

Sometimes creating an object from scratch is costly or complicated. For example, it is loaded from config, or it has many nested settings.

And you often need many similar copies with small changes. Examples: campaign templates, document templates, game units.

Think of a wedding invitation card. The printer designs one card. For each guest, he only changes the name — he does not redesign the card each time.

What is happening internally?

  1. You keep one fully configured object. This is the prototype.
  2. You create new objects by copying it.
  3. Then you customise the copy.

In Java, prefer copy constructors or copy()/with… methods. Avoid Object.clone(), because:

  • it makes a shallow copy by default,
  • it needs the Cloneable marker interface, and
  • it skips the constructor, so your constructor's checks don't run.

How does it work?

final class CampaignTemplate {
    private final String name; private final List<String> skus; private final Map<String, Integer> slabs;
    CampaignTemplate(String name, List<String> skus, Map<String, Integer> slabs) {
        this.name = name; this.skus = List.copyOf(skus); this.slabs = Map.copyOf(slabs);
    }
    CampaignTemplate copyFor(String newName) { return new CampaignTemplate(newName, skus, slabs); }   // deep enough: immutables
}

Example

CampaignTemplate diwali = festiveTemplate.copyFor("Diwali 2026"); — you set up one template, then stamp out a copy for each tenant or season.

When would I use it?

  • Templates.
  • Cloning objects that are already configured.
  • Undo snapshots (together with the Memento pattern).

What can go wrong?

  • Shallow copies share the nested objects that can change. So changing one copy also changes the other.
  • The pitfalls of clone() listed above.

Interview questions

Q1. Shallow vs deep copy in Prototype? A shallow copy shares the nested mutable objects with the original. A deep copy makes its own copies of them. I prefer immutable components or explicit copy constructors, so sharing is safe.

9.12 Adapter

Why?

In simple words: An Adapter is like a travel plug adapter. Your laptop charger has one shape, the wall socket has another, and the adapter sits in between so both work without changing either.

Sometimes you must connect to an outside API (a third-party API) or an old system (a legacy system). Its methods do not match what your code expects. For example:

  • An SMS vendor's SDK has strange method names and its own number-based error codes.
  • An old SOAP service sends and receives data in a different format.

You do not want the vendor's classes spread all over your business code. If they spread, changing the vendor later means touching many files. You want to swap vendors later with one small change.

What is happening internally?

An adapter is a small class that sits between your code and the vendor:

  1. It implements your interface. This is called the target.
  2. Inside, it holds the vendor class. This is called the adaptee.
  3. When your code calls the adapter, it translates the call for the vendor. It converts method names, parameters, data formats and errors.

This is composition: the adapter wraps (holds) the adaptee. It does not extend it.

How does it work?

RedemptionService only knows about the SmsSender interface. The adapter implements that interface and forwards each call to the vendor client.

RedemptionService ──► «interface» SmsSender ◄── LegacyGatewayAdapter ──► LegacyGatewayClient (vendor)

Example

In the code below, the adapter does two translations. First, it changes the phone format (removes the +). Second, it turns the vendor's number error code into a proper Java exception.

public interface SmsSender { void send(String phone, String text); }                // your port

class LegacyGatewayClient {                                                           // vendor API you can't change
    int push(String msisdn, byte[] payload, int flags) { return 0; }                  // 0 = OK, non-zero = error code
}

class LegacyGatewayAdapter implements SmsSender {
    private final LegacyGatewayClient client;
    LegacyGatewayAdapter(LegacyGatewayClient client) { this.client = client; }
    @Override public void send(String phone, String text) {
        String msisdn = phone.replace("+", "");                                      // format translation
        int rc = client.push(msisdn, text.getBytes(StandardCharsets.UTF_8), 0);
        if (rc != 0) throw new SmsDeliveryException("gateway returned " + rc);        // error translation
    }
}
class SmsDeliveryException extends RuntimeException { SmsDeliveryException(String m) { super(m); } }

When would I use it?

  • Every third-party integration: payment gateways, SMS/WhatsApp providers, partner APIs.
  • Connecting to legacy (old) systems.
  • Making several different providers fit behind one common interface.

What can go wrong?

  • Leaking vendor details. If vendor types or vendor exceptions come out of the adapter, your business code depends on the vendor again.
  • Business logic creeping in. Adapters slowly collect business rules. Keep them thin — they should only translate.

Interview questions

Q1. What does an Adapter do? It converts one interface into a different interface that the client expects. It wraps the incompatible class and translates the calls, the data and the errors.

9.13 Decorator

Why?

In simple words: A Decorator wraps an object to add one extra feature, like putting a gift wrap on a box. You can wrap the same box many times, and each layer adds something.

You want to add behaviour to an object. For example:

  • Add tax on top of a price.
  • Add logging or caching around a client.
  • Add compression around a stream.

You also want to choose the combination at runtime. Without Decorator, you would need a subclass for every combination: TaxedDiscountedPrice, LoggedCachedClient, and so on. The number of classes explodes.

What is happening internally?

A decorator has three properties:

  1. It implements the same interface as the object it wraps.
  2. It holds a reference to that wrapped object.
  3. It adds its own behaviour before or after passing the call on (delegating) to the wrapped object.

Because the decorator has the same interface, you can wrap a decorator inside another decorator. So decorators can be stacked.

Java I/O is the classic example: new BufferedReader(new InputStreamReader(new FileInputStream(f))). Each layer adds one feature.

How does it work?

The outer layer calls the inner layer, gets its result, and changes it. Here, the base price goes in, then the discount is applied, then GST is added.

GstTax ──► SchemeDiscount ──► BasePrice
price(o) = GstTax( SchemeDiscount( BasePrice(o) ) )

Example

The order is ₹100 (10,000 paise). The 10% discount makes it 9,000. Then 18% GST makes it 10,620.

interface PriceCalculator { long price(Order o); }
record Order(long amountPaise) {}

class BasePrice implements PriceCalculator { public long price(Order o) { return o.amountPaise(); } }

abstract class PriceDecorator implements PriceCalculator {
    protected final PriceCalculator inner;
    PriceDecorator(PriceCalculator inner) { this.inner = inner; }
}
class SchemeDiscount extends PriceDecorator {
    private final int pct;
    SchemeDiscount(PriceCalculator inner, int pct) { super(inner); this.pct = pct; }
    public long price(Order o) { return inner.price(o) * (100 - pct) / 100; }
}
class GstTax extends PriceDecorator {
    GstTax(PriceCalculator inner) { super(inner); }
    public long price(Order o) { return inner.price(o) * 118 / 100; }
}

PriceCalculator calc = new GstTax(new SchemeDiscount(new BasePrice(), 10));
calc.price(new Order(10_000));     // 10000 → 9000 → 10620

When would I use it?

  • Pricing pipelines (base price → discount → tax).
  • Common behaviour around clients, such as retry, cache and metrics. These are called cross-cutting concerns. Spring often does this with AOP proxies.
  • Stream processing.
  • Add-ons, such as an extra shot on a coffee (10.16).

What can go wrong?

  • Order matters. Tax-then-discount does not give the same result as discount-then-tax.
  • Long chains are hard to debug. You must step through many layers to find the bug.
  • Broken contract. A decorator might behave differently from what the interface promises.

Interview questions

Q1. Decorator vs inheritance? Decorators add behaviour at runtime by wrapping objects (composition), and you can combine them freely. Inheritance fixes behaviour at compile time, and you need a new subclass for every combination, so the number of classes explodes.

9.14 Proxy

Why?

In simple words: A Proxy is a stand-in that sits in front of the real object. Like a receptionist, it decides who gets through, may answer some questions itself, and only calls the real person when needed.

Sometimes you need to control access to an object without changing the object itself. You may want to:

  • Create it only when it is first needed (lazy loading).
  • Cache its results.
  • Check permissions before allowing a call.
  • Count or log calls.
  • Represent a remote object as if it were local.

A proxy stands in for the real object and does these jobs.

What is happening internally?

A proxy implements the same interface as the real object (the real subject). For every call, it decides whether, when and how to pass the call to the real object.

Common types of proxy:

  • Virtual proxy: creates the real object lazily, only on first use.
  • Caching proxy: remembers results and returns them without calling the real object again.
  • Protection proxy: checks access before forwarding the call.
  • Remote proxy: a local stub that hides a network call.
  • Smart reference: adds counting or logging.

You use proxies daily without noticing. Spring AOP, Hibernate lazy-loaded entities and Spring Data repositories are all proxies (6.7, 7.8).

How does it work?

The structure looks the same as Decorator. The difference is the purpose (intent):

  • A decorator adds features. The client builds the chain of decorators itself.
  • A proxy controls access. It usually hides the fact that it exists — the client thinks it is talking to the real object.

Example

CachingCatalogProxy saves each product after the first slow network call. TenantGuardProxy blocks SKUs that are not in this tenant's catalogue.

interface Catalog { Product get(String sku); }
record Product(String sku, String name) {}

class RemoteCatalog implements Catalog {                               // slow: network call
    public Product get(String sku) { return new Product(sku, "loaded-" + sku); }
}
class CachingCatalogProxy implements Catalog {
    private final Catalog real;
    private final Map<String, Product> cache = new ConcurrentHashMap<>();
    CachingCatalogProxy(Catalog real) { this.real = real; }
    public Product get(String sku) { return cache.computeIfAbsent(sku, real::get); }
}
class TenantGuardProxy implements Catalog {                            // protection proxy
    private final Catalog real; private final Set<String> allowedSkus;
    TenantGuardProxy(Catalog real, Set<String> allowed) { this.real = real; this.allowedSkus = allowed; }
    public Product get(String sku) {
        if (!allowedSkus.contains(sku)) throw new SecurityException("sku not in tenant catalogue");
        return real.get(sku);
    }
}

When would I use it?

  • Caching layers.
  • Lazy loading of heavy objects.
  • Access control.
  • Stubs for remote services.
  • Wrappers for metrics and tracing.

What can go wrong?

  • Unbounded caching. A caching proxy with no size limit keeps growing. This is a memory leak.
  • Hidden cost. A simple-looking method call may actually be an expensive remote call behind the proxy.
  • Self-invocation. When an object calls its own method (this.method()), the call does not go through the proxy. So the proxy's behaviour (for example, a transaction) is skipped.

Interview questions

Q1. Proxy vs Decorator vs Adapter? A Proxy keeps the same interface and controls access. A Decorator keeps the same interface and adds behaviour. An Adapter changes the call to a different interface.

9.15 Facade

Why?

In simple words: A Facade is one simple front door to a complicated system. Like a hotel reception desk, you make one request and it coordinates housekeeping, kitchen and billing for you.

Placing an order touches five subsystems: inventory reservation, pricing, payment, loyalty accrual and notification.

Now imagine every client does this coordination itself — the mobile API, the partner API and the admin tool. Two problems follow:

  1. The same coordination code is copied in three places.
  2. Every client depends on the details of all five subsystems. This is called tight coupling.

What is happening internally?

A facade gives one simple, high-level method over a complex subsystem. (Coarse-grained means one big call instead of many small ones.) The facade makes all the inner calls in the right order.

The subsystems are still there. Code that really needs them can still call them directly.

How does it work?

All three clients call one method. The facade talks to the five subsystems.

Mobile API ─┐
Partner API ─┼─► CheckoutFacade.placeOrder() ─► Inventory · Pricing · Payment · Loyalty · Notification
Admin tool  ─┘

Example

The steps are:

  1. Reserve the stock.
  2. Calculate the total price.
  3. Charge the payment.
  4. Confirm (commit) the stock reservation.
  5. Add loyalty points.
  6. Send the notification.

If anything fails, the catch block releases the reserved stock. This undo step is called a compensation.

class CheckoutFacade {
    private final InventoryService inventory; private final PricingService pricing;
    private final PaymentService payment; private final LoyaltyService loyalty; private final Notifier notifier;
    CheckoutFacade(InventoryService i, PricingService p, PaymentService pay, LoyaltyService l, Notifier n) {
        inventory = i; pricing = p; payment = pay; loyalty = l; notifier = n;
    }
    public OrderResult placeOrder(Cart cart, String paymentMethod) {
        Reservation r = inventory.reserve(cart.items());
        try {
            long total = pricing.total(cart);
            Receipt receipt = payment.charge(cart.customerId(), total, paymentMethod);
            inventory.commit(r);
            loyalty.accrue(cart.customerId(), total);
            notifier.orderPlaced(cart.customerId(), receipt);
            return OrderResult.ok(receipt);
        } catch (RuntimeException e) {
            inventory.release(r);                       // compensate
            throw e;
        }
    }
}

When would I use it?

  • Application services that coordinate several domain services.
  • A simple SDK on top of a complex library.
  • BFF layers (Backend for Frontend — one backend API shaped for one specific app).

What can go wrong?

  • God class. The facade slowly collects all the business logic and becomes one huge class.
  • Hidden distributed-transaction problems. If the subsystems are separate microservices, one try/catch is not enough. You need a saga — a series of local steps, each with an undo step (11.15).

Interview questions

Q1. What problem does a Facade solve? It hides a complex subsystem behind one simple interface. This reduces coupling, and clients no longer copy the same coordination code.

9.16 Composite

Why?

In simple words: Composite lets you treat one item and a group of items in the same way. A folder and a file both answer "what is your size?" — the folder just asks its children and adds up.

Some data is a tree, where groups and single items must be handled the same way. Examples:

  • Folders and files.
  • Organisation charts.
  • Menus.
  • Product bundles.
  • Rule conditions joined with AND/OR.

Without Composite, the client code is full of checks like "if it is a group, loop over it; else handle the single item".

What is happening internally?

There is one common interface, called the component. Two kinds of classes implement it:

  • Leaves: single items with no children.
  • Composites: containers that hold child components.

When you call an operation on a composite, it calls the same operation on each child. Then it combines the results. Because a child can itself be a composite, this happens recursively down the tree.

How does it work?

The tree below means: sales must be at least 50,000, AND (visits at least 20 OR at least 5 new outlets).

AllOf ─┬─ MinAmount(50000)
       └─ AnyOf ─┬─ MinVisits(20)
                 └─ MinNewOutlets(5)
test(order) = MinAmount.test && (MinVisits.test || MinNewOutlets.test)

Example

AllOf and AnyOf are composites. MinSales and MinVisits are leaves. The client just calls scheme.test(...) and does not care which is which.

interface Condition { boolean test(Metrics m); }
record Metrics(double sales, int visits, int newOutlets) {}
record MinSales(double min) implements Condition { public boolean test(Metrics m) { return m.sales() >= min; } }
record MinVisits(int min) implements Condition { public boolean test(Metrics m) { return m.visits() >= min; } }
record AllOf(List<Condition> parts) implements Condition { public boolean test(Metrics m) { return parts.stream().allMatch(c -> c.test(m)); } }
record AnyOf(List<Condition> parts) implements Condition { public boolean test(Metrics m) { return parts.stream().anyMatch(c -> c.test(m)); } }

Condition scheme = new AllOf(List.of(new MinSales(50_000), new AnyOf(List.of(new MinVisits(20), new MinVisits(30)))));
scheme.test(new Metrics(81_000, 22, 1));      // true

When would I use it?

  • Rules engines (10.12).
  • File systems.
  • Permission hierarchies.
  • Bundle pricing.
  • UI trees (a panel holding buttons and other panels).

What can go wrong?

  • Deep recursion. A very deep tree can cause a stack overflow.
  • Type checks leaking into clients. If clients ask "is this a composite?", the pattern is not doing its job.
  • Cycles. If a node ends up as its own child, recursion never ends.

Interview questions

Q1. Where have you seen Composite? In rule trees that combine conditions with AND/OR, such as incentive schemes. Also in file systems and organisation charts.

9.17 Strategy

Why?

In simple words: Strategy means "put each way of doing a job in its own class, and plug in the one you need". Like choosing Ola, Uber or auto for the same trip — the trip stays the same, only the method changes.

Often one step of the logic changes depending on the situation. Examples:

  • Parking fee depends on vehicle type.
  • Split rules in Splitwise (equal, exact, percentage).
  • Eviction policy in a cache (LRU, LFU).
  • Rate-limiting algorithm.
  • Pricing per tenant.

If you hard-code all of these with if/else or switch, every new variant means editing old code. This breaks OCP (the Open/Closed Principle: open for adding, closed for editing).

Strategy makes each algorithm a separate, pluggable object. It is the most-used pattern in LLD rounds.

What is happening internally?

There are three parts:

  1. A strategy interface declares the operation.
  2. Concrete strategies each implement it in their own way.
  3. The context holds a strategy and passes the work to it. The strategy is either injected or picked from a registry (a map of strategies).

It is simply polymorphism plus composition.

How does it work?

The parking lot does not know how fees are calculated. It just asks its FeeStrategy.

ParkingLot (context) ──► «interface» FeeStrategy ◄── HourlyFee · FlatDailyFee · WeekendFee

Example

HourlyFee rounds up to whole hours, with a minimum of one hour. ParkingTicketing keeps a map from vehicle type to fee strategy.

interface FeeStrategy { long fee(Duration parked); }
class HourlyFee implements FeeStrategy {
    private final long perHour;
    HourlyFee(long perHour) { this.perHour = perHour; }
    public long fee(Duration d) { return Math.max(1, (d.toMinutes() + 59) / 60) * perHour; }   // ceil hours, min 1
}
class FlatDailyFee implements FeeStrategy {
    public long fee(Duration d) { return Math.max(1, d.toDays() + 1) * 500; }
}

class ParkingTicketing {
    private final Map<VehicleType, FeeStrategy> feeByType;
    ParkingTicketing(Map<VehicleType, FeeStrategy> feeByType) { this.feeByType = feeByType; }
    long charge(VehicleType t, Duration d) { return feeByType.get(t).fee(d); }
}
enum VehicleType { BIKE, CAR }
// new ParkingTicketing(Map.of(VehicleType.BIKE, new HourlyFee(10), VehicleType.CAR, new HourlyFee(40)))

How to justify it in an interview: "I used Strategy for fees because pricing varies independently of the parking flow, and I want to add weekend or event pricing without modifying ticketing logic."

When would I use it?

Use it for any behaviour that has several swappable versions:

  • Pricing, discounts, payouts.
  • Routing, ranking.
  • Retry policies.
  • Serialisation formats (JSON, XML, CSV).

Simple strategies can just be lambdas, for example Function<Duration, Long>.

What can go wrong?

  • Too many strategies. Making a new class for a tiny difference is overkill. A parameter would do.
  • The giant switch moves. The client still picks the strategy with a big switch. Use a registry or a factory instead.

Interview questions

Q1. Strategy vs State? They have the same structure. In Strategy, the client chooses the strategy, and it stays fixed for the whole operation. In State, the state objects themselves move the context to other states as events happen.

Q2. How does Strategy support OCP? A new algorithm is just a new class, registered with the context. The context and the existing strategies do not change.

9.18 Observer

Why?

In simple words: Observer is a subscription system. Interested parties sign up once, and when something happens, everyone on the list is told — like a WhatsApp group getting a message.

When an order is placed, many things must happen:

  • Loyalty must add points.
  • Inventory must update.
  • Notifications must go out.
  • Analytics must record it.

If OrderService calls each of these directly, it depends on all of them. Every new reaction means editing OrderService again.

Observer fixes this. Interested parties subscribe to events, and OrderService just announces what happened.

What is happening internally?

  1. The subject keeps a list of observers (also called listeners).
  2. When an event happens, the subject notifies each observer in the list.

The direction of dependency is important. Observers depend on the subject's event type. The subject does not depend on the observers.

  • Inside one service (in-process): Spring gives you ApplicationEventPublisher and @EventListener (6.10).
  • Across services: the same idea becomes pub/sub messaging, for example Kafka topics (11.12).

How does it work?

OrderService ──publish(OrderPlaced)──► [LoyaltyListener, InventoryListener, NotificationListener, AnalyticsListener]

Example

Note two details in the code. First, CopyOnWriteArrayList lets you loop safely even if someone subscribes or unsubscribes at the same time. Second, each listener call is inside its own try/catch, so one bad listener cannot break the others or the order.

record OrderPlaced(String orderId, String outletId, long amountPaise) {}
interface OrderListener { void onOrderPlaced(OrderPlaced e); }

class OrderService {
    private final List<OrderListener> listeners = new CopyOnWriteArrayList<>();   // safe iteration while (un)subscribing
    void subscribe(OrderListener l) { listeners.add(l); }
    void unsubscribe(OrderListener l) { listeners.remove(l); }
    void place(String orderId, String outletId, long amount) {
        // ... persist order ...
        OrderPlaced e = new OrderPlaced(orderId, outletId, amount);
        for (OrderListener l : listeners) {
            try { l.onOrderPlaced(e); }
            catch (RuntimeException ex) { /* log; one bad listener must not break others or the order */ }
        }
    }
}

When would I use it?

  • Separating side effects from the main action.
  • UI updates.
  • Domain events inside one service.
  • Low-stock alerts (10.16).

Use durable messaging (such as Kafka) when the observers live in other services, or when they must never miss an event.

What can go wrong?

  • Listener exceptions break the subject if not caught.
  • Slow listeners that run synchronously block the caller.
  • Memory leaks from listeners that are never unsubscribed.
  • Unclear ordering — you cannot be sure which listener runs first.
  • Lost events on crash — in-memory events disappear if the process dies, when they should have been stored durably.

Interview questions

Q1. Where is Observer used in Java/Spring? Spring application events and listeners, GUI listeners, and reactive streams. Across services, it becomes pub/sub messaging.

9.19 State

Why?

In simple words: The State pattern gives each status its own class, and that class decides what is allowed next. Like a railway ticket: a "confirmed" ticket can be cancelled with refund, but a "journey done" ticket cannot.

Some objects behave differently depending on their current state. Examples: orders, vending machines, elevators, tickets and trips.

For example, you can cancel a paid order (with a refund), but you cannot cancel a shipped one.

If you write if (status == …) inside every method, two problems follow:

  1. The rules for moving between states (transitions) are scattered everywhere.
  2. It is easy to make an illegal transition by mistake.

What is happening internally?

  1. Each state is its own class. All states implement one common interface, with one method per event (pay, ship, cancel).
  2. The object (the context) holds the current state object.
  3. When an event arrives, the context passes it to the current state.
  4. The state handles only the events it allows. It returns the next state — or rejects the event.

For simple machines, you do not need classes. An enum with a transition table is enough.

How does it work?

CREATED ──pay──► PAID ──ship──► SHIPPED ──deliver──► DELIVERED
   │               │
   └──cancel──► CANCELLED ◄──cancel (refund)

Example

The interface has default methods that throw an error. Each state class overrides only the events it allows. So any event not allowed fails automatically.

interface OrderState {
    default OrderState pay(OrderCtx c)    { throw new IllegalStateException("cannot pay in " + name()); }
    default OrderState ship(OrderCtx c)   { throw new IllegalStateException("cannot ship in " + name()); }
    default OrderState cancel(OrderCtx c) { throw new IllegalStateException("cannot cancel in " + name()); }
    String name();
}
interface OrderCtx { void charge(); void refund(); }

final class Created implements OrderState {
    public OrderState pay(OrderCtx c) { c.charge(); return new Paid(); }
    public OrderState cancel(OrderCtx c) { return new Cancelled(); }
    public String name() { return "CREATED"; }
}
final class Paid implements OrderState {
    public OrderState ship(OrderCtx c) { return new Shipped(); }
    public OrderState cancel(OrderCtx c) { c.refund(); return new Cancelled(); }
    public String name() { return "PAID"; }
}
final class Shipped implements OrderState { public String name() { return "SHIPPED"; } }
final class Cancelled implements OrderState { public String name() { return "CANCELLED"; } }

// Enum alternative for simple machines
enum Status {
    CREATED, PAID, SHIPPED, CANCELLED;
    private static final Map<Status, Set<Status>> ALLOWED = Map.of(
            CREATED, Set.of(PAID, CANCELLED), PAID, Set.of(SHIPPED, CANCELLED), SHIPPED, Set.of(), CANCELLED, Set.of());
    Status to(Status next) {
        if (!ALLOWED.get(this).contains(next)) throw new IllegalStateException(this + " → " + next);
        return next;
    }
}

In a database, enforce transitions with a conditional update: UPDATE orders SET status='PAID' WHERE id=? AND status='CREATED'. The WHERE status='CREATED' part makes it safe:

  • It is atomic — the check and the change happen as one step.
  • It is idempotent — running it twice has the same effect as running it once. The second run simply updates zero rows.

When would I use it?

Use it for lifecycles where each state has its own rules:

  • Orders and payments.
  • Trips (10.17).
  • Vending machines (10.7).
  • Elevators (10.8).
  • Approval workflows.
  • Ticket holds (10.10).

What can go wrong?

  • Huge state classes. One state class grows too big.
  • Scattered transitions. Transition rules spread across many states and services.
  • Concurrent transitions without atomicity. Two threads both move PAID → CANCELLED at the same time, and the customer is refunded twice.

Interview questions

Q1. When do you use the State pattern instead of an enum? When each state has its own distinct behaviour and transitions involve real logic. For a simple status machine, an enum with a transition table is enough.

9.20 Command

Why?

In simple words: Command turns an action into an object — like a written order slip in a restaurant. Because it is written down, you can queue it, keep a record of it, repeat it, or cancel it.

Sometimes you want to treat an action as data. Then you can:

  • Put it in a queue.
  • Log it.
  • Retry it.
  • Schedule it for later.
  • Undo it.

Many systems need this:

  • Text editors (undo/redo).
  • Job queues.
  • Macro recording.
  • Ledgers, where accrue, redeem and reverse are stored as recorded operations.

What is happening internally?

A command object packs one request into an object (encapsulates it). It holds:

  • What to do.
  • On which object (the receiver).
  • With which parameters.
  • Optionally, how to undo it.

There are two other roles:

  • The invoker runs commands and keeps the history.
  • The receiver does the real work.

How does it work?

The editor keeps a stack of commands it has run. Undo takes the last one off the stack and calls its undo().

Editor (invoker) — history stack: [AddText("Hello"), AddText(" World")]
undo() → pop → AddText(" World").undo()

Example

The editor uses two stacks:

  1. Running a command pushes it on the undo stack and clears the redo stack.
  2. Undo pops from the undo stack, reverses the command, and pushes it on the redo stack.
  3. Redo pops from the redo stack, runs it again, and pushes it back on the undo stack.
interface Command { void execute(); void undo(); }

class AddText implements Command {
    private final StringBuilder doc; private final String text;
    AddText(StringBuilder doc, String text) { this.doc = doc; this.text = text; }
    public void execute() { doc.append(text); }
    public void undo() { doc.setLength(doc.length() - text.length()); }
}
class Editor {
    private final StringBuilder doc = new StringBuilder();
    private final Deque<Command> undo = new ArrayDeque<>(), redo = new ArrayDeque<>();
    void run(Command c) { c.execute(); undo.push(c); redo.clear(); }
    void undo() { if (!undo.isEmpty()) { Command c = undo.pop(); c.undo(); redo.push(c); } }
    void redo() { if (!redo.isEmpty()) { Command c = redo.pop(); c.execute(); undo.push(c); } }
    String text() { return doc.toString(); }
    AddText add(String t) { return new AddText(doc, t); }
}
// Editor e = new Editor(); e.run(e.add("Hello")); e.run(e.add(" World")); e.undo(); → "Hello"

When would I use it?

  • Undo/redo.
  • Job and task queues.
  • Scheduled operations.
  • Operations that must be recorded in an audit log.
  • Compensating actions in sagas — each step has an "execute" and a "compensate" (undo).
  • Command handlers in CQRS (a design that separates writes/commands from reads/queries).

What can go wrong?

  • Undo is not a true reverse. If other changes happened since, simply undoing may give the wrong result.
  • Unbounded history. The history stack grows forever and uses up memory.
  • Heavy commands. Commands that hold large state use a lot of memory.

Interview questions

Q1. How would you implement undo/redo? Make each action a command with execute and undo. Keep an undo stack and a redo stack. When a new command is executed, clear the redo stack.

9.21 Chain of Responsibility

Why?

In simple words: Chain of Responsibility passes a request through a line of checkers, one after another. Like airport security: ID check, then baggage scan, then body scan — anyone can stop you, and you can add or reorder checks easily.

A request must pass through a series of checks or handlers. For example:

  • Authentication.
  • Validation.
  • Fraud check.
  • Geofence check (is the user inside the allowed area?).
  • Photo-evidence check.

The set of steps and their order change over time. If you hard-code all of them in one method, the method becomes long and hard to change.

What is happening internally?

  1. All handlers implement one common interface.
  2. They are linked in a chain.
  3. Each handler does one of two things. Either it handles the request and stops the chain, or it does its part and passes the request to the next handler.

Servlet filters and Spring Security's filter chain both use this pattern.

How does it work?

claim ─► GeoFenceCheck ─► PhotoCheck ─► DuplicateClaimCheck ─► accepted
             └─ reject          └─ reject        └─ reject

Example

Each check throws an exception to reject the claim. If every check passes, the claim is accepted. The list order is the chain order, and you can configure it per tenant.

record Claim(String outletId, boolean insideGeofence, List<String> photos) {}

interface ClaimCheck { void check(Claim c); }
class GeoFenceCheck implements ClaimCheck {
    public void check(Claim c) { if (!c.insideGeofence()) throw new IllegalArgumentException("outside geofence"); }
}
class PhotoCheck implements ClaimCheck {
    public void check(Claim c) { if (c.photos().isEmpty()) throw new IllegalArgumentException("photo evidence required"); }
}
class ClaimValidator {
    private final List<ClaimCheck> chain;                     // order matters; configurable per tenant
    ClaimValidator(List<ClaimCheck> chain) { this.chain = List.copyOf(chain); }
    void validate(Claim c) { for (ClaimCheck check : chain) check.check(c); }
}

(The classic version links each handler to the next one directly. A simple list of handlers, as above, is the modern and simpler form.)

When would I use it?

  • Validation pipelines, such as Perfect Store evidence checks.
  • Request filters.
  • Approval workflows (escalate to the next approver).
  • Logging levels.
  • Middleware.

What can go wrong?

  • Unhandled requests. A request reaches the end of the chain and nobody handled it — silently.
  • Hidden order rules. One handler depends on another running first, but nobody wrote that down.
  • Hard debugging. Long chains are hard to trace. Log which handler made the decision.

Interview questions

Q1. Where is Chain of Responsibility used in Spring? Servlet filters and the Spring Security filter chain. HandlerInterceptors work in a similar way.

9.22 Template Method

Why?

In simple words: Template Method fixes the order of steps in a parent class and lets child classes fill in only the steps that differ. Like a standard form where the layout is printed and you only fill in the blanks.

Several processes often share the same skeleton (the same overall steps) but differ in a few steps. For example:

  • Every report job fetches data, transforms it, and publishes it.
  • Every import validates, parses, saves and audits.

If you copy the skeleton into each job, the fixed parts are duplicated. Over time the copies drift apart and behave differently.

What is happening internally?

  1. An abstract base class defines the algorithm in one final method. This is the template method. Because it is final, subclasses cannot change the order.
  2. The template method calls abstract steps. Subclasses must implement these.
  3. It may also call hooks. These are optional steps with a default behaviour that subclasses can override.

This version is based on inheritance. There is also a callback-based version, where you pass in lambdas instead of subclassing. Spring's JdbcTemplate and TransactionTemplate use this callback version.

How does it work?

run() is the fixed skeleton. fetch and publish are required steps. transform has a default. shouldPublish is a hook.

abstract class ReportJob {
    public final void run() {                                  // fixed skeleton
        var data = fetch();
        var rows = transform(data);
        if (shouldPublish(rows)) publish(rows);
    }
    protected abstract List<Map<String, Object>> fetch();     // required steps
    protected abstract void publish(List<String> rows);
    protected List<String> transform(List<Map<String, Object>> d) { return d.stream().map(Object::toString).toList(); }  // default
    protected boolean shouldPublish(List<String> rows) { return !rows.isEmpty(); }                                      // hook
}

Example

class DailyRedemptionReport extends ReportJob { … fetch from ClickHouse, publish to S3 … } — you write only the steps that change.

When would I use it?

  • Batch jobs.
  • Importers.
  • Framework extension points, such as OncePerRequestFilter.doFilterInternal and AbstractList.

What can go wrong?

  • Deep class hierarchies. Many levels of inheritance become hard to follow.
  • Rigid skeleton. A subclass needs to change the skeleton itself. In that case, prefer composition — use Strategy for the steps instead.

Interview questions

Q1. Template Method vs Strategy? Template Method keeps a fixed skeleton and lets subclasses change individual steps (inheritance). Strategy swaps the whole algorithm by plugging in a different object (composition).

9.23 Specification, and patterns to recognise

Why?

In simple words: Specification turns each business rule into a small object that answers "yes or no". You can then join rules with AND, OR and NOT, like building blocks.

Consider this business rule: "eligible outlet = active AND in region North AND (sales > X OR new outlet)".

Rules like this need to be:

  • Combined with other rules.
  • Reused in many places.
  • Tested on their own.
  • Sometimes turned into database queries.

Specification makes each rule an object that you can combine (compose).

What is happening internally?

A Specification<T> has:

  • A method isSatisfiedBy(T) that returns true or false.
  • Combinators and, or and not that join it with other specifications.

Spring Data JPA's Specification<T> works a little differently. Instead of checking objects in memory, it builds a JPA Criteria predicate (a condition). So the combined rules become a SQL WHERE clause and run in the database.

How does it work?

Each small rule is one line. Then eligible joins them together.

interface Spec<T> {
    boolean test(T t);
    default Spec<T> and(Spec<T> o) { return t -> test(t) && o.test(t); }
    default Spec<T> or(Spec<T> o)  { return t -> test(t) || o.test(t); }
    default Spec<T> not()          { return t -> !test(t); }
}
record Outlet(boolean active, String region, double sales, boolean isNew) {}
Spec<Outlet> active = Outlet::active;
Spec<Outlet> north = o -> o.region().equals("NORTH");
Spec<Outlet> bigOrNew = ((Spec<Outlet>) o -> o.sales() > 50_000).or(Outlet::isNew);
Spec<Outlet> eligible = active.and(north).and(bigOrNew);

Example

The same idea in Spring Data JPA. Here the filter runs inside the database, not in Java memory.

// Spring Data JPA: same idea, executed in the database
static Specification<OutletEntity> inRegion(String r) { return (root, q, cb) -> cb.equal(root.get("region"), r); }
static Specification<OutletEntity> isActive() { return (root, q, cb) -> cb.isTrue(root.get("active")); }
// outletRepo.findAll(inRegion("NORTH").and(isActive()))   // repo extends JpaSpecificationExecutor

Other patterns to recognise (one sentence each in interviews): - Iterator: walk through a collection without showing how it is stored inside (Iterator<T>). - Mediator: objects talk through one central coordinator instead of talking to each other directly (an elevator dispatcher, a chat room). - Visitor: add new operations over a fixed set of types without changing those types. In modern Java, sealed types plus a pattern-matching switch do this more simply (3.8). - Memento: save an object's state and restore it later (undo snapshots). - Flyweight: share common, unchanging (immutable) data among many objects to save memory (the Integer cache). - Bridge: separate an abstraction from its implementation, so both can change independently (notification type × delivery channel).

When would I use it?

  • Eligibility rules.
  • Dynamic search filters.
  • Policy checks.
  • Building queries.

What can go wrong?

  • Filtering in memory instead of SQL. Running in-memory specifications on large datasets is slow. Large data should be filtered in the database.
  • Too clever. Combinator code can become so clever that nobody can read it.

Interview questions

Q1. What is the Specification pattern? It turns business rules into predicate objects (yes/no checks) that you can combine with and, or and not. You can reuse them in memory or turn them into database queries, as Spring Data JPA Specifications do.

9.24 Supporting principles interviewers listen for

Why?

In simple words: Patterns are tools; principles tell you when to use a tool and when to leave it in the box. Knowing when to stop adding layers is as much a senior skill as knowing how to add them.

If you name these principles at the right moment, the interviewer sees good judgement. Knowing when to stop abstracting is as senior a skill as knowing how to abstract.

What is happening internally?

  • DRY (Don't Repeat Yourself): every piece of knowledge should live in one official place. If a rule is copied, the copies drift apart over time.
  • KISS (Keep It Simple): choose the simplest design that meets the requirements.
  • YAGNI (You Aren't Gonna Need It): do not build for future needs that may never come.
  • Law of Demeter: talk only to your direct collaborators. order.customer().address().city() ties you to three classes. Instead, ask order.shippingCity().
  • Tell, don't ask: tell an object to do something. Do not pull out its data and make the decision outside it.
  • High cohesion, low coupling: keep related code together inside a class; keep classes loosely connected to each other.
  • Composition over inheritance (1.11): build behaviour by holding other objects, rather than by extending classes.
  • Program to interfaces, not implementations: depend on the interface type, not on a concrete class.
  • Fail fast: check inputs early, and throw clear exceptions.
  • Immutability by default for values and events (1.14): once created, they do not change.

How does it work?

Use these principles to explain your decisions out loud. For example: "I'm not adding a plugin system for payment types yet — YAGNI; but the gateway is behind an interface, so adding one later is cheap."

Example

In the "Ask" version, outside code reads the balance and decides. In the "Tell" version, the account checks its own rule.

// Ask (violates tell-don't-ask and Demeter)
if (account.getBalance() >= points) account.setBalance(account.getBalance() - points);
// Tell
account.debit(points);         // the account enforces its own rule

When would I use it?

In every design discussion and every code review.

What can go wrong?

  • Wrong DRY. Two pieces of code only look similar but represent different knowledge. Merging them couples unrelated things.
  • YAGNI as an excuse. Someone uses YAGNI to skip extension points that are clearly needed.

Interview questions

Q1. How do you avoid over-engineering in an LLD round? Build the stated requirements simply (KISS/YAGNI). But put abstractions at the obvious places of variation that the interviewer mentioned. Then explain how you would extend the design.

9.25 How to run an LLD interview (60–90 minutes)

Why?

In simple words: Follow a fixed timetable in the LLD round — requirements, classes, patterns, code, demo, extensions — so you never panic and always end with working code.

Most candidates fail LLD rounds because of poor process, not because they lack knowledge. They start coding too early, or design for too long, or run out of time with nothing working.

A fixed routine keeps you calm. It also keeps your thinking visible to the interviewer, and keeps you on time.

What is happening internally?

The interviewer scores you on:

  • Clarifying requirements.
  • Modelling the entities.
  • Using OOP and SOLID.
  • Choosing suitable patterns.
  • Working code.
  • Handling edge cases and concurrency.
  • Extensibility (how easily new features fit in).
  • Communication.

Machine-coding rounds (Flipkart, Swiggy, PhonePe, Uber style) give heavy weight to runnable, modular code.

How does it work?

Minutes Step What you do and say
0–7 Requirements Say 4–6 core use cases out loud and write them down. Confirm what is out of scope. Ask about concurrency, persistence (in-memory is usually fine) and scale
7–15 Entities and relationships Nouns become classes, enums and records; verbs become methods. Draw a quick class diagram (9.2)
15–20 Interfaces and patterns Define the public API of the main service. Point out where things vary and which pattern you will use there, with a one-line reason
20–70 Code Models → interfaces → in-memory repositories → core service → one or two strategies → a main demo. Get the happy path working end to end first
70–80 Walkthrough Run a scenario. Handle invalid input and edge cases
80–90 Extensions Concurrency (what is shared, how you protect it), new features (where they plug in), persistence, tests
