1.1 How Java runs: JDK, JRE, JVM, bytecode and JIT

Why?

In simple words: Java compiles your code into a common "middle language" called bytecode. A program called the JVM runs that bytecode on any machine, and it speeds up the busy parts while the program runs.

A C or C++ program is compiled straight into machine code. That machine code is for one CPU and one operating system. So a binary built for Linux x86 won't run on Windows or on ARM.

Java was designed for "write once, run anywhere". You compile once, and the same file runs on any machine.

Java also wanted two more things: - Memory safety — no pointer arithmetic, and no manual free. - Optimisation while the program runs.

Both need a layer between your code and the hardware. That layer is the Java Virtual Machine (JVM).

Think of a film with subtitles. The film (bytecode) is the same in every country. Only the subtitle track (the JVM) changes for each local audience.

What is happening internally?

 Hello.java ──javac──► Hello.class (bytecode) ──► JVM
                                                  ├─ Class loader: finds and loads .class files
                                                  ├─ Bytecode verifier: rejects unsafe/corrupt code
                                                  ├─ Interpreter: executes bytecode instruction by instruction
                                                  ├─ JIT compiler (C1, C2): turns HOT methods into native machine code
                                                  ├─ Garbage collector: frees unreachable objects
                                                  └─ Runtime data areas: heap, stacks, metaspace
  • Bytecode is a set of instructions for an imaginary stack machine. A stack machine does its work by pushing values onto a stack and popping them off.
  • For example, iload_1 pushes local variable 1 onto the operand stack.
  • iadd pops two ints and pushes their sum.
  • Bytecode doesn't depend on any real CPU.
  • JVM is a program that understands bytecode. A separate JVM is written for each OS and CPU. This is where portability comes from: the bytecode is the same everywhere, and only the JVM differs.
  • JRE = JVM + the standard library (java.lang, java.util, …).
  • JDK = JRE + developer tools (javac, jshell, jar, jcmd, jstack, jmap, jfr). Since Java 11, you install only the JDK.
  • JIT (Just-In-Time) compiler — it compiles code to machine code while the program runs: 1. The JVM counts how often each method and loop runs. 2. When a method crosses a threshold, C1 compiles it to native code. C1 compiles fast but optimises lightly. 3. If the method stays busy ("hot"), C2 compiles it again. C2 is slower to compile but optimises heavily: inlining (copying a called method's body into the caller), loop unrolling, and escape analysis (spotting objects that never leave a method). 4. This two-level setup is called tiered compilation.

How does it work?

  1. javac Hello.java reads the source, checks the types, and writes Hello.class. No machine code is made yet.
  2. java Hello starts the JVM. The class loader loads Hello.class. It also loads what it needs, such as java.lang.Object and String.
  3. The verifier checks that the bytecode is type-safe. For example, no jumping into the middle of an instruction, and no treating an int as a reference.
  4. main starts running in the interpreter. The interpreter runs bytecode one instruction at a time.
  5. Counters go up as code runs. Hot methods are queued for JIT compilation on background threads. When compilation finishes, later calls jump to the native code.
  6. Sometimes an optimisation assumption breaks. For example, the JIT turned a call into a direct call because there was only one possible target. Then a new subclass is loaded, and now there are two targets. When this happens, the JVM deoptimises — it throws away that compiled code and goes back to the interpreter. It may recompile later.

Example

public class Hello {
    static int square(int x) { return x * x; }
    public static void main(String[] args) {
        long sum = 0;
        for (int i = 0; i < 50_000_000; i++) sum += square(i % 1000);  // square() becomes hot -> JIT-compiled, then inlined
        System.out.println(sum);
    }
}
// javac Hello.java && java Hello
// javap -c Hello      -> prints the bytecode of square():  iload_0, iload_0, imul, ireturn
// java -XX:+PrintCompilation Hello   -> shows square() being compiled by tier 3 (C1) then tier 4 (C2)

What happens when it runs: 1. The first few thousand loop iterations run in the interpreter. 2. Once square crosses the C1 threshold, it is compiled. 3. Once the loop is hot, C2 recompiles main with square inlined. Now there is no method call at all, so no call overhead.

This is why a "warmed-up" Java service is faster than one that just started.

When would I use it?

You use this every day without thinking about it. It matters in interviews and in production when you: - explain why the first requests after a deploy are slow (the JIT and caches are still cold), and why load tests need a warm-up period; - use javap -c to see what the compiler really produced (for string concatenation, autoboxing, lambdas); - choose startup optimisations (Class Data Sharing, GraalVM native image) for short-lived jobs or serverless functions.

What can go wrong?

  • Micro-benchmarks lie. Say you time a loop with System.nanoTime(). You may be measuring the interpreter, or JIT compilation itself, or dead-code elimination. (Dead-code elimination means the JIT removes code whose result is never used — so you end up timing nothing.) Use JMH for benchmarks.
  • "Java is slow" is usually a cold-start problem or a badly configured GC. It is rarely a JIT problem.
  • Version mismatch. Code compiled for Java 21 (class file version 65) fails on a Java 17 JVM with UnsupportedClassVersionError. The build target and the runtime image must match.

Interview questions

Q1. Is Java compiled or interpreted? Both. javac compiles source code ahead of time into bytecode, which is the same on every platform. At runtime, the JVM interprets that bytecode, and it JIT-compiles hot methods into native machine code using profiling data (counts of what actually runs).

Q2. JDK vs JRE vs JVM? The JVM runs bytecode. The JRE is the JVM plus the standard libraries. The JDK is the JRE plus development tools such as javac, jcmd and jstack.

Q3. What makes Java platform-independent? Bytecode is the same on every platform. Only the JVM implementation is different for each platform.

Q4. What is tiered compilation? Code starts in the interpreter. Hot methods are compiled quickly by C1, which also collects profiling data. The hottest methods are compiled again by C2 with aggressive optimisations. If an assumption becomes invalid, the code can be deoptimised back to the interpreter.

1.2 Primitives, wrappers, autoboxing and the Integer cache

Why?

In simple words: Java has fast plain numbers (int) and slower "boxed" numbers (Integer) that are real objects. Collections need the boxed kind, and Java converts between the two for you — which sometimes causes surprising bugs.

Collections and generics work only with objects. But doing arithmetic on objects is slow. Every number would need its own memory on the heap, and the CPU would have to follow a pointer to read it.

So Java keeps 8 primitive types for fast plain values. Each one also has a wrapper class, so the value can live inside a collection. Autoboxing does the conversion for you, so you don't have to write it by hand.

Think of a tiffin box. The roti (the int) is the actual food. The tiffin box (the Integer) lets you pack it and put it in a bag (a collection). But it takes extra space, and you must open it before eating.

What is happening internally?

Primitive Size Wrapper Default value
byte / short / int / long 8 / 16 / 32 / 64 bit Byte / Short / Integer / Long 0
float / double 32 / 64 bit IEEE-754 Float / Double 0.0
char 16 bit unsigned UTF-16 unit Character '\u0000'
boolean Depends on the JVM Boolean false

A primitive local variable sits directly in the stack frame. int x = 5 is just 4 bytes that hold 5.

An Integer is an object on the heap. It takes about 16 bytes: - an object header (~12 bytes), - a 4-byte int value field, - plus padding.

Your variable holds only a reference (a pointer) to that object.

Stack frame                       Heap
┌────────────┐
│ int a = 5  │  (value itself)
│ Integer b ─┼──────────────────► [header | value=5]   ~16 bytes
└────────────┘

Autoboxing is a shortcut the compiler writes for you: - Integer b = 5; compiles to Integer b = Integer.valueOf(5); - int c = b; compiles to int c = b.intValue();

The Integer cache: Integer.valueOf(int) keeps a static array of ready-made Integer objects for −128 to 127. - For a value in that range, it returns the shared cached object. - Outside that range, it creates a new object every time. - You can raise the upper limit with -XX:AutoBoxCacheMax. - Short, Byte, Long and Character (0–127) cache in a similar way. Double and Float don't cache.

How does it work?

  1. You write Integer x = 100;. The compiler turns this into Integer.valueOf(100). The cache returns the shared object for 100.
  2. You write Integer y = 100;. The same cached object comes back. So x == y is true, because == compares references (addresses).
  3. Now use 1000 instead. Each valueOf(1000) call creates a new object. So you get two different objects, and == is false even though the values are equal.
  4. Arithmetic on wrappers works in three steps: unbox, compute on primitives, box again. Wrappers are immutable (they can't change), so x++ on an Integer creates a new object.

Example

Integer a = 127, b = 127;
System.out.println(a == b);        // true   — both point to the cached object
Integer c = 128, d = 128;
System.out.println(c == d);        // false  — two different objects
System.out.println(c.equals(d));   // true   — compares the int values

Map<String, Integer> stock = new HashMap<>();
stock.put("sku1", 500); stock.put("sku2", 500);
System.out.println(stock.get("sku1") == stock.get("sku2"));            // false! (500 > 127)
System.out.println(stock.get("sku1").equals(stock.get("sku2")));      // true

Integer missing = stock.get("sku3");    // null
int qty = missing;                      // NullPointerException: unboxing null

When would I use it?

  • Primitives wherever you calculate: loops, counters, arrays (int[]), DSA code.
  • Wrappers when an API needs objects: List<Integer>, Map<String, Long>, generics. Also when you need null to mean "no value" — for example, a nullable DB column mapped in JPA.
  • Primitive streams (IntStream, mapToInt) in large calculations, so you avoid boxing.

What can go wrong?

  • == on wrappers. Tests with small numbers pass, because those come from the cache. In production, large numbers fail. Always use equals, or unbox first.
  • NullPointerException on unboxing. This often happens when map.get() returns null and you assign it to an int. Use getOrDefault(key, 0) instead.
  • Performance. A List<Integer> of a million elements takes ~16 MB of objects plus 4–8 MB of references. An int[] of the same size takes only 4 MB. Heavy boxing in hot loops also creates lots of garbage, which puts pressure on the GC.
  • Ternary unboxing surprise. In Integer r = flag ? map.get(k) : 0; the 0 is an int. Because of that, Java unboxes map.get(k) too. If it is null, you get an NPE.

Interview questions

Q1. Why does Integer a = 128, b = 128; a == b print false? Integer.valueOf caches only −128 to 127. So 128 creates two separate objects, and == compares references, not values.

Q2. What is autoboxing and what does it cost? The compiler adds valueOf() and xxxValue() calls to convert between primitives and wrappers for you. The costs are: a new object for values outside the cache, extra memory, more GC pressure, and a possible NullPointerException when unboxing null.

Q3. When would you use Integer instead of int in an entity or DTO? When the value can genuinely be missing, like a nullable column or an optional field. An int would quietly default to 0, and 0 may be a valid business value, so you could not tell "missing" from "zero".

Q4. Why can't you write List<int>? Generics work only with reference types because of type erasure (1.16). After compilation, the element type becomes Object, and an Object can't hold a primitive.

1.3 Integer overflow and numeric conversions

Why?

In simple words: An int has a fixed size. If a result gets too big, Java does not complain — the number silently wraps around to a negative value and your answer is wrong.

Primitive integers have fixed sizes. When a calculation goes past the range, Java doesn't throw an error. The value just wraps around silently.

This hits money, counters, IDs, DSA sums and midpoints. The wrong answer often passes small tests and then fails the hidden tests.

Think of a car's odometer that shows only 6 digits. After 999999 km it goes back to 000000. The car really drove more, but the meter shows a small number.

What is happening internally?

int is 32-bit two's complement — the standard way CPUs store signed numbers. Its range is −2,147,483,648 to 2,147,483,647.

Add 1 to the maximum, and the bit pattern 0111…1 becomes 1000…0. That pattern is the minimum value. The CPU does set an overflow flag, but Java ignores it for + - *.

 Integer.MAX_VALUE = 0111 1111 ... 1111  (2,147,483,647)
                + 1
                   = 1000 0000 ... 0000  (-2,147,483,648)   ← wraps, no error

Type rules: - Widening (int → long → float → double) happens automatically. It is safe for integers. But long → double can lose precision above 2⁵³. - Narrowing (double → int, long → int) needs a cast. It cuts off the decimal part (towards zero) or drops the high bits. - Inside an expression, byte, short and char are first promoted to int. If any operand is long, the whole expression is calculated in long.

How does it work?

Take long total = a * b; where a and b are int.

  1. Both operands are int, so Java calculates a * b in int.
  2. The result overflows.
  3. Only then is the already-wrong result widened to long.

The type of the variable on the left does not change how the right-hand side is calculated.

Example

int a = 50_000, b = 50_000;
long wrong = a * b;            // 2,500,000,000 doesn't fit in int -> -1,794,967,296, then widened
long right = (long) a * b;     // cast ONE operand first -> computed in long -> 2,500,000,000
long alsoRight = 1L * a * b;

int lo = 2_000_000_000, hi = 2_100_000_000;
int badMid = (lo + hi) / 2;          // lo + hi overflows -> negative midpoint
int goodMid = lo + (hi - lo) / 2;    // 2,050,000,000

Math.addExact(Integer.MAX_VALUE, 1); // throws ArithmeticException instead of wrapping
Math.abs(Integer.MIN_VALUE);         // still -2,147,483,648 (no positive counterpart)
(int) 3.99;                          // 3   (truncates)
(int) -3.99;                         // -3
'a' + 1;                             // 98 (int);  (char) ('a' + 1) -> 'b'
0.1 + 0.2 == 0.3;                    // false — binary floating point can't represent 0.1 exactly

When would I use it?

  • In DSA, use long for sums of many ints, for products, and for prefix sums. Write midpoints as lo + (hi - lo) / 2.
  • For money and points, use long in the smallest unit (paise), or use BigDecimal. Never use double.
  • Use the Math.*Exact methods where you must detect overflow, such as balances and quotas. They throw an exception instead of wrapping.

What can go wrong?

  • double for currency. 0.1 + 0.2 is not 0.3. Small rounding errors add up in totals, and reconciliations fail.
  • BigDecimal traps:
  • new BigDecimal(0.1) copies the binary error from the double. Use BigDecimal.valueOf(0.1) or the String constructor.
  • equals also compares scale (the number of decimal places). So 2.0 ≠ 2.00. Use compareTo instead.
  • Comparators written as a - b overflow for large or negative values (see 1.13).

Interview questions

Q1. What happens on integer overflow in Java? The value wraps around silently, using two's complement — no error is thrown. When overflow is possible, use long, Math.addExact/multiplyExact (which throw instead), or BigInteger.

Q2. Why should you never use double for money? Binary floating point can't store most decimal fractions exactly, so every calculation adds a small rounding error, and these add up. Use long in minor units (paise) or BigDecimal with an explicit rounding mode.

Q3. Why is (lo + hi) / 2 dangerous? When both are large, lo + hi can overflow and give a negative number. lo + (hi - lo) / 2 can't overflow.

1.4 Strings, the String pool and immutability

Why?

In simple words: A Java String can never change after it is created. Because of that, Java can safely share one copy of the same text everywhere, remember its hash, and hand it to many threads without locks.

Strings are the most used objects in any program: keys, URLs, SQL, JSON, log lines.

Strings are immutable — once created, they can't change. This gives four benefits: 1. Memory saving. The JVM can share one copy of identical literals. 2. Speed as map keys. The hash code can be calculated once and cached. 3. Thread safety. Threads can pass strings around without locks. 4. Security. Say a file path is checked and found safe. Nobody holding a reference can change it afterwards.

Think of a printed railway ticket. Once printed, nobody can change the seat number. If you need a different seat, a new ticket is printed. So the ticket checker can trust whatever he sees.

What is happening internally?

public final class String {            // final: nobody can subclass and add mutability
    private final byte[] value;        // the characters (Java 9+ "compact strings")
    private final byte coder;          // 0 = LATIN1 (1 byte/char), 1 = UTF16 (2 bytes/char)
    private int hash;                  // cached hashCode, computed lazily on first call
}
  • Compact strings (Java 9+). ASCII and Latin-1 text uses 1 byte per character instead of 2. In most applications, this roughly halves the memory used by Strings.
  • String pool (also called the intern table). It is a hash table in the heap. (It moved out of PermGen in Java 7.) It holds exactly one shared copy of each distinct literal. Every literal in your code, like "tenant_id", goes into the pool when its class loads.
  • hashCode is s[0]*31^(n-1) + … + s[n-1]. It is calculated once and stored in the hash field.
            Heap
 s1 ───┐   ┌──────────── String pool ────────────┐
 s2 ───┼──►│  "java"  (one shared object)          │
       │   └───────────────────────────────────────┘
 s3 ──────► "java"  (separate object from new String(...))

How does it work?

  1. A literal "java". The JVM looks it up in the pool. If it is not there, it is added. The variable gets the pooled reference.
  2. new String("java"). This always creates a new object on the heap. Its contents are copied from the pooled literal.
  3. s.intern(). This returns the pooled copy for that content. If there is no pooled copy, it adds one first.
  4. "Modifying" methods (toUpperCase, replace, substring, concat) return a new String. The original never changes.
  5. Compile-time constants are joined early. "ja" + "va" becomes "java" inside the class file, so it is pooled.

Example

String s1 = "java";
String s2 = "java";
String s3 = new String("java");
String s4 = s3.intern();

System.out.println(s1 == s2);       // true  (same pooled object)
System.out.println(s1 == s3);       // false (s3 is a separate heap object)
System.out.println(s1 == s4);       // true  (intern returned the pooled one)
System.out.println(s1.equals(s3));  // true  (same characters)

final String ja = "ja";
String part = "ja";
System.out.println(("ja" + "va") == s1);   // true  — folded at compile time
System.out.println((ja + "va") == s1);     // true  — ja is a compile-time constant (final + literal)
System.out.println((part + "va") == s1);   // false — computed at runtime, new object

String up = s1.toUpperCase();
System.out.println(s1 + " " + up);         // java JAVA — s1 unchanged

When would I use it?

  • Compare string contents with equals / equalsIgnoreCase. Never use ==.
  • Use Strings freely as HashMap keys. They are immutable, and their hash is cached.
  • You rarely need intern(). It helps only when parsing creates millions of duplicate strings (country codes, status values) that waste heap. Even then, the G1 flag -XX:+UseStringDeduplication is usually better.

What can go wrong?

  • == comparison works by luck with literals. It fails with strings that come from input, from the DB, or from concatenation.
  • Passwords in Strings stay in memory until the GC removes them, and they may show up in heap dumps. That is why security APIs use char[] — you can wipe it after use.
  • substring makes a copy (since Java 7u6). So it costs O(length) — time grows with the length. Calling it in a loop can become O(n²).
  • split(".") takes a regex, and . in a regex means "any character". So "a.b".split(".") returns an empty array. Use split("\\.") or Pattern.quote(".").

Interview questions

Q1. Why is String immutable? Four reasons. It makes the string pool possible, because shared copies can't be changed. It allows a cached hash code, which makes Strings fast map keys. It gives thread safety without synchronisation. And it helps security, because a value can't be changed after it has been validated.

Q2. Where is the String pool and how do strings get into it? It is a table in the heap (since Java 7). Literals and compile-time constants are added when the class loads. Strings created at runtime are added only if you call intern().

Q3. How many objects does new String("abc") create? Up to two. One is the pooled literal "abc", if it isn't pooled already. The other is the new heap object.

Q4. What changed in Java 9 for Strings? Compact strings: a byte[] plus a coder flag stores Latin-1 text in 1 byte per character. Also, concatenation now compiles to invokedynamic (StringConcatFactory), which performs better.

1.5 StringBuilder and string concatenation

Why?

In simple words: Adding to a String in a loop makes a brand-new copy every time, which gets very slow. A StringBuilder is a changeable buffer — you keep adding to the same buffer, and make one String at the end.

Strings are immutable. So when you build a long string with += in a loop, each step creates a new String. Each step also copies all the earlier characters again.

That costs O(n²) time — doubling the input makes it about four times slower. It also creates lots of garbage.

StringBuilder is a mutable (changeable) character buffer. You append to it in place.

Think of writing a long list on a whiteboard. With +=, you rewrite the whole list on a fresh board every time you add one item. With StringBuilder, you just add the next line to the same board.

What is happening internally?

StringBuilder holds two things: - a growable byte[] (like an ArrayList, but for characters); - a count of how many slots are used.

When the array is full, it grows to about 2 × old + 2 and copies the old contents once. So appends are amortised O(1) — usually instant, sometimes slow when it grows, but fast on average.

toString() makes one final copy into a new immutable String.

StringBuffer is the same class, but every method is synchronized (locked so only one thread can use it at a time). It is a leftover from Java 1.0. It is slower, and you almost never need it.

How does it work?

s = ""; for 4 iterations: s += "ab"
  iter1: new String "ab"        (copy 2 chars)
  iter2: new String "abab"      (copy 4)
  iter3: new String "ababab"    (copy 6)
  iter4: new String "abababab"  (copy 8)   → total copies 2+4+6+8 = O(n²)

StringBuilder sb (capacity 16): append "ab" ×4 → writes into the same buffer, no copies until full → O(n)

The compiler already optimises a + b + c when it is a single expression. Since Java 9 it does this through invokedynamic. So the problem is only repeated concatenation across loop iterations.

Example

// O(n^2): avoid
String csv = "";
for (String id : outletIds) csv += id + ",";

// O(n): correct
StringBuilder sb = new StringBuilder(outletIds.size() * 12);   // pre-size if you know roughly
for (String id : outletIds) sb.append(id).append(',');
if (sb.length() > 0) sb.setLength(sb.length() - 1);           // drop trailing comma
String result = sb.toString();

// Cleanest for joining:
String joined = String.join(",", outletIds);
String viaStream = outletIds.stream().collect(Collectors.joining(",", "[", "]"));

// DSA uses: reverse, insert, deleteCharAt, setCharAt
String rev = new StringBuilder("level").reverse().toString();

When would I use it?

  • When building strings in loops: CSV export, dynamic SQL fragments, log messages built with conditions, DSA output.
  • String.join / Collectors.joining for simple joins with a delimiter.
  • StringBuffer practically never. If several threads really do build one string, put the synchronisation at a higher level.

What can go wrong?

  • Sharing one StringBuilder across threads corrupts it. It is not thread-safe.
  • Comparing builders with sb.equals(otherSb). StringBuilder doesn't override equals, so this compares references, not text. Use sb.toString().equals(...), or sb.compareTo(other) == 0 (Java 11+).
  • Logging with +. Even when the log level is off, the string still gets built. Use parameterised logging instead: log.debug("user {} points {}", id, pts).

Interview questions

Q1. String vs StringBuilder vs StringBuffer? String is immutable. StringBuilder is mutable and not synchronised — it is fast and the default choice for building strings. StringBuffer is mutable and synchronised — it is a legacy class and slower.

Q2. Is s1 + s2 + s3 inefficient? Not inside one expression, because the compiler optimises it. The problem is repeated += across loop iterations, which is O(n²).

Q3. How does StringBuilder grow? When its internal array is full, it grows to about double the old capacity plus 2 and copies once. This gives amortised O(1) appends — fast on average.

1.6 Stack vs heap, and why Java is always pass-by-value

Why?

In simple words: Each thread has its own small "stack" for local variables, and all objects live in one shared "heap". When you call a method, Java always passes a copy — for an object, it copies the address, not the object.

You need a clear picture of where data lives. Without it, you can't reason about performance, thread safety, memory leaks or method calls.

Two common bugs come from this: - "Why did my change not show up?" - "Why did this change show up when I didn't expect it?"

Both are explained by this model.

Think of your house address written on a slip of paper. If you give a friend a photocopy of the slip, he can visit your house and rearrange the furniture — you will see the change. But if he scribbles a new address on his copy, your slip still has your address.

What is happening internally?

Thread 1 stack                        Heap (shared by all threads)
┌──────────────────────────┐
│ frame: process()          │
│   int count = 3           │
│   Order order ────────────┼──────► Order{id=7, lines ─┐}
├──────────────────────────┤                            ▼
│ frame: main()             │                       ArrayList[OrderLine, OrderLine]
│   String[] args ──────────┼──────► String[] {...}
└──────────────────────────┘
Thread 2 stack (its own frames) ── may reference the SAME heap objects
  • Stack — one per thread.
  • Each method call pushes a frame onto the stack.
  • The frame holds local variables and an operand stack (scratch space for calculations).
  • A primitive local stores the value itself. An object local stores a reference.
  • When the method returns, its frame is popped. Memory cleanup is automatic and instant.
  • Heap — one per JVM, shared by all threads.
  • Every object and every array lives here.
  • The garbage collector frees an object when nothing can reach it any more.
  • Because each thread has its own stack, local variables are thread-confined — only one thread sees them, so they are safe. Heap objects that several threads can reach need synchronisation (Chapter 4).

Pass-by-value: when you call a method, Java copies each argument's value into the new frame. - For a primitive, the value is the number. - For an object, the value is the reference (the address). The object itself is not copied.

How does it work?

  1. The caller has List<Integer> list. This is a reference, say 0xA1, pointing to an ArrayList on the heap.
  2. Calling mutate(list) copies 0xA1 into the parameter l in the new frame. Now both variables point to the same heap object.
  3. l.add(1) follows 0xA1 and changes the shared object. So the caller sees the change.
  4. l = new ArrayList<>() changes only the copy in the called method's frame, to 0xB2. The caller's variable still holds 0xA1.

Example

static void mutate(List<Integer> l)   { l.add(1); }                       // changes shared object
static void reassign(List<Integer> l) { l = new ArrayList<>(); l.add(2); } // changes local copy only
static void bump(int x)               { x++; }                             // copy of primitive

List<Integer> list = new ArrayList<>();
mutate(list);     // list = [1]
reassign(list);   // list = [1]  — the new list was attached to the callee's copy and is now garbage
int n = 5; bump(n);   // n = 5

// "Return two values" in Java: return an object instead of out/ref parameters
record MinMax(int min, int max) {}
static MinMax minMax(int[] a) { return new MinMax(Arrays.stream(a).min().orElseThrow(), Arrays.stream(a).max().orElseThrow()); }

When would I use it?

  • To explain why a method can change a collection you pass in. This is why defensive copies matter (1.14).
  • To reason about thread safety. Locals are safe; shared heap state needs protection.
  • To tell apart StackOverflowError and OutOfMemoryError. The first means too many frames, usually from deep recursion. The second means the heap is full.

What can go wrong?

  • Expecting a method to "swap" two variables or to point the caller's variable at a new object. This is impossible in Java. Java has no C# ref/out.
  • Exposing internal mutable state. If you return your private List directly, callers can change it.
  • Deep recursion. For example, DFS on 10⁵ nodes can overflow the default thread stack of ~512 KB–1 MB. Use an explicit stack instead.

Interview questions

Q1. Is Java pass-by-value or pass-by-reference? Always pass-by-value. For objects, the value that gets copied is the reference. So the called method can change the object, but it can't make the caller's variable point to a different object.

Q2. What lives on the stack and what on the heap? The stack holds per-thread frames with local variables, primitive values and references. The heap holds all objects and arrays; it is shared across threads and managed by the GC.

Q3. Why are local variables thread-safe? Each thread has its own stack, so local variables are never shared between threads. But the objects they point to can still be shared.

1.7 Classes, objects, constructors, static, final and initialisation order

Why?

In simple words: A class bundles data with the methods that protect it, and a constructor makes sure every new object starts valid. static means "belongs to the class, one copy"; final means "can't be changed later". The order in which Java sets things up explains some strange null bugs.

A class keeps state together with the behaviour that protects it. A constructor guarantees an object starts in a valid state.

  • static gives you data and utility methods at class level (one shared copy).
  • final gives you guarantees:
  • a value that is set once;
  • a method that can't be overridden;
  • a class that can't be extended.

Interviewers test the initialisation order. It explains surprising null values and bugs in real code.

Think of building a house. The foundation (parent class) must be laid before the upper floor (child class). If someone tries to use the upper floor's furniture while only the foundation exists, the furniture isn't there yet — that is the null.

What is happening internally?

  • A class is loaded once per class loader. Its static fields live with the class, so there is one copy. They are set up when the class is first actively used.
  • An object is a block of memory on the heap. It has:
  • a header — a mark word (used for locking, hash code and GC age) and a pointer to its class;
  • then the instance fields.
  • new Account("A1") runs in this order: 1. Allocate memory. All fields start at zero values: 0, false, null. 2. Run field initialisers and instance blocks. 3. Run the constructor body.
  • A subclass constructor first calls super(...). If you don't write it, Java adds super() for you. So the parent part is always set up first.
  • final fields get a special memory-model guarantee. Once the constructor finishes, other threads see the final fields correctly set, without any synchronisation. The condition: this must not have escaped (been handed to other code) during construction.

How does it work?

The order when new Child() runs for the first time:

1. Parent static fields/blocks   (once, at class init, in source order)
2. Child static fields/blocks    (once)
3. Parent instance fields/blocks, then Parent constructor body
4. Child instance fields/blocks, then Child constructor body

Example

class Parent {
    static { System.out.println("1 parent static"); }
    { System.out.println("3 parent instance block"); }
    Parent() { System.out.println("4 parent ctor"); init(); }   // calls an overridable method: dangerous
    void init() {}
}
class Child extends Parent {
    static { System.out.println("2 child static"); }
    private final String name = "child";
    { System.out.println("5 child instance block"); }
    Child() { System.out.println("6 child ctor"); }
    @Override void init() { System.out.println("init sees name = " + name); }   // prints null!
}
// new Child();  ->  1, 2, 3, 4, "init sees name = null", 5, 6
// new Child();  ->  3, 4, "init sees name = null", 5, 6   (statics don't run again)

public class Account {
    private static int created = 0;            // one per class
    private final String id;                   // must be set exactly once, in every constructor path
    private long balancePaise;

    public Account(String id) { this(id, 0); }                       // constructor chaining
    public Account(String id, long opening) {
        if (opening < 0) throw new IllegalArgumentException("negative opening balance");
        this.id = Objects.requireNonNull(id);
        this.balancePaise = opening;
        created++;
    }
    public static int created() { return created; }                  // static: no 'this'
}

Why does it print null? 1. Parent() calls init(). 2. Because of dynamic dispatch (Java picks the method by the object's real type), Child.init() runs. 3. But Child's field initialisers (step 4 of the order) haven't run yet. 4. So name is still null.

When would I use it?

  • static for constants (static final int MAX_RETRY = 3), factory methods (Money.inr(100)) and stateless utilities.
  • final fields by default for everything set in the constructor. This gives immutability and thread safety.
  • final classes for value types.
  • private constructors for singletons, utility classes and static factories.
  • Validation in the constructor, so an invalid object can never exist.

What can go wrong?

  • Calling overridable methods from constructors — this causes the null shown above. Only call private or final methods there.
  • Mutable static state (like static Map cache). It is global, shared across all threads and requests, and never garbage-collected. It is a classic cause of memory leaks and race conditions.
  • Leaking this from a constructor — for example, registering a listener or starting a thread. Other threads may then see a half-built object.
  • Exceptions in a static initialiser. The first failure throws ExceptionInInitializerError. After that, every later use throws NoClassDefFoundError. This is a confusing error in production, because the real cause was earlier.

Interview questions

Q1. What is the order of initialisation in Java? First the static parts — parent then child, once, when the class is initialised. Then, for each new object: the parent's instance initialisers and constructor, then the child's instance initialisers and constructor.

Q2. Can a constructor be private, and why would it be? Yes. It is used for singletons, utility classes, static factory methods like List.of, and builders that force you to create the object through build().

Q3. What does final mean on a field, method, class? On a field: it is assigned only once, and it also gets safe-publication guarantees (other threads see it correctly set). On a method: it can't be overridden. On a class: it can't be extended.

Q4. Why shouldn't constructors call overridable methods? The subclass's override runs before the subclass's fields are initialised. So it sees default values (null or 0) instead of the real ones.

1.8 Access modifiers and encapsulation

Why?

In simple words: Keep an object's data private and only let people change it through methods that check the rules. Then the object can never get into a wrong state, like a negative balance.

An invariant is a rule that must always be true for an object, like "balance is never negative". Encapsulation keeps invariants true. It makes the state reachable only through methods that check the rules.

Access modifiers are the language tool that enforces this. They also define a module's public API. Everything behind that API can be changed freely.

Think of an ATM. You can't open the cash box and take notes yourself. You must go through the machine, and the machine checks your PIN and balance first.

What is happening internally?

Access is checked twice: by the compiler and by the JVM verifier. - Private members aren't visible outside the class. - Package-private members (no modifier) are visible only inside the same package. - Nested classes may access each other's private members. Since Java 11, the JVM supports this directly through "nestmates".

Modifier Same class Same package Subclass in another package Everyone
private ✔
(none — package-private) ✔ ✔
protected ✔ ✔ ✔
public ✔ ✔ ✔ ✔

C# comparison: - Java has no internal. Package-private is the closest thing. - Java's protected also opens access to the whole package, not only to subclasses.

How does it work?

Design rule: 1. Start with the most restrictive access (private). 2. Widen it only when a real caller needs it. 3. Expose behaviour (debit, credit) instead of raw setters. Then the class itself enforces the rules.

Example

// Anaemic (bad): anyone can break the invariant
public class Wallet { public long balance; }
wallet.balance -= 1_000_000;          // negative balance, no audit, no rule

// Encapsulated (good)
public final class Wallet {
    private long balancePaise;
    private final List<String> audit = new ArrayList<>();

    public void debit(long paise, String reason) {
        if (paise <= 0) throw new IllegalArgumentException("amount must be positive");
        if (paise > balancePaise) throw new IllegalStateException("insufficient balance");
        balancePaise -= paise;
        audit.add("DEBIT " + paise + " " + reason);
    }
    public long balance() { return balancePaise; }
    public List<String> audit() { return List.copyOf(audit); }   // don't leak the mutable list
}

When would I use it?

  • private for fields, always.
  • public methods form the API.
  • Package-private for helpers used only inside one feature package. This works well with a "package by feature" layout.
  • protected rarely — mainly for template-method hooks (steps a subclass is meant to fill in).
  • In Spring, @Transactional and @Async work only on public methods called through the proxy (Chapter 6.7).

What can go wrong?

  • Getters that return internal mutable collections. Callers can change the collection and skip your rules.
  • A public setter for every field ("JavaBean style"). Objects become plain data bags, and the rules end up scattered across many services.
  • Reflection with setAccessible(true) (used by frameworks and tests) can get around private. So don't rely on access modifiers for security.

Interview questions

Q1. What is encapsulation and why does it matter? It means hiding state behind methods that enforce the invariants (rules that must always hold). So the object is always valid, and you can change the internals without breaking callers.

Q2. Difference between protected and package-private? Package-private is visible only inside the same package. protected is visible in the package too, and also to subclasses in other packages.

Q3. Are getters and setters encapsulation? Not by themselves. A setter for every field exposes state just like a public field does. Real encapsulation exposes meaningful operations that keep the invariants true.

1.9 Inheritance and polymorphism (overloading vs overriding)

Why?

In simple words: You write code that talks to a general type, like "any payment gateway". At runtime, Java runs the correct version for the real object. So you can add new types later without touching the old code.

Polymorphism means "one call, many behaviours". You write code against a general type such as PaymentGateway or Shape. When the program runs, each object runs its own specific version of the method.

Why does this help? Because you can add a new type (say, a new payment gateway) without editing the code that uses it.

Inheritance is one way to get polymorphism. A subclass is a kind of its parent. It reuses the parent's code. It replaces (overrides) only the parts that are different.

What is happening internally?

  • Overriding (runtime polymorphism) — the method is chosen while the program runs: 1. Every class has a virtual method table (vtable). This is an array of pointers, one for each method, pointing to that class's code. 2. A subclass's vtable starts as a copy of its parent's. Then the entries it overrides are replaced with its own methods. 3. A call like animal.speak() compiles to the bytecode instruction invokevirtual Animal.speak. 4. At runtime, the JVM reads the object's actual class (every object stores a pointer to its class). 5. It looks up the speak slot in that class's vtable and jumps there. 6. This is called dynamic dispatch — the decision is made at runtime, not compile time.
  • Interface calls use invokeinterface, which works with similar tables.
  • The JIT (the just-in-time compiler that turns hot bytecode into machine code) often sees only one implementation at a call site. Such a call is called monomorphic. The JIT then turns it into a direct call and inlines it (copies the method body into the caller).
  • Overloading (compile-time polymorphism) — the method is chosen while compiling:
  • Several methods share one name but have different parameter lists.
  • The compiler picks one. It looks only at the static (declared) types of the arguments — the types written in the code.
  • That choice is fixed in the bytecode. It never changes at runtime.
  • In Java, every non-static, non-private, non-final method is virtual by default. "Virtual" means it can be overridden and is chosen at runtime. In C#, you must opt in with the virtual keyword.
  • @Override does not change behaviour. It only asks the compiler to check that you really are overriding something.

The picture below shows the two types involved in one call. The reference type decides what you are allowed to call. The object type decides which code actually runs.

Animal a = new Dog();     a.speak()
   reference type: Animal ─ decides WHICH METHODS are callable (compile time)
   object type:    Dog    ─ decides WHICH IMPLEMENTATION runs (runtime, via Dog's vtable)

How does it work?

The table compares the two side by side. "Covariant" means the overriding method may return a more specific type (a subtype).

Overloading Overriding
Where Same class (or inherited) Subclass
Signature Same name, different parameters Same name and same parameters
Return type Anything Same or a subtype (covariant)
Access Anything Same or wider (e.g. protected → public)
Checked exceptions Anything Same, narrower or none
Resolved At compile time, by declared argument types At runtime, by the actual object type
static methods Can be overloaded Can't be overridden; they are hidden instead

Example

class Animal {
    void speak() { System.out.println("..."); }
    static void kind() { System.out.println("animal"); }
}
class Dog extends Animal {
    @Override void speak() { System.out.println("Woof"); }
    static void kind() { System.out.println("dog"); }       // hides, doesn't override
}

Animal a = new Dog();
a.speak();          // Woof   -> runtime dispatch on the actual object
a.kind();           // animal -> static: chosen by the reference type at compile time

// Overloading is resolved by DECLARED types, not runtime types
class Printer {
    void print(Object o) { System.out.println("object"); }
    void print(String s) { System.out.println("string"); }
}
Object o = "hello";
new Printer().print(o);   // "object" — the declared type of o is Object

Step-by-step trace of a.speak():

  1. The compiler sees that a is declared as Animal.
  2. It checks that Animal has a speak() method. It does, so the call is allowed.
  3. It writes invokevirtual Animal.speak into the bytecode.
  4. At runtime, the object's class pointer says Dog.
  5. Dog's vtable slot for speak points to Dog.speak.
  6. So "Woof" prints.

a.kind() is different. kind() is static, so there is no vtable lookup. The compiler picks Animal.kind() from the declared type, and "animal" prints.

When would I use it?

  • Overriding: Strategy implementations (swappable behaviours behind one interface), template-method hooks (a base class calls a method that subclasses fill in), equals/hashCode/toString, and Spring beans that implement interfaces.
  • Overloading: convenience APIs such as log(String) and log(String, Throwable). Also constructors with optional parameters. But if you have more than 3–4 parameters, consider a builder instead.
  • Inheritance: only for true is-a relationships where the shared behaviour is stable. Otherwise prefer composition (1.11).

What can go wrong?

  • A silent non-override. You forget @Override. Then you misspell the method name or change a parameter type. You have now created an overload, not an override. Your "override" is silently never called. @Override would have caught this at compile time.
  • Confusing overloads with boxing and varargs. Think of m(long) vs m(Integer) vs m(int...). Boxing means wrapping a primitive int into an Integer object. Varargs means "any number of arguments". The compiler's order of preference is: first widening (int → long), then boxing, then varargs.
  • Deep inheritance trees. You change a base class, and subclasses break in unexpected ways. This is called the fragile base class problem.
  • Calling static methods through an object reference (like a.kind()). It looks like runtime dispatch, but it is not. This misleads readers about which method runs.

Interview questions

Q1. Difference between overloading and overriding? Overloading means the same method name with different parameters; the compiler picks one at compile time using the declared types of the arguments. Overriding means a subclass redefines a method with the same signature; the JVM picks one at runtime using the actual object type, through dynamic dispatch.

Q2. Can you override static or private methods? No. Static methods are hidden, not overridden — the compiler picks them by the reference type. Private methods are not inherited at all, so a method with the same name in a subclass is simply a new, separate method.

Q3. How does the JVM decide which overridden method to call? It looks at the object's runtime class and finds the method in that class's virtual method table (via the invokevirtual instruction). If the JIT sees only one implementation at that call site, it may inline the call for speed.

Q4. What is covariant return type? An overriding method is allowed to return a subtype of the parent method's return type. For example, Dog clone() can override Animal clone().

1.10 Interfaces vs abstract classes

Why?

In simple words: An interface is a promise — "I can do this". Any class can make that promise, even unrelated ones. An abstract class is a half-built parent class that shares real code and fields with its children.

Both let you write code against an abstraction (a general type) instead of a concrete class.

  • Interfaces describe a capability or contract. Unrelated classes can share it, like Comparable or PaymentGateway. One class can implement many interfaces.
  • Abstract classes share state (fields) and code among closely related classes. They give subclasses a partly built skeleton to complete.

Think of a driving licence (interface): a truck driver, a taxi driver and a doctor can all hold one. A family recipe book (abstract class) is passed only within one family, with half the recipes already written.

What is happening internally?

  • An interface compiles to a class file with the ACC_INTERFACE flag set.
  • Its fields are automatically public static final. So they can only be constants.
  • Since Java 8, it can have default methods (instance methods with a body) and static methods.
  • Since Java 9, it can also have private helper methods.
  • It still has no instance fields and no constructor.
  • An abstract class is a normal class that you can't create directly with new.
  • It can have fields.
  • It can have constructors. Subclasses run them through super(...).
  • It can mix abstract methods (no body) and concrete methods (with body) freely.
  • Inheritance limits. A Java class can extend only one class. But it can implement many interfaces.
  • The diamond problem. Two interfaces may provide the same default method. Then the class must override that method itself. Inside, it can pick one version with A.super.method().

How does it work?

Interface Abstract class
A class can extend/implement Many Only one
Instance state No (constants only) Yes
Constructors No Yes
Method kinds abstract, default, static, private Any
Access of members public (private helpers allowed) Any
Good for Capabilities, ports, strategies, APIs Template methods, a shared base implementation

A port here means an interface your core code depends on, which an adapter implements (for example a repository). A template method is a fixed algorithm in the base class that calls "hook" methods subclasses fill in.

Example

The example below shows three things:

  1. RewardRule is an interface: a contract with a shared default method and a static factory method.
  2. MinimumAmountRule is an abstract class: it holds shared state (minAmountPaise) and fixed logic, with a hook (extraCheck) for subclasses.
  3. Duck shows the diamond: two interfaces give move(), so Duck must decide.
// Interface: a contract many unrelated classes can satisfy
public interface RewardRule {
    boolean applies(Order o);
    long points(Order o);
    default String describe() { return getClass().getSimpleName() + " rule"; }   // shared default
    static RewardRule none() { return new RewardRule() {                         // factory on the interface
        public boolean applies(Order o) { return false; }
        public long points(Order o) { return 0; } }; }
}

// Abstract class: shared state + skeleton for related rules
public abstract class MinimumAmountRule implements RewardRule {
    protected final long minAmountPaise;                         // shared state
    protected MinimumAmountRule(long min) { this.minAmountPaise = min; }
    @Override public final boolean applies(Order o) {            // shared, fixed logic
        return o.amountPaise() >= minAmountPaise && extraCheck(o);
    }
    protected boolean extraCheck(Order o) { return true; }       // hook for subclasses
}

public final class FlatBonusRule extends MinimumAmountRule {
    private final long bonus;
    public FlatBonusRule(long min, long bonus) { super(min); this.bonus = bonus; }
    @Override public long points(Order o) { return bonus; }
}
record Order(long amountPaise) {}

// Diamond with defaults: must resolve explicitly
interface Walker { default String move() { return "walk"; } }
interface Swimmer { default String move() { return "swim"; } }
class Duck implements Walker, Swimmer {
    @Override public String move() { return Walker.super.move() + "+" + Swimmer.super.move(); }
}

When would I use it?

  • Start with an interface for anything a caller depends on: repositories, gateways, strategies, Spring service ports.
  • It keeps dependencies inverted. This is the "D" in SOLID: high-level code depends on abstractions, not on concrete classes.
  • It also makes mocking easy in tests.
  • Add an abstract class underneath when several implementations share real code or state. Examples: AbstractList in the JDK, or a base MinimumAmountRule.
  • Use default methods to evolve a published interface. You can add a new method without breaking every class that already implements it. That is exactly how Collection.stream() was added in Java 8.

What can go wrong?

  • Abstract class just to share a few helpers. A class can extend only one class. So this locks subclasses out of extending anything else. Prefer composition or static helper methods.
  • State-like behaviour in default methods. Default methods can't hold fields. Complex defaults also make interfaces hard to understand.
  • "Constant interfaces". These are interfaces holding only constants, which classes implement just to use short names. This is an anti-pattern (a common bad practice). Use a final class or an enum instead.

Interview questions

Q1. Interface vs abstract class, and how do you choose? Use an interface for a contract that many classes — possibly unrelated — implement, and when you need multiple inheritance of type. Use an abstract class when related classes share state and implementation, especially with a template method.

Q2. Why were default methods added? To let interfaces grow — for example, adding stream() to Collection — without breaking every existing implementation.

Q3. Can an interface have a constructor or instance fields? No. It can have only constants, plus abstract, default, static and private methods.

Q4. What happens if a class inherits the same default method from two interfaces? The code does not compile unless the class overrides that method. Inside the override, it can call one of them with InterfaceName.super.method().

1.11 Composition vs inheritance

Why?

In simple words: Instead of being something (inheritance), your class has something and asks it to do the work (composition). This keeps classes loosely connected, and you can swap the helper at runtime.

Inheritance ties a subclass to its parent's implementation — the inner details of how the parent works.

  • When the parent changes, subclasses can break.
  • The relationship is fixed. You can't change it while the program runs.

Composition means an object has a collaborator and passes work to it. This is called delegation. You get the same code reuse, but with looser coupling (less dependence between classes) and flexibility at runtime.

"Favour composition over inheritance" is a core principle of good LLD (low-level design).

Think of a tiffin service. A restaurant doesn't need to be a delivery company. It has a delivery partner. If the partner is bad, it switches to another one tomorrow.

What is happening internally?

  • Inheritance:
  • The subclass object physically contains all the parent's fields.
  • Calls go through the vtable (the per-class table of method pointers).
  • The relationship is fixed at compile time by extends.
  • Composition:
  • The object holds a reference to another object. That reference is usually typed as an interface.
  • It forwards calls to that object.
  • The collaborator can be swapped, for example through constructor injection (passing it in the constructor). So the behaviour is chosen at runtime.

How does it work?

Ask yourself two questions:

  1. "Is X truly a kind of Y, in every situation, forever?" If not, use composition.
  2. "Do I want all of the parent's public methods in my public API?" With inheritance, you get all of them, whether you want them or not.

Example

The first class below shows how inheritance can go wrong:

  1. You call addAll with 3 items. Your override adds 3 to the counter.
  2. Then super.addAll runs. Inside HashSet, addAll calls add() once per item.
  3. But add() is your overridden version, so each call adds 1 more.
  4. Result: 6 instead of 3.

The composition version wraps a Set and doesn't care how the set works inside. The last part shows swapping behaviour at runtime with the Strategy pattern.

// Inheritance gone wrong: a counting set that double-counts
class CountingSet<E> extends HashSet<E> {
    int added = 0;
    @Override public boolean add(E e) { added++; return super.add(e); }
    @Override public boolean addAll(Collection<? extends E> c) { added += c.size(); return super.addAll(c); }
}
CountingSet<String> s = new CountingSet<>();
s.addAll(List.of("a", "b", "c"));
System.out.println(s.added);   // 6, not 3 — HashSet.addAll internally calls add(), which we also counted

// Composition: wrap and delegate — immune to the parent's internal calls
class CountingSet2<E> {
    private final Set<E> inner;                       // has-a
    private int added = 0;
    CountingSet2(Set<E> inner) { this.inner = inner; }
    boolean add(E e) { added++; return inner.add(e); }
    boolean addAll(Collection<? extends E> c) { added += c.size(); return inner.addAll(c); }
    int added() { return added; }
}

// Runtime flexibility: swap pricing behaviour without subclassing Ride
interface PricingStrategy { long fare(double km); }
final class Ride {
    private final PricingStrategy pricing;            // composition + Strategy pattern
    Ride(PricingStrategy pricing) { this.pricing = pricing; }
    long fare(double km) { return pricing.fare(km); }
}

When would I use it?

  • Composition by default. Services built from repositories and clients. Strategy and Decorator patterns. Spring DI (dependency injection) — every injected dependency is composition.
  • Inheritance for:
  • Genuine type hierarchies with stable shared behaviour (Shape → Circle).
  • Framework extension points designed for it (AbstractList, OncePerRequestFilter).
  • Sealed hierarchies of value types (a fixed, closed set of subclasses).

What can go wrong?

  • Inheriting only to reuse code. This leads to deep, fragile hierarchies. You also get subclasses that override methods just to throw UnsupportedOperationException. That breaks the Liskov substitution principle (9.5) — a subclass should work anywhere its parent works.
  • Composition done badly. You end up writing endless one-line forwarding methods. If you forward everything, maybe the type really is a subtype, or the abstraction is wrong.

Interview questions

Q1. Why favour composition over inheritance? Less coupling to the parent's implementation details. Flexibility at runtime, because you can swap collaborators. No fragile base class problems. And you control exactly which API you expose.

Q2. Give an example where inheritance broke something. A HashSet subclass that counts additions double-counts, because addAll calls add internally and both are overridden. Composition avoids depending on the parent's internal self-calls.

Q3. When is inheritance the right choice? When there is a true, stable is-a relationship with shared behaviour, or when a framework class is explicitly designed to be extended.

1.12 equals() and hashCode()

Why?

In simple words: equals decides when two objects mean "the same thing". hashCode gives each object a number so that hash collections can jump to the right place. If two objects are equal, their numbers must also be equal.

== asks: "Is this the very same object in memory?"

Business logic usually asks something else: "Do these two represent the same thing?" For example, two Sku("ABC", 6) objects created separately are the same SKU.

  • equals defines this logical equality.
  • hashCode helps hash-based collections (HashMap, HashSet) find equal objects fast. It narrows the search to one bucket (one slot in the internal array).

What is happening internally?

  • Default behaviour from Object:
  • Object.equals is just this == o.
  • Object.hashCode returns an identity hash — a number tied to that object. In HotSpot it comes from a thread-local random generator and is stored in the object header on the first call. It is not the memory address.
  • How a HashMap uses them (full details in 2.3): 1. First, it calls hashCode() to pick a bucket. 2. Then, it calls equals() to find the exact key inside that bucket.

The trace below shows what happens when hashCode is and isn't overridden:

put(sku1) → hash(sku1) = 37 → bucket 5 → stored
get(sku2) where sku2.equals(sku1):
    if sku2.hashCode() == 37 → bucket 5 → equals() true → FOUND
    if hashCode not overridden → identity hash 9182 → bucket 14 → empty → NOT FOUND (bug)

The contract (the rules every equals/hashCode pair must follow):

  1. equals must be: - reflexive — x.equals(x) is true; - symmetric — if x.equals(y) then y.equals(x); - transitive — if x equals y and y equals z, then x equals z; - consistent — the same answer every time, if nothing changed; - and x.equals(null) is false.
  2. If a.equals(b), then a.hashCode() == b.hashCode(). (This is mandatory.)
  3. Equal hash codes do not mean the objects are equal. Two different objects may share a hash code. This is a collision. It is allowed; it just makes lookups slower.

How does it work?

To implement equals and hashCode:

  1. If this == o, return true. This is a fast shortcut.
  2. Check the type with instanceof. (Or use getClass() if you want strict equality, where a subclass object is never equal to a parent object.)
  3. Compare the significant fields — the ones that define identity.
  4. Build hashCode from exactly the same fields. Use Objects.hash(...) or the "multiply by 31" pattern.

Example

The second half shows the mutable-key disaster:

  1. A Tag named "gold" is added to the set. It goes into the bucket for "gold"'s hash.
  2. Then the name is changed to "platinum". Its hash changes too.
  3. contains(t) now looks in the "platinum" bucket. That bucket is empty.
  4. The entry is stuck in the old bucket — unreachable but still in memory. That is a leak.
public final class Sku {
    private final String code;
    private final int packSize;
    public Sku(String code, int packSize) { this.code = code; this.packSize = packSize; }

    @Override public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Sku other)) return false;          // also handles null
        return packSize == other.packSize && code.equals(other.code);
    }
    @Override public int hashCode() { return 31 * code.hashCode() + packSize; }   // same fields as equals
}

Set<Sku> set = new HashSet<>();
set.add(new Sku("ABC", 6));
System.out.println(set.contains(new Sku("ABC", 6)));   // true. Without hashCode(): false

// Records generate correct equals/hashCode/toString automatically
record SkuKey(String code, int packSize) {}

// The mutable-key disaster
class Tag { String name; Tag(String n) { name = n; }
    public boolean equals(Object o) { return o instanceof Tag t && t.name.equals(name); }
    public int hashCode() { return name.hashCode(); } }
Set<Tag> tags = new HashSet<>();
Tag t = new Tag("gold"); tags.add(t);
t.name = "platinum";                       // hash changes after insertion
System.out.println(tags.contains(t));      // false — searching the wrong bucket
System.out.println(tags.size());           // 1 — the entry is stuck: unreachable but still referenced (leak)

When would I use it?

  • Value objects and keys: Money, Sku, composite map keys (keys made of several fields), and comparing DTOs in tests. Prefer records — they generate a correct equals and hashCode for you.
  • JPA entities are special.
  • Base equality on a stable business key, or on the ID with care. The ID is null until the entity is saved (persisted).
  • Never include lazy collections (collections loaded from the database only when first used).
  • A common safe pattern: equals compares a non-null ID, and hashCode returns a constant (getClass().hashCode()).

What can go wrong?

  • Overriding equals without hashCode. Hash collections can't find equal objects. Sets end up holding "duplicates".
  • Mutable fields in hashCode. You change a field after inserting the object. The entry becomes lost.
  • instanceof with subclasses that add fields. This can break symmetry: point.equals(colorPoint) is true, but the reverse is false. Make value classes final, or use getClass().
  • double fields compared with ==. Use Double.compare instead. For arrays, use Arrays.equals and Arrays.hashCode.

Interview questions

Q1. What is the equals/hashCode contract? Equal objects must have equal hash codes. Equal hash codes do not require the objects to be equal. equals must be reflexive, symmetric, transitive and consistent, and must return false for null.

Q2. What happens if you override equals but not hashCode? Two equal objects usually get different hash codes and land in different buckets. So HashMap.get and HashSet.contains fail, and sets accept logical duplicates.

Q3. What happens if two unequal objects have the same hashCode? That is a collision. They share a bucket, and equals tells them apart. Everything stays correct, but lookups slow down if collisions happen often.

Q4. Why should map keys be immutable? If a field used in hashCode changes after insertion, the entry stays in its old bucket. Lookups now compute a different bucket, so the entry can't be found — and it leaks.

1.13 Comparable and Comparator

Why?

In simple words: Comparable is the one "default" way a class sorts itself, like dates in time order. Comparator is any extra sorting rule you write from outside, like "by rating, then by name".

Sorting, TreeMap, TreeSet, PriorityQueue and binary search all need to know how to order objects.

  • Comparable gives a class its single natural order. This is written inside the class.
  • Comparator gives any number of external orders, such as by rating, then by name. You don't need to touch the class at all.

Think of a merit list. The default order is by marks (Comparable). But the admission office may also sort the same list by category, then by date of birth (a Comparator).

What is happening internally?

  • Comparable<T> has one method: int compareTo(T o).
  • It returns a negative number if this comes first, zero if equal, and positive if this comes after.
  • Comparator<T> is a functional interface (an interface with one abstract method, so you can use a lambda). Its method is int compare(T a, T b).
  • It comes with handy helper methods to build and combine comparators: comparing, comparingInt, thenComparing, reversed, nullsFirst.
  • Who calls these methods:
  • Collections.sort and List.sort use TimSort. It is stable — equal elements keep their original order. It is O(n log n) and very fast on data that is already partly sorted.
  • TreeMap calls compare at every node of its red-black tree (a self-balancing binary search tree).
  • PriorityQueue calls it when moving elements up or down the heap (sift-up/sift-down).

How does it work?

Look at Comparator.comparingInt(Employee::level).thenComparing(Employee::name). It works like this:

  1. Compare the two employees by level.
  2. If the levels differ, that's the answer.
  3. Only if the levels are equal, compare by name.

Each thenComparing wraps the previous comparator. So you can chain as many tie-breakers as you need.

Example

The last part shows the overflow bug. a - b looks fine, but Integer.MIN_VALUE - 1 is too small for an int. It wraps around to a large positive number. So the comparator gives the wrong sign.

record Employee(String name, int level, double rating) implements Comparable<Employee> {
    @Override public int compareTo(Employee o) { return Integer.compare(level, o.level); }   // natural order
}

List<Employee> list = new ArrayList<>(List.of(
        new Employee("Asha", 2, 4.1), new Employee("Bharat", 3, 3.9), new Employee("Chirag", 2, 4.8)));

Collections.sort(list);                                       // by level: Asha(2), Chirag(2), Bharat(3) — stable
list.sort(Comparator.comparingInt(Employee::level)
        .thenComparing(Employee::rating, Comparator.reverseOrder())
        .thenComparing(Employee::name));                      // level asc, rating desc, name asc
                                                              // -> Chirag(2,4.8), Asha(2,4.1), Bharat(3,3.9)

PriorityQueue<Employee> best = new PriorityQueue<>(Comparator.comparingDouble(Employee::rating).reversed());
TreeMap<String, Integer> ci = new TreeMap<>(String.CASE_INSENSITIVE_ORDER);

// The overflow bug
Comparator<Integer> broken = (a, b) -> a - b;
System.out.println(broken.compare(Integer.MIN_VALUE, 1));   // positive (overflow!) -> MIN_VALUE sorts after 1
Comparator<Integer> correct = Integer::compare;

When would I use it?

  • Comparable when a type has one obvious order: dates, money, version numbers.
  • Comparator for everything else:
  • sorting DTOs for the UI;
  • heaps in DSA, like PriorityQueue<int[]> ordered by distance;
  • leaderboards (score descending, then time ascending);
  • TreeMap with custom keys.

What can go wrong?

  • a - b comparators overflow. Always use Integer.compare, Long.compare or comparingInt.
  • compareTo inconsistent with equals in a TreeSet/TreeMap. These collections use compare, not equals, to detect duplicates. So two different objects that compare as 0 are treated as duplicates. One is silently dropped. Example: ordering employees only by level.
  • Comparators that aren't transitive (they give random or inconsistent results). TimSort can detect this and throws "Comparison method violates its general contract!".
  • Null elements. compareTo(null) throws a NullPointerException (NPE). Use Comparator.nullsFirst or nullsLast.

Interview questions

Q1. Comparable vs Comparator? Comparable defines a class's single natural ordering, written inside the class. Comparator defines external orderings; you can combine them, and the class itself does not need to change.

Q2. Why not write return a - b? Because it can overflow for large values or values with mixed signs. Then the result has the wrong sign and the sort order is wrong.

Q3. What does "consistent with equals" mean and why does it matter? It means compareTo returns 0 exactly when equals returns true. Sorted collections use compare to decide uniqueness, so if the two disagree, distinct elements get dropped or merged.

Q4. Which algorithm does List.sort use, and is it stable? TimSort — a stable mix of merge sort and insertion sort, with O(n log n) worst case.

1.14 Immutable objects

Why?

In simple words: An immutable object can never change after it is created. So many threads can share it safely, you can use it as a map key, and you never have to ask "who changed this?".

Once an immutable object is built, its state never changes. Because of that, it is:

  • Automatically thread-safe. There is nothing to synchronise.
  • A safe map key. Its hash code can never change.
  • Safe to cache and share. Nobody can modify it behind your back.
  • Easy to reason about. No "who changed this?" debugging.

Money, IDs, configuration snapshots and events should be immutable.

Think of a printed train ticket. Once printed, nobody edits it. If you change your journey, you get a new ticket.

What is happening internally?

  • final fields get safe-publication guarantees from the JMM (Java Memory Model, the rules for what one thread sees of another thread's writes).
  • Any thread that sees the object reference also sees the final fields fully set up. No locks are needed.
  • This holds as long as this doesn't escape during construction — that is, the constructor doesn't hand this to another thread before it finishes.
  • Shallow vs deep immutability.
  • final List<String> skus stops you from pointing the field at a different list.
  • But it does not stop skus.add(...).
  • True immutability needs the contents to be immutable too. You get this with defensive copies (your own private copy) or unmodifiable collections.
  • New objects are cheap. The JVM and GC are tuned for many short-lived objects.
  • Allocation is cheap because each thread has its own buffer to allocate from.
  • Young-generation garbage collection (cleaning up new, short-lived objects) is cheap too.
  • So "create a new object instead of changing the old one" is usually cheap.

How does it work?

Recipe:

  1. Make the class final (or give it only private constructors). Then no subclass can add mutable state.
  2. Make all fields private final.
  3. Provide no setters.
  4. Copy mutable inputs in the constructor (for example with List.copyOf). Never return your internal mutable objects.
  5. For "changes", return a new instance. This method is often called a "wither", like withSku(...).

Example

public final class Campaign {
    private final String id;
    private final List<String> skus;
    private final Instant start;            // java.time types are already immutable

    public Campaign(String id, List<String> skus, Instant start) {
        this.id = Objects.requireNonNull(id);
        this.skus = List.copyOf(skus);       // defensive copy + unmodifiable; caller's later edits can't affect us
        this.start = Objects.requireNonNull(start);
    }
    public List<String> skus() { return skus; }            // safe: unmodifiable
    public Campaign withSku(String sku) {                   // "modification" = new object
        List<String> next = new ArrayList<>(skus); next.add(sku);
        return new Campaign(id, next, start);
    }
}

List<String> input = new ArrayList<>(List.of("A", "B"));
Campaign c = new Campaign("C1", input, Instant.now());
input.add("HACK");                        // no effect on c
// c.skus().add("X");                     // UnsupportedOperationException

// Record version (shallowly immutable — copy collections in the compact constructor)
record CampaignR(String id, List<String> skus) {
    CampaignR { skus = List.copyOf(skus); }
}

When would I use it?

Use immutable objects for:

  • value objects (Money, Sku, DateRange);
  • DTOs and API responses (records);
  • events published to Kafka;
  • configuration loaded at startup;
  • cache values and map keys.

Keep mutable objects for entities with a lifecycle (JPA entities) and for builders.

What can go wrong?

  • Forgetting the defensive copy. The caller still holds the original list and can change your "immutable" list.
  • Returning Date or arrays directly. Both are mutable. Use Instant and return copies.
  • Too much copying of huge collections in hot loops. Use persistent collections or builder patterns, or keep immutability only at API boundaries.
  • Records are only shallowly immutable. A record holding an ArrayList can still be changed through that list.

Interview questions

Q1. How do you make a class immutable? Make the class final and all fields private final. Provide no setters. Make defensive copies of mutable inputs and outputs. And return new instances for any change.

Q2. Why are immutable objects thread-safe? Their state never changes after safe construction. So threads reading at the same time can never see half-updated state, and no locks are needed.

Q3. Is a class with only final fields immutable? Not necessarily. A final reference can still point to a mutable object — a list, an array, a Date — and that object must be protected too.

1.15 Exceptions: checked vs unchecked, try-with-resources

Why?

In simple words: When something fails, Java throws an exception that jumps straight to the code that can handle it. Checked exceptions are ones the compiler forces you to deal with, like file and network errors.

Error codes have two problems. People forget to check them. And they mix error handling into the normal logic.

Exceptions fix both:

  • They keep the "happy path" (normal flow) separate from failure handling.
  • They carry context: a message, a stack trace (the list of method calls that led here), and a cause.

Java also has checked exceptions. The compiler forces you to handle or declare them. This is a reminder for recoverable failures like I/O and network errors. C# does not have this.

What is happening internally?

Here is the exception class tree:

Throwable
├── Error                 JVM-level problems: OutOfMemoryError, StackOverflowError — don't catch
└── Exception             checked (must be declared or caught): IOException, SQLException, InterruptedException
    └── RuntimeException  unchecked: NullPointerException, IllegalArgumentException, IllegalStateException,
                          ArithmeticException, IndexOutOfBounds, ConcurrentModificationException

What happens when an exception is thrown:

  1. The JVM creates the exception object.
  2. It captures the stack trace by walking all the stack frames. This is the most expensive part.
  3. Then it unwinds the stack, one frame at a time: - Each method has an exception table in its bytecode. It maps ranges of instructions to their handlers. - If a matching catch covers the current instruction, the JVM jumps there. - If not, it pops the frame (exits that method) and repeats in the caller.
  4. If nobody catches it, the thread ends. The default handler prints the stack trace.

Other points:

  • The checked rule exists only at compile time. The JVM itself treats checked and unchecked exceptions the same.
  • try-with-resources compiles into a finally-like block. It calls close() on each resource, in reverse order of opening.
  • If both the body and close() throw, the close exception is attached to the main one as a suppressed exception. So nothing is lost.

How does it work?

  1. Code inside try throws an exception.
  2. The first catch whose type matches runs. A subclass counts as a match. So order your catches from most specific to least specific.
  3. finally always runs after try/catch, even if there was a return. It does not run on System.exit or a JVM crash.
  4. To re-throw with more context, wrap it: throw new LedgerException("posting failed for " + id, e). This keeps the original exception as the cause.

Example

// Domain exception: unchecked, carries context
public class InsufficientPointsException extends RuntimeException {
    private final String accountId; private final long requested, available;
    public InsufficientPointsException(String accountId, long requested, long available) {
        super("Account %s requested %d but has %d".formatted(accountId, requested, available));
        this.accountId = accountId; this.requested = requested; this.available = available;
    }
}

// try-with-resources + wrapping a checked exception at a boundary
public List<String> readSkus(Path file) {
    try (BufferedReader in = Files.newBufferedReader(file)) {
        return in.lines().map(String::strip).filter(s -> !s.isEmpty()).toList();
    } catch (IOException e) {
        throw new UncheckedIOException("could not read " + file, e);   // keep the cause
    }
}

// finally beats return — and a return in finally swallows exceptions (never do this)
static int f() { try { return 1; } finally { System.out.println("finally runs"); } }
static int g() { try { throw new RuntimeException("lost"); } finally { return 2; } }   // exception silently discarded

// InterruptedException: restore the flag if you can't rethrow
try { Thread.sleep(1000); } catch (InterruptedException e) { Thread.currentThread().interrupt(); return; }

Notes on the example:

  • f() returns 1, but "finally runs" prints first.
  • g() is a trap. The return 2 inside finally throws away the exception. Never return from finally.
  • For InterruptedException, if you can't re-throw, call Thread.currentThread().interrupt(). This sets the interrupt flag again so code higher up knows the thread was asked to stop.

When would I use it?

  • Unchecked exceptions for programming errors and broken business rules (IllegalArgumentException, InsufficientPointsException).
  • Spring and most modern code prefer unchecked exceptions.
  • Map them to HTTP responses in one place, a @ControllerAdvice (Chapter 7.4).
  • Checked exceptions in APIs where the caller can really recover (retry a file read, use a fallback). Or when a library forces them on you (I/O, JDBC). Wrap them at layer boundaries.
  • try-with-resources for everything that is AutoCloseable: streams, readers, JDBC connections and statements, and locks wrapped in closeable helpers.

What can go wrong?

  • Swallowing. catch (Exception e) {} hides failures. At the very least, log and re-throw — or handle it on purpose.
  • Losing the cause. throw new MyException(e.getMessage()) drops the original stack trace. Pass e as the cause.
  • Logging and re-throwing at every layer. The same stack trace fills your logs five times. Log once, at the boundary.
  • Exceptions for control flow. For example, using NumberFormatException to test whether input is numeric in a hot loop. This is slow, because each exception captures a stack trace.
  • Transactions. Spring rolls back on unchecked exceptions by default, but not on checked ones (Chapter 7.12).

Interview questions

Q1. Checked vs unchecked exceptions? Checked exceptions extend Exception (but not RuntimeException), and you must declare or handle them. Unchecked exceptions extend RuntimeException and represent programming errors or conditions you can't recover from.

Q2. Does finally always execute? Yes, after try/catch — even when there is a return. The exceptions are System.exit, a JVM crash or an infinite loop. Also, a return inside finally overrides any exception or return value from the try block.

Q3. What are suppressed exceptions? In try-with-resources, if close() throws after the body already threw, the close exception does not replace the main one. Instead it is attached to the main exception using addSuppressed.

Q4. Should you catch Exception or Throwable? Catch the most specific type you can actually handle. Use a catch-all only at top-level boundaries, for logging and translating errors. Never swallow Errors like OutOfMemoryError (OOM).

1.16 Generics, type erasure and wildcards (PECS)

Why?

In simple words: Generics let you say "this list holds only Strings", and the compiler checks it for you. After checking, Java removes the type details from the compiled code — this is called type erasure.

Before Java 5, collections held plain Object.

  • Every read needed a cast.
  • Wrong types were found only at runtime, as a ClassCastException.

Generics move these checks to compile time. A List<String> can't accept an Integer. And reading from it needs no cast.

What is happening internally?

Type erasure works in three steps:

  1. The compiler checks all the generic types.
  2. Then it erases them. Each type parameter is replaced by its bound. The bound is Object by default, or Comparable for <T extends Comparable<T>>.
  3. Where a value comes out, the compiler inserts a cast.

So at runtime, List<String> and List<Integer> are the same class: ArrayList.

C# is different. C# generics are reified — the runtime knows the real type, such as List<int>. That is why C# allows new T() and List<int>.

Source:    List<String> l = new ArrayList<>();  String s = l.get(0);
Bytecode:  List l = new ArrayList();            String s = (String) l.get(0);   ← cast inserted

What erasure stops you from doing:

  • No primitive type arguments like List<int>. The erased type is Object, and an Object can't hold a raw int.
  • No new T(), no new T[n], no obj instanceof List<String>. The type isn't known at runtime.
  • No overloading f(List<String>) with f(List<Integer>). Both erase to f(List), so they clash.
  • Bridge methods. The compiler generates small extra methods so that overriding still works after erasure.

How does it work?

Variance — whether List<Child> counts as a List<Parent>.

Generics are invariant: List<String> is not a List<Object>. Why? If it were, you could add an Integer to a list of strings through the List<Object> view. That would corrupt the list.

Wildcards (?) bring back flexibility, safely:

  • List<? extends Number> means "a list of some subtype of Number".
  • You can read items as Number.
  • You can't add anything (except null).
  • It is a producer — it gives you values.
  • List<? super Integer> means "a list of Integer or some parent type of it".
  • You can add Integers.
  • Reads give you only Object.
  • It is a consumer — it takes your values.
  • PECS: Producer Extends, Consumer Super.

Think of a tiffin box. If someone only gives you a box of "some kind of Indian food" (producer), you can eat from it, but you can't put random food in. If someone only collects boxes for "any food" (consumer), you can put your paneer in, but you don't know what you'll get out.

Example

// Bounded generic method: works for any comparable type
static <T extends Comparable<T>> T max(List<T> items) {
    T best = items.get(0);
    for (T t : items) if (t.compareTo(best) > 0) best = t;
    return best;
}

// PECS in practice
static double total(List<? extends Number> nums) {              // producer: we only read
    double s = 0; for (Number n : nums) s += n.doubleValue(); return s;
}
static void addDefaults(List<? super Integer> sink) {           // consumer: we only write Integers
    sink.add(0); sink.add(1);
}
total(List.of(1, 2, 3)); total(List.of(1.5, 2.5));             // List<Integer>, List<Double> both OK
addDefaults(new ArrayList<Number>()); addDefaults(new ArrayList<Object>());

// Working around erasure: pass a type token or a factory
static <T> T create(Supplier<T> factory) { return factory.get(); }
static <T> T[] newArray(Class<T> type, int n) {
    @SuppressWarnings("unchecked") T[] a = (T[]) java.lang.reflect.Array.newInstance(type, n);
    return a;
}

// Arrays are covariant — and that's unsafe at runtime
Object[] objs = new String[1];
objs[0] = 42;            // compiles, throws ArrayStoreException at runtime
// List<Object> lo = new ArrayList<String>();   // doesn't compile — generics caught it at compile time

The last part shows why Java made generics invariant. Arrays are covariant (String[] counts as Object[]). So the bad store compiles and fails only at runtime with ArrayStoreException. With generics, the same mistake is caught at compile time.

When would I use it?

  • Every collection and every reusable component: repositories (Repository<T, ID>), API wrappers (ApiResponse<T>), caches (Cache<K, V>), result types.
  • Wildcards in method parameters of library-style utilities, like Collections.copy(List<? super T> dst, List<? extends T> src). Avoid wildcards in return types — they make life hard for callers.

What can go wrong?

  • Raw types like List list = new ArrayList(). They switch off type checking. This causes "heap pollution" — a wrong type gets into a collection, and the ClassCastException appears far away from the real bug.
  • Ignoring unchecked warnings. Each warning marks a place where type safety can break.
  • Deserialising generic types with Jackson/Spring. To read a List<Order>, they need type info that erasure removed. Use TypeReference<List<Order>> or ParameterizedTypeReference.
  • Overcomplicated bounds like <T extends Comparable<? super T>> in business code. Keep generics simple outside libraries.

Interview questions

Q1. What is type erasure? The compiler checks generic types, then replaces type parameters with their bounds and inserts casts. So generic type information is not available at runtime.

Q2. What can't you do because of erasure? You can't use primitives as type arguments, create a T or a T[], use instanceof with a parameterised type, or overload methods that differ only in their type arguments.

Q3. Explain PECS. Producer Extends, Consumer Super. Use ? extends T when the structure produces values that you read. Use ? super T when it consumes values that you write.

Q4. Why isn't List<String> a subtype of List<Object>? Because generics are invariant. Otherwise you could insert non-String objects through the List<Object> reference and corrupt the list.

1.17 Nested, inner, local and anonymous classes

Why?

In simple words: Some small classes are only useful inside one bigger class, so you put them inside it. Be careful: a non-static inner class secretly holds on to its outer object, which can cause memory leaks.

Some classes make sense only inside another class:

  • a Node inside a linked list;
  • a Builder inside the class it builds;
  • an Iterator that walks over a collection's internals.

Nesting keeps them close to their only user. It also lets them access the outer class's private members.

What is happening internally?

Kind Declared Holds a hidden reference to the outer instance? Typical use
Static nested static class Node inside the class No Builders, nodes, DTOs, helper types
Inner (non-static) class Itr inside the class Yes (Outer.this) Iterators that need the outer object's state
Local Inside a method Yes (if inside an instance method), plus copies of captured effectively-final locals Rare
Anonymous new Interface() { ... } Yes (if inside an instance method) Callbacks, before lambdas existed

"Effectively final" means a local variable that is never changed after it is set, even if it isn't marked final.

How the hidden reference works:

  1. An inner class object stores a hidden, compiler-generated field called this$0.
  2. This field points to its outer object.
  3. So as long as the inner object is alive, the outer object can't be garbage-collected (freed from memory).

Lambdas are smarter. They capture this only if they actually use instance members.

Think of a child holding a parent's hand in a crowd. As long as the child (inner object) stays, the parent (outer object) can't leave either.

How does it work?

public class Outer {
    private int secret = 42;
    static class StaticNested { int read(Outer o) { return o.secret; } }   // needs an explicit Outer
    class Inner { int read() { return secret; } }                          // uses the hidden Outer.this
}
Outer.StaticNested sn = new Outer.StaticNested();
Outer outer = new Outer();
Outer.Inner in = outer.new Inner();      // must be created from an outer instance

Key points from the code:

  • A static nested class is created on its own. If it needs an outer object, you must pass one explicitly.
  • An inner class must be created from an outer object, using the special outer.new Inner() syntax.

Example

Here is the leak, step by step:

  1. Each ReportService holds a 50 MB buffer.
  2. Each Task (an inner class) holds a hidden reference to its ReportService.
  3. A long-lived static QUEUE holds the tasks.
  4. So every task in the queue keeps a full 50 MB ReportService alive — even though run() never uses the buffer.

The fix makes Task a static nested class that stores only what it needs.

// The leak: a long-lived cache holding inner-class objects keeps every outer ReportService alive
class ReportService {
    private final byte[] bigBuffer = new byte[50_000_000];
    class Task implements Runnable { public void run() { /* doesn't even use bigBuffer */ } }
    Runnable task() { return new Task(); }      // each Task keeps a hidden ref to its ReportService (+ 50 MB)
}
static final List<Runnable> QUEUE = new ArrayList<>();
// QUEUE.add(new ReportService().task());  -> 50 MB retained per entry

// Fix: static nested class with only what it needs
class ReportService2 {
    static class Task implements Runnable { private final String reportId; Task(String id) { reportId = id; } public void run() { } }
}

When would I use it?

  • Static nested by default: Node in DSA linked lists and tries, Builder, internal value types.
  • Inner classes only when the nested object truly needs the outer instance (for example, collection iterators).
  • Lambdas instead of anonymous classes for single-method interfaces.

What can go wrong?

  • The memory leak shown above. Inner classes or anonymous listeners live longer than their outer object should, and keep it in memory.
  • Serialisation. Serialising an inner class object also serialises the outer object — or fails if the outer one can't be serialised.
  • Capturing loop variables in lambdas. Captured variables must be effectively final. A loop counter changes, so copy it to a local variable first.

Interview questions

Q1. Static nested vs inner class? A static nested class has no reference to an outer instance, so you can create it on its own. An inner class silently holds a reference to its outer instance and needs one to be created.

Q2. How can an inner class cause a memory leak? Its hidden reference to the outer object keeps the outer object — and everything it references — reachable for as long as the inner object lives.

Q3. Why must captured local variables be effectively final? Lambdas and inner classes capture a copy of the value. If later changes were allowed, the copy and the original would drift apart, which is confusing — and across threads it would cause race conditions.

1.18 Enums

Why?

In simple words: An enum is a fixed list of allowed values, like SILVER, GOLD and PLATINUM. The compiler blocks anything outside the list. In Java, each value is a real object that can hold data and methods.

Suppose you store a fixed set of values — order status, tier, channel — as strings or ints. That invites typos and invalid values, like "DELIVRED" or 7.

Enums fix this:

  • The set of values is closed. Nothing else is allowed.
  • The compiler checks the type.
  • In Java, enums are full classes. They can carry data and behaviour.

Think of the coach classes on Indian Railways: SL, 3A, 2A, 1A. There is a fixed list. You can't book a "4A" ticket.

What is happening internally?

  1. Each enum compiles to final class Tier extends java.lang.Enum<Tier>.
  2. Each constant becomes one public static final instance of that class.
  3. These instances are created once, when the class is first initialised.

That makes each constant a singleton (only one instance ever exists). So comparing with == is safe and correct.

Useful built-in methods:

  • values() returns a copy of the array of all constants.
  • valueOf("GOLD") finds a constant by its name.
  • ordinal() gives the constant's position (0, 1, 2…).

Special collections:

  • EnumMap is backed by an array indexed by ordinal.
  • EnumSet is backed by a bit vector (one bit per constant).
  • Both are extremely fast and compact.

How does it work?

  • Constants can pass arguments to the enum's constructor.
  • The enum can have fields and methods.
  • Each constant can override an abstract method with its own version. This is constant-specific behaviour — a compact form of the Strategy pattern.

Example

public enum Tier {
    SILVER(1.0) { Tier next() { return GOLD; } },
    GOLD(1.5)   { Tier next() { return PLATINUM; } },
    PLATINUM(2.0) { Tier next() { return this; } };

    private final double multiplier;
    Tier(double m) { this.multiplier = m; }
    public long apply(long basePoints) { return Math.round(basePoints * multiplier); }
    abstract Tier next();                                        // constant-specific behaviour
}

Tier t = Tier.valueOf("GOLD");
System.out.println(t.apply(100) + " " + t.next());              // 150 PLATINUM

String label = switch (t) {                                      // exhaustive switch, no default needed
    case SILVER -> "Silver member";
    case GOLD -> "Gold member";
    case PLATINUM -> "Platinum member";
};

Map<Tier, Long> members = new EnumMap<>(Tier.class);             // array-backed, ordered by declaration
Set<Tier> premium = EnumSet.of(Tier.GOLD, Tier.PLATINUM);        // bit vector

The switch covers every constant, so it is exhaustive — the compiler knows nothing is missing and no default is needed.

When would I use it?

  • Statuses and state machines (OrderStatus with allowed transitions).
  • Types and categories.
  • Configuration flags.
  • Simple strategies, one per constant.
  • Singletons: enum IdGenerator { INSTANCE; } is the safest singleton in Java.

What can go wrong?

  • Persisting ordinal(). JPA uses EnumType.ORDINAL by default. If you insert a new constant in the middle, every number after it shifts. Every stored row is now wrong. Always use @Enumerated(EnumType.STRING).
  • valueOf on bad input. It throws IllegalArgumentException for unknown names, and it is case-sensitive. Validate external input first.
  • Adding a constant. It breaks clients that switch over every constant. For public APIs, plan for unknown values.

Interview questions

Q1. Why are enums good singletons? The JVM guarantees exactly one instance per constant and thread-safe initialisation. It also blocks reflection and serialisation from creating extra copies.

Q2. Can enums have constructors, fields and methods? Yes. Constructors are automatically private, and each constant can override methods with its own behaviour.

Q3. Why store enums as strings in the database? Ordinals change when constants are reordered or inserted, and that silently corrupts stored data. Names are stable and readable.

1.19 Annotations and reflection

Why?

In simple words: Annotations are labels you stick on code, like @Service. Reflection is how a framework reads those labels while the program runs and then acts on them — creating objects, filling fields, calling methods.

Frameworks need to know things about your code that the Java language itself doesn't say. For example:

  • "This class is a Spring service."
  • "This field maps to the column tenant_id."
  • "This method is a test."

Annotations attach this extra information (metadata) to your code.

Reflection lets a framework read that metadata at runtime and act on your classes. It can create objects, inject fields and call methods.

Spring, Hibernate, Jackson and JUnit are all built on this pair.

Think of luggage tags at an airport. The tag (annotation) does nothing by itself. The baggage system (framework) scans the tag (reflection) and sends the bag to the right plane.

What is happening internally?

  • An annotation is a special kind of interface, declared with @interface.
  • Its retention decides how long it survives:
    • SOURCE — thrown away by the compiler (like @Override);
    • CLASS — kept in the bytecode but not visible at runtime (this is the default);
    • RUNTIME — readable through reflection. This is what frameworks need.
  • @Target limits where you can put the annotation (class, field, method…).
  • Reflection uses the classes Class, Method, Field and Constructor.
  • It reads class metadata at runtime.
  • It can call methods and read fields — even private ones, using setAccessible(true). Since Java 9, module rules can block this.
  • Reflection is slower than a direct call. It does access checks, boxes the arguments (wraps primitives into objects), and is not inlined at first. So frameworks speed things up by:
  • caching metadata;
  • using MethodHandles (a faster way to call methods dynamically);
  • generating bytecode or proxies at runtime (CGLIB, ByteBuddy);
  • or doing the work at compile time with annotation processors (Lombok, MapStruct).

How does it work?

At startup, Spring does roughly this:

  1. Scans the classpath for classes.
  2. Reads @Component/@Service on them through reflection.
  3. Finds their constructors.
  4. Works out the dependencies each one needs.
  5. Creates the beans (instantiates them).
  6. Wraps some of them in proxies (for things like transactions).

Jackson works similarly. It uses reflection over getters, fields and record components to turn objects into JSON.

Example

This example defines a @Masked annotation. A small reflection method reads every field. If a field has @Masked, it prints **** instead of the value.

import java.lang.annotation.*;
import java.lang.reflect.*;

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.FIELD)
@interface Masked {}                           // our own annotation: mask this field in logs

record Customer(String name, @Masked String phone) {}

static String toSafeString(Object o) throws IllegalAccessException {
    StringBuilder sb = new StringBuilder(o.getClass().getSimpleName()).append('{');
    for (Field f : o.getClass().getDeclaredFields()) {
        f.setAccessible(true);
        Object v = f.get(o);
        sb.append(f.getName()).append('=').append(f.isAnnotationPresent(Masked.class) ? "****" : v).append(' ');
    }
    return sb.append('}').toString();
}
// toSafeString(new Customer("Asha", "9876543210")) -> Customer{name=Asha phone=**** }

When would I use it?

  • Mostly you are a user of annotation-driven frameworks: Spring, JPA, validation, Jackson, JUnit.
  • Write your own annotations for cross-cutting concerns — things needed in many places, like timing, auditing or masking (@Timed, @Audited, @Masked). Something must process them: an aspect or a validator.
  • Reflection inside business code is rarely justified.

What can go wrong?

  • Annotations do nothing on their own. Something must process them. A custom @Timed with no aspect behind it is just a comment.
  • Reflection breaks encapsulation and refactoring safety. Method names live in strings, so renaming a method won't update them. It also fails with the module system or GraalVM native images unless you configure it.
  • Performance. Reflective calls in hot paths, without caching, are slow.

Interview questions

Q1. What is annotation retention? It defines how long an annotation lives: SOURCE (only for the compiler), CLASS (in the bytecode, but not at runtime), or RUNTIME (available through reflection, which frameworks need).

Q2. How does Spring use reflection? It scans classes, reads their annotations, finds constructors and fields, creates and injects beans, and builds proxies. It caches this metadata for performance.

Q3. What are the downsides of reflection? Slower calls, broken encapsulation, loss of compile-time safety, and problems with the module system and native images.
