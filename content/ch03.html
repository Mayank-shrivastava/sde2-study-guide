Interviewers assume you know Java 17 or 21. So you must be able to:

  • write streams without thinking,
  • explain what a lambda turns into after compiling,
  • explain records, sealed types and pattern matching.

Virtual threads are covered in depth in 4.12.

3.1 Lambdas and functional interfaces

Why?

In simple words: A lambda is a small piece of code that you pass around like a value. You hand it to a method, and the method runs it when it needs to.

Sometimes you need to pass behaviour to a method. For example: a comparator for sorting, a callback, or a filter rule.

Before Java 8, the only way was an anonymous inner class — a class with no name, written inline. That meant five lines of boilerplate for one line of real logic. Each one also created an extra .class file.

Lambdas fix this. You can pass behaviour as a short value, like o -> o.amount() > 100. This is what made streams, CompletableFuture and Spring's functional configuration practical to use.

If you know C#, a Java lambda is like a C# lambda assigned to a Func or Action delegate.

What is happening internally?

Functional interface. This is an interface with exactly one abstract method. Default methods and static methods don't count.

  • A lambda is an implementation of that one method.
  • The target type — the variable or parameter type the lambda is assigned to — decides which interface it becomes.

Lambdas are not anonymous inner classes. The compiler does something smarter:

  1. It moves the lambda body into a private hidden method. The compiler creates this method itself, so it is called a synthetic method (for example lambda$main$0).
  2. At the place where the lambda is created, it writes an invokedynamic instruction. This instruction means "work out what to do the first time this line runs".
  3. The first time the line runs, the JVM calls a helper called the LambdaMetafactory bootstrap method.
  4. The LambdaMetafactory generates a tiny class at runtime. This class implements the interface and simply calls the synthetic method.
  5. The JVM then links that call site permanently. Later runs skip the setup.

Capturing vs non-capturing.

  • A non-capturing lambda uses no outside variables. It is created once and reused as a singleton (one shared object).
  • A capturing lambda uses outside variables. Each time, it creates a small object that holds the captured values. The JVM's escape analysis (a check that sees the object never leaves the method) can often remove even this allocation.

Effectively final. A local variable used inside a lambda must be effectively final. This means you never change it after you assign it. The reason: the lambda gets a copy of the value, not the variable itself.

source:    list.forEach(x -> System.out.println(x));
bytecode:  invokedynamic accept() → LambdaMetafactory → generated Consumer class → calls lambda$0(x)

How does it work?

Java gives you ready-made functional interfaces in java.util.function. Learn the shape of each one — what goes in and what comes out.

Interface Method Shape C# equivalent
Function<T,R> apply T → R Func<T,R>
BiFunction<T,U,R> apply (T,U) → R Func<T,U,R>
Supplier<T> get () → T Func<T>
Consumer<T> accept T → void Action<T>
Predicate<T> test T → boolean Predicate<T>
UnaryOperator<T> / BinaryOperator<T> apply T → T / (T,T) → T
Runnable / Callable<V> run / call () → void / () → V (may throw) Action / Func<V>

There are also primitive versions, like IntPredicate, IntFunction, ToLongFunction and IntBinaryOperator. They work on int or long directly. So Java does not need to box each number (wrap it in an Integer or Long object). This matters in hot paths — code that runs millions of times.

Method references. When a lambda only calls one existing method, you can write a shorter form called a method reference:

Kind Reference Equivalent lambda
Static Integer::parseInt s -> Integer.parseInt(s)
Bound instance System.out::println x -> System.out.println(x)
Unbound instance String::toUpperCase s -> s.toUpperCase()
Constructor ArrayList::new () -> new ArrayList<>()

"Bound" means the object is already fixed (System.out). "Unbound" means the object comes in as the lambda's argument.

Example

The example below shows three things:

  • Composition: joining small predicates and functions with and, negate, compose and andThen.
  • Your own functional interface: marked with @FunctionalInterface.
  • Effectively final: what happens if you change a captured variable.
Predicate<Order> highValue = o -> o.amount() > 10_000;
Predicate<Order> delivered = o -> o.status() == Status.DELIVERED;
Predicate<Order> rule = highValue.and(delivered).negate();          // composition

Function<Long, Long> gst = p -> p * 118 / 100;
Function<Long, Long> discount = p -> p * 90 / 100;
gst.compose(discount).apply(1000L);     // discount first, then gst -> 1062
gst.andThen(discount).apply(1000L);     // gst first, then discount -> 1062 (same here, order matters generally)

@FunctionalInterface
interface PointsCalculator { long points(Order o); }                 // your own functional interface
PointsCalculator flat = o -> 100;

int threshold = 500;                     // effectively final: captured by copy
Predicate<Order> big = o -> o.amount() > threshold;
// threshold = 600;                      // compile error if uncommented: no longer effectively final

Remember the order: f.compose(g) runs g first, then f. f.andThen(g) runs f first, then g.

When would I use it?

  • Comparators for sorting.
  • Stream operations.
  • Callbacks, such as CompletableFuture.thenApply.
  • Strategy objects that are really just one function — pricing rules, validators.
  • Spring beans of type Function or Supplier.
  • Event handlers.

What can go wrong?

  • Changing a local counter inside a lambda. It won't compile. People then hack around it with int[] count = {0} or an AtomicInteger. This is usually a sign you should use a stream reduction instead, like count() or sum().
  • Checked exceptions. Function cannot throw checked exceptions. So a lambda that does I/O must wrap the exception (for example in UncheckedIOException). Or you write your own functional interface that declares throws.
  • Long multi-line lambdas. They are hard to read. Stack traces also show ugly names like lambda$process$7. Move the logic into a named method and use a method reference.
  • this means something different. Inside a lambda, this is the enclosing object (the class the lambda is written in). Inside an anonymous class, this is the anonymous object itself.

Interview questions

Q1. What is a functional interface? It is an interface with exactly one abstract method. You can use it as the target of a lambda or a method reference. The @FunctionalInterface annotation makes the compiler check this rule.

Q2. How are lambdas implemented — are they anonymous classes? No. The compiler moves the body into a private synthetic method. The lambda object is created through invokedynamic and LambdaMetafactory the first time that line runs. Non-capturing lambdas are cached and reused as singletons.

Q3. Why must captured variables be effectively final? The lambda captures a copy of the value, not the variable. If you could change the variable later, the copy would be out of date. It would also invite data races when the lambda runs on another thread.

Q4. Function vs Supplier vs Consumer vs Predicate? Function takes T and returns R (T→R). Supplier takes nothing and returns T (()→T). Consumer takes T and returns nothing (T→void). Predicate takes T and returns a boolean (T→boolean).

3.2 Streams: the pipeline model

Why?

In simple words: A stream is a factory conveyor belt for your data. You describe the stations — filter, transform, collect — and each item travels down the belt one at a time.

A normal loop mixes two things:

  • What you want — filter, transform, add up.
  • How to loop — indexes, temporary lists, running totals.

Streams let you write only the what. You describe the data transformation as a pipeline. This gives you code that:

  • is easier to read,
  • joins together cleanly,
  • can stop early (short-circuit) when it has enough,
  • can run in parallel if needed.

C# developers: streams are Java's version of LINQ.

What is happening internally?

A stream pipeline always has this shape: source → zero or more intermediate operations → one terminal operation.

Laziness. An intermediate operation (filter, map, …) does not run anything. It only returns a new pipeline stage, linked to the previous one. Nothing happens until you call the terminal operation. This is called lazy evaluation.

One element at a time. When the terminal operation runs:

  1. Java joins all the stages into one chain of small objects called Sinks.
  2. The source's Spliterator (the object that walks over the source data) pushes elements into this chain one at a time.
  3. Element 1 goes through filter → map → collect. Then element 2 does the same. And so on.
  4. So no temporary collection is created between stages.

Stateless vs stateful operations.

  • Stateless operations (filter, map, flatMap, peek) look at each element on its own.
  • Stateful operations (sorted, distinct, and limit in parallel) must remember or hold back elements.
  • sorted is a barrier. It must collect every element before it can pass even one forward.

Short-circuiting. Some operations (limit, findFirst, anyMatch, takeWhile) stop pulling from the source as soon as they have their answer. This is why a stream can even work on an infinite source like Stream.iterate.

One use only. You can consume a stream only once. Using it again throws IllegalStateException.

The diagram shows each element flowing down the whole pipe before the next one starts:

orders.stream().filter(paid).map(Order::amount).limit(3).toList()

element 1 ─► filter ✓ ─► map ─► limit(1/3) ─► list
element 2 ─► filter ✗ (stops here)
element 3 ─► filter ✓ ─► map ─► limit(2/3) ─► list
element 4 ─► filter ✓ ─► map ─► limit(3/3) ─► list  → limit signals "done": source stops, element 5 is never read

How does it work?

Intermediate (lazy) Terminal (triggers execution)
filter, map, mapToInt/Long/Obj, flatMap, distinct, sorted, peek, limit, skip, takeWhile, dropWhile, boxed forEach, collect, toList, reduce, count, min, max, sum, average, anyMatch/allMatch/noneMatch, findFirst/findAny, toArray

map vs flatMap:

  • map turns each element into exactly one element. If your function returns a list, you get a Stream<List<X>> — a stream of lists.
  • flatMap turns each element into a stream. Then it flattens all those streams into one Stream<X>.
  • Think of tiffin boxes. map gives you a row of tiffin boxes. flatMap opens every box and puts all the food on one plate.

reduce: It combines all elements into one value. You give it a starting value (the identity) and a combining function. The function must be associative — grouping must not change the answer, like (a+b)+c == a+(b+c). Example: reduce(0, Integer::sum).

Example

record Txn(String outletId, String type, long points, LocalDate date) {}

// Top 5 outlets by points accrued this month
List<Map.Entry<String, Long>> top5 = txns.stream()
        .filter(t -> t.type().equals("ACCRUAL"))
        .filter(t -> !t.date().isBefore(LocalDate.now().withDayOfMonth(1)))
        .collect(Collectors.groupingBy(Txn::outletId, Collectors.summingLong(Txn::points)))
        .entrySet().stream()
        .sorted(Map.Entry.<String, Long>comparingByValue().reversed())
        .limit(5)
        .toList();

// flatMap: all distinct SKUs across orders
Set<String> skus = orders.stream().flatMap(o -> o.lines().stream()).map(Line::sku).collect(Collectors.toSet());

// Laziness proof: peek prints only for elements actually pulled
Stream.of("a", "bb", "ccc", "dddd")
      .peek(s -> System.out.println("saw " + s))
      .filter(s -> s.length() > 1)
      .findFirst();                       // prints "saw a", "saw bb" — then stops

// Primitive streams avoid boxing
long total = txns.stream().mapToLong(Txn::points).sum();
IntSummaryStatistics stats = IntStream.rangeClosed(1, 100).summaryStatistics();

Look at the "laziness proof". findFirst gets its answer at "bb". So "ccc" and "dddd" are never even read.

When would I use it?

Use streams for business data transformation:

  • filtering,
  • mapping entities to DTOs,
  • grouping and adding up results,
  • building lookup maps from lists,
  • generating reports,
  • validating collections.

In DSA problems, a simple for loop is usually clearer and faster.

What can go wrong?

  • Side effects in lambdas. For example forEach(x -> externalList.add(x)), or changing shared state inside map. These break in parallel and hide what you mean. Use collectors instead.
  • Using peek for real logic. peek is meant for debugging. It may not run at all if the terminal operation can skip elements.
  • Reusing a stream, or storing a Stream in a field.
  • Performance. For small collections inside hot loops, streams add extra object creation and extra method calls. Measure with a profiler before you "optimise" in either direction.
  • Debugging. Stack traces through stream internals are long. Keep pipelines short and move logic into named methods.
  • Checked exceptions inside lambdas must be wrapped.

Interview questions

Q1. What is lazy evaluation in streams? Intermediate operations only build the pipeline; nothing runs until a terminal operation is called. Then each element flows through all the stages, one element at a time. This allows short-circuiting and avoids temporary collections between stages.

Q2. Intermediate vs terminal operations? Intermediate operations return a stream and are lazy. Terminal operations produce a result or a side effect, and they start the execution.

Q3. map vs flatMap? map is one-to-one: one element in, one element out. flatMap maps each element to a stream and then flattens all those streams into one stream.

Q4. Can you reuse a stream? No. After a terminal operation the stream is consumed, and using it again throws IllegalStateException. Create a new stream from the source instead.

3.3 Collectors and groupingBy

Why?

In simple words: A collector is the last station on the stream's belt. It decides what box the items land in — a list, a set, a map, a count or a joined string.

Most real stream code ends with collecting the results. For example:

  • a list,
  • a map by ID,
  • a count per status,
  • a total per outlet,
  • a comma-separated string.

Collectors gives you these patterns ready-made. The official name is mutable reduction: you build up a result by adding into a changeable container. Because Collectors does this for you, you don't hand-write accumulation loops.

What is happening internally?

A Collector<T, A, R> is just four functions working together:

  1. supplier — creates an empty mutable container of type A (for example a new ArrayList).
  2. accumulator — adds one element into that container.
  3. combiner — merges two containers into one. This is used in parallel streams, where each thread fills its own container.
  4. finisher — converts the container A into the final result R.

How groupingBy(classifier, downstream) works:

  1. It keeps a Map<K, A> — one container per key.
  2. For each element, it calculates the key using the classifier.
  3. It gets that key's container, or creates it if it is new.
  4. It adds the element into that container using the downstream collector.

The downstream collector can itself be another groupingBy. You can nest them as deep as you like.

Think of a school teacher sorting answer sheets into piles by section. The classifier is "which section?". The downstream collector is what she does with each pile — count it, total the marks, or just keep the sheets.

How does it work?

// Collectors you'll use weekly
.toList()                                                    // Java 16, unmodifiable
.collect(Collectors.toSet())
.collect(Collectors.toMap(User::id, Function.identity()))   // throws IllegalStateException on duplicate keys!
.collect(Collectors.toMap(User::city, u -> 1, Integer::sum)) // merge function handles duplicates
.collect(Collectors.toMap(k, v, merge, LinkedHashMap::new))  // choose the map type
.collect(Collectors.groupingBy(Emp::dept))                                         // Map<Dept, List<Emp>>
.collect(Collectors.groupingBy(Emp::dept, Collectors.counting()))                  // Map<Dept, Long>
.collect(Collectors.groupingBy(Emp::dept, Collectors.summingDouble(Emp::salary)))
.collect(Collectors.groupingBy(Emp::dept, Collectors.mapping(Emp::name, Collectors.toList())))
.collect(Collectors.groupingBy(Emp::dept, TreeMap::new, Collectors.toList()))      // sorted keys
.collect(Collectors.partitioningBy(e -> e.salary() > 100_000))                     // Map<Boolean, List<Emp>>
.collect(Collectors.joining(", ", "[", "]"))
.collect(Collectors.collectingAndThen(Collectors.toList(), Collections::unmodifiableList))
.collect(Collectors.teeing(Collectors.counting(), Collectors.summingLong(Emp::age), (c, s) -> s / c))  // Java 12

A few notes on the list above:

  • toMap with a merge function (the third argument) tells Java what to do when two elements have the same key.
  • teeing (Java 12) sends every element to two collectors at once, then combines their two results.

Example

// Second-highest distinct salary
Optional<Double> second = emps.stream().map(Employee::salary).distinct()
        .sorted(Comparator.reverseOrder()).skip(1).findFirst();

// Highest-paid employee per department
Map<String, Optional<Employee>> top = emps.stream().collect(Collectors.groupingBy(Employee::dept,
        Collectors.maxBy(Comparator.comparingDouble(Employee::salary))));

// First non-repeating character (LinkedHashMap keeps first-seen order)
Optional<Character> firstUnique = "swiss".chars().mapToObj(c -> (char) c)
        .collect(Collectors.groupingBy(Function.identity(), LinkedHashMap::new, Collectors.counting()))
        .entrySet().stream().filter(e -> e.getValue() == 1).map(Map.Entry::getKey).findFirst();   // 'w'

// Duplicates in a list
Set<Integer> seen = new HashSet<>();
Set<Integer> dups = nums.stream().filter(n -> !seen.add(n)).collect(Collectors.toSet());   // sequential streams only!

// Orders -> Map<customerId, totalAmount>
Map<String, Long> totals = orders.stream().collect(Collectors.groupingBy(Order::customerId, Collectors.summingLong(Order::amount)));

  2. Second-highest salary.
  3. Highest-paid employee per department.
  4. Character frequencies.
  5. First non-repeating character.
  6. Partition numbers into even and odd.
  7. Flatten a List<List<Integer>> and sum it.
  8. Orders → total per customer.

  10. Names per department, joined with commas, sorted.

When would I use it?

  • Building lookup maps from database results: toMap(Entity::getId, identity()).
  • Dashboard numbers: counts and sums per status, per tenant.
  • CSV export: joining.
  • Splitting records into valid and invalid: partitioningBy.

What can go wrong?

  • toMap throws on bad input. Duplicate keys throw IllegalStateException. Null values throw NullPointerException (NPE). So give a merge function and avoid nulls.
  • groupingBy order is random. It returns a HashMap, so key order is not fixed. Pass TreeMap::new (sorted keys) or LinkedHashMap::new (insertion order) when order matters.
  • The seen.add trick is wrong in parallel streams. It is a stateful lambda — it changes shared state, and a plain HashSet is not thread-safe.
  • Grouping huge datasets in memory. When the data is large, do the aggregation in the database with GROUP BY instead.

Interview questions

Q1. Why does Collectors.toMap throw? There are two cases. Duplicate keys without a merge function throw IllegalStateException. Null values throw an NPE.

Q2. How do you count elements per category? Use groupingBy(classifier, counting()).

Q3. groupingBy vs partitioningBy? partitioningBy always splits into exactly two groups, true and false, using a predicate. groupingBy creates as many groups as there are distinct keys.

3.4 Parallel streams

Why?

In simple words: A parallel stream splits your data into pieces and gives each piece to a different CPU core. It is like opening more billing counters when the queue is long.

On a machine with many cores, a big CPU-heavy job can be split across those cores. parallelStream() does this for you. You don't write any thread code yourself.

What is happening internally?

  1. Splitting. The source's Spliterator keeps cutting the data into smaller chunks. This works well for arrays and ArrayList. It works badly for LinkedList and I/O sources, because they can't be cut in the middle cheaply.
  2. Running. Each chunk becomes a task on the common ForkJoinPool. This is one thread pool shared by the whole JVM. It has (cores − 1) worker threads, plus the thread that called the stream.
  3. Work stealing. When a thread finishes its own tasks, it takes ("steals") tasks from the queue of a busy thread. So no core sits idle.
  4. Merging. The partial results are combined using the collector's combiner.

How does it work?

Splitting and merging have a cost. A parallel stream is faster only when all of these are true:

  • There is a lot of data — roughly 10,000+ elements.
  • The work per element is CPU-heavy.
  • The source is easy to split.
  • There is no shared mutable state (no shared variable that threads change).
  • The operations are associative — grouping the work differently gives the same answer.

Example

long primes = LongStream.rangeClosed(2, 5_000_000).parallel().filter(Primes::isPrime).count();   // good fit

// Bad fit: blocking I/O on the shared common pool starves everyone else in the JVM
orderIds.parallelStream().map(id -> restClient.fetch(id)).toList();   // don't

// Wrong result: shared mutable state
List<Integer> out = new ArrayList<>();
IntStream.range(0, 10_000).parallel().forEach(out::add);   // lost elements or ArrayIndexOutOfBoundsException

When would I use it?

Rarely in server code. It fits:

  • offline batch calculations,
  • CPU-heavy transformations over big in-memory arrays,
  • one-off data processing jobs.

For I/O fan-out — calling many services or URLs at once — use your own executor with CompletableFuture, or virtual threads (Chapter 4).

What can go wrong?

  • The common pool is shared by the whole JVM. This includes CompletableFutures that were not given an executor. So one blocking task in it can stall unrelated code elsewhere.
  • Order-dependent operations lose most of the benefit. For example findFirst, forEachOrdered and limit. They force threads to wait for each other.
  • Thread-unsafe collectors or lambdas corrupt the results.
  • Busy servers don't gain anything. Every request already uses a thread. So parallel streams just add fighting for CPU (contention) without adding speed.

Interview questions

Q1. How do parallel streams work? A Spliterator splits the source into chunks. Each chunk runs as a ForkJoin task on the common pool, and idle threads use work stealing to pick up extra tasks. Finally the partial results are combined.

Q2. When are parallel streams a bad idea? With small data; with I/O or other blocking work; with shared mutable state; with order-dependent operations; with sources that split poorly; and inside servers, where the common pool is shared by everything.

3.5 Optional

Why?

In simple words: Optional is a box that may be empty. The method's return type tells the caller "check the box first", so nobody forgets.

When a method returns null, you can't see that in its signature. Every caller must remember to check for null. Someone forgets, and you get a NullPointerException.

Optional<T> puts "this may be missing" right in the return type. The caller can't ignore it. They must decide what to do when the value is absent.

C# developers: this is similar in spirit to nullable reference types (User?), but as a real wrapper object.

What is happening internally?

Optional is a small final wrapper class. It holds either one value or nothing. Optional.empty() is one shared object (a singleton).

It is a value-based class. This means its identity has no meaning. So never use synchronized on it, and never compare two Optionals with ==. Use equals instead.

How does it work?

Optional.of(x)            // x must be non-null (NPE otherwise)
Optional.ofNullable(x)    // empty if x is null
opt.map(f)                // transform if present
opt.flatMap(f)            // f returns Optional — avoids Optional<Optional<T>>
opt.filter(p)
opt.orElse(def)           // def evaluated ALWAYS (eagerly)
opt.orElseGet(() -> def)  // supplier evaluated only when empty (lazy)
opt.orElseThrow()         // NoSuchElementException; or orElseThrow(() -> new NotFound(...))
opt.ifPresentOrElse(consumer, runnable)
opt.stream()              // 0 or 1 element — handy in flatMap

The most important pair to remember:

  • orElse(def) — the default is calculated every time (eagerly), even when a value is present.
  • orElseGet(() -> def) — the default is calculated only when the box is empty (lazily).

Example

Optional<User> u = userRepo.findById(id);      // Spring Data returns Optional

String city = u.map(User::address).map(Address::city).orElse("UNKNOWN");
User mustExist = u.orElseThrow(() -> new NotFoundException("user " + id));

// orElse vs orElseGet
User a = cache.get(id).orElse(loadFromDb(id));           // loadFromDb runs EVERY time, even on a cache hit
User b = cache.get(id).orElseGet(() -> loadFromDb(id));  // runs only on a miss

// Flatten a list of optionals
List<String> emails = users.stream().map(User::email).flatMap(Optional::stream).toList();

When would I use it?

Use it as the return type of a lookup that may find nothing. For example findById or findFirstActiveScheme.

Don't use it for:

  • fields,
  • method parameters,
  • collections. Return an empty collection instead of Optional<List<T>>.

What can go wrong?

  • Calling opt.get() without checking. This just swaps the NPE for a NoSuchElementException. Use orElseThrow() so the intent is clear.
  • orElse(expensiveCall()). The expensive call runs every time, even when the value is present. Use orElseGet.
  • Optional fields. Optional isn't Serializable. It also adds one extra heap object per field.
  • Returning null from a method declared to return Optional. This defeats the whole purpose.

Interview questions

Q1. Why use Optional? To make "value may be absent" visible in the API signature. It forces callers to handle the empty case, so you get fewer NullPointerExceptions.

Q2. orElse vs orElseGet? orElse evaluates its argument eagerly, even when a value is present. orElseGet calls the supplier only when the Optional is empty.

Q3. Where shouldn't you use Optional? In fields, method parameters and collections, and in performance-critical inner loops.

3.6 The java.time API

Why?

In simple words: The old Date and Calendar classes were buggy and confusing. java.time gives you clean, safe types — one for each idea of time — so date bugs become much rarer.

The old classes, java.util.Date and Calendar, had many problems:

  • Mutable. Anyone holding a shared date object could change it by accident.
  • Not thread-safe. SimpleDateFormat gives wrong results when many threads use it at once.
  • Months start from zero. January is 0, which causes off-by-one bugs.
  • Mixed concepts. They mix an exact moment in time with a calendar date.

Our platform runs in 32+ countries. There, a date bug means wrong expiry dates, wrong reports and missed schedules. java.time (Java 8) fixes all of these problems.

What is happening internally?

Every class in java.time is immutable and thread-safe. A "change" like plusDays(1) never edits the object. It returns a new object instead.

Each type models one clear idea:

Type Represents Example use
Instant A point on the UTC timeline (seconds + nanos since epoch) Event timestamps, DB audit columns, logs
LocalDate / LocalTime / LocalDateTime Wall-clock values with no zone Birthdays, business dates, "store opens at 09:00"
ZonedDateTime / OffsetDateTime Date-time with a zone / offset Scheduling in Asia/Kolkata, API payloads
ZoneId A region with DST rules (Asia/Kolkata, Europe/London) Conversions
Duration / Period Time-based amount (hours, seconds) / date-based (days, months) Timeouts / validity periods
DateTimeFormatter Thread-safe formatting/parsing APIs, reports
Clock Source of "now" — injectable Testable time

A few terms from the table:

  • Epoch — the fixed starting point, 1 January 1970 UTC.
  • Wall-clock value — what a clock on the wall shows, with no idea which country it is in.
  • DST (Daylight Saving Time) — some countries move clocks one hour forward in summer and back in winter.

How does it work?

Follow one simple rule:

  1. Store and calculate in UTC, using Instant.
  2. Convert to a time zone only at the edges — in the UI, in reports, or for a user's schedule.

For amounts of time, pick the right type:

  • Use Period for calendar maths. Adding 1 month to 31 Jan gives 28 Feb (or 29 Feb in a leap year).
  • Use Duration for exact elapsed time, like "2 seconds".

Example

Instant now = Instant.now();
ZonedDateTime ist = now.atZone(ZoneId.of("Asia/Kolkata"));
LocalDate today = LocalDate.now(ZoneId.of("Asia/Kolkata"));
LocalDate expiry = today.plusMonths(12);                       // points validity
boolean expired = LocalDate.now().isAfter(expiry);
long daysLeft = ChronoUnit.DAYS.between(today, expiry);
Duration timeout = Duration.ofSeconds(2);
String s = DateTimeFormatter.ISO_LOCAL_DATE.format(today);     // "2026-10-05"

// Testable time: inject a Clock instead of calling now() directly
class ExpiryService {
    private final Clock clock;
    ExpiryService(Clock clock) { this.clock = clock; }
    boolean isExpired(Instant expiresAt) { return Instant.now(clock).isAfter(expiresAt); }
}
new ExpiryService(Clock.fixed(Instant.parse("2027-01-01T00:00:00Z"), ZoneOffset.UTC));   // deterministic tests

The Clock trick matters for tests. If code calls now() directly, the answer changes every second. If you pass in a Clock, a test can give a fixed time. So the test gives the same result every run — it is deterministic.

When would I use it?

Everywhere time appears:

  • expiry of points and coupons,
  • scheduling jobs in a tenant's time zone,
  • audit timestamps,
  • report periods,
  • SLAs and timeouts.

What can go wrong?

  • Using LocalDateTime for event timestamps. It has no zone. So the same value means different moments on servers in different countries. Use Instant.
  • Calling LocalDate.now() with the server's default zone. A server running in UTC will think "today" is still yesterday until 05:30 IST.
  • DST. In zones with DST, some local times don't exist, and some happen twice. India has no DST, but European tenants do.
  • Mixing with old JDBC code that uses Date/Timestamp. Convert at the boundary, for example Timestamp.from(instant).

Interview questions

Q1. Why is java.time better than Date/Calendar? It is immutable and thread-safe. It keeps exact instants separate from local and zoned values. Its API is clear, and its formatter is thread-safe.

Q2. Instant vs LocalDateTime? Instant is one exact moment on the UTC timeline. LocalDateTime is a wall-clock value with no zone, so it can mean different moments in different places.

Q3. How do you make time-dependent code testable? Inject a Clock and call now(clock). In tests, pass Clock.fixed(...) so time does not move.

3.7 Records

Why?

In simple words: A record is a class whose only job is to carry data. You write one line, and Java writes the constructor, getters, equals, hashCode and toString for you.

Classes that only carry data are everywhere: DTOs, events, value objects, composite keys. Each one needed:

  • a constructor,
  • getters,
  • equals,
  • hashCode,
  • toString.

That is about 50 lines of boilerplate, and it is easy to get wrong (1.12). Records (Java 16) generate all of it from a one-line declaration. They are also immutable by design — the values can't change after creation.

C# developers: this is the same idea as a C# record.

What is happening internally?

When you write record Money(long paise, String currency) {}, the compiler turns it into a final class extends java.lang.Record with:

  • a private final field for each component,
  • a canonical constructor — the one constructor that takes all components,
  • accessor methods named exactly after the components (paise(), not getPaise()),
  • equals, hashCode and toString that use all components. These are built through invokedynamic and the ObjectMethods helper.

What records can do:

  • implement interfaces,
  • have static fields and static methods,
  • have extra instance methods.

What records cannot do:

  • extend another class (they already extend Record),
  • declare extra instance fields.

How does it work?

You can add a compact constructor. It has no parameter list. It runs before the fields are assigned. So you use it to check inputs (validation) or to clean them up (normalisation), for example converting "inr" to "INR".

Example

public record Money(long paise, String currency) implements Comparable<Money> {
    public Money {                                             // compact constructor
        if (paise < 0) throw new IllegalArgumentException("negative amount");
        currency = Objects.requireNonNull(currency).toUpperCase();   // normalise before assignment
    }
    public static Money inr(long paise) { return new Money(paise, "INR"); }
    public Money plus(Money o) {
        if (!currency.equals(o.currency)) throw new IllegalArgumentException("currency mismatch");
        return new Money(paise + o.paise, currency);
    }
    @Override public int compareTo(Money o) { return Long.compare(paise, o.paise); }
}

record OrderPlaced(String eventId, String tenantId, List<String> skus, Instant at) {
    OrderPlaced { skus = List.copyOf(skus); }                  // records are only SHALLOWLY immutable
}

Money a = Money.inr(500), b = new Money(500, "inr");
System.out.println(a.equals(b) + " " + a);                     // true Money[paise=500, currency=INR]

Note OrderPlaced. A record's fields are final, but a List inside it can still be changed by whoever holds it. That is what "shallowly immutable" means. List.copyOf makes a read-only copy, so the record is truly safe.

When would I use it?

  • API request and response DTOs.
  • Kafka event payloads.
  • Value objects (like Money).
  • Composite map keys — a key made of two or more values.
  • Query projections — Spring Data supports records as projections.
  • Configuration properties — @ConfigurationProperties records.
  • Returning more than one value from a method.

What can go wrong?

  • JPA entities can't be records. Hibernate needs a no-arg constructor, mutable state, and the ability to create proxies (subclasses). Use records only for DTOs and projections.
  • Mutable components leak. A List or array inside a record can still be changed, unless you copy it in the compact constructor. Arrays have another problem: the generated equals compares them by reference, not by contents.
  • Every component is part of equals. This includes ones you may not want, like timestamps. So choose components with care.
  • Changing a record's components breaks its JSON. Its serialised form changes, which is a breaking change for clients.

Interview questions

Q1. What does a record generate? Private final fields, a canonical constructor, accessor methods, and equals/hashCode/toString that use all components.

Q2. Records vs Lombok @Data? Records are part of the language, they are immutable, and they need no annotation processing. @Data generates mutable getters and setters, and it needs the Lombok library. Use records for DTOs and value objects.

Q3. Can a JPA entity be a record? No. JPA needs a no-arg constructor, mutable fields, and classes it can subclass to create proxies.

3.8 Sealed classes and pattern matching

Why?

In simple words: A sealed type says "these are the only possible kinds, no others". Then when you switch over it, the compiler can check you handled every kind — and shouts if you forget one.

Some domains have a closed set of variants. For example, a payment result is Success, Declined or Pending — nothing else.

With a normal open interface, the compiler can't know all the variants. So it can't check that your switch handles every case. When someone adds a new variant, it silently falls into default, and the bug ships.

Two features fix this:

  • Sealed types make the hierarchy closed. The compiler knows the full list of subtypes.
  • Pattern matching lets you check a type and pull out its data in one step. So the compiler can verify the switch is exhaustive — it covers every case.

Together they give Java algebraic data types — a type that is "exactly one of these fixed shapes".

Think of a railway ticket status: Confirmed, RAC or Waitlisted. There is no fourth option. A sealed type lets you say that in code.

What is happening internally?

Sealed declaration.

  • sealed interface PaymentResult permits Success, Declined, Pending stores the allowed subclasses in the class file, in the PermittedSubclasses attribute.
  • The JVM refuses to load any other subclass.
  • Each permitted subclass must itself be final, sealed or non-sealed.

Pattern matching for instanceof (Java 16). if (o instanceof Order ord) checks the type and creates the variable ord in one go. No cast is needed.

Pattern matching for switch and record patterns (Java 21).

  • case Declined(String reason) when … does three things at once: 1. checks the type, 2. deconstructs the record — pulls its fields out into variables, 3. applies a guard — the extra when condition.
  • Pattern switches compile to invokedynamic with SwitchBootstraps.typeSwitch.
  • Because the hierarchy is sealed, the compiler knows all the cases. So no default is needed.
  • If you add a new variant, every switch that doesn't handle it becomes a compile error.

How does it work?

  1. Declare the sealed hierarchy. Records make ideal leaves (the final concrete types).
  2. Switch over the base type, with one case per variant.
  3. Later, add a new variant. Every switch that doesn't cover it now fails to compile, until you handle it.

Example

public sealed interface PaymentResult permits Success, Declined, Pending {}
public record Success(String txnId, long paise) implements PaymentResult {}
public record Declined(String reason) implements PaymentResult {}
public record Pending(Instant retryAt) implements PaymentResult {}

static String describe(PaymentResult r) {
    return switch (r) {
        case Success(String txnId, long paise) -> "paid %d paise, txn %s".formatted(paise, txnId);
        case Declined(String reason) when reason.contains("limit") -> "over limit — ask for another method";
        case Declined d -> "declined: " + d.reason();
        case Pending(Instant at) -> "retry at " + at;
    };                                    // exhaustive: no default needed
}

// instanceof pattern
Object payload = readMessage();
if (payload instanceof OrderPlaced op && !op.skus().isEmpty()) handle(op);

When would I use it?

  • Results and errors: Result = Ok | Err.
  • Domain events: OrderEvent = Placed | Paid | Shipped | Cancelled.
  • State machines.
  • Command types in a CQRS handler (CQRS = keeping write commands separate from read queries).
  • Parsed syntax-tree (AST) nodes. The rules engine in 11.12 uses a sealed Condition.

What can go wrong?

  • Adding default to a sealed switch. It silently switches off the exhaustiveness check. A new variant will then fall into default without any compile error.
  • Placement rules across modules or packages. Permitted subclasses must be in the same module. If you are not using modules (the unnamed module), they must be in the same package.
  • Case order matters. Guards (when) are checked from top to bottom. Put specific cases before general ones. Otherwise the compiler reports a dominated pattern — a case that can never be reached.

Interview questions

Q1. What are sealed classes for? To restrict which classes can extend a type. This makes the hierarchy closed and known to the compiler, so pattern-matching switches can be checked for exhaustiveness.

Q2. What does pattern matching for switch add? It allows type patterns, record deconstruction and guards (when) in case labels. The compiler also checks exhaustiveness over sealed types.

Q3. How does this compare to the Visitor pattern? It reaches the same goal — one operation per variant — without the boilerplate of double dispatch (the accept/visit back-and-forth calls). A new operation is just a new method with a switch.

3.9 Switch expressions, var and text blocks

Why?

In simple words: Three small features that make everyday code shorter and safer: a switch that returns a value and never falls through, var to skip repeating long types, and """ for clean multi-line strings.

Each feature removes a common bug or a lot of noise:

  • Old switch statements fell through to the next case when you forgot a break. They also couldn't return a value.
  • Long generic types made variable declarations hard to read.
  • Multi-line SQL or JSON strings needed + and \n everywhere.

What is happening internally?

Switch expressions (Java 14).

  • case X -> arms never fall through.
  • The whole switch yields a value — you can assign it to a variable.
  • Inside a block arm { ... }, use yield to return the value.
  • The compiler checks exhaustiveness for enums and sealed types.

var (Java 10).

  • The compiler works out the type of a local variable from its right-hand side. This is type inference, and it happens at compile time.
  • The variable still has one fixed type. This is not dynamic typing like JavaScript.
  • It only works for local variables that have an initial value. It doesn't work for fields, parameters or return types.
  • C# developers: it is the same as C# var.

Text blocks (Java 15).

  • A """ literal can span many lines.
  • The compiler removes the common indentation and makes line endings consistent.
  • The result is an ordinary String.

How does it work?

int bonus = switch (tier) {
    case SILVER -> 100;
    case GOLD, PLATINUM -> 250;          // multiple labels, no fall-through
};
String label = switch (code) {
    case 1 -> "one";
    default -> { log.debug("unknown {}", code); yield "other"; }
};

var byOutlet = new HashMap<String, List<Order>>();   // inferred HashMap<String, List<Order>>
for (var e : byOutlet.entrySet()) { /* e is Map.Entry<String, List<Order>> */ }

String sql = """
    SELECT outlet_id, SUM(points) AS total
    FROM ledger_entry
    WHERE tenant_id = ?
    GROUP BY outlet_id
    """;

Example

See the code above. In interviews:

  • write switch expressions for state machines and enum mappings,
  • write text blocks for SQL inside @Query annotations.

When would I use it?

  • Switch expressions — for any mapping over an enum or a sealed type.
  • var — when the type is obvious from the right-hand side, like var list = new ArrayList<Order>().
  • Text blocks — for SQL, JSON test fixtures (sample data for tests) and templates.

What can go wrong?

  • var x = getThing(); hides the type when it isn't obvious. This hurts readability.
  • var list = new ArrayList<>(); infers ArrayList<Object>, because there is nothing to infer the element type from.
  • Text block whitespace. Trailing spaces at line ends are removed unless you escape them with \s. A closing """ on its own line adds a final newline.

Interview questions

Q1. Is var dynamic typing? No. The type is inferred once, at compile time, and then it is fixed. var only removes the repeated type name from the declaration.

Q2. What does yield do? It returns a value from a block-style arm ({ ... }) of a switch expression.

3.10 What else is new in Java 21

  • Virtual threads — very light threads managed by the JVM, not the OS. They let you run a huge number of blocking I/O tasks at once (full section: 4.12).
  • Sequenced collections — new interfaces SequencedCollection and SequencedMap. They give the same methods everywhere: getFirst(), getLast(), reversed(), firstEntry(), pollLastEntry(). They work on lists, deques, LinkedHashMap and TreeMap.
  • Record patterns and pattern-matching switch — now final (no longer preview) in 21 (3.8).
  • Generational ZGC — the low-pause garbage collector, now with separate young and old generations (5.5).
  • Mention-only previews (features you can try but which may still change):
  • structured concurrency — start a group of tasks together and treat them as one unit;
  • scoped values — an immutable replacement for ThreadLocal;
  • unnamed variables _ — final in Java 22.
  • String templates were previewed and then withdrawn. So don't mention them as a feature.

Interview questions

Q1. What are the headline features of Java 21? Virtual threads; record patterns and pattern matching for switch (now final); sequenced collections; and generational ZGC. There are also previews of structured concurrency and scoped values.
