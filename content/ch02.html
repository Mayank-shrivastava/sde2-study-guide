This is the Java topic that Indian product companies ask about the most. At SDE2 level, saying "HashMap is O(1)" is not enough. You must explain why it is fast. You must also say what makes it slow, and how each structure is laid out in memory.

2.1 The collections hierarchy and choosing the right one

Why?

In simple words: Java gives you a few standard "containers" for groups of data. Each one is good at some jobs and bad at others. Pick the one that matches how you will read and write the data.

Every program keeps groups of things: orders, users, IDs. If you pick the wrong structure, two bad things can happen:

  • A fast operation becomes slow. For example, an O(1) lookup (constant time — same speed for any size) turns into O(n) (time grows with the number of items).
  • You waste memory.

The Collections Framework gives you a small set of interfaces: List, Set, Queue, Deque and Map. Each interface has several implementations that you can swap. So you write your code against the interface. Then you pick the implementation based on your access pattern — how you will add, find and remove items.

What is happening internally?

Here is the family tree of the main types:

Iterable
└── Collection
    ├── List   : ArrayList (resizable array) · LinkedList (doubly linked nodes) · CopyOnWriteArrayList
    ├── Set    : HashSet (HashMap inside) · LinkedHashSet · TreeSet (TreeMap inside) · EnumSet (bit vector)
    └── Queue  : PriorityQueue (binary heap) · ArrayDeque · BlockingQueues
        └── Deque : ArrayDeque (circular array) · LinkedList
Map (separate root): HashMap · LinkedHashMap · TreeMap (red-black tree) · EnumMap · ConcurrentHashMap · WeakHashMap

Under the hood, almost every class uses one of only four memory layouts:

  1. A contiguous array — items sit side by side in one block of memory.
  2. Linked nodes — each item is in its own small object that points to the next one.
  3. A hash table — the key is turned into a number that picks a slot.
  4. A balanced tree — items are kept sorted in a tree that never gets too tall.

If you know which layout sits under a class, you can work out its speed for each operation. You do not need to memorise tables.

How does it work?

Choose by asking yourself a few simple questions:

  • Do I need the items kept in order?
  • Must every item be unique?
  • Do I look things up by a key?
  • Do I need sorted order, or ranges like "between X and Y"?
  • Do I need the smallest or largest item quickly?
  • Will many threads use it at the same time?

Then match your answer to this table. ("Amortised O(1)" means usually instant, sometimes slow, but fast on average.)

Requirement Pick Layout Key operations
Indexed list, append ArrayList Array get O(1), add O(1) amortised
Stack or queue ArrayDeque Circular array push/pop/offer/poll O(1)
Key → value, fast HashMap Hash table get/put O(1) average
Key → value in insertion/access order LinkedHashMap Hash table + linked list O(1) + ordered iteration
Sorted keys, floor/ceiling/ranges TreeMap Red-black tree O(log n)
Unique elements HashSet / TreeSet Same as maps O(1) / O(log n)
Repeatedly take min/max PriorityQueue Binary heap offer/poll O(log n), peek O(1)
Enum keys or flags EnumMap / EnumSet Array / bit vector O(1), tiny memory
Shared across threads ConcurrentHashMap, CopyOnWriteArrayList, BlockingQueue Chapter 4

Coming from C#? Here is the mapping:

  • List<T> → ArrayList
  • Dictionary → HashMap
  • SortedDictionary → TreeMap
  • Queue / Stack → ArrayDeque
  • PriorityQueue<T,P> → PriorityQueue<T> with a Comparator
  • ConcurrentDictionary → ConcurrentHashMap

Example

Declare the variable with the interface type. Create the object with the implementation class.

List<Order> recent = new ArrayList<>();                 // declare by interface, construct the implementation
Map<String, Long> pointsByOutlet = new HashMap<>();
NavigableMap<Instant, Price> priceHistory = new TreeMap<>();
Deque<Integer> stack = new ArrayDeque<>();
Queue<int[]> pq = new PriorityQueue<>(Comparator.comparingInt(a -> a[0]));

When would I use it?

On every task. In an interview, say your choice and the reason in one sentence. For example: "I'll use a TreeMap, because I need the nearest earlier timestamp (floorKey) in O(log n)."

What can go wrong?

  • Using legacy classes. Vector, Stack and Hashtable lock (synchronise) on every single call, so they are slow. Use ArrayList, ArrayDeque, and HashMap or ConcurrentHashMap instead.
  • Choosing LinkedList "because inserts are O(1)". This is usually wrong in practice (see 2.3).
  • Using a List for "is it present?" checks inside a loop. list.contains is O(n) — it checks items one by one. Inside a loop, the whole thing becomes O(n²). Use a HashSet instead.

Interview questions

Q1. Which collection would you use for X? Decide by how the data will be accessed: random access by index → ArrayList; lookup by key → HashMap; sorted order or ranges → TreeMap; take the min or max again and again → PriorityQueue; first-in-first-out (FIFO) or last-in-first-out (LIFO) → ArrayDeque.

Q2. Why is Map not part of the Collection interface? A map holds key-value pairs and works through keys. It does not fit the Collection contract, which is about single elements added with add(E). Instead, a map gives you collection views of itself: keySet, values and entrySet.

2.2 ArrayList

Why?

In simple words: An ArrayList is a normal array that grows by itself. When it is full, Java makes a bigger array and copies everything across.

Arrays are the fastest structure when you read by index. But an array has a fixed size. ArrayList is a growable array. You get array speed, plus good locality (items sit close together in memory, so the CPU reads them fast). And it resizes itself automatically.

What is happening internally?

Inside, there are just two fields:

transient Object[] elementData;   // backing array (references to elements)
private int size;                 // how many slots are used

size is how many items you have stored. Capacity is the length of the backing array — how many items fit before it must grow.

size = 5, capacity = 10
elementData: [ A | B | C | D | E | _ | _ | _ | _ | _ ]

Key facts:

  • new ArrayList<>() starts with a shared empty array. The first add creates the real array with capacity 10.
  • When the array is full, grow() makes a new array 1.5× the old capacity (old + (old >> 1)). It copies everything with Arrays.copyOf, which is a fast native memory copy.
  • The array holds references (pointers) to your objects, side by side. So looping over it is friendly to the CPU cache. The objects themselves live elsewhere on the heap.
  • A counter called modCount goes up on every structural change (add or remove). Iterators use it to detect changes and fail fast (see 2.10).

Think of a tiffin box with 10 compartments. When all are full, you buy a box with 15 compartments and move the food across.

How does it work?

  • get(i): check that i is in range, then return elementData[i] → O(1).
  • add(e): if size == capacity, grow first (an O(n) copy). Then store at position size and increase size. Growth is rare and the array grows by a multiple each time. So across n adds, the total copying is only O(n). That makes each add amortised O(1) — usually instant, occasionally slow, fast on average.
  • add(i, e) / remove(i): System.arraycopy shifts all items after i right or left → O(n − i).
  • remove(Object): search item by item using equals, then shift → O(n).
  • contains / indexOf: check item by item → O(n).

Why is the average add O(1)? Start at 10 and grow ×1.5 each time. The copies are 10 + 15 + 22 + … and this total stays below 3n. Spread over n adds, each add costs O(1) on average.

Example

List<Integer> ids = new ArrayList<>(expectedCount);   // pre-size: avoids ~log1.5(n) reallocations
for (int i = 0; i < 1_000_000; i++) ids.add(i);

ids.remove(5);                      // removes INDEX 5
ids.remove(Integer.valueOf(5));     // removes VALUE 5  — the classic trap
ids.removeIf(x -> x % 2 == 0);      // single pass, O(n) — better than removing in a loop
List<Integer> page = ids.subList(0, 20);   // VIEW backed by ids: modifying ids structurally invalidates it
ids.trimToSize();                   // shrink capacity to size after bulk loading

When would I use it?

It is the default list for almost everything: query results, DTO lists, DSA arrays when you don't know the size up front, building responses. It is best at two things: adding at the end, and looping over items.

What can go wrong?

  • remove(int) vs remove(Object) confusion with a List<Integer>. remove(5) removes the item at index 5, not the value 5.
  • Removing items one by one from the front, in a loop, is O(n²). Each removal shifts every item after it. Use removeIf, loop from the back, or use an ArrayDeque.
  • subList is a view, not a copy. If you then add to or remove from the parent list, using the view throws ConcurrentModificationException.
  • Not thread-safe. If two threads add at the same time, items can get lost. You may also see ArrayIndexOutOfBoundsException during a resize.
  • Huge lists of boxed numbers waste memory. Each Integer is a full object. For millions of numbers, prefer int[] or a primitive collection library.

Interview questions

Q1. How does ArrayList grow? When the array is full, it creates a new array 1.5× larger and copies the elements over. Because it grows by a multiple each time (geometric growth), adding at the end is amortised O(1).

Q2. What is the default capacity? 10. It is created lazily, only on the first add.

Q3. Time complexity of get, add, add(index), remove(index)? O(1), amortised O(1), O(n), O(n).

2.3 LinkedList

Why?

In simple words: A LinkedList is a chain of small boxes, each holding one item and pointing to the box before and after it. Adding or removing in the middle is cheap only if you are already standing at that spot.

In a doubly linked list, each element knows its previous and next neighbour. So you can insert or remove an element in O(1), without shifting anything. But there is a condition: you must already hold a reference to the neighbour (for example, an iterator's current position). LinkedList implements both List and Deque (a double-ended queue — you can add or remove at both ends).

What is happening internally?

private static class Node<E> { E item; Node<E> next; Node<E> prev; }
transient Node<E> first, last;

first → [prev|A|next] ⇄ [prev|B|next] ⇄ [prev|C|next] ← last

Every element needs its own Node object. A node has an object header (~12 bytes) plus 3 references. That is roughly 24–32 bytes per element, on top of the element itself.

These nodes are scattered across the heap. So the CPU cannot read them in one smooth run. This is called poor cache locality, and it makes the list slow to walk through.

Think of a treasure hunt. Each clue tells you where the next clue is. To reach clue 50, you must visit all 49 before it.

How does it work?

  • addFirst / addLast / removeFirst / removeLast: change a few pointers → O(1).
  • get(i): walk from whichever end is closer → O(n).
  • add(i, e): O(n) to walk to the position, then O(1) to relink.
  • ListIterator.add/remove at the iterator's current position: O(1), because you are already there.

Example

LinkedList<String> ll = new LinkedList<>(List.of("a", "b", "c"));
ll.addFirst("start"); ll.addLast("end");          // O(1)
ListIterator<String> it = ll.listIterator();
while (it.hasNext()) if (it.next().equals("b")) it.add("b2");   // O(1) insert at the cursor

// The trap: index loops are O(n^2)
for (int i = 0; i < ll.size(); i++) ll.get(i);     // each get walks the list

When would I use it?

Rarely. Even for queues and stacks, ArrayDeque is faster and uses less memory.

Real uses are few:

  • You hold iterators and keep inserting or removing in the middle all the time.
  • You need a list that is also a deque, and you need to store null.

In DSA, you usually write your own node class instead (LRU cache, LeetCode ListNode). You don't use LinkedList there.

What can go wrong?

  • Calling get(i) inside a loop. Each get walks the list, so the loop takes quadratic time — O(n²).
  • Memory. It uses 3–5× more memory than an ArrayList with the same elements.
  • It loses in practice. In benchmarks, ArrayList usually beats LinkedList even for middle inserts on lists of moderate size. Why? System.arraycopy moves contiguous memory extremely fast. Following pointers, on the other hand, keeps missing the CPU cache.

Interview questions

Q1. ArrayList vs LinkedList? ArrayList is a contiguous array: O(1) random access, amortised O(1) append, cache-friendly, and low memory. LinkedList is a chain of nodes: O(1) insert/remove at the ends or at a position you already hold, but O(n) access by index and high memory use. Choose ArrayList by default.

Q2. When is LinkedList actually better? When you insert or remove often at an iterator position inside a large list, or when you need a Deque that allows nulls. In other cases, ArrayDeque or ArrayList wins.

2.4 HashMap internals

Why?

In simple words: A HashMap is a set of numbered boxes. From the key itself, Java calculates which box the value goes in — so to find it again, it jumps straight to that box instead of searching everywhere.

You often need to find something by a key, fast. For example: find a user by ID, count how many times each word appears, or look up a product by SKU.

If you keep the data in a list, you must check items one by one. With a million items, that can be a million checks. This is O(n) — the work grows with the size of the data.

A hash table avoids this. It uses the key to calculate where the value should be stored. Finding it later means doing the same calculation and going straight there. So a lookup takes about the same time whether you have 10 items or 10 million. This is called O(1) on average.

Think of a railway parcel office with 16 numbered racks. The clerk does a small sum on your receipt number to pick a rack. When you come back, he does the same sum and walks straight to the right rack.

What is happening internally?

The main fields:

transient Node<K,V>[] table;        // the bucket array; length is ALWAYS a power of two
static class Node<K,V> { final int hash; final K key; V value; Node<K,V> next; }
int size;  int threshold;           // threshold = capacity × loadFactor
final float loadFactor;             // default 0.75
// defaults: capacity 16 (allocated lazily on first put), threshold 12

A few terms:

  • Bucket — one slot in the table array.
  • Capacity — the number of buckets (the array length).
  • Load factor — how full the table may get before it grows. Default 0.75, meaning 75% full.
  • Threshold — the size at which the table grows: capacity × load factor. For the default, 16 × 0.75 = 12.

Here is what the table can look like:

table (capacity 16)
 [0] → null
 [1] → (hash=17,"apple",3) → (hash=33,"mango",9) → null      ← collision: chain (linked list)
 [2] → null
 ...
 [5] → TreeNode (red-black tree)                              ← chain grew ≥ 8 → treeified
 ...
[15] → (hash=31,"kiwi",1) → null

A collision is when two different keys land in the same bucket. They are then kept in a small linked list (a chain) in that bucket.

Key constants:

  • TREEIFY_THRESHOLD = 8 — a chain this long may turn into a tree.
  • UNTREEIFY_THRESHOLD = 6 — a tree this small turns back into a chain.
  • MIN_TREEIFY_CAPACITY = 64 — the table needs at least this many buckets before any tree is made.

How does it work?

put(key, value) in steps:

  1. Hash spreading. Java computes h = key.hashCode(); hash = h ^ (h >>> 16). This mixes (XORs) the top 16 bits into the bottom 16 bits. Why? Only the low bits are used to choose the bucket. Without mixing, keys whose hashCodes differ only in the high bits would all land in the same bucket.
  2. Index. Java computes i = (n - 1) & hash. Here n is always a power of two, so n - 1 is all ones in binary (16 → 1111). So this & is a fast way to do hash % n.
  3. Empty bucket? If table[i] is empty, put a new Node there. Done.
  4. Look for the same key. Otherwise, walk through the bucket. If a node has the same hash and key.equals() is true, replace its value and return the old value.
  5. Add a new node. If no node matched, append the new node at the end of the chain. (Java 8+ adds at the tail; Java 7 added at the head.)
  6. Chain too long? If the chain length reaches 8: - If the table has at least 64 buckets, convert this bucket into a red-black tree (a self-balancing sorted tree). Now the worst case in this bucket is O(log n). - Otherwise, resize the table instead. In a small table, too few buckets is the more likely reason for collisions.
  7. Too full? If ++size > threshold, resize the table.

get(key) in steps:

  1. Compute the same hash and the same index.
  2. Check the first node in that bucket.
  3. If it is not a match, walk the list or search the tree.
  4. At each node, compare the hash first (cheap). Call equals only if the hashes match.

Resize in steps:

  1. Make a new table with double the capacity.
  2. For each node, check just one bit: (hash & oldCap).
  3. If that bit is 0, the node stays at index i.
  4. If that bit is 1, the node moves to i + oldCap.

No hash is recomputed. Each old chain simply splits into a "low" chain and a "high" chain, and the order inside each chain is kept.

oldCap = 16 (10000b). Node hash ...0 0101 → bit 16 is 0 → stays at 5
                      Node hash ...1 0101 → bit 16 is 1 → moves to 5 + 16 = 21

Why 0.75 and 8?

  • 0.75 is a balance. A lower value wastes many empty buckets. A higher value makes chains longer.
  • With a decent hash function, chain lengths follow roughly a Poisson distribution (a standard pattern for random events). At this load the average chain length is about 0.5.
  • So the chance of one chain reaching 8 is about 0.00000006 — practically never.
  • That means treeification is a safety net. It protects against bad hashCodes or deliberate collision attacks. It is not the normal path.

Example

Map<String, Integer> freq = new HashMap<>();
for (String w : "to be or not to be".split(" ")) freq.merge(w, 1, Integer::sum);
System.out.println(freq);    // {not=1, or=1, be=2, to=2} — bucket order, not insertion order; never rely on it

// Trace of put("to", 1) into an empty default map:
//  1. table allocated with capacity 16
//  2. "to".hashCode() = 3707; spread: 3707 ^ (3707 >>> 16) = 3707
//  3. index = 15 & 3707 = 11  (3707 = ...1110 0111 1011; low 4 bits 1011 = 11)
//  4. table[11] empty → store Node(3707, "to", 1)
//  later put("to", ...) → same index 11 → hash equal & "to".equals("to") → value updated

// Java 8 API that makes DSA code shorter and atomic-per-call
Map<Integer, List<String>> byLength = new HashMap<>();
for (String w : words) byLength.computeIfAbsent(w.length(), k -> new ArrayList<>()).add(w);
freq.getOrDefault("xyz", 0);
freq.computeIfPresent("be", (k, v) -> v > 1 ? v - 1 : null);   // returning null REMOVES the entry

// Pre-size to avoid resizes when you know n
Map<String, Order> byId = HashMap.newHashMap(100_000);          // Java 19+; else new HashMap<>((int)(n/0.75f)+1)

When would I use it?

All the time:

  • Caches and lookups by ID.
  • Counting and grouping.
  • Memoisation in DSA — saving answers you already computed (Map<String, Integer> memo).
  • Removing duplicates.
  • Two-sum style problems, where you look up the "complement" you need.
  • Adjacency lists for sparse graphs (graphs with few edges).

What can go wrong?

  • Bad or mutable keys. If a key class has no proper hashCode/equals, or you change a key after putting it in (1.12), the entry can no longer be found.
  • All keys colliding. For example, a hashCode that returns a constant. Then every key lands in one bucket, and lookups slow down to O(n). After treeification it is O(log n), but the tree works well only if the keys are Comparable.
  • Iteration order is not stable. It can change after a resize, or between Java versions. Never depend on it. Use LinkedHashMap or TreeMap when order matters.
  • Not thread-safe. Two threads calling put together can lose updates and corrupt the size. In Java 7, a concurrent resize could even create a loop in a chain, so get ran forever. Use ConcurrentHashMap (4.9).
  • Memory. Each entry is a Node object (~32–48 bytes), plus the key and value objects. A map of a million Long → Long takes about 80+ MB.
  • Double lookups. Looping over keySet() and calling get(k) for each key does two lookups per key. Loop over entrySet() instead.

Interview questions

Q1. Explain HashMap internals. It is an array of buckets whose length is always a power of two. The key's hashCode is spread (h ^ h>>>16) and masked to get an index. Keys that collide form a linked list in the bucket; that list becomes a red-black tree when a chain reaches 8 and the table has 64+ buckets. A lookup compares the hash first, then equals. When size goes above capacity × 0.75, the table doubles, and each node either stays at i or moves to i + oldCap, decided by one bit.

Q2. Why is HashMap O(1) and when isn't it? A good hash spreads keys evenly, so each bucket holds about one entry; a lookup is just index arithmetic plus one or two comparisons. It gets slow when many keys collide because of a poor hashCode — O(n) per bucket, or O(log n) once the bucket becomes a tree.

Q3. Why must the capacity be a power of two? So that (n-1) & hash can replace the slower modulo (%), and so that a resize can split each bucket by checking a single bit.

Q4. What changed in Java 8? Long chains are turned into trees (treeification); new nodes are added at the tail instead of the head, which fixed Java 7's infinite loop during concurrent resize; and the hash spreading was simplified.

Q5. Can HashMap have a null key? Yes, one. Its hash is treated as 0, so it is stored in bucket 0. Values can be null too. ConcurrentHashMap allows neither null keys nor null values.

Q6. What happens when two keys have the same hashCode? Both go into the same bucket, and equals tells them apart. Both are stored and found correctly — it just costs one extra comparison.

2.5 LinkedHashMap and building an LRU cache

Why?

In simple words: A LinkedHashMap is a HashMap that also remembers order. It can remember the order you added keys, or the order you last used them — and the second one gives you an LRU cache almost for free.

HashMap gives no promise about order. Sometimes you need fast lookup and a predictable order. Two common cases:

  • Insertion order — the order in which keys were first added. Useful to keep JSON fields in order, or to get the same output every run.
  • Access order — the order in which keys were last used. Useful to throw out the least recently used entry. This is an LRU cache (Least Recently Used).

What is happening internally?

LinkedHashMap extends HashMap. Each entry gets two extra pointers, before and after. These pointers join all entries into one doubly linked list. The map also keeps head and tail pointers to the two ends of that list.

hash table buckets: normal HashMap structure (for O(1) lookup)
linked list:  head ⇄ [k1] ⇄ [k2] ⇄ [k3] ⇄ tail     (insertion or access order)

When accessOrder = true:

  • Every get or put of an existing key moves that entry to the tail. The tail is the "most recently used" end.
  • After each insertion, the map calls removeEldestEntry(head). If your method returns true, the head is removed. The head is the least recently used entry.

Think of a stack of newspapers on a table. Whenever you read one, you put it back on top. When the table is full, you throw away the one at the bottom — the one nobody has touched for longest.

How does it work?

  1. get(k): a normal hash lookup, O(1). Then the node is unlinked and relinked at the tail, also O(1).
  2. put(k, v) for a new key: the entry goes into its bucket and is appended at the tail. Then removeEldestEntry is asked whether to remove the head.
  3. Iteration walks the linked list. So it costs O(size). A plain HashMap must scan every bucket, which costs O(capacity + size).

Example

public class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;
    public LruCache(int capacity) {
        super(capacity, 0.75f, true);            // true = access order
        this.capacity = capacity;
    }
    @Override protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;
    }
}

LruCache<String, String> c = new LruCache<>(2);
c.put("a", "1"); c.put("b", "2");     // order: a, b
c.get("a");                           // order: b, a   (a moved to most-recent end)
c.put("c", "3");                      // insert c → size 3 > 2 → evict eldest = b
System.out.println(c.keySet());       // [a, c]

When would I use it?

  • Small caches inside one process (per request or per instance).
  • When output must always come in the same order.
  • When you need LRU behaviour quickly.

In LeetCode 146 (LRU Cache), interviewers usually want the manual HashMap + doubly linked list version (10.3). Mention this one as the production shortcut. For real production caches, use Caffeine — it has better hit rates, handles concurrency, and supports TTL (time-to-live, i.e. entries expire after a set time).

What can go wrong?

  • Not thread-safe. In access-order mode, even get changes the structure (it moves the entry). So two threads that only read can still corrupt it. Guard it with a lock, or use Caffeine.
  • ConcurrentModificationException with access order. If you call get while looping over the map, it throws. This is because get counts as a structural change in this mode.
  • No TTL. It cannot expire entries by time. It also cannot evict by weight (for example, by how many bytes an entry uses).

Interview questions

Q1. How does LinkedHashMap maintain order? A doubly linked list runs through all the entries. It keeps insertion order by default, or access order when accessOrder is true.

Q2. How do you build an LRU cache in Java quickly? Extend LinkedHashMap with accessOrder=true, and override removeEldestEntry to return size() > capacity.

Q3. Is that LRU cache thread-safe? No — even reads change the order. Synchronise access to it, or use Caffeine or ConcurrentLinkedHashMap-style libraries.

2.6 TreeMap and TreeSet

Why?

In simple words: A TreeMap keeps its keys sorted all the time. So it can answer "what is just before or just after this key?" and "give me everything between A and B" quickly.

A hash map cannot answer questions about order. For example:

  • "What was the price at 14:05?" — that is, the latest price change at or before that time.
  • "Give me all orders between two timestamps."
  • "What is the smallest key greater than x?"
  • "Give me the top or bottom N."

A sorted structure answers all of these in O(log n) — the work grows very slowly, roughly with the number of times you can halve n.

What is happening internally?

TreeMap is a red-black tree. That is a binary search tree (smaller keys go left, larger keys go right) that balances itself.

It follows four rules:

  1. Every node is red or black.
  2. The root is black.
  3. A red node has only black children.
  4. Every path from the root down to a leaf has the same number of black nodes.

Because of these rules, the tree's height stays at most 2·log₂(n+1). So search, insert and delete are O(log n), guaranteed — even in the worst case.

After an insert or a delete, the tree may break the rules for a moment. It fixes them with rotations (small re-arrangements of a few nodes) and by recolouring nodes. Insert needs at most 2 rotations; delete needs at most 3.

            (20,B)
           /      \
       (10,R)    (30,R)
       /   \
    (5,B) (15,B)
in-order traversal = 5, 10, 15, 20, 30  → sorted iteration

How are keys ordered? By the key's compareTo method (if the key is Comparable), or by a Comparator you pass in. equals is not used at all.

TreeSet is simply a TreeMap where every value is the same dummy object.

Think of a dictionary book. Words are always in alphabetical order. So you can open it in the middle and quickly narrow down to the word — or to the word just before it.

How does it work?

Example: floorKey(25) — find the largest key that is ≤ 25, using the tree above.

  1. Start at the root, 20. Since 20 ≤ 25, remember 20 as a possible answer and go right.
  2. Now at 30. Since 30 > 25, go left.
  3. There is nothing on the left. Stop.
  4. The answer is the last remembered key: 20.

Each step throws away about half of the remaining tree. So the search is O(log n).

Example

TreeMap<LocalTime, Long> priceChanges = new TreeMap<>();     // effective time -> price
priceChanges.put(LocalTime.of(9, 0), 100L);
priceChanges.put(LocalTime.of(13, 30), 110L);
priceChanges.put(LocalTime.of(17, 0), 95L);

priceChanges.floorEntry(LocalTime.of(14, 5)).getValue();     // 110 — latest change at or before 14:05
priceChanges.ceilingKey(LocalTime.of(14, 5));                // 17:00
priceChanges.headMap(LocalTime.of(13, 30));                  // keys < 13:30 (a live VIEW)
priceChanges.subMap(LocalTime.of(9, 0), true, LocalTime.of(17, 0), false);
priceChanges.firstKey(); priceChanges.lastEntry(); priceChanges.pollFirstEntry();
priceChanges.descendingMap();

// DSA: sliding window with duplicates -> multiset via TreeMap<value, count>
TreeMap<Integer, Integer> window = new TreeMap<>();
window.merge(5, 1, Integer::sum);
window.computeIfPresent(5, (k, v) -> v == 1 ? null : v - 1);  // remove one occurrence
int maxInWindow = window.lastKey();

When would I use it?

  • Time-series lookups: rates, prices or configs that were effective at a given time.
  • Calendar and booking conflicts: find the neighbouring bookings of a new interval.
  • Leaderboards where you loop in rank order.
  • Range queries: everything between A and B.
  • DSA problems that need a sorted multiset (a sorted collection that allows duplicates): sliding window median, "contains nearby almost duplicate", "my calendar".

What can go wrong?

  • Comparator inconsistent with equals. If two different keys compare as 0, TreeMap treats them as the same key. One silently overwrites the other.
  • null keys throw NPE (NullPointerException), because null cannot be compared. The only exception is a comparator that handles null.
  • Slower than HashMap for plain lookups. It is O(log n) and must follow pointers down the tree. So use it only when you need order.
  • headMap/subMap are views. Changing them changes the original map too.

Interview questions

Q1. TreeMap vs HashMap? TreeMap keeps keys sorted, is O(log n), has navigation methods (floor, ceiling, ranges), needs Comparable keys or a Comparator, and allows no null keys. HashMap has no order, is O(1) on average, and uses hashCode/equals.

Q2. What data structure backs TreeMap? A red-black tree — a self-balancing binary search tree (BST) with height ≤ 2·log₂(n+1). So every operation is O(log n) even in the worst case.

Q3. How would you find the latest price effective at a given time? Store the price changes in a TreeMap keyed by effective time, and call floorEntry(time).

2.7 HashSet, LinkedHashSet and EnumSet

Why?

In simple words: A set is a bag that never holds the same thing twice. Use it to ask "have I already seen this?" in one quick step.

You use a set to:

  • Answer "have I seen this before?" in O(1).
  • Remove duplicates.
  • Do set operations like union (everything in either) and intersection (only what is in both), without writing nested loops.

What is happening internally?

public class HashSet<E> { private transient HashMap<E, Object> map;
    private static final Object PRESENT = new Object();
    public boolean add(E e) { return map.put(e, PRESENT) == null; } }

A HashSet is really a HashMap. Your elements are the keys. Every value is the same shared dummy object. So everything in 2.4 applies here too, including the hashCode/equals rules.

The other sets follow the same idea:

  • LinkedHashSet uses a LinkedHashMap inside, so it keeps insertion order.
  • TreeSet uses a TreeMap inside, so it keeps elements sorted.
  • EnumSet is different. It stores one bit per enum constant inside a long (or a long[] if there are more than 64 constants). So checking membership is a single bit operation — extremely fast and tiny in memory.

Think of a guest register at a wedding gate. Before writing a name, the guard checks whether it is already there. If it is, he does not write it again.

How does it work?

add(e) returns false if e was already in the set. So "detect a duplicate while adding" takes just one line.

For set algebra, use the bulk methods:

  • retainAll — intersection (keep only common items).
  • addAll — union (add everything).
  • removeAll — difference (remove the other set's items).

Example

Set<String> seen = new HashSet<>();
for (String eventId : incomingEventIds)
    if (!seen.add(eventId)) System.out.println("duplicate " + eventId);    // dedupe in one pass

Set<String> eligible = new HashSet<>(outletsInScheme);
eligible.retainAll(activeOutlets);                 // intersection
Set<String> ordered = new LinkedHashSet<>(List.of("c", "a", "b", "a"));   // [c, a, b]
EnumSet<DayOfWeek> weekend = EnumSet.of(DayOfWeek.SATURDAY, DayOfWeek.SUNDAY);

When would I use it?

  • Removing duplicates.
  • "Visited" sets in BFS/DFS (graph searches).
  • Membership checks inside loops.
  • Set algebra across lists of IDs.
  • "First unique element" problems (use LinkedHashSet, since it keeps order).
  • Flags (use EnumSet).

What can go wrong?

The same problems as HashMap keys: a missing hashCode/equals, or elements that change after being added.

Also, retainAll with a List as the argument is O(n·m). For each of your n elements, it searches the m-item list one by one. Pass a Set instead.

Interview questions

Q1. How does HashSet work internally? It wraps a HashMap. Elements are stored as keys with one constant dummy value. Uniqueness comes from how the map treats keys — the same key cannot be stored twice.

Q2. HashSet vs TreeSet vs LinkedHashSet? HashSet: no order, O(1). TreeSet: sorted, O(log n). LinkedHashSet: insertion order, O(1).

2.8 ArrayDeque — your stack and your queue

Why?

In simple words: ArrayDeque is one class that works as both a stack and a queue. It is an array whose ends wrap around in a circle, so adding or removing at either end is instant.

Stacks and queues need O(1) operations at their ends:

  • Stacks (last in, first out): DFS, undo, matching brackets, monotonic stack.
  • Queues (first in, first out): BFS, task buffers, sliding windows.

The older options are poor. Stack is a legacy class and locks (synchronises) on every call. LinkedList creates a new node object for every element. ArrayDeque is a circular array that does both jobs faster.

What is happening internally?

elements: [ _ | _ | C | D | E | _ | A | B ]    (capacity 8)
                ↑ tail          ↑ head
logical order: A, B, C, D, E  (wraps around the end of the array)

Here is how it works inside:

  • Two indices, head and tail, mark the two ends.
  • They move using modular arithmetic. When an index passes the end of the array, it wraps back to the start.
  • When the array fills up, it doubles in size and "unwraps" the items into the new array in order.
  • Every operation at either end is O(1) amortised (usually instant; occasionally a resize, but fast on average). No node objects are created per element.
  • null elements are not allowed. Inside, null means "empty slot". Also, poll returns null to tell you the deque is empty.

Think of a round table in a canteen with numbered seats. People join at one end and leave from the other. When you reach the last seat number, you simply continue from seat 1.

How does it work?

Use as Methods
Stack (LIFO, at the head) push, pop, peek
Queue (FIFO) offer (tail), poll (head), peek
Deque (both ends) offerFirst/Last, pollFirst/Last, peekFirst/Last

The methods come in two families:

  • add / remove / element throw an exception when they fail.
  • offer / poll / peek return a special value instead (false or null).

Prefer the second family in DSA loops.

Example

Deque<Character> stack = new ArrayDeque<>();
for (char c : "{[()]}".toCharArray()) {
    if ("({[".indexOf(c) >= 0) stack.push(c);
    else if (stack.isEmpty() || "({[".indexOf(stack.pop()) != ")}]".indexOf(c)) { System.out.println("invalid"); break; }
}

Deque<int[]> queue = new ArrayDeque<>();     // BFS over a grid
queue.offer(new int[]{0, 0});
while (!queue.isEmpty()) { int[] cell = queue.poll(); /* expand neighbours */ }

When would I use it?

  • Every stack and queue in DSA: BFS, DFS, monotonic stack, sliding-window deque.
  • Task buffers in single-threaded code.
  • Undo history.

If several threads share the queue, use a BlockingQueue instead (4.14).

What can go wrong?

  • push and offer add to different ends. push adds to the head, but offer adds to the tail. If you mix them on the same deque, the order becomes confusing.
  • Adding null throws NPE.
  • Not thread-safe.

Interview questions

Q1. Why prefer ArrayDeque over Stack and LinkedList? Stack is old, synchronised code that extends Vector. LinkedList creates a node object for every element. ArrayDeque is a cache-friendly circular array with O(1) amortised operations at both ends.

Q2. Why can't ArrayDeque hold null? Inside, null is used to mark empty slots. Also, poll/peek return null to say "the deque is empty".

2.9 PriorityQueue — a binary heap

Why?

In simple words: A PriorityQueue always keeps the smallest item at the front. You can peek at it instantly and take it out quickly, without sorting everything.

Many problems keep asking for "the smallest (or largest) item so far". For example:

  • The next job by deadline.
  • The K most frequent elements.
  • The nearest unvisited node in Dijkstra's shortest-path algorithm.
  • Merging K sorted lists.

Sorting everything for each question costs O(n log n) every time. A heap is much cheaper. It gives you the minimum in O(1) and removes it in O(log n).

Think of a hospital emergency ward. The most serious patient is always seen next. But the waiting patients are not kept in a perfectly sorted line.

What is happening internally?

PriorityQueue is a binary min-heap stored in an array. A binary min-heap is a complete binary tree (every level is full except maybe the last, which fills from the left). Its one rule: every parent is ≤ its children.

array: [1, 3, 2, 7, 4, 5]          tree:          1
index:  0  1  2  3  4  5                       /     \
                                              3       2
children of i: 2i+1, 2i+2                    / \     /
parent of i:   (i-1)/2                      7   4   5

Only the root is guaranteed to be the minimum. Siblings are not ordered between themselves. So looping over a PriorityQueue does not give you sorted order.

How does it work?

  • offer(x): put x at the end of the array. Then sift up: while x is smaller than its parent, swap them. This is O(log n).
  • poll(): take the root. Move the last element into the root's place. Then sift down: while it is larger than its smaller child, swap with that child. This is O(log n).
  • peek(): just read the root → O(1).
  • remove(Object) and contains: O(n), because they search item by item.
  • Building from a collection (new PriorityQueue<>(list)): this "heapifies" all items at once in O(n).

Trace of offer(0) into [1,3,2,7,4,5]:

  1. Append 0 at index 6. Its parent is at index 2, with value 2.
  2. 0 < 2, so swap. Now 0 is at index 2. Its parent is at index 0, with value 1.
  3. 0 < 1, so swap. Now 0 is at the root.
  4. The result is [0,3,1,7,4,5,2], with 0 at the root.

Example

PriorityQueue<Integer> minHeap = new PriorityQueue<>();
PriorityQueue<Integer> maxHeap = new PriorityQueue<>(Comparator.reverseOrder());

// Top-K frequent SKUs: keep a MIN-heap of size k by count; the root is the weakest of the current top k
Map<String, Integer> freq = Map.of("A", 9, "B", 3, "C", 7, "D", 1);
PriorityQueue<Map.Entry<String, Integer>> heap = new PriorityQueue<>(Map.Entry.comparingByValue());
for (var e : freq.entrySet()) { heap.offer(e); if (heap.size() > 2) heap.poll(); }
// heap now holds A=9 and C=7 → O(n log k)

// Scheduler: jobs by run time, then priority
record Job(String id, Instant runAt, int priority) {}
PriorityQueue<Job> jobs = new PriorityQueue<>(Comparator.comparing(Job::runAt).thenComparingInt(Job::priority));

When would I use it?

  • Top-K problems.
  • K-way merges (merging K sorted lists).
  • Dijkstra and Prim (graph algorithms).
  • Scheduling by time or priority (timer wheels, cron schedulers).
  • Running medians (using two heaps).
  • Event simulation.

What can go wrong?

  • Expecting sorted iteration or a sorted toString(). You won't get it. To get sorted output, call poll again and again.
  • Changing an element's priority field after adding it. The heap does not notice, so its order breaks. Remove the element and add it again instead. (In Dijkstra, the usual trick is to add a new entry and skip the old, stale ones when you poll them.)
  • Comparator overflow. Writing a[0] - b[0] can overflow with large values and give the wrong sign. Use Integer.compare.
  • Not thread-safe. Across threads, use PriorityBlockingQueue.

Interview questions

Q1. How is PriorityQueue implemented? As an array-based binary min-heap. offer and poll are O(log n) using sift-up and sift-down, and peek is O(1).

Q2. Why use a min-heap of size k to find the k largest elements? The root is the smallest of the current top k. Each new element either replaces the root in O(log k) or is thrown away. So the total time is O(n log k), and memory is only O(k).

Q3. Is PriorityQueue iteration sorted? No. Only the head is guaranteed to be the minimum.

2.10 Iterators: fail-fast vs fail-safe

Why?

In simple words: If you change a list while you are looping over it, things go wrong. Normal Java collections notice this and throw an error at once; concurrent collections instead let you loop safely over a stable picture of the data.

Changing a collection while looping over it causes trouble. The loop can skip elements, see some twice, or read half-updated data.

Java's standard collections fail fast. They throw an exception immediately, instead of quietly giving you wrong results.

Concurrent collections make a different choice. They let you loop safely, either over a snapshot (a frozen copy) or over a weakly consistent view (the live data, which may or may not show recent changes).

Think of a teacher taking attendance from a register. If someone tears out a page in the middle, she stops and complains at once. She does not quietly mark the wrong students.

What is happening internally?

  • Non-concurrent collections keep a counter, int modCount. It goes up on every structural change — an add or a remove. (set does not count, because it doesn't change the size.)
  • When an iterator is created, it saves a copy: expectedModCount = modCount.
  • On each next(), the iterator checks that both numbers still match. If they don't, it throws ConcurrentModificationException (CME).
  • The iterator's own remove() updates both counters. So removing through the iterator is allowed.
  • Fail-safe / weakly consistent iterators work differently:
  • CopyOnWriteArrayList loops over the array snapshot taken when the iterator was created. Later writes are not seen.
  • ConcurrentHashMap iterators walk the live buckets (bins). They may or may not see changes made at the same time, but they never throw.

How does it work?

The enhanced for loop is just a shortcut for an iterator. So for (x : list) list.remove(x) changes the list behind the iterator's back. The next call to next() then throws.

Example

List<Integer> nums = new ArrayList<>(List.of(1, 2, 3, 4));
for (Integer n : nums) if (n % 2 == 0) nums.remove(n);    // throws ConcurrentModificationException

Iterator<Integer> it = nums.iterator();
while (it.hasNext()) if (it.next() % 2 == 0) it.remove(); // correct
nums.removeIf(n -> n % 2 == 0);                           // simplest and O(n)

Map<String, Integer> m = new HashMap<>(Map.of("a", 1, "b", 0));
m.entrySet().removeIf(e -> e.getValue() == 0);            // remove while iterating a map
m.replaceAll((k, v) -> v * 10);                           // modify values in place (not structural)

// Quirk: removing the second-to-last element may NOT throw (hasNext() returns false first)
// -> CME is "best effort", never rely on it for correctness

When would I use it?

To filter a collection in place, use removeIf, iterator.remove(), replaceAll, or "collect first, then remove". When other threads change the collection while you loop, use a concurrent collection.

What can go wrong?

  • Treating CME as a thread-safety tool. It is only best-effort detection — it may not fire every time. And it is not only about threads: single-threaded code can trigger it too.
  • Using CopyOnWriteArrayList for data that changes often. Every write copies the whole array (O(n)). Use it only for data that is read much more than written, such as listener lists.

Interview questions

Q1. What is ConcurrentModificationException and when is it thrown? A fail-fast iterator throws it when the collection was structurally changed after the iterator was created, by anything other than the iterator itself. It detects this using modCount.

Q2. Fail-fast vs fail-safe iterators? Fail-fast iterators throw CME when the collection is changed during the loop (ArrayList, HashMap). Fail-safe or weakly consistent iterators work on a snapshot, or put up with changes, without throwing (CopyOnWriteArrayList, ConcurrentHashMap).

Q3. How do you remove elements while iterating? Use Iterator.remove() or Collection.removeIf, or collect the items to remove first and remove them after the loop.

2.11 Immutable collections, utilities and sorting

Why?

In simple words: An immutable collection cannot be changed after it is made, so nobody can break your data by mistake. Java also gives you ready-made helpers in Collections and Arrays, and its sort methods — you use these daily, so know their traps.

If your class returns its internal list as-is, callers can change it and corrupt your object. Immutable collections fix this: nobody can change them. They are also thread-safe by nature, because there is nothing to change.

The Collections and Arrays utility classes, and the JDK's sort methods, are used constantly. They have a few sharp edges worth knowing.

Think of a printed railway timetable versus a whiteboard. Anyone can scribble on the whiteboard. The printed copy stays the same, no matter who reads it.

What is happening internally?

Two words matter in this table:

  • A view is a window onto another collection. If the original changes, the view shows the change.
  • A copy has its own data. Later changes to the original do not affect it.
Factory Mutability Nulls Notes
List.of(...), Set.of, Map.of (Java 9) Immutable Rejected (NPE) Small, specially built classes; Set.of/Map.of reject duplicates; the iteration order of Set.of/Map.of is deliberately left unspecified
List.copyOf(c) (Java 10) Immutable copy Rejected Independent of the source
Collections.unmodifiableList(l) Read-only view Allowed Changes to l show through
Arrays.asList(arr) Fixed size, backed by the array Allowed set works (it writes into the array), add/remove throw
stream.toList() (Java 16) Unmodifiable Allowed

Sorting:

  • Arrays.sort(int[]) (primitives) uses dual-pivot quicksort. It is O(n log n) on average. It is not stable — stable means equal items keep their original order. For primitives this doesn't matter, because two equal numbers look exactly the same.
  • Arrays.sort(Object[]), List.sort and Collections.sort use TimSort. It is a stable mix of merge sort and insertion sort. It spots runs of data that are already sorted and reuses them. It is O(n log n) in the worst case, and O(n) on input that is already sorted.

How does it work?

Immutability is enforced simply: every method that would change the collection throws UnsupportedOperationException.

A view passes every read through to the collection it wraps. A copy owns its own data.

Example

List<String> view = Collections.unmodifiableList(internal);
internal.add("x");            // view now shows "x" too
List<String> copy = List.copyOf(internal);   // snapshot, unaffected by later changes

int[] arr = {3, 1, 2};
List<int[]> wrong = Arrays.asList(arr);       // List with ONE element: the int[] itself
List<Integer> right = Arrays.stream(arr).boxed().toList();

Integer[] boxed = {3, 1, 2};
Arrays.sort(boxed, Collections.reverseOrder());   // descending needs objects
Arrays.fill(dp, -1); Arrays.copyOfRange(a, 2, 5); Arrays.equals(a, b); Arrays.toString(a);
Collections.frequency(list, "x"); Collections.nCopies(3, 0); Collections.swap(list, 0, 1);
int pos = Collections.binarySearch(sortedList, key);   // negative = -(insertionPoint) - 1

When would I use it?

  • From getters, return List.copyOf(...) or an unmodifiable view.
  • Use List.of / Map.of for constants and test data.
  • Use the immutable factories for DTOs and records.
  • Use the Arrays utilities all the time in DSA.

What can go wrong?

  • List.of with a null element throws NPE. This surprises code that used to use Arrays.asList, which allows nulls.
  • Arrays.asList(...).add() throws UnsupportedOperationException, because the list has a fixed size.
  • Map.of iteration order changes between runs. Don't rely on it in tests.
  • Sorting a huge boxed Integer[] is much slower than sorting an int[].

Interview questions

Q1. Collections.unmodifiableList vs List.copyOf? The first is a read-only view: the original list can still change, and the changes show through the view. The second is an independent immutable copy.

Q2. What sorting algorithms does Java use? Dual-pivot quicksort for arrays of primitives, and TimSort (which is stable) for objects and lists.

Q3. What is the gotcha with Arrays.asList? The list has a fixed size and is backed by the array, so add/remove don't work. And if you pass a primitive array, you get a list with one element: the array itself.
