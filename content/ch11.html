11.1 The system design interview framework

Why?

In simple words: A system design interview is like a vague order — "design a URL shortener". A fixed set of steps helps you ask the right questions, use numbers, and finish on time instead of drawing random boxes.

System design questions are kept vague on purpose. For example: "design a URL shortener".

The strong candidates are not the ones who know the most technologies. They are the ones who: - give the conversation a clear structure, - put numbers on the problem (users, requests per second, data size), and - explain why they chose one option over another (trade-offs).

Without a framework, you jump straight to drawing boxes. You miss requirements. Then you run out of time before you reach the interesting parts.

What is happening internally?

While you talk, the interviewer is checking seven things:

  1. Requirement gathering — do you ask questions to fix the scope?
  2. Estimation — do you reason with numbers?
  3. Design — are your components and data flows sensible?
  4. Depth — can you go deep on the hard parts?
  5. Trade-offs — do you know the other options and what they cost?
  6. Operability — do you think about failures, scaling and monitoring?
  7. Communication — can they follow your thinking easily?

How does it work?

Use this time plan for a 60-minute round. QPS means queries per second — how many requests hit the system each second. DAU means daily active users.

Minutes Step What goes on the board
0–5 Functional requirements 3–5 main use cases; clearly list what is out of scope
5–8 Non-functional requirements DAU, QPS, read/write ratio, latency targets, availability, consistency, durability (data must not be lost), data size, compliance
8–12 Estimates Average and peak QPS, storage per year, bandwidth, cache size
12–16 API 3–6 endpoints or events with their key fields
16–20 Data model Entities, keys, access patterns (how data is read and written) → choice of store with a one-line reason
20–30 High-level architecture Clients → edge/gateway → services → caches/queues → stores; walk one read and one write through it
30–50 Deep dives 2 hard components (you suggest them, the interviewer picks)
50–60 Bottlenecks and evolution How it fails, what happens at 10× growth, monitoring, what you would do differently

Example

This is how you can open a URL shortener question:

"Before designing, let me pin down scope. Users create short links and get redirected; optional custom aliases and expiry; basic click counts. Out of scope: user accounts UI and link editing. Non-functionally, redirects are latency-critical and must be highly available; creation can be slower. Reads dominate — roughly 100:1. Let me estimate…"

Notice what this does. In under a minute, you fixed the scope, said what is out, named the most important non-functional need (fast, always-up redirects) and gave a read/write ratio.

When would I use it?

In every HLD (high-level design) round. Also at work, in real design reviews and RFCs (written design proposals). The same structure makes a good design document.

What can go wrong?

  • Drawing boxes before you know the requirements.
  • Giving no numbers at all.
  • Naming technologies without reasons — for example, just saying "use Kafka".
  • Spending 30 minutes on the API.
  • Going deep on something easy while ignoring the real bottleneck (the slowest, most loaded part).
  • Silence — the interviewer cannot judge thinking they cannot hear.

Interview questions

Q1. How do you approach a system design question? First I clarify the functional and non-functional requirements and estimate the scale. Then I define the APIs and the data model and sketch the architecture. Next I go deep on the hardest components. Finally I discuss bottlenecks, failures and how the system grows — and I justify each choice with its trade-offs.

11.2 Back-of-envelope estimation

Why?

In simple words: Quick rough maths tells you how big the problem really is. A small problem needs one server; a huge one needs many machines, caches and queues. The numbers pick the design for you.

Numbers decide the architecture. For example: - 50 QPS fits easily on one server with one Postgres database. - 500,000 QPS needs sharding (splitting data across many databases), caching and queues.

When you estimate, the interviewer sees that you are designing for this problem. You are not just repeating a standard architecture from memory.

What is happening internally?

First, know roughly how long common operations take. Only the order of size matters, not the exact number. (1 ms = 1,000 µs; 1 µs = 1,000 ns.)

Operation Approximate time
L1 cache / main memory reference 1 ns / 100 ns
Read 1 MB sequentially from memory ~3 µs
SSD random read ~16–100 µs
Round trip within a datacentre ~0.5 ms
Redis GET over the network ~0.5–1 ms
Indexed DB lookup ~1–10 ms
Read 1 MB sequentially from SSD ~0.05–1 ms
HDD seek ~10 ms
India ↔ US round trip ~150–250 ms

The main lesson: memory is very fast, the network adds about a millisecond, the database adds a few milliseconds, and crossing continents costs hundreds of milliseconds.

Capacity rules of thumb (rough numbers you can use in any interview): - A day is 86,400 seconds. Round it to 10⁵ s. So 1 million requests/day ≈ 12 QPS. - Peak traffic is about 2–5× the average. Use 3× unless told otherwise. - One app instance (4–8 CPU cores, running on the JVM): about 1,000–5,000 simple requests per second. - One PostgreSQL/MySQL primary (the main database server): about 5,000–20,000 simple queries per second. It is comfortable up to a few TB of data. - One Redis node: 100,000+ operations per second. Its limit is usually RAM, not speed. - One Kafka partition: about 10 MB/s of writes. A full Kafka cluster can handle millions of messages per second. - Powers of two: 2¹⁰ ≈ 10³ (KB), 2²⁰ ≈ 10⁶ (MB), 2³⁰ ≈ 10⁹ (GB), 2⁴⁰ ≈ 10¹² (TB).

How does it work?

Follow these four calculations:

  1. QPS: users → actions per user per day → requests per day → ÷ 10⁵ → average QPS → × 3 → peak QPS.
  2. Storage: writes per day × bytes per record → storage per day → × 365 × number of years. Multiply again by the replication factor (how many copies you keep).
  3. Bandwidth: read QPS × response size.
  4. Cache size: hot set × object size. The hot set is the data that is read most often — often about 20% of daily reads.

Example

NOVA-like ordering assistant: 10M daily active retailers × 5 API calls = 50M/day ÷ 10⁵ = 500 QPS average, ~1,500 peak. 2M orders/day × 1 KB = 2 GB/day ≈ 730 GB/year → a single well-indexed Postgres primary handles it for a while; partition the orders table by month for retention. Catalogue reads are 10× higher (5,000 QPS) → cache SKU and price data in Redis; hot set ~200k SKUs × 2 KB ≈ 400 MB.

What this tells you: - 1,500 peak QPS and 730 GB/year are small enough for one good Postgres primary for some time. No sharding needed yet. - Splitting the orders table by month (partitioning) makes it easy to delete old data later (retention). - Catalogue reads are much heavier, so they go to a Redis cache. The hot data is only about 400 MB, so it fits easily in memory.

When would I use it?

  • At the start of every design and every capacity plan.
  • When deciding between "one database" and "shard it".
  • When sizing caches, Kafka partitions and pods.

What can go wrong?

  • False precision. Do not do exact maths. Spend about 3 minutes and round hard.
  • Forgetting peaks, replication and indexes. Real storage is often 2–3× the raw data size.
  • Looking at the wrong bottleneck. The limit is usually the database, not the app servers.

Interview questions

Q1. How many QPS is 100 million requests per day? About 1,150 on average (10⁸ / 86,400). At a 3× peak, that is roughly 3,500.

Q2. Why estimate at all? Because the scale decides the architecture. It tells you whether one node is enough or you need sharding, how much caching you need, how much queue throughput you need, and what it will cost.

11.3 Scaling basics: vertical, horizontal and stateless services

Why?

In simple words: When traffic grows, you either buy a bigger machine or add more machines. Adding machines works best — but only if any machine can handle any request, which means the machines must not keep user data in their own memory.

Traffic grows over time. You have two choices: - Buy a bigger machine. This is vertical scaling. - Add more machines. This is horizontal scaling.

Only horizontal scaling can keep growing without a hard limit. It also survives a machine failure, because the other machines keep working. But it needs a design where any instance can serve any request.

What is happening internally?

  • Vertical scaling means more CPU and RAM on one box.
  • Good: it is simple and needs no code changes.
  • Bad: hardware has a maximum size, big machines get expensive, and that one box is still a single point of failure (if it dies, everything dies).
  • Horizontal scaling means N identical instances behind a load balancer (a component that spreads requests across them).
  • It needs stateless services. Stateless means the instance keeps no user session or request data in its own memory between requests.
  • The state lives somewhere shared instead: a database, a cache, or a token the client carries (such as a JWT — a signed token).
  • The data tier is the hard part. App servers are easy to scale — just add more. Databases are harder. They need replication (11.8), partitioning (11.9) and caching (11.5).

Think of a bank with many counters. If any clerk can serve you because your account is in the central system, you can open more counters any time. If only "your" clerk knows your details, you must always wait for that one clerk.

Availability maths: - Components in series (a request must pass through all of them) multiply their availability. Two parts at 99.9% each give 0.999 × 0.999 = 0.998. So the chain is less available than each part. - Redundant components in parallel (any one can do the job) improve availability. Two parts at 99.9% give 1 − 0.001² ≈ 0.999999. - 99.9% availability ≈ 8.8 hours of downtime per year. 99.99% ≈ 53 minutes per year.

How does it work?

Clients → Load balancer → [App 1] [App 2] [App 3]   (stateless, autoscaled)
                              ↓       ↓       ↓
                        Cache (Redis) · DB primary + replicas · Queue · Object storage

The app instances are all the same and hold no state. All shared data sits in the layer below them. So you can add or remove app instances freely (autoscaling).

Example

Take a shopping cart (session state):

  1. The cart is stored in the memory of one app pod.
  2. The user's next request lands on a different pod.
  3. That pod has no cart. The cart looks empty — the design is broken.

The fix: move the cart to Redis (or into a signed token). Now every pod is the same. Kubernetes can add and remove pods freely.

When would I use it?

  • Always design the app tier to be stateless and horizontally scalable.
  • For databases, scale vertically first because it is simpler. Move to replicas or shards only when you need them.

What can go wrong?

  • Sticky sessions hiding state. Sticky sessions send a user always to the same instance. This hides the fact that the service keeps state. It causes uneven load, and sessions are lost when that instance fails (failover).
  • Local file storage on instances. Files saved on one instance are missing on the others.
  • In-memory caches that drift apart. Each instance's local cache can hold a different version of the data.
  • The database becomes the bottleneck. Adding more app servers just sends more load to the same database.

Interview questions

Q1. Vertical vs horizontal scaling? Vertical scaling adds resources to one machine. It is simple, but it has a limit and is a single point of failure. Horizontal scaling adds more machines. It has no hard limit and tolerates failures, but it needs stateless services and load balancing.

Q2. What makes a service stateless? The instance keeps no client-specific state in its memory between requests. All state is moved out to databases, caches or tokens.

11.4 Load balancing

Why?

In simple words: A load balancer is the traffic police at the front. It spreads requests across your servers and stops sending traffic to any server that is sick.

Having many instances only helps if: - traffic is spread across them, and - dead instances stop getting requests.

A load balancer does both. It also does other jobs: - It handles TLS (HTTPS encryption), so the app servers don't have to. This is called terminating TLS. - It routes by path or host name. - It is the first line of defence against too much traffic.

What is happening internally?

  • L4 (transport layer) load balancers route TCP/UDP connections using only IP address and port. They don't read the HTTP request. They are very fast, but they cannot route by URL.
  • L7 (application layer) load balancers understand HTTP. They can route by path, header or cookie. They can terminate TLS, retry failed requests, rewrite requests and rate-limit (cap how many requests a client can send).
  • Health checks regularly test each instance and remove the failing ones.
  • Connection draining lets requests that are already running finish before an instance is removed, for example during a deploy.
  • Global load balancing sends users to the nearest healthy region. It uses DNS/GeoDNS (DNS answers differently based on the user's location) or Anycast (many locations share one IP; the network picks the nearest).
  • In Kubernetes: a Service gives L4 balancing (through kube-proxy). An Ingress or Gateway gives L7 routing. In Azure: Load Balancer is L4; Application Gateway and Front Door are L7.

Ways to pick the next instance (algorithms):

Algorithm Use
Round robin / weighted Identical, stateless instances (weighted gives bigger machines more traffic)
Least connections / least response time Requests that cost very different amounts of work
IP hash / consistent hashing Affinity — the same user or key always goes to the same server (caches, sticky routing)

How does it work?

A request passes through these layers:

DNS → Front Door / CDN (global L7) → regional L7 LB (TLS, path routing) → service pods (L4 Service) → app
  1. DNS points the user to the global edge.
  2. The global L7 layer (Front Door / CDN) picks the nearest healthy region.
  3. The regional L7 load balancer decrypts TLS and routes by path.
  4. The Kubernetes Service (L4) picks one healthy pod.
  5. The app handles the request.

Example

  • /api/orders/* goes to the order service.
  • /api/loyalty/* goes to the loyalty service.
  • /static/* goes to the CDN.

Pods that fail their readiness probes (the "am I ready to serve?" check) are removed within seconds. A canary release — a new version tried on a small slice of users — gets 5% of traffic through weighted routing.

When would I use it?

In front of every horizontally scaled tier. Also between services — often through the service mesh or the Kubernetes Service.

What can go wrong?

  • The load balancer itself becomes a single point of failure. Use managed, redundant load balancers.
  • Bad health checks. Some only test "is the process alive?" and miss real problems. Others fail whenever any dependency has a tiny blip, which removes healthy instances.
  • Sticky sessions make the load uneven.
  • Long-lived connections don't rebalance. WebSockets and gRPC keep one connection open for a long time. When you add new instances, the old connections stay on the old instances, so the new ones get little traffic.

Interview questions

Q1. L4 vs L7 load balancing? L4 routes connections by IP and port. It is fast and works with any protocol. L7 understands HTTP. It routes by path, header or cookie, and it terminates TLS.

Q2. How does a load balancer know an instance is unhealthy? In two ways. Active health checks call the instance regularly — for example an HTTP readiness endpoint or a TCP check. Passive detection watches real traffic for errors or timeouts.

11.5 Caching

Why?

In simple words: A cache keeps a copy of popular data in fast memory. Most requests get their answer from this copy and never touch the slow database.

The fastest request is the one that never reaches the database.

Caching serves data that is read often and changed rarely, straight from memory. This gives two benefits: - Lower latency — from milliseconds down to microseconds. - Protection for the database — it is saved from load it could not handle.

Think of a kirana shop. The shopkeeper keeps the fast-selling items on the counter. Only for rare items does he go to the back storeroom.

What is happening internally?

Cache layers — a request can be answered at any of these levels, from nearest to farthest: browser → CDN → API gateway → in-process cache inside the app (Caffeine) → distributed cache shared by all instances (Redis/Memcached) → the database's own in-memory buffer pool.

Read and write strategies:

Strategy How Trade-off
Cache-aside (lazy) Read the cache → on a miss, load from DB → fill the cache. On a write, update the DB, then delete the key The default choice; data can be stale for a short time; the first read is always a miss
Read-through The cache itself loads from the DB on a miss Simpler app code; but the cache becomes critical
Write-through Write the cache and the DB together, synchronously Reads are always fresh; writes are slower
Write-behind Write the cache; copy to the DB later, asynchronously Fast writes; risk of losing data
Write-around Write only to the DB; cache it when it is read Avoids caching data that is rarely read again

Eviction — which item to throw out when the cache is full: - LRU (least recently used) — the most common. - LFU (least frequently used). - FIFO (first in, first out). - TTL (time to live) — the item expires after a fixed time.

Redis uses an approximate LRU/LFU. It checks a small random sample of keys instead of tracking all of them exactly.

How does it work?

Common failure modes and their fixes:

  • Stampede (thundering herd). A popular key expires. Thousands of requests miss at the same moment and all hit the DB together. Fixes:
  • Single-flight — only one request loads the key; the others wait for its result.
  • Short locks.
  • Early probabilistic refresh — refresh the key a little before it expires.
  • Stale-while-revalidate — keep serving the old value while one request fetches the new one.
  • Penetration. Requests ask for keys that don't exist, so they always miss and always hit the DB. Fixes: cache "not found" results for a short time, or put a Bloom filter (a small structure that quickly says "definitely not present") in front.
  • Avalanche. Many keys expire at the same time and the DB gets flooded. Fix: add random jitter to TTLs so they expire at different times.
  • Hot keys. One key gets huge traffic and overloads one cache node. Fixes: copy it under several names (key#1..#n), and add a local in-process cache in front.
  • Consistency. Cache and DB can disagree. Fixes: delete on write (don't update), keep short TTLs as a safety net, and evict the key only after the DB transaction commits.

Example

GET /outlets/42/schemes
  → Redis GET schemes:t7:42 → hit (0.8 ms) → return
  → miss → DB query (25 ms) → SET schemes:t7:42 (TTL 10 min ± 60 s jitter) → return
Admin edits a scheme → DB commit → DEL schemes:t7:* for affected outlets (or bump a version in the key)

Step by step: 1. The app checks Redis. On a hit, it answers in under 1 ms. 2. On a miss, it queries the DB (25 ms) and stores the result with a 10-minute TTL plus some random jitter. 3. When an admin edits a scheme, the DB commits first. Then the related keys are deleted (or a version number in the key is increased, so old keys are simply never read again).

Cache sizing: 20% of 10M outlet profiles × 2 KB = 4 GB. A small Redis cluster is enough.

When would I use it?

  • Data that is read a lot and changes little: catalogues, configuration, profiles, pre-computed totals, session data.
  • Expensive computations.
  • Protecting slow or rate-limited dependencies.

What can go wrong?

  • Caching data that must be strongly consistent — for example, point balances during a redemption. A stale value can cause wrong results.
  • Unbounded caches that grow until memory runs out.
  • Caching per-user data that is rarely reused — it wastes memory.
  • Stale data after writes.
  • Using the cache as the database — data is lost when it is evicted or when the cache restarts.

Interview questions

Q1. What caching strategy would you use and why? Usually cache-aside with TTLs. It is simple, and the system still works if the cache fails. I delete the key on writes and add jitter to TTLs.

Q2. How do you prevent a cache stampede? Use single-flight loading per key, locks, early refresh, serving stale data while one request refreshes it, and TTL jitter.

Q3. Why delete instead of update the cache on writes? An update can race with a read happening at the same time. That read may put old data back into the cache after your update. If you delete instead, the next read loads fresh data from the DB.

11.6 CDNs and the edge

Why?

In simple words: A CDN keeps copies of your images and files in many cities, close to users. Users download from the nearby copy instead of your far-away main server.

Users are often far from your datacentre. Images, scripts and videos are large files.

A Content Delivery Network (CDN) caches this content at hundreds of edge locations — small data centres close to users. This gives two benefits: - Lower latency, because the data travels a shorter distance. - Less load (and cost) on your origin servers (your own main servers), because the CDN serves most of the bandwidth.

Think of a newspaper. It is printed in many city presses, not shipped from one office to the whole country.

What is happening internally?

  • Pull CDN: on a miss, the edge fetches the file from the origin. It then caches it, following the Cache-Control headers. Push CDN: you upload the content to the CDN ahead of time.
  • Cache keys: the CDN identifies a cached item by its URL plus some chosen headers. Use versioned file names (app.3f9a.js). A new version gets a new name, so users get it at once. This is better than purging (deleting) old copies.
  • Other jobs of the edge: it terminates TLS, absorbs DDoS attacks (floods of fake traffic), compresses responses, converts images (to WebP/AVIF, or resizes them), and can run small pieces of your code called edge functions.
  • Dynamic API responses can also be cached at the edge for a short time (using s-maxage and stale-while-revalidate).

How does it work?

User in Varanasi → nearest edge (Delhi) → cache hit → 20 ms
                                         → miss → origin (Mumbai region) → cache → serve
  1. A user in Varanasi is sent to the nearest edge, in Delhi.
  2. If Delhi has the file (a hit), it answers in about 20 ms.
  3. If not (a miss), Delhi fetches it from the origin in the Mumbai region, caches it, and serves it. The next user near Delhi gets a hit.

Example

Product images in a retailer app: 1. Upload the original images to object storage. 2. The CDN serves URLs like img.cdn/sku/123?w=320&fmt=webp. The edge resizes the image, converts it to WebP, and caches it. 3. Cheap, low-end Android phones on 4G get small images in tens of milliseconds.

When would I use it?

For all static assets, images, video segments (13.16), downloadable files, and public API responses that are safe to cache.

What can go wrong?

  • Caching personalised responses. One user's private data can be shown to another user — a data leak.
  • Forgetting invalidation. Users keep getting old assets.
  • Query-string explosion. Many slightly different URLs for the same file split the cache into many small, rarely-hit entries.
  • Origin overload after a purge. All edges miss at once and hit the origin together. A shield (origin-shield) layer — one middle cache in front of the origin — helps.

Interview questions

Q1. How does a CDN reduce latency? It serves cached content from edge locations close to users. So requests avoid the long round trip to the origin.

Q2. How do you invalidate CDN content? Use versioned URLs (the preferred way), Cache-Control TTLs, or the CDN's explicit purge APIs.

11.7 Choosing a database

Why?

In simple words: Pick the database based on how your data is read and written, how correct it must be, and how big it will get — not because a database is popular. Start with PostgreSQL and add others only for a clear reason.

The data store is the hardest component to change later. It is also usually the bottleneck.

So choose it based on: - access patterns (how data is read and written), - consistency needs (how correct and up to date reads must be), and - scale.

Do not choose by fashion. Making this choice well is one of the most visible SDE2 skills.

What is happening internally?

Type Examples Strengths Typical use
Relational (OLTP — everyday transactions) PostgreSQL, MySQL, SQL Server ACID transactions, joins, constraints, flexible queries Orders, payments, ledgers, users — the default
Key-value Redis, DynamoDB O(1) access by key (same speed at any size), at huge scale Sessions, carts, idempotency keys (to detect repeated requests), caches
Wide-column Cassandra, ScyllaDB, Bigtable Very high write throughput, access by partition key, multiple datacentres Messages, activity feeds, time series, IoT
Document MongoDB, Cosmos DB Flexible schema, nested documents Catalogues, content, configuration
Search Elasticsearch, OpenSearch Full-text search, fuzzy (typo-tolerant) matching, facets (filters with counts), relevance ranking Product and log search
Columnar OLAP (analytics) ClickHouse, BigQuery, Snowflake, Trino over a lake Fast totals and group-bys over billions of rows Analytics, dashboards, incentive aggregates
Graph Neo4j Queries that follow many relationship hops Social graphs, fraud rings
Time-series Prometheus, TimescaleDB, InfluxDB Retention and downsampling (keeping old data at lower detail) Metrics
Object storage S3, Azure Blob Cheap, durable storage for large objects Images, files, backups, data lake

ACID vs BASE: - ACID — atomic (all or nothing), consistent (rules always hold), isolated (transactions don't disturb each other), durable (committed data is not lost). Use it for data where correctness is critical. - BASE — basically available, soft state, eventually consistent (copies agree after some time). Many distributed NoSQL stores work this way.

How does it work?

Decision path:

  1. Start with PostgreSQL.
  2. Switch or add a store only when a specific requirement forces it. Name that requirement out loud. For example: - "100k writes/s of append-only events with partition-key reads → Cassandra" - "full-text with typo tolerance → Elasticsearch" - "aggregations over 5 billion rows → ClickHouse"
  3. Using several stores in one system is normal. This is called polyglot persistence. A common setup: Postgres for the truth, Redis for hot paths, Elasticsearch for search, ClickHouse for analytics. The other stores are fed from Postgres by events or CDC (change data capture — streaming every change from the database's log).

How indexes, MVCC and locking work inside the database is covered in Chapter 12.

Example

A loyalty platform: - Ledger and accounts in PostgreSQL — it needs transactions and constraints. - Balances cached in Redis. - Redemption history search in Elasticsearch (optional). - Monthly incentive and analytics totals in ClickHouse, fed via CDC.

When would I use it?

At the data-model step of every design.

What can go wrong?

  • Choosing NoSQL "for scale", then finding out you need transactions and joins.
  • Choosing SQL for a write volume that a single primary cannot handle.
  • Using the search index or the cache as the source of truth.
  • Designing NoSQL tables like relational ones. In NoSQL you should design query-first — start from the queries you need and shape the tables around them.

Interview questions

Q1. SQL vs NoSQL — how do you decide? I default to SQL, because it gives transactional integrity and flexible queries. I choose NoSQL only for a concrete need: massive write throughput, a flexible schema, simple key access at huge scale, or multi-region availability.

Q2. Why might you use several databases in one system? Because each one serves a different access pattern — transactions, caching, search, analytics. I keep one source of truth and feed the others from it using events or CDC.

11.8 Replication

Why?

In simple words: Replication means keeping copies of the database on other machines. If the main one dies, a copy takes over, and copies can also share the read load — but keeping all copies in sync is the hard part.

One database server is a single point of failure. It is also a limit on how many reads you can serve.

Copies on other machines are called replicas. They give you: - Availability — if the main server fails, a replica takes over. This is called failover. - Read scaling — reads can be spread across replicas. - Geographic closeness — a replica can sit near users in another region.

The cost: you must keep all the copies consistent.

What is happening internally?

  • Leader–follower (primary–replica). All writes go to the leader. The leader streams its log of changes (the WAL in Postgres, the binlog in MySQL) to the followers. Reads can go to the followers.
  • Synchronous: the leader waits for a follower to confirm each write. No data is lost on failover, but writes are slower.
  • Asynchronous: the leader does not wait. Writes are fast, but followers lag behind. The latest writes can be lost on failover.
  • Semi-synchronous: the leader waits for at least one follower.
  • Multi-leader. Writes are accepted in several regions. When two regions change the same data, the conflict must be resolved — by last-write-wins, CRDTs (data types that merge automatically) or merge logic in the application.
  • Leaderless (Dynamo-style, as in Cassandra): 1. Write to N replicas. The write succeeds after W of them confirm (acks). 2. Read from R replicas. 3. If R + W > N, the replicas you read from and the replicas you wrote to always overlap. So at least one read sees the latest write. 4. Read repair (fixing stale copies during reads) and anti-entropy (a background job that compares and syncs copies) fix any differences.
  • Failover has three steps: detect that the leader failed, promote a follower to be the new leader, and point clients to it. The risks:
  • Asynchronous writes that never reached the follower are lost.
  • Split brain — two nodes both think they are the leader. This is prevented with consensus (Raft/Paxos, through etcd, ZooKeeper or Patroni) and fencing tokens (a number that lets storage reject writes from the old leader).

Think of a head office and branch offices. The head office makes every change and sends copies of the register to the branches. A branch can answer questions, but its register may be a few minutes old.

How does it work?

writes → Primary ──WAL stream──► Replica 1 (reads)
                  └────────────► Replica 2 (reads, other AZ)
primary dies → orchestrator (Patroni/managed service) promotes Replica 1 → DNS/endpoint switches
  1. All writes go to the primary.
  2. The primary streams its WAL to both replicas. Replica 2 is in another availability zone (AZ — a separate datacentre in the same region).
  3. If the primary dies, an orchestrator (Patroni or the managed cloud service) promotes Replica 1.
  4. The DNS name or endpoint switches to the new primary, so clients reconnect there.

Example

Read-your-writes problem: 1. A retailer redeems points. This write goes to the primary. 2. The app immediately reads the balance from a replica that is lagging. 3. The screen shows the old balance. The user is confused.

Fixes: - Read the user's own recent data from the primary for a short time after they write. - Track a "last write LSN/timestamp" (the position of their last write in the log) per session. Send reads only to replicas that have caught up to it. - For critical screens, always read from the primary.

When would I use it?

In every production database: - At least one synchronous or semi-synchronous standby in another availability zone, for failover. - Plus asynchronous replicas for read scaling and reporting.

What can go wrong?

  • Replica lag causes stale reads and a confusing user experience.
  • Asynchronous failover loses recent writes.
  • Heavy reports run on the primary instead of a replica, slowing everything down.
  • Split brain, when fencing is not set up properly.

Interview questions

Q1. Synchronous vs asynchronous replication? Synchronous replication waits for replicas to confirm each write. It is durable but makes writes slower. Asynchronous replication does not wait. It is fast, but replicas lag and recent writes can be lost on failover.

Q2. What is replication lag and how do you handle it? It is the delay before replicas show the leader's writes. I handle it with read-your-writes routing (send a user's reads to the leader right after they write), lag-aware routing, or by accepting eventual consistency where that is fine.

Q3. What is a quorum? In leaderless replication with N replicas, a write needs W acks and a read needs R responses, with R + W > N. Because the two sets must overlap, every read includes at least one replica with the latest successful write.

11.9 Partitioning and sharding

Why?

In simple words: When one database can't hold all the data or keep up with the writes, you split the data across several databases. Each one holds only its own part.

Sometimes one database node cannot hold all the data. Or it cannot keep up with the rate of writes.

Then you split the data across nodes. Each piece is called a shard, and each shard holds only part of the data. So storage and write capacity grow as you add shards.

Think of a railway reservation office with separate counters by train number range. Each counter handles only its own trains, so the queues move faster.

What is happening internally?

Strategy How Pros Cons
Range Each shard gets a range of keys (A–F, G–M; or date ranges) Range scans are efficient Hot spots (recent dates, popular ranges get all the traffic)
Hash hash(key) % N, or consistent hashing (11.11) Data spreads evenly Range queries must go to all shards; resharding is costly
Directory / lookup A service keeps a map of key → shard Flexible placement; easy to move data An extra hop; the directory itself must be highly available
Geo / tenant Split by region or by tenant (customer company) Data stays local, helps compliance, one noisy tenant can't hurt others Shards have uneven sizes → move big tenants to their own shards

Choosing a shard key. A good shard key: - has high cardinality (many different values), - spreads data evenly, and - matches the main access pattern, so most queries hit one shard.

For a multi-tenant SaaS, tenant_id is the natural choice. The largest tenants can be split further or given their own shards.

How does it work?

Router / client library: shard = hash(tenant_id) → shard 3
Shard 0 [tenants a..]  Shard 1 [...]  Shard 2 [...]  Shard 3 [tenant t-42] ← query goes only here
Cross-shard query (global top-10) → scatter to all shards, gather and merge (expensive; avoid on hot paths)
  1. A router (or a client library) hashes the tenant_id to pick the shard — here, shard 3.
  2. The query for tenant t-42 goes only to shard 3.
  3. A query across all tenants (like a global top-10) must be sent to every shard. The results are then collected and merged. This is called scatter-gather. It is expensive, so avoid it on hot paths.

Rebalancing (moving data when you add shards): - With plain % N, adding one shard changes N. Almost every key moves to a new shard. - Consistent hashing, or many fixed virtual partitions, moves only a small fraction. For example, use 4,096 logical partitions and map them to physical nodes. Adding a node just moves some whole partitions to it. - Many systems (Citus, Vitess, Cassandra, DynamoDB) handle this for you.

Example

A loyalty ledger taking 50,000 writes/s: 1. Shard by tenant_id. All of a tenant's accounts sit on one shard, so per-tenant queries stay on one shard. 2. Inside each shard, partition the ledger table by month (Chapter 12.8). This makes it easy to drop old data (retention). 3. The largest FMCG tenant gets its own shard.

When would I use it?

Only after you have used up the simpler options: vertical scaling, read replicas, caching and table partitioning. Sharding adds a lot of complexity — cross-shard joins, transactions, rebalancing and harder operations.

What can go wrong?

  • A shard key that creates hot spots. For example, IDs that always increase in range sharding (all new writes go to the last shard), or one giant tenant.
  • Cross-shard transactions. Avoid them; use sagas instead (a chain of local steps, each with an undo step).
  • Global secondary indexes (indexes across all shards) are hard to keep correct.
  • Uneven growth between shards.
  • Downtime during resharding.

Interview questions

Q1. How do you choose a shard key? It needs high cardinality and an even spread. It should match the main access path, so most queries hit one shard. For range sharding, avoid keys that always increase.

Q2. What problems does sharding introduce? Cross-shard queries and joins, distributed transactions, rebalancing, hot shards, and more operational complexity.

Q3. Partitioning vs sharding? Partitioning splits a table inside one database. It helps with pruning (skipping partitions a query doesn't need) and retention. Sharding spreads data across multiple database servers. It adds capacity and write scale.

11.10 CAP, PACELC and consistency models

Why?

In simple words: When the network between your database copies breaks, you must choose: refuse some requests to stay correct, or keep answering with possibly old data. You make this choice per feature — money needs correct, likes can be a bit old.

A distributed data store cannot be perfectly consistent, always available, and tolerant of network breaks, all at the same time.

So you must know which guarantee each part of your system needs, and say it out loud. This is how you justify your database and replication choices.

What is happening internally?

  • CAP. Sometimes the network splits nodes into groups that cannot talk to each other. This is a partition. During a partition, the system must choose:
  • Consistency — refuse or delay requests it cannot answer correctly, or
  • Availability — answer anyway, maybe with stale data.

Partitions will happen in real networks. So the real choice is C vs A during a partition. - PACELC adds the normal case: - If there is a Partition → choose A or C. - Else (normal operation) → choose Latency or Consistency. Waiting for every copy to agree is slower. - Dynamo/Cassandra are PA/EL (prefer availability and low latency). Spanner and etcd are PC/EC (prefer consistency). - Consistency models, from strong to weak:

Model Guarantee Example need
Linearizable (strong) Every read sees the latest committed write Balances, inventory counts, leader election
Sequential All nodes see operations in the same order
Causal If one operation caused another, everyone sees them in that order A reply appears after its message
Read-your-writes A user always sees their own writes Profile updates
Monotonic reads Reads never go back in time (you never see older data after newer) Feeds
Eventual Copies become the same once writes stop Likes, view counts, search indexes

Think of an ATM when the link to the bank is down. A strict bank refuses withdrawals (consistency). A relaxed one allows small withdrawals and settles later (availability).

How does it work?

Choose per feature, not for the whole system: - Redemptions need strong consistency. Otherwise the same points can be spent twice (double spend). - A leaderboard or an analytics dashboard can be a few seconds stale.

Example

The network between two regions breaks: - The payment service refuses writes in the smaller (minority) region. It chooses CP, because double charges are worse than a short outage. - The product catalogue keeps serving cached data in both regions. It chooses AP, because slightly old product details are acceptable.

When would I use it?

  • When choosing stores and replication modes.
  • When designing multi-region systems.
  • When justifying caching and asynchronous updates.

What can go wrong?

  • Claiming a system is "CA". In a real distributed system, partitions happen, so you cannot skip P.
  • Assuming eventual consistency is fine for money.
  • Not handling what users see under eventual consistency — for example, you need "payment processing…" states and read-your-writes.

Interview questions

Q1. Explain CAP with an example. During a network partition, you must choose consistency (reject or block some requests) or availability (serve data that might be stale). A payment ledger chooses C. A social feed chooses A.

Q2. What does PACELC add? It says that even with no partition, there is still a trade-off — between latency and consistency.

Q3. Where would you use strong vs eventual consistency in a loyalty platform? Strong consistency for balances, redemptions and idempotency checks (checks that stop the same request being processed twice). Eventual consistency for leaderboards, analytics, notifications and search.

11.11 Consistent hashing

Why?

In simple words: With simple % N hashing, adding one server moves almost every key to a new place. Consistent hashing puts servers and keys on a circle, so adding a server moves only a small share of keys.

With hash(key) % N, adding or removing one cache or database node changes N. That moves almost every key to a different node. The result is a mass of cache misses, or a huge data migration.

Consistent hashing moves only about 1/N of the keys.

What is happening internally?

  1. Picture a ring of numbers from 0 to 2³²−1. Hash each node onto a point on this ring. Hash each key onto the ring too.
  2. A key belongs to the first node you meet going clockwise from the key's position.
  3. When you add a node, it takes only the keys between itself and the node before it.
  4. When you remove a node, its keys go to the next node clockwise.
  5. Virtual nodes: each physical node is placed at many points (100–200) on the ring. This spreads the load more evenly. A bigger machine can be given more points, so it takes more keys.

Think of a round dining table with plates (keys) and waiters (nodes) standing at spots. Each plate is served by the next waiter clockwise. A new waiter joining takes over only the plates just before him.

ring: 0 ──[A#1]──k1──[B#1]──k2──[A#2]──k3──[C#1]──… (wraps)
k1 → B, k2 → A, k3 → C.  Add node D between A#2 and C#1 → only keys in that arc move to D.

How does it work?

The ring is a TreeMap from hash position to node. ceilingEntry finds the first node at or after the key's hash (clockwise). If there is none, the search wraps around to the first entry.

class ConsistentHashRing<T> {
    private final TreeMap<Long, T> ring = new TreeMap<>();
    private final int vnodes;
    ConsistentHashRing(int vnodes) { this.vnodes = vnodes; }
    void add(T node)    { for (int i = 0; i < vnodes; i++) ring.put(hash(node + "#" + i), node); }
    void remove(T node) { for (int i = 0; i < vnodes; i++) ring.remove(hash(node + "#" + i)); }
    T nodeFor(String key) {
        Map.Entry<Long, T> e = ring.ceilingEntry(hash(key));
        return (e != null ? e : ring.firstEntry()).getValue();          // wrap around
    }
    private long hash(String s) {                                         // well-mixed hash: MD5's first 8 bytes (as in ketama)
        try {
            byte[] d = java.security.MessageDigest.getInstance("MD5").digest(s.getBytes(java.nio.charset.StandardCharsets.UTF_8));
            long h = 0;
            for (int i = 0; i < 8; i++) h = (h << 8) | (d[i] & 0xff);
            return h;                                                     // Murmur3/xxHash are faster alternatives
        } catch (java.security.NoSuchAlgorithmException e) { throw new IllegalStateException(e); }
    }
}

Key points in the code: - add places each node at vnodes points, using the names node#0, node#1 and so on. - nodeFor is O(log n), because TreeMap is a sorted tree. - The hash must be well mixed so the points spread evenly around the ring. Here it takes the first 8 bytes of MD5, as the ketama library does.

Example

A Redis cache tier grows from 4 nodes to 5: - With modulo hashing, about 80% of keys move. That causes a storm of cache misses on the DB. - With consistent hashing, only about 20% move.

When would I use it?

  • Distributed caches.
  • Cassandra/Dynamo partitioning.
  • Load balancing with affinity (always routing the same key to the same server).
  • Sharded rate limiters.
  • Routing chat connections.

What can go wrong?

  • Too few virtual nodes — the load is uneven.
  • A poor hash function — points cluster together on the ring.
  • Hot keys still overload one node — consistent hashing spreads keys, not traffic per key. Replicate hot keys.

Interview questions

Q1. What problem does consistent hashing solve? It keeps key movement small when nodes are added or removed. Only about 1/N of the keys move, instead of nearly all of them.

Q2. Why virtual nodes? They spread each physical node's ranges all around the ring, which evens out the load. They also let you give bigger nodes more points, so they take a bigger share.

11.12 Message queues and asynchronous processing (RabbitMQ and friends)

Why?

In simple words: A queue is a waiting line between two services. One service drops a job in the line and moves on; another service picks it up when it is ready.

When services call each other directly and wait for the answer, they are tightly tied together. This is a synchronous call chain. The problems are easy to see:

  • If the notification service is slow, checkout also becomes slow.
  • If the loyalty service is down, orders fail.

A queue fixes this. The service that sends work is the producer. It puts the job in the queue and continues without waiting. The service that does the work is the consumer. This gives you four benefits:

  • Decoupling — the producer does not care if the consumer is slow or down right now.
  • Absorbing traffic spikes — a sudden burst waits in the queue; workers finish it at a steady speed. This is called load levelling.
  • Retries — failed work can be tried again in the background. The user does not wait for it.
  • Fan-out — one event can be sent to many consumers.

Think of a restaurant token system. You order at the counter, get a token and sit down. The kitchen cooks orders one by one. The cashier does not stand and wait for your food.

What is happening internally?

There are two families of messaging systems. A message queue deletes a message once it is handled. A log (or stream) keeps every message for days, and each reader remembers its own position.

Message queue (RabbitMQ, Amazon SQS, Azure Service Bus) Log / stream (Kafka, Kinesis, Event Hubs, Pulsar)
Model A message is deleted once a consumer confirms it (acks) Messages are only added to the end of a log and kept for days; each consumer remembers its position (offset)
Consumers Several consumers share one queue and compete for messages Consumers form groups; many separate groups can read the same data again
Ordering Per queue (but parallel consumers and redelivery can break it) Per partition
Replay No (gone once acked) Yes (move the offset back)
Routing Rich (exchanges, topics, headers) Topic + partition key
Per-message features Ack/nack, TTL, delay, priority, DLQ Mostly works in batches and offsets
Best for Task/work queues, commands, RPC-style workflows Event streaming, event sourcing, CDC, analytics pipelines, high throughput

A few terms from the table:

  • Ack (acknowledge) — the consumer tells the broker "I am done, delete it". Nack means "I failed".
  • TTL (time to live) — how long a message may wait before it expires.
  • DLQ (dead-letter queue) — a side queue where failed or expired messages are parked for a human to check.
  • Offset — the position number of a message in a log, like a page number.
  • CDC (change data capture) — streaming every change made in a database as events.

RabbitMQ in particular: - The path of a message is: Producer → exchange → (binding with routing key) → queue → consumer. The exchange is a sorting desk. It reads the message's routing key (a label) and decides which queue gets it. Exchange types: - direct — the key must match exactly. - topic — the key can match wildcards, like order.*.created or #. - fanout — copy the message to every queue bound to it. This is pub/sub (publish/subscribe). - headers — match on message headers instead of the key. - Acks: the consumer sends an ack only after it finishes processing. If the consumer dies before acking, RabbitMQ gives the message to someone else. So each message is delivered at least once (at-least-once). A consumer can also nack or reject a message, with or without putting it back in the queue (requeue). - Prefetch (QoS): this limits how many unacked messages one consumer can hold at a time. Because of this, a slow consumer does not hoard work, and load is shared fairly. - Durability: to survive a broker restart, you need three things together: durable queues, persistent messages and publisher confirms (the broker tells the producer "saved"). For high availability (HA), use quorum queues. These copy each queue to several nodes using Raft, a voting-based replication protocol. - Dead-letter exchanges (DLX): some messages cannot be handled — they are rejected, expired (TTL) or the queue is full. These go to a DLX. You use a DLX for two things: 1. DLQs — a parking place for failed messages. 2. Delayed retries — send the message to a waiting queue with a TTL. When the TTL expires, it is dead-lettered back to the work queue for another try. - Azure Service Bus is closer to RabbitMQ than to Kafka. It offers queues and topics/subscriptions, sessions for ordering, a built-in DLQ, scheduled messages and duplicate detection.

Delivery semantics (how many times a message is delivered): - At-most-once: the consumer acks (or commits) first and processes later. If it crashes in between, the message is lost. So you may lose messages. - At-least-once: the consumer processes first and acks later. If it crashes after processing but before acking, the message comes again. So you may get duplicates. Because of this, consumers must be idempotent (11.14) — handling the same message twice must give the same result as handling it once. This is the practical default. - Exactly-once: possible only inside one closed system. For example, Kafka transactions for read-process-write inside Kafka. Across different systems you get "effectively once". That means at-least-once delivery + idempotency.

How does it work?

  1. Checkout publishes a SendReceipt message to the notifications queue and returns to the user.
  2. Three workers compete for messages. Each message goes to only one worker.
  3. If a message fails three times, it goes to the DLX and then to notifications.dlq. Someone gets an alert, inspects it and replays it.
  4. If 50k messages arrive at once, the queue holds them. Workers finish them at their own speed. KEDA (a Kubernetes autoscaler) adds more workers when the queue gets deep or lag grows.
Checkout ──publish "SendReceipt"──► [notifications queue] ──► worker 1 / worker 2 / worker 3 (competing)
                                         │ fails 3× → DLX → [notifications.dlq] → alert, inspect, replay
Spike of 50k messages → the queue absorbs it; workers drain at their own pace; autoscale on queue depth/lag (KEDA)

Example

Perfect Store photo verification works like this:

  1. The app uploads photos.
  2. The API puts a VerifyAudit{auditId} message in the queue (enqueues it).
  3. GPU/AI workers pick up messages at their own pace.
  4. They write the results back and publish a notification event.

The user sees "verification in progress". They do not wait 30 seconds on an HTTP call.

When would I use it?

Use a queue when:

  • The work is slow or unreliable, and the user does not need it done right now. Examples: notifications, image processing, report generation, third-party calls.
  • Traffic comes in sudden spikes.
  • One event must reach many consumers (fan-out).
  • Services owned by different teams must talk to each other.

How to choose:

  • Work queue (RabbitMQ / Service Bus / SQS) — for tasks and commands.
  • Kafka — for event streams that several consumers need, or when you need replay.

What can go wrong?

  • Duplicates with non-idempotent consumers. The same message is processed twice, and the effect happens twice.
  • Poison messages. A message that always fails can block the queue. Use a DLQ with a retry limit.
  • Hidden slow consumers. The queue keeps growing without limit, and nobody notices. Monitor queue depth and lag, and alert on them.
  • Lost messages with auto-ack. The message is acked as soon as it is received. If the consumer then crashes, the message is gone.
  • Broken ordering. Parallel consumers can process messages out of order. Don't assume order.
  • Wrong tool. Don't use a queue when the user actually needs an answer right now (a synchronous response).

Interview questions

Q1. Why introduce a message queue? It decouples producers from consumers, so one being slow or down does not stop the other. It absorbs traffic spikes, retries failed work in the background, and fans out events to many consumers. Overall, the user path becomes more resilient and faster.

Q2. Queue (RabbitMQ) vs log (Kafka)? A queue hands out tasks and deletes each message once it is acknowledged; it has rich routing and per-message features like TTL, priority and DLQ. Kafka keeps an ordered log per partition that can be replayed. Many consumer groups read it independently, at very high throughput.

Q3. What delivery guarantee do you design for? At-least-once delivery with idempotent consumers, so duplicates are harmless. Exactly-once is possible only inside systems that support transactions end to end.

11.13 Kafka in depth

Why?

In simple words: Kafka is a giant, shared notebook that you can only add lines to. Many readers read it at their own speed, each with their own bookmark, and can go back to old pages when needed.

Kafka has become the backbone of event-driven systems. It carries order events, CDC streams (database changes as events), analytics pipelines and audit logs.

Its design is a partitioned, replicated, append-only log. In plain words:

  • Append-only log — new messages are only added at the end, never edited.
  • Partitioned — the log is split into pieces, so many machines can work in parallel.
  • Replicated — each piece is copied to several machines, so nothing is lost if one dies.

Because of this design you get very high throughput, ordering per key, durability and replay. Kafka questions come up in almost every SDE2 system-design round.

What is happening internally?

  • Storage: a topic is split into partitions. Each partition is an ordered, append-only log. On disk, it is stored as several segment files. Every message has a number called its offset — its position in the partition.
  • Performance: Kafka is fast for four reasons: 1. It writes to disk sequentially (always at the end), which is very fast. 2. It uses the OS page cache (the operating system keeps recent file data in memory). 3. It batches and compresses messages. 4. It uses zero-copy transfer (sendfile). Data goes from the page cache straight to the network, without passing through the application's memory.
  • Replication: each partition has one leader and some followers. Producers and consumers talk to the leader. Followers copy from it. Followers that are fully caught up are called the ISR (in-sync replicas). A safe setup is:
  • replication.factor=3 — three copies of each partition.
  • min.insync.replicas=2 — at least two copies must be in sync.
  • Producer acks=all — the write is confirmed only when all in-sync replicas have it.

With this, a write is acknowledged only after at least two replicas have it. So if one broker dies, no data is lost. - Producer: - It picks the partition using hash(key) % partitions. The same key always goes to the same partition, so messages with the same key stay in order. - It batches messages for speed, controlled by linger.ms (how long to wait to fill a batch) and batch.size. - The idempotent producer (on by default since 3.0) gives each message a sequence number. Because of this, a retry does not create a duplicate. - Transactions let a producer write to several partitions and commit consumer offsets as one atomic unit — all or nothing. This gives exactly-once read-process-write within Kafka. - Consumer groups: the partitions of a topic are divided among the members of a group. One partition goes to only one member of the group. So max parallelism = number of partitions. Different groups read independently, so each group gets every message (pub/sub). When members join or leave, Kafka reassigns partitions. This is rebalancing. Cooperative-sticky assignment moves as few partitions as possible, so there is less disruption. - Offsets: a consumer saves its position (commits its offset) in an internal topic called __consumer_offsets. If it commits after processing, you get at-least-once delivery. - Retention: Kafka deletes old data by time or by size. Or it uses log compaction — keep only the latest value for each key. This is ideal for changelogs and state. - Coordination: older Kafka used ZooKeeper to manage the cluster. Since 3.x, Kafka has KRaft, its own built-in Raft (voting-based) coordination. ZooKeeper was removed in Kafka 4.0. - Ecosystem: - Kafka Connect — ready-made source/sink connectors to move data in and out. - Debezium — CDC; it reads the database's log and turns changes into events. - Kafka Streams / Flink — stream processing. - Schema Registry — stores Avro/Protobuf/JSON schemas and enforces compatibility rules, so producers can't break consumers.

Think of a railway reservation register with several counters. Each counter (partition) has its own register, written line by line. Photocopies are kept at two other stations (replicas). Different departments (consumer groups) read the registers, each with its own bookmark (offset).

How does it work?

The picture below shows:

  1. A producer sends events with key = accountId to the topic points-events.
  2. The topic has three partitions, with leaders on different brokers.
  3. The "notifications" group has two members. Member A reads p0 and p1; member B reads p2.
  4. The "analytics" group has one member reading all three partitions.
  5. Each group has its own offsets, so both groups see every event.
Producer (key = accountId) ──► topic points-events
   partition 0: [0][1][2][3]…   leader on broker 1, followers on 2 and 3
   partition 1: [0][1][2]…      leader on broker 2
   partition 2: …
Consumer group "notifications": member A ← p0, p1;  member B ← p2
Consumer group "analytics":     member X ← p0, p1, p2   (independent offsets — both see every event)

Choosing the partition count: divide your target throughput by what one partition can handle. Then add room for more consumers in future (e.g., 12–48 for a busy topic). Plan this well at the start. If you increase the count later, the key → partition mapping changes. During that change, per-key ordering breaks.

Example

Month-end spike: 500 accrual events/s for 2 hours. Here is how the setup handles it:

  • The order-completed topic has 24 partitions, keyed by outletId.
  • The loyalty consumer group autoscales from 4 to 24 pods based on consumer lag (how far the consumers are behind the latest message).
  • Because the key is outletId, events for each outlet stay in order.
  • Kafka keeps data for 7 days. So if you find a bug, you can fix the consumer and replay from an earlier offset.

When would I use it?

  • Event-driven microservices.
  • CDC pipelines (DB → Kafka → search/analytics).
  • High-volume telemetry and logs.
  • Event sourcing (storing every change as an event).
  • Stream processing.

What can go wrong?

  • Too few partitions. You can't add more consumers than partitions, so you can't scale.
  • Hot partitions. If keys are skewed (one key gets most of the traffic), one partition gets overloaded.
  • Rebalance storms. A consumer that takes longer than max.poll.interval.ms between polls is treated as dead. Its partitions move, then come back, again and again.
  • Data loss on broker failure. This happens with acks=1 or min.insync.replicas=1.
  • High storage cost. Retention with no limit grows forever.
  • Broken consumers. A schema change that is not compatible breaks the readers.
  • Wrong use. Kafka is not a database. Don't use it for random lookups by key.

Interview questions

Q1. How does Kafka guarantee ordering? Only within a partition. So choose the message key so that events which must stay in order share the same key, and therefore the same partition.

Q2. What limits consumer parallelism? The number of partitions. Each partition is read by at most one member of a consumer group, so extra members sit idle.

Q3. How do you configure Kafka for no data loss? Replication factor 3, min.insync.replicas=2, and producer acks=all with idempotence on. On the consumer side, commit offsets only after processing.

Q4. What is log compaction? Kafka keeps only the latest record for each key, plus tombstones (a key with an empty value) to mark deletes. This turns the topic into a durable changelog of the current state.

11.14 Idempotency and delivery guarantees in practice

Why?

In simple words: Idempotent means "doing it twice is the same as doing it once". If the user presses "Pay" two times, they should still pay only once.

Networks fail in the worst possible way: the request succeeds, but the response is lost. The caller does not know it succeeded. So:

  • Clients retry.
  • Queues redeliver.
  • Users double-tap "Pay".

Without idempotency, every retry can double-charge, double-credit or double-ship. This is exactly the "duplicate reward postings under retry/failure" problem you solved at FieldAssist. Design for it on purpose, at every layer.

What is happening internally?

An operation is idempotent if doing it many times has the same effect as doing it once. By HTTP's own definition, GET, PUT and DELETE are idempotent. POST is not — unless you make it so.

Think of an ATM. If the network drops after cash is debited, the bank must not debit you again when the machine retries. It checks the transaction number first.

You handle this at four layers:

  1. API:
  2. The client creates an Idempotency-Key (a UUID) for each logical operation. On retry, it sends the same key again.
  3. The server stores (key, request hash, status, response) with a unique constraint on the key. It does this in the same transaction as the business change.
  4. On a replay (same key, same payload), the server returns the stored response.
  5. Same key with a different payload → 422.
  6. A second copy arrives while the first is still running → 409 (or wait for the first to finish).
  7. Consumers: two options. - Keep a processed-event table keyed by event ID. Write to it in the same transaction as the effect. - Or make the effect naturally idempotent. For example, an upsert by business key, or a conditional update like UPDATE … SET status='PAID' WHERE status='PENDING' (the second run changes nothing).
  8. Downstream calls: pass idempotency keys to payment gateways and partner APIs. Most of them support it.
  9. Retries: use exponential backoff (wait longer after each failure) with jitter (a little randomness, so clients don't all retry together). Cap the number of attempts, and use retry budgets (a limit on what share of traffic can be retries).

How does it work?

  1. Attempt 1: the server inserts the key with status IN_PROGRESS, debits points, writes the ledger and outbox, saves the response, and commits. The response is lost on the network.
  2. Attempt 2 (the retry): the insert fails with a unique-key violation. The server reads the saved response and returns the same 201 body. Nothing is debited again.
POST /redemptions  Idempotency-Key: 7f3c…   (attempt 1: response lost on the network)
   BEGIN; INSERT idempotency(key=7f3c, status=IN_PROGRESS) → OK; debit; ledger; outbox;
          UPDATE idempotency SET status=DONE, response=…; COMMIT
POST /redemptions  Idempotency-Key: 7f3c…   (attempt 2, retry)
   INSERT idempotency(key=7f3c) → unique violation → SELECT response → return the same 201 body

Example

The table is keyed by tenant and key. It stores a hash of the request, so a different request with the same key can be caught.

CREATE TABLE idempotency_key (
  tenant_id     VARCHAR(40)  NOT NULL,
  key           VARCHAR(80)  NOT NULL,
  request_hash  CHAR(64)     NOT NULL,
  status        VARCHAR(16)  NOT NULL,            -- IN_PROGRESS, DONE
  response_body JSONB,
  created_at    TIMESTAMPTZ  NOT NULL DEFAULT now(),
  PRIMARY KEY (tenant_id, key)
);
-- expire rows after e.g. 24–72 h with a cleanup job (clients don't retry forever)

When would I use it?

Use it for every operation that:

  • moves money, points or inventory,
  • creates orders,
  • sends messages, or
  • is triggered by an event that may be retried.

What can go wrong?

  • Check and effect in separate transactions. Two copies arrive at the same time. Both check, both find no key, and both do the effect.
  • Server-generated keys per attempt. Each retry gets a new key, so the key is useless. The client must create it.
  • Not hashing the payload. A different request that reuses a key silently gets the wrong (old) result.
  • Keys that never expire. The table grows without limit.

Interview questions

Q1. How do you make a POST endpoint idempotent? The client sends an idempotency key. The server stores the key and the response under a unique constraint, in the same transaction as the business effect. On a duplicate, it returns the stored response instead of doing the work again.

Q2. How do you make a Kafka consumer idempotent? Save each processed event ID under a unique constraint, in the same transaction as the business effect. Or make the effect itself safe to repeat, such as an upsert or a conditional update.

Q3. Can you guarantee exactly-once delivery? Not across independent systems. Instead, you get exactly-once effects: deliver at least once, and make the processing idempotent.

11.15 The transactional outbox and sagas

Why?

In simple words: The outbox makes sure "save to DB" and "send the event" never get out of step. A saga breaks one big multi-service job into small steps, each with an "undo" step if something later fails.

In microservices you face two related consistency problems:

  1. Dual write: look at save(order); kafka.send(OrderCreated). Two things can go wrong: - The DB commits, but the publish fails. - Or the publish succeeds, but the DB commit fails.

Either way, the systems disagree. And you cannot make a database and a message broker commit together as one atomic step. 2. Distributed business transactions: redeeming points for a partner voucher touches three systems — loyalty, the voucher partner and notifications. One option is two-phase commit (2PC): a coordinator asks all parties to prepare, then tells all to commit. But 2PC is slow and blocking, and most brokers and SaaS APIs don't support it.

What is happening internally?

Transactional outbox:

  1. In the same local transaction as the business change, also insert the event into an outbox table. Now both are saved together, or neither is.
  2. A separate process, the relay, reads outbox rows, publishes them to Kafka and marks them as published. It finds new rows in one of two ways: - Polling — run a query like SELECT … WHERE published_at IS NULL ORDER BY created_at LIMIT 100 FOR UPDATE SKIP LOCKED again and again. SKIP LOCKED lets several relays run without picking the same rows. - CDC — Debezium reads the database's log and streams new outbox inserts.
  3. Delivery is at-least-once (a row can be sent twice if the relay crashes after sending). So consumers must stay idempotent.

Think of a post office outbox tray. You write the letter and put it in the tray in the same moment. The postman collects from the tray later. The letter can't get "lost between desk and post box".

Saga: a long-running business transaction written as a chain of local transactions (each service commits its own step). Each step has a compensating action. If a later step fails, the compensation undoes the earlier step in business terms (for example, credit points back). There are two styles:

  • Choreography: services react to each other's events, with no central boss. For example: OrderCreated → PaymentService charges → PaymentCompleted → Inventory reserves → … This is simple for 2–3 steps. But the overall flow is not written anywhere, so it is hard to follow.
  • Orchestration: one coordinator tells each participant what to do. The coordinator is a state machine — Temporal, Camunda, AWS Step Functions, or your own table-driven orchestrator. It handles timeouts and retries. If a step fails, it runs the compensations in reverse order. The flow is explicit and easy to observe.

How does it work?

The outbox part:

  1. In one transaction: debit 500 points (only if the balance is enough), add a ledger entry and insert an outbox row.
  2. The relay runs every 200 ms (or uses CDC). It reads unpublished rows, sends them to Kafka with acks=all, and sets published_at.

The saga part (redeem points for a voucher):

  1. Loyalty debits points. Compensation: credit them back.
  2. The voucher partner issues a code, called with an idempotency key. Compensation: void the code.
  3. Notification sends the code. No compensation needed.
  4. If step 2 still fails after retries, the orchestrator runs compensation 1. The redemption becomes FAILED, and the user is told.
Outbox:
  BEGIN
    UPDATE account SET balance = balance - 500 WHERE id='A1' AND balance >= 500;
    INSERT INTO ledger_entry (...);
    INSERT INTO outbox (id, topic, key, payload) VALUES (uuid, 'points-events', 'A1', '{"type":"PointsRedeemed",...}');
  COMMIT
  Relay (every 200 ms or via CDC): read unpublished → send to Kafka (acks=all) → mark published_at

Saga (orchestrated) — redeem points for a voucher:
  1. Loyalty: debit points (local tx)                 compensation: credit points back
  2. Voucher partner: issue code (idempotency key)    compensation: void the code
  3. Notification: send the code                      (no compensation needed)
  Step 2 fails after retries → orchestrator runs compensation 1 → redemption = FAILED, user informed

Example

The outbox table below has a partial index on unpublished rows only. So the relay's query stays fast even when the table has many published rows.

CREATE TABLE outbox (
  id           UUID PRIMARY KEY,
  aggregate_id VARCHAR(40) NOT NULL,
  topic        VARCHAR(80) NOT NULL,
  payload      JSONB NOT NULL,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  published_at TIMESTAMPTZ
);
CREATE INDEX ix_outbox_unpublished ON outbox (created_at) WHERE published_at IS NULL;

For an orchestrator, keep a saga state table: redemption_saga(id, step, status, attempts, last_error, updated_at). Because the state is saved, the saga can continue after a crash. Each step must also be idempotent, because it may run again.

When would I use it?

  • Outbox: whenever a DB change must reliably produce an event.
  • Sagas: business processes that span several services or external partners. Examples: checkout, redemption with partner vouchers, payouts, onboarding.

What can go wrong?

  • Outbox problems:
  • The relay lags or fails. Monitor the age of the oldest unpublished row.
  • The outbox table grows forever. Clean up published rows.
  • Ordering breaks when several relay instances run. Partition the work by aggregate key.
  • Saga problems:
  • Some steps can't be fully undone — for example, an email already sent. Design semantic compensations instead (e.g., send a "please ignore" message).
  • Users see in-between states. Show "processing".
  • Steps that are not idempotent run twice after retries.
  • Saga state is lost because it was not saved to storage.

Interview questions

Q1. What is the dual-write problem and how does the outbox solve it? Writing to a database and to a broker can't be done as one atomic step, so one can succeed while the other fails. The outbox writes the event into a table in the same DB transaction as the change. Then a relay or CDC publishes it reliably, at-least-once.

Q2. Saga vs 2PC? 2PC locks resources across all participants and gets stuck if the coordinator fails. Sagas use local transactions with compensating actions instead. You get eventual consistency without distributed locks, which is why sagas are preferred in microservices.

Q3. Choreography vs orchestration? In choreography, services react to each other's events with no central coordinator; it is simple, but the flow is hidden. In orchestration, a coordinator drives the steps and compensations; it is explicit and easier to monitor and change.

11.16 Rate limiting and API gateways

Why?

In simple words: Rate limiting means "each caller gets only so many requests per second". The API gateway is the front gate where every request is checked before it goes in.

Without limits, one buggy client, scraper or tenant can flood your service. Then it becomes slow for everyone. Partners also give you quotas that you must respect when you call them.

Rate limiting keeps things fair and protects your capacity. The API gateway is the natural place to enforce it. It already handles authentication and routing for every request.

Think of a railway reservation counter that allows only a fixed number of forms per person per day. One person can't block the line for everyone else.

What is happening internally?

  • Algorithms (explained with code in 10.5): fixed window, sliding window log, sliding window counter, token bucket, leaky bucket. A token bucket, for example, fills with tokens at a steady rate; each request spends one token; when the bucket is empty, requests are refused.
  • Distributed limiting: when you have many servers, the counters must be shared. You keep them in Redis. The key is user, API key, IP or tenant + endpoint. You update the counters atomically (in one step, so two servers can't clash):
  • INCR + EXPIRE for a fixed window.
  • Sorted sets for a sliding log.
  • A Lua script (runs inside Redis in one step) for a token bucket.

The full design is in 13.2. - API gateway jobs: routing, authentication (JWT validation), rate limiting, TLS termination (decrypting HTTPS at the edge), changing requests/responses, CORS, observability and canary routing (sending a small share of traffic to a new version). No business logic. - BFF (backend for frontend): a separate gateway shaped for each client type — mobile, web or partner.

How does it work?

  1. The client calls the API gateway.
  2. The gateway validates the JWT and finds tenant = t-42, plan = GOLD.
  3. It builds the rate-limit key t-42:/redemptions and checks a token bucket in Redis. A Lua script does this in one round trip.
  4. If allowed, the request is routed to loyalty-service.
  5. If denied, the gateway returns 429 with Retry-After and X-RateLimit-Remaining headers.
Client → API Gateway: validate JWT → tenant = t-42, plan = GOLD
         rate limit key "t-42:/redemptions" → Redis token bucket (Lua, 1 round trip)
         allowed → route to loyalty-service;  denied → 429 + Retry-After + X-RateLimit-Remaining

Example

  • Plans: FREE gets 10 req/s and GOLD gets 100 req/s, per tenant.
  • OTP endpoints: 5 requests/hour per phone number.
  • Outbound calls to a partner API: 50 req/s across all pods. Use a shared Redis bucket, or give each of the N pods a share of 50/N.

When would I use it?

  • Public and partner APIs.
  • Login, OTP and password-reset endpoints, to stop abuse.
  • Fairness between tenants in a multi-tenant system.
  • Outbound calls to partners that rate-limit you.
  • Load shedding during incidents (dropping extra work to stay alive).

What can go wrong?

  • Per-instance limits. If each server has its own counter, the real limit becomes limit × number of instances.
  • Redis as a hard dependency. If Redis is down, what happens? Decide per endpoint: fail-open (allow requests) or fail-closed (block them).
  • Hot keys. A huge tenant puts all its load on one Redis key.
  • No Retry-After. Clients don't know when to try again, so they retry immediately and hammer you.
  • Blocking real bursts. Limits that are too strict block normal short bursts. A token bucket allows controlled bursts.

Interview questions

Q1. Where would you implement rate limiting? At the API gateway or edge for limits on clients, backed by a shared store like Redis so all instances see the same counts. Also inside your own clients, to respect outbound partner limits.

Q2. What should an API gateway do and not do? It should do routing, auth, rate limiting, TLS, observability and request shaping. It should not contain business logic.

11.17 API design: REST, gRPC, GraphQL and real-time

Why?

In simple words: An API is a promise to other teams and apps about how to talk to your service. Pick the right style for each job, and design it carefully, because changing it later is painful.

APIs live for years. Clients build on them. A badly chosen style or careless design causes years of pain for those clients. Typical mistakes:

  • no pagination,
  • no versioning,
  • write calls that are not idempotent (not safe to retry),
  • a different error format on every endpoint.

Interviewers expect you to define clean APIs in your design. They also expect you to pick the right protocol for each interaction.

What is happening internally?

Style Strengths Typical use
REST/JSON over HTTP Works everywhere, can be cached, easy to debug Public, mobile and most internal APIs
gRPC (HTTP/2 + Protobuf) Fast binary format, typed contracts, streaming, deadlines Internal service-to-service calls, low latency
GraphQL The client picks the fields it wants; one round trip can pull from many sources Complex UIs that combine many entities
WebSockets Both sides can send at any time (full-duplex); the connection stays open Chat, live tracking, collaborative editing
Server-Sent Events A simple one-way stream from server to client over HTTP Notifications, LLM token streaming
Long polling Works everywhere Fallback for real-time
Webhooks The server calls the client when an event happens Payment callbacks, partner integrations

A few words from the table:

  • Protobuf — Google's compact binary format with a fixed schema.
  • Deadline — the caller says "I'll wait at most 300 ms", and the whole call chain respects it.
  • Long polling — the client asks "anything new?", and the server holds the request open until there is something to send.

How does it work?

Use this design checklist:

  • Resources and verbs: put nouns in paths (/accounts/{id}/redemptions). Use HTTP methods for actions. Return the correct status codes (7.2).
  • Idempotency: add idempotency keys on POSTs that change data (11.14), so retries are safe.
  • Pagination: for large or changing data, use cursor/keyset pagination (?after=<lastId>&limit=50). "Give me the next 50 after this ID" stays fast and does not skip or repeat rows. Use offset pagination only for small admin lists.
  • Filtering and sorting: use query parameters. Put a maximum on the page size.
  • Versioning: putting the version in the URI (/v1/) is explicit and common. Within one version, make only additive (backward-compatible) changes, like adding new optional fields.
  • Errors: use one consistent format (ProblemDetail, 7.4).
  • Security: auth scopes per endpoint, tenant checks and rate-limit headers.
  • Webhooks:
  • Sign the payloads with HMAC (a shared-secret signature), so receivers know the call is genuine.
  • Retry with backoff.
  • Make receivers idempotent.
  • Allow replay of past events.

Example

  • Create a redemption with an idempotency key; get back 201.
  • List redemptions with a cursor (after=R_812); the response gives the next cursor.
  • Read the balance.
  • Receive a signed partner webhook, idempotent on event ID.
  • Call an internal gRPC method with a 300 ms deadline.
POST   /v1/accounts/{id}/redemptions        Idempotency-Key    → 201 {id, status}
GET    /v1/accounts/{id}/redemptions?after=R_812&limit=20      → 200 {items:[…], next:"R_792"}
GET    /v1/accounts/{id}/balance                                → 200 {points, asOf}
POST   /webhooks/voucher-partner   X-Signature: sha256=…        → 200 (idempotent on event id)
gRPC   LoyaltyService.Accrue(AccrueRequest) returns (AccrueResponse)   // internal, deadline 300 ms

When would I use it?

Use this in the API step of every design:

  • REST — the default.
  • gRPC — between internal services with tight latency budgets.
  • WebSockets/SSE — for live updates.
  • GraphQL — when many clients need different shapes of the same data.

What can go wrong?

  • Breaking changes without versioning. Old clients stop working.
  • Chatty APIs. One screen needs N separate calls.
  • Offset pagination on huge tables. The database must skip millions of rows, so it gets slow.
  • Leaking internal models. Your DB structure becomes the public contract and can't change.
  • Webhooks without signatures or retries. Anyone can fake them, and failed ones are lost.
  • GraphQL without query cost limits. A deeply nested query can be very expensive.

Interview questions

Q1. REST vs gRPC? REST/JSON works everywhere, humans can read it, and it can be cached. gRPC is a typed, binary protocol on HTTP/2 with streaming and lower latency. So gRPC fits better for internal service-to-service calls.

Q2. How do you paginate a large, changing dataset? Use keyset/cursor pagination on an indexed, unique ordering column. Return an opaque "next" cursor that the client sends back for the next page.

Q3. How do you design reliable webhooks? Sign the payloads, retry with backoff, make receivers idempotent by keying on the event ID, and give a replay endpoint or dashboard.

11.18 Storage for files, search and analytics

Why?

In simple words: Your main database is good at small, quick reads and writes. Big files, text search and huge reports each need their own special store, filled with copies from the main database.

Not all data belongs in your OLTP database — the one that handles day-to-day transactions. Here is why:

  • Large files make it bloated.
  • Full-text search is slow in SQL.
  • Analytical queries that scan billions of rows slow down normal transactions.

So you use a specialised store for each job. Each one is fed from the source of truth — the main database that holds the correct data.

What is happening internally?

  • Object storage (S3, Azure Blob):
  • Cheap and very durable (11 nines — 99.999999999%).
  • Holds unlimited files, each fetched by a key (like a file path).
  • You can't edit a file in place; you replace it.
  • Clients upload directly to storage using pre-signed URLs. A pre-signed URL is a temporary link that allows one specific upload and expires soon. Because of this, large files never pass through your app servers.
  • The file's metadata (name, owner, key) lives in the DB.
  • Files are delivered to users through a CDN.
  • Search engines (Elasticsearch/OpenSearch):
  • They use an inverted index: a map from each word to the list of documents that contain it — like the index at the back of a book.
  • Analysers break text into words and clean them up: lowercasing, stemming (running → run), synonyms and transliteration.
  • Results are ranked by relevance using BM25, a scoring formula.
  • Indexing is near-real-time — new data is searchable within about a second.
  • The search engine is fed by events or CDC. So it is eventually consistent (it catches up a little later) and is never the source of truth.
  • Analytics (ClickHouse, BigQuery, Snowflake, Trino over a data lake):
  • Data is stored by column, not by row (columnar), and compressed. It is processed in large chunks at once (vectorised execution). This makes big scans fast.
  • It is fed by CDC/streams or by batch ETL (scheduled extract-transform-load jobs).
  • Two common designs: Lambda architecture has a batch layer plus a fast "speed" layer; Kappa uses only streams.

Think of a library. The books (files) sit on shelves (object storage). The catalogue cards (DB rows) say which shelf. The subject index (search engine) helps you find books by word. The yearly statistics report (analytics) is made in a separate office so the front desk is not disturbed.

How does it work?

  1. Upload: the app asks the API for an upload. The API returns a pre-signed PUT URL. The app uploads straight to Blob. An event triggers processing, and a metadata row is saved.
  2. Search: Postgres changes go through Debezium CDC into Kafka. An indexer writes them to Elasticsearch. The search API reads from Elasticsearch.
  3. Analytics: data flows from Postgres/Kafka into ClickHouse (MergeTree tables, materialised views). Dashboards read from ClickHouse.
Upload: app → POST /uploads → API returns pre-signed PUT URL → app uploads to Blob → event → processing → metadata row
Search: Postgres → Debezium CDC → Kafka → indexer → Elasticsearch ← search API
Analytics: Postgres/Kafka → ClickHouse (MergeTree, materialised views) ← dashboards

Example

Perfect Store audits:

  1. Photos (2–5 MB each) go straight to Azure Blob through pre-signed URLs.
  2. The audit row stores only the blob keys.
  3. An AI verification worker processes the photos.
  4. Compliance dashboards per region come from ClickHouse, not from the transactional database.

When would I use it?

  • Object storage — for any user-uploaded media or documents.
  • Search engine — for product, outlet or text search.
  • OLAP (analytics store) — for dashboards and reports over a large history.

What can go wrong?

  • Uploads through app servers. They use up memory and hit timeouts.
  • Public buckets. Anyone can read the files, so data leaks.
  • Search index drift. The index slowly differs from the source. You need reindexing and reconciliation (comparing and fixing).
  • Analytics on the OLTP primary. Heavy reports slow down live transactions.

Interview questions

Q1. How would you handle large file uploads? Give the client a pre-signed URL so it uploads directly to object storage, using multipart/resumable upload for big files. Keep metadata in the DB, start processing from storage events, and deliver files through a CDN.

Q2. Why not use the database for full-text search? A search engine has inverted indexes, analysers and relevance scoring. It handles fuzzy, multilingual, ranked search at scale far better than SQL. Feed it via CDC, and keep the DB as the source of truth.

11.19 Reliability patterns

Why?

In simple words: In a big system, something is always broken somewhere. Good design expects this, and makes sure one broken part can't take down everything else.

At scale, something is always failing — a pod, a zone, a dependency or a deploy. Reliable systems assume failure will happen. They limit its blast radius — how much of the system one failure can damage. Interviewers expect you to discuss how each component you draw can fail.

Think of a building with fuses on each floor. A short circuit on one floor trips that fuse only. The rest of the building keeps its lights on.

What is happening internally?

  • Timeouts: put a timeout on every network call. Each timeout must be shorter than the caller's own timeout, so the whole chain fits in its timeout budget.
  • Retries:
  • Use exponential backoff (wait longer each time) with jitter (random spread, so clients don't retry together).
  • Retry only idempotent operations and transient errors (temporary ones, like a timeout).
  • Use retry budgets to avoid retry storms.
  • Circuit breakers: if a dependency is unhealthy, stop calling it for a while and fail fast (8.7).
  • Bulkheads: give each dependency its own thread or connection pool. Then one slow dependency can't use up everything. (The name comes from the walls inside a ship that stop water spreading.)
  • Graceful degradation: serve stale or cached data, or a smaller set of features. For example, hide recommendations but keep checkout working.
  • Load shedding: under overload, reject low-priority work early (429/503). This protects the core flows.
  • Redundancy: run N+1 instances (one more than you need) across availability zones. For critical paths, use multi-region active-passive (one region on standby) or active-active (both serve traffic).
  • Backups and DR (disaster recovery):
  • RPO (recovery point objective) — how much data you can afford to lose.
  • RTO (recovery time objective) — how fast you must be back up.

These two numbers decide your replication and backup design. Test restores regularly. - Health checks: liveness ("is it alive?") vs readiness ("can it take traffic?") (8.9). - Safe deployments: - Rolling, blue-green or canary releases, with automatic rollback if the SLO is breached. - Feature flags. - Backward-compatible schema changes (7.16). - Coordination: leader election and distributed locks use etcd, ZooKeeper or Kubernetes leases. Always add fencing tokens. A fencing token is a number that goes up with every new lock. If an old lock holder was paused and wakes up with a stale lock, its writes carry an old number and get rejected. - Clocks: machine wall clocks drift apart. So don't order distributed events by timestamps alone. Use sequence numbers, partitions or logical clocks (counters that only go up).

How does it work?

For each box in your diagram, ask three questions:

  1. What if it is slow?
  2. What if it is down?
  3. What if it is wrong (bad data, duplicate messages)?

Then add the matching pattern and the alert for each answer.

Example

The voucher partner is down for 20 minutes during a festival campaign. Here is what happens:

  1. The circuit breaker opens after 50% of calls fail.
  2. Redemptions are still accepted and points are debited.
  3. The saga parks the voucher step for a later retry. The user sees "voucher arriving shortly".
  4. The bulkhead keeps the other APIs responsive.
  5. The breaker goes half-open (lets a few test calls through). When they succeed, the backlog drains with rate limiting.
  6. Alerts fire when the breaker opens and when the saga backlog gets too old.

When would I use it?

In the "failure handling" step of every design, and in production readiness reviews.

What can go wrong?

  • Retry storms. Everyone retries at once and makes the outage worse.
  • Silent fallbacks. Fallbacks hide failures, and no alert fires.
  • Untested backups. You find out they don't restore only during a disaster.
  • Single-AZ deployments. One zone outage takes everything down.
  • Distributed locks without fencing. A stale lock holder can still write.
  • Deploys that can't roll back. A schema change makes the old version incompatible.

Interview questions

Q1. How do you prevent cascading failures? Use timeouts, limited retries with backoff and jitter, circuit breakers, bulkheads, load shedding and graceful degradation. Together they stop one failing part from pulling down the services that call it.

Q2. What are RPO and RTO? RPO is the maximum data loss you can accept, measured in time. RTO is the maximum time you can take to restore service. Together they decide your replication, backup and failover design.

Q3. Why do distributed locks need fencing tokens? A client can pause (because of GC or the network) and its lock can expire while another client takes the lock. A token that always increases lets the resource reject writes from the old, stale holder.

11.20 Observability, SLIs and SLOs

Why?

In simple words: Observability means you can see what your system is doing from the outside. SLOs turn "is it healthy?" into a clear number that everyone agrees on.

You can't run what you can't see. And "is the system healthy?" needs an exact definition, based on what users experience.

An SLO (service level objective) turns reliability into a measurable target. That target then guides your alerts and your release decisions.

Think of a car dashboard. The speedometer and fuel gauge are your metrics. The rule "keep the speed under 80" is your objective.

What is happening internally?

  • Metrics (Prometheus/Grafana, Azure Monitor): numbers measured over time.
  • RED per service: rate (requests/sec), errors, duration.
  • USE per resource: utilisation, saturation (how much work is waiting), errors.
  • Business KPIs.
  • Logs (ELK/OpenSearch/Loki): structured JSON, with trace, tenant and request IDs in every line.
  • Traces (OpenTelemetry → Jaeger/Tempo/App Insights): one request's journey across services, queues and DB calls, split into timed steps called spans.
  • SLI (service level indicator): what you measure. For example, "% of redemption requests completing successfully in < 500 ms".
  • SLO (objective): the target. For example, 99.9% over 30 days.
  • Error budget: 100% − SLO. Here that is 0.1%, which is about 43 minutes of "bad" per month. If the budget is burning fast, slow down releases and fix reliability.
  • SLA (service level agreement): the promise in the customer contract, with penalties. It is looser than the internal SLO, so you get warned before you break it.
  • Alerting on burn rate: page someone when the error budget is being used up fast. For example, 2% of the monthly budget in 1 hour. Don't page on every CPU spike.

How does it work?

  1. Instrument the code once (Micrometer/OpenTelemetry).
  2. Build a dashboard for each service.
  3. Define 2–4 SLOs for each critical user journey.
  4. Alert on symptoms (what users feel), not on causes.
  5. Link every alert to a runbook (a step-by-step fix guide).

Example

Loyalty SLOs:

  • Redemption availability: 99.9%.
  • Redemption p99 latency: < 800 ms (99% of requests finish faster than this).
  • Accrual freshness: 99% of order events appear in balances within 60 s. You measure this from consumer lag and event timestamps.

When would I use it?

From the first deploy of any service. Also in the "monitoring" step of every design interview.

What can go wrong?

  • Alert fatigue. Alerts on causes (like CPU) fire all the time, so people start ignoring them.
  • Dashboards without SLOs. Lots of charts, but no clear "good or bad" line.
  • High-cardinality metrics cost. Labels with too many unique values (like user ID) make the metrics store huge and expensive.
  • Sampling away the traces you need. Use tail-based sampling — decide what to keep after the request ends, so errors and slow requests are always kept.

Interview questions

Q1. SLI vs SLO vs SLA? The SLI is the measured indicator. The SLO is the internal target for it. The SLA is the external promise in the customer contract.

Q2. What is an error budget used for? It puts a number on how much unreliability is allowed. When it burns fast, alerts fire and feature releases slow down so the team can focus on reliability work.

11.21 Security in system design

Why?

In simple words: Security means only the right person can do the right thing on the right data. In a multi-tenant system, the biggest job is making sure one company can never see another company's data.

Security failures are the most expensive kind. They cause data breaches, fraud, regulatory penalties and lost customer trust.

In a multi-tenant SaaS, many customer companies (tenants) share the same system. So one authorisation bug can show one brand's data to another brand. That is why designs are expected to cover security explicitly.

Think of a bank locker room. The guard checks your ID at the door (authentication). Your key opens only your own locker (authorisation). Every visit is written in the register (audit).

What is happening internally?

  • Authentication (who are you?): OAuth2/OIDC with an identity provider. JWT access tokens are validated at the gateway and in the services (8.2).
  • Authorisation (what can you do?): check roles and scopes. Also check resource- and tenant-level access on every query. The most common real-world vulnerability is broken access control — OWASP #1.
  • Transport: TLS everywhere. Use mTLS (both sides show certificates) between services, often through a service mesh.
  • Secrets: keep them in a vault (Azure Key Vault, HashiCorp Vault) and rotate them. Never put them in code or images.
  • Data:
  • Encrypt data at rest.
  • For sensitive data, use field-level encryption or tokenisation (replace the real value with a stand-in token). This covers PII (personal data) and payment data. For cards, use a PSP (payment service provider).
  • Keep as little PII as possible, and mask it in logs.
  • Input:
  • Validate all input.
  • Use parameterised queries (stops SQL injection).
  • Encode output (stops XSS — cross-site scripting).
  • Protect URL fetches against SSRF (tricking your server into calling internal addresses).
  • Edge: WAF (web application firewall), DDoS protection and rate limits (11.16).
  • Audit: keep immutable (unchangeable) audit logs for sensitive actions, like admin adjustments and payouts. Add maker-checker approvals: one person makes the change, a second person approves it.
  • Webhooks and partners: signed requests, IP allow-lists and idempotency.

How does it work?

Threat-model each flow. That means asking:

  1. Who can call it?
  2. With which identity?
  3. Which tenant's data does it touch?
  4. What could an attacker replay or forge?
  5. What gets logged?

Example

Admin points adjustment:

  1. It needs ROLE_ADMIN and the same tenant claim as the account.
  2. It creates a pending adjustment (the maker).
  3. A second admin approves it (the checker).
  4. The ledger entry records both identities.
  5. The action is audited. If it is above a threshold, an alert fires.

When would I use it?

In the API and data steps of every design. Also when reviewing any feature that touches money, PII or cross-tenant data.

What can go wrong?

  • Trusting client-supplied tenant or user IDs. The client can simply change them.
  • Secrets in Git. Anyone with repo access, or a leak, gets them.
  • Verbose errors. Error messages leak internal details.
  • Logging tokens or PII. Logs become a security risk.
  • No rate limits on OTP/login. Attackers can guess codes or passwords.
  • Overly broad service credentials. One stolen credential opens too much.

Interview questions

Q1. How do you ensure tenant isolation in a multi-tenant system? Take the tenant from the authenticated token, never from the request body. Enforce it in authorisation checks, and apply mandatory tenant filters at the data layer — or use separate schemas/databases for strong isolation. Add tests that try cross-tenant access.

Q2. What security measures would you add to a payments or points system? Strong auth, idempotency, maker-checker for manual adjustments, audit logs, encryption, rate limits, anomaly alerts and reconciliation.

11.22 Generating unique IDs at scale

Why?

In simple words: When many servers create records at the same time, each record still needs a unique ID. The trick is to make IDs unique without all servers asking one central place every time.

Orders, messages, events and short links all need unique IDs. There are two simple options, and both have problems:

  • One auto-increment database sequence. With many shards and regions, everyone waits on this one counter. It becomes a bottleneck and a single point of failure (SPOF).
  • Random UUIDs. They are unique, but large and unordered. That is bad for B-tree index locality (new rows land all over the index) and for sorting by time.

Think of restaurant token numbers. If each counter prints tokens starting with its own counter number, two counters can never give out the same token — and they don't need to talk to each other.

What is happening internally?

Approach Properties
DB auto-increment / sequence Simple and ordered; a bottleneck/SPOF across shards
UUIDv4 (random) No coordination needed; 128 bits; random → poor index locality
UUIDv7 Starts with a timestamp, then randomness; no coordination; friendly to indexes
Snowflake (Twitter) 64-bit: 1 sign bit + 41-bit millisecond timestamp (~69 years) + 10-bit machine ID (1,024 nodes) + 12-bit sequence (4,096 IDs per ms per node) → roughly sorted by time, compact
Range allocation Each service instance leases a block (e.g., 1M IDs) from a coordinator and hands them out locally

How does it work?

Each node makes Snowflake IDs like this:

  1. On each request, read the current millisecond.
  2. If it is the same millisecond as last time, add 1 to the sequence.
  3. If the sequence goes past 4,095 (overflows), wait for the next millisecond.
  4. If it is a new millisecond, reset the sequence to 0.
  5. Combine the parts: (timestamp − epoch) << 22 | machineId << 12 | sequence.

The epoch is a fixed starting date. Subtracting it keeps the timestamp small enough to fit in 41 bits.

Example

final class Snowflake {
    private static final long EPOCH = 1_735_689_600_000L;   // 2025-01-01
    private final long machineId; private long lastMs = -1, seq = 0;
    Snowflake(long machineId) { if (machineId < 0 || machineId > 1023) throw new IllegalArgumentException(); this.machineId = machineId; }
    synchronized long next() {
        long now = System.currentTimeMillis();
        if (now < lastMs) throw new IllegalStateException("clock moved backwards");
        if (now == lastMs) {
            seq = (seq + 1) & 4095;
            if (seq == 0) while ((now = System.currentTimeMillis()) <= lastMs) { }   // sequence exhausted: wait for the next ms
        } else seq = 0;
        lastMs = now;
        return ((now - EPOCH) << 22) | (machineId << 12) | seq;
    }
}

When would I use it?

  • Snowflake-style or UUIDv7 IDs — for high-volume entities across shards: orders, events, messages, tweets (13.17).
  • Range allocation — for short-link codes (13.1).
  • DB sequences — when one database is enough.

What can go wrong?

  • Duplicate machine IDs. Two nodes with the same ID can create the same IDs. Assign machine IDs through config, a coordinator or Kubernetes StatefulSet ordinals (each pod gets a fixed number).
  • Clock moving backwards. NTP (time sync) can move the clock back. Refuse to create IDs, or wait until the clock catches up.
  • Exposing sequential IDs publicly. Attackers can guess other IDs by counting (enumeration attacks). Use opaque public IDs instead.

Interview questions

Q1. How would you generate unique IDs across many servers? Use Snowflake-style IDs (timestamp + machine ID + sequence) or UUIDv7. Both are time-ordered and need no coordination. Use range leasing when IDs must be dense or short.

Q2. Why are random UUIDs bad as primary keys in B-tree indexes? Random inserts land all over the index. This causes page splits, poor cache locality and larger indexes. Time-ordered IDs are added near the end of the index instead.
