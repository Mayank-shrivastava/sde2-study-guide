8.1 Spring Security architecture

Why?

In simple words: Spring Security is a security guard that stands in front of your code. It checks who the caller is and what they may do, before your controller ever runs.

Every endpoint must answer two questions:

  • Who is calling? This is called authentication.
  • Are they allowed to do this? This is called authorisation.

In a multi-tenant SaaS there is a third question. A tenant is one customer company that shares the platform with others. So you also ask: can this caller touch this tenant's data?

If you write these checks by hand in every controller, someone will forget one. One missed check can leak data. Spring Security puts all these checks in one place. It is a configurable chain of filters that runs before your code.

Think of a company office. The guard at the gate checks your ID card (authentication). The lift only takes you to the floors your card allows (authorisation). You do not ask each desk to check your ID again.

What is happening internally?

Request → DelegatingFilterProxy (a servlet filter registered with Tomcat)
        → FilterChainProxy → picks the first SecurityFilterChain whose matcher fits the URL
            ├─ CorsFilter
            ├─ CsrfFilter (for browser/cookie sessions)
            ├─ authentication filters: BearerTokenAuthenticationFilter (JWT), UsernamePasswordAuthenticationFilter, BasicAuthenticationFilter …
            │     → AuthenticationManager → AuthenticationProvider(s) → Authentication object
            │     → stored in SecurityContextHolder (ThreadLocal) for this request
            ├─ ExceptionTranslationFilter: AuthenticationException → 401 (entry point); AccessDeniedException → 403
            └─ AuthorizationFilter: checks URL rules (requestMatchers … hasAuthority …)
        → DispatcherServlet → controller → method security (@PreAuthorize) via AOP proxy

Here is the same flow as steps:

  1. Tomcat receives the request. It passes it to DelegatingFilterProxy, a normal servlet filter.
  2. That filter hands over to FilterChainProxy. It picks the first SecurityFilterChain whose URL matcher fits the request.
  3. The chain runs its filters in order: CORS, CSRF, then the authentication filters.
  4. An authentication filter (for example, the JWT one) asks the AuthenticationManager to check the credentials. The manager uses one or more AuthenticationProviders. If the check passes, you get an Authentication object.
  5. This object is stored in SecurityContextHolder. That is a ThreadLocal — a per-thread storage box — so it lives only for this request.
  6. ExceptionTranslationFilter catches security errors. An AuthenticationException becomes 401. An AccessDeniedException becomes 403.
  7. AuthorizationFilter checks your URL rules (requestMatchers … hasAuthority …).
  8. The request reaches DispatcherServlet and then your controller.
  9. If a service method has @PreAuthorize, an AOP proxy (a wrapper object Spring puts around your bean) checks it before the method runs.

Key objects you should know:

  • Authentication — holds the principal (who the user is), the credentials and the authorities (what they may do).
  • SecurityContextHolder — where the current Authentication is kept for this request.
  • AuthenticationManager / AuthenticationProvider — the classes that actually check credentials.
  • UserDetailsService — loads a user from your store for username/password login.
  • PasswordEncoder — hashes passwords with BCrypt or Argon2. Never store plain text or MD5.
  • GrantedAuthority — one permission. It can be a role like ROLE_ADMIN or a scope like SCOPE_points.redeem.

401 vs 403:

  • 401 Unauthorized means "I don't know who you are". Credentials are missing or invalid. The name is confusing — it really means not authenticated.
  • 403 Forbidden means "I know who you are, but you are not allowed to do this".

How does it work?

You define one or more SecurityFilterChain beans. You write them with the lambda DSL — the http.csrf(...).authorizeHttpRequests(...) style shown below. Spring Boot auto-configures everything else.

You protect at two levels:

  • URL rules give coarse protection. For example, "everything under /admin needs ADMIN".
  • Method security (@PreAuthorize) gives fine-grained checks. It sits close to the business logic, so it can look at method arguments like tenantId.

Example

@Configuration
@EnableMethodSecurity
class SecurityConfig {
    @Bean
    SecurityFilterChain api(HttpSecurity http) throws Exception {
        return http
            .csrf(csrf -> csrf.disable())                                      // stateless bearer-token API
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/actuator/health/**").permitAll()
                .requestMatchers(HttpMethod.POST, "/api/v1/accounts/*/redemptions").hasAuthority("SCOPE_points.redeem")
                .requestMatchers("/api/v1/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated())
            .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()))      // validate JWTs (8.2)
            .build();
    }
}

@Service
class CampaignService {
    @PreAuthorize("hasRole('ADMIN') and #tenantId == authentication.token.claims['tenant_id']")
    public Campaign create(String tenantId, CreateCampaignRequest req) { /* ... */ return null; }
}

When would I use it?

In every service that exposes HTTP. Use three layers together:

  1. URL rules — coarse checks.
  2. Method security — fine checks near the business logic.
  3. Data-level tenant filtering — every query is scoped by tenant. You can use a Hibernate filter or an explicit WHERE tenant_id = ? condition.

Why all three? Because in a multi-tenant system, one authorisation bug can show one customer's data to another customer. That is the worst kind of bug in SaaS.

What can go wrong?

  • When you add the security starter, every endpoint suddenly needs login. Spring prints a generated password at startup. This surprises people, but it is the safe default.
  • Rule order matters. Rules are matched from top to bottom. If you put anyRequest().permitAll() before the specific rules, everything is open.
  • Trusting a tenant ID from a request header without checking it against the token's tenant claim. A user can just change the header and read another tenant's data. This is called an IDOR: insecure direct object reference.
  • Disabling CSRF for a browser app that uses cookie sessions. CSRF protection is needed there. (It is only safe to disable for stateless bearer-token APIs.)
  • The SecurityContext does not move to @Async threads on its own, because it is stored in a ThreadLocal. Use DelegatingSecurityContextExecutor to carry it over.

Interview questions

Q1. How does Spring Security process a request? A FilterChainProxy runs the matching SecurityFilterChain. First, authentication filters check the credentials, build an Authentication object and store it in the SecurityContextHolder. Then authorisation filters check the URL rules. Security exceptions are turned into 401 or 403 responses. Finally, method security checks like @PreAuthorize run at the service proxy.

Q2. Authentication vs authorisation? Authentication checks who you are; if it fails, you get 401. Authorisation decides what an already-authenticated user may do; if it fails, you get 403.

Q3. How do you enforce tenant isolation? Take the tenant from the verified token, not only from a header the client sends. Check it in method security. And apply a mandatory tenant filter to every data query, so even a missed check cannot return another tenant's rows.

8.2 JWT, OAuth2 and OpenID Connect

Why?

In simple words: A JWT is a signed pass that the caller carries with every request. Any service can check the signature by itself, so nobody needs to call a central session store. OAuth2 is the set of rules for how you get that pass.

In microservices, you don't want every service to call a central session store on every request. That store becomes slow and a single point of failure.

  • A JWT (JSON Web Token) is a self-contained, signed token. Any service can verify it locally, without a network call.
  • OAuth2 is the standard for how clients get tokens.
  • OpenID Connect (OIDC) sits on top of OAuth2 and adds the user's identity.

Different callers use different OAuth2 flows. Your mobile apps use one flow, partner integrations another, and service-to-service calls another.

Think of a railway ticket with an official stamp. The TT on any coach can check the stamp himself. He does not phone the booking office for every passenger.

What is happening internally?

A JWT has three parts joined by dots: base64url(header).base64url(payload).signature. Base64url is just a text encoding, not encryption.

header:  {"alg":"RS256","kid":"2026-key-1"}
payload: {"iss":"https://login.example.com","sub":"user-123","aud":"loyalty-api","exp":1790000000,
          "iat":1789999100,"scope":"points.read points.redeem","tenant_id":"t-42","roles":["RETAILER"]}
signature: RSA-SHA256(header.payload, issuer's PRIVATE key)

What this means:

  • Signed, not encrypted. Anyone can decode and read the payload. So never put secrets or sensitive PII (personal data like phone numbers) inside it. The signature only proves that nobody changed it.
  • Asymmetric signing (RS256/ES256). The identity provider (Keycloak, Azure AD/Entra ID, Auth0, Cognito) signs with its private key. Your services verify with the matching public keys. These public keys are published at the provider's JWKS endpoint (JSON Web Key Set). Services cache them. When keys rotate, the kid (key ID) in the header tells which key to use.
  • What a resource server checks. A resource server is your API that receives the token. It checks: 1. the signature; 2. exp (expiry) and nbf (not-before), allowing a small clock skew; 3. iss — who issued it; 4. aud — which API it was made for.

Then it maps scope and roles to Spring authorities. - Stateless — but revocation is hard. There is no server-side session to look up. The downside: you cannot easily cancel a token before it expires. So keep access tokens short-lived (5–15 min). Pair them with refresh tokens. Refresh tokens live longer, are rotated on use, can be revoked, and must be stored securely.

OAuth2 flows:

Flow Who uses it
Authorization Code + PKCE Mobile and web apps acting for a user (no client secret is stored on the device)
Client Credentials Service-to-service calls (a machine identity, no user)
Refresh Token Getting new access tokens without logging in again
Device Code TVs and CLIs
(Implicit, Password — deprecated) Don't use them

PKCE (Proof Key for Code Exchange) is a one-time secret the app creates for each login. It stops a stolen authorisation code from being used by another app.

OIDC adds two things: an ID token (it says who the user is) and a userinfo endpoint. The access token is still the one your APIs check.

How does it work?

You point Spring at the identity provider. From the issuer-uri, Spring discovers the JWKS URL and also validates iss. You list the expected audience.

spring.security.oauth2.resourceserver.jwt:
  issuer-uri: https://login.example.com/realms/fieldassist     # discovers JWKS, validates iss
  audiences: loyalty-api

Often your provider puts roles in a custom claim, like roles. Spring does not know about it by default. This converter maps that claim to ROLE_ authorities:

@Bean
JwtAuthenticationConverter jwtAuthConverter() {                  // map a custom "roles" claim to ROLE_ authorities
    var roles = new JwtGrantedAuthoritiesConverter();
    roles.setAuthoritiesClaimName("roles");
    roles.setAuthorityPrefix("ROLE_");
    var conv = new JwtAuthenticationConverter();
    conv.setJwtGrantedAuthoritiesConverter(roles);
    return conv;
}

Example

A service-to-service call using client credentials (loyalty service → voucher partner gateway). The interceptor gets a token, attaches it to each request and refreshes it when it expires:

@Bean
RestClient voucherClient(RestClient.Builder b, OAuth2AuthorizedClientManager mgr) {
    var interceptor = new OAuth2ClientHttpRequestInterceptor(mgr);       // Spring Security 6.4+: attaches and refreshes tokens
    interceptor.setClientRegistrationIdResolver(req -> "voucher-gateway");
    return b.baseUrl("https://vouchers.internal").requestInterceptor(interceptor).build();
}
// application.yml: spring.security.oauth2.client.registration.voucher-gateway.authorization-grant-type=client_credentials …

When would I use it?

  • JWT resource server — for every API behind an identity provider.
  • Client credentials — for calls between services.
  • Authorization Code + PKCE — for mobile app login.
  • mTLS or service-mesh identity — for internal calls in high-security setups. mTLS means both sides show certificates to each other.

What can go wrong?

  • Accepting alg: none (no signature at all), or HS256 with a secret that can be guessed. Good libraries block this if you configure them correctly.
  • Not checking aud. Then a token made for some other API is accepted by yours.
  • Long-lived access tokens that cannot be revoked.
  • Storing tokens in browser localStorage. An XSS attack (injected script) can steal them. Use secure cookies or keep them in memory instead.
  • Huge tokens with too many claims. They can hit HTTP header size limits.
  • Clocks on servers that differ slightly (clock skew). This causes random "token expired" errors.

Interview questions

Q1. How does JWT authentication work? The client sends a signed token with the request. The service checks the signature using the issuer's public key from the JWKS endpoint. It then checks expiry, issuer and audience, and builds the security context from the claims. There is no session lookup.

Q2. How do you revoke a JWT? You cannot revoke it directly. So you keep access tokens short-lived and revoke the refresh tokens instead. For sensitive actions, use token introspection (ask the provider if the token is still valid) or keep a deny-list of token IDs (jti).

Q3. OAuth2 vs OpenID Connect? OAuth2 is delegated authorisation — it gives access tokens for calling APIs. OIDC is an identity layer on top of it — it adds ID tokens and user info, so you know who the user is.

Q4. Which flow for a mobile app, and which for service-to-service? Authorization Code with PKCE for a mobile app. Client Credentials for service-to-service.

8.3 Unit testing with JUnit 5 and Mockito

Why?

In simple words: Unit tests are small, fast checks of one class at a time. You replace its neighbours with fakes, so you test only your logic. They let you change code later without fear.

Tests let you change code without fear. Unit tests give the fastest feedback — they run in milliseconds. They are also the cheapest way to lock down business rules, such as redemption limits, rule evaluation and idempotency behaviour. (Idempotent means doing the same thing twice has the same effect as doing it once.)

Interviewers also judge your code quality by asking: can you test what you design?

What is happening internally?

  • JUnit 5 (Jupiter) finds methods marked @Test and runs them. It gives you:
  • lifecycle hooks such as @BeforeEach and @AfterEach (run before/after each test);
  • parameterised tests (@ParameterizedTest + @CsvSource/@MethodSource) — one test method run with many inputs;
  • extensions (@ExtendWith) that plug in extra behaviour.
  • Mockito creates fake objects:
  • Mocks are generated subclasses or proxies. They record the calls they get and return the answers you stubbed.
  • Spies wrap a real object.
  • @InjectMocks builds the class under test and passes the mocks into it.
  • AssertJ gives fluent, readable assertions, like assertThat(x).isEqualTo(…) and assertThatThrownBy(…).

The test pyramid tells you the mix: many fast unit tests at the bottom, fewer slice and integration tests in the middle (8.4), and only a handful of end-to-end tests at the top.

Think of a car-mechanic testing an engine on a stand. He does not fit the whole car. He feeds fake fuel and fake signals and checks what the engine does.

How does it work?

Every test has three parts:

  1. Arrange — set up data and stubs.
  2. Act — call the method.
  3. Assert — check the result and the important interactions.

Mock only collaborators at the boundaries: repositories, HTTP clients, clocks. Never mock the class under test, and never mock value objects (simple data holders).

Example

@ExtendWith(MockitoExtension.class)
class RedemptionServiceTest {
    @Mock AccountRepository accounts;
    @Mock LedgerRepository ledger;
    @Mock OutboxRepository outbox;
    @InjectMocks RedemptionService service;

    @Test
    void rejectsWhenBalanceIsInsufficient() {
        when(ledger.findByTenantIdAndIdempotencyKey("t1", "k1")).thenReturn(Optional.empty());
        when(accounts.debitIfSufficient("a1", 500)).thenReturn(0);           // conditional update failed
        when(accounts.balance("a1")).thenReturn(120L);

        assertThatThrownBy(() -> service.redeem("t1", "a1", "k1", 500))
                .isInstanceOf(InsufficientPointsException.class)
                .hasMessageContaining("has 120");
        verify(ledger, never()).save(any());
        verifyNoInteractions(outbox);
    }

    @Test
    void replayingSameIdempotencyKeyDoesNotDebitAgain() {
        var prior = new LedgerEntry("t1", "a1", EntryType.REDEMPTION, -50, "k1", Instant.EPOCH);
        when(ledger.findByTenantIdAndIdempotencyKey("t1", "k1")).thenReturn(Optional.of(prior));

        service.redeem("t1", "a1", "k1", 50);

        verify(accounts, never()).debitIfSufficient(anyString(), anyLong());
    }

    @ParameterizedTest
    @CsvSource({"SILVER,100,100", "GOLD,100,150", "PLATINUM,100,200"})
    void tierMultiplier(Tier tier, long base, long expected) {
        assertThat(tier.apply(base)).isEqualTo(expected);
    }

    @Test
    void capturesPublishedEvent() {
        when(ledger.findByTenantIdAndIdempotencyKey(any(), any())).thenReturn(Optional.empty());
        when(accounts.debitIfSufficient("a1", 50)).thenReturn(1);
        when(ledger.save(any())).thenAnswer(inv -> inv.getArgument(0));       // return what was saved
        service.redeem("t1", "a1", "k2", 50);
        ArgumentCaptor<OutboxEvent> captor = ArgumentCaptor.forClass(OutboxEvent.class);
        verify(outbox).save(captor.capture());
        assertThat(captor.getValue().type()).isEqualTo("PointsRedeemed");
    }
}

What each test shows:

  • rejectsWhenBalanceIsInsufficient — a failed debit throws the right exception, and nothing is saved to the ledger or outbox.
  • replayingSameIdempotencyKeyDoesNotDebitAgain — the same key sent twice does not debit twice.
  • tierMultiplier — one parameterised test covers three tiers.
  • capturesPublishedEvent — an ArgumentCaptor grabs the object passed to outbox.save, so you can check its contents.

When would I use it?

For all domain logic and service orchestration (services that call other services in order).

Inject Clock, ID generators and random sources instead of calling them directly. Then tests can control them, and results are deterministic — the same every run.

What can go wrong?

  • Over-mocking. Tests copy the implementation line by line. They break on every refactor and prove nothing. Check behaviour — outputs and important interactions — not every single call.
  • Mocking value objects or the class under test.
  • Unused stubs. Mockito's strict stubs fail the test when a stub is never used. This is good: it catches outdated tests.
  • Tests that depend on time, randomness, HashMap ordering or the state left by other tests. They pass sometimes and fail sometimes (flaky tests).

Interview questions

Q1. Mock vs stub vs spy? A stub just returns canned answers. A mock also lets you verify which calls were made. A spy wraps a real object and calls the real methods unless you stub them.

Q2. What should you mock? External boundaries and collaborators — repositories, HTTP clients, clocks and message publishers. Do not mock value objects or the logic you are testing.

Q3. How do you test time-dependent code? Inject a Clock into the class. In tests, pass Clock.fixed so "now" is always the same.

8.4 Slice tests and integration tests with Testcontainers

Why?

In simple words: Mocks can't tell you if your SQL is wrong or your JSON mapping is broken. So you also run tests with real Spring wiring and a real database in Docker. Testcontainers starts that database for you inside the test.

Unit tests with mocks cannot catch:

  • a wrong JPQL query;
  • a broken JSON mapping;
  • a missing index;
  • a Postgres-specific SQL feature;
  • a misconfigured Kafka listener.

You need tests that run the real Spring wiring against real infrastructure. These tests must still be fast and give the same result on every laptop and every CI run.

What is happening internally?

  • Slice tests start only part of the application context — one layer:
  • @WebMvcTest(Controller.class) loads the MVC setup, the controller, its advice and Jackson. Services are replaced by @MockitoBeans. MockMvc sends fake requests without starting a real server.
  • @DataJpaTest loads JPA and your repositories. Each test runs in a transaction that is rolled back at the end.
  • There are others too, like @JsonTest and @RestClientTest.
  • @SpringBootTest starts the full context. It can also start a real server on a random port.
  • Testcontainers starts real Docker containers (PostgreSQL, Kafka, Redis) from inside the test. With @ServiceConnection (Boot 3.1+), Spring automatically picks up their dynamic URLs and ports. Containers can be reused across test classes.
  • The context cache: Spring keeps an application context and reuses it for other test classes with the same configuration. But each different set of @MockitoBeans creates a new context. That slows the suite.

Think of a dress rehearsal for a wedding. Practising each dance alone is a unit test. The rehearsal on the real stage, with the real sound system, is the integration test.

How does it work?

A web-slice test. It checks that bad input gives a 400 with two field errors, without any real service:

@WebMvcTest(RedemptionController.class)
class RedemptionControllerTest {
    @Autowired MockMvc mvc;
    @MockitoBean RedemptionService service;                    // Spring Framework 6.2+ (older: @MockBean)

    @Test
    void returns400WithFieldErrors() throws Exception {
        mvc.perform(post("/api/v1/accounts/a1/redemptions")
                .header("Idempotency-Key", "k1")
                .contentType(MediaType.APPLICATION_JSON)
                .content("{\"points\": -5, \"rewardCode\": \"\"}"))
           .andExpect(status().isBadRequest())
           .andExpect(jsonPath("$.errors.length()").value(2));
    }
}

Example

A full integration test against real Postgres. Twenty threads try to redeem 100 points each from an account holding 1,000:

@SpringBootTest
@Testcontainers
class RedemptionConcurrencyIT {
    @Container @ServiceConnection
    static PostgreSQLContainer<?> pg = new PostgreSQLContainer<>("postgres:16-alpine");

    @Autowired RedemptionService service;
    @Autowired AccountRepository accounts;

    @Test
    void twentyConcurrentRedemptionsNeverOverdraw() throws Exception {
        accounts.save(new Account("a1", "t1", 1_000));
        try (ExecutorService pool = Executors.newFixedThreadPool(20)) {
            List<Future<?>> fs = new ArrayList<>();
            for (int i = 0; i < 20; i++) {
                String key = "k" + i;
                fs.add(pool.submit(() -> {
                    try { service.redeem("t1", "a1", key, 100); } catch (InsufficientPointsException ignored) { }
                }));
            }
            for (Future<?> f : fs) f.get();
        }
        assertThat(accounts.findById("a1").orElseThrow().balance()).isZero();   // exactly 10 succeeded, never negative
    }
}

Exactly 10 redemptions should succeed and the balance must end at zero — never negative. This concurrency test against real Postgres is the single most convincing thing to show in your Java project (8.11).

When would I use it?

  • @WebMvcTest — for request mapping, validation, error format and security rules.
  • @DataJpaTest + Testcontainers — for custom queries and constraints.
  • @SpringBootTest + Testcontainers — for end-to-end flows (API → DB → Kafka) and concurrency guarantees.

Run all of them in CI on every pull request.

What can go wrong?

  • Using H2 (an in-memory database) instead of your real database. H2 has a different SQL dialect, different locking, different JSONB and constraint behaviour. Tests pass and production breaks.
  • Slow suites because of many unique contexts. Each different mock set or property set builds a new context. Standardise your test configurations so they share one.
  • Tests that share data and don't clean up. Then a test passes or fails depending on run order.
  • @Transactional on integration tests can hide bugs. The data never really commits. Lazy loading works only because the test's transaction is still open — in production it would fail.

Interview questions

Q1. @WebMvcTest vs @DataJpaTest vs @SpringBootTest? @WebMvcTest is a web-layer slice with mocked services. @DataJpaTest is a JPA slice with repositories, each test in a rolled-back transaction. @SpringBootTest loads the full application context.

Q2. Why use Testcontainers instead of H2? Your tests run against the same database engine and version as production. So they catch differences in SQL dialect, locking, constraints and features that H2 would hide.

Q3. How would you test that concurrent redemptions never overdraw? Write an integration test against real Postgres. Fire N concurrent redemptions, each with a different idempotency key. Then assert the final balance and the exact number of successes.

8.5 Kafka with Spring: producers, consumers, idempotency and dead letters

Why?

In simple words: Kafka is a durable notice board of events. One service pins up "order completed", and other services read it whenever they are ready — even if they were down for an hour. Spring Kafka makes writing and reading these events easy.

Services must react to each other's events. For example: order completed → accrue points → notify the retailer → update analytics.

But they should not depend on each other synchronously (waiting for a direct reply):

  • If the loyalty service is down, ordering must still work.
  • When loyalty comes back, it must process everything it missed.

Kafka gives you an event log that is durable (survives crashes), ordered and replayable (you can read it again). Spring Kafka makes producing and consuming events simple. The Kafka concepts are in 11.12–11.13; this section covers the Spring side.

What is happening internally?

  • Producer side. KafkaTemplate wraps a thread-safe KafkaProducer. The producer groups records per partition into batches and sends them asynchronously. With acks=all plus producer idempotence (on by default since Kafka 3.0), producer retries cause neither lost nor duplicate records.
  • Consumer side. @KafkaListener creates a listener container: 1. It starts one or more consumer threads (set by concurrency). 2. Each thread owns a KafkaConsumer in the consumer group. 3. Each consumer polls records from the partitions assigned to it and calls your method. 4. After your method returns, the container commits the offset (the "read up to here" bookmark). The default is AckMode.BATCH.
  • So delivery is at-least-once. If the app crashes after processing but before the commit, the same record comes again. Your code must handle duplicates.
  • Error handling. DefaultErrorHandler retries a failed record with a backoff (wait) by seeking back to it. After the retries run out, it gives the record to a recoverer. Usually that is DeadLetterPublishingRecoverer. It publishes the record to <topic>.DLT (dead-letter topic) with headers explaining the error.
  • Ordering is only per partition. If you use accountId as the key, all events of one account go to the same partition, so they stay in order.

Think of the railway parcel office register. Each parcel is noted down. Every godown clerk marks the last entry he handled. If he goes on leave, he restarts from his mark — and may handle one parcel twice, so he must check before acting.

How does it work?

spring.kafka:
  bootstrap-servers: kafka:9092
  producer:
    acks: all
    key-serializer: org.apache.kafka.common.serialization.StringSerializer
    value-serializer: org.springframework.kafka.support.serializer.JsonSerializer
  consumer:
    group-id: loyalty-accrual
    auto-offset-reset: earliest
    key-deserializer: org.apache.kafka.common.serialization.StringDeserializer
    value-deserializer: org.springframework.kafka.support.serializer.JsonDeserializer
    properties.spring.json.trusted.packages: "com.fa.events"

Example

public record OrderCompleted(String eventId, String tenantId, String outletId, String orderId, long amountPaise, Instant at) {}

@Component
class AccrualConsumer {
    private final ProcessedEventRepository processed;
    private final AccrualService accrual;
    AccrualConsumer(ProcessedEventRepository processed, AccrualService accrual) { this.processed = processed; this.accrual = accrual; }

    @KafkaListener(topics = "order-completed", concurrency = "3")
    @Transactional
    public void on(OrderCompleted evt) {
        if (processed.existsById(evt.eventId())) return;                       // duplicate delivery → no-op
        accrual.accrue(evt.tenantId(), evt.outletId(), evt.orderId(), evt.amountPaise());
        processed.save(new ProcessedEvent(evt.eventId(), Instant.now()));      // same DB transaction as the effect
        // PK on event_id also protects against two consumers racing on a redelivered record
    }
}

@Configuration
class KafkaErrorConfig {
    @Bean
    DefaultErrorHandler errorHandler(KafkaTemplate<Object, Object> template) {
        var backoff = new ExponentialBackOffWithMaxRetries(3);
        backoff.setInitialInterval(500); backoff.setMultiplier(2.0);
        var handler = new DefaultErrorHandler(new DeadLetterPublishingRecoverer(template), backoff);
        handler.addNotRetryableExceptions(ValidationException.class, DeserializationException.class);   // poison → DLT now
        return handler;
    }
}

@Service
class PointsEventPublisher {
    private final KafkaTemplate<String, Object> kafka;
    PointsEventPublisher(KafkaTemplate<String, Object> kafka) { this.kafka = kafka; }
    void publish(PointsEvent e) {
        kafka.send("points-events", e.accountId(), e)                           // key → partition → per-account order
             .whenComplete((res, ex) -> { if (ex != null) log.error("publish failed {}", e.eventId(), ex); });
    }
}

How the consumer stays safe against duplicates:

  1. It checks if this eventId was already processed. If yes, it returns and does nothing.
  2. It applies the accrual.
  3. It saves the eventId in processed_event — in the same database transaction as the accrual.
  4. The primary key on event_id blocks two consumers that race on the same redelivered record.

The error handler retries 3 times with exponential backoff (500 ms, then doubling). Validation and deserialisation errors skip the retries — those records are poison (they will never succeed), so they go to the DLT at once.

For non-blocking retries, use @RetryableTopic. It sends failed records through separate retry topics with delays, and finally to the DLT. This way one failing record does not stall its whole partition.

When would I use it?

  • Event-driven integration between services.
  • Asynchronous processing of high-volume events: accruals, notifications, analytics.
  • CDC pipelines (Change Data Capture — streaming every database change as an event).
  • Audit streams.

When the event must not be lost, publish from the outbox relay (11.15), not directly inside the business transaction.

What can go wrong?

  • Non-idempotent consumers apply the effect twice when a record is redelivered. This is the root cause of "duplicate reward postings under retries".
  • Dual writes: repo.save(); kafka.send(); — two separate systems. The DB may commit while the send fails, or the reverse. Use the outbox pattern.
  • Poison messages retried forever, blocking the partition. Classify exceptions as retryable or not, and use a DLT.
  • Slow processing. If one poll takes longer than max.poll.interval.ms, Kafka kicks the consumer out of the group. This causes rebalance storms and redeliveries. Keep handlers fast, or reduce max.poll.records.
  • Hot keys. If one huge tenant is the key, all its events land in one partition. So one consumer does all the work.
  • Schema changes that break consumers. Use a schema registry, or allow only additive JSON changes (add fields, never remove or rename).

Interview questions

Q1. How does Spring Kafka deliver messages — exactly once? No — by default it is at-least-once. Offsets are committed after the listener returns, so a failure causes redelivery. So you make consumers idempotent. Kafka transactions give exactly-once only for Kafka-to-Kafka processing.

Q2. How do you make a consumer idempotent? Store the processed event ID, with a unique constraint, in the same DB transaction as the business effect. Or make the effect itself idempotent, for example an upsert by business key.

Q3. What is a dead-letter topic and when do you send to it? It is a separate topic for records that failed after all retries, or that can never succeed (validation or deserialisation errors). Moving them out stops them from blocking the partition. The DLT is monitored; records are fixed and replayed.

Q4. How do you preserve ordering per account? Use the account ID as the record key. All of that account's events then go to one partition and are processed by one consumer thread, in order.

8.6 Caching with Spring Cache and Redis

Why?

In simple words: A cache keeps a copy of often-read data in fast memory. Next time, you read the copy instead of asking the database again.

Some data is read far more often than it changes: scheme definitions, SKU catalogues, tenant settings, computed balances.

Reading it from the database every time wastes DB capacity and adds latency. A cache serves repeated reads from memory:

  • a local in-process cache answers in microseconds;
  • Redis answers in about a millisecond.

Think of a shopkeeper who keeps the 20 most-sold items on the counter. He only goes to the godown for the rest.

What is happening internally?

  • @EnableCaching makes Spring wrap beans that use caching annotations in a proxy (6.7). A proxy is a wrapper object that runs extra logic before and after your method.
  • @Cacheable works like this: 1. Build the key. By default it comes from the method arguments. You can customise it with SpEL (Spring's expression language). 2. Look up the key in the CacheManager. 3. Hit (found): return the cached value. Your method is not called. 4. Miss (not found): call your method and store the result.
  • @CacheEvict removes entries. @CachePut always calls the method and updates the cache.
  • The CacheManager implementation decides where data is stored:
  • Caffeine — in-process, one copy per instance, nanosecond access, bounded by size and TTL (time to live).
  • Redis — shared by all instances, one network hop away, values are serialised, TTL per cache.
  • sync = true: if many requests miss the same key at once on one instance, only one loads it; the others wait. This is local protection against a stampede (many requests hitting the DB together).

How does it work?

The pattern is called cache-aside:

  1. On a read, look in the cache first. On a miss, load from the DB and store it.
  2. On a write, update the DB, then evict (delete) the key.

Why delete instead of writing the new value into the cache? Because writing can race with a concurrent reader. That reader may put the old, stale value back in after your update. Deleting forces the next read to load fresh data.

Example

@Configuration
@EnableCaching
class CacheConfig {
    @Bean
    RedisCacheManager cacheManager(RedisConnectionFactory cf) {
        var defaults = RedisCacheConfiguration.defaultCacheConfig()
                .entryTtl(Duration.ofMinutes(10))
                .serializeValuesWith(RedisSerializationContext.SerializationPair
                        .fromSerializer(new GenericJackson2JsonRedisSerializer()));
        return RedisCacheManager.builder(cf)
                .cacheDefaults(defaults)
                .withCacheConfiguration("balances", defaults.entryTtl(Duration.ofSeconds(60)))
                .build();
    }
}

@Service
class SchemeService {
    @Cacheable(cacheNames = "schemes", key = "#tenantId + ':' + #outletId", sync = true)
    public List<SchemeDto> eligible(String tenantId, String outletId) { return repo.findEligible(tenantId, outletId); }

    @CacheEvict(cacheNames = "schemes", allEntries = true)
    public void onSchemesChanged(String tenantId) { }
}

@Service
class BalanceService {
    @Cacheable(cacheNames = "balances", key = "#accountId")
    public long balance(String accountId) { return ledger.balance(accountId); }

    @CacheEvict(cacheNames = "balances", key = "#accountId")
    @Transactional
    public void redeem(String accountId, long pts) { /* ... */ }      // evict after the change
}

Redis is useful for much more than caching (11.5, 13.x):

  • atomic counters (INCR);
  • rate limiting (a token bucket written in Lua);
  • distributed locks (SET key value NX PX 30000, or Redisson);
  • leaderboards (sorted sets);
  • idempotency keys with a TTL;
  • pub/sub and streams.

When would I use it?

For read-heavy, change-light data, expensive computations and per-tenant configuration.

  • Caffeine — for small reference data where brief per-instance staleness is fine.
  • Redis — when instances must share results, or the data set is large.
  • Both together — a two-level cache: Caffeine first, then Redis, then the DB.

What can go wrong?

  • Stale data. Two common causes:
  • You evict before the transaction commits. Another request then caches the old value again.
  • You evict on only one instance, while others still hold local copies.

Fix: evict after commit (@TransactionalEventListener), and keep TTLs as a safety net. - Self-invocation. @Cacheable on a method called from the same class does not cache. The call skips the proxy. - Stampede. A hot key expires and thousands of requests hit the DB at once. See 11.5: single-flight, jitter, early refresh. - Unbounded caches. The default ConcurrentMapCacheManager has no limits, so memory keeps growing — a memory leak. Always set a size limit and a TTL. - Caching mutable objects locally. Callers change the shared cached object, and everyone sees the change. Cache immutable DTOs or records. - Serialisation changes. After a deploy, old Redis entries may no longer be readable. Version your cache keys, or clear the cache on deploy.

Interview questions

Q1. How does @Cacheable work? A proxy builds a key from the method arguments. On a hit, it returns the cached value without calling the method. On a miss, it calls the method and stores the result.

Q2. Why evict on write instead of updating the cache? Updating can race with a concurrent read that reloads old data and writes it to the cache last, leaving stale data. Deleting forces the next read to load fresh data.

Q3. Local cache vs Redis? A local cache (Caffeine) is fastest, but each instance has its own copy and they can drift apart. Redis is shared and consistent across instances, but costs a network hop and serialisation.

8.7 Resilience: timeouts, retries, circuit breakers and bulkheads (Resilience4j)

Why?

In simple words: Other services will sometimes be slow or down. These patterns make sure one sick dependency doesn't drag your whole service down with it — you stop waiting, stop calling it for a while, and show a sensible fallback.

In a distributed system, dependencies will be slow or down. Without protection, this happens:

  1. One partner API becomes slow.
  2. Your threads wait on it, and your thread pool fills up.
  3. Your service stops responding to anyone.
  4. Your callers' thread pools fill up too.
  5. The outage cascades across the whole platform.

Resilience patterns contain the failure:

  • fail fast instead of waiting;
  • retry only what is safe to retry;
  • isolate what is slow;
  • degrade gracefully (give a reduced but useful answer).

Think of the electrical circuit breaker (MCB) in your house. When there is a short circuit, it trips and cuts power to that line, so the whole house doesn't catch fire. After the fault is fixed, you switch it back on.

What is happening internally?

Resilience4j wraps (decorates) your calls. You use it with annotations and Spring AOP, or in functional style.

  • TimeLimiter / client timeouts — limit how long you wait. Always set this first.
  • Retry — calls again on the transient exceptions you list. It waits longer each time (exponential backoff), plus some randomness (jitter) so clients don't retry together.
  • CircuitBreaker — keeps a sliding window of recent results (by call count or by time).
  • If the failure rate or slow-call rate goes above a threshold, the breaker opens.
  • While open, calls fail at once with CallNotPermittedException. The dependency is not touched.
  • After a wait, it becomes half-open and lets a few trial calls through.
  • If they succeed, it closes. If they fail, it opens again.
  • Bulkhead — caps how many calls can run at once (with a semaphore), or gives the dependency its own thread pool. So one dependency cannot use up all your threads. (The name comes from the walls inside a ship that stop one leak from sinking the whole ship.)
  • RateLimiter — caps the number of calls per time unit, to respect a partner's quota.
CLOSED ──(failure rate ≥ 50% over last 50 calls)──► OPEN ──(after 30 s)──► HALF_OPEN
   ▲                                                  ▲                          │
   └──────────────(trial calls succeed)───────────────┴──(trial calls fail)──────┘

Order of decorators with annotations, outermost first: Retry → CircuitBreaker → RateLimiter → TimeLimiter → Bulkhead → your call.

Because Retry is outside the CircuitBreaker:

  • every retry attempt is recorded by the breaker; and
  • once the breaker opens, the retries fail fast too, so they stop quickly.

How does it work?

With this config, the breaker looks at the last 50 calls (and needs at least 20 before it decides). It opens if 50% fail, or if 60% take longer than 2 s. It stays open for 30 s, then allows 5 trial calls. Retry tries up to 3 times, starting at 200 ms and doubling, only for I/O and timeout errors. The bulkhead allows 20 calls at once and waits at most 50 ms for a free slot.

resilience4j:
  circuitbreaker.instances.voucherPartner:
    sliding-window-type: COUNT_BASED
    sliding-window-size: 50
    minimum-number-of-calls: 20
    failure-rate-threshold: 50
    slow-call-duration-threshold: 2s
    slow-call-rate-threshold: 60
    wait-duration-in-open-state: 30s
    permitted-number-of-calls-in-half-open-state: 5
  retry.instances.voucherPartner:
    max-attempts: 3
    wait-duration: 200ms
    enable-exponential-backoff: true
    exponential-backoff-multiplier: 2
    retry-exceptions: [java.io.IOException, java.net.SocketTimeoutException]
    ignore-exceptions: [com.fa.voucher.InvalidVoucherRequestException]
  bulkhead.instances.voucherPartner:
    max-concurrent-calls: 20
    max-wait-duration: 50ms

Example

@Service
class VoucherClient {
    private final RestClient client;
    VoucherClient(RestClient voucherClient) { this.client = voucherClient; }

    @Retry(name = "voucherPartner")
    @CircuitBreaker(name = "voucherPartner", fallbackMethod = "queueForLater")
    @Bulkhead(name = "voucherPartner")
    public VoucherResult issue(IssueVoucher cmd) {
        return client.post().uri("/v1/vouchers")
                .header("Idempotency-Key", cmd.redemptionId())          // makes the retried POST safe
                .body(cmd).retrieve().body(VoucherResult.class);
    }

    VoucherResult queueForLater(IssueVoucher cmd, Throwable t) {          // graceful degradation
        pendingVouchers.enqueue(cmd);                                     // a job retries later; user sees "processing"
        return VoucherResult.pending(cmd.redemptionId());
    }
}

Two points to notice:

  • The Idempotency-Key header makes the retried POST safe. The partner sees the same key and does not issue a second voucher.
  • queueForLater is the fallback. When the breaker is open, the request goes into a queue, a background job retries it later, and the user sees "processing". This is graceful degradation.

When would I use it?

Around every remote dependency: partner APIs, other microservices, even the database for non-critical reads.

Combine it with:

  • client timeouts (7.6);
  • idempotency keys on any write that may be retried;
  • fallbacks that keep core flows working — cached prices, "processing" states, hiding optional widgets.

What can go wrong?

  • Retrying non-idempotent operations creates duplicates — double vouchers, double payments.
  • Retry storms. If every layer retries 3 times, three layers multiply the load 27 times (3 × 3 × 3) on a dependency that is already struggling. Retry at one layer only, with backoff, jitter and a retry budget (a cap on total retries).
  • No timeout. Calls just hang, so the circuit breaker never sees a failure.
  • Fallbacks that hide real outages and raise no alert.
  • Breaker windows that are too small, so the breaker keeps flipping open and closed (flapping). Or thresholds so high that it never opens.
  • Self-invocation again: the annotations only work when the call goes through the proxy.

Interview questions

Q1. Explain the circuit breaker states. Closed: calls flow normally and results are recorded. It moves to Open when the failure or slow-call rate crosses a threshold; now calls fail fast. After a wait, it moves to Half-open and allows a few trial calls. If they succeed, it goes back to Closed; if they fail, it goes back to Open.

Q2. Which calls should you retry? Only idempotent operations that fail with transient errors — timeouts, 503s, connection resets. Use exponential backoff with jitter, a limited number of attempts, and ideally retry at one layer only.

Q3. What is a bulkhead? It isolates resources per dependency, using a semaphore or a thread-pool limit. So one slow dependency cannot use up all your threads.

Q4. How do these patterns prevent cascading failures? Timeouts limit how long you wait. Circuit breakers stop calling a failing dependency. Bulkheads limit how many resources one dependency can use. Fallbacks keep the caller responsive.

8.8 Async execution and scheduled jobs

Why?

In simple words: @Async runs a task in the background so the user doesn't wait for it. @Scheduled runs a task at fixed times. The big catch: with many pods, every pod runs the scheduled job unless you add a lock.

Some work should not make the request wait: sending an SMS after a redemption, generating a report, warming a cache.

Other work runs on a timetable: daily point expiry at 02:00, hourly reconciliation, retrying pending vouchers.

Spring gives you @Async and @Scheduled for these. Both have pitfalls that matter when you run many instances.

What is happening internally?

  • @Async. Add @EnableAsync. Then a proxy intercepts every @Async method. It hands the call to a TaskExecutor (a thread pool) and returns at once. The method returns void or a CompletableFuture. If you configure nothing, Boot gives you a ThreadPoolTaskExecutor — or virtual threads when spring.threads.virtual.enabled=true.
  • @Scheduled. Add @EnableScheduling. A TaskScheduler then triggers @Scheduled methods by fixedRate, fixedDelay or cron. Note: by default it has only one thread!
  • Many instances. If you run several pods, every pod runs every @Scheduled method. So a daily job runs N times unless you coordinate.

Think of a society with three watchmen and one rule: "lock the main gate at 10 pm". If nobody coordinates, all three walk to the gate. ShedLock is the register at the gate — the first one to sign does the job.

How does it work?

This config sets up a dedicated pool for notifications and a DB-based lock for jobs:

  • 4 core threads, up to 8, and a queue of 500 tasks.
  • When the queue is full, CallerRunsPolicy makes the caller run the task itself. This slows the caller down instead of dropping work.
  • A TaskDecorator copies MDC and tenant context into the worker thread (4.15).
  • ShedLock stores its locks in a shedlock table in your DB, so only one instance runs each job.
@Configuration
@EnableAsync
@EnableScheduling
@EnableSchedulerLock(defaultLockAtMostFor = "PT30M")         // ShedLock: one instance per job run
class AsyncConfig {
    @Bean("notificationExecutor")
    ThreadPoolTaskExecutor notificationExecutor() {
        var ex = new ThreadPoolTaskExecutor();
        ex.setCorePoolSize(4); ex.setMaxPoolSize(8); ex.setQueueCapacity(500);
        ex.setThreadNamePrefix("notify-");
        ex.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        ex.setTaskDecorator(new MdcTaskDecorator());           // your TaskDecorator copying MDC/tenant context (4.15)
        ex.initialize();
        return ex;
    }
    @Bean
    LockProvider lockProvider(DataSource ds) { return new JdbcTemplateLockProvider(ds); }   // shedlock table in the DB
}

Example

@Service
class Notifier {
    @Async("notificationExecutor")
    public CompletableFuture<Void> sms(String phone, String text) {
        gateway.send(phone, text);
        return CompletableFuture.completedFuture(null);
    }
}

@Component
class ExpiryJob {
    @Scheduled(cron = "0 0 2 * * *", zone = "Asia/Kolkata")          // 02:00 IST daily
    @SchedulerLock(name = "pointsExpiry", lockAtMostFor = "PT2H", lockAtLeastFor = "PT5M")
    public void expirePoints() {
        for (String tenant : tenants.active()) {
            expiryService.expireDueLots(tenant);                      // chunked, resumable, idempotent per lot
        }
    }
}

The expiry job runs at 02:00 IST every day. ShedLock holds the lock for at least 5 minutes and at most 2 hours. The work is chunked, resumable and idempotent per lot, so a crash in the middle is safe to restart.

When would I use it?

  • @Async — for fire-and-forget side effects where losing one on a crash is acceptable (or a later job will fix it).
  • Durable queue (Kafka/outbox) — for work that must not be lost.
  • @Scheduled + ShedLock — for periodic maintenance.
  • Kubernetes CronJobs or a workflow engine — for heavy or long batch jobs.

What can go wrong?

  • Self-invocation and private methods. Proxy rules again — these calls skip the proxy, so they run synchronously.
  • An exception in a void @Async method disappears silently, unless you configure an AsyncUncaughtExceptionHandler.
  • ThreadLocal context (tenant, security, MDC) is lost in async threads. Use a TaskDecorator to copy it.
  • The default single scheduler thread. One slow job delays all the others. Configure a pool (spring.task.scheduling.pool.size).
  • Jobs running on every pod — duplicate expiry or duplicate payouts — when there is no ShedLock or leader election. Also, jobs that are not idempotent and cannot resume after a crash.
  • Time zones and DST (daylight-saving time changes) in cron expressions. Always set the zone.

Interview questions

Q1. How does @Async work and what are its limits? A proxy hands the call to an executor and returns immediately. Limits: it does not work on self-invocation or private methods; it loses ThreadLocal context unless you propagate it; and the work is lost if the app crashes.

Q2. How do you ensure a scheduled job runs once across multiple instances? Use a distributed lock (ShedLock on a DB or Redis), or leader election. Or run the job outside the app — a Kubernetes CronJob, or Quartz in clustered mode.

8.9 Observability: health, metrics, logs and traces

Why?

In simple words: In production you can't debug line by line. So the service must report on itself: numbers that say something is wrong, traces that show where, and logs that explain why.

In production you cannot attach a debugger. You find problems only through what the system emits:

  • Metrics tell you that something is wrong — for example, the error rate went up.
  • Traces tell you where — which hop in the request is slow.
  • Logs tell you why — the exception and its context.

Health endpoints let Kubernetes send traffic only to healthy instances.

Think of a car dashboard. The warning light (metric) says something is wrong. The mechanic's diagnostic scan (trace) finds which part. The service record (logs) explains what happened.

What is happening internally?

  • Actuator adds management endpoints:
  • /actuator/health, with liveness and readiness groups for Kubernetes probes;
  • /info, /metrics, /prometheus;
  • /loggers — change log levels at runtime;
  • /threaddump, /heapdump, /conditions, /startup.
  • Micrometer is the metrics facade — like SLF4J, but for metrics. You write counters, gauges, timers and distribution summaries, each with tags (labels). It exports them to Prometheus, Azure Monitor or Datadog. Boot measures many things for you automatically: HTTP server and client requests, JVM memory/GC/threads, Hikari connection pools, Kafka clients and caches.
  • Micrometer Tracing + OpenTelemetry work like this: 1. Each request gets a trace ID. 2. A span (one timed step) is created for each HTTP call, DB query and Kafka message. 3. The trace context travels to the next service in W3C traceparent HTTP headers and in Kafka headers. 4. Spans are exported to Jaeger, Tempo, Zipkin or Application Insights.
  • Structured logging means logs written as JSON. It is built into Boot 3.4+. Put the trace ID and tenant ID in every line using MDC (a per-thread map of log fields). Then logs are searchable and you can join them with traces.

How does it work?

What to measure:

  • RED for each endpoint and dependency: Rate (requests per second), Errors, Duration (p50/p95/p99). p95 means 95% of requests were faster than this.
  • USE for each resource: Utilisation, Saturation (queue lengths, waits for a pool), Errors. Apply it to thread pools, connection pools, Kafka consumer lag and GC.
  • Business KPIs: redemptions per minute, accrual lag, failed vouchers.

Alert on symptoms measured against SLOs, not on every CPU blip. An SLO (service level objective) is a target such as "99.9% of redemptions succeed in < 500 ms". The error budget is the 0.1% you are allowed to fail. Alert when you are burning that budget too fast (the burn rate).

Example

@Component
class RedemptionMetrics {
    private final MeterRegistry registry;
    private final Timer latency;
    RedemptionMetrics(MeterRegistry registry) {
        this.registry = registry;
        this.latency = Timer.builder("loyalty.redemption.latency")
                .publishPercentileHistogram()                       // enables p95/p99 in Prometheus
                .register(registry);
    }
    <T> T timed(Supplier<T> op) { return latency.record(op); }
    void outcome(String tenant, String result) {
        registry.counter("loyalty.redemptions", "result", result).increment();   // low-cardinality tags only
    }
}

management:
  endpoints.web.exposure.include: health,info,prometheus
  endpoint.health.probes.enabled: true          # /actuator/health/liveness and /readiness
  tracing.sampling.probability: 0.1             # sample 10% of traces in prod
logging.structured.format.console: ecs          # Boot 3.4+: JSON logs

This config exposes only health, info and prometheus. It turns on the liveness and readiness probes, samples 10% of traces in production, and writes JSON logs.

When would I use it?

From day one, in every service:

  • a dashboard per service (RED + USE);
  • alerts on SLO burn;
  • traces to investigate slow requests;
  • logs linked to traces by trace ID.

In interviews, the question "how would you know it's working in production?" is answered with exactly these.

What can go wrong?

  • High-cardinality tags. Cardinality means how many different values a tag can have. User IDs, order IDs or raw URLs as tags create millions of series. This blows up the metrics backend's memory and cost. Use tags with a small, fixed set of values: status, endpoint template, tenant tier.
  • Exposing /heapdump or /env to the public. They can leak data. Keep management endpoints on an internal port or network.
  • Liveness probes that check the database. If the DB has a short blip, Kubernetes restarts every pod. Liveness should reflect only the app process itself. Put dependency checks in readiness — and carefully.
  • Logging PII or secrets. Logging at DEBUG in production. Logging the same exception in many layers.

Interview questions

Q1. Metrics vs logs vs traces? Metrics are aggregated numbers, used to detect problems and alert. Traces follow one request across services to find where the latency or error is. Logs are detailed events that explain what happened.

Q2. Liveness vs readiness probes? Liveness asks: is the process healthy, or should Kubernetes restart it? Readiness asks: can it serve traffic right now — is it warmed up and are its dependencies reachable? A failing readiness probe takes the pod out of load balancing without restarting it.

Q3. What are RED and USE? RED (rate, errors, duration) is for request-driven services. USE (utilisation, saturation, errors) is for resources such as pools, queues and CPU.

8.10 Microservices patterns in the Spring ecosystem

Why?

In simple words: Breaking an app into many small services gives teams freedom, but brings new problems — network calls fail, data is spread out. Each common problem has a well-known pattern and a well-known tool.

Splitting a system into services gives you:

  • independent deployment;
  • independent scaling;
  • clear team ownership.

The price is network calls, partial failures, data spread across services, and more operational work.

A set of well-known patterns solves the recurring problems. Interviewers expect you to:

  1. name the patterns;
  2. know the Spring or Kubernetes tool for each;
  3. say when not to use microservices.

What is happening internally?

Concern Pattern Typical implementation
One entry point for all calls: routing, auth, rate limits API Gateway / BFF (Backend for Frontend) Spring Cloud Gateway, Azure API Management, Kong, Envoy
Finding where service instances are running Service discovery Kubernetes Services + DNS; Eureka outside Kubernetes
Keeping configuration in one central place Externalised config ConfigMaps/Secrets, Azure App Configuration, Spring Cloud Config
One failure spreading to others (cascading failures) Timeouts, retries, circuit breakers, bulkheads Resilience4j (8.7)
Who owns which data Database per service Each service owns its schema; no shared tables
Keeping data consistent across services Saga (choreography/orchestration) + outbox Kafka, Temporal/Camunda, outbox relay or Debezium CDC (11.15)
Queries that need data from many services API composition, CQRS read models An aggregator service; a read model fed by events
Moving away from a monolith Strangler fig Gateway sends new paths to new services, step by step
Seeing what happens across services Correlation IDs, distributed tracing, central logs Micrometer Tracing + OpenTelemetry (8.9)
Deployment Containers, orchestration, progressive delivery Docker, Kubernetes, Helm/Kustomize, Argo/Flagger canaries
Security between services mTLS, OAuth2 client credentials Istio/Linkerd service mesh, Spring Security (8.2)

A few terms from the table:

  • Saga — a long business process split into local steps. Each step has a compensation (an undo step) if a later step fails. In choreography, services react to each other's events. In orchestration, one coordinator tells each service what to do.
  • CQRS — keep separate models for writing and for reading. The read model is built from events.
  • Strangler fig — named after a plant that slowly grows around a tree. You move features out of the monolith one route at a time.
  • Canary — send a small share of traffic to the new version first.

How does it work?

Draw service boundaries around business capabilities, also called bounded contexts: Ordering, Loyalty, Incentives, Notifications, Catalogue.

  • Each service owns its own data.
  • It publishes events when its data changes.
  • Other services keep a local copy of what they need, instead of calling synchronously for everything. The copy may be a little behind for a short time. This is called eventual consistency.

Think of the departments in a big hospital. Billing, pharmacy and lab each keep their own records. When the lab finishes a test, it sends a slip to billing. Billing does not walk into the lab and read its register.

Example

Mobile app ─► API Gateway (JWT validation, rate limits, routing)
                ├─► Order service ──(OrderCompleted via outbox→Kafka)──► Loyalty service ──► Notification service
                ├─► Loyalty service (owns ledger DB) ──► Voucher partner (Resilience4j, idempotency key)
                └─► Catalogue service (read-heavy, cached, CDN for images)
Each service: own DB, own deploy pipeline, health probes, metrics, traces with a shared trace ID

When would I use it?

When teams and domains are large enough that independent deployment and scaling pay for the extra complexity.

For a small team or a new product, a modular monolith is often the better senior answer. That means one deployable app with clear internal modules. Extract a module into a service only when its scaling or ownership needs become different from the rest.

What can go wrong?

  • Distributed monolith. Services must be deployed together, and they call each other synchronously in long chains. Latency adds up. Availability multiplies down: 5 services at 99.9% each, called in series, give about 99.5% (0.999⁵).
  • Shared database between services. This is hidden coupling. One team's schema change breaks another team's service.
  • Chatty APIs (N calls to render one page), missing timeouts, no idempotency, and data that drifts apart with no reconciliation job.
  • Operational load without platform support — no proper CI/CD, observability or on-call setup for each service.

Interview questions

Q1. Monolith vs microservices — how do you decide? Weigh the benefits — team size, clear domain boundaries, need for independent scaling and deployment — against the costs: operational complexity, network failure modes and data consistency. Start with a modular monolith, and split along bounded contexts when it is justified.

Q2. How do services stay consistent without distributed transactions? Use local transactions plus events (the outbox pattern), sagas with compensation steps, idempotent consumers and reconciliation jobs. You accept eventual consistency.

Q3. What does an API gateway do? Routing, authentication and token validation, rate limiting, TLS termination, request shaping, CORS, observability and canary routing. It should contain no business logic.

Loyalty Ledger Service — spec

Purpose: a multi-tenant points ledger. It supports:

  • accrual (from order events);
  • redemption (through the API);
  • reversal;
  • expiry;
  • balance queries.

It must stay correct under retries and concurrency — no double postings, no negative balances.

Stack: Java 21, Spring Boot 3.x, PostgreSQL, Spring Data JPA, Flyway, Kafka, Redis, Resilience4j, Spring Security (JWT resource server), Testcontainers, Docker Compose, GitHub Actions.

Schema (Flyway V1)

Key points of the schema:

  • CHECK (balance >= 0) — the database itself refuses a negative balance.
  • UNIQUE (tenant_id, idempotency_key) — the same request can never create two ledger entries.
  • The index on (account_id, created_at DESC, id DESC) serves the keyset-paginated ledger query.
  • The partial index on outbox covers only unpublished rows, so the relay's poll stays fast.
CREATE TABLE account (
  id            VARCHAR(40) PRIMARY KEY,
  tenant_id     VARCHAR(40) NOT NULL,
  outlet_id     VARCHAR(40) NOT NULL,
  balance       BIGINT NOT NULL DEFAULT 0 CHECK (balance >= 0),
  version       BIGINT NOT NULL DEFAULT 0,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (tenant_id, outlet_id)
);
CREATE TABLE ledger_entry (
  id              BIGSERIAL PRIMARY KEY,
  tenant_id       VARCHAR(40) NOT NULL,
  account_id      VARCHAR(40) NOT NULL REFERENCES account(id),
  type            VARCHAR(20) NOT NULL,          -- ACCRUAL, REDEMPTION, REVERSAL, EXPIRY
  points          BIGINT NOT NULL,               -- signed
  idempotency_key VARCHAR(80) NOT NULL,
  ref_entry_id    BIGINT,                         -- for reversals
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (tenant_id, idempotency_key)
);
CREATE INDEX ix_ledger_account_created ON ledger_entry (account_id, created_at DESC, id DESC);
CREATE TABLE outbox (
  id           UUID PRIMARY KEY,
  aggregate_id VARCHAR(40) NOT NULL,
  topic        VARCHAR(80) NOT NULL,
  payload      JSONB NOT NULL,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  published_at TIMESTAMPTZ
);
CREATE INDEX ix_outbox_unpublished ON outbox (created_at) WHERE published_at IS NULL;
CREATE TABLE processed_event (event_id VARCHAR(80) PRIMARY KEY, processed_at TIMESTAMPTZ NOT NULL);
