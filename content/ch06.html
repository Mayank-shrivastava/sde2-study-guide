6.1 What Spring and Spring Boot solve

Why?

In simple words: Spring builds all your objects and connects them to each other, so you don't write new everywhere. Spring Boot does the remaining setup for you, so a working web service needs almost no configuration.

A real backend has hundreds of objects that depend on each other:

  • Controllers need services.
  • Services need repositories, clients, caches and config.
  • Repositories need a DataSource (the object that gives out database connections).

You could create and connect all of them by hand with new. But that causes three problems:

  1. The code becomes rigid. Each class hard-codes which implementation it uses.
  2. The code is hard to test. You can't swap in a fake object for a test.
  3. The same plumbing repeats everywhere. Transactions, security checks and logging get copy-pasted into many methods.

Spring fixes this. It creates these objects and connects them for you. It can also add shared behaviour (like transactions) around them. Behaviour that many classes need is called cross-cutting behaviour.

Spring Boot removes the setup that is still left. It gives you:

  • sensible defaults,
  • infrastructure that configures itself automatically,
  • a web server built into your app,
  • and a single JAR file that you can run directly.

What is happening internally?

  • Spring Framework = an IoC container (ApplicationContext) + modules built on top of it. The container is the object that creates and holds all your objects. The modules include Web MVC, Data/JDBC/ORM integration, transactions, AOP, events, Security (a separate project), and more.
  • Spring Boot adds these things on top:
  • Starters: ready-made bundles of dependencies. For example, spring-boot-starter-web brings Spring MVC, Jackson (for JSON), embedded Tomcat and validation hooks — all in one line.
  • Auto-configuration: configuration classes guarded by @Conditional checks. They create beans (DataSource, ObjectMapper, transaction manager…) only when two things are true: the needed classes and properties are present, and you haven't defined your own bean (6.9). A bean is simply an object that Spring creates and manages.
  • Externalised configuration: settings live outside the code — in application.yml, profiles and environment variables (6.8).
  • An embedded server: Tomcat runs inside your app. So you don't deploy your app onto a separate server; the app carries its own server.
  • Executable fat JAR: one JAR that holds your classes, all dependency JARs nested inside, and a special launcher class loader that can read the nested JARs.
  • Actuator: ready-made endpoints for health, metrics and info (8.9).

Here is how the ideas map from ASP.NET Core, which you already know:

How does it work?

When you run the JAR, these steps happen in order:

java -jar loyalty.jar
 → JarLauncher sets up a class loader over BOOT-INF/classes + BOOT-INF/lib/*.jar
 → your main(): SpringApplication.run(App.class)
 → creates the ApplicationContext, scans components, applies auto-configuration
 → instantiates and wires beans, wraps some in proxies
 → starts embedded Tomcat on port 8080 → ready

In plain words:

  1. JarLauncher sets up a class loader. It can read your classes and every library JAR nested inside the fat JAR.
  2. Your main() method calls SpringApplication.run.
  3. Spring creates the ApplicationContext (the container).
  4. It scans your packages for components and applies auto-configuration.
  5. It creates all the beans, connects them, and wraps some of them in proxies (wrapper objects — see 6.7).
  6. It starts the embedded Tomcat server on port 8080. The app is now ready.

Example

@SpringBootApplication              // = @Configuration + @EnableAutoConfiguration + @ComponentScan
public class LoyaltyApplication {
    public static void main(String[] args) { SpringApplication.run(LoyaltyApplication.class, args); }
}

@RestController
@RequestMapping("/api/v1/accounts")
class AccountController {
    private final AccountService service;
    AccountController(AccountService service) { this.service = service; }   // injected by Spring

    @GetMapping("/{id}/balance")
    BalanceDto balance(@PathVariable String id) { return service.balance(id); }
}

When would I use it?

For any Java backend service. It is the default stack at most Indian product companies (Flipkart, PhonePe, Swiggy, Walmart Global Tech). It is also widely used at FAANG for internal services.

What can go wrong?

  • "Magic" you don't understand. A bean you never defined behaves in an unexpected way. Learn to read the auto-configuration report, which tells you what Boot set up and why (6.9).
  • Pulling in starters you don't need. This gives you a larger JAR, slower startup and surprise auto-configuration. For example, adding spring-boot-starter-data-jpa makes the app fail to start if there is no DataSource configured.
  • Overriding managed dependency versions by hand. If you change versions that the BOM picked, you can break compatibility between libraries.

Interview questions

Q1. Spring vs Spring Boot? Spring is the IoC container plus its family of modules. Boot is an opinionated layer on top of it — it makes default choices for you. It adds starters, auto-configuration, externalised config, an embedded server, executable JARs and Actuator, so an app needs almost no setup.

Q2. What does @SpringBootApplication do? It combines three annotations: @Configuration, @EnableAutoConfiguration and @ComponentScan. The component scan starts from the annotated class's package and goes downward into its sub-packages.

Q3. What is a starter? It is a dependency bundle that brings everything needed for one capability (web, JPA, security), with versions that work together. Having it on the classpath also triggers the matching auto-configuration.

6.2 Inversion of Control and Dependency Injection

Why?

In simple words: A class should not build the things it needs. It should just ask for them, and someone else (the Spring container) hands them over. This makes the class easy to test and easy to change.

Suppose RedemptionService creates its own dependencies:

  • new PostgresLedgerRepository()
  • new TwilioSmsClient()

Now it is welded to those exact implementations. Two problems follow:

  1. You can't unit test it without a real database and a real SMS account.
  2. Switching to another SMS vendor means editing your business code.

Inversion of Control (IoC) flips this. The class only declares what it needs. An outside container creates those dependencies and hands them in. This handing-in is called Dependency Injection (DI).

Think of a restaurant kitchen. The chef does not go to the market for vegetables. He writes what he needs on a list, and the supplier delivers it. If the supplier changes, the chef's recipes don't change.

What is happening internally?

The ApplicationContext works in two phases.

  1. Phase 1 — Bean definitions (the recipes). - Spring collects a recipe for each bean. A recipe says: which class, which scope, which constructor arguments, which dependencies, and which init/destroy methods. - Recipes come from component scanning, @Bean methods and auto-configuration. - Each recipe is stored as a BeanDefinition object in a registry. - No real objects exist yet.
  2. Phase 2 — Instantiation (cooking the recipes). For each singleton that is not marked lazy, Spring:
  3. works out the dependency graph (who needs whom),
  4. creates the dependencies first,
  5. calls the constructor with them,
  6. injects fields and setters,
  7. runs lifecycle callbacks,
  8. applies post-processors (these may wrap the bean in a proxy),
  9. stores the result in the singleton cache (a ConcurrentHashMap<String, Object>).

Spring finds a dependency by type first. If several beans match that type, it narrows the choice by qualifier or by name (6.4).

Bean definitions:  accountController → needs AccountService
                   accountService    → needs AccountRepository, Clock
                   accountRepository (Spring Data proxy) → needs EntityManager
Creation order:    EntityManager → AccountRepository → Clock → AccountService → AccountController

In the diagram, nothing can be created before the things it needs. So the EntityManager comes first and the controller comes last.

How does it work?

There are three ways to inject a dependency:

@Service
public class RedemptionService {
    private final LedgerRepository ledger;           // 1. Constructor injection — use this
    private final NotificationSender notifier;

    public RedemptionService(LedgerRepository ledger, NotificationSender notifier) {   // single constructor: @Autowired optional
        this.ledger = ledger;
        this.notifier = notifier;
    }
}

@Service
class LegacyService {
    @Autowired private AuditClient audit;            // 2. Field injection — avoid (hidden deps, no final, needs reflection in tests)
    private Notifier notifier;
    @Autowired void setNotifier(Notifier n) { this.notifier = n; }   // 3. Setter — only for optional deps
}
  1. Constructor injection — use this by default.
  2. Field injection — avoid it. The dependencies are hidden, the field can't be final, and tests need reflection to set it.
  3. Setter injection — use it only for optional dependencies.

Why constructor injection wins:

  • Dependencies are explicit. You can see them all in the constructor signature.
  • Fields are final. So they are immutable (can't change), and other threads always see them correctly set. This is called safe publication.
  • The object is never half-built. It can't exist without its dependencies.
  • Unit tests are simple. You just call new RedemptionService(fakeLedger, fakeNotifier).
  • It warns you about bad design. If the constructor has too many parameters, the class is clearly doing too much.

Example

// Unit test with no Spring at all — the payoff of DI
class RedemptionServiceTest {
    @Test void notifiesAfterRedemption() {
        var ledger = new InMemoryLedgerRepository();
        var notifier = new RecordingNotifier();
        var service = new RedemptionService(ledger, notifier);
        service.redeem("acc1", 100);
        assertThat(notifier.sent()).hasSize(1);
    }
}

This test needs no Spring at all. You pass in fake objects by hand. This is the real payoff of DI.

When would I use it?

For every service, repository, client and component.

Program to interfaces (also called ports) for anything you might swap or fake in tests:

  • external clients,
  • notification channels,
  • clocks,
  • ID generators.

What can go wrong?

  • Circular dependencies. A needs B, and B needs A.
  • With constructor injection, Spring can't create either one first. So startup fails with BeanCurrentlyInCreationException.
  • Since Boot 2.6, circular references are blocked by default, even with field injection.
  • The fix is to change the design. Extract the shared logic into a third bean, or use events.
  • Putting @Lazy on one parameter is a last resort. It injects a proxy (a stand-in object) instead of the real bean.
  • Calling new yourself on a Spring-managed class. The object you get has no injection, no proxies and no @Transactional. Spring never touched it.
  • Static access to beans. For example, a static holder that keeps the ApplicationContext. This hides the dependencies again, which is exactly what DI was meant to fix.

Interview questions

Q1. What are IoC and DI? IoC means the container, not your code, controls creating objects and connecting them. DI means dependencies are given to the object through the constructor, a setter or a field, instead of the object creating them itself. This gives loose coupling, easy testing and one central place for configuration.

Q2. Why prefer constructor injection? Dependencies are explicit and immutable, objects are never partly initialised, unit tests are easy without Spring, and circular dependencies fail early at startup.

Q3. How does Spring resolve which bean to inject? First by type. If several beans match, it uses @Primary, then @Qualifier, then the parameter name matching a bean name. If none of these decides it, startup fails with NoUniqueBeanDefinitionException.

Q4. How do you fix a circular dependency? Refactor the design: move the shared responsibility into a new bean, or reverse one dependency using an interface or events. Only as a last resort, use @Lazy injection.

6.3 Defining beans: stereotypes, @Bean and @Configuration

Why?

In simple words: You must tell Spring which objects to create. For your own classes, put an annotation on the class. For classes you can't edit, write a small method that builds the object and mark it @Bean.

The container needs to know two things: which classes to manage, and how to build them.

  • Your own classes: an annotation on the class is enough.
  • Third-party classes you can't annotate (an ObjectMapper, an ExecutorService, an SDK client), or objects that need some building logic: you write a factory method — a method whose job is to create and return the object.

What is happening internally?

  • Component scanning walks through the packages under your @SpringBootApplication class.
  • It reads the class files with a library called ASM. So it does not need to load every class into memory.
  • For each class marked with @Component, or with an annotation built on @Component (a stereotype), it registers a bean definition.
Annotation Meaning
@Component A general managed component
@Service Business logic (just a label; no extra behaviour)
@Repository Data access; Spring also converts database exceptions into its own DataAccessException family
@Controller / @RestController Web handler; @RestController = @Controller + @ResponseBody
@Configuration A class that holds @Bean factory methods
  • @Configuration classes are wrapped in a CGLIB proxy. CGLIB is a library that creates a subclass of your class at runtime.
  • Because of this proxy, when one @Bean method calls another @Bean method in the same class, the call goes through the proxy.
  • The proxy returns the existing singleton instead of creating a new object.
  • "Lite mode": @Configuration(proxyBeanMethods = false). There is no proxy, so startup is a bit faster.
  • But now the methods are plain Java calls. Calling one @Bean method from another creates a new instance each time.
  • So in lite mode, take other beans as method parameters instead of calling their methods.

How does it work?

@Configuration
class InfraConfig {
    @Bean
    Clock clock() { return Clock.systemUTC(); }                       // third-party type → @Bean

    @Bean(destroyMethod = "shutdown")
    ExecutorService rewardExecutor() {
        return new ThreadPoolExecutor(4, 16, 60, TimeUnit.SECONDS, new ArrayBlockingQueue<>(500),
                Thread.ofPlatform().name("reward-", 0).factory(), new ThreadPoolExecutor.CallerRunsPolicy());
    }

    @Bean
    PartnerClient partnerClient(RestClient.Builder builder, PartnerProps props) {   // dependencies as parameters
        return new PartnerClient(builder.baseUrl(props.baseUrl()).build());
    }
}

Three patterns are shown here:

  1. Clock is a third-party type, so you create it with a @Bean method.
  2. The thread pool uses destroyMethod = "shutdown". So Spring calls shutdown() on it when the app stops.
  3. PartnerClient needs other beans. It receives them as method parameters, and Spring fills them in.

Example

@Configuration
class Demo {
    @Bean A a() { return new A(b()); }
    @Bean B b() { return new B(); }
}
// With full @Configuration (default): b() inside a() returns the SAME singleton B as the "b" bean.
// With proxyBeanMethods = false: b() creates a SECOND B — two instances, subtle bugs (two caches, two pools).

With the default full @Configuration, both places get the same B. In lite mode you silently get two B objects. That can mean two caches or two connection pools — bugs that are hard to spot.

When would I use it?

  • Stereotype annotations for your own classes.
  • @Bean for third-party objects, clients that need configuration, thread pools, and variants that depend on a condition or a profile.
  • Group your infrastructure beans into a few @Configuration classes, one per concern. For example: PersistenceConfig, KafkaConfig, SecurityConfig.

What can go wrong?

  • A class outside the scanned packages is silently ignored. If it sits above the main class's package, scanning never sees it. You get NoSuchBeanDefinitionException.
  • final @Configuration classes or final @Bean methods can't be proxied by CGLIB. CGLIB works by subclassing and overriding, and final blocks both.
  • Two beans of the same type defined in different places (yours plus an auto-configured one).
  • Usually yours wins, because the auto-configured one has @ConditionalOnMissingBean and steps back.
  • But if the two beans have the same name, it is a clash. Bean overriding is disabled by default, so startup fails.

Interview questions

Q1. @Component vs @Bean? @Component marks your own class so component scanning picks it up. @Bean is a factory method inside a @Configuration class; you use it for third-party types or when building the object needs custom logic.

Q2. @Component vs @Service vs @Repository? All three register beans. @Service is only a label that shows meaning. @Repository also adds persistence exception translation — it converts database exceptions into Spring's DataAccessException types.

Q3. Why are @Configuration classes proxied? So that when one @Bean method calls another, it gets back the container's singleton instead of creating a new instance.

6.4 Multiple implementations: @Primary, @Qualifier, and injecting collections

Why?

In simple words: When one interface has several implementations, you must tell Spring which one to use. You can mark a default, ask for a specific one by name, or take all of them and choose at runtime.

Real systems often have several implementations of one interface. For example:

  • payment gateways: Razorpay, UPI, card,
  • notification channels: SMS, WhatsApp, email,
  • reward rules.

You need one of three things:

  1. a default one,
  2. a specific one,
  3. all of them, so you can pick one at runtime. This is the Strategy pattern — choose the algorithm while the program runs.

What is happening internally?

Say a constructor parameter has type T. The container collects every bean that can be assigned to T. Then:

  1. If there is exactly one, it injects that one.
  2. If there are several, a bean marked @Primary wins.
  3. If there is no @Primary, a @Qualifier on the parameter filters the candidates.
  4. If there is no qualifier, Spring matches the parameter name to a bean name.
  5. If nothing decides it, startup fails with NoUniqueBeanDefinitionException.

Collections work differently:

  • For List<T>, Spring injects all candidates. They are ordered by @Order or the Ordered interface.
  • For Map<String, T>, Spring injects a map of bean name → bean.

Think of an ATM that accepts several bank cards. It has a default network, but it can also route to a specific bank when the card says so.

How does it work?

public interface PaymentGateway { Receipt pay(Money amount, String ref); String code(); }

@Component("razorpay") @Primary class RazorpayGateway implements PaymentGateway { /* ... */ }
@Component("upi")                 class UpiGateway implements PaymentGateway { /* ... */ }
@Component("card")                class CardGateway implements PaymentGateway { /* ... */ }

Each gateway is a bean with its own name. RazorpayGateway is marked @Primary, so it is the default.

Example

@Service
class CheckoutService {
    private final PaymentGateway defaultGateway;                    // the @Primary one
    private final Map<String, PaymentGateway> gateways;              // "razorpay" -> ..., "upi" -> ..., "card" -> ...

    CheckoutService(PaymentGateway defaultGateway, Map<String, PaymentGateway> gateways) {
        this.defaultGateway = defaultGateway;
        this.gateways = gateways;
    }

    Receipt pay(String method, Money amount, String ref) {
        PaymentGateway gw = Optional.ofNullable(gateways.get(method))
                .orElseThrow(() -> new IllegalArgumentException("unsupported method " + method));
        return gw.pay(amount, ref);                                   // Strategy chosen at runtime
    }
}

@Service
class Refunds {
    Refunds(@Qualifier("upi") PaymentGateway upi) { /* explicitly the UPI one */ }
}
  • CheckoutService gets the @Primary gateway as its default.
  • It also gets a map of all gateways, keyed by bean name. It picks one at runtime from the method the user chose.
  • Refunds asks for the UPI gateway by name with @Qualifier("upi").

Now, adding a new gateway is just one new @Component class. You don't edit any existing code. This is the open/closed principle (9.4) for free — open for extension, closed for modification.

When would I use it?

  • Strategy registries: payment methods, notification channels, incentive rule evaluators keyed by rule type.
  • Plugin-style extension points: new behaviour is added by dropping in a new bean.
  • Environment-specific defaults: @Primary on the real client, and a stub (fake) under a test profile.

What can go wrong?

  • Two @Primary beans of the same type. Spring can't choose, so you get an ambiguity error.
  • Qualifier strings scattered across the code. If someone renames a bean, these strings break silently. Prefer a custom qualifier annotation, or a map keyed by a method on the interface (like code()).
  • Relying on parameter-name matching. It breaks easily when someone renames a parameter during refactoring.

Interview questions

Q1. Two beans implement the same interface. How does Spring choose? First @Primary, then @Qualifier, then the parameter name. If none of these decides it, Spring throws NoUniqueBeanDefinitionException. If you want all of them, inject List<T> or Map<String, T>.

Q2. How do you implement the Strategy pattern with Spring? Make each strategy a bean that implements a common interface. Then inject Map<String, Strategy> or a List, and build a registry keyed by type to pick the right strategy at runtime.

6.5 Bean scopes

Why?

In simple words: Scope decides how many copies of a bean exist and how long each one lives. Most beans are one shared copy for the whole app; a few need a new copy per request or per use.

  • Most beans are stateless services — they hold no per-user data. So everyone can share one instance.
  • Some objects must exist once per request (for example, a request context).
  • Some must be brand new each time (stateful helpers that collect data).

Scope controls how many instances exist and how long they live.

What is happening internally?

Scope Instances Lifecycle managed by container
singleton (default) One per ApplicationContext, cached Full (created at startup, destroyed at shutdown)
prototype A new instance on every lookup or injection Creation only — no destroy callbacks
request One per HTTP request (stored in request attributes) Web only
session One per HTTP session Web only
application One per ServletContext Web only

A Spring singleton is one per container, not one per JVM. This is different from the classic GoF Singleton pattern (from the "Gang of Four" design patterns book).

A singleton is shared by every request thread at the same time. So it must be stateless or thread-safe.

Think of a railway enquiry counter with one clerk. Everyone talks to the same clerk. If he writes your coach number on a single shared slate, the next person can overwrite it before you read it back.

How does it work?

Suppose you inject a shorter-lived bean (request or prototype) into a singleton. The injection happens only once — when the singleton is created. After that, the singleton keeps the same object forever.

To get a fresh instance each time, you need a middle step:

  • ObjectProvider<T>: call getObject() whenever you need a new one.
  • @Lookup method injection: Spring overrides the method so that it fetches a fresh bean from the container.
  • A scoped proxy (@Scope(value = "request", proxyMode = ScopedProxyMode.TARGET_CLASS)): the singleton holds a proxy. On every call, the proxy finds the instance for the current request.

Example

@Component @Scope("prototype")
class ReportBuilder { private final List<String> rows = new ArrayList<>(); void add(String r) { rows.add(r); } }

@Service
class ReportService {
    private final ObjectProvider<ReportBuilder> builders;
    ReportService(ObjectProvider<ReportBuilder> builders) { this.builders = builders; }
    String build(List<Order> orders) {
        ReportBuilder b = builders.getObject();            // fresh, unshared instance per call
        orders.forEach(o -> b.add(o.toString()));
        return String.join("\n", b.rows);
    }
}

// The bug: request state in a singleton
@Service
class BadPricingService {
    private String currentTenant;                           // shared by ALL threads!
    Price price(String tenant, String sku) {
        currentTenant = tenant;                             // thread A sets "t1", thread B sets "t2"…
        return lookup(currentTenant, sku);                  // …thread A may now read "t2" → wrong tenant's price
    }
}
  • ReportService gets a new ReportBuilder on each call through ObjectProvider. So two requests never share the same rows.
  • BadPricingService stores request data in a field of a singleton. Thread A sets the tenant to "t1". Then thread B sets it to "t2". Thread A now reads "t2" and returns the wrong tenant's price.

When would I use it?

  • Singleton for almost all services, repositories, clients and controllers.
  • Request scope for request context objects. (Or use a ThreadLocal holder — a per-thread variable — that a filter sets.)
  • Prototype for stateful, short-lived helpers built by a factory.

What can go wrong?

  • Mutable fields in singletons. They cause race conditions (threads overwriting each other) and cross-tenant data leaks, as shown above.
  • Prototype beans holding resources. The container never destroys them, so you must clean them up yourself.
  • Request-scoped beans used outside a request. In async threads or scheduled jobs there is no request. So they fail with "No thread-bound request found".

Interview questions

Q1. What bean scopes exist? singleton (the default), prototype, request, session and application — plus websocket.

Q2. Are singleton beans thread-safe? Only if you make them so. Spring does not synchronise them. Keep them stateless, or use thread-safe fields.

Q3. What happens when a prototype is injected into a singleton? It is injected only once, so the singleton always uses the same instance. To get a fresh one, use ObjectProvider, @Lookup, or a scoped proxy.

Q4. Spring singleton vs GoF Singleton? Spring's singleton is one instance per container, so several contexts mean several instances. The GoF Singleton is one per class loader, and the class itself enforces it.

6.6 Bean lifecycle and post-processors

Why?

In simple words: Every bean goes through fixed stages: it is created, filled with its dependencies, set up, used, and finally cleaned up. Knowing these stages tells you where to put your setup and cleanup code — and when Spring adds its proxies.

Beans often need two kinds of extra work:

  • Setup after dependencies are injected: load a rule cache, check the config, open a connection.
  • Cleanup at shutdown: flush buffers, close pools.

Spring itself also needs hooks to add behaviour to beans. For example, it adds proxies for transactions, security and async.

The lifecycle defines exactly when each of these happens.

What is happening internally?

1. Instantiate              constructor (constructor injection happens here)
2. Populate properties      field / setter injection
3. Aware callbacks          BeanNameAware, BeanFactoryAware, ApplicationContextAware
4. BeanPostProcessor.postProcessBeforeInitialization   (all BPPs, in order)
5. Initialisation           @PostConstruct → InitializingBean.afterPropertiesSet() → custom init-method
6. BeanPostProcessor.postProcessAfterInitialization    ← AOP auto-proxy creator WRAPS the bean in a proxy here
7. Ready — the PROXY (if any) is what gets stored and injected everywhere
   ...
8. Shutdown (singletons)    @PreDestroy → DisposableBean.destroy() → custom destroy-method

Step by step:

  1. Instantiate. Spring calls the constructor. Constructor injection happens here.
  2. Populate properties. Field and setter injection happen.
  3. Aware callbacks. If the bean asks for it, Spring gives it its own name, the BeanFactory, or the ApplicationContext.
  4. Before-init post-processing. Every BeanPostProcessor runs postProcessBeforeInitialization, in order.
  5. Initialisation. First @PostConstruct, then InitializingBean.afterPropertiesSet(), then any custom init-method.
  6. After-init post-processing. Every BeanPostProcessor runs postProcessAfterInitialization. Here the AOP auto-proxy creator wraps the bean in a proxy.
  7. Ready. If a proxy was made, the proxy is stored and injected everywhere — not the raw object.
  8. Shutdown (singletons only). First @PreDestroy, then DisposableBean.destroy(), then any custom destroy-method.

There are two extension points. Their names are similar, so keep them apart:

  • BeanFactoryPostProcessor works on the recipes.
  • It runs before any bean is created, and it changes bean definitions.
  • Examples: PropertySourcesPlaceholderConfigurer fills in ${...} placeholders. Configuration-class processing registers more bean definitions.
  • BeanPostProcessor works on the finished objects.
  • It runs for each bean instance, and it can change the bean or replace it completely.
  • Examples: AutowiredAnnotationBeanPostProcessor does the @Autowired injection. AnnotationAwareAspectJAutoProxyCreator creates AOP proxies for @Transactional, @Async, @Cacheable and aspects.

Think of a tiffin service. The BeanFactoryPostProcessor edits the menu card before anything is cooked. The BeanPostProcessor works on each packed tiffin — it can add a label, or put the box inside a bigger insulated bag (the proxy).

How does it work?

Order matters here.

  • Inside a constructor or @PostConstruct, this is the raw object. It is not the proxy, because the proxy is created later, in step 6.
  • So if you call your own @Transactional method from @PostConstruct, it runs without a transaction.
  • Work that needs the full context and the proxies should run after startup. Use ApplicationRunner or @EventListener(ApplicationReadyEvent.class).

Example

@Component
class RuleCache {
    private final RuleRepository repo;
    private volatile Map<String, Rule> rules = Map.of();
    RuleCache(RuleRepository repo) { this.repo = repo; }        // 1: dependencies available

    @PostConstruct
    void load() { rules = repo.findAllActive(); }               // 5: safe to use injected deps

    @PreDestroy
    void close() { rules = Map.of(); }                          // 8: on graceful shutdown
}

@Component
class WarmUp {
    private final RecommendationService recs;
    WarmUp(RecommendationService recs) { this.recs = recs; }
    @EventListener(ApplicationReadyEvent.class)                 // after everything (proxies, server) is ready
    void warm() { recs.preloadPopularSkus(); }
}

// A custom BeanPostProcessor (how frameworks add behaviour)
@Component
class TimingPostProcessor implements BeanPostProcessor {
    @Override public Object postProcessAfterInitialization(Object bean, String name) {
        // could return a proxy wrapping 'bean' — exactly how AOP works
        return bean;
    }
}
  • RuleCache loads its rules in @PostConstruct (step 5), when the repository is already injected. It clears them in @PreDestroy (step 8).
  • WarmUp waits for ApplicationReadyEvent. At that point all proxies exist and the server is running.
  • TimingPostProcessor shows the hook frameworks use. It could return a proxy around bean instead of bean itself — that is exactly how AOP works.

When would I use it?

  • @PostConstruct: cache warm-up and validation that use injected dependencies.
  • @PreDestroy: flushing and closing things.
  • ApplicationRunner: jobs that should run once at startup.
  • BeanPostProcessors: only when you write infrastructure or library code.

What can go wrong?

  • Heavy or slow work in constructors or @PostConstruct. It delays startup and readiness. And if it fails, the whole startup is aborted.
  • Expecting @Transactional or @Async to work inside @PostConstruct. There is no proxy yet, so they do nothing.
  • @PreDestroy not being called. It is never called for prototype beans, or when the process is killed with kill -9. Enable graceful shutdown (server.shutdown=graceful) and handle SIGTERM (the polite stop signal) in Kubernetes.

Interview questions

Q1. Describe the Spring bean lifecycle. Instantiate → inject dependencies → Aware callbacks → BPP before-init → @PostConstruct / afterPropertiesSet / init-method → BPP after-init (this is where proxies are created) → in use → @PreDestroy / destroy on shutdown.

Q2. BeanFactoryPostProcessor vs BeanPostProcessor? A BFPP changes bean definitions (the recipes) before any bean is created. A BPP changes or wraps each bean instance, around the time it is initialised.

Q3. When are AOP proxies created? In postProcessAfterInitialization, by the auto-proxy creator BeanPostProcessor. The proxy then replaces the raw bean in the container.

6.7 Proxies and AOP: how @Transactional, @Async and @Cacheable really work

Why?

In simple words: Spring puts a wrapper object (a proxy) in front of your bean. Every outside call passes through the wrapper, which adds extra work like starting a transaction. But a call from inside the bean to itself skips the wrapper — and that is the source of many Spring bugs.

Some concerns cut across hundreds of methods: transactions, security checks, caching, retries, metrics and logging.

If you copy-paste begin/commit/rollback or timing code into each method, you will make mistakes. Aspect-Oriented Programming (AOP) solves this. You write the behaviour once, and it is applied around every matching method.

Spring builds AOP using proxies. Once you understand proxies, you can explain the most common Spring bugs.

Think of a bank branch. You don't walk straight to the cashier. The security guard at the door checks you first, and logs you on the way out. The cashier (your real method) only does the money work.

What is happening internally?

A proxy is an object that:

  1. has the same type as your bean,
  2. catches each call made to it,
  3. runs advice — extra logic before, after or around the call,
  4. and passes the call on to the real object.

There are two kinds of proxy:

  • JDK dynamic proxy: it implements the bean's interfaces (using java.lang.reflect.Proxy). Because it only implements interfaces, you can't cast it to the concrete class.
  • CGLIB proxy: it creates a subclass of your class at runtime and overrides its methods. Spring Boot uses CGLIB by default.
  • Result: final classes, and final or private methods, can't be intercepted. A subclass can't override them.
caller ──► [CGLIB proxy of RedemptionService]
              TransactionInterceptor: begin tx
              ──► real RedemptionService.redeem()
                     └── this.audit()   ← internal call on 'this' — NOT through the proxy
              TransactionInterceptor: commit (or rollback on RuntimeException)

In the diagram, the outside call goes through the proxy, so the transaction starts. But this.audit() is called on the real object directly. It never passes through the proxy.

Key words you should know:

  • Aspect: the module that holds the cross-cutting logic.
  • Advice: the logic itself, and when it runs — @Before, @After, @AfterReturning, @AfterThrowing, @Around.
  • Pointcut: an expression that selects which methods get the advice.
  • Join point: one single method execution.
  • Weaving: applying aspects to code. Spring does it at runtime with proxies. AspectJ can also weave at compile time or when classes are loaded.

How does it work?

Only calls that come in through the proxy are intercepted.

A call from inside the object (this.method()) goes straight to the real object and bypasses the proxy. This is the self-invocation problem.

Because of it, these annotations silently stop working on the called method: @Transactional, @Async, @Cacheable, @Retryable, @PreAuthorize. There is no error — they just do nothing.

Example

@Service
public class LedgerService {
    public void processBatch(List<Txn> txns) {
        for (Txn t : txns) post(t);           // this.post(t): bypasses proxy → NO new transaction per txn
    }
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void post(Txn t) { /* ... */ }
}

// Fix 1 (cleanest): move the transactional method to another bean
@Service class LedgerPoster { @Transactional(propagation = Propagation.REQUIRES_NEW) public void post(Txn t) { } }
@Service class LedgerBatch {
    private final LedgerPoster poster;
    LedgerBatch(LedgerPoster poster) { this.poster = poster; }
    public void processBatch(List<Txn> txns) { txns.forEach(poster::post); }   // through the proxy
}

// Fix 2: programmatic transactions
@Service class LedgerBatch2 {
    private final TransactionTemplate tx;
    LedgerBatch2(PlatformTransactionManager tm) { this.tx = new TransactionTemplate(tm); }
    public void processBatch(List<Txn> txns) { for (Txn t : txns) tx.executeWithoutResult(s -> post(t)); }
    private void post(Txn t) { /* ... */ }
}

// Writing your own aspect: time any method annotated @Timed
@Retention(RetentionPolicy.RUNTIME) @Target(ElementType.METHOD) @interface Timed {}

@Aspect @Component
class TimingAspect {
    private static final Logger log = LoggerFactory.getLogger(TimingAspect.class);
    @Around("@annotation(com.fa.loyalty.Timed)")
    public Object time(ProceedingJoinPoint pjp) throws Throwable {
        long start = System.nanoTime();
        try { return pjp.proceed(); }
        finally { log.info("{} took {} ms", pjp.getSignature().toShortString(), (System.nanoTime() - start) / 1_000_000); }
    }
}

What the code shows:

  • The bug. processBatch calls post(t) on this. The proxy is skipped, so there is no new transaction per transaction record.
  • Fix 1 (cleanest). Move the transactional method into another bean (LedgerPoster). Now the call goes through that bean's proxy.
  • Fix 2. Use programmatic transactions with TransactionTemplate. You start each transaction in code, so no proxy is needed.
  • Your own aspect. TimingAspect times any method marked @Timed. @Around wraps the call, and pjp.proceed() runs the real method.

When would I use it?

  • Use the built-in proxied annotations every day: @Transactional, @Async, @Cacheable, @PreAuthorize, @Retryable.
  • Write custom aspects only for truly cross-cutting concerns: timing and metrics, audit logging, tenant checks, and idempotency guards (checks that make a repeated request safe — doing it twice has the same effect as doing it once).
  • Keep business logic out of aspects.

What can go wrong?

  • Self-invocation (explained above). This is the #1 Spring interview trap.
  • Annotations on private or final methods. They are ignored, with no error at all.
  • Calling the bean before it is proxied. For example, in the constructor or in @PostConstruct.
  • Objects created with new. Spring never sees them, so they are not proxied.
  • Aspect ordering surprises. For example, is the retry inside the transaction or outside it? Set the order explicitly with @Order.
  • Over-broad pointcuts like execution(* com..*(..)). They slow everything down and make the code hard to reason about.

Interview questions

Q1. How does Spring AOP work? Spring creates proxies — CGLIB subclasses or JDK interface proxies — inside a BeanPostProcessor. The proxy runs the advice around each call and then passes the call to the target bean.

Q2. Why doesn't @Transactional work when I call the method from the same class? The internal call goes through this, not through the proxy, so the transaction interceptor never runs. Move the method to another bean, or use TransactionTemplate.

Q3. JDK proxy vs CGLIB? A JDK proxy can only implement interfaces. CGLIB creates a subclass of the class, and it is Boot's default. Because it subclasses, final classes and final methods can't be advised.

Q4. Name the advice types. @Before, @AfterReturning, @AfterThrowing, @After (runs always, like finally), and @Around (wraps the call and decides whether and when to proceed).

6.8 Configuration, @ConfigurationProperties and profiles

Why?

In simple words: Build the app once, and change its settings from outside — through files, environment variables and secrets. The same JAR then runs on your laptop, in QA and in production.

The same JAR must run in different places: on a laptop, in QA and in production. Each place has different databases, URLs, credentials and feature settings.

If you hard-code these values, you must rebuild the app for every environment.

Externalised configuration fixes this. You keep one artefact (one built JAR). Only the files, environment variables and secrets change.

What is happening internally?

Spring builds an Environment object from an ordered list of property sources (places where settings come from). If two sources set the same key, the higher one wins.

Simplified order, highest first:

  1. Command-line arguments (--server.port=9090)
  2. SPRING_APPLICATION_JSON
  3. OS environment variables (SPRING_DATASOURCE_URL, LOYALTY_REDEMPTION_MAXPOINTSPERDAY). Relaxed binding maps these to normal keys — so SPRING_DATASOURCE_URL becomes spring.datasource.url.
  4. Profile-specific files: application-prod.yml
  5. application.yml / application.properties
  6. @PropertySource, then defaults

@ConfigurationProperties takes all properties under one prefix and loads them into a typed object at startup. A record works well for this. It also:

  • converts values — durations like 10s, data sizes like 10MB,
  • validates values — with @Validated.

So bad config fails at startup, not at 2 a.m. in production.

Profiles (spring.profiles.active=prod) switch on profile-specific files, and beans marked @Profile("prod").

Think of a mobile phone. The phone is the same everywhere. When you change the SIM card, it picks up a different network and number. The JAR is the phone; the config is the SIM.

How does it work?

# application.yml
spring:
  application.name: loyalty-service
  datasource:
    url: jdbc:postgresql://localhost:5432/loyalty
    username: ${DB_USER:loyalty}            # env var with a default
    password: ${DB_PASSWORD}                # must come from the environment/secret store
  jpa.open-in-view: false
loyalty:
  redemption:
    max-points-per-day: 50000
    hold-timeout: 10m
---
spring.config.activate.on-profile: prod
logging.level.root: WARN

Key points in this file:

  • ${DB_USER:loyalty} reads an environment variable, and uses loyalty if it is not set.
  • ${DB_PASSWORD} has no default. It must come from the environment or a secret store.
  • The part after --- applies only when the prod profile is active.

Example

@ConfigurationProperties(prefix = "loyalty.redemption")
@Validated
public record RedemptionProps(@Positive long maxPointsPerDay, @NotNull Duration holdTimeout) {}

@SpringBootApplication
@ConfigurationPropertiesScan
public class LoyaltyApplication { }

@Service
class RedemptionLimits {
    private final RedemptionProps props;
    RedemptionLimits(RedemptionProps props) { this.props = props; }
    boolean allowed(long todaysTotal, long requested) { return todaysTotal + requested <= props.maxPointsPerDay(); }
}

@Configuration
class SmsConfig {
    @Bean @Profile("!prod") SmsSender fakeSms() { return (to, msg) -> System.out.println("SMS to " + to + ": " + msg); }
    @Bean @Profile("prod")  SmsSender realSms(GupshupProps p) { return new GupshupSmsSender(p); }
}
  • RedemptionProps is a typed, validated record for everything under loyalty.redemption. A negative limit or a missing timeout stops startup.
  • @ConfigurationPropertiesScan tells Spring to find such records.
  • SmsConfig gives a fake SMS sender in every profile except prod, and the real Gupshup sender in prod.

In Kubernetes:

  • Non-secret config comes through ConfigMaps — as mounted files or environment variables.
  • Secrets come through Kubernetes Secrets or Azure Key Vault. Spring Cloud Azure can load Key Vault secrets as a property source.

When would I use it?

For every value that changes per environment: URLs, timeouts, limits, feature flags, pool sizes and credentials.

Prefer typed @ConfigurationProperties over many scattered @Value("${...}") strings.

What can go wrong?

  • Secrets committed to application.yml in Git. Use environment variables or a vault instead.
  • A typo in a property name is silently ignored. This happens with @Value plus a default, or with properties that nothing binds to. Validated properties records catch type errors. Add the configuration processor to get IDE hints for property names.
  • Too many profiles that combine in surprising ways (dev,local,kafka-off). Keep only a few profiles, one per environment.
  • Different values in different pods because of a stale ConfigMap. A config change needs a rollout or a refresh mechanism to reach every pod.

Interview questions

Q1. How does Spring Boot resolve a property that's defined in several places? By property-source precedence. Command-line arguments beat environment variables. Environment variables beat profile-specific files. Profile-specific files beat application.yml.

Q2. @Value vs @ConfigurationProperties? @Value injects one value at a time by its string key. @ConfigurationProperties loads a whole prefix into a typed object that can be validated. It is better for groups of related settings.

Q3. How do you manage secrets? Never in source control. Inject them through environment variables from Kubernetes Secrets, or from a vault (Azure Key Vault, HashiCorp Vault), and rotate them regularly.

6.9 Auto-configuration and starters

Why?

In simple words: Boot looks at which libraries you added and sets up the matching objects for you. If you define your own version of an object, Boot sees it and steps back.

Without Boot, every app wrote the same 200 lines of setup:

  • a DataSource and a connection pool,
  • an EntityManagerFactory,
  • a transaction manager,
  • Jackson's ObjectMapper,
  • the DispatcherServlet,
  • Tomcat…

Auto-configuration does this for you when it sees that you need it. And it steps aside the moment you define your own.

Think of a hotel room. The basic things — bed, towel, kettle — are already set up when you arrive. If you bring your own kettle, housekeeping doesn't add a second one.

What is happening internally?

  1. @EnableAutoConfiguration reads a file inside each JAR on the classpath: META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports. It lists the candidate configuration classes. The spring-boot-autoconfigure JAR alone lists about 150.
  2. Each candidate is an @AutoConfiguration class. It is guarded by conditions that are checked at startup:
Condition The config applies when…
@ConditionalOnClass(DataSource.class) that class is on the classpath (a driver or library is present)
@ConditionalOnMissingBean(DataSource.class) you haven't defined your own bean of that type
@ConditionalOnProperty("spring.kafka.bootstrap-servers") a property is set (or has a given value)
@ConditionalOnBean some other bean exists
@ConditionalOnWebApplication it's a web app
  1. Auto-configurations are processed after your own configuration. So @ConditionalOnMissingBean can already see your beans, and it backs off.
  2. Properties classes feed values into the auto-configured beans. For example, DataSourceProperties is bound to spring.datasource.*.

How does it work?

Here is a real chain. You add spring-boot-starter-data-jpa and the Postgres driver. Then:

  1. DataSourceAutoConfiguration creates a HikariCP connection pool from spring.datasource.*.
  2. HibernateJpaAutoConfiguration creates the EntityManagerFactory and a JpaTransactionManager.
  3. JpaRepositoriesAutoConfiguration scans for repository interfaces and creates proxies for them.

If you define your own DataSource bean, step 1 backs off.

To debug what was configured:

  • Run with --debug. This prints the condition evaluation report. It lists positive matches (applied) and negative matches (skipped), each with a reason.
  • Or call the Actuator endpoint /actuator/conditions.

To switch something off explicitly: @SpringBootApplication(exclude = DataSourceAutoConfiguration.class).

Example

// Your own starter: shared multi-tenancy support for all services in the platform
@AutoConfiguration
@ConditionalOnClass(TenantResolver.class)
@EnableConfigurationProperties(TenantProps.class)
public class TenantAutoConfiguration {
    @Bean @ConditionalOnMissingBean
    TenantResolver tenantResolver(TenantProps props) { return new HeaderTenantResolver(props.header()); }

    @Bean @ConditionalOnMissingBean
    FilterRegistrationBean<TenantFilter> tenantFilter(TenantResolver resolver) {
        var reg = new FilterRegistrationBean<>(new TenantFilter(resolver));
        reg.setOrder(Ordered.HIGHEST_PRECEDENCE + 10);
        return reg;
    }
}
// + one line in META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports:
//   com.fa.platform.tenant.TenantAutoConfiguration

This is your own starter. It gives every service on the platform the same multi-tenancy support:

  • It only applies when TenantResolver is on the classpath.
  • Each bean has @ConditionalOnMissingBean, so a service can still replace it.
  • You register it with one line in the AutoConfiguration.imports file.

A platform team publishing a "tenant starter" is a great senior-level example to mention in interviews. Every service then gets the same tenant header handling, MDC tagging (adding the tenant to every log line) and Hibernate filter.

When would I use it?

  • Every day, as a user. Read the condition report when something is configured (or not configured) unexpectedly.
  • Write your own starter for conventions shared across services: tenancy, auth, log format, standard error responses.

What can go wrong?

  • Surprise auto-config from a transitive dependency (a library pulled in by another library). For example, Spring Security on the classpath suddenly protects every endpoint with a generated password. Or a Kafka client starts trying to connect.
  • Defining a bean with the "wrong" type or name. The auto-config doesn't recognise it, so it doesn't back off. You end up with two beans.
  • Startup failure "Failed to configure a DataSource". JPA is on the classpath, but no database URL is set.

Interview questions

Q1. How does Spring Boot auto-configuration work? Starters put auto-configuration classes on the classpath, listed in AutoConfiguration.imports. Each class applies only if its @Conditional checks pass. It backs off if you have already defined that bean yourself.

Q2. How do you see why something was or wasn't auto-configured? Run with --debug to get the condition evaluation report, or use Actuator's /conditions endpoint.

Q3. How do you disable a specific auto-configuration? Use @SpringBootApplication(exclude = …) or spring.autoconfigure.exclude in properties. Or simply define your own bean of that type.

6.10 Startup sequence and application events

Why?

In simple words: Know what Spring does, step by step, from java -jar until the app is ready. And learn Spring events: one part of your app announces "this happened", and other parts react, without the two knowing about each other.

Knowing what happens between java -jar and "Started in 4.2 seconds" helps you:

  • debug startup failures,
  • put initialisation code in the right place,
  • make startup faster,
  • and decouple parts of your app with events (inside one process).

What is happening internally?

  1. SpringApplication.run decides the app type (servlet, reactive, or none). It loads initializers and listeners.
  2. It prepares the Environment (property sources and profiles) and prints the banner.
  3. It creates the ApplicationContext.
  4. Bean definition loading. Component scan, @Configuration processing and auto-configuration all run. These are done by BeanFactoryPostProcessors.
  5. Singleton instantiation. Spring resolves the dependency graph. Beans are created, injected, initialised and proxied (by BeanPostProcessors).
  6. The embedded web server starts. The port opens.
  7. ApplicationStartedEvent fires. Then the ApplicationRunner / CommandLineRunner beans run. Then ApplicationReadyEvent fires, and readiness becomes UP.
  8. On shutdown: stop accepting new traffic (graceful), destroy beans, close pools.

Application events are a publish–subscribe system inside one process.

  • You call ApplicationEventPublisher.publishEvent(obj).
  • Spring calls every matching @EventListener method.
  • By default this is synchronous, on the same thread. If a transaction is open, the listener runs inside that same transaction.

Think of the announcement system at a railway station. The station master announces once, and every passenger waiting for that train reacts. He doesn't need to know who they are.

How does it work?

@TransactionalEventListener(phase = AFTER_COMMIT) waits until the surrounding transaction commits. If the transaction rolls back, the listener is skipped.

That makes it the correct place to send notifications about database changes.

Example

public record PointsRedeemed(String accountId, long points, String redemptionId) {}

@Service
class RedemptionService {
    private final ApplicationEventPublisher events;
    RedemptionService(ApplicationEventPublisher events) { this.events = events; }
    @Transactional
    public void redeem(String acc, long pts) {
        // ... debit ledger, save redemption ...
        events.publishEvent(new PointsRedeemed(acc, pts, "R-123"));   // listener runs only if we commit
    }
}

@Component
class RedemptionNotifier {
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    @Async("notificationExecutor")                                     // don't block the request thread
    void on(PointsRedeemed e) { smsSender.send(e.accountId(), "Redeemed " + e.points() + " points"); }
}

What happens here:

  1. redeem runs inside a transaction and publishes PointsRedeemed.
  2. The listener does not run yet. It waits for the commit.
  3. If the transaction commits, the listener runs. If it rolls back, the listener never runs.
  4. @Async("notificationExecutor") runs the SMS on another thread pool, so the request thread is not blocked.

When would I use it?

To separate side effects from core logic inside one service: notifications, audit, cache eviction (removing stale cache entries) and metrics.

For cross-service reliability, in-process events are not enough. If the process crashes right after the commit, the in-process event is lost. When the event must reach Kafka no matter what, use the transactional outbox pattern (11.15).

What can go wrong?

  • Synchronous listeners hurting the publisher. A slow listener slows the publisher's request. An exception in a plain @EventListener goes back up to the publisher and can roll back its transaction.
  • @TransactionalEventListener with no active transaction. By default the event is silently dropped. Set fallbackExecution = true if you need it to run anyway.
  • Slow startup from eagerly creating heavy beans. Measure it with the /actuator/startup endpoint (with BufferingApplicationStartup). Consider lazy init for beans that aren't critical, and keep @PostConstruct light.

Interview questions

Q1. What happens when a Spring Boot application starts? Spring prepares the environment, creates the context, and loads bean definitions (scan, config, auto-config). Then it creates the singletons, running post-processors and creating proxies. It starts the embedded server, runs the runners, and finally fires ApplicationReadyEvent.

Q2. Are Spring events synchronous? Yes, by default — they run on the publisher's thread. Add @Async to handle them asynchronously. @TransactionalEventListener ties delivery to a transaction phase, such as after commit.

Q3. Why use @TransactionalEventListener(AFTER_COMMIT) for notifications? So users are never told about changes that later roll back. For guaranteed delivery across services, use an outbox instead.
