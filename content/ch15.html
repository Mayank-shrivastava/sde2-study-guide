Going blank in an interview is not a knowledge problem. It happens for two reasons:

  • You have only recognised the material — you watched it or read it. You never practised pulling it out of memory under pressure.
  • You don't have a ready next step to say out loud.

This chapter fixes both. It gives you training habits, and a script for every round. So there is always something useful to say.

15.1 Why people blank, and the fixes

Cause What it feels like Fix
Passive learning (videos, re-reading) "I've seen this, but nothing comes" Close the source. Solve or explain it again from memory. Use spaced repetition (review at growing gaps: 1 day, 3 days, 1 week)
Practising in silence Your mind goes empty when someone watches Say every practice solution out loud. Record yourself once a week
No fallback move You panic, and the panic feeds itself Memorise the scripts below. When stuck, just run the next step
Perfectionism You wait for the best idea before you speak Always start with brute force. Say it first, then improve it
Stress reaction in the body Racing heart, tunnel vision Breathe slowly twice (4 s in, 6 s out). Write the problem down. Say it back in your own words
Unfamiliar setting Shared editor, no IDE autocomplete Practise in plain editors (LeetCode, CoderPad-style, Google Docs)

15.2 Coding round script (45 minutes)

  1. Restate the problem in your own words. Confirm the input types, input sizes and output format (2 min).
  2. Examples: write one normal case and one edge case — empty, single item, duplicates, negatives, very large (2 min).
  3. Brute force: say the simplest solution out loud with its time and space complexity, even if it is clearly slow (2 min).
  4. Pattern search: go through your pattern triggers out loud (15.3). For example: "Sorted? → two pointers or binary search. Subarray? → sliding window or prefix sum…" Pick one, and explain why it fits (3–5 min).
  5. Agree on the approach and its complexity with the interviewer before you start coding.
  6. Code cleanly in Java. Write the method signature first, then helper methods. Use meaningful names. Explain your decisions as you go (15 min).
  7. Dry-run your example line by line. Then dry-run the edge case (5 min).
  8. Complexity: state the final time and space complexity, and suggest one possible improvement (2 min).

When stuck (say these out loud)

  • "Let me try a smaller input by hand and look for a pattern."
  • "What if the array were sorted? What if I process it from the right?"
  • "What would I need to store so I don't recompute this?" (→ hashing or DP)
  • "Can I binary-search on the answer? Is feasibility monotonic — once an answer works, do all bigger answers also work?"
  • After about 5 minutes of being truly stuck, ask a focused question: "I'm considering X and Y. X fails because… Would it be reasonable to think about Y?" A targeted question like this earns a hint, and you don't look lost.

15.3 Coding round: what this guide adds to your DSA prep

Your DSA resource already covers patterns and problems, so this guide does not repeat them.

What this guide adds for the coding round is Java fluency. The goal is simple: the language should never slow you down.

Need in a coding round Section
Pick the right collection and know its cost 2.1 (choosing), 2.4 HashMap, 2.6 TreeMap, 2.8 ArrayDeque, 2.9 PriorityQueue
Sort objects by several keys without bugs 1.13 Comparable/Comparator (never a - b)
Avoid overflow and boxing traps 1.2 Integer cache, 1.3 overflow
Build strings efficiently 1.5 StringBuilder
Design a data structure where every operation is O(1) 10.3 LRU cache (HashMap + doubly linked list)
Coding questions with a concurrency angle 4.14 bounded blocking queue, producer–consumer, odd–even printing

Keep a short personal list of the pattern triggers from your DSA resource. For example: "sorted → two pointers / binary search; subarray → window / prefix sum…". Say this list out loud in step 4 of the script above.

15.4 LLD round script (60–90 minutes)

  1. Clarify. List 4–6 core use cases and write them down. Confirm what is out of scope. Ask about concurrency and persistence (saving data).
  2. Entities. Nouns become classes, enums or records. Verbs become methods.
  3. Relationships. Draw a quick class diagram.
  4. Interfaces first. Name the design patterns at the places where behaviour can vary.
  5. Code in this order: models → repositories (in-memory) → services → strategies → a main demo. Make the happy path work end to end before adding extras.
  6. Walk through one scenario using the code.
  7. Close with three points: - Thread safety — what is shared, and how it is protected. - Extensibility — where a new feature would plug in. - Testing approach.

Justify every pattern in one sentence. That is what interview-level LLD sounds like. For example: "I used Strategy for pricing because pricing varies independently of the Ride entity, and I want to add new pricing schemes without modifying ride logic." Practise saying a line like this for each pattern, in every problem you solve.

When stuck, say: "Let me write the main use case as a sequence of calls first." Write main using the API you wish you had. This often unlocks the design.

15.5 HLD round script (45–60 minutes)

  1. Functional requirements — list 3–5. Also say clearly what is out of scope.
  2. Non-functional requirements — users/DAU (daily active users), QPS (queries per second), read/write ratio, latency, availability, consistency and data size.
  3. Estimates — calculate out loud: QPS, storage per year, cache size.
  4. API — 3–6 endpoints.
  5. Data model and store choice — give a one-line reason for the choice.
  6. High-level diagram — then walk one read request and one write request through it.
  7. Offer deep dives: "The interesting parts are A and B — which would you like to explore?"
  8. Close with bottlenecks, failure modes, a plan for 10× scale, and monitoring.

When stuck, go back to the requirements. Say: "Given we need X at Y QPS, the bottleneck is Z, so…". Naming the bottleneck is always a valid next sentence.

15.6 Java/Spring theory round

Answer in three layers:

  1. Definition — 1 sentence.
  2. How it works — 2–3 sentences.
  3. When or why it matters in production — 1 example from your own work.

Example: "@Transactional is declarative transaction management. Spring wraps the bean in a proxy that begins a transaction before the method and commits or rolls back after — rolling back on unchecked exceptions by default. In practice the classic bug is self-invocation, where an internal call skips the proxy; I'd move the method to another bean."

If you don't know the answer, say: "I haven't used that directly. My understanding is … and I'd verify by …". Never bluff with a confident wrong answer.

15.7 Mock interviews: how to run them and score them

From Week 13, do one mock every Sunday. From Week 15, do two per week.

Trade mocks with a peer — you interview them too. You learn as much from the interviewer's side.

Scoring rubric (1–4 each)

Dimension 1 4
Problem understanding Jumped into code; solved the wrong problem Clarified, gave examples, confirmed constraints
Approach No brute force, no pattern Brute force → optimal, with reasons
Communication Long silences Continuous, structured narration
Code quality Buggy, messy Clean, modular, correct on the first run
Testing None Dry run + edge cases; found own bugs
Complexity Wrong or missing Correct for both time and space

Weekly mock mix from Week 15 (when you can find partners):

  • 2 DSA
  • 1 LLD
  • 1 HLD
  • 1 Java/backend theory round. A peer asks 15–20 questions from Chapter 16 and asks two follow-ups on each.

Don't wait until you feel "100% ready". Mocks are how you get ready.

Timed DSA simulation (45 min, Java only, no autocomplete):

  1. 5 min — understand the problem.
  2. 5 min — brute force.
  3. 10 min — optimise.
  4. 20 min — code.
  5. 5 min — test and state the complexity.

Practise in a plain editor: LeetCode's editor with autocomplete off, or a blank doc.

The failure notebook

After every mock and every real interview, write one entry for each mistake. Do it within the hour, while it is fresh.

Date / company / round:
Question:
Mistake:                     (what went wrong — be specific: "used HashMap, missed that order mattered")
Why I made it:               (didn't clarify / didn't recognise pattern / panicked / didn't know concept)
Correct approach:            (the right solution or answer, written fully)
Pattern or concept missed:   (e.g. "monotonic stack", "@Transactional self-invocation", "fan-out on read")
What I'll revise:            (chapter/section + a re-solve date 3 days out)

Review the notebook every Sunday. Look at the "why I made it" column. The causes that keep coming back are your real weak spots. Fix those causes — not just the individual questions.

Interview mode (Weeks 13–16): the loop

DSA / LLD / HLD practice ─► Mock ─► Real interview ─► Failure analysis (notebook)
          ▲                                                    │
          └──────────── Targeted revision of what failed ◄─────┘

Don't follow the path course → course → course → "now I'll start interviewing". That approach wastes months.

Instead, start applying from Week 13. Apply to practice companies first. Then your early real interviews feed this loop.

Re-attempt every failed mock problem 3 days later.

15.8 Online assessments (OA)

An OA usually has 2–3 problems in 60–90 minutes. It runs on HackerRank, Codility or HackerEarth, with hidden tests.

  • Read all the problems first. Solve the easiest one first.
  • When input comes through stdin, use fast I/O: BufferedReader + StringTokenizer, not Scanner.
  • Watch for int overflow and edge cases. Hidden tests target exactly these.
  • Partial credit counts. Submit a brute force that passes some tests first, then optimise.
  • Keep a personal Java template file with imports, a fast reader and common helpers.

15.9 The day before and the day of

Day before:

  • No new topics.
  • Review your flashcards, your story bank and your pattern triggers.
  • Prepare your setup: camera, mic, charged laptop, quiet room, water, paper and pen.
  • Sleep 7–8 hours.

Day of:

  • 1 hour before: solve 2 easy problems out loud to warm up.
  • 10 minutes before: read your "tell me about yourself" answer and your 3 questions to ask.
  • During the round: restate the problem, write things down, think out loud.
  • Between rounds: don't replay the last round in your head. Reset with a short walk and some water.

After each round: within the hour, write down the questions and how you did. Patterns across companies tell you what to fix.

15.10 The weekly review (Sunday, 1 hour)

  1. Tick off the week's tasks in the plan (Chapter 0).
  2. Pick 3 random sections from the week. Re-explain each one without notes — all seven steps, out loud.
  3. Answer 10 random Q&A cards out loud.
  4. Update the failure notebook and schedule your re-attempts.
  5. Check your gates (the pass/fail checkpoints in the plan). If a gate fails, repeat the weak part next week instead of moving on.
  6. Plan next week's sections from the plan in Chapter 0.
