13.1 URL Shortener (TinyURL / bit.ly)

Why?

In simple words: You give a long link and get back a short code. When someone opens the short code, you look up the long link and send them there — very fast, millions of times a day.

Functional (what it must do): - Create a short link for a long URL. Optionally allow a custom alias and an expiry date. - Redirect from the short link to the long URL. - Basic click analytics.

Non-functional (how well it must do it): - Redirects must be fast (p99 < 50 ms — 99% of requests finish within 50 ms) and highly available. - Reads are about 100 times more than writes (read:write ≈ 100:1). - Two links must never get the same code (no collisions).

What it tests: ID generation, caching a path that is mostly reads, and keeping analytics off the hot path (the path every request takes).

What is happening internally?

Estimates: - 100M new links/month ≈ 40 writes/s (peak ~120). - Reads are ×100 → ~4,000/s (peak ~12,000). - Each record is ~500 B. So 100M × 12 × 5 years × 500 B ≈ 3 TB over 5 years. - Base62 (digits + lowercase + uppercase = 62 characters) with 7 characters gives 62⁷ ≈ 3.5 trillion codes. That is plenty.

API:

POST /api/v1/urls   {longUrl, customAlias?, expiresAt?}  → 201 {shortUrl}
GET  /{code}         → 302 Location: longUrl   (301 is cached by browsers: less load, but clicks become invisible)
GET  /api/v1/urls/{code}/stats

Data model: url(code PK, long_url, owner_id, created_at, expires_at). You always look a link up by its code. So a key-value store (DynamoDB/Cassandra) fits well. Postgres split into shards by code also works.

Architecture:

  • Redirects go through a CDN/edge, then a load balancer, then the redirect service. Redis holds the ~20% of codes that are hot. On a cache miss, you go to the URL store.
  • The create service takes IDs from a range allocator and encodes them in base62.
  • Clicks are sent to Kafka. Analytics consumers read them and write to ClickHouse.
Client → CDN/edge → LB → Redirect service → Redis (code→url, ~20% hot set) → miss → URL store
Create service → ID range allocator → base62 encode → URL store
Redirect service → Kafka "clicks" → analytics consumers → ClickHouse

How does it work?

Code generation (the core deep dive). There are four common ways:

Approach How Trade-off
Hash + truncate base62(md5(longUrl))[0..7] You must detect collisions and retry; the same URL always gets the same code (deduped)
Global counter + base62 Sequence → base62 No collisions; but one central counter for everyone; codes are easy to guess
Pre-allocated ID ranges Each instance leases (borrows) a block of 1M IDs from a coordinator (a DB row or ZooKeeper), then encodes locally No coordination per request, no collisions — preferred
Key generation service Random unused keys are generated in advance and handed out in batches Codes are hard to guess; but you run one more service

Write path: 1. Validate the URL. 2. Take the next ID from this instance's local range. 3. Encode it in base62. 4. Insert it. For a custom alias, use a conditional insert, so the insert fails if the alias is already taken. 5. Return the short URL.

Read path: 1. Look up the code at the edge or in Redis. 2. On a hit, return a 302 redirect. 3. On a miss, read from the store, put the result into Redis, then return 302. 4. Publish a click event in the background (asynchronously), so the user does not wait for it.

Example

  1. Instance A leases IDs 5,000,000–5,999,999.
  2. Request 1 gets ID 5,000,000. It is encoded in base62 and padded on the left to make a 7-character code. Then it is stored.
  3. Later, a redirect for that code finds it in Redis in 0.8 ms.
  4. The click event goes to Kafka. ClickHouse counts it a few seconds later.

When would I use it?

  • Link shortening.
  • Referral and campaign links.
  • QR codes for retail promotions.
  • In general, any service that maps "key → value", is mostly reads, and needs keys that are unique everywhere.

What can go wrong?

  • Collisions with hashing. Two URLs can give the same truncated hash. You must detect this and retry.
  • Hot links. One very popular link can overload one cache shard. Fix: copy hot keys to several places, and cache at the edge.
  • Slow analytics. Writing analytics synchronously (while the user waits) slows down redirects.
  • Malicious URLs. Scan URLs when they are created, and rate-limit each user.
  • Expired links still in cache. Set the cache TTL (time to live) so it respects the link's expiry.

Interview questions

Q1. How do you generate short codes without collisions at scale? Give each instance its own pre-allocated range of IDs and encode them in base62. (Snowflake or UUIDv7 IDs, encoded, also work.) This way, no request needs to coordinate with other machines.

Q2. 301 or 302? A 301 is cached by browsers. That means less load on you, but you lose analytics because repeat clicks never reach you. A 302 lets you see every click. Choose based on whether analytics matter.

Q3. How do you keep redirects fast while counting clicks? Serve the redirect from the cache. Publish click events in the background to Kafka, and count them there.

13.2 Distributed Rate Limiter

Why?

In simple words: A rate limiter counts how many requests each client sends and says "slow down" (HTTP 429) when they cross their limit. The hard part is keeping one shared, correct count when many servers handle the same client.

Functional (what it must do): - Limit requests per client — by user, API key, IP or tenant. - Limits are set per rule, for example 100/min per tenant per endpoint. - When the limit is crossed, return 429 with a Retry-After header. - Rules can be configured.

Non-functional (how well it must do it): - Add less than 2 ms of latency. - Stay correct across many gateway instances. - Have a clear, decided behaviour when the limiter itself fails: fail-open (allow requests) or fail-closed (block requests).

What it tests: rate-limiting algorithms (10.5), atomic updates in a shared store, and failure handling.

What is happening internally?

Placement: Put the limiter at the API gateway, or as a sidecar/middleware next to each service. Cache the rules locally and refresh them from a config service.

Store: Use a Redis cluster, with keys split across shards by client ID.

The check must be atomic — read, check and write must happen as one step. Otherwise two servers could both read "99 used" and both allow request 100. Redis Lua scripts solve this. The whole script runs in one round trip, and nothing else runs in between. So there is no race between the read and the write.

Here is a token bucket script. Think of a bucket that holds tokens. Each request takes a token. Tokens refill at a fixed rate. If the bucket is empty, the request is rejected.

-- Token bucket (KEYS[1] = bucket key; ARGV = capacity, refill_per_ms, now_ms, cost)
local b = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local cap, rate, now, cost = tonumber(ARGV[1]), tonumber(ARGV[2]), tonumber(ARGV[3]), tonumber(ARGV[4])
local tokens = tonumber(b[1]) or cap
local ts = tonumber(b[2]) or now
tokens = math.min(cap, tokens + (now - ts) * rate)
local allowed = tokens >= cost
if allowed then tokens = tokens - cost end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(cap / rate) * 2)
return allowed and 1 or 0

Alternatives: - Fixed window (INCR key:minute + EXPIRE): the simplest. But bursts can slip through at window edges (end of one minute + start of the next). - Sliding log (ZADD, ZREMRANGEBYSCORE, ZCARD): exact, but uses more memory because it stores every request time. - Sliding window counter (a weighted mix of two buckets): a good balance of accuracy and memory.

How does it work?

  1. A request arrives and the gateway authenticates it.
  2. The gateway builds the key, for example t-42:/redemptions.
  3. It runs the script with EVALSHA, using Redis server time.
  4. If the result is 1, it forwards the request.
  5. If the result is 0, it returns 429 with Retry-After and X-RateLimit-Remaining.

Example

Tenant t-42 is on the GOLD plan: capacity 200, refill 100/s. It sends a burst of 300 requests in one second:

  • 200 pass immediately (the bucket was full).
  • The next ~100 pass as tokens refill.
  • The rest get 429 with Retry-After: 1.

When would I use it?

  • Public and partner APIs.
  • Protecting OTP and login from abuse.
  • Fairness between tenants.
  • Protecting your outbound calls to partners that give you a quota.

What can go wrong?

  • Redis slow or down. Keep local fallback buckets. Fail open for non-critical APIs; fail closed for OTP/login.
  • Hot keys for very large tenants. One key gets too much traffic. Split it into N sub-keys, each with limit/N.
  • Multi-region limits. Use a quota per region, or sync counts between regions in the background.
  • Clock skew. App servers' clocks may differ. Use Redis TIME so everyone uses one clock.

Interview questions

Q1. How do you make the limiter atomic across instances? Keep the state in Redis and update it with a Lua script. Then read, check and write all happen in one atomic operation.

Q2. What happens if Redis is down? It is a deliberate policy decision. For normal APIs, fail open and use approximate local limits. For sensitive endpoints, fail closed. Either way, raise an alert.

Q3. Token bucket or sliding window? Use token bucket when you want to allow controlled bursts while keeping a smooth average rate. Use a sliding window counter for simple, accurate limits per time window.

13.3 Notification System

Why?

In simple words: Services say "tell this user X", and the system picks the right channel (SMS, email, push, WhatsApp), respects their preferences, and delivers it — without sending duplicates and without bulk campaigns blocking urgent OTPs.

Functional (what it must do): - Send notifications by SMS, email, push and WhatsApp/in-app. - Triggered by services (order placed, points credited) and by campaigns (bulk sends). - Respect user preferences and opt-outs. - Templates with localisation (different languages). - Scheduling. - Delivery tracking.

Non-functional (how well it must do it): - Transactional messages (like OTPs) arrive within seconds. - Millions of campaign messages must not delay OTPs. - No duplicates. - Switch to a backup provider if one fails (failover).

What it tests: queue design, prioritisation, idempotency (doing the same request twice has the same effect as once) and third-party integration.

What is happening internally?

Estimates: 10M transactional messages/day (~120/s, peaks ~1,000/s). Plus 5M-message campaigns sent within an hour (~1,400/s).

The flow in the diagram, in plain words:

  1. Producer services call POST /notify.
  2. The Notification API validates the request and removes duplicates using the idempotency key. It checks preferences, quiet hours and DND. Then it renders the template in the user's language.
  3. It puts the message on one of two Kafka topics. notify.high is for transactional messages; notify.bulk is for campaigns. Separate topics keep the priorities apart.
  4. Channel workers (one consumer group per channel) send through provider adapters. Each adapter has a circuit breaker (stops calling a failing provider for a while), a per-provider rate limit, and failover to a second provider.
  5. Providers call back through delivery webhooks, and a status updater records the result.
Producers (order, loyalty, campaign service)
   │  POST /notify {userId, templateId, params, channelHints, idempotencyKey, priority}
   ▼
Notification API: validate → dedupe (idempotency key) → preferences, quiet hours, DND → render template (locale)
   ├─► Kafka "notify.high"  (transactional)        separate topics = priority isolation
   └─► Kafka "notify.bulk"  (campaigns, rate-shaped)
Channel workers (SMS / email / push / WhatsApp consumer groups)
   → provider adapters (Strategy) with circuit breakers, per-provider rate limits, failover to a secondary provider
   → providers (Gupshup/Twilio, SES, FCM/APNs) ─► delivery webhooks ─► status updater
Stores: preferences + templates (Postgres + cache), notification log/status (Cassandra or ClickHouse), scheduled sends (DB + scheduler)

How does it work?

  1. Remove duplicates using an (event, user, channel) key. Render the template. Put the message on the right priority topic.
  2. Channel workers read the message and apply the provider's rate limit. They call the provider with an idempotency/reference ID, and record SENT.
  3. Provider webhooks update the status to DELIVERED/FAILED/READ. Each webhook's signature is verified, and the handling is idempotent, so a repeated webhook does no harm.
  4. Failures are retried with backoff (waiting longer each time). After N attempts, the message goes to a DLQ (dead-letter queue — a parking place for failed messages), and a fallback channel is tried (SMS if push fails).

Example

  1. A "points credited" event arrives. The template points_credited_hi (Hindi) is chosen.
  2. Push is tried first. The device is offline for 10 minutes, so no delivery receipt comes back.
  3. The system falls back to SMS, and the SMS is delivered.

Meanwhile, a 5M-message Diwali campaign drains through notify.bulk. It runs at the SMS provider's limit of 1,000 msg/s. It does not delay any OTPs, because they travel on notify.high.

When would I use it?

  • Any messaging over several channels.
  • Alerting.
  • Marketing campaigns.
  • In general: "spread work out to slow outside providers, with priorities".

What can go wrong?

  • Duplicate sends on retries. Fix with idempotency keys.
  • Campaigns starving transactional messages. Fix with separate topics and separate worker pools.
  • Provider throttling. Shape the send rate and use more than one provider.
  • Regulatory issues. Respect opt-outs, DND and quiet hours in each user's timezone.
  • Template bugs sent to millions. Preview templates and roll out in stages.
  • Webhook storms. Too many status callbacks at once. Batch the status updates.

Interview questions

Q1. How do you ensure OTPs aren't delayed by a marketing campaign? Give each priority its own topics, its own consumer pools and its own provider quotas. Also shape (throttle) the rate of bulk traffic.

Q2. How do you avoid sending duplicate notifications? Use an idempotency key per (event, user, channel). Store it with a TTL and a unique constraint. Also make the webhook handling idempotent.

Q3. How do you track delivery? Keep a status machine for each message, updated by provider callbacks. Store it in a store built for heavy writes, with dashboards showing delivery rates per provider.

13.4 News Feed (Twitter/LinkedIn/Instagram home feed)

Why?

In simple words: When you open the app, you see recent posts from people you follow. The main choice is when to build that list: when someone posts (push), or when you open the app (pull) — and celebrities with millions of followers need special handling.

Functional (what it must do): - Users post. - Users follow others. - The home feed shows posts from the people you follow, newest first or ranked, page by page.

Non-functional (how well it must do it): - The feed loads in < 200 ms. - New posts may take a few seconds to appear. This is called eventual consistency. - 300M DAU (daily active users). - Far more reads than writes.

What it tests: fan-out strategies (how a post is spread to followers), caching at scale, and the celebrity problem.

What is happening internally?

Estimates: 300M DAU × 10 feed loads = 3B/day ≈ 35k QPS (peak ~100k). 150M posts/day ≈ 1.7k writes/s.

There are two ways to build feeds:

Fan-out on write (push) Fan-out on read (pull)
How When someone posts, add the post ID to each follower's ready-made feed (a Redis list) When someone opens the feed, fetch recent posts from everyone they follow and merge them
Read cost O(1) — read one list O(followees) — grows with how many people you follow
Write cost O(followers) — huge for celebrities O(1)
Best for Normal users Celebrities with millions of followers

The architecture in plain words:

  1. The post service saves the post in the Posts DB, sends media to blob storage/CDN, and publishes a PostCreated event.
  2. Fan-out workers ask the social graph service for the followers. They add the post ID to each follower's feed:{userId} list in Redis (capped at ~800 IDs).
  3. The feed service reads the user's list, merges in recent celebrity posts, fills in the full post details (hydrates the IDs), ranks them, and returns one page using a cursor.
Post service → Posts DB (Cassandra/sharded, by post_id) + media to blob/CDN → PostCreated event
Fan-out workers → Social graph service (followers) → feed:{userId} lists in Redis (capped ~800 IDs)
Feed service: read feed:{userId} + merge recent posts of followed celebrities → hydrate IDs from post cache → rank → cursor page

How does it work?

Hybrid — use both methods: - Normal authors: push their posts to followers' feeds. - Celebrities (above a follower threshold): skip fan-out. Merge their recent posts in when a follower reads the feed. - Inactive users: do not precompute their feeds. Build the feed on their next login.

Example

  • A user with 300 followers posts. Fan-out workers do 300 LPUSH + LTRIM operations within ~1 s.
  • A celebrity with 20M followers posts. No fan-out happens. When their followers load the feed, it includes "recent posts from followed celebrities" — a small cached list. It is merged in by timestamp or score.

When would I use it?

  • Activity feeds.
  • Notification inboxes.
  • "What's new" panels.
  • B2B feeds, such as new schemes shown to an outlet.
  • Any problem where one item must be shown to many people (one-to-many distribution).

What can go wrong?

  • Celebrity fan-out storms. One post triggers millions of writes.
  • Feed caches too big. Cache feeds only for active users, and cap list sizes.
  • Deleted or privacy-changed posts still showing. Filter them out at hydration time.
  • Slow ranking. Precompute the features used for ranking.
  • Unstable pagination. New posts shift the pages. Use a cursor on (score + ID).

Interview questions

Q1. Push vs pull for feeds? Push makes reads cheap but makes writes expensive for popular authors. Pull is the opposite. Use a hybrid: push for most users, pull for celebrities.

Q2. How do you paginate a feed that changes constantly? Use a cursor based on (score or timestamp, postId), not page offsets. Offsets break when new posts are added at the top.

13.5 Chat System (WhatsApp / Slack)

Why?

In simple words: Every phone keeps an open connection to a chat server. When you send a message, the server saves it, gives it a number in the conversation, and pushes it to the receiver's connection — or sends a push notification if they are offline.

Functional (what it must do): - 1:1 chat and group chat (≤ 500 members). - Presence (online/last seen). - Delivery and read receipts. - Offline delivery through push notifications. - History synced across multiple devices. - Media.

Non-functional (how well it must do it): - < 200 ms delivery when the receiver is online. - Messages are never lost. - Messages stay in order within each conversation. - 500M DAU.

What it tests: long-lived connections, routing messages to the right server, ordering, storage at huge write volume, and delivery guarantees.

What is happening internally?

Estimates: 500M DAU × 40 messages = 20B messages/day ≈ 230k messages/s. At ~100 B each, that is ~2 TB/day of text.

The architecture in plain words:

  1. Clients connect over WebSocket (a connection that stays open both ways) to connection (gateway) servers. Each server holds ~100k–1M connections. These servers are stateful — they remember who is connected to them.
  2. Each connection server records "userId → serverId" in a session registry in Redis.
  3. The chat service stores messages in Cassandra. The partition key is conversation_id and the clustering key (sort order) is message_seq.
  4. To deliver, the chat service finds the receiver's connection server in the registry and sends the message through internal pub/sub.
  5. If the receiver is offline, it sends a push notification (FCM/APNs).
  6. Large groups use fan-out workers on Kafka. Media is uploaded directly to blob storage using a pre-signed URL and served via CDN. Presence uses heartbeats stored in Redis with a TTL.
Clients ══ WebSocket ══► Connection (gateway) servers — stateful, ~100k–1M connections each
                            register userId → serverId in a session registry (Redis)
                            ▼
                        Chat service → Message store (Cassandra: partition = conversation_id, clustering = message_seq)
                            ├─► route to the recipient's connection server (registry lookup + internal pub/sub)
                            └─► recipient offline → push notification (FCM/APNs)
Group fan-out workers (Kafka) for large groups · Media → pre-signed upload to blob + CDN · Presence → heartbeats in Redis with TTL

How does it work?

  1. The sender's client sends {clientMsgId, conversationId, body} over its WebSocket.
  2. The chat service gives the message a per-conversation sequence number. It saves the message, then confirms (acks) to the sender — "sent" ✓. The clientMsgId makes resends idempotent: if the client sends the same message twice, it is stored once.
  3. The service finds the receivers' connection servers and pushes the message. When the receiver's device acks, "delivered" ✓✓ flows back to the sender. When the receiver opens the chat, it becomes "read".
  4. Offline receivers get a push notification. When they reconnect, the client asks for all messages after its last seen sequence in each conversation.

Example

  1. Asha sends "Order confirmed?" to the distributor group (40 members).
  2. The message gets seq 1043 in the group conversation.
  3. 32 online members receive it through their connection servers in ~100 ms.
  4. 8 offline members get a push notification.
  5. One of them reconnects an hour later. Its last seen seq was 1029, so it fetches seq > 1029 and receives 14 messages, in order.

When would I use it?

  • Chat and live support.
  • The conversational ordering channel of an assistant like NOVA.
  • Collaborative apps.
  • Any real-time messaging that goes both ways.

What can go wrong?

  • Connection server fails. Clients reconnect to another server and resync using their sequence number.
  • Ordering across devices. Fix with a server-assigned sequence per conversation.
  • Hot group conversations. Use fan-out workers and rate limits.
  • Presence storms. Too many online/offline updates. Fetch presence lazily, only when a chat is opened.
  • Message loss. This happens if you ack before saving. Always save first, then ack.

Interview questions

Q1. How do you route a message to a user connected to a different server? Keep a session registry in Redis that maps each user to their connection server. Then send the message to that server through internal pub/sub or a direct RPC call.

Q2. How do you guarantee ordering and no loss? Save the message before acking. Assign a sequence number per conversation. Make sends idempotent using client message IDs. On reconnect, resync from the last seen sequence.

Q3. Why Cassandra for messages? The write volume is very high, and messages are read by conversation in time order. That fits Cassandra's partition key + clustering key model well, and Cassandra scales out by adding machines.

13.6 Distributed Cache (design Redis/Memcached)

Why?

In simple words: A cache keeps hot data in memory so reads take well under a millisecond. To hold more data than one machine can, you split keys across many machines and keep copies so a crash does not lose everything.

Functional (what it must do): - get, put with a TTL (time to live), and delete. - Grow beyond one machine. - Survive node failures.

Non-functional (how well it must do it): - Sub-millisecond latency. - Millions of operations per second.

What it tests: in-memory data structures, eviction (removing old data when memory is full), partitioning, replication and consistency trade-offs.

What is happening internally?

  • Single node: a hash map plus an eviction structure. This can be an LRU list (least recently used goes first). Or it can be approximate LRU/LFU (least frequently used) done by sampling a few keys, as Redis does. TTLs are enforced in two ways: lazily, when a key is accessed, and by regularly checking a random sample of keys that have expiry.
  • Partitioning (splitting keys across nodes): consistent hashing with virtual nodes, done in the client or through a proxy. Redis Cluster instead uses 16,384 hash slots, and each node owns some of the slots.
  • Replication: each shard has a primary and replicas, copied asynchronously (in the background). Failover is handled by Sentinel or by cluster consensus (the nodes vote).
  • Memory efficiency: slab allocation in Memcached (memory pre-cut into fixed-size chunks), and compact encodings for small objects in Redis (listpacks).
  • Concurrency model: Redis runs commands on a single thread, so it needs no locks (newer versions add I/O threads). Memcached is multi-threaded, with striped locks (many small locks, each covering part of the data).
  • Persistence (optional): snapshots (RDB) and append-only logs (AOF).

How does it work?

  1. For GET k, the client hashes k to get a slot.
  2. The slot tells it which node owns the key.
  3. That node looks up the key in memory and returns the value.

If a node fails, its replica is promoted to primary. Keys written to the old primary just before the failure may be lost, because replication is asynchronous. For a cache, this is acceptable.

Example

  • A 6-node Redis Cluster (3 primaries + 3 replicas, 32 GB each) holds 80 GB of hot data.
  • You add 2 primaries. Some slots move to them while the cluster keeps running (online).
  • One hot key — a festival scheme list read 50k times/s — is also copied into an in-process Caffeine cache on every app pod, with a 5 s TTL. So most reads never even reach Redis.

When would I use it?

  • Caching.
  • Sessions.
  • Rate-limit counters.
  • Leaderboards.
  • Distributed locks (carefully).
  • Short-lived coordination state.

What can go wrong?

  • Cache as the only copy. Never keep critical data only in the cache.
  • Hot keys. One very popular key overloads one node.
  • Cache and DB disagree. Use cache-aside: delete the cache entry on every write, and use TTLs (11.5).
  • Large values. A big value blocks Redis's single thread for everyone.
  • Eviction storms. When memory is too small, keys are evicted constantly.

Interview questions

Q1. How would you scale a cache horizontally? Split keys across nodes with consistent hashing or hash slots. Add replicas for failover, and let the client route each key to the right node.

Q2. Why is Redis single-threaded yet fast? In-memory operations take microseconds. A single thread avoids lock contention and context switches. And I/O multiplexing (one thread watching many sockets) lets it serve many connections at once.

13.7 Loyalty and Rewards Platform (your system — rehearse it three levels deep)

Why?

In simple words: Outlets earn points on orders and spend them on rewards. Every change is written as a permanent line in a ledger (like a bank passbook), so points are never credited twice, never spent twice, and every rupee can be traced.

Functional (what it must do): - Tenants (brands) set up their own programmes. - Outlets earn points on orders, scans and achievements. - They redeem points for rewards: catalogue items, vouchers, cashback. - Tiers, expiry, statements and admin adjustments. - Reverse the points when an order is cancelled.

Non-functional (how well it must do it): - Never double-credit, never double-spend. - Balance reads < 100 ms. - Accrual (adding points) may lag by a few seconds. - 700+ tenants and 8.9M outlets. - Strict tenant isolation — one tenant never sees another's data. - Full audit.

What it tests: idempotency, ledger design, sagas and multi-tenancy. And it is your strongest story.

What is happening internally?

Estimates: - 5M orders/day → 5M accrual events (~60/s; month-end peaks ~500/s). - 200k redemptions/day. - 20M balance reads/day (~230/s). - Ledger: ~6M entries/day × 200 B ≈ 1.2 GB/day ≈ 440 GB/year.

API and events:

POST /v1/accounts/{id}/redemptions   Idempotency-Key  {rewardId, points}
GET  /v1/accounts/{id}/balance
GET  /v1/accounts/{id}/statement?after=cursor
POST /v1/admin/adjustments           (maker-checker)
Consumes: OrderCompleted, OrderCancelled, AchievementUnlocked
Produces: PointsAccrued, PointsRedeemed, PointsExpired, TierChanged

(Maker-checker means one person makes the adjustment and a second person approves it.)

Data (PostgreSQL, monthly partitions for the ledger): - account(id, tenant_id, outlet_id, balance, tier, version) - ledger_entry(id, tenant_id, account_id, type, points, idempotency_key UNIQUE(tenant_id, key), ref_id, lot_id, created_at) — append-only: rows are only added, never changed - lot(id, account_id, points_remaining, expires_at) — each batch of earned points, used for FIFO expiry (oldest points expire first, 10.11) - redemption(id, account_id, reward_id, points, status, partner_ref) — saga state - outbox, processed_event

The architecture in plain words:

  1. The order service publishes order events to Kafka. Accrual consumers read them (idempotently) and use a rules engine to compute points. In one local transaction, they write the ledger entry, the lot, the balance and an outbox row.
  2. API requests come through the API gateway to the Loyalty API, backed by PostgreSQL (a primary for writes, replicas for statements).
  3. Redemption is a saga — a series of steps, each with an undo. First debit points in a local transaction. Then call the voucher partner with an idempotency key. Then confirm, or compensate (undo).
  4. An outbox relay (or CDC — change data capture, reading the DB's change log) publishes points events to Kafka. Notifications, analytics (ClickHouse) and the tier service consume them.
  5. Balances are cached in Redis and evicted on change. An expiry job runs daily per tenant, in chunks, guarded by ShedLock (so only one instance runs it).
Order svc → Kafka order-events → Accrual consumers (idempotent; rules engine computes points)
                                   │ local tx: ledger + lot + balance + outbox
API GW → Loyalty API → PostgreSQL (primary; replicas for statements)
            │ redemption saga: debit (local tx) → voucher partner (idempotency key) → confirm / compensate
            ▼
         Outbox relay/CDC → Kafka points-events → notifications, analytics (ClickHouse), tier service
Balance cache: Redis (evicted on change) · Expiry job: daily per tenant in chunks (ShedLock)

How does it work?

Accrual (adding points): 1. Consume OrderCompleted. 2. If this event ID was already processed, skip it. 3. Compute the points. 4. In one transaction, insert the ledger entry, the lot, the balance update, the processed-event row and the outbox event.

Redemption (spending points): 1. Check the idempotency key. If it was seen before, return the stored response. 2. Debit atomically with a condition (balance >= points). If the balance is too low, nothing changes. 3. In the same transaction, write the ledger entry, the saga row and the outbox row. 4. The orchestrator calls the voucher partner, using the redemption ID as the idempotency key. 5. On success: confirm and notify. 6. On failure after retries: compensate (credit the points back) and mark the redemption FAILED.

Example

  1. An outlet with 1,200 points redeems 1,000 for a ₹100 voucher. The user double-taps the button, so two requests arrive.
  2. Request 1 debits the points (balance becomes 200) and stores the key.
  3. Request 2 has the same key, so it just gets the stored response. No second debit.
  4. The partner times out once. The retry uses the same key, so the partner returns the same voucher code.
  5. The SMS goes out via the outbox → Kafka → notification service.

When would I use it?

  • Points, wallets, credits, cashback, gift cards.
  • Any balance system built on a ledger.

What can go wrong?

  • Double credit: happens if the event-ID dedupe is not in the same transaction as the ledger write.
  • Double spend: happens if you read the balance and then write it, without a conditional update or a lock.
  • Balance/ledger drift: the stored balance stops matching the ledger. Run a nightly reconciliation that compares SUM(ledger) with the balance for each account, and alert on any difference.
  • Expiry at scale: expire lot by lot, in chunks. The job must be resumable (can continue after a crash) and idempotent per lot. Notify users before their points expire.
  • Month-end spikes: Kafka absorbs the burst. Scale consumers based on lag (how far behind they are). Partition by account so each account's events stay in order.
  • Tenant isolation: put the tenant ID on every row and in every query. Apply rate limits per tenant.

Say this: "The most important property is that every balance change is an immutable, idempotent ledger entry written in the same transaction as the balance update and the outbox event. Everything else — caching, notifications, analytics — hangs off that."

Interview questions

Q1. How do you prevent duplicate accruals when Kafka redelivers? Keep a unique constraint on the processed event ID (or idempotency key), and write it in the same transaction as the ledger entry. A redelivered event then fails the constraint and is skipped.

Q2. What if the voucher partner fails after points are debited? The saga retries with the same idempotency key, so the partner never issues two vouchers. If the failure is permanent, the saga compensates: it credits the points back and marks the redemption failed.

Q3. How do you keep balance reads fast? Keep a cached balance column that is updated in the same transaction as the ledger. Add Redis on top, evicted whenever the balance changes. Serve statements from read replicas.

13.8 Payment System

Why?

In simple words: A payment system must never lose money and never charge twice. You track every payment through fixed states, make every step safe to repeat, never treat a timeout as a failure, and check your records against the bank's file every day.

Functional (what it must do):

  • Merchants create payment intents — a record saying "this order needs ₹X".
  • Customers pay by card, UPI or netbanking through external gateways. These gateways are called PSPs (payment service providers), like Razorpay or PayU.
  • Handle the PSP's callbacks (webhooks) that tell you the result.
  • Handle refunds.
  • Keep a ledger — a record of every movement of money.
  • Do reconciliation — match your records against the PSP's settlement files.

Non-functional (how well it must do it):

  • Correctness matters more than speed.
  • Exactly-once effect — a message may arrive twice, but money moves only once.
  • A full audit trail.
  • High availability.
  • PCI-DSS compliance (the card industry's security rules). Never store card data yourself — the PSP gives you a token (a safe stand-in ID) to use instead.

This question tests state machines, idempotency at every hop (making each step safe to repeat), unknown outcomes and reconciliation.

What is happening internally?

Client → Payment API: POST /payments {orderId, amount, method}  Idempotency-Key
   → payment row (CREATED) + outbox, in one transaction
   → PSP "create order" (idempotency key = payment id) → status PENDING → return PSP intent / UPI deep link
Customer pays in the PSP/UPI app
PSP → webhook /psp/callback (verify signature) → idempotent transition PENDING → SUCCEEDED / FAILED
   → double-entry ledger rows (debit customer receivable, credit merchant payable) in the same transaction
   → outbox PaymentSucceeded → order service, notifications
Status poller: PENDING older than N minutes → query the PSP (webhooks get lost)
Reconciliation: daily settlement file vs ledger → mismatches to an ops queue

The flow in steps:

  1. The client calls POST /payments with an Idempotency-Key, so a retry does not create a second payment.
  2. In one DB transaction, you save the payment row (status CREATED) and an outbox row. An outbox row is a message saved in the same transaction, which a separate process later publishes — so the DB and the events never disagree.
  3. You call the PSP's "create order" API. You use the payment ID as the idempotency key there too. The status becomes PENDING. You return the PSP intent or a UPI deep link to the client.
  4. The customer pays inside the PSP page or UPI app.
  5. The PSP calls your webhook /psp/callback. You first verify its signature, so nobody can fake it.
  6. You move the status PENDING → SUCCEEDED or FAILED. This step is idempotent — safe if the webhook comes twice.
  7. In the same transaction, you write double-entry ledger rows: debit the customer receivable, credit the merchant payable.
  8. The outbox publishes PaymentSucceeded to the order service and notifications.
  9. A status poller checks payments that have been PENDING for more than N minutes, by asking the PSP directly. This is needed because webhooks sometimes get lost.
  10. Reconciliation runs daily. It compares the PSP's settlement file against your ledger and sends any mismatch to an ops queue.

Tables:

  • payment(id, order_id, amount_minor, currency, method, status, psp_ref, version)
  • ledger_entry(id, account, direction, amount_minor, payment_id, created_at) — the double-entry ledger
  • refund(...)
  • idempotency_key(...)

amount_minor means the amount in the smallest unit — paise, not rupees — stored as a whole number.

How does it work?

  • State machine. A payment can only move along allowed paths: CREATED → PENDING → SUCCEEDED/FAILED, and SUCCEEDED → REFUND_PENDING → REFUNDED.
  • Every move is a conditional update, like WHERE status = 'PENDING'.
  • So if a duplicate callback arrives, the condition no longer matches and nothing changes. It is a no-op.
  • Double-entry ledger. Every money movement is written as balanced debits and credits — the totals always match.
  • Balances are calculated from these entries.
  • Amounts are never edited in place; you only add new rows.
  • Think of a shop's khata book: you never rub out a line, you only add a correcting line.
  • Unknown outcomes. A timeout when calling the PSP is not a failure. The money may have moved. 1. Mark the payment UNKNOWN. 2. Ask the PSP's status API what really happened. 3. Then resolve it to SUCCEEDED or FAILED.
  • Never retry a charge with a new idempotency key — that can charge the customer twice.

Example

A UPI payment of ₹1,250:

  1. The API returns a deep link, and the user pays.
  2. The webhook arrives twice, because the PSP retried.
  3. The first webhook moves PENDING → SUCCEEDED and writes the ledger rows.
  4. The second webhook sees the status is no longer PENDING. It returns 200 and changes nothing.

Another payment's webhook never arrives. After 10 minutes the poller asks the PSP, finds it SUCCEEDED, and completes it.

Next morning, reconciliation matches 99.98% of settlements. The two mismatches go to the ops team.

When would I use it?

Payments, wallets, payouts (such as incentive payouts to sales reps), refunds, and any integration where real money moves through an outside system.

What can go wrong?

  • Using floating-point for money. 0.1 + 0.2 is not exactly 0.3 in floating point. Use minor units (paise) as whole numbers.
  • Treating a timeout as a failure. The customer retries and gets charged twice.
  • Not checking webhook signatures. Anyone can send a forged "payment succeeded" callback.
  • Non-idempotent refunds. A retried refund sends money back twice.
  • No reconciliation. Your records and the bank's slowly drift apart, and nobody notices.
  • Storing card data. This puts your whole system in PCI scope — very costly audits and risk.

Interview questions

Q1. How do you avoid double charging? Use idempotency keys at every hop — from client to API, and from API to PSP. Make state changes conditional, so a repeat does nothing. And when the outcome is unknown, ask the PSP for the status instead of retrying blindly.

Q2. Why a double-entry ledger? Every movement balances debits and credits. So errors show up immediately, balances can be calculated from the entries, and the full history can be audited.

Q3. What if the PSP webhook never arrives? A poller asks the PSP for the status of payments that have been pending too long. Daily reconciliation against the settlement files catches anything still missed.

13.9 Leaderboard (gaming / sales incentives)

Why?

In simple words: A leaderboard needs a list that stays sorted by score while scores keep changing. Redis sorted sets do exactly this, so updating a score and asking "what is my rank?" are both very fast.

Functional (what it must do):

  • Update a user's score.
  • Show the top N users.
  • Show a user's rank and the people just above and below them (neighbours).
  • Keep separate boards per tenant, per region and per period (daily or monthly).

Non-functional (how well it must do it):

  • Near real-time — scores show up within seconds.
  • Top-N reads in under 50 ms.
  • Millions of members on one board.

This question tests whether you choose the right data structure (sorted sets) and how you scale beyond one node.

What is happening internally?

Use Redis sorted sets (ZSETs). Inside, a sorted set is a skip list (a sorted linked list with "express lanes" for fast jumping) plus a hash map. The costs:

  • ZINCRBY (add to a score) — O(log n).
  • ZREVRANGE 0 99 (top 100) — O(log n + k), where k is how many you fetch.
  • ZREVRANK (a user's rank) — O(log n).

O(log n) means even with millions of users, it takes only around 20 steps.

Sales events → Kafka → score updater (idempotent per event) → ZINCRBY lb:{tenant}:{region}:{month} amount repId
API: top 100 → ZREVRANGE … WITHSCORES ; my rank → ZREVRANK ; neighbours → ZREVRANGE rank-5 rank+5
Period close → snapshot to Postgres for payouts; key TTL after the period

The flow:

  1. Sales events go to Kafka.
  2. A score updater reads them. It is idempotent per event — the same event never counts twice.
  3. It runs ZINCRBY on a key like lb:{tenant}:{region}:{month}.
  4. The API serves the top 100 with ZREVRANGE, "my rank" with ZREVRANK, and neighbours with a range around your rank.
  5. When the period closes, you snapshot the board to Postgres for payouts. Then the Redis key expires through a TTL (time to live).

The real source of truth stays in the database or ledger. The board in Redis is only a fast view, and you can rebuild it from the events at any time.

How does it work?

Ties. Two reps may have the same score. Put a tiebreaker inside the score itself. For example: score × 10¹⁰ + (MAX_TS − achievedAt). The person who reached the score earlier gets a slightly higher number, so they rank higher.

Going beyond one sorted set (tens of millions of members):

  1. Split users across shards by a hash of the user ID.
  2. For the global top N, take each shard's top N and merge them.
  3. For any user's global rank, you can estimate it using a histogram of score buckets — counts of how many users fall in each score range.

Example

A Gold-tier rep in the North region opens the app. It shows: "Rank 37 of 2,140 this month, ₹4,200 behind #36".

This is just ZREVRANK for the rank, plus ZSCORE for this user and the user one place above. It takes about 1 ms.

When would I use it?

Gamified incentives for field reps, gaming, contests, trending lists, and "top K" dashboards.

What can go wrong?

  • Double-counted events. Remove duplicates by event ID before calling ZINCRBY.
  • Boards that grow forever. Set a TTL on each period's key.
  • Calculating ranks from SQL on every request. This is far too slow at scale.
  • Ties not handled in a fixed way. Two users swap places randomly between page loads.

Interview questions

Q1. Which data structure would you use? A sorted set built on a skip list — Redis ZSETs. Score updates and rank lookups are O(log n), and fetching the top k is O(log n + k).

Q2. How do you scale beyond one Redis node? Shard the users. For the global top k, merge each shard's top k. For a global rank, estimate it using histograms of scores.

13.10 Typeahead / Search Autocomplete

Why?

In simple words: As the user types each letter, you must show the best suggestions in a few milliseconds. So you work out the answers in advance, store them in a tree of letters (a trie), and just look them up.

Functional (what it must do):

  • As the user types, return the top 5–10 suggestions, ranked by popularity. Optionally, personalise them for the user.
  • Update popularity from search logs.

Non-functional (how well it must do it):

  • Under 50 ms end to end, because it runs on every keystroke.
  • Very high QPS (queries per second).
  • Suggestions may be minutes or even hours old — that is acceptable.

This question tests tries, precomputation and caching.

What is happening internally?

Estimates: 10M daily active users × 10 searches each × about 6 keystrokes ≈ 600M requests per day. That is about 7k QPS on average, and around 20k QPS at peak.

Search logs → Kafka → aggregation job (hourly/daily: Spark/Flink) → top queries with counts
   → build a trie in which every node stores its precomputed top-K completions
   → serialise, shard by prefix range, load into the memory of Suggest servers (or Redis)
Client (debounce ~100 ms, cache prefixes) → CDN/edge cache for popular prefixes → Suggest service (O(prefix length) lookup)

The flow:

  1. Search logs go into Kafka.
  2. An aggregation job (Spark or Flink, run hourly or daily) counts the top queries.
  3. You build a trie — a tree where each step down is one letter. Every node stores its own precomputed top-K completions.
  4. You serialise the trie, split it by prefix ranges (shards), and load it into the memory of the Suggest servers (or into Redis).
  5. On the client side, the app waits about 100 ms after the last keystroke before sending a request. This is called debounce. The app also caches prefixes it has already seen.
  6. Popular prefixes are served from a CDN/edge cache.
  7. Anything else reaches the Suggest service, which looks it up in O(prefix length) — the time depends only on how many letters were typed.

How does it work?

To look up a prefix:

  1. Walk down the trie, one character at a time.
  2. At the last node, return the top-K list already stored there.

You never search the whole subtree at query time. Storing the top-K at every node uses more memory, but it makes lookups very fast. That is the trade-off: memory for speed.

Example

A retailer types "maz". You walk m → a → z. That node already holds ["maaza 600ml", "maaza 1.2l", "maaza 250ml"…]. It returns from memory in about 1 ms.

For SKU search in an ordering assistant like NOVA, a trie alone is not enough. Combine it with Elasticsearch for:

  • fuzzy matching — handling spelling mistakes ("mazza" → "maaza"),
  • transliteration — handling Hinglish queries typed in English letters.

When would I use it?

Search boxes, product and SKU lookup, address autocomplete, and command palettes.

What can go wrong?

  • Memory blows up. Cap the size of top-K and remove rare prefixes.
  • Uneven shards — one shard gets far more traffic. Shard by prefix ranges, and split a range when its load is high.
  • Offensive or old suggestions. Use filter lists, and add a small real-time layer for trending queries.
  • Calling the server on every keystroke without debounce and client caching. This multiplies the load.

Interview questions

Q1. How do you make suggestions fast? Keep a trie in memory with the top-K precomputed at each node. Add edge and client caching, and debounce requests so you don't call on every keystroke.

Q2. How do you keep suggestions fresh? Rebuild from the logs in regular batches, and merge in a small real-time trending layer at query time.

13.11 Metrics and Logging Pipeline

Why?

In simple words: Thousands of services send a flood of numbers and logs. You catch the flood in Kafka, store it in a column-based database like ClickHouse, keep pre-summed totals for dashboards, and move old data to cheap storage.

Functional (what it must do):

  • Collect events, metrics and logs from thousands of services and devices.
  • Query totals and averages over time and by dimensions (tenant, service, region…).
  • Show dashboards.
  • Raise alerts.
  • Apply retention policies — delete data after a set time.

Non-functional (how well it must do it):

  • Take in 1M events per second.
  • Query billions of rows in seconds.
  • Keep the cost low.

This question tests streaming ingestion, columnar storage and tiering (hot vs cold storage). It is a strong question for you because of your ClickHouse and Trino experience.

What is happening internally?

Agents/SDKs (batch + compress) → ingestion gateway (auth, rate limits) → Kafka (partition by tenant/service)
  → stream processors (validation, enrichment, pre-aggregation, downsampling)
  → ClickHouse (MergeTree: PARTITION BY day, ORDER BY (tenant, metric, timestamp)); materialised views for rollups
  → object storage (Parquet) for raw and cold data, queried with Trino
Query service → Grafana dashboards ; alerting service evaluates rules on rollups

The flow:

  1. Agents and SDKs on each service collect data, batch it and compress it.
  2. An ingestion gateway checks auth and applies rate limits.
  3. Data goes into Kafka, partitioned by tenant or service.
  4. Stream processors validate it, enrich it (add extra fields), pre-aggregate it (sum it up early) and downsample it (keep fewer points for old data).
  5. Data lands in ClickHouse, in a MergeTree table with PARTITION BY day and ORDER BY (tenant, metric, timestamp). Materialised views keep the rollups (summary tables).
  6. Raw and cold data also goes to object storage as Parquet files, and you query it with Trino.
  7. A query service feeds Grafana dashboards. An alerting service checks rules against the rollups.

How does it work?

  • Kafka absorbs bursts. It sits between the producers and storage, so a sudden spike doesn't crash the database. Producers and storage don't depend on each other's speed.
  • Batch inserts — thousands of rows per insert — keep ClickHouse efficient. It hates many tiny inserts.
  • Materialised views keep per-minute and per-hour rollups up to date at the moment data is inserted. So dashboards never need to sum raw data.
  • TTL rules move data from fast SSD (hot, 7 days) to cheap object storage (cold), and delete it when the retention period ends.

Example

Query: "p99 latency of the redemption API per tenant over the last 24 hours". (p99 = the time within which 99% of requests finished.)

It is served from a per-minute rollup table — about 1,440 rows per tenant. It takes tens of milliseconds. Without the rollup, you would scan a billion raw events.

When would I use it?

Observability platforms, product analytics, IoT telemetry, and audit-event analytics.

What can go wrong?

  • High-cardinality labels. Cardinality means the number of distinct values. If you use user IDs as metric tags, you get millions of separate series, and storage explodes.
  • Too many small inserts. ClickHouse slows down badly.
  • Late-arriving data. Some events arrive after their time window has been summed. Use watermarks (a marker of "how late we still accept data") and re-aggregation windows.
  • One noisy tenant fills up ingestion for everyone. Use per-tenant quotas.
  • Dashboards that query raw data instead of rollups — slow and expensive.

Interview questions

Q1. Why a columnar store for metrics and logs? Queries read only a few columns, but across huge time ranges. A columnar store reads just those columns, compresses them well and scans them in vectorised batches (many values at once). So these aggregations are fast and cheap.

Q2. How do you handle 10× traffic bursts? Kafka buffers the burst. Consumers scale up based on lag (how far behind they are). Ingestion applies per-tenant rate limits and sampling.

13.12 Distributed Job Scheduler (cron at scale)

Why?

In simple words: You have millions of jobs that must run at set times, and several scheduler machines. Each machine picks up a batch of due jobs inside a database lock, so no two machines take the same job. Each job run has a unique ID, so if it is delivered twice, the second copy does nothing.

Almost every product has work that must happen at a time, not on a user click:

  • Expire loyalty points every night at 02:00 for each tenant.
  • Send "your offer ends tomorrow" reminders.
  • Run end-of-month incentive payouts.
  • Retry a failed webhook in 10 minutes.

On one server, a Spring @Scheduled method or Linux cron is enough. At scale it breaks:

  • If that one server is down at 02:00, the job never runs.
  • If you run three copies of the service, the job runs three times.
  • One server cannot run 10 million jobs per day on time.

So you need a distributed job scheduler: a service that stores jobs, decides when each one is due, and makes sure each due run happens — on time, once in effect, even when machines crash.

Functional requirements (what it must do):

  1. Create a job: one-time ("run at 2026-10-05 10:00") or repeating (a cron expression like 0 2 * * * plus a time zone).
  2. Run each job at its time.
  3. Retry failed runs with backoff (waiting longer after each failure).
  4. Keep a history of runs: status, start, end, error.
  5. Pause, resume, cancel and "run now".

Non-functional requirements (how well it must do it):

  • No missed runs and no double effects. Delivery is at-least-once (every run happens, rarely twice); jobs are written so a repeat does no harm. Together this gives effectively once.
  • On time: start within a few seconds of the due time.
  • Scale: 10 million job definitions, peaks of many thousands of runs per second (everyone schedules at midnight).
  • No single point of failure: losing any one machine must not stop scheduling.

Back-of-envelope estimate (say these numbers aloud in the interview):

  • 10M jobs, average 3 runs/day → 30M runs/day ÷ ~10⁵ s/day ≈ 300 runs/s average.
  • Peaks are the real problem. If 20% of jobs are due at exactly 00:00, that is 2M runs in one minute ≈ 33,000 runs/s for a minute.
  • Storage: a job row ≈ 500 bytes → 10M × 500 B = 5 GB. A run-history row ≈ 200 bytes → 30M/day × 200 B = 6 GB/day; keep 30 days hot (~180 GB), archive the rest.

So the database for definitions is small. The hard parts are finding due jobs fast, spreading the peak, and never running a job twice in effect.

This question tests coordination between machines, idempotency (safe to repeat), time handling and failure thinking.

What is happening internally?

The design separates deciding when (scheduler) from doing the work (workers). A queue sits between them.

 Clients ──►│ Job API      │──────────────────────────┐

The two main tables:

CREATE TABLE jobs (
  job_id        BIGINT PRIMARY KEY,
  tenant_id     BIGINT       NOT NULL,
  name          TEXT         NOT NULL,
  schedule_type TEXT         NOT NULL,          -- 'ONCE' or 'CRON'
  cron_expr     TEXT,                           -- e.g. '0 2 * * *'
  time_zone     TEXT         NOT NULL,          -- e.g. 'Asia/Kolkata' (never store a fixed offset)
  payload       JSONB        NOT NULL,          -- what the worker needs: handler name + arguments
  status        TEXT         NOT NULL,          -- ACTIVE, PAUSED, CANCELLED, DONE
  next_run_at   TIMESTAMPTZ,                    -- next fire time in UTC; NULL when nothing is due
  misfire_policy TEXT        NOT NULL DEFAULT 'RUN_ONCE',  -- RUN_ONCE, RUN_ALL, SKIP
  max_attempts  INT          NOT NULL DEFAULT 5,
  timeout_sec   INT          NOT NULL DEFAULT 900,
  version       BIGINT       NOT NULL DEFAULT 0  -- optimistic locking for API edits
);
-- partial index: only active jobs, ordered by time -> "what is due?" is a cheap index range scan
CREATE INDEX idx_jobs_due ON jobs (next_run_at) WHERE status = 'ACTIVE';

CREATE TABLE job_runs (
  execution_id  TEXT PRIMARY KEY,               -- job_id + '@' + scheduled_for  (idempotency key)
  job_id        BIGINT       NOT NULL,
  scheduled_for TIMESTAMPTZ  NOT NULL,
  attempt       INT          NOT NULL,
  status        TEXT         NOT NULL,          -- QUEUED, RUNNING, SUCCEEDED, FAILED, DEAD
  worker_id     TEXT,
  lease_until   TIMESTAMPTZ,                    -- worker must heartbeat before this
  started_at    TIMESTAMPTZ, finished_at TIMESTAMPTZ, error TEXT
);

Key ideas in this layout:

  • next_run_at is always stored in UTC. The cron expression and time zone are used only to calculate it. So the "is it due?" check is a simple number comparison.
  • The partial index contains only ACTIVE jobs, sorted by time. Finding due jobs is like opening a register at today's page — you never scan paused or finished jobs.
  • execution_id is UNIQUE. The same scheduled slot can never create two run rows. This is the idempotency key the worker checks.

How does it work?

A. The scheduler loop (every scheduler node runs this, every ~1 second):

BEGIN;
SELECT job_id, cron_expr, time_zone, next_run_at
FROM   jobs
WHERE  status = 'ACTIVE' AND next_run_at <= now()
ORDER  BY next_run_at
LIMIT  500
FOR UPDATE SKIP LOCKED;            -- rows locked by another scheduler are skipped, not waited on

-- for each row:
INSERT INTO job_runs (execution_id, job_id, scheduled_for, attempt, status)
VALUES ('42@2026-10-03T20:30:00Z', 42, '2026-10-03T20:30:00Z', 1, 'QUEUED')
ON CONFLICT (execution_id) DO NOTHING;            -- already created? do nothing
UPDATE jobs SET next_run_at = <next fire time after the current one> WHERE job_id = 42;
COMMIT;
-- after commit: publish the run to the queue (or use an outbox table so publish can't be lost - see 11.15)

Step by step:

  1. Open a transaction and lock up to 500 due rows. SKIP LOCKED means scheduler 2 does not wait for scheduler 1's rows — it simply takes the next free rows. Three schedulers get three different batches.
  2. For each job, create a run row. The execution_id is job_id@scheduled_time.
  3. Move next_run_at forward to the next fire time. Now the job is no longer "due", so no one else can pick this slot.
  4. Commit. Steps 2 and 3 happen together or not at all. If the scheduler crashes before commit, the locks are released and another scheduler picks the same rows a second later. Nothing is lost.
  5. Publish each run to the queue. To make "DB change + publish" safe, write the message to an outbox table in the same transaction and let a relay publish it (11.15).

Think of a railway parcel office with three clerks and one big register sorted by delivery time. Each clerk takes a pencil, marks the next free lines as "mine", writes a delivery slip for each and moves the line's date to its next delivery. A clerk never touches lines another clerk has marked.

B. Computing the next run time (time zones and DST).

  • Parse the cron expression in the job's own time zone, then convert the result to UTC. In Spring: CronExpression.parse("0 0 2 * * *").next(ZonedDateTime.now(zone)).
  • DST gap (clocks jump 02:00 → 03:00): a 02:30 job has no 02:30 that night. Java's atZone moves it forward to 03:30. Decide and document that policy.
  • DST overlap (clocks go back, 01:30 happens twice): run once, at the first occurrence.
  • India has no DST, but your global tenants do. Always store the zone name (America/New_York), never a fixed offset (-05:00).

C. Workers: leases, heartbeats and idempotency.

  1. A worker takes a run from the queue.
  2. It updates the run row: status = RUNNING, worker_id = me, lease_until = now() + 60s. This is a lease — "I own this run for 60 seconds".
  3. While working, it renews the lease every ~20 seconds (a heartbeat).
  4. If the worker dies, heartbeats stop and the lease expires. A reaper (a small background task) finds RUNNING runs with expired leases and puts them back on the queue.
  5. Because a run can be delivered twice (queue redelivery, reaper, retry), the job's own work must be idempotent. Example: the points-expiry handler writes INSERT ... ON CONFLICT (execution_id, account_id) DO NOTHING, so a second run changes nothing. For long jobs, save a checkpoint (e.g. last processed account ID) so a retry continues instead of starting over.

D. Retries and the dead-letter queue.

  • On failure: if attempt < max_attempts, re-queue with delay = base × 2^attempt plus random jitter (so 10,000 failed jobs don't all retry in the same second).
  • After the last attempt: mark the run DEAD, send it to a DLQ (dead-letter queue) and alert the job owner. A human fixes the cause and clicks "replay".
  • Retry only errors that can heal (timeouts, 503s). A validation error will fail every time — send it to DLQ immediately.

E. Missed runs after downtime (misfire policy).

Suppose the whole system was down from 01:00 to 05:00. An hourly job missed four slots. When it comes back, next_run_at is in the past. What should happen? This is the misfire policy, chosen per job:

Policy Behaviour Use it for
RUN_ONCE (default) Run one catch-up now, then continue the normal schedule Cleanup, expiry, sync jobs — one run catches up everything
RUN_ALL Run every missed slot, in order Billing or reports per period, where each slot is its own result
SKIP Ignore missed slots, wait for the next one Reminders and notifications — a 2-hour-late "good morning" is worse than none

F. Handling the midnight peak and scaling to millions of jobs.

  1. Jitter at create time. For jobs that don't need an exact time ("daily cleanup"), store a random offset in next_run_at (say 0–10 minutes). The 00:00 spike becomes a gentle 10-minute hill.
  2. Pre-load the near future. A loader moves jobs due in the next ~5 minutes from the DB into a fast in-memory structure — a Redis sorted set (score = due time, ZRANGEBYSCORE to pop due ones) or a timing wheel (a ring of time buckets, like a clock face with a bucket per second). The DB is touched once per job per window, not every second.
  3. Partition the work. Split jobs into, say, 256 buckets by hash(job_id) % 256. Each scheduler node holds a lease on a set of buckets (stored in the DB, ZooKeeper or etcd). If a node dies, its bucket leases expire and other nodes take them over. Within a bucket, ordering by time is local and cheap.
  4. Separate queues by priority or tenant. One tenant scheduling a million jobs must not delay everyone else. Give each priority (or large tenant) its own topic, and cap concurrency per tenant (fairness).
  5. Scale workers independently of schedulers — workers do the heavy lifting; autoscale them on queue lag.

G. What to monitor.

  • Schedule lag: now − scheduled_for when a run starts. This is the main health number; alert if p99 > 30 s.
  • Queue lag (messages waiting), runs per second, failure rate per job type, DLQ size, number of expired leases.

Daily points expiry for 1,000 tenants at 02:00 IST, with three scheduler nodes. The code below is a single-file simulation of the core ideas: DST-safe next-run calculation, atomic claiming by several nodes, at-least-once delivery with duplicates, idempotent execution, retries and a dead-letter queue. // FILE: SchedulerDemo.java
import java.time.*;
import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.*;

public class SchedulerDemo {

    // ---- 1. Job definition and execution record ----
    enum ExecStatus { CLAIMED, RUNNING, SUCCEEDED, FAILED, DEAD }

    static final class Job {
        final String id; final LocalTime runAt; final ZoneId zone; final int maxAttempts;
        Instant nextRunAt;                       // UTC instant of the next fire time
        Job(String id, LocalTime runAt, ZoneId zone, int maxAttempts, Instant firstRun) {
            this.id = id; this.runAt = runAt; this.zone = zone; this.maxAttempts = maxAttempts; this.nextRunAt = firstRun;
        }
    }

    record Execution(String executionId, String jobId, Instant scheduledFor, int attempt) {}

    // ---- 2. "Daily at HH:mm in a time zone" -> next UTC instant (DST-safe) ----
    static Instant nextDailyRun(LocalTime at, ZoneId zone, Instant after) {
        LocalDate day = after.atZone(zone).toLocalDate();
        for (int i = 0; i < 3; i++) {
            // atZone() moves a time that falls in a DST gap forward, and picks the earlier offset in an overlap
            Instant candidate = day.plusDays(i).atTime(at).atZone(zone).toInstant();
            if (candidate.isAfter(after)) return candidate;
        }
        throw new IllegalStateException("unreachable");
    }

    // ---- 3. Job store: claim due jobs atomically ----
    // `synchronized` stands in for the database transaction with SELECT ... FOR UPDATE SKIP LOCKED:
    // pick due rows, create one execution per row, move next_run_at forward, commit.
    static final class JobStore {
        private final Map<String, Job> jobs = new ConcurrentHashMap<>();
        void add(Job j) { jobs.put(j.id, j); }

        /** Atomically claim up to `limit` due jobs. A claimed job is no longer due, so no other node sees it. */
        synchronized List<Execution> claimDue(String node, Instant now, int limit) {
            List<Execution> claimed = new ArrayList<>();
            jobs.values().stream()
                .filter(j -> !j.nextRunAt.isAfter(now))
                .sorted(Comparator.comparing(j -> j.nextRunAt))
                .limit(limit)
                .forEach(j -> {
                    String execId = j.id + "@" + j.nextRunAt;                      // idempotency key
                    claimed.add(new Execution(execId, j.id, j.nextRunAt, 1));
                    j.nextRunAt = nextDailyRun(j.runAt, j.zone, j.nextRunAt);       // advance in the same "transaction"
                });
            return claimed;
        }
        Job get(String id) { return jobs.get(id); }
    }

    // ---- 4. Worker side: idempotent execution + retry with backoff + dead-letter queue ----
    static final Set<String> doneExecutions = ConcurrentHashMap.newKeySet(); // "processed executions" table
    static final List<String> deadLetters = Collections.synchronizedList(new ArrayList<>());
    static final AtomicInteger realRuns = new AtomicInteger(), retries = new AtomicInteger();

    static void execute(Execution e, JobStore store, BlockingQueue<Execution> queue, Set<String> flakyJobs) {
        if (doneExecutions.contains(e.executionId())) return;          // duplicate delivery -> no-op
        boolean ok = !(flakyJobs.contains(e.jobId()) && e.attempt() < 3); // flaky jobs succeed on attempt 3
        if (e.jobId().equals("broken")) ok = false;                      // always fails
        if (ok) {
            if (doneExecutions.add(e.executionId())) realRuns.incrementAndGet();
            return;
        }
        int max = store.get(e.jobId()).maxAttempts;
        if (e.attempt() >= max) { deadLetters.add(e.executionId()); return; }
        long backoffMs = (long) Math.pow(2, e.attempt()) * 100;         // 200, 400, 800 ms ... (simulated)
        queue.add(new Execution(e.executionId(), e.jobId(), e.scheduledFor(), e.attempt() + 1));
        retries.incrementAndGet();   // a real system waits backoffMs (plus jitter) before redelivery
    }

    public static void main(String[] args) throws Exception {
        ZoneId ist = ZoneId.of("Asia/Kolkata"), ny = ZoneId.of("America/New_York");

        // DST check: "daily at 02:30 New York" on the night clocks jump 02:00 -> 03:00 (8 March 2026)
        Instant beforeGap = ZonedDateTime.of(2026, 3, 7, 12, 0, 0, 0, ny).toInstant();
        Instant r1 = nextDailyRun(LocalTime.of(2, 30), ny, beforeGap);
        Instant r2 = nextDailyRun(LocalTime.of(2, 30), ny, r1);
        System.out.println("NY 02:30 job, run 1: " + r1.atZone(ny) + "  (02:30 does not exist that night)");
        System.out.println("NY 02:30 job, run 2: " + r2.atZone(ny));
        System.out.println("IST 02:00 job fires at UTC: " + nextDailyRun(LocalTime.of(2, 0), ist, Instant.parse("2026-10-03T00:00:00Z")));

        // 1,000 tenant jobs due "now", 3 scheduler nodes racing to claim them
        JobStore store = new JobStore();
        Instant now = Instant.parse("2026-10-03T20:30:00Z");
        for (int i = 1; i <= 1000; i++) store.add(new Job("tenant-" + i, LocalTime.of(2, 0), ist, 4, now));
        store.add(new Job("broken", LocalTime.of(2, 0), ist, 3, now));
        Set<String> flaky = Set.of("tenant-7", "tenant-42");

        BlockingQueue<Execution> queue = new LinkedBlockingQueue<>();
        Map<String, Integer> claimedBy = new ConcurrentHashMap<>();
        ExecutorService schedulers = Executors.newFixedThreadPool(3);
        for (int n = 1; n <= 3; n++) {
            String node = "sched-" + n;
            schedulers.submit(() -> {
                List<Execution> batch;
                while (!(batch = store.claimDue(node, now, 50)).isEmpty()) {
                    for (Execution e : batch) { claimedBy.merge(e.executionId(), 1, Integer::sum); queue.add(e); }
                }
            });
        }
        schedulers.shutdown(); schedulers.awaitTermination(10, TimeUnit.SECONDS);
        long doubleClaims = claimedBy.values().stream().filter(c -> c > 1).count();
        System.out.println("executions claimed: " + claimedBy.size() + ", claimed twice: " + doubleClaims);

        // Simulate the queue delivering 5 messages twice (at-least-once delivery)
        List<Execution> firstFive = new ArrayList<>(queue).subList(0, 5);
        queue.addAll(firstFive);

        ExecutorService workers = Executors.newFixedThreadPool(8);
        while (!queue.isEmpty()) {
            List<Execution> drained = new ArrayList<>(); queue.drainTo(drained);
            CountDownLatch latch = new CountDownLatch(drained.size());
            for (Execution e : drained) workers.submit(() -> { try { execute(e, store, queue, flaky); } finally { latch.countDown(); } });
            latch.await();
        }
        workers.shutdown();

        System.out.println("real runs: " + realRuns.get() + " (1000 tenants, duplicates ignored)");
        System.out.println("retries: " + retries.get() + ", dead letters: " + deadLetters);
        System.out.println("tenant-1 next run: " + store.get("tenant-1").nextRunAt.atZone(ist));
    }
}

Interview questions

Q1. How do you ensure a job runs once even with multiple scheduler nodes? Two layers. First, claiming is atomic: schedulers select due rows with FOR UPDATE SKIP LOCKED (or own partitions through leases), create the run and move next_run_at forward in the same transaction — so a slot can be claimed only once. Second, delivery is still at-least-once (queue redelivery, worker crashes), so each run has an execution_id = job + scheduled time with a UNIQUE constraint, and handlers are idempotent. Together: effectively once.

Q2. How do you scale to millions of near-term jobs? Keep definitions in a DB with a partial index on next_run_at. Partition jobs into buckets by hash and give each scheduler a lease on some buckets. Pre-load jobs due in the next few minutes into a Redis sorted set or a timing wheel so the DB is not polled every second. Publish runs to a queue and scale workers separately based on queue lag. Spread fixed-time peaks with jitter.

Q3. A worker picks up a job and dies halfway. What happens? The worker holds a lease on the run and renews it with heartbeats. When it dies, the lease expires; a reaper finds the run and re-queues it as the next attempt. Because the handler is idempotent and saves checkpoints, the retry continues safely without double effects.

Q4. The whole system was down for 4 hours. What happens to jobs that should have run? Their next_run_at is in the past, so they are due immediately. The per-job misfire policy decides: run once to catch up (cleanup jobs), run every missed slot (per-period billing), or skip to the next slot (time-sensitive notifications). Also throttle the catch-up so the backlog doesn't overload downstream systems.

Q5. How do you handle time zones and daylight saving time? Store the IANA zone name with the job and always store next_run_at in UTC. Compute the next time with the cron expression in the job's zone, then convert to UTC. Define policy for the DST gap (move forward) and overlap (run at the first occurrence) and test both dates.

Q6. Why put a queue between schedulers and workers? It separates "when" from "how". Schedulers stay small and fast; workers can be slow, many and autoscaled. The queue absorbs peaks, gives retries and a DLQ, and lets you route jobs by priority or tenant. Without it, a slow job would block the scheduler loop and delay every other job.

Q7. When would you not build this, and use something off the shelf? For a few fixed jobs in one service, @Scheduled + ShedLock or a Kubernetes CronJob is enough. For long multi-step workflows, Temporal; for data pipelines with dependencies, Airflow; for clustered Java scheduling at moderate scale, Quartz. Build your own when you need millions of user-defined, multi-tenant schedules with custom misfire, fairness and retry policies.

13.13 Ride Matching and Nearby Search (Uber, delivery partner assignment)

Why?

In simple words: Keep every driver's latest location in memory, grouped into map cells. When a rider asks, look in nearby cells, rank drivers by real travel time, and lock one driver before offering the ride so two riders never get the same driver.

Functional (what it must do):

  • Drivers send their location every few seconds.
  • Riders request rides.
  • Match the nearest suitable driver who is free.
  • Track the trip.

Non-functional (how well it must do it):

  • Match within 1–2 seconds.
  • Handle a huge rate of location writes.
  • High availability for each city.

This question tests geo-indexing (searching by location), keeping hot state in memory, atomic assignment (all-or-nothing, so no clash) and partitioning by city. (The LLD version is in 10.17.)

What is happening internally?

Estimates: 1M active drivers × 1 update every 4 s = 250k writes per second. This is too many for a disk database. So keep current locations in memory.

A geo index is a structure that quickly answers "who is near this point?". The main options:

Geo index Idea Notes
Geohash Turn lat/lng into a base32 string; a longer shared prefix ≈ closer together Redis GEO (GEOADD, GEOSEARCH); at cell edges, also check the neighbouring cells
Quadtree Keep splitting busy areas into four smaller boxes Adjusts to how crowded an area is; in-memory
H3 / S2 Hexagon cells / cells on a sphere Every neighbour is the same distance away; good for surge pricing per cell 
Driver app → location service (WebSocket/UDP) → in-memory geo index per city shard (Redis GEO or custom)
                                              └→ Kafka location stream → trip tracking, ETA, analytics
Rider request → matching service: candidates in nearby cells (expand rings until K found)
   → rank by ETA (routing engine), rating, acceptance probability → offer to driver (10–15 s timeout)
   → atomic reserve (AVAILABLE → OFFERED) to prevent double assignment → accept → trip ACCEPTED
Trip service (state machine, Postgres) · Pricing service (surge per H3 cell from supply/demand)

The flow:

  1. The driver app sends locations (over WebSocket or UDP) to the location service.
  2. The location service updates an in-memory geo index for that city's shard (Redis GEO or a custom index).
  3. It also writes the location stream to Kafka, for trip tracking, ETA and analytics.
  4. A rider request goes to the matching service. It finds candidates in nearby cells. If it doesn't find K drivers, it expands outward ring by ring.
  5. It ranks candidates by ETA (from a routing engine), rating and how likely they are to accept.
  6. It atomically reserves the top driver: AVAILABLE → OFFERED. This prevents double assignment.
  7. It offers the ride, with a 10–15 s timeout.
  8. If the driver accepts, the trip becomes ACCEPTED.
  9. The trip service keeps the trip's state machine in Postgres. The pricing service sets surge per H3 cell, based on supply and demand.

How does it work?

  1. A request comes in.
  2. Search nearby — about 1 km first, then wider if needed.
  3. Pick the top candidates by ETA.
  4. Reserve the first one atomically.
  5. Send the offer.
  6. If the driver declines or the timer runs out, release them and try the next one.
  7. When a driver accepts, create the trip and notify the rider.

Example

A rider in Gurugram Sector 29 requests a ride:

  1. Search the rider's H3 cell plus 1 ring around it → 14 free drivers.
  2. Rank them by ETA using the routing service.
  3. Driver D7 (3 min away) is reserved and offered the ride. D7 declines.
  4. Driver D2 (4 min away) is reserved next, and accepts within 6 s.
  5. The trip is created.

When would I use it?

Ride-hailing, assigning food and grocery delivery partners (13.18), assigning field-force visits and planning routes (related to your Route Optimization product), and any "find what's near me" search.

What can go wrong?

  • Double assignment if you don't reserve the driver atomically.
  • Using straight-line distance instead of road ETA. A driver across a river may look close but be 20 minutes away.
  • GPS noise. Snap locations to the nearest road.
  • Hot cells at big events — too many people in one cell. Use smaller cells and surge pricing.
  • Queries that cross cities. Partition by city to avoid them.

Interview questions

Q1. How do you find nearby drivers efficiently? Keep a geo index (geohash, H3 or quadtree) of current locations in memory. Search the rider's cell first, then the rings of neighbouring cells.

Q2. How do you prevent two riders getting the same driver? Change the driver's status atomically before sending the offer — with Redis SET NX, CAS (compare-and-set), or a conditional update. Release the driver if they decline or the offer times out.

Q3. How would you handle 250k location updates per second? Keep only the latest location per driver, in memory, sharded by city. Write the stream to Kafka for history. Avoid a synchronous DB write for each update.

13.14 Incentive Engine at Scale (your system)

Why?

In simple words: Field reps earn bonuses for hitting targets. Show them their progress quickly using live streaming numbers, but calculate the actual money carefully, at month end, from the original data.

Functional requirements (what the system must do):

  • Tenants (client companies) define incentive schemes for field reps and distributors, per period. A scheme sets targets on sales, visits, coverage or focus SKUs (products the company wants to push).
  • Show live progress towards each target.
  • Calculate payouts when the period closes.
  • Explain how each result was calculated.
  • Handle data that arrives late or gets corrected.

Non-functional requirements (how well it must do it):

  • 700+ tenants and hundreds of thousands of users.
  • Progress must be fresh within a few minutes.
  • Payouts must be exactly correct and auditable (anyone can check how they were reached).
  • Heavy load at month end.

This question tests streaming vs batch processing, rules engines (10.12), versioning, and multi-tenant fairness — making sure one big client cannot slow down everyone else.

What is happening internally?

The flow, top to bottom:

  1. Source events (orders, visits, new outlets) are captured with CDC (Change Data Capture — reading every change from the database log) or app events, and sent to Kafka.
  2. A stream job keeps running counters per (tenant, user, period, metric). It stores them as aggregates in Postgres or ClickHouse.
  3. The scheme evaluation service (a rules engine) re-checks a user when a metric changes, or every N minutes. It reads the versioned scheme definitions (cached), walks the condition tree and saves a progress snapshot.
  4. A cached progress API serves mobile dashboards and leaderboards (13.9).
  5. At period close, the system freezes the data cut-off. Then a batch job recalculates every user from the source of truth.
  6. This produces payout records in a ledger. They go through a maker-checker approval (one person prepares, another approves). Then they are exported to payroll or a wallet.
Sources (orders, visits, outlet onboarding) → CDC/events → Kafka
  → metric aggregation (stream): per (tenant, user, period, metric) counters → Postgres/ClickHouse aggregates
  → scheme evaluation service (rules engine): on metric change or every N minutes per user
        reads versioned scheme definitions (cached) → evaluates the condition tree → writes a progress snapshot
  → progress API (cached) → mobile dashboards, leaderboards (13.9)
Period close: freeze the data cut-off → recompute every user from the source of truth (batch)
  → payout records (ledger) → approval workflow (maker-checker) → payroll/wallet export

How does it work?

  • Streaming for progress, batch for money. Small, quick updates (incremental updates) keep the app responsive. But at period close, a full batch recalculation is the final, official answer. It correctly includes late and corrected data.
  • Rule versioning. A period is always evaluated with the scheme version that was active when the period started. Editing a scheme creates a new version; it does not overwrite the old one.
  • Idempotent, re-runnable payouts. Idempotent means running it twice gives the same result as running it once. Each payout is keyed by (scheme, user, period, version). A re-run replaces draft payouts, and it never creates a duplicate of an approved payout.
  • Explainability. The evaluation trace (the step-by-step record of how the rules were checked) is saved with each payout.
  • Fairness. Each tenant gets its own queue and quota. So one large tenant's recalculation cannot starve the others.

Think of a school exam. During the term, you see your running marks on a notice board — quick but rough. The final report card is made carefully at the end, from the actual answer sheets.

Example

  1. By the 20th, a rep has sold ₹62,000 of focus SKUs.
  2. The progress card shows 124% of target, and "4 more new outlets to reach the next slab".
  3. On the 28th, an order is returned. An event reduces the rep's sales.
  4. At period close, the batch job recalculates from the source data.
  5. The payout uses the corrected figure. The trace is attached, so the rep's manager can see exactly how it was calculated.

When would I use it?

Any calculation driven by rules over summed-up activity. Examples: sales incentives and commissions, loyalty tier evaluation, SLA and bonus calculations, gamification.

What can go wrong?

  • Paying from streaming counters. Counters drift because of duplicate events or late data. Fix: recalculate from the source at close.
  • Editing rules mid-period without versions. Fix: version every scheme change.
  • Evaluating on raw transaction tables for every request. This is too slow. Fix: pre-aggregate (keep summed-up totals ready).
  • Month-end load spikes. Fix: autoscale and partition work by tenant.
  • Payouts nobody can explain. This creates a big support burden. Fix: store the trace.

Interview questions

Q1. Why both streaming and batch? Streaming gives users timely progress. Batch over the source of truth guarantees payouts that are correct and can be reproduced, even when data arrives late or gets corrected.

Q2. How do you handle a scheme changed mid-month? I version the scheme definitions. Each period is evaluated with the version that was effective for it. I also show users which version applies to them.

13.15 Instagram (photo sharing + feed)

Why?

In simple words: The phone uploads the photo straight to cloud storage, background workers make smaller copies, and a CDN serves those copies from servers near the user. The feed is the same feed design as 13.4.

Functional requirements:

  • Upload photos and short videos with captions.
  • Follow users.
  • Home feed.
  • Likes and comments.
  • Profile grid.
  • Stories that expire after 24 hours.

Non-functional requirements:

  • 500M DAU (daily active users).
  • Feed loads in under 200 ms.
  • Uploads are visible within seconds.
  • Read-heavy: far more viewing than posting.
  • Media delivered fast all over the world.

It tests the media pipeline, plus the feed design (13.4).

What is happening internally?

Estimates:

  • 100M uploads a day ≈ 1,200 uploads per second.
  • About 3 MB per upload, including resized versions → about 300 TB of media a day.
  • Feed reads: about 115k QPS (queries per second).
  • About 100 GB of metadata a day.
Client → POST /media/upload-url → media service returns a PRE-SIGNED URL
Client → PUT bytes directly to object storage            (app servers never proxy large files)
Storage event → Kafka media.uploaded → processing workers: virus scan, EXIF strip, resize (thumb/320/640/1080), WebP/AVIF, video transcode
Client → POST /posts {mediaIds, caption} → post service → posts DB (sharded by post_id) → PostCreated
PostCreated → feed fan-out (hybrid, 13.4) · hashtag/search indexer · notifications

In plain steps:

  1. The client asks the media service for an upload URL. It gets a pre-signed URL — a temporary link that allows uploading one file straight to storage.
  2. The client uploads the bytes directly to object storage. App servers never pass large files through themselves.
  3. Storage fires an event to Kafka. Processing workers scan for viruses, strip EXIF data (hidden photo info like GPS location), resize to several sizes, convert to WebP/AVIF, and transcode videos.
  4. The client creates the post with the media IDs and caption. The post service saves it (sharded by post_id) and publishes PostCreated.
  5. PostCreated triggers feed fan-out (hybrid, 13.4), the hashtag/search indexer and notifications.
  6. On reads, the CDN serves all media. The feed returns post IDs, which are filled in with details from the post cache (hydration). Media URLs point to the CDN.

Data:

  • Follows: follower_id, followee_id, indexed in both directions.
  • Posts: keyed by post_id, plus a user_id → post_ids timeline for profile grids.
  • Likes: sharded counters (one count split across several keys), plus a likes(post_id, user_id) table.
  • Comments: partitioned by post_id.
  • Stories: in a TTL store (a store where each item has an expiry time and is deleted automatically).

How does it work?

Upload:

  1. The client gets a pre-signed URL.
  2. It uploads directly to storage.
  3. Processing creates the size variants in the background (asynchronously).
  4. Post creation refers to the media IDs.
  5. Fan-out delivers the post to followers' feeds.

Read:

  1. Get the feed post IDs.
  2. Hydrate them (fill in details).
  3. Return CDN URLs. The client picks the image size that fits its screen.

Example

  1. A user posts a 4 MB photo.
  2. The direct upload to Blob storage takes 1.5 s on 4G.
  3. Processing creates 4 sizes in 2 s.
  4. The post appears in followers' feeds within about 3 s.
  5. 95% of image bytes are served from the CDN edge (servers close to the user).

When would I use it?

Any platform where users upload media. Also product catalogues with images, and Perfect Store photo audits. The pattern is the same: direct upload + background processing + CDN.

What can go wrong?

  • Passing uploads through app servers. This chokes them.
  • Processing synchronously. The post is blocked until processing ends.
  • Hot posts overwhelming counters. Fix: shard the counters and cache them.
  • Privacy. Private accounts must be checked during hydration.
  • Stories not expiring. Fix: use a TTL.

Interview questions

Q1. How do you handle uploads at scale? Clients upload directly to object storage using pre-signed URLs. Storage events trigger background processing pipelines. Metadata goes into the database, and the media is delivered through a CDN.

Q2. How do you count likes on a viral post? I use sharded counters in Redis and add them up into the database from time to time. A separate likes table answers "did I like it?".

13.16 YouTube / Netflix (video upload and streaming)

Why?

In simple words: Chop each video into small pieces, convert every piece into many qualities in parallel, and let the player pick a quality for each piece based on how fast the internet is right now.

Functional requirements:

  • Upload videos.
  • Transcode them (convert them) into several resolutions.
  • Stream with adaptive bitrate — the quality changes automatically with network speed.
  • Search.
  • View counts.

Non-functional requirements:

  • Videos start fast and rarely pause to buffer (rebuffer), all over the world.
  • Processing is allowed to take minutes.
  • Huge storage, and huge egress (data sent out to viewers).

It tests large-file pipelines, parallel transcoding and CDN strategy.

What is happening internally?

Estimates:

  • 500 hours of video uploaded every minute.
  • 1 hour of 1080p ≈ 2–3 GB.
  • All the versions (renditions) together ≈ 2× the original. So petabytes of new storage are needed every day.
  • Playback egress is the biggest cost. So the CDN carries about 95%+ of the bytes.
Upload: resumable chunked upload (pre-signed URLs, e.g. 8 MB parts) → object storage (originals)
   → video.uploaded → transcoding DAG: split into segments → parallel encode per segment × resolution (240p…4K) × codec (H.264/VP9/AV1)
   → package HLS/DASH (2–6 s segments + manifests) → thumbnails, captions → store renditions → metadata READY → notify
Playback: Video API (metadata, manifest URL, signed CDN token) → CDN edge serves segments
   player measures bandwidth and switches rendition per segment (adaptive bitrate)
Views: client beacons → Kafka → stream aggregation → approximate counts

In plain steps:

  1. Upload. The video is uploaded in chunks (for example 8 MB parts) using pre-signed URLs. The upload is resumable — if the network drops, it continues from where it stopped. The original goes into object storage.
  2. Transcode. A video.uploaded event starts a transcoding DAG (a directed acyclic graph — a set of tasks with a fixed order and no loops). The video is split into segments. Each segment is encoded in parallel, for each resolution (240p…4K) and each codec (H.264/VP9/AV1).
  3. Package. The output is packaged as HLS/DASH (streaming formats): 2–6 s segments plus manifests (index files that list the segments and qualities). Thumbnails and captions are made. Renditions are stored, the metadata is marked READY, and the uploader is notified.
  4. Playback. The Video API returns metadata, the manifest URL and a signed CDN token. The CDN edge serves the segments. The player measures bandwidth and switches quality per segment. This is adaptive bitrate.
  5. Views. The client sends small "I watched" pings (beacons) to Kafka. A stream job adds them up into approximate counts.

How does it work?

Segment-level parallelism. One worker encoding a 2-hour video takes a long time. Split into segments, many workers share the work, so it finishes in minutes. If one segment fails, only that segment is retried.

Adaptive bitrate.

  1. The manifest lists all available qualities (renditions).
  2. Before each segment, the player checks the measured download speed and how much video it has buffered.
  3. It picks the best quality it can safely play for that segment.

Think of a car's gears. On an open highway you shift up; in traffic you shift down. The player does the same with video quality, segment by segment.

Example

  1. Someone uploads a 10-minute 1080p video (~400 MB).
  2. The network drops at 60%. Because the upload is resumable, it continues from there.
  3. The video is split into 100 six-second segments × 5 renditions = 500 encode tasks.
  4. 200 workers process them, so it is ready in about 2 minutes.
  5. A viewer on a weak network starts at 360p. After 10 seconds, the player climbs to 720p.

When would I use it?

Video platforms, training videos for field forces, and any pipeline for large media (audio, documents).

What can go wrong?

  • Non-resumable uploads. These fail often on mobile networks.
  • Serial transcoding. Encoding one piece after another is far too slow.
  • Origin overload on viral content. Fix: pre-warm the CDN, and add an origin shield (a middle cache layer that protects the origin servers).
  • Exact view counts at huge scale. These are too costly. Fix: count approximately, and deduplicate per session.
  • Storage cost. Fix: move old videos to cold (cheaper) storage tiers, and keep fewer renditions for videos that are rarely watched.

Interview questions

Q1. How does adaptive bitrate streaming work? The video is encoded into several renditions (qualities). Each is split into short segments, listed in a manifest. The player chooses a rendition for each segment based on bandwidth and how full its buffer is.

Q2. How do you transcode quickly? Split the video into segments. Encode them in parallel across a fleet of workers, organised as a DAG. Then package and publish.

13.17 Twitter / X — what's specific beyond the generic feed

Why?

In simple words: "Design Twitter" is the normal feed design from 13.4 plus a few Twitter-only parts — special tweet IDs, fast search, and trending topics. Show you can adapt a known design to them.

When interviewers say "design Twitter", they usually expect the feed (13.4) plus Twitter-specific parts: timelines, IDs, search and trending.

It tests whether you can adapt a design you know to the details of a specific product.

What is happening internally?

  • Timelines. There are two kinds:
  • The home timeline — what you see from people you follow. It is a fan-out cache of tweet IDs per user in Redis, about 800 entries.
  • The user timeline — one user's own tweets, read from the tweet store.
  • Celebrities' tweets are not fanned out. They are merged in when you read your timeline.
  • Tweet IDs. Snowflake IDs (11.22). They are unique, roughly sorted by time, and generated without servers needing to coordinate.
  • Search. A near-real-time inverted index (a map from each word to the tweets containing it), built on Lucene, in the Earlybird style. It is fed from the tweet stream. Recent data stays in memory; older data is in larger indexes.
  • Trending. A stream job counts hashtags and terms over sliding windows (for example, the last 5 minutes, moving forward continuously), per region. It compares current counts with a baseline. What matters is velocity — how fast mentions are rising — not raw volume. A Count-Min Sketch (a small, approximate counting structure) finds the most frequent items (heavy hitters).
  • Counters. Likes and retweets use sharded counters, saved to the database in the background.

Trending is like the noise level in a stadium. A crowd that is always loud is not news. A sudden roar is.

How does it work?

  1. A tweet gets a Snowflake ID.
  2. It is saved in the tweet store.
  3. It is fanned out to followers' timelines (or skipped, for celebrities).
  4. The search indexer adds it to the index.
  5. The trending stream counts its terms.
  6. Mentioned users get notifications.

Example

  1. It is a cricket final. Mentions of "#INDvAUS" in Mumbai jump from 200/min to 40,000/min.
  2. Within 30 seconds, the trending job's velocity score spikes.
  3. The topic shows up in regional trends.
  4. Celebrity tweets reach followers through the read-time merge, so there are no fan-out storms.

When would I use it?

Social products, real-time topic detection, and any messaging system with many writes and large fan-out.

What can go wrong?

  • Fan-out storms. One tweet triggers millions of timeline writes.
  • Spam taking over trends. Fix: rate limits and quality signals.
  • Search index lag. New tweets take too long to become searchable.
  • Inconsistent counters. Fix: accept eventual consistency (counts become correct after a short delay), and reconcile them later.

Interview questions

Q1. How would you detect trending topics? A stream processor keeps sliding-window counts per term and per region. Each term is scored by how fast it is rising compared with its normal baseline. Approximate structures like Count-Min Sketch keep this cheap.

13.18 Food Delivery (Swiggy / Zomato)

Why?

In simple words: Fast search for restaurants, a careful and correct order flow, and smart timing so the delivery partner reaches the restaurant just as the food is ready — with each city handled separately.

Functional requirements:

  • Browse nearby restaurants and menus.
  • Place an order and pay.
  • The restaurant accepts and prepares the food.
  • Assign a delivery partner.
  • Live tracking and ETA (estimated time of arrival).
  • Ratings.

Non-functional requirements:

  • Discovery (browsing) in under 300 ms.
  • Ordering is strongly consistent — no lost orders and no duplicate orders.
  • A partner is assigned within seconds.
  • Lunch and dinner peaks of 5–10× normal traffic.
  • City-level isolation — a problem in one city must not affect others.

It combines search, ordering, payments, dispatch and real-time tracking.

What is happening internally?

Estimates:

  • 3M orders a day, with a dinner peak of about 300 orders per second.
  • 300k active partners, each sending location every 5 s → about 60k location writes per second.
Discovery: app → listing/search service → Elasticsearch (geo + cuisine + availability) + Redis (menus, open/closed)
Ordering:  app → cart → order service (Postgres, idempotency key) → payment (13.8) → OrderPlaced
           order state machine: PLACED → ACCEPTED → PREPARING → READY → PICKED_UP → DELIVERED (or CANCELLED + refund)
Restaurant: tablet app ◄ order push (WebSocket/FCM) → accept/reject, prep-time estimate
Dispatch:  OrderAccepted → assignment service (per city): candidates from the geo index near the restaurant (13.13)
           → score by ETA-to-restaurant vs food-ready time, partner load, batching opportunities → offer → atomic reserve
Tracking:  partner app → location service → geo index + Kafka → customer app via WebSocket/SSE (throttled updates)
ETA:       ML model (prep time + travel time + handover), re-estimated on each state change

In plain words:

  • Discovery. The app calls the listing/search service. Elasticsearch handles location, cuisine and availability. Redis holds menus and open/closed status.
  • Ordering. Cart → order service (Postgres, with an idempotency key — a unique request ID, so a repeated request does not create a second order) → payment (13.8) → OrderPlaced event.
  • Order states. PLACED → ACCEPTED → PREPARING → READY → PICKED_UP → DELIVERED. Or CANCELLED, with a refund.
  • Restaurant. Its tablet app receives the order by push (WebSocket or FCM). The restaurant accepts or rejects and gives a prep-time estimate.
  • Dispatch. OrderAccepted goes to the city's assignment service. It finds nearby partners from the geo index (13.13). It scores them by: time to reach the restaurant vs food-ready time, partner's current load, and chances to batch orders. Then it makes an offer and reserves the partner atomically (all-or-nothing, so two orders can't grab the same partner).
  • Tracking. The partner app sends locations to the location service. These go into the geo index and Kafka, and on to the customer app over WebSocket/SSE, with updates throttled (limited in rate).
  • ETA. An ML model adds prep time + travel time + handover time. It re-estimates on every state change.

How does it work?

  1. The order is placed.
  2. The restaurant accepts, with a prep time of 15 minutes.
  3. The dispatcher waits, then assigns a partner who will arrive just as the food is ready. - Assign too early, and the partner wastes time waiting. - Assign too late, and the food goes cold.
  4. The partner gets the offer and accepts.
  5. Pickup → live tracking → delivery.
  6. The partner and the restaurant are paid.

Example

  1. It is dinner peak in Gurugram: 4,000 orders in 30 minutes.
  2. The city's dispatch shard sees two orders from the same restaurant going in the same direction. It batches both onto one partner.
  3. A restaurant has not accepted an order for 5 minutes. The order is auto-cancelled, with an immediate refund.
  4. A partner goes offline mid-route. The system reassigns the order.

When would I use it?

Hyperlocal delivery, quick commerce, field-service dispatch, and B2B order-to-delivery flows for distributors.

What can go wrong?

  • Duplicate orders from a double tap. Fix: idempotency keys.
  • Stale menu stock. Fix: invalidate the cache within seconds.
  • One partner assigned twice. Fix: atomic reserve.
  • Peak overload. Fix: buffer in Kafka, autoscale, and switch off non-essential features (graceful degradation).
  • No auto-cancel or reassignment paths. Orders get stuck.

Interview questions

Q1. How do you decide when to assign a delivery partner? I use the predicted food-ready time and the partner's travel time, so the partner arrives just as the food is ready. I re-check this as the estimates change.

Q2. Why partition by city? Almost every operation stays inside one city. Partitioning by city limits the blast radius — how far a failure spreads — and lets each city scale on its own.

13.19 E-commerce Checkout and Flash Sales (Flipkart Big Billion Days)

Why?

In simple words: Never sell more than you have. For a flash sale, stop the crowd before it reaches the database — use a waiting room and a fast Redis counter, so only about as many buyers as there are items ever get through.

Functional requirements:

  • Browse and search.
  • Cart.
  • Checkout with inventory reservation (holding stock for a buyer for a while).
  • Payment.
  • Order creation.
  • Flash sales: limited stock that goes on sale at a fixed time.

Non-functional requirements:

  • Never oversell.
  • Checkout must stay up at 10–50× normal traffic when a sale starts.
  • Browsing may be eventually consistent (slightly out of date for a short time).
  • Payments must be correct.

It tests inventory concurrency (many buyers fighting for the same stock), traffic shaping (controlling how fast traffic reaches the backend) and sagas (multi-step flows where each step can be undone if a later step fails).

What is happening internally?

Normal checkout:

Cart (Redis/DB) → checkout: recompute price and promotions server-side (cart prices are only hints)
  → inventory reservation:  UPDATE inventory SET reserved = reserved + q
                            WHERE sku = ? AND available - reserved >= q        (atomic; 1 row updated = success)
  → order PENDING_PAYMENT + reservation with TTL (10–15 min)
  → payment (13.8) → success: commit reservation → stock decrement → order CONFIRMED → fulfilment events
                   → failure/timeout: release the reservation (a sweeper releases expired ones)

In plain steps:

  1. The cart lives in Redis or the database.
  2. At checkout, the server recalculates price and promotions itself. Prices in the cart are only hints — never trust them.
  3. Inventory is reserved with one conditional UPDATE. It only succeeds if enough stock is free. If exactly 1 row is updated, the reservation worked. This is atomic — it either fully happens or doesn't happen at all.
  4. The order is created as PENDING_PAYMENT, with a reservation that expires after 10–15 minutes (a TTL).
  5. Payment runs (13.8). - Success: the reservation is committed, stock is reduced, the order becomes CONFIRMED, and fulfilment events go out. - Failure or timeout: the reservation is released. A background sweeper job also releases any reservations that have expired.

Flash sale (1M users hit "Buy" for 10,000 units at 12:00:00): 1. Absorb the spike before the database. Product pages are cached on the CDN. A waiting room (virtual queue) lets users in at a controlled rate. Per-user and per-device rate limits apply, and bots are detected and blocked. 2. Pre-load stock into Redis. An atomic DECR (or a Lua script that checks and decrements in one step) decides admission fast. If the stock is still ≥ 0 after your decrement, you get a time-limited purchase token. Everyone else sees "sold out" immediately. 3. Create orders asynchronously. Purchases from token holders are put in a queue. Workers create orders and reservations at a rate the database can handle. The database's conditional update is still the final guard against overselling. 4. Reconcile. Unpaid tokens expire, and their stock is returned (INCR). After the sale, Redis and database counts are compared and fixed. 5. Avoid hot rows. A hot row is one database row that everyone tries to lock at once. Split one SKU's stock into N buckets (rows or keys), and pick one at random. This spreads out the lock contention.

Think of the Tatkal ticket rush. If all the crowd ran onto the platform at once, nobody would get anything. Instead, a token counter hands out exactly as many tokens as there are seats. Only token holders go on to book.

How does it work?

  • Normal traffic goes straight to the reservation step, guarded by the database.
  • Flash-sale traffic is filtered first by the waiting room and then by Redis admission. So only about as many requests as there are units ever reach the order pipeline.

Example

  1. 10,000 phones are on sale, and 1M users want them.
  2. The waiting room admits 50k users a minute.
  3. Redis hands out exactly 10,000 tokens in about 40 seconds.
  4. 9,200 buyers pay within 10 minutes.
  5. 800 tokens expire. Their units go back to the pool for the next users the waiting room lets in.
  6. The database never sees more than about 2,000 order writes per second.

When would I use it?

Flash sales, ticket drops, limited-edition launches, coupon redemptions with a cap, and booking systems with scarce inventory.

What can go wrong?

  • Locking a single inventory row for a million requests. Requests pile up behind the lock (lock convoys) and time out.
  • Trusting prices sent by the client.
  • Charging the customer without creating an order. Fix: the payment-success event triggers an idempotent retry of order creation. If the order still can't be created, refund.
  • Bots buying everything.
  • Cache and database stock drifting apart.

Interview questions

Q1. How do you prevent overselling? With an atomic conditional decrement or reservation at the source of truth — a database conditional update, or a Redis Lua script. I add reservation TTLs and reconciliation on top.

Q2. How do you survive the flash-sale spike? I shape the traffic before it reaches the backend, using a CDN, a waiting room and rate limits. Buyers are admitted through fast atomic counters in Redis. Orders are then created asynchronously, at a rate the system can sustain.

Q3. What if payment succeeds but order creation fails? The payment-success event drives an idempotent retry of order creation — retrying is safe and never creates two orders. If it still can't complete, the system refunds automatically.
