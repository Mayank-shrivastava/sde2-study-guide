How every topic is explained

Every topic follows the same seven steps. So you always know where you are. You also know what an interviewer can dig into next.

  1. Why? — the problem that made this thing exist. If you know the problem, you can rebuild the solution even under pressure.
  2. What is happening internally? — what sits underneath: the data structures, how memory is laid out, the threads, or the network hops.
  3. How does it work? — the mechanism, step by step.
  4. Example — runnable Java (or SQL / config). Type it out yourself and run it.
  5. When would I use it? — the rule for deciding, and what you would pick instead.
  6. What can go wrong? — the bugs you see in production and the traps interviewers set.
  7. Interview question — asked the way interviewers ask it, with a model answer.

Use the same order when you answer in an interview: problem → internals → mechanism → example → trade-off → what can fail. This structure is what makes an answer sound like SDE2 level. A plain definition does not.

The honest starting point

Your resume says "Solved 500+ DSA problems". Remove that line now.

Here is why. Your LeetCode and GFG links sit right above that line. Interviewers at product companies open those links. If the profile shows far fewer solved problems, they stop trusting you in the first five minutes. After that, they doubt every other line on the resume too.

Put a true number back once you have one. Also, before you apply, make sure the "Java, Spring Boot" skills line is backed by the project in Chapter 8.11.

Rule: Put nothing on the resume that you cannot defend for 10 minutes of follow-up questions. Interviewers are trained to pick one claim and keep digging until it either holds or breaks.

Weekly metric — 1 new + 2 revised. In each study session, do one new section. Then answer again the interview questions from two sections you studied earlier. Answering an old section aloud, without notes, is worth more than reading a new one.

Stuck rule: Sometimes a section won't make sense after one careful read. Then run its code, change one thing, and guess the output before you run it again. If it still doesn't make sense, mark it and move on. Come back to it on Saturday.

Gates — do not move on until they pass

A gate is a self-test at the end of a phase. If you can't pass it, spend more time on that phase before moving ahead.

  • Gate 1 (end of Week 4): Without notes, explain these aloud:
  • HashMap internals (hashing, treeify, resize);
  • the equals/hashCode contract;
  • why String is immutable, and the String pool;
  • checked vs unchecked exceptions;
  • why generics are erased, and what PECS means;
  • how a stream pipeline runs lazily (only when a final operation asks for results).
  • Gate 2 (end of Week 8):
  • Code a thread-safe bounded blocking queue and a producer–consumer from scratch in 30 minutes.
  • Explain how ThreadPoolExecutor behaves with core size, max size, queue and rejection.
  • Explain volatile vs synchronized.
  • Explain why @Transactional does nothing when a method calls another method in the same class (self-invocation).
  • Finish six LLD problems in Java.
  • Gate 3 (end of Week 12):
  • Java project deployed, with a README, tests and a load-test number.
  • From memory, explain the Spring bean lifecycle, @Transactional propagation and the N+1 fix.
  • Write a window-function query that returns the top 3 per group.
  • Explain why a given index is or isn't used.
  • Present one HLD case study end to end in 40 minutes.

How to study a section (and remember it)

  1. Read the section once, slowly. Run every code block (IntelliJ Community is free).
  2. Close the guide. Say the seven steps for the topic aloud, in about two minutes.
  3. Answer the section's interview question aloud in ~90 seconds. Then compare it with the model answer. Mark the ones where you stumble.
  4. Review the flashcards for 15 minutes every day. This is spaced repetition — seeing a card again just before you would forget it. It is what prevents the "I knew this yesterday" blank.

Remember: Recognising something is not the same as recalling it. Re-reading feels productive, but it leaves you blank in interviews. Closing the guide and pulling the answer out of your own head is what builds recall.
