This chapter solves seventeen LLD (low-level design) problems, in the order interviewers usually ask them. LLD means designing the classes, data structures and methods for one small system.

Every problem follows the same seven steps:

  • Why? — what the interviewer asks, and what skill it tests.
  • What is happening internally? — the classes (entities), data structures and design patterns.
  • How does it work? — the main flows, step by step, and how we handle many threads at once.
  • Example — complete code. It compiles and runs with java File.java. A short trace of the output follows it.
  • When would I use it? — where the same design shows up in real systems.
  • What can go wrong? — edge cases and common mistakes.
  • Interview questions — the follow-up questions you will most likely get.

10.1 Tic-Tac-Toe

Why?

In simple words: Build a noughts-and-crosses game. The clever part is checking for a winner with a few counters, instead of looking at the whole board after every move.

This is a 45-minute warm-up. Many companies ask it in the first LLD round.

It tests four things:

  • Basic modelling — splitting the problem into a board, players and a game.
  • Turn management — whose move is it now?
  • Input validation — rejecting bad moves.
  • One algorithm idea — checking a win in O(1) per move. O(1) means the work does not grow with the board size. The slow way is to scan the whole board every time.

What is happening internally?

  • Entities (the main classes):
  • Player — a name and a symbol.
  • Board — an N×N grid of cells, plus some counters.
  • Game — the turn order and the current status.
  • Enums (fixed lists of values): Symbol {X, O} and Status {IN_PROGRESS, X_WON, O_WON, DRAW}.
  • Key data structure: one counter for every row, one for every column, and two for the diagonals.
  • When X plays, add +1 to the counters of that cell's lines. When O plays, add −1.
  • If X fills a whole line, its counter becomes +N. If O fills it, the counter becomes −N.
  • If both players have marks on a line, the +1s and −1s cancel out, so it can never reach N.
  • So: if the absolute value of a counter reaches N, one player owns that full line.
  • Turn order: a Deque<Player> (a double-ended queue). After each move, take the front player and put them at the back. This works for more than two players without any change.

Think of it like a scoreboard per line. X adds a run, O takes one away. Only a line where one side scored every time reaches the full score.

How does it work?

  1. move(r, c) is called. First, check the move is valid: - the game is not already over, - the cell is on the board, - the cell is empty.
  2. Place the current player's symbol in the cell.
  3. Update rows[r] and cols[c].
  4. If r == c, the cell is on the main diagonal, so update that counter too.
  5. If r + c == n − 1, the cell is on the anti-diagonal (top-right to bottom-left), so update that counter.
  6. Check only the counters you just touched: - If any has absolute value N → this player wins. - Else, if all cells are filled → it is a draw. - Else → rotate the turn to the next player.

Example

// FILE: TicTacToe.java
import java.util.*;

public class TicTacToe {
    enum Symbol { X, O }
    enum Status { IN_PROGRESS, X_WON, O_WON, DRAW }
    record Player(String name, Symbol symbol) {}

    static class Board {
        private final int n;
        private final Symbol[][] cells;
        private final int[] rows, cols;
        private int diag, anti, filled;
        Board(int n) { this.n = n; cells = new Symbol[n][n]; rows = new int[n]; cols = new int[n]; }

        /** @return true if this move wins */
        boolean place(int r, int c, Symbol s) {
            if (r < 0 || c < 0 || r >= n || c >= n) throw new IllegalArgumentException("off board");
            if (cells[r][c] != null) throw new IllegalArgumentException("cell taken");
            cells[r][c] = s; filled++;
            int d = s == Symbol.X ? 1 : -1;
            rows[r] += d; cols[c] += d;
            if (r == c) diag += d;
            if (r + c == n - 1) anti += d;
            return Math.abs(rows[r]) == n || Math.abs(cols[c]) == n || Math.abs(diag) == n || Math.abs(anti) == n;
        }
        boolean full() { return filled == n * n; }
    }

    static class Game {
        private final Board board;
        private final Deque<Player> turn = new ArrayDeque<>();
        private Status status = Status.IN_PROGRESS;
        Game(int n, Player p1, Player p2) { board = new Board(n); turn.add(p1); turn.add(p2); }

        Status move(int r, int c) {
            if (status != Status.IN_PROGRESS) throw new IllegalStateException("game over: " + status);
            Player p = turn.peekFirst();
            if (board.place(r, c, p.symbol())) status = p.symbol() == Symbol.X ? Status.X_WON : Status.O_WON;
            else if (board.full()) status = Status.DRAW;
            else turn.addLast(turn.pollFirst());
            return status;
        }
    }

    public static void main(String[] args) {
        Game g = new Game(3, new Player("Asha", Symbol.X), new Player("Ravi", Symbol.O));
        int[][] moves = {{0,0},{1,1},{0,1},{2,2},{0,2}};
        Status s = null;
        for (int[] m : moves) s = g.move(m[0], m[1]);
        System.out.println(s);   // X_WON
    }
}

Trace, move by move (N = 3):

  1. X plays (0,0) → rows[0]=1, cols[0]=1, diag=1.
  2. O plays (1,1) → rows[1]=−1, cols[1]=−1, diag=0, anti=−1. (The centre is on both diagonals.)
  3. X plays (0,1) → rows[0]=2.
  4. O plays (2,2) → diag=−1.
  5. X plays (0,2) → rows[0]=3. That equals N, so the result is X_WON.

When would I use it?

The counter trick works for any "N in a line" check.

The split into Game, Board and Player, plus the turn queue, comes back again and again. You will see it in Snake & Ladder (10.13), chess and card games.

What can go wrong?

  • Scanning the whole board after every move. That is O(N²) work — it grows with the square of the board size — when O(1) is possible.
  • Allowing a move after the game has ended.
  • Allowing a move on a cell that is already taken.
  • Hard-coding two players or a 3×3 board. Keep N and the player list flexible.

Interview questions

Q1. How do you check a win in O(1)? Keep one counter per row, per column and for both diagonals. Add +1 for X and −1 for O on the lines that pass through the played cell. If a counter reaches +N or −N, that player has won.

Q2. How would you support K-in-a-row on an N×N board (K < N)? The full-line counters no longer work. Instead, after each move, start from the placed cell and count matching symbols in a row along the 4 directions (row, column, two diagonals). That costs O(K) per move — the work depends only on K.

Q3. How would you add undo or a bot? For undo, use the Command pattern: push each move onto a stack, and to undo, pop it and reverse its counter changes. For a bot, add a MoveStrategy interface. Plug in different versions behind it — random, greedy, or minimax (a search that tries all future moves).

10.2 Parking Lot

Why?

In simple words: Cars, bikes and trucks come in, get a suitable free spot and a ticket, and pay by the hour when they leave. The key point is that two entry gates must never hand out the same spot.

This is the most common LLD question of all.

It tests:

  • Modelling with several kinds of entities (lot, spot, vehicle, ticket).
  • The Strategy pattern — putting a changeable rule (like pricing or spot choice) behind an interface.
  • Clean separation of responsibilities — each class does one job.
  • Concurrency — many threads running at the same time. Here, two entry gates working at the same moment must never assign the same spot.

What is happening internally?

  • Entities:
  • ParkingLot — the whole system.
  • Spot — id, floor and type.
  • Vehicle — number plate and type.
  • Ticket — id, vehicle, spot and entry time.
  • Receipt — what you get on exit, with the fee.
  • Enums: VehicleType {BIKE, CAR, TRUCK} and SpotType {SMALL, MEDIUM, LARGE}.
  • A mapping says which spot types each vehicle may use. A bike can use any spot. A truck can use only large ones.
  • Data structures:
  • Free spots are kept per spot type in a ConcurrentLinkedDeque. It is lock-free — threads do not wait on a lock — and its pollFirst is atomic. Atomic means it happens as one single step that no other thread can break into.
  • Active tickets are kept in a ConcurrentHashMap. Its remove on exit is also atomic.
  • Patterns:
  • Strategy: FeeStrategy decides the price. Spot allocation could be a second strategy.
  • An injected Clock: the lot does not read the system time directly; we pass a clock in. So tests can control time.

How does it work?

  1. Park:
  2. Get the list of spot types this vehicle may use, best fit first.
  3. For each type, call pollFirst() to take a free spot.
  4. The first spot you get creates a ticket.
  5. If every type is empty → "lot full".
  6. Exit:
  7. Atomically remove the ticket from the active map. If two exits race, only one gets the ticket, so a ticket can never be closed twice.
  8. Work out how long the vehicle stayed, and ask the fee strategy for the price.
  9. Put the spot back into its free deque.
  10. Availability: just the size of each free deque.

Concurrency: there is no global lock. pollFirst on a concurrent deque is atomic. So if two gates call it at the very same moment, they always get different spots.

Think of a token counter at a busy restaurant. Each token can be torn off the roll by only one waiter. Two waiters grabbing at the same time still get two different tokens.

Example

// FILE: ParkingLotDemo.java
import java.time.*;
import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicLong;

public class ParkingLotDemo {
    enum VehicleType { BIKE, CAR, TRUCK }
    enum SpotType { SMALL, MEDIUM, LARGE }

    record Vehicle(String plate, VehicleType type) {}
    record Ticket(String id, Vehicle vehicle, Spot spot, Instant entry) {}
    record Receipt(Ticket ticket, Instant exit, long feeRupees) {}

    static final class Spot {
        final String id; final int floor; final SpotType type;
        Spot(String id, int floor, SpotType type) { this.id = id; this.floor = floor; this.type = type; }
        public String toString() { return id; }
    }

    interface FeeStrategy { long fee(VehicleType t, Duration d); }
    static class HourlyFee implements FeeStrategy {
        private final Map<VehicleType, Long> perHour;
        HourlyFee(Map<VehicleType, Long> perHour) { this.perHour = perHour; }
        public long fee(VehicleType t, Duration d) {
            long hours = Math.max(1, (d.toMinutes() + 59) / 60);    // ceil, minimum 1 hour
            return hours * perHour.get(t);
        }
    }

    /** Which spot types a vehicle may use, in order of preference. */
    static List<SpotType> compatible(VehicleType v) {
        return switch (v) {
            case BIKE -> List.of(SpotType.SMALL, SpotType.MEDIUM, SpotType.LARGE);
            case CAR -> List.of(SpotType.MEDIUM, SpotType.LARGE);
            case TRUCK -> List.of(SpotType.LARGE);
        };
    }

    static class ParkingLot {
        // free spots per type: a concurrent queue gives lock-free, thread-safe allocation across gates
        private final Map<SpotType, ConcurrentLinkedDeque<Spot>> free = new EnumMap<>(SpotType.class);
        private final ConcurrentHashMap<String, Ticket> active = new ConcurrentHashMap<>();
        private final FeeStrategy fees;
        private final Clock clock;
        private final AtomicLong seq = new AtomicLong();

        ParkingLot(List<Spot> spots, FeeStrategy fees, Clock clock) {
            for (SpotType t : SpotType.values()) free.put(t, new ConcurrentLinkedDeque<>());
            spots.forEach(s -> free.get(s.type).add(s));
            this.fees = fees; this.clock = clock;
        }

        Ticket park(Vehicle v) {
            for (SpotType t : compatible(v.type())) {
                Spot s = free.get(t).pollFirst();        // atomic: two gates never get the same spot
                if (s != null) {
                    Ticket ticket = new Ticket("T" + seq.incrementAndGet(), v, s, clock.instant());
                    active.put(ticket.id(), ticket);
                    return ticket;
                }
            }
            throw new IllegalStateException("No spot for " + v.type());
        }

        Receipt exit(String ticketId) {
            Ticket t = active.remove(ticketId);          // atomic: a ticket can be closed only once
            if (t == null) throw new IllegalArgumentException("Unknown or closed ticket " + ticketId);
            Instant now = clock.instant();
            long fee = fees.fee(t.vehicle().type(), Duration.between(t.entry(), now));
            free.get(t.spot().type).addFirst(t.spot());
            return new Receipt(t, now, fee);
        }

        Map<SpotType, Integer> availability() {
            Map<SpotType, Integer> m = new EnumMap<>(SpotType.class);
            free.forEach((k, v) -> m.put(k, v.size()));
            return m;
        }
    }

    /** Test clock we can move forward. */
    static class MutableClock extends Clock {
        private Instant now = Instant.parse("2026-10-05T09:00:00Z");
        void advance(Duration d) { now = now.plus(d); }
        public ZoneId getZone() { return ZoneOffset.UTC; }
        public Clock withZone(ZoneId z) { return this; }
        public Instant instant() { return now; }
    }

    public static void main(String[] args) {
        List<Spot> spots = new ArrayList<>();
        for (int f = 0; f < 2; f++) {
            for (int i = 0; i < 2; i++) spots.add(new Spot("F" + f + "-S" + i, f, SpotType.SMALL));
            for (int i = 0; i < 3; i++) spots.add(new Spot("F" + f + "-M" + i, f, SpotType.MEDIUM));
            spots.add(new Spot("F" + f + "-L0", f, SpotType.LARGE));
        }
        MutableClock clock = new MutableClock();
        ParkingLot lot = new ParkingLot(spots,
                new HourlyFee(Map.of(VehicleType.BIKE, 10L, VehicleType.CAR, 40L, VehicleType.TRUCK, 100L)), clock);

        Ticket t1 = lot.park(new Vehicle("UP65AB1234", VehicleType.CAR));
        Ticket t2 = lot.park(new Vehicle("UP65ZZ0001", VehicleType.TRUCK));
        System.out.println(t1.spot() + " " + t2.spot() + " " + lot.availability());
        clock.advance(Duration.ofMinutes(130));
        System.out.println("Fee: " + lot.exit(t1.id()).feeRupees());   // 3 hours * 40 = 120
        System.out.println(lot.availability());
    }
}

Trace:

  1. The car gets the first MEDIUM spot (F0-M0).
  2. The truck gets the first LARGE spot (F0-L0).
  3. The clock moves 130 minutes ahead.
  4. The car exits. Hours are rounded up: ceil(130/60) = 3 hours. 3 × ₹40 = ₹120.
  5. F0-M0 goes back to the free pool.

When would I use it?

The same shape appears whenever you have a stock of similar slots, hand them out, and bill by time. Examples:

  • EV charging stations.
  • Co-working desk booking.
  • Warehouse bins.
  • Cloud resource allocation (handing out servers or IP addresses).

What can go wrong?

  • One global synchronized on the whole lot. It is correct, but it serialises all gates — only one gate can work at a time.
  • Check-then-act races. You "find a free spot" in one step and "mark it occupied" in a second step. Between the two steps, another gate can take the same spot.
  • Billing with double. Floating-point maths gives rounding errors with money; use long or BigDecimal.
  • Forgetting the minimum charge or the rounding rule.
  • Hard-coded pricing instead of a strategy, so every price change means editing the core code.

Interview questions

Q1. How do you prevent two gates assigning the same spot? Take the spot with an atomic poll from a concurrent free-spot structure, one per spot type. A lock per spot type also works. If the spots live in a database, use SELECT … FOR UPDATE SKIP LOCKED (lock a free row and skip rows others have locked) or a conditional update like "set occupied where it is still free".

Q2. How would you allocate the nearest spot to the entry gate? Keep, for each gate, a PriorityQueue/TreeSet of free spots sorted by distance from that gate. Hide it behind an AllocationStrategy interface so you can swap the rule later.

Q3. How would you add weekend pricing or a monthly pass? Write new FeeStrategy implementations and pick one based on the date or the vehicle. The parking flow itself does not change.

Q4. How does this change for 1,000 lots in a city? It becomes an HLD (high-level design) problem. Store the spot inventory in a database, per lot. Add a booking service that uses conditional updates so two bookings cannot take one spot. Cache availability so the "how many spots free?" reads are cheap.

10.3 LRU Cache

Why?

In simple words: A fixed-size cache that, when full, throws out the item nobody has used for the longest time. A HashMap finds items fast, and a linked list keeps them in "most recently used" order.

LRU means Least Recently Used. This is LeetCode 146, and product companies ask it all the time.

It tests:

  • Combining two data structures so that both get and put run in O(1) — constant time, no matter how big the cache is.
  • Careful pointer handling in a linked list.
  • For SDE2: thread safety and real-world trade-offs.

What is happening internally?

  • A HashMap from key → node. It finds any node in O(1).
  • A doubly linked list kept in order of use. The head side holds the most recently used item; the tail side holds the least recently used one.
  • Each node knows both its previous and next node, so you can remove it from the middle in O(1).
  • Moving a node to the front is O(1).
  • Throwing out the oldest item is O(1) — it is always just before the tail.
  • Sentinel head and tail nodes. These are dummy nodes that are always there. Because the list is never truly empty, you never need null checks at the ends.
  • A ReentrantLock makes it thread-safe. Note: even get mutates the cache — it moves the node to the front. So reads need the lock too, not just writes.

Think of a small bookshelf with room for only a few books. Every time you read a book, you put it back on the far left. When the shelf is full and a new book comes, you remove the one on the far right — the one you haven't touched for the longest time.

map: {1→n1, 2→n2, 3→n3}
list: HEAD ⇄ n3 ⇄ n1 ⇄ n2 ⇄ TAIL     (most recent … least recent)
get(2) → move n2 to front;  put(4) at capacity 3 → evict TAIL.prev (n1)

How does it work?

get(k):

  1. Look up the key in the map.
  2. If it is missing, return empty.
  3. If it is there, unlink the node from where it is.
  4. Add it right after the head (the "most recent" end).
  5. Return the value.

put(k, v):

  1. If the key already exists, update its value and move it to the front. Done.
  2. Otherwise, check if the cache is full.
  3. If full, take tail.prev (the least recently used node). Unlink it, and also remove its key from the map.
  4. Create a new node.
  5. Add it to the map and to the front of the list.

Example

// FILE: LRUCacheDemo.java
import java.util.*;
import java.util.concurrent.locks.ReentrantLock;

public class LRUCacheDemo {
    static class LRUCache<K, V> {
        private static final class Node<K, V> { K key; V val; Node<K, V> prev, next; Node(K k, V v) { key = k; val = v; } }
        private final int capacity;
        private final Map<K, Node<K, V>> map = new HashMap<>();
        private final Node<K, V> head = new Node<>(null, null), tail = new Node<>(null, null);
        private final ReentrantLock lock = new ReentrantLock();   // get() mutates order, so reads need the lock too

        LRUCache(int capacity) {
            if (capacity <= 0) throw new IllegalArgumentException("capacity must be > 0");
            this.capacity = capacity; head.next = tail; tail.prev = head;
        }

        public Optional<V> get(K key) {
            lock.lock();
            try {
                Node<K, V> n = map.get(key);
                if (n == null) return Optional.empty();
                moveToFront(n);
                return Optional.of(n.val);
            } finally { lock.unlock(); }
        }

        public void put(K key, V val) {
            lock.lock();
            try {
                Node<K, V> n = map.get(key);
                if (n != null) { n.val = val; moveToFront(n); return; }
                if (map.size() == capacity) {
                    Node<K, V> lru = tail.prev;
                    unlink(lru);
                    map.remove(lru.key);
                }
                n = new Node<>(key, val);
                map.put(key, n);
                addFront(n);
            } finally { lock.unlock(); }
        }

        private void addFront(Node<K, V> n) { n.next = head.next; n.prev = head; head.next.prev = n; head.next = n; }
        private void unlink(Node<K, V> n) { n.prev.next = n.next; n.next.prev = n.prev; }
        private void moveToFront(Node<K, V> n) { unlink(n); addFront(n); }
    }

    public static void main(String[] args) {
        LRUCache<Integer, String> c = new LRUCache<>(2);
        c.put(1, "a"); c.put(2, "b");
        c.get(1);                 // 1 becomes most recent
        c.put(3, "c");            // evicts 2
        System.out.println(c.get(2).isPresent() + " " + c.get(1).orElse("-") + " " + c.get(3).orElse("-")); // false a c
    }
}

Trace (capacity 2, list shown most recent first):

  1. put 1, put 2 → list [2,1].
  2. get 1 → 1 moves to the front → [1,2].
  3. put 3 → cache is full → evict the tail (2) → [3,1].
  4. get 2 → miss, because 2 was evicted.

When would I use it?

  • In-process caches that must not grow beyond a fixed size.
  • Page caches.
  • Database buffer pools (they use approximations of LRU).
  • CDN edge caches.

In real Java code, don't write your own. Use Caffeine — it uses W-TinyLFU (a smarter eviction rule with better hit rates) and also handles concurrency and TTL (time-to-live expiry). For simple cases, LinkedHashMap with access order is enough (2.5).

What can go wrong?

  • Forgetting to remove the evicted key from the map. The list stays small, but the map grows forever.
  • Updating an existing key without moving it to the front.
  • No lock. Concurrent gets also change the list, so without a lock they can corrupt it.
  • Storing only values in the nodes. Then, when you evict the tail node, you don't know which key to remove from the map.

Interview questions

Q1. Why HashMap plus a doubly linked list? The map finds the node in O(1). The doubly linked list lets you remove a node from the middle and insert it at the front in O(1). It also gives O(1) access to the least recently used item at the tail. Neither structure can do all of this alone.

Q2. How would you make it scale under heavy concurrency? Use lock striping: split the cache into N independent LRU segments, each with its own lock, and choose the segment by key hash. Threads on different segments don't block each other. The trade-off is that eviction is LRU per segment, so it only approximates a global LRU. Or use Caffeine, which buffers and samples accesses instead of locking on every read.

Q3. How would you add a TTL? Store an expiry time in each node. On access, if the entry has expired, treat it as a miss and remove it. Clean up the rest either with a periodic sweep or lazily when you touch them.

Q4. How would you implement LFU? LFU means Least Frequently Used. Keep two maps: key → (value, freq), and freq → LinkedHashSet of keys. The LinkedHashSet keeps insertion order, so among keys with the same frequency you evict the least recently used one. Also track the current minimum frequency, so eviction is O(1).

10.4 Logger Framework

Why?

In simple words: Build a mini SLF4J/Logback. A logger drops messages below its level, sends the rest to one or more outputs, and can write them on a background thread so the app never waits for the disk.

It tests:

  • Interface design — logger, appender and formatter as separate pieces.
  • The Chain of Responsibility / filtering idea — each message passes a check before it goes further.
  • Thread safety — many threads log at the same time.
  • The async producer–consumer trade-off. Async means the app hands the message off and moves on. That makes logging fast (low latency), but you can lose messages if the queue is full or the app crashes (less reliable).

What is happening internally?

  • Entities:
  • Logger — a name, a minimum level and a list of appenders.
  • LogEvent — one log line's data, as a Java record.
  • Appender — where events go (console, file, memory…).
  • Formatter — how events look as text.
  • LoggerFactory — a registry that hands out one logger per name.
  • Patterns:
  • Strategy — the formatter can be swapped.
  • Observer-like fan-out — one event is sent to every appender.
  • Decorator — AsyncAppender wraps any appender and makes it async, without changing that appender.
  • Factory/registry — LoggerFactory uses computeIfAbsent, so each name gets exactly one logger, even with many threads.
  • Async: a bounded BlockingQueue (a queue with a size limit) plus one writer thread. Application threads only drop events into the queue. They never wait on I/O (disk or network).

Think of a courier drop box at an office. You drop the parcel and go back to work. One delivery person empties the box and does the slow travel. If the box is full, the office must decide: drop the parcel or wait.

How does it work?

  1. log(level, msg) is called. First, do a cheap level check: if ordinal < min, return at once. So a disabled DEBUG call costs almost nothing.
  2. Build an immutable LogEvent (it cannot change after creation) holding time, level, logger name, thread name and message.
  3. Hand the event to every appender.
  4. AsyncAppender.append only offers the event to its queue. If the queue is full, the event is dropped. The app is never blocked.
  5. The async worker thread takes events off the queue and passes them to the real appender.
  6. close() stops the worker, but only after it has written all remaining events.

Example

// FILE: LoggerDemo.java
import java.time.*;
import java.util.*;
import java.util.concurrent.*;

public class LoggerDemo {
    enum Level { DEBUG, INFO, WARN, ERROR }
    record LogEvent(Instant at, Level level, String logger, String thread, String message) {}

    interface Formatter { String format(LogEvent e); }
    static class PlainFormatter implements Formatter {
        public String format(LogEvent e) { return "%s [%s] %-5s %s - %s".formatted(e.at(), e.thread(), e.level(), e.logger(), e.message()); }
    }

    interface Appender { void append(LogEvent e); }
    static class ConsoleAppender implements Appender {
        private final Formatter f; ConsoleAppender(Formatter f) { this.f = f; }
        public synchronized void append(LogEvent e) { System.out.println(f.format(e)); }   // keep lines whole
    }
    static class MemoryAppender implements Appender {
        final List<LogEvent> events = new CopyOnWriteArrayList<>();
        public void append(LogEvent e) { events.add(e); }
    }
    /** Decorator: makes any appender asynchronous via a bounded queue and one worker thread. */
    static class AsyncAppender implements Appender, AutoCloseable {
        private final BlockingQueue<LogEvent> q = new ArrayBlockingQueue<>(10_000);
        private final Thread worker;
        private volatile boolean running = true;
        AsyncAppender(Appender delegate) {
            worker = Thread.ofPlatform().name("log-writer").daemon(true).start(() -> {
                try {
                    while (running || !q.isEmpty()) {
                        LogEvent e = q.poll(100, TimeUnit.MILLISECONDS);
                        if (e != null) delegate.append(e);
                    }
                } catch (InterruptedException ie) { Thread.currentThread().interrupt(); }
            });
        }
        public void append(LogEvent e) { if (!q.offer(e)) { /* drop or count: never block the app on logging */ } }
        public void close() throws InterruptedException { running = false; worker.join(); }
    }

    static class Logger {
        private final String name; private volatile Level min; private final List<Appender> appenders;
        Logger(String name, Level min, List<Appender> appenders) { this.name = name; this.min = min; this.appenders = appenders; }
        void setLevel(Level l) { this.min = l; }
        void log(Level l, String msg) {
            if (l.ordinal() < min.ordinal()) return;                      // cheap level check first
            LogEvent e = new LogEvent(Instant.now(), l, name, Thread.currentThread().getName(), msg);
            for (Appender a : appenders) a.append(e);
        }
        void debug(String m) { log(Level.DEBUG, m); } void info(String m) { log(Level.INFO, m); }
        void warn(String m) { log(Level.WARN, m); }   void error(String m) { log(Level.ERROR, m); }
    }

    static final class LoggerFactory {
        private static final ConcurrentHashMap<String, Logger> LOGGERS = new ConcurrentHashMap<>();
        private static volatile List<Appender> defaults = List.of(new ConsoleAppender(new PlainFormatter()));
        static void configure(List<Appender> appenders) { defaults = List.copyOf(appenders); }
        static Logger get(String name) { return LOGGERS.computeIfAbsent(name, n -> new Logger(n, Level.INFO, defaults)); }
    }

    public static void main(String[] args) throws Exception {
        MemoryAppender mem = new MemoryAppender();
        try (AsyncAppender async = new AsyncAppender(new ConsoleAppender(new PlainFormatter()))) {
            LoggerFactory.configure(List.of(async, mem));
            Logger log = LoggerFactory.get("redemption");
            log.debug("hidden");
            log.info("redeemed 500 points");
            log.error("partner timeout");
        }
        System.out.println("captured=" + mem.events.size());   // 2
    }
}

Trace:

  1. debug("hidden") is dropped, because the logger's level is INFO.
  2. INFO and ERROR pass the check.
  3. Each goes to the async console appender. The log-writer thread prints them.
  4. Each also goes to the memory appender. So 2 events are captured.

When would I use it?

  • To understand how SLF4J/Logback work inside: async appenders, MDC (per-request context) and level hierarchies.
  • When designing audit logs or metrics pipelines.
  • For any component that sends ("fans out") events to several outputs ("sinks").

What can go wrong?

  • Doing synchronous file or network I/O on the request path. Every request then waits for the disk.
  • An unbounded async queue. During a log storm it grows until you get an OOM (OutOfMemoryError).
  • A queue that blocks when full. When the disk is slow, the whole app stalls.
  • So choose a drop policy (drop, or block) on purpose, and document it.
  • Half lines mixed together from different threads. Fix it by synchronising per appender.
  • Losing buffered events at shutdown because nobody flushed the queue.

Interview questions

Q1. How do you make logging not slow the application? Check the level first, so disabled logs cost nothing. Use parameterised messages, so the string is built only if the log is enabled. Use asynchronous appenders with a bounded queue, and a clear policy for what happens when it is full — drop or block.

Q2. How would you support per-package levels like com.fa.loyalty=DEBUG? Use hierarchical logger names, split by dots. A logger takes the level of its nearest configured ancestor. So com.fa.loyalty.redeem gets DEBUG from com.fa.loyalty.

Q3. How would you add request IDs to every line? Use an MDC (Mapped Diagnostic Context). It is a ThreadLocal map — a map private to each thread. A request filter puts the request ID into it at the start, every LogEvent copies it, and the filter clears it after the request ends.

10.5 Rate Limiter

Why?

In simple words: Allow each client only so many requests per second, and reject the extra ones. The usual way is a token bucket — each request spends a token, and tokens slowly come back over time.

Almost every product company asks this. It comes as LLD (in memory, per client) and as HLD (distributed across many servers, 13.2).

It tests:

  • Algorithm knowledge — token bucket vs window-based counting.
  • Clean Strategy design — different algorithms behind one interface.
  • Fine-grained concurrency — locking per client, not the whole system.

What is happening internally?

The common algorithms:

Algorithm State per client Behaviour
Fixed window count + window start Simple; but up to 2× the limit can pass around a window edge
Sliding window log deque of timestamps Exact; but O(limit) memory per client (one timestamp per request)
Sliding window counter two counts Close estimate using a weighted mix of two windows; little memory
Token bucket tokens + last refill time Allows short bursts up to capacity, with a smooth average rate
Leaky bucket queue Lets requests out at a constant rate
  • Interface: RateLimiter.tryAcquire(clientId) returns allow or reject. Different algorithms implement it, and you can swap them (Strategy).
  • Per-client state lives in a ConcurrentHashMap.
  • Lock per client (synchronized (bucket)), not one global lock. So client A never waits for client B.
  • Lazy refill: no background thread adds tokens. Instead, on each call, you calculate how many tokens were earned since the last call.
  • Injected clock: the limiter asks a clock object for the time. Tests use a fake clock, so results are always the same (deterministic).

Think of a bus pass with a few tickets. Each trip uses one ticket. One new ticket is added every second, but the pass holds at most 5. You can make 5 trips quickly, then only one per second.

How does it work?

Token bucket tryAcquire:

  1. Find the time passed since the last call.
  2. Add the tokens earned in that time, but never go above capacity: tokens = min(capacity, tokens + elapsed × rate).
  3. If tokens ≥ 1, take one token and allow the request.
  4. Else reject it.

Sliding window log tryAcquire:

  1. Remove timestamps older than the window from the front of the deque.
  2. If fewer than limit timestamps remain, add "now" and allow.
  3. Else reject.

Example

// FILE: RateLimiterDemo.java
import java.util.*;
import java.util.concurrent.*;

public class RateLimiterDemo {
    interface RateLimiter { boolean tryAcquire(String clientId); }

    /** Token bucket per client. Lazy refill on each call: no background threads. */
    static class TokenBucketLimiter implements RateLimiter {
        private static final class Bucket {
            double tokens; long lastNanos;
            Bucket(double tokens, long now) { this.tokens = tokens; this.lastNanos = now; }
        }
        private final double capacity, refillPerNano;
        private final ConcurrentHashMap<String, Bucket> buckets = new ConcurrentHashMap<>();
        private final LongSupplierClock clock;

        TokenBucketLimiter(int capacity, double tokensPerSecond, LongSupplierClock clock) {
            this.capacity = capacity; this.refillPerNano = tokensPerSecond / 1e9; this.clock = clock;
        }
        public boolean tryAcquire(String client) {
            long now = clock.nanos();
            Bucket b = buckets.computeIfAbsent(client, k -> new Bucket(capacity, now));
            synchronized (b) {                                     // lock per client, not global
                b.tokens = Math.min(capacity, b.tokens + (now - b.lastNanos) * refillPerNano);
                b.lastNanos = now;
                if (b.tokens >= 1) { b.tokens -= 1; return true; }
                return false;
            }
        }
    }

    /** Exact sliding window log. */
    static class SlidingWindowLogLimiter implements RateLimiter {
        private final int limit; private final long windowNanos; private final LongSupplierClock clock;
        private final ConcurrentHashMap<String, Deque<Long>> logs = new ConcurrentHashMap<>();
        SlidingWindowLogLimiter(int limit, long windowMillis, LongSupplierClock clock) {
            this.limit = limit; this.windowNanos = windowMillis * 1_000_000; this.clock = clock;
        }
        public boolean tryAcquire(String client) {
            long now = clock.nanos();
            Deque<Long> log = logs.computeIfAbsent(client, k -> new ArrayDeque<>());
            synchronized (log) {
                while (!log.isEmpty() && now - log.peekFirst() >= windowNanos) log.pollFirst();
                if (log.size() < limit) { log.addLast(now); return true; }
                return false;
            }
        }
    }

    interface LongSupplierClock { long nanos(); }
    static class FakeClock implements LongSupplierClock { long t; public long nanos() { return t; } void plusMillis(long ms) { t += ms * 1_000_000; } }

    public static void main(String[] args) {
        FakeClock clock = new FakeClock();
        RateLimiter tb = new TokenBucketLimiter(5, 1.0, clock);       // burst 5, then 1/second
        int ok = 0; for (int i = 0; i < 8; i++) if (tb.tryAcquire("u1")) ok++;
        System.out.println("burst allowed=" + ok);                     // 5
        clock.plusMillis(2000);
        System.out.println("after 2s: " + tb.tryAcquire("u1") + " " + tb.tryAcquire("u1") + " " + tb.tryAcquire("u1")); // true true false

        RateLimiter sw = new SlidingWindowLogLimiter(3, 1000, clock);
        System.out.println(sw.tryAcquire("u2") + " " + sw.tryAcquire("u2") + " " + sw.tryAcquire("u2") + " " + sw.tryAcquire("u2")); // t t t f
    }
}

Trace:

  1. Token bucket, capacity 5, refill 1 token per second.
  2. 8 calls at once → only 5 allowed. That is the burst.
  3. Clock moves 2 seconds → 2 tokens come back → true, true, then false.
  4. Sliding log, 3 per second: the first 3 calls pass; the 4th call inside the same window is rejected.

When would I use it?

  • API gateways.
  • Login and OTP endpoints, to stop brute-force attempts.
  • Partner API quotas — when you call a partner, stay within their limits.
  • Per-tenant fairness in multi-tenant platforms, so one big customer can't starve the others.
  • Throttling background jobs.

What can go wrong?

  • A global lock. It serialises all clients — only one client is checked at a time.
  • Memory growth from clients who stopped calling. Their state stays forever unless you expire buckets after a period of no activity.
  • Using wall-clock time, which can jump (for example, when the server clock is corrected). Use System.nanoTime or an injected monotonic clock — one that only moves forward.
  • In a distributed setup, each server instance runs its own limiter. So the real limit becomes limit × number of instances (13.2).

Interview questions

Q1. Token bucket vs sliding window? A token bucket allows controlled bursts while keeping a smooth average rate, and it needs only O(1) state per client. A sliding window log is exact, but it stores one timestamp per request. A sliding window counter gives a close estimate using just two counters.

Q2. How would you make it distributed? Keep the state in Redis and update it with an atomic Lua script per key, so the read-and-update happens as one step (13.2). Another option: keep local buckets on each instance, and give each instance a share of the global quota.

Q3. How do you clean up idle clients? Store the last-access time for each bucket. Remove buckets that have been idle longer than a TTL. Or simply use a cache with expireAfterAccess, which does this for you.

10.6 Bounded Blocking Queue and a Job Processing System

Why?

In simple words: Producers put jobs into a queue with a size limit, and a few worker threads take them out and do them. When the queue is full, producers wait — so the system slows down instead of running out of memory.

This tests concurrency basics inside an LLD problem:

  • Producer–consumer — some threads create work, others do it.
  • Back-pressure — a full queue makes producers slow down.
  • Clean shutdown — every worker stops after the real work is done.
  • Per-key ordering — jobs for the same key run in order.

Sometimes it is asked as "implement a blocking queue" (4.14). Sometimes as "design a job processor".

What is happening internally?

  • A bounded ArrayBlockingQueue sits between the producers and a fixed pool of consumer threads. Bounded means it has a maximum size.
  • Back-pressure: when the queue is full, put blocks — the producer waits. So producers slow down instead of filling all memory.
  • Poison pills: a special "stop" job. We add one per consumer after all the real jobs. A consumer that takes a pill exits.
  • (The hand-written queue built with a lock and conditions is in 4.14.)

Think of a railway reservation counter with a fixed number of chairs in the waiting area. When all chairs are full, new people must wait outside. The clerks keep serving from the front.

How does it work?

Producer:

  1. put 50 jobs into the queue. If the queue is full, it waits.
  2. Then put one POISON job per consumer.

Each consumer:

  1. Loop and call take(). It waits if the queue is empty.
  2. If the job is the pill, exit the loop.
  3. Else process the job and loop again.

The main thread shuts down the pool and waits for all threads to finish.

Example

// FILE: JobQueueDemo.java
import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;

public class JobQueueDemo {
    record Job(int id, String payload) {}
    static final Job POISON = new Job(-1, "STOP");

    public static void main(String[] args) throws Exception {
        BlockingQueue<Job> queue = new ArrayBlockingQueue<>(10);
        AtomicInteger processed = new AtomicInteger();
        int consumers = 3;
        ExecutorService pool = Executors.newFixedThreadPool(consumers + 1);

        pool.submit(() -> {                                            // producer
            try {
                for (int i = 1; i <= 50; i++) queue.put(new Job(i, "order-" + i));   // blocks when full
                for (int i = 0; i < consumers; i++) queue.put(POISON);              // one pill per consumer
            } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
            return null;
        });
        for (int c = 0; c < consumers; c++) {
            pool.submit(() -> {
                try {
                    while (true) {
                        Job j = queue.take();
                        if (j == POISON) break;
                        processed.incrementAndGet();                   // do the work
                    }
                } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
                return null;
            });
        }
        pool.shutdown();
        pool.awaitTermination(5, TimeUnit.SECONDS);
        System.out.println("processed=" + processed.get());           // 50
    }
}

Trace:

  1. The queue (capacity 10) fills up quickly.
  2. The producer blocks while the 3 consumers take jobs out.
  3. Space opens up, so the producer continues.
  4. Each consumer exits when it gets its pill.
  5. All 50 jobs are processed exactly once.

When would I use it?

  • In-process work queues: sending notifications, writing audit records, enriching data.
  • Batching writers, which collect items and write them together.
  • As the mental model for Kafka consumers and thread pools — they work the same way inside.

What can go wrong?

  • Unbounded queues. There is no back-pressure, so memory can fill up.
  • Fewer pills than consumers. Some consumers wait for work forever and never exit.
  • A consumer thread dying on an exception. Catch errors per job, and send failed jobs to a retry list or a dead-letter list (a parking place for jobs that keep failing).
  • Losing in-memory jobs on a crash. For work that must not be lost, use a durable broker (like Kafka) or an outbox table.

Interview questions

Q1. How do you preserve ordering per key with multiple consumers? Give each worker its own queue. Send each job to a fixed worker using hash(key) % workers. All jobs for one key then go to one worker, which handles them in order. This is exactly how Kafka partitions keep per-key order.

Q2. How would you add retries? Keep an attempt count in the job. On failure, put it back in the queue after a delay, using a DelayQueue or a scheduled executor. Retry up to N times. After that, move it to a dead-letter list.

Q3. Why bounded? So that overload causes back-pressure (producers wait) or rejection. Without a bound, the queue grows without limit and you get an OOM (OutOfMemoryError).

10.7 Vending Machine

Why?

In simple words: A vending machine behaves differently depending on what "mode" it is in. Before you pick a product, it should not take your coins. The State pattern gives each mode its own class, so the machine always knows what is allowed right now.

This is the standard, most-asked question for the State pattern. (The State pattern means: put the behaviour for each mode of an object into its own class, and switch between those classes as the mode changes.)

The interviewer checks three things:

  • Can you model a machine where the allowed actions depend on its current state?
  • Can you handle money correctly, including giving back change? This is called change-making.
  • Can you update stock atomically? Atomic means all-or-nothing: either the whole sale happens, or nothing changes.

What is happening internally?

  • Entities (the main objects):
  • Machine — the context, meaning the object that holds the current state and passes each action to it.
  • Product — has a code, a name and a price.
  • Inventory — a Map<code, qty> that says how many of each product are left.
  • Cash box — an EnumMap<Coin, count> that says how many of each coin the machine holds.
  • The coins the customer has inserted so far.
  • States: 1. Idle — the only allowed action is select. 2. HasSelection — you can insert coin or cancel. 3. Dispensing — the product comes out. 4. Back to Idle.

If you try an action the current state does not allow, the default method in the State interface throws an exception. So invalid actions fail loudly instead of silently doing something wrong. - Change-making: the machine uses a greedy approach. Greedy means: always take the largest coin that still fits, then repeat. This gives the fewest coins for canonical coin systems — coin sets like Indian coins, where greedy is always the best answer. - The calculation runs on a copy of the cash box. - The real cash box is updated only if exact change was possible. So a failed attempt never damages the real cash box.

How does it work?

  1. select(code) while Idle: check that the product exists and is in stock. Then move to HasSelection.
  2. insert(coin): add the coin to the inserted coins and to the cash box. When the total inserted is ≥ the price, start dispensing.
  3. Dispense:
  4. Calculate the change due.
  5. If exact change is not possible, refund everything and stay in a safe state.
  6. Otherwise, reduce the stock by one, give the change, and reset to Idle.
  7. cancel() while in HasSelection: give back all inserted coins.

Example

// FILE: VendingMachineDemo.java
import java.util.*;

public class VendingMachineDemo {
    enum Coin { ONE(1), TWO(2), FIVE(5), TEN(10), TWENTY(20); final int value; Coin(int v) { value = v; } }
    record Product(String code, String name, int price) {}

    interface State {
        default void select(Machine m, String code) { throw new IllegalStateException("Can't select now"); }
        default void insert(Machine m, Coin c) { throw new IllegalStateException("Select a product first"); }
        default List<Coin> cancel(Machine m) { throw new IllegalStateException("Nothing to cancel"); }
    }

    static class Idle implements State {
        public void select(Machine m, String code) {
            Product p = m.products.get(code);
            if (p == null) throw new IllegalArgumentException("Unknown product");
            if (m.stock.getOrDefault(code, 0) == 0) throw new IllegalStateException("Out of stock");
            m.selected = p;
            m.state = new HasSelection();
        }
    }

    static class HasSelection implements State {
        public void insert(Machine m, Coin c) {
            m.inserted.add(c);
            m.cashbox.merge(c, 1, Integer::sum);
            if (m.insertedTotal() >= m.selected.price()) m.dispense();
        }
        public List<Coin> cancel(Machine m) {
            List<Coin> refund = new ArrayList<>(m.inserted);
            refund.forEach(c -> m.cashbox.merge(c, -1, Integer::sum));
            m.reset();
            return refund;
        }
    }

    static class Machine {
        final Map<String, Product> products = new HashMap<>();
        final Map<String, Integer> stock = new HashMap<>();
        final Map<Coin, Integer> cashbox = new EnumMap<>(Coin.class);
        final List<Coin> inserted = new ArrayList<>();
        Product selected; State state = new Idle();
        List<Coin> lastChange = List.of();

        void addProduct(Product p, int qty) { products.put(p.code(), p); stock.merge(p.code(), qty, Integer::sum); }
        void loadCoins(Coin c, int n) { cashbox.merge(c, n, Integer::sum); }

        void select(String code) { state.select(this, code); }
        void insert(Coin c) { state.insert(this, c); }
        List<Coin> cancel() { return state.cancel(this); }

        int insertedTotal() { return inserted.stream().mapToInt(c -> c.value).sum(); }

        void dispense() {
            int changeDue = insertedTotal() - selected.price();
            List<Coin> change = makeChange(changeDue);
            if (change == null) {                                   // can't make change: refund everything
                lastChange = cancel();
                throw new IllegalStateException("Exact change only; refunded " + lastChange);
            }
            stock.merge(selected.code(), -1, Integer::sum);
            System.out.println("Dispensed " + selected.name() + ", change " + change);
            lastChange = change;
            reset();
        }

        /** Greedy change from largest coin; works for canonical coin systems like INR. */
        private List<Coin> makeChange(int amount) {
            List<Coin> out = new ArrayList<>();
            Map<Coin, Integer> temp = new EnumMap<>(cashbox);
            Coin[] desc = Coin.values(); Arrays.sort(desc, Comparator.comparingInt((Coin c) -> c.value).reversed());
            for (Coin c : desc) {
                while (amount >= c.value && temp.getOrDefault(c, 0) > 0) { amount -= c.value; temp.merge(c, -1, Integer::sum); out.add(c); }
            }
            if (amount != 0) return null;
            cashbox.clear(); cashbox.putAll(temp);
            return out;
        }

        void reset() { inserted.clear(); selected = null; state = new Idle(); }
    }

    public static void main(String[] args) {
        Machine m = new Machine();
        m.addProduct(new Product("A1", "Chips", 15), 2);
        m.loadCoins(Coin.FIVE, 5); m.loadCoins(Coin.ONE, 10);
        m.select("A1"); m.insert(Coin.TEN); m.insert(Coin.TEN);       // pays 20, change 5
        m.select("A1"); m.insert(Coin.TWO);
        System.out.println("Refund " + m.cancel());
        System.out.println("Stock A1=" + m.stock.get("A1"));          // 1
    }
}

Trace:

  1. Chips cost ₹15.
  2. You insert ₹10 + ₹10 = ₹20. The change is ₹5, given as one FIVE coin.
  3. A second purchase is started with ₹2, then cancelled. The refund is [TWO].
  4. Stock of A1 goes from 2 to 1.

When would I use it?

Use this for any device or workflow that has modes — situations where what you are allowed to do depends on where you are in the process. Examples:

  • ATMs, kiosks and payment terminals.
  • Order lifecycles (placed → packed → shipped → delivered).
  • Trip lifecycles in a ride app.

The general recipe is: the State pattern plus atomic transitions (each move from one state to the next either fully happens or does not happen at all).

What can go wrong?

  • if (state == …) checks spread across every method. This is hard to read and easy to break. The State pattern exists to remove these.
  • Giving out the product before confirming that change can be made. Then the customer gets the product but the machine cannot pay back the balance.
  • Concurrency — many users acting at the same time — if several users can use the machine at once. Fix: make the machine's operations synchronized (only one thread at a time), or model one session at a time.
  • Using double for money. A double cannot store values like 0.1 exactly, so small rounding errors creep in. Use whole numbers (paise or rupees) instead.

Interview questions

Q1. Why the State pattern here? Each state allows a different set of actions. If you put each state's behaviour in its own class, every transition is written clearly in one place, and illegal actions simply cannot happen — the state class rejects them.

Q2. When does greedy change-making fail and what's the alternative? Greedy fails for non-canonical coin sets, where taking the biggest coin first is not always best. Example: coins 1, 3, 4 and amount 6 — greedy gives 4+1+1 (three coins), but 3+3 (two coins) is better. The alternative is dynamic programming (DP) — the classic "coin change" problem — extended to respect the limited number of each coin in the cash box.

Q3. How would you add UPI payment? Add a PaymentMethod strategy with implementations for coins, UPI and card. (A strategy is a swappable piece of behaviour behind one interface.) When any payment method completes, it moves the machine to the dispensing state.

10.8 Elevator System

Why?

In simple words: Each lift keeps a list of floors to stop at above it and below it. It keeps going in one direction until no stops are left that way, then turns around. A controller decides which lift should answer each button press.

This question tests several things at once:

  • Scheduling logic — deciding the order in which floors are served.
  • State per elevator — each lift tracks its own floor and direction.
  • A dispatcher that chooses which elevator answers a call. This is a Strategy (a swappable rule behind one interface).
  • Reasoning about efficiency and fairness — fast service overall, but no floor left waiting forever.
  • Thread safety — how you make a real-time controller safe when many requests arrive at once.

What is happening internally?

  • Entities (the main objects):
  • Elevator — has an id, current floor, direction, a set of stops above (up stops) and a set of stops below (down stops).
  • Controller — holds all the elevators and the dispatch strategy.
  • Hall calls — the button pressed on a floor (floor + direction wanted).
  • Car calls — the destination button pressed inside the lift.
  • Data structures: each elevator has two TreeSet<Integer>s — one for stops above, one for stops below. A TreeSet keeps numbers sorted, so finding the next stop takes O(log n) — very fast, even with many stops.
  • Algorithm: LOOK. 1. Keep moving in the current direction while there are stops ahead. 2. When no stops are left that way, reverse.

This is the same idea used to move the arm of a hard disk efficiently. - Patterns: - Strategy — DispatchStrategy, so the rule for picking a lift can be swapped. - State — direction or idle, stored as an enum. - Mediator — the controller sits in the middle and coordinates all the elevators, so they don't talk to each other directly.

How does it work?

  1. A hall call comes in. The strategy picks the elevator with the lowest cost (a score — lower is better): - An idle elevator costs its distance from the caller. - An elevator already moving toward the caller, in the same direction the caller wants, also costs just its distance. - Any other elevator gets a big penalty added.
  2. The chosen elevator adds that floor to its up set or down set.
  3. On each tick() (one step of time), every elevator moves one floor in its direction. - If the new floor is in its set, it stops there. - If it has no stops ahead, it reverses or becomes idle.

Example

// FILE: ElevatorDemo.java
import java.util.*;

public class ElevatorDemo {
    enum Direction { UP, DOWN, IDLE }

    static class Elevator {
        final int id; int floor = 0; Direction dir = Direction.IDLE;
        final TreeSet<Integer> upStops = new TreeSet<>(), downStops = new TreeSet<>();
        Elevator(int id) { this.id = id; }

        void addStop(int target) {
            if (target == floor && dir == Direction.IDLE) { System.out.println("E" + id + " doors open at " + floor); return; }
            if (target > floor) upStops.add(target); else if (target < floor) downStops.add(target);
            else (dir == Direction.UP ? downStops : upStops).add(target);   // same floor while moving: next pass
            if (dir == Direction.IDLE) dir = target >= floor ? Direction.UP : Direction.DOWN;
        }

        /** Move one floor per tick (LOOK). */
        void step() {
            if (dir == Direction.UP) {
                if (upStops.isEmpty()) { dir = downStops.isEmpty() ? Direction.IDLE : Direction.DOWN; return; }
                floor++;
                if (upStops.remove(floor)) System.out.println("E" + id + " stops at " + floor + " (up)");
            } else if (dir == Direction.DOWN) {
                if (downStops.isEmpty()) { dir = upStops.isEmpty() ? Direction.IDLE : Direction.UP; return; }
                floor--;
                if (downStops.remove(floor)) System.out.println("E" + id + " stops at " + floor + " (down)");
            }
        }
        int pending() { return upStops.size() + downStops.size(); }
    }

    interface DispatchStrategy { Elevator choose(List<Elevator> elevators, int floor, Direction wanted); }

    /** Prefer an elevator already moving toward the caller in the same direction, else the nearest idle, else least busy. */
    static class NearestSuitable implements DispatchStrategy {
        public Elevator choose(List<Elevator> es, int floor, Direction wanted) {
            return es.stream().min(Comparator.comparingInt(e -> cost(e, floor, wanted))).orElseThrow();
        }
        private int cost(Elevator e, int floor, Direction wanted) {
            int dist = Math.abs(e.floor - floor);
            if (e.dir == Direction.IDLE) return dist;
            boolean onTheWay = (e.dir == Direction.UP && wanted == Direction.UP && e.floor <= floor)
                            || (e.dir == Direction.DOWN && wanted == Direction.DOWN && e.floor >= floor);
            return onTheWay ? dist : dist + 2 * 100 + e.pending();   // heavily penalise wrong-way elevators
        }
    }

    static class Controller {
        final List<Elevator> elevators = new ArrayList<>();
        final DispatchStrategy strategy;
        final int floors;
        Controller(int n, int floors, DispatchStrategy s) {
            for (int i = 0; i < n; i++) elevators.add(new Elevator(i));
            this.floors = floors; this.strategy = s;
        }
        void hallCall(int floor, Direction d) {
            validate(floor);
            Elevator e = strategy.choose(elevators, floor, d);
            System.out.println("Hall call " + floor + " " + d + " -> E" + e.id);
            e.addStop(floor);
        }
        void carCall(int elevatorId, int floor) { validate(floor); elevators.get(elevatorId).addStop(floor); }
        void tick() { elevators.forEach(Elevator::step); }
        private void validate(int f) { if (f < 0 || f >= floors) throw new IllegalArgumentException("bad floor " + f); }
    }

    public static void main(String[] args) {
        Controller c = new Controller(2, 10, new NearestSuitable());
        c.hallCall(5, Direction.UP);
        c.hallCall(2, Direction.DOWN);
        for (int t = 0; t < 6; t++) c.tick();
        c.carCall(0, 8);
        for (int t = 0; t < 6; t++) c.tick();
    }
}

Trace:

  1. Both elevators start at floor 0.
  2. The call at floor 5 goes to E0.
  3. The call at floor 2 goes to E1, because E1 is idle and nearest.
  4. The ticks move E1 to floor 2 and E0 to floor 5.
  5. Then someone inside E0 presses 8 (a car call). E0 keeps going up to 8.

When would I use it?

Use this for scheduling problems — deciding who serves what, and in which order:

  • Banks of elevators in a building.
  • Disk scheduling (moving the disk arm efficiently).
  • Delivery or rider dispatch (13.13, 13.18).
  • Sending jobs to a pool of workers.

What can go wrong?

  • Starvation: a floor is never served because the lifts keep turning around near busy floors. LOOK prevents this — it puts a limit on how long any floor can wait, because the lift always finishes its current direction before reversing.
  • Giving every call to the nearest elevator without checking its direction. A lift that is close but going the wrong way may take a long time to arrive.
  • Concurrency: requests can arrive while the elevators are moving (during a tick). The cleanest fix is a single event-loop thread — one thread that reads requests from a queue and handles them one by one. This is simpler and safer than putting locks everywhere.

Interview questions

Q1. Which scheduling algorithm would you use and why? LOOK (or SCAN): serve all stops in the current direction, then reverse. It is efficient, and unlike "always go to the nearest request" it is starvation-free — no floor waits forever.

Q2. How do you choose which elevator answers a hall call? Use a cost function that looks at distance, whether the lift is going the right direction, and its current load. Put it behind a DispatchStrategy interface, so you can swap in other strategies — for example, one tuned for peak hours or one that saves energy.

Q3. How would you handle concurrency? Use one controller thread that processes a queue of requests and ticks, one at a time. This is actor style — one owner of the data that handles messages in order. Because only one thread touches the shared state, there are no race conditions (bugs where two threads change the same data at once).

10.9 Splitwise (Expense Sharing)

Why?

In simple words: Friends share bills, and the app remembers who owes whom. At the end, it works out the fewest payments needed to settle everyone, instead of everyone paying everyone.

This question tests:

  • Strategy — different ways to split a bill (equal, exact amounts, percentages), each a swappable class.
  • Money handling — especially rounding, so no paisa is lost or created.
  • Modelling balances between users — who owes whom, and how much.
  • Debt simplification — the algorithm that reduces the number of payments.

What is happening internally?

  • Entities (the main objects):
  • User.
  • Share — a user plus the amount they owe, stored in paise (₹1 = 100 paise).
  • Expenses.
  • Balances — a Map<user, Map<user, paise>>. A positive value means the other user owes me.
  • Strategies: EqualSplit, ExactSplit and PercentSplit, all behind one SplitStrategy interface. The right one is picked from a map using the SplitType.
  • Rounding:
  • All money is in whole paise, never decimals.
  • When the total does not divide evenly, the leftover paise are handed out in a fixed, predictable way: the first remainder users each get +1 paisa.
  • So the shares always add up exactly to the total.
  • Simplification: 1. Work out each user's net balance — what they are owed minus what they owe. 2. Repeatedly match the person owed the most (the largest creditor) with the person who owes the most (the largest debtor). 3. Two max-heaps (priority queues that always give you the biggest item first) make this fast.

How does it work?

  1. addExpense(paidBy, total, users, type, values):
  2. The chosen strategy produces the shares.
  3. For every share that is not the payer's own, increase "user owes payer" on the payer's side.
  4. Decrease the same amount on the user's side (the reverse entry).
  5. net(): add up each user's row to get their net balance.
  6. simplify():
  7. Put creditors in one heap and debtors in another.
  8. Take the top of each. Settle min(credit, debt) between them.
  9. If either still has something left, push the remainder back into its heap.
  10. Repeat until a heap is empty.

Example

// FILE: SplitwiseDemo.java
import java.util.*;

public class SplitwiseDemo {
    record User(String id, String name) {}
    enum SplitType { EQUAL, EXACT, PERCENT }
    record Share(User user, long paise) {}

    interface SplitStrategy { List<Share> split(long totalPaise, List<User> users, List<Double> values); }

    static class EqualSplit implements SplitStrategy {
        public List<Share> split(long total, List<User> users, List<Double> ignored) {
            long base = total / users.size(), rem = total % users.size();
            List<Share> out = new ArrayList<>();
            for (int i = 0; i < users.size(); i++) out.add(new Share(users.get(i), base + (i < rem ? 1 : 0))); // distribute leftover paise
            return out;
        }
    }
    static class ExactSplit implements SplitStrategy {
        public List<Share> split(long total, List<User> users, List<Double> amounts) {
            long sum = 0; List<Share> out = new ArrayList<>();
            for (int i = 0; i < users.size(); i++) { long p = Math.round(amounts.get(i)); sum += p; out.add(new Share(users.get(i), p)); }
            if (sum != total) throw new IllegalArgumentException("exact amounts must add up to total");
            return out;
        }
    }
    static class PercentSplit implements SplitStrategy {
        public List<Share> split(long total, List<User> users, List<Double> pct) {
            double s = pct.stream().mapToDouble(Double::doubleValue).sum();
            if (Math.abs(s - 100.0) > 1e-9) throw new IllegalArgumentException("percentages must add to 100");
            List<Share> out = new ArrayList<>(); long assigned = 0;
            for (int i = 0; i < users.size(); i++) {
                long p = i == users.size() - 1 ? total - assigned : Math.round(total * pct.get(i) / 100.0);
                assigned += p; out.add(new Share(users.get(i), p));
            }
            return out;
        }
    }

    static class ExpenseService {
        private final Map<SplitType, SplitStrategy> strategies = Map.of(
                SplitType.EQUAL, new EqualSplit(), SplitType.EXACT, new ExactSplit(), SplitType.PERCENT, new PercentSplit());
        /** balance[a][b] > 0 means b owes a. Stored as nested maps for sparse groups. */
        private final Map<String, Map<String, Long>> balances = new HashMap<>();

        synchronized void addExpense(User paidBy, long totalPaise, List<User> users, SplitType type, List<Double> values) {
            for (Share s : strategies.get(type).split(totalPaise, users, values)) {
                if (s.user().equals(paidBy)) continue;
                adjust(paidBy.id(), s.user().id(), s.paise());
                adjust(s.user().id(), paidBy.id(), -s.paise());
            }
        }
        private void adjust(String a, String b, long d) {
            balances.computeIfAbsent(a, k -> new HashMap<>()).merge(b, d, Long::sum);
        }
        Map<String, Long> net() {                                 // + means others owe this user
            Map<String, Long> net = new TreeMap<>();
            balances.forEach((a, m) -> m.values().forEach(v -> net.merge(a, v, Long::sum)));
            return net;
        }
        /** Greedy settlement: largest creditor paid by largest debtor. */
        List<String> simplify() {
            PriorityQueue<long[]> cred = new PriorityQueue<>((x, y) -> Long.compare(y[1], x[1]));
            PriorityQueue<long[]> debt = new PriorityQueue<>((x, y) -> Long.compare(y[1], x[1]));
            List<String> ids = new ArrayList<>(net().keySet());
            Map<String, Long> net = net();
            for (int i = 0; i < ids.size(); i++) {
                long v = net.get(ids.get(i));
                if (v > 0) cred.add(new long[]{i, v}); else if (v < 0) debt.add(new long[]{i, -v});
            }
            List<String> tx = new ArrayList<>();
            while (!cred.isEmpty() && !debt.isEmpty()) {
                long[] c = cred.poll(), d = debt.poll();
                long amt = Math.min(c[1], d[1]);
                tx.add(ids.get((int) d[0]) + " pays " + ids.get((int) c[0]) + " " + amt / 100.0);
                if (c[1] > amt) cred.add(new long[]{c[0], c[1] - amt});
                if (d[1] > amt) debt.add(new long[]{d[0], d[1] - amt});
            }
            return tx;
        }
    }

    public static void main(String[] args) {
        User a = new User("A", "Asha"), b = new User("B", "Bharat"), c = new User("C", "Chirag");
        ExpenseService s = new ExpenseService();
        s.addExpense(a, 90000, List.of(a, b, c), SplitType.EQUAL, null);                 // A paid 900 for all
        s.addExpense(b, 30000, List.of(a, b, c), SplitType.PERCENT, List.of(50.0, 25.0, 25.0));
        System.out.println(s.net());           // {A=45000, B=-7500, C=-37500}
        System.out.println(s.simplify());      // [C pays A 375.0, B pays A 75.0]
    }
}

Trace:

  1. A pays ₹900 for A, B and C. That is ₹300 each. So B owes A ₹300, and C owes A ₹300.
  2. B pays ₹300, split 50/25/25. So A owes B ₹150, and C owes B ₹75.
  3. Net balances: A +450, B −75, C −375.
  4. Simplified: C pays A ₹375, and B pays A ₹75.

That is two payments instead of four.

When would I use it?

  • Any ledger-style balance tracking — where you record every transaction and work out balances from them.
  • Settlement and reconciliation systems (checking that two sets of records agree).
  • Marketplace payouts to sellers.
  • Inter-company netting — companies cancelling out what they owe each other so only the difference is paid.

What can go wrong?

  • Problems with input and money values:
  • Using double for money. Small rounding errors add up over time (rounding drift).
  • Percentages that do not add up to 100.
  • Exact amounts that do not add up to the total.
  • Claiming the greedy simplification is optimal (the best possible). Finding the true minimum number of payments is NP-hard in general — no known fast method exists for large groups. Greedy is a good heuristic — a practical method that gives a good answer, not always the perfect one.
  • Editing or deleting expenses by changing balances directly. Instead, keep expenses as immutable records (never changed after saving). Then either recompute balances from them, or post reversal entries that cancel the old expense.

Interview questions

Q1. How do you handle ₹100 split three ways? Work in paise: 3333, 3333 and 3334. Hand out the leftover paisa in a fixed, predictable way, so the shares always add up exactly to the total.

Q2. How do you minimise settlements? First work out each user's net balance. Then repeatedly pair the largest creditor with the largest debtor, using heaps — this runs in O(n log n). Mention that finding the exact minimum number of payments is NP-hard, so this greedy method is a good approximation, not a guaranteed best.

Q3. How would you support groups and expense edits? Keep balances scoped to each group. Store expenses as immutable records, and treat an edit as a reversal of the old expense plus a new expense. Then either recompute the balances or apply just the differences (deltas).

10.10 BookMyShow (Movie Ticket Booking)

Why?

In simple words: When you pick seats, the system blocks them for you for a few minutes while you pay. The hard part is making sure two people clicking at the same moment can never get the same seat.

This question tests:

  • A realistic domain: cities → theatres → screens → shows → seats.
  • A booking lifecycle with temporary holds — seats are reserved for a short time while you pay.
  • Payment integration.
  • Above all, concurrency on shared inventory — many users touching the same seats at the same time. The rule is simple: no seat may ever be sold twice.

What is happening internally?

  • Entities (the main objects):
  • Show — holds its seats, the state of each seat, and a lock.
  • Seat — id, category and price.
  • SeatState — AVAILABLE, HELD or BOOKED; plus which booking ID holds it and when the hold expires.
  • Booking — starts as PENDING, then becomes CONFIRMED, EXPIRED or CANCELLED.
  • Concurrency strategy:
  • One ReentrantLock per show. So users only wait for each other if they are booking the same show. Different shows run in parallel.
  • Inside the lock, first check all the requested seats, then mark all of them. This is all-or-nothing: you get every seat you asked for, or none.
  • Holds expire after N minutes.
  • An expired hold is treated as available the next time someone tries to book. This is called lazy expiry — you clean up only when you need to.
  • A background sweeper job can also clean up old holds.
  • confirm is idempotent — calling it twice gives the same result as calling it once. So if the payment gateway sends the same success callback twice, the second call just returns the same booking.

How does it work?

  1. hold(user, show, seats):
  2. Lock the show.
  3. Check that every seat is AVAILABLE, or HELD with an expired hold.
  4. Mark all of them HELD, with the booking ID and expiry time.
  5. Create a PENDING booking.
  6. Unlock.
  7. Payment happens outside the lock, so a slow payment does not block other users.
  8. confirm(bookingId, paymentOk):
  9. Lock the show.
  10. If the booking is already final, just return it (idempotent).
  11. If payment failed, or the hold expired, or the seats were taken by someone else — release the seats and mark the booking CANCELLED or EXPIRED. Refund if the user already paid.
  12. Otherwise, mark the seats BOOKED and the booking CONFIRMED.

Example

// FILE: BookMyShowDemo.java
import java.time.*;
import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicLong;
import java.util.concurrent.locks.ReentrantLock;

public class BookMyShowDemo {
    enum SeatStatus { AVAILABLE, HELD, BOOKED }
    enum BookingStatus { PENDING, CONFIRMED, EXPIRED, CANCELLED }
    record Seat(String id, String category, long pricePaise) {}

    static final class SeatState { SeatStatus status = SeatStatus.AVAILABLE; String bookingId; Instant holdUntil; }

    static final class Show {
        final String id; final Map<String, Seat> seats = new LinkedHashMap<>();
        final Map<String, SeatState> state = new HashMap<>();
        final ReentrantLock lock = new ReentrantLock();             // one lock per show: contention is per show only
        Show(String id, List<Seat> seatList) { this.id = id; seatList.forEach(s -> { seats.put(s.id(), s); state.put(s.id(), new SeatState()); }); }
    }

    static final class Booking {
        final String id, userId, showId; final List<String> seatIds; final long amount; final Instant expiresAt;
        volatile BookingStatus status = BookingStatus.PENDING;
        Booking(String id, String u, String show, List<String> seats, long amt, Instant exp) {
            this.id = id; userId = u; showId = show; seatIds = List.copyOf(seats); amount = amt; expiresAt = exp;
        }
    }

    static class BookingService {
        private final Map<String, Show> shows = new ConcurrentHashMap<>();
        private final Map<String, Booking> bookings = new ConcurrentHashMap<>();
        private final AtomicLong seq = new AtomicLong();
        private final Duration holdFor; private final Clock clock;
        BookingService(Duration holdFor, Clock clock) { this.holdFor = holdFor; this.clock = clock; }

        void addShow(Show s) { shows.put(s.id, s); }

        Booking hold(String userId, String showId, List<String> seatIds) {
            Show show = Objects.requireNonNull(shows.get(showId), "no show");
            Instant now = clock.instant();
            show.lock.lock();
            try {
                for (String sid : seatIds) {                                   // 1. check ALL seats first
                    SeatState st = show.state.get(sid);
                    if (st == null) throw new IllegalArgumentException("bad seat " + sid);
                    boolean expiredHold = st.status == SeatStatus.HELD && st.holdUntil.isBefore(now);
                    if (st.status != SeatStatus.AVAILABLE && !expiredHold)
                        throw new IllegalStateException("Seat " + sid + " not available");
                }
                String bid = "B" + seq.incrementAndGet();
                long amount = seatIds.stream().mapToLong(s -> show.seats.get(s).pricePaise()).sum();
                Instant until = now.plus(holdFor);
                for (String sid : seatIds) {                                   // 2. then mark ALL (all-or-nothing)
                    SeatState st = show.state.get(sid);
                    st.status = SeatStatus.HELD; st.bookingId = bid; st.holdUntil = until;
                }
                Booking b = new Booking(bid, userId, showId, seatIds, amount, until);
                bookings.put(bid, b);
                return b;
            } finally { show.lock.unlock(); }
        }

        Booking confirm(String bookingId, boolean paymentOk) {
            Booking b = Objects.requireNonNull(bookings.get(bookingId));
            Show show = shows.get(b.showId);
            show.lock.lock();
            try {
                if (b.status != BookingStatus.PENDING) return b;               // idempotent
                boolean stillHeld = b.seatIds.stream().allMatch(s -> bookingId.equals(show.state.get(s).bookingId)
                        && show.state.get(s).status == SeatStatus.HELD);
                if (!paymentOk || !stillHeld || clock.instant().isAfter(b.expiresAt)) {
                    release(show, b); b.status = paymentOk ? BookingStatus.EXPIRED : BookingStatus.CANCELLED;
                    return b;                                                   // caller refunds if payment succeeded
                }
                b.seatIds.forEach(s -> show.state.get(s).status = SeatStatus.BOOKED);
                b.status = BookingStatus.CONFIRMED;
                return b;
            } finally { show.lock.unlock(); }
        }

        private void release(Show show, Booking b) {
            for (String s : b.seatIds) {
                SeatState st = show.state.get(s);
                if (b.id.equals(st.bookingId) && st.status == SeatStatus.HELD) { st.status = SeatStatus.AVAILABLE; st.bookingId = null; st.holdUntil = null; }
            }
        }
    }

    public static void main(String[] args) throws Exception {
        List<Seat> seats = new ArrayList<>();
        for (int i = 1; i <= 5; i++) seats.add(new Seat("A" + i, "GOLD", 25000));
        BookingService svc = new BookingService(Duration.ofMinutes(10), Clock.systemUTC());
        svc.addShow(new Show("S1", seats));

        // 10 users race for seats A1 + A2: exactly one must win
        ExecutorService pool = Executors.newFixedThreadPool(10);
        List<Future<String>> results = new ArrayList<>();
        for (int u = 0; u < 10; u++) {
            String user = "u" + u;
            results.add(pool.submit(() -> {
                try { return svc.hold(user, "S1", List.of("A1", "A2")).id; } catch (IllegalStateException e) { return null; }
            }));
        }
        List<String> winners = new ArrayList<>();
        for (Future<String> f : results) if (f.get() != null) winners.add(f.get());
        pool.shutdown();
        System.out.println("winners=" + winners.size());                             // 1
        System.out.println(svc.confirm(winners.get(0), true).status);                // CONFIRMED
    }
}

Trace:

  1. 10 threads race for seats A1 + A2.
  2. The first thread to get the show lock holds both seats.
  3. The other 9 threads find the seats HELD and fail.
  4. Result: exactly one winner, and its confirmation succeeds.

When would I use it?

Use this for any limited inventory where there is a delay between choosing and paying:

  • Flight and hotel seats.
  • Flash-sale stock (13.19).
  • Appointment slots.
  • Coupons that can only be redeemed a limited number of times.

What can go wrong?

  • Checking seats one by one and marking them one by one. You can end up holding only some of the seats (a partial hold).
  • Using one global lock for everything. Then no two shows can be booked in parallel.
  • Keeping the lock held while calling the payment gateway. Payment is slow, so every other user of that show waits.
  • Holds that never expire. Seats stay stuck forever.
  • Payment succeeding after the hold expired. You need a refund path for this case.
  • At scale, in-memory locks do not work across several server instances — each server has its own lock. Move the seat state to a shared store:
  • The database: a conditional UPDATE … WHERE status='AVAILABLE' OR hold_until < now(), then check how many rows were updated. If fewer rows changed than seats requested, someone else got there first.
  • Redis: SET seat:{show}:{seat} bookingId NX PX 600000. NX means "only set if it does not already exist", and PX 600000 makes it expire after 10 minutes.

Interview questions

Q1. How do you prevent double booking? Check and hold all the requested seats atomically (all-or-nothing). In a single server, do this under a per-show lock. In a distributed system, use a conditional multi-row UPDATE and verify the updated row count, or use Redis SET NX.

Q2. How do seat holds work? Seats move to HELD, with a booking ID and an expiry time. If the user confirms within that window, the seats become BOOKED. When the hold expires — detected lazily on the next attempt, or by a sweeper job — the seats are released.

Q3. What if payment succeeds after the hold expired and someone else took the seat? Mark the booking EXPIRED and trigger a refund. The payment callback handler must be idempotent, so a repeated callback does not refund twice or book twice.

10.11 Loyalty Points Ledger (your domain)

Why?

In simple words: Instead of just storing "you have 500 points", you write down every earn, spend and expiry as a separate line, like a bank passbook. The balance is just the total of those lines, so you can always explain and check it.

This is your own system. So treat it as the design you can defend three levels deep — expect the interviewer to keep asking "and then what?".

It tests:

  • Ledger modelling — recording every change as an entry.
  • Idempotency — the same request processed twice has the same effect as once.
  • FIFO expiry — first in, first out: the oldest points are used first and expire first.
  • Per-account concurrency — two operations on the same account must not clash.

It also doubles as your best behavioural story ("tell me about something you built").

What is happening internally?

  • A ledger, not just a balance:
  • Every change is an immutable entry (never edited after saving): ACCRUAL (points earned), REDEMPTION (points spent), REVERSAL (an undo), or EXPIRY.
  • The balance is a cached sum of the entries. It is updated in the same transaction as the entry, so the two always match.
  • Idempotency:
  • Each operation carries an idempotency key — a unique ID from the source, such as the order ID or the redemption request ID.
  • If the same key arrives again, the system returns the original entry instead of posting the points a second time.
  • Lots for FIFO expiry:
  • Each accrual creates a lot — a batch of points with "points still remaining" and an expiry date.
  • Redemptions use up the oldest lots first.
  • So at expiry time, the system knows exactly how many points from each accrual are still unused.
  • Concurrency: handle one operation at a time per account. This is called serialising per account.
  • In memory: synchronized (account).
  • In the database: a row lock or an atomic conditional update.
  • Patterns:
  • Command — each operation is stored as an entry.
  • Repository — one class hides how entries are stored.
  • An injected Clock — time is passed in, so tests can control "now".

How does it work?

  1. accrue(acc, pts, key):
  2. Check the idempotency key.
  3. Lock the account.
  4. Add an ACCRUAL entry.
  5. Push a new lot that expires after the validity period.
  6. redeem(acc, pts, key):
  7. Check the idempotency key.
  8. Lock the account.
  9. Expire any lots that are already due.
  10. Check that the balance is enough.
  11. Use up lots, oldest first.
  12. Add a REDEMPTION entry (with negative points).
  13. expireDue(acc):
  14. Remove every lot whose expiry date has passed.
  15. Add one EXPIRY entry for the points those lots still had.

Example

// FILE: LoyaltyLedgerDemo.java
import java.time.*;
import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicLong;

public class LoyaltyLedgerDemo {
    enum EntryType { ACCRUAL, REDEMPTION, REVERSAL, EXPIRY }
    record Entry(long id, String accountId, EntryType type, long points, String idemKey, Instant at, Long refId) {}

    static final class Lot {                    // an accrual with remaining points, consumed FIFO
        final long entryId; final Instant expiresAt; long remaining;
        Lot(long entryId, long pts, Instant exp) { this.entryId = entryId; this.remaining = pts; this.expiresAt = exp; }
    }

    static final class Account {
        final String id; long balance;
        final List<Entry> entries = new ArrayList<>();
        final Deque<Lot> lots = new ArrayDeque<>();          // ordered by accrual time
        Account(String id) { this.id = id; }
    }

    static class InsufficientPoints extends RuntimeException { InsufficientPoints(String m) { super(m); } }

    static class LedgerService {
        private final Map<String, Account> accounts = new ConcurrentHashMap<>();
        private final Map<String, Entry> byIdemKey = new ConcurrentHashMap<>();
        private final AtomicLong seq = new AtomicLong();
        private final Clock clock; private final Period validity;
        LedgerService(Clock clock, Period validity) { this.clock = clock; this.validity = validity; }

        Account account(String id) { return accounts.computeIfAbsent(id, Account::new); }

        Entry accrue(String accountId, long points, String idemKey) {
            if (points <= 0) throw new IllegalArgumentException("points must be > 0");
            return idempotent(idemKey, () -> {
                Account a = account(accountId);
                synchronized (a) {                                        // per-account serialisation
                    Entry e = append(a, EntryType.ACCRUAL, points, idemKey, null);
                    Instant exp = clock.instant().atZone(ZoneOffset.UTC).plus(validity).toInstant();
                    a.lots.addLast(new Lot(e.id(), points, exp));
                    return e;
                }
            });
        }

        Entry redeem(String accountId, long points, String idemKey) {
            return idempotent(idemKey, () -> {
                Account a = account(accountId);
                synchronized (a) {
                    expireDue(a);                                         // never redeem expired points
                    if (a.balance < points) throw new InsufficientPoints("have " + a.balance + ", need " + points);
                    long left = points;
                    while (left > 0) {                                    // consume oldest lots first
                        Lot lot = a.lots.peekFirst();
                        long take = Math.min(left, lot.remaining);
                        lot.remaining -= take; left -= take;
                        if (lot.remaining == 0) a.lots.pollFirst();
                    }
                    return append(a, EntryType.REDEMPTION, -points, idemKey, null);
                }
            });
        }

        /** Expire lots past their date; returns points expired. Run daily by a scheduler, and lazily before redemption. */
        long expireDue(Account a) {
            synchronized (a) {
                long expired = 0; Instant now = clock.instant();
                while (!a.lots.isEmpty() && !a.lots.peekFirst().expiresAt.isAfter(now)) expired += a.lots.pollFirst().remaining;
                if (expired > 0) append(a, EntryType.EXPIRY, -expired, "expiry-" + a.id + "-" + now, null);
                return expired;
            }
        }

        private Entry idempotent(String key, Callable<Entry> op) {
            Entry existing = byIdemKey.get(key);
            if (existing != null) return existing;
            synchronized (key.intern()) {                                 // demo only; in prod a DB unique constraint does this
                existing = byIdemKey.get(key);
                if (existing != null) return existing;
                try { Entry e = op.call(); byIdemKey.put(key, e); return e; }
                catch (RuntimeException e) { throw e; }
                catch (Exception e) { throw new IllegalStateException(e); }
            }
        }

        private Entry append(Account a, EntryType t, long pts, String key, Long ref) {
            Entry e = new Entry(seq.incrementAndGet(), a.id, t, pts, key, clock.instant(), ref);
            a.entries.add(e); a.balance += pts;
            return e;
        }
    }

    static class MutableClock extends Clock {
        Instant now = Instant.parse("2026-01-01T00:00:00Z");
        public ZoneId getZone() { return ZoneOffset.UTC; } public Clock withZone(ZoneId z) { return this; }
        public Instant instant() { return now; }
    }

    public static void main(String[] args) {
        MutableClock clock = new MutableClock();
        LedgerService svc = new LedgerService(clock, Period.ofMonths(12));
        svc.accrue("acc1", 500, "order-1");
        clock.now = Instant.parse("2026-06-01T00:00:00Z");
        svc.accrue("acc1", 300, "order-2");
        svc.accrue("acc1", 300, "order-2");                  // duplicate event: ignored
        svc.redeem("acc1", 600, "redeem-1");                 // takes 500 from lot1, 100 from lot2
        System.out.println("balance=" + svc.account("acc1").balance);                  // 200
        clock.now = Instant.parse("2027-06-02T00:00:00Z");   // lot2 (expires 2027-06-01) is now due
        System.out.println("expired=" + svc.expireDue(svc.account("acc1")) + " balance=" + svc.account("acc1").balance); // 200, 0
    }
}

Trace:

  1. January: +500 points. This is lot 1, expiring January 2027.
  2. June: +300 points. This is lot 2, expiring June 2027.
  3. The duplicate order-2 event is ignored.
  4. Redeem 600: all 500 from lot 1, plus 100 from lot 2. Balance is now 200.
  5. On 2 June 2027, the remaining 200 in lot 2 expire. Balance is now 0.

When would I use it?

Use this for points, wallets, credits, gift cards, prepaid balances and inventory movements. In other words, anywhere that auditability (being able to show the history of every change) and "never post the same thing twice" matter more than raw speed.

What can go wrong?

  • Keeping only a balance that you overwrite, with no ledger. Then there is no audit trail, and nothing to reconcile against (cross-check the balance with).
  • Checking idempotency outside the transaction or lock. Two duplicate requests can then both pass the check at the same moment and both get posted. In the database, the real guard is a unique constraint on (tenant_id, idempotency_key).
  • Redeeming points that should already have expired. Always run expiry before a redemption.
  • Reversals that do not put the points back into the right lots.

Interview questions

Q1. How do you prevent duplicate reward postings when events are retried? Store an idempotency key for each source event. Protect it with a unique constraint, saved in the same transaction as the ledger entry. If a duplicate arrives, return the existing entry instead of posting again.

Q2. How does FIFO expiry work? Each accrual becomes a lot, with its remaining points and an expiry date. Redemptions use up the oldest lots first. Expiry then removes whatever is left in lots that are past their date.

Q3. How do balance and ledger stay consistent? Both are updated in one transaction, so they change together or not at all. On top of that, a reconciliation job regularly checks, for each account, that the sum of the entries equals the cached balance.

10.12 Rules Engine for Incentives (your domain)

Why?

In simple words: Admins describe incentive rules as data — "if sales ≥ X and visits ≥ Y, pay Z". The engine reads that data, checks each sales rep against it, and pays out. No developer needs to change code for a new scheme.

This is also your own domain.

Product teams want admins to define schemes like this without code changes:

sales of group X ≥ ₹50,000 AND (visits ≥ 20 OR new outlets ≥ 5) → slab payout

It tests several patterns:

  • Composite — a tree where single items and groups are treated the same way.
  • Specification — a business rule as an object that answers "does this pass?".
  • Strategy — swappable payout calculations.
  • Factory — building the objects from a stored definition (parsing).
  • Explainability — telling the user why they did or did not qualify.

What is happening internally?

  • Conditions form a tree:
  • A sealed Condition interface. (Sealed means only the listed classes may implement it.)
  • Threshold leaves — a single check like "visits ≥ 20".
  • All / Any / Not composites — AND, OR and NOT over other conditions.
  • Together this is Composite + Specification + Interpreter. (Interpreter means: walking a tree of objects to "run" a small language.)
  • Payouts are strategies:
  • Flat — a fixed amount.
  • PercentOf(metric) — a percentage of some metric.
  • Slabs(metric, ranges) — a fixed amount depending on which range the metric falls in.
  • Context: the facts for one user for one period, as a Map<metric, value>. These are computed earlier, upstream — pre-aggregated (totals already calculated), not worked out from raw data during evaluation.
  • Factory: parse(Map) builds the condition tree from a JSON-like definition stored per tenant (per client company).
  • Explainability: every evaluation also returns the why, for example: "sales 81000 GTE 50000 ✓, visits 14 GTE 20 ✗ …".

How does it work?

engine.evaluate(schemes, ctx) does this for each scheme:

  1. Evaluate the condition tree recursively — each node asks its children first, then combines their answers. Build the explanation along the way.
  2. If the condition passes, calculate the payout using the scheme's payout strategy.
  3. Return one outcome per scheme.

Example

// FILE: IncentiveRulesDemo.java
import java.util.*;
import java.util.function.*;

public class IncentiveRulesDemo {
    /** Facts about one user for one period. */
    record Context(String userId, Map<String, Double> metrics) {
        double get(String k) { return metrics.getOrDefault(k, 0.0); }
    }
    record Result(boolean passed, String explanation) {}

    // ---------- Conditions: Composite + Specification ----------
    sealed interface Condition permits Threshold, All, Any, Not {
        Result eval(Context c);
    }
    enum Op { GTE, LTE, EQ;
        boolean test(double a, double b) { return switch (this) { case GTE -> a >= b; case LTE -> a <= b; case EQ -> a == b; }; }
    }
    record Threshold(String metric, Op op, double value) implements Condition {
        public Result eval(Context c) {
            double actual = c.get(metric);
            boolean ok = op.test(actual, value);
            return new Result(ok, "%s=%.0f %s %.0f %s".formatted(metric, actual, op, value, ok ? "✓" : "✗"));
        }
    }
    record All(List<Condition> parts) implements Condition {
        public Result eval(Context c) {
            List<Result> rs = parts.stream().map(p -> p.eval(c)).toList();
            return new Result(rs.stream().allMatch(Result::passed), "ALL(" + String.join(", ", rs.stream().map(Result::explanation).toList()) + ")");
        }
    }
    record Any(List<Condition> parts) implements Condition {
        public Result eval(Context c) {
            List<Result> rs = parts.stream().map(p -> p.eval(c)).toList();
            return new Result(rs.stream().anyMatch(Result::passed), "ANY(" + String.join(", ", rs.stream().map(Result::explanation).toList()) + ")");
        }
    }
    record Not(Condition inner) implements Condition {
        public Result eval(Context c) { Result r = inner.eval(c); return new Result(!r.passed(), "NOT(" + r.explanation() + ")"); }
    }

    // ---------- Payouts: Strategy ----------
    interface Payout { long amountPaise(Context c); }
    record Flat(long paise) implements Payout { public long amountPaise(Context c) { return paise; } }
    record PercentOf(String metric, double pct) implements Payout {
        public long amountPaise(Context c) { return Math.round(c.get(metric) * 100 * pct / 100.0); }
    }
    record Slab(double from, double to, long paise) {}
    record Slabs(String metric, List<Slab> slabs) implements Payout {
        public long amountPaise(Context c) {
            double v = c.get(metric);
            return slabs.stream().filter(s -> v >= s.from() && v < s.to()).mapToLong(Slab::paise).findFirst().orElse(0);
        }
    }

    record Scheme(String id, String name, Condition eligibility, Payout payout) {}
    record Outcome(String schemeId, String userId, boolean qualified, long payoutPaise, String why) {}

    static class Engine {
        List<Outcome> evaluate(List<Scheme> schemes, Context ctx) {
            List<Outcome> out = new ArrayList<>();
            for (Scheme s : schemes) {
                Result r = s.eligibility().eval(ctx);
                out.add(new Outcome(s.id(), ctx.userId(), r.passed(), r.passed() ? s.payout().amountPaise(ctx) : 0, r.explanation()));
            }
            return out;
        }
    }

    // ---------- Factory: build conditions from a simple definition (would be JSON in production) ----------
    static Condition parse(Map<String, Object> def) {
        String type = (String) def.get("type");
        return switch (type) {
            case "threshold" -> new Threshold((String) def.get("metric"), Op.valueOf((String) def.get("op")), ((Number) def.get("value")).doubleValue());
            case "all" -> new All(children(def));
            case "any" -> new Any(children(def));
            case "not" -> new Not(parse(castMap(def.get("child"))));
            default -> throw new IllegalArgumentException("unknown condition " + type);
        };
    }
    @SuppressWarnings("unchecked") static Map<String, Object> castMap(Object o) { return (Map<String, Object>) o; }
    @SuppressWarnings("unchecked") static List<Condition> children(Map<String, Object> def) {
        return ((List<Object>) def.get("children")).stream().map(o -> parse(castMap(o))).toList();
    }

    public static void main(String[] args) {
        Condition cond = parse(Map.of("type", "all", "children", List.of(
                Map.of("type", "threshold", "metric", "sales_groupX", "op", "GTE", "value", 50000),
                Map.of("type", "any", "children", List.of(
                        Map.of("type", "threshold", "metric", "visits", "op", "GTE", "value", 20),
                        Map.of("type", "threshold", "metric", "new_outlets", "op", "GTE", "value", 5))))));

        Scheme festive = new Scheme("S1", "Festive push", cond,
                new Slabs("sales_groupX", List.of(new Slab(50000, 75000, 200000), new Slab(75000, Double.MAX_VALUE, 350000))));
        Engine engine = new Engine();
        Context rep1 = new Context("rep1", Map.of("sales_groupX", 81000.0, "visits", 14.0, "new_outlets", 6.0));
        Context rep2 = new Context("rep2", Map.of("sales_groupX", 52000.0, "visits", 11.0, "new_outlets", 1.0));
        engine.evaluate(List.of(festive), rep1).forEach(System.out::println);
        engine.evaluate(List.of(festive), rep2).forEach(System.out::println);
    }
}

Trace:

  • rep1: 1. Sales 81,000 ✓. 2. Visits 14 ✗, but new outlets 6 ✓ — so the ANY part passes. 3. So rep1 qualifies. 4. Sales fall in the 75,000+ slab, so the payout is ₹3,500.
  • rep2: 1. Sales 52,000 ✓. 2. Visits 11 ✗ and new outlets 1 ✗ — so the ANY part fails. 3. So rep2 does not qualify. The explanation shows exactly why.

When would I use it?

Use this anywhere business users need to configure logic themselves:

  • Incentive and commission schemes.
  • Promotions and coupon eligibility.
  • Fraud rules.
  • Feature-flag targeting (who sees a new feature).
  • Pricing rules.

What can go wrong?

  • Rules changing in the middle of a period. Fix: version the scheme definitions, and evaluate each period with the version that was active when the period started.
  • Very deep nesting or very expensive conditions. Fix: validate definitions when they are saved — limit the depth and allow only known metrics.
  • Evaluating against raw transaction data for every user on every request. This is slow. Fix: pre-aggregate the metrics (13.14).
  • Payouts that cannot be reproduced later. Fix: store the evaluation trace and the input values with every payout.

Interview questions

Q1. How would you let admins create rules without deployments? Store rule trees as data (JSON). When loading, parse them into Composite condition objects and payout strategies. Validate them when they are saved, and keep versions.

Q2. How do you explain to a sales rep why they didn't qualify? Each node in the tree returns pass/fail plus a short description. The engine joins these into a full explanation and stores it with the outcome.

Q3. How does this scale to hundreds of thousands of reps? Use pre-aggregated metrics per user and period. Run the evaluation in parallel — it is stateless (it keeps no data between calls), so it can be split by tenant across workers. Cache the scheme definitions so they are not loaded again for every rep (13.14).

10.13 Snake and Ladder

Why?

In simple words: Snake and Ladder is a small game, but it shows whether you can split a problem into clean classes. The key trick: a snake and a ladder are the same thing — a jump from one cell to another.

Interviewers often use this as a warm-up for machine coding. (Machine coding means writing working code for a design problem in 60–90 minutes.)

It checks four things:

  • Clean entity design — the right classes, each with one job.
  • Pluggable dice — the dice is an interface, so you can swap it. This is the Strategy pattern. It also makes testing easy, because a test can use fixed dice that always roll the same numbers (deterministic dice).
  • Board validation — rejecting a bad board before the game starts.
  • The game loop — the turn-by-turn logic.

What is happening internally?

  • Entities (the main classes):
  • Board — holds the size and one Map<Integer, Integer> of jumps. Snakes and ladders both go into this one map, because both are just "if you land on cell X, move to cell Y".
  • Player — just a name.
  • Game — keeps a turn queue (whose turn is next) and each player's position.
  • Dice — an interface with one method, roll().
  • Validation (checks when building the board):
  • A snake must go down. A ladder must go up.
  • Two jumps cannot start on the same cell.
  • Every jump must stay inside the board.
  • Rules you must decide and state clearly:
  • You must land exactly on 100. If the roll takes you past 100 (overshoot), you stay where you are.
  • Jumps can chain: a ladder may end on a snake's head. The code follows jumps in a loop until it reaches a cell with no jump.

How does it work?

Each turn goes like this:

  1. Roll the dice.
  2. Calculate next = pos + roll.
  3. If next is past the last cell, the player stays in place.
  4. Otherwise, follow any jumps (snake or ladder) from next.
  5. If next == size, this player wins and the game ends.
  6. Otherwise, put the player at the back of the turn queue and move to the next player.

Example

// FILE: SnakeLadderDemo.java
import java.util.*;

public class SnakeLadderDemo {
    interface Dice { int roll(); }
    static class RandomDice implements Dice {
        private final Random rnd; private final int count;
        RandomDice(long seed, int count) { rnd = new Random(seed); this.count = count; }
        public int roll() { int s = 0; for (int i = 0; i < count; i++) s += rnd.nextInt(6) + 1; return s; }
    }
    record Player(String name) {}

    static class Board {
        final int size; final Map<Integer, Integer> jumps = new HashMap<>();   // snakes and ladders unified
        Board(int size) { this.size = size; }
        Board snake(int head, int tail) { check(head > tail, "snake must go down"); add(head, tail); return this; }
        Board ladder(int bottom, int top) { check(top > bottom, "ladder must go up"); add(bottom, top); return this; }
        private void add(int from, int to) {
            check(from > 1 && from < size && to >= 1 && to <= size, "out of board");
            check(!jumps.containsKey(from), "cell already has a jump");
            jumps.put(from, to);
        }
        int resolve(int pos) { while (jumps.containsKey(pos)) pos = jumps.get(pos); return pos; }
        private static void check(boolean ok, String msg) { if (!ok) throw new IllegalArgumentException(msg); }
    }

    static class Game {
        private final Board board; private final Dice dice;
        private final Deque<Player> turns; private final Map<Player, Integer> pos = new HashMap<>();
        Game(Board b, Dice d, List<Player> players) { board = b; dice = d; turns = new ArrayDeque<>(players); players.forEach(p -> pos.put(p, 0)); }

        Player play() {
            while (true) {
                Player p = turns.pollFirst();
                int roll = dice.roll(), cur = pos.get(p), next = cur + roll;
                if (next <= board.size) next = board.resolve(next); else next = cur;   // exact landing rule
                pos.put(p, next);
                System.out.printf("%s rolled %d: %d -> %d%n", p.name(), roll, cur, next);
                if (next == board.size) return p;
                turns.addLast(p);
            }
        }
    }

    public static void main(String[] args) {
        Board b = new Board(100).ladder(4, 56).ladder(12, 50).ladder(20, 98).snake(99, 7).snake(54, 19).snake(70, 55);
        Player winner = new Game(b, new RandomDice(42, 1), List.of(new Player("Asha"), new Player("Ravi"))).play();
        System.out.println("Winner: " + winner.name());
    }
}

Trace: the dice use a fixed seed (new Random(42)). A seed is the starting number for the random generator. With the same seed, you get the same "random" numbers every time. So every run prints the same game.

  • Each line shows the roll and the move.
  • Ladders lift a player up: 4→56, 12→50, 20→98.
  • Snakes drop a player down: 99→7, 54→19, 70→55.
  • If a roll would take a player past 100, they stay in place. They win only when they roll the exact number needed.

When would I use it?

  • Any turn-based game, like Ludo or other board games.
  • As practice for entity modelling (choosing classes and their fields).
  • As practice for making randomness testable — random in production, fixed in tests.

What can go wrong?

  • Two separate maps for snakes and ladders. The logic gets duplicated. One jumps map is enough.
  • Real randomness in tests. Tests become flaky — they pass sometimes and fail sometimes. Inject a deterministic Dice instead.
  • Infinite jump loops. If jumps form a cycle (A→B, B→A), resolve never ends. Validate that no chain of jumps forms a cycle.
  • Game state shared across rooms. If many games run at once, two rooms could change the same positions. Create one Game object per room.

Interview questions

Q1. How do you make the game testable? I pass a Dice strategy into the game instead of creating dice inside it. In production it is random; in tests I pass dice that return a fixed sequence of rolls, so every test gives the same result.

Q2. How would you add "roll again on a 6, three 6s forfeits the turn"? I would put this rule in the turn loop as a separate rule object, say TurnPolicy. The game asks the policy what happens after each roll. Then each rule variant is its own class, and you can plug in a different one without changing the game loop.

10.14 In-Memory Pub-Sub (a mini Kafka)

Why?

In simple words: You build a tiny Kafka in one program. Publishers add messages to the end of a list, and each subscriber reads that list at its own speed, remembering how far it has reached.

This problem tests how well you can design a message broker. A broker is the middleman that takes messages from publishers and hands them to subscribers.

It checks these ideas:

  • Topics — named channels, like "orders".
  • Ordered logs — messages kept in the order they arrived.
  • Independent subscribers — each one tracks its own position, called an offset.
  • At-least-once delivery — every message is delivered, but sometimes more than once.
  • Back-pressure — a slow reader must not overload or slow down the system.
  • Thread safety — many threads reading and writing at the same time without corrupting data.

It connects directly to the Kafka discussion in 11.13.

What is happening internally?

  • Topic = a List<Message> that you only add to at the end. This is called an append-only log. A message's offset is simply its index in the list (0, 1, 2…).
  • Subscription = four things together: the topic, its current offset, a handler (the code that processes a message), and a worker thread.
  • Pull-based delivery. Each subscriber pulls (reads) messages at its own pace. The broker does not push to them. So a slow subscriber never blocks the others.
  • Topic.read(offset, timeout) waits until a message exists at that offset. It uses Java's wait/notifyAll: the reader sleeps, and a new message wakes it up.
  • Delivery rule: the offset moves forward only after the handler succeeds. If the handler fails, the same offset is tried again. So no message is skipped — this gives at-least-once delivery.
  • Replay: to process old messages again, just set a subscription's offset back to an earlier number.

Think of a railway announcement register. The clerk writes each new announcement on the next line. Each department keeps its own bookmark showing which line it has read up to. A slow department doesn't stop anyone else.

How does it work?

  1. publish(topic, key, body):
  2. Take the topic's lock.
  3. Add the message at the end of the log.
  4. Call notifyAll to wake any readers waiting for a new message.
  5. Each subscription's worker thread runs a loop:
  6. Read the message at its current offset. If there is none yet, wait.
  7. Run the handler on the message.
  8. If the handler succeeds, move the offset forward by one.
  9. If the handler throws an exception, sleep briefly and retry the same offset.
  10. close() stops all the worker threads.

Example

// FILE: PubSubDemo.java
import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicLong;
import java.util.function.Consumer;

public class PubSubDemo {
    record Message(long offset, String key, String body) {}

    static final class Topic {
        final String name; private final List<Message> log = new ArrayList<>();
        Topic(String name) { this.name = name; }
        synchronized long append(String key, String body) {
            long off = log.size(); log.add(new Message(off, key, body)); notifyAll(); return off;
        }
        /** Blocks until a message at `offset` exists or timeout. */
        synchronized Message read(long offset, long timeoutMs) throws InterruptedException {
            long deadline = System.currentTimeMillis() + timeoutMs;
            while (offset >= log.size()) {
                long wait = deadline - System.currentTimeMillis();
                if (wait <= 0) return null;
                wait(wait);
            }
            return log.get((int) offset);
        }
    }

    static final class Subscription implements Runnable {
        final String id; final Topic topic; final Consumer<Message> handler;
        final AtomicLong offset; volatile boolean running = true;
        Subscription(String id, Topic t, long startOffset, Consumer<Message> h) { this.id = id; topic = t; offset = new AtomicLong(startOffset); handler = h; }
        public void run() {
            try {
                while (running) {
                    Message m = topic.read(offset.get(), 200);
                    if (m == null) continue;
                    try { handler.accept(m); offset.incrementAndGet(); }        // advance only after success
                    catch (RuntimeException e) { Thread.sleep(50); }             // retry same offset (at-least-once)
                }
            } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        }
        void resetTo(long off) { offset.set(off); }                              // replay
    }

    static class Broker implements AutoCloseable {
        private final Map<String, Topic> topics = new ConcurrentHashMap<>();
        private final List<Subscription> subs = new CopyOnWriteArrayList<>();
        private final ExecutorService workers = Executors.newCachedThreadPool();
        void createTopic(String name) { topics.putIfAbsent(name, new Topic(name)); }
        long publish(String topic, String key, String body) { return get(topic).append(key, body); }
        Subscription subscribe(String subId, String topic, long fromOffset, Consumer<Message> handler) {
            Subscription s = new Subscription(subId, get(topic), fromOffset, handler);
            subs.add(s); workers.submit(s); return s;
        }
        private Topic get(String t) { return Optional.ofNullable(topics.get(t)).orElseThrow(() -> new IllegalArgumentException("no topic " + t)); }
        public void close() throws InterruptedException { subs.forEach(s -> s.running = false); workers.shutdown(); workers.awaitTermination(2, TimeUnit.SECONDS); }
    }

    public static void main(String[] args) throws Exception {
        try (Broker b = new Broker()) {
            b.createTopic("orders");
            List<String> fast = new CopyOnWriteArrayList<>(), slow = new CopyOnWriteArrayList<>();
            b.subscribe("loyalty", "orders", 0, m -> fast.add(m.body()));
            b.subscribe("analytics", "orders", 0, m -> { slow.add(m.body()); sleep(20); });
            for (int i = 1; i <= 5; i++) b.publish("orders", "outlet-" + i, "order-" + i);
            Thread.sleep(600);
            System.out.println("loyalty=" + fast + "\nanalytics=" + slow);
        }
    }
    static void sleep(long ms) { try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); } }
}

Trace: there are two subscribers. "loyalty" is fast. "analytics" is slow (it sleeps 20 ms per message). Both receive all 5 orders, in the correct order. Analytics simply finishes later — and it does not slow loyalty down at all.

When would I use it?

  • To understand how Kafka, Pulsar and Redis Streams work inside.
  • For an event bus inside one application (in-process), where parts of the code publish and listen to events.
  • When designing notification fan-out — one event sent to many listeners.

What can go wrong?

  • Push-based delivery. If the broker pushes each message to every subscriber, a slow subscriber can block the publisher.
  • Moving the offset before processing. If the handler then fails, that message is skipped forever. This is at-most-once delivery, and it loses messages on failure.
  • A log that grows forever in memory. Eventually you run out of memory. Add retention: drop old segments (chunks of the log) older than X.
  • Poison messages retried forever. A poison message is one that always fails, for example because of bad data. It blocks the subscriber in an endless retry. Add a maximum attempt count, then move the message to a dead-letter topic (a side topic for failed messages).

Interview questions

Q1. How would you add partitions and ordering per key? Keep several logs per topic — each log is a partition. Choose the partition with hash(key) % partitions, so the same key always goes to the same partition. Ordering is then guaranteed within a partition, which means all messages for one key stay in order.

Q2. How do consumer groups work? Subscribers in one group share the partitions between them. Each partition is read by only one member of the group. The group stores one shared offset per partition. Different groups are fully independent — each group gets every message.

Q3. At-least-once vs at-most-once here? If you move the offset after processing, you get at-least-once: nothing is lost, but a crash can cause duplicates. If you move it before processing, you get at-most-once: no duplicates, but a crash can lose a message. Because duplicates can happen, consumers should be idempotent — processing the same message twice must give the same result as processing it once.

10.15 Library Management System

Why?

In simple words: A library has one book (title, author) but many physical copies of it on the shelf. Keep those as two separate classes, and the rest — borrowing, returning, fines, waiting lists — becomes simple.

This is a classic first-round LLD problem. (LLD = low-level design: classes, methods and how they work together.)

The main thing interviewers look for: do you separate Book from BookCopy?

  • Book = catalogue details (metadata) — ISBN, title, author.
  • BookCopy = one physical item, with its own status.

It also tests:

  • Loans and loan limits per member.
  • Fines, using the Strategy pattern so the fine rule can change.
  • Reservations — a waiting queue, plus an Observer-style notification when a book comes back.
  • Search by title or author.

What is happening internally?

  • Entities:
  • Book — ISBN, title, author.
  • BookCopy — id, status (AVAILABLE / LOANED / ON_HOLD), and which member it is held for.
  • Member — includes the maximum number of loans allowed.
  • Loan — the copy, the member, the due date, and the returned date.
  • Collections (how data is stored):
  • Copies grouped by ISBN.
  • A reservation queue per ISBN (Deque<Member>) — first come, first served.
  • Active loans per member.
  • Patterns used:
  • Strategy — FinePolicy, so the fine rule can be swapped.
  • Observer-like — a Notifier that tells the next member when a book is returned.
  • Facade — one service class (LibraryService) that hides all the details behind simple methods.
  • Injected Clock — the service asks a Clock for "today", so tests can move time forward.

How does it work?

  1. Borrow:
  2. Check the member has not hit their loan limit.
  3. Find a copy that is AVAILABLE, or one ON_HOLD for this same member.
  4. Mark the copy LOANED.
  5. Create a loan due in 14 days.
  6. Reserve: if no copy is available, add the member to the end of the book's waiting queue.
  7. Return:
  8. Close the loan (set the returned date).
  9. If someone is waiting, hold the copy for the first person in the queue and notify them.
  10. If nobody is waiting, mark the copy AVAILABLE.
  11. Calculate the fine by comparing the due date with the return date.

Example

// FILE: LibraryDemo.java
import java.time.*;
import java.util.*;
import java.util.concurrent.atomic.AtomicLong;

public class LibraryDemo {
    record Book(String isbn, String title, String author) {}
    enum CopyStatus { AVAILABLE, LOANED, ON_HOLD }
    static final class BookCopy { final String id; final Book book; CopyStatus status = CopyStatus.AVAILABLE; String heldFor;
        BookCopy(String id, Book b) { this.id = id; this.book = b; } }
    record Member(String id, String name, int maxLoans) {}
    static final class Loan { final long id; final BookCopy copy; final Member member; final LocalDate due; LocalDate returned;
        Loan(long id, BookCopy c, Member m, LocalDate due) { this.id = id; copy = c; member = m; this.due = due; } }

    interface FinePolicy { long fineRupees(LocalDate due, LocalDate returned); }
    static class PerDayFine implements FinePolicy {
        private final long perDay, cap; PerDayFine(long perDay, long cap) { this.perDay = perDay; this.cap = cap; }
        public long fineRupees(LocalDate due, LocalDate ret) { long late = Math.max(0, Duration.between(due.atStartOfDay(), ret.atStartOfDay()).toDays()); return Math.min(cap, late * perDay); }
    }
    interface Notifier { void notify(Member m, String msg); }

    static class LibraryService {
        private final Map<String, Book> books = new HashMap<>();
        private final Map<String, List<BookCopy>> copiesByIsbn = new HashMap<>();
        private final Map<String, Deque<Member>> reservations = new HashMap<>();
        private final Map<String, List<Loan>> activeLoans = new HashMap<>();         // memberId -> loans
        private final Map<String, Member> members = new HashMap<>();
        private final AtomicLong seq = new AtomicLong();
        private final FinePolicy fines; private final Notifier notifier; private final Clock clock;
        private final Period loanPeriod = Period.ofDays(14);
        LibraryService(FinePolicy f, Notifier n, Clock c) { fines = f; notifier = n; clock = c; }

        void addMember(Member m) { members.put(m.id(), m); }
        void addCopies(Book b, int n) {
            books.putIfAbsent(b.isbn(), b);
            for (int i = 0; i < n; i++) copiesByIsbn.computeIfAbsent(b.isbn(), k -> new ArrayList<>()).add(new BookCopy(b.isbn() + "-" + (i + 1), b));
        }
        List<Book> search(String q) {
            String s = q.toLowerCase();
            return books.values().stream().filter(b -> b.title().toLowerCase().contains(s) || b.author().toLowerCase().contains(s)).toList();
        }

        synchronized Loan borrow(String memberId, String isbn) {
            Member m = Objects.requireNonNull(members.get(memberId), "no member");
            List<Loan> loans = activeLoans.computeIfAbsent(memberId, k -> new ArrayList<>());
            if (loans.size() >= m.maxLoans()) throw new IllegalStateException("loan limit reached");
            BookCopy copy = copiesByIsbn.getOrDefault(isbn, List.of()).stream()
                    .filter(c -> c.status == CopyStatus.AVAILABLE || (c.status == CopyStatus.ON_HOLD && memberId.equals(c.heldFor)))
                    .findFirst().orElseThrow(() -> new IllegalStateException("no copy available; reserve instead"));
            copy.status = CopyStatus.LOANED; copy.heldFor = null;
            Loan loan = new Loan(seq.incrementAndGet(), copy, m, LocalDate.now(clock).plus(loanPeriod));
            loans.add(loan);
            return loan;
        }

        synchronized void reserve(String memberId, String isbn) {
            reservations.computeIfAbsent(isbn, k -> new ArrayDeque<>()).addLast(members.get(memberId));
        }

        /** @return fine in rupees */
        synchronized long giveBack(long loanId) {
            Loan loan = activeLoans.values().stream().flatMap(List::stream).filter(l -> l.id == loanId).findFirst()
                    .orElseThrow(() -> new IllegalArgumentException("unknown loan"));
            loan.returned = LocalDate.now(clock);
            activeLoans.get(loan.member.id()).remove(loan);
            BookCopy copy = loan.copy;
            Deque<Member> queue = reservations.getOrDefault(copy.book.isbn(), new ArrayDeque<>());
            Member next = queue.pollFirst();
            if (next != null) {                                    // hold for the first reserver (Observer-style notify)
                copy.status = CopyStatus.ON_HOLD; copy.heldFor = next.id();
                notifier.notify(next, "'" + copy.book.title() + "' is ready for pickup");
            } else copy.status = CopyStatus.AVAILABLE;
            return fines.fineRupees(loan.due, loan.returned);
        }
    }

    static class MutableClock extends Clock {
        Instant now = Instant.parse("2026-10-05T10:00:00Z");
        public ZoneId getZone() { return ZoneOffset.UTC; } public Clock withZone(ZoneId z) { return this; } public Instant instant() { return now; }
    }

    public static void main(String[] args) {
        MutableClock clock = new MutableClock();
        LibraryService lib = new LibraryService(new PerDayFine(5, 200), (m, msg) -> System.out.println("notify " + m.name() + ": " + msg), clock);
        lib.addMember(new Member("m1", "Asha", 3)); lib.addMember(new Member("m2", "Ravi", 3));
        Book ddia = new Book("978-1449373320", "Designing Data-Intensive Applications", "Kleppmann");
        lib.addCopies(ddia, 1);
        System.out.println(lib.search("kleppmann").size());                     // 1
        Loan l = lib.borrow("m1", ddia.isbn());
        try { lib.borrow("m2", ddia.isbn()); } catch (IllegalStateException e) { System.out.println(e.getMessage()); }
        lib.reserve("m2", ddia.isbn());
        clock.now = clock.now.plus(Duration.ofDays(17));                       // 3 days late
        System.out.println("fine=" + lib.giveBack(l.id));                      // 15
        System.out.println("m2 got loan " + lib.borrow("m2", ddia.isbn()).copy.id);
    }
}

Trace:

  1. Asha borrows the only copy.
  2. Ravi tries to borrow it and fails, so he reserves it.
  3. Asha returns it 3 days late. At ₹5 per day, her fine is ₹15.
  4. The copy is held for Ravi, and he is notified.
  5. Ravi then borrows it.

When would I use it?

The Book/BookCopy split (shared details vs individual physical items) appears in many systems:

  • Inventory — SKU (the product type) vs a serialised item (one unit with its own serial number).
  • Rentals and equipment tracking.
  • Ticketing — the event vs each seat.

What can go wrong?

  • One class for both the book and the copy. Then you cannot track multiple copies of the same book.
  • Holds that never expire. If the reserving member never comes, the copy stays ON_HOLD forever and nobody can borrow it.
  • Allowing renewals while others are waiting. One member can keep the book forever while the queue waits.
  • A global synchronized service at scale. Every borrow and return waits for one lock, so the system gets slow. Use locking per ISBN, or database constraints, instead.

Interview questions

Q1. Why separate Book from BookCopy? All copies share the same details — title, author, ISBN — so those live once in Book. But each physical copy has its own status, location and loan history, so that lives in BookCopy. With one class you could not track several copies of the same title.

Q2. How do reservations work? Each book has a FIFO (first-in, first-out) queue of members. When a copy is returned, it is held for the first member in the queue, and that member is notified. If they don't collect it before the hold expires, it passes to the next member in the queue.

Q3. How would you search by title or author at scale? I would not scan every book. I would build an inverted index — a map from each word to the books that contain it — over the tokenised (split into words) titles and authors. In production, Elasticsearch does this for you.

10.16 Coffee Machine

Why?

In simple words: A drink needs several ingredients. The machine must either take all of them or take none — never use the milk and then find out there's no coffee.

This is a popular machine-coding problem. It has come up in several Indian product-company rounds.

It tests four things:

  • Data-driven recipes — each drink is described by data (a list of ingredients), not by its own class.
  • Atomic all-or-nothing deduction — removing several ingredients as one step. Atomic means it either fully happens or doesn't happen at all.
  • Parallel outlets — several drinks made at the same time.
  • Low-stock alerts — warnings when an ingredient runs low.

What is happening internally?

  • Recipes are data. A recipe is Recipe(name, Map<Ingredient, qty>). So adding a new drink means adding a new entry — configuration, not code.
  • Inventory. Stock is kept in an EnumMap<Ingredient, qty>. Each ingredient can have a low-stock threshold. Listeners get told when it goes below that mark (Observer pattern).
  • Atomic deduction. Inside one lock, the code does two passes: 1. Check every ingredient first. 2. Only if all are enough, deduct every ingredient.

So a drink never uses up milk and then fails because coffee is short. - Outlets. A thread pool with N threads, so N drinks brew in parallel. - Add-ons (extra shot, oat milk) use the Decorator pattern. A decorator wraps a base recipe and returns a new recipe with extra ingredients.

Think of a tiffin service packing a thali. The cook first checks there is enough dal, rice and sabzi. Only then does he start filling the box. He doesn't fill dal and then discover the rice is finished.

How does it work?

  1. order(recipe) sends the order to an outlet thread.
  2. That thread calls tryConsume(needs), which:
  3. Takes the lock.
  4. Collects every ingredient that is short.
  5. If anything is short, returns failure. Nothing has been deducted.
  6. Otherwise, deducts all ingredients and notes which ones crossed their low mark.
  7. Releases the lock.
  8. Low-stock listeners are notified outside the lock, so a slow listener doesn't block other drinks.
  9. The drink is brewed.

Example

// FILE: CoffeeMachineDemo.java
import java.util.*;
import java.util.concurrent.*;
import java.util.function.Consumer;

public class CoffeeMachineDemo {
    enum Ingredient { WATER, MILK, COFFEE, SUGAR, FOAM }
    record Recipe(String name, Map<Ingredient, Integer> needs) {}

    /** Decorator for add-ons: wraps a recipe and adds ingredients. */
    static Recipe withAddOn(Recipe base, String addOn, Ingredient i, int qty) {
        Map<Ingredient, Integer> m = new EnumMap<>(base.needs());
        m.merge(i, qty, Integer::sum);
        return new Recipe(base.name() + " + " + addOn, m);
    }

    static class Inventory {
        private final Map<Ingredient, Integer> stock = new EnumMap<>(Ingredient.class);
        private final Map<Ingredient, Integer> lowMark = new EnumMap<>(Ingredient.class);
        private final List<Consumer<Ingredient>> lowStockListeners = new CopyOnWriteArrayList<>();
        void refill(Ingredient i, int qty) { synchronized (this) { stock.merge(i, qty, Integer::sum); } }
        void setLowMark(Ingredient i, int qty) { lowMark.put(i, qty); }
        void onLowStock(Consumer<Ingredient> l) { lowStockListeners.add(l); }

        /** All-or-nothing deduction: check every ingredient, then deduct every ingredient, under one lock. */
        boolean tryConsume(Map<Ingredient, Integer> needs, List<Ingredient> missing) {
            List<Ingredient> low = new ArrayList<>();
            synchronized (this) {
                needs.forEach((i, q) -> { if (stock.getOrDefault(i, 0) < q) missing.add(i); });
                if (!missing.isEmpty()) return false;
                needs.forEach((i, q) -> {
                    int left = stock.merge(i, -q, Integer::sum);
                    if (left <= lowMark.getOrDefault(i, -1)) low.add(i);
                });
            }
            low.forEach(i -> lowStockListeners.forEach(l -> l.accept(i)));   // notify outside the lock
            return true;
        }
        synchronized int level(Ingredient i) { return stock.getOrDefault(i, 0); }
    }

    static class CoffeeMachine implements AutoCloseable {
        private final Inventory inventory; private final Map<String, Recipe> menu = new LinkedHashMap<>();
        private final ExecutorService outlets;
        CoffeeMachine(int outletCount, Inventory inv) { this.outlets = Executors.newFixedThreadPool(outletCount); this.inventory = inv; }
        void addRecipe(Recipe r) { menu.put(r.name(), r); }

        Future<String> order(Recipe r) {
            return outlets.submit(() -> {
                List<Ingredient> missing = new ArrayList<>();
                if (!inventory.tryConsume(r.needs(), missing)) return r.name() + " cannot be prepared: insufficient " + missing;
                Thread.sleep(50);                                            // brewing
                return r.name() + " is prepared";
            });
        }
        Future<String> order(String name) { return order(Objects.requireNonNull(menu.get(name), "unknown beverage")); }
        public void close() { outlets.shutdown(); }
    }

    public static void main(String[] args) throws Exception {
        Inventory inv = new Inventory();
        inv.refill(Ingredient.WATER, 500); inv.refill(Ingredient.MILK, 300); inv.refill(Ingredient.COFFEE, 60);
        inv.refill(Ingredient.SUGAR, 50); inv.refill(Ingredient.FOAM, 40);
        inv.setLowMark(Ingredient.COFFEE, 20);
        inv.onLowStock(i -> System.out.println("ALERT: low " + i));

        try (CoffeeMachine m = new CoffeeMachine(3, inv)) {
            Recipe latte = new Recipe("latte", Map.of(Ingredient.WATER, 50, Ingredient.MILK, 150, Ingredient.COFFEE, 20));
            m.addRecipe(new Recipe("espresso", Map.of(Ingredient.WATER, 30, Ingredient.COFFEE, 20)));
            m.addRecipe(latte);
            m.addRecipe(new Recipe("cappuccino", Map.of(Ingredient.WATER, 50, Ingredient.MILK, 100, Ingredient.COFFEE, 20, Ingredient.FOAM, 30)));
            List<Future<String>> results = List.of(m.order("latte"), m.order("cappuccino"), m.order("espresso"),
                                                   m.order(withAddOn(latte, "extra shot", Ingredient.COFFEE, 10)));
            for (Future<String> f : results) System.out.println(f.get());
            System.out.println("coffee left=" + inv.level(Ingredient.COFFEE) + ", milk left=" + inv.level(Ingredient.MILK));
        }
    }
}

Trace: the machine starts with 60 units of coffee.

  • Latte, cappuccino and espresso each take 20 coffee.
  • The extra-shot latte needs 30 coffee and 150 milk. There isn't enough of either, so it fails cleanly with "insufficient [MILK, COFFEE]". Nothing is deducted for it.
  • The low-coffee alert fires once coffee drops to the threshold of 20.

When would I use it?

Any time you must reserve several resources together, all-or-nothing:

  • An order that reserves several SKUs (products) at once.
  • A booking that holds several seats together.
  • A job that needs several resources before it can start.

What can go wrong?

  • Checking and deducting one ingredient at a time. If the third ingredient is short, the first two are already used up. This is partial consumption.
  • Per-ingredient locks taken in different orders. Thread A locks milk then waits for coffee; thread B locks coffee then waits for milk. Both wait forever — a deadlock. If you use one lock per ingredient (fine-grained locks), always lock them in enum order.
  • Notifying listeners while holding the lock. A slow listener then blocks all brewing.
  • A hard-coded class for every beverage instead of recipe data. Every new drink then needs new code.

Interview questions

Q1. How do you guarantee a drink never partially consumes ingredients? I check all the ingredients and deduct all of them inside one critical section (one locked block). If any check fails, nothing is deducted. The alternative is one lock per ingredient, but then I must always take the locks in the same fixed order to avoid deadlock.

Q2. How would you support N outlets? I use a fixed thread pool of N workers, or a semaphore with N permits. Orders are processed in parallel by these workers. The inventory is the one shared resource, and it is synchronised so only one thread changes the stock at a time.

Q3. How would you add a new beverage or an add-on? A new beverage is just a new recipe entry — data, not code. An add-on is a decorator: it takes a base recipe and returns a new recipe with the extra ingredient quantities added.

10.17 Cab Booking (Uber/Ola)

Why?

In simple words: When a rider books, you find nearby free drivers, offer the ride to the best one, and move to the next if they say no. The hard part is making sure two riders booking at the same moment never get the same driver.

This is a high-signal problem for SDE2 — it shows a lot about your skill in one question. It combines:

  • Spatial search — finding the nearest drivers on a map.
  • Matching — offering the ride to drivers, who can accept or decline.
  • A trip state machine — a trip moves through fixed stages in a fixed order.
  • Pricing strategies — fare rules, including surge pricing.
  • A real concurrency hazard — the same driver being assigned to two riders at once.

What is happening internally?

  • Entities:
  • Rider.
  • Driver — location, vehicle type, and status stored in an AtomicReference<DriverStatus>.
  • Trip — a state machine: REQUESTED → ACCEPTED → STARTED → COMPLETED / CANCELLED.
  • Location.
  • Spatial index (a structure for fast "who is near here?" lookups):
  • The map is cut into a uniform grid of square cells: cell = floor(coord / cellKm).
  • To find nearby drivers, scan the rider's cell, then the ring of cells around it, and so on, up to the radius.
  • At real scale you would use geohash, H3 or quadtrees instead — see 13.13.
  • Strategies (swappable rules):
  • MatchingStrategy — how to rank drivers: nearest first, weighted by rating, and so on.
  • PricingStrategy — base fare + per km + per minute, all multiplied by surge.
  • Concurrency:
  • driver.tryReserve() calls compareAndSet(AVAILABLE, ON_TRIP). This is CAS (compare-and-set): "change the status to ON_TRIP only if it is still AVAILABLE", done as one atomic step.
  • So only one rider can claim a driver, and you don't need a global lock.
  • DriverGateway.offer stands in for the driver's app, where the driver accepts or declines.

Think of a restaurant with a token board. Two waiters may both see table 5 is free. But only the one who flips the "occupied" sign first gets it. The other sees the sign and goes to the next table.

How does it work?

  1. request(rider, from, to, type):
  2. Try search radii of 1, 3 and 5 km, in that order.
  3. For each radius, get the candidate drivers near from, and rank them with the matching strategy.
  4. For each ranked driver, try to reserve them with CAS. If that fails, someone else got them — skip to the next.
  5. If reserved, send the offer to the driver.
  6. If the driver accepts, the trip becomes ACCEPTED and we return it.
  7. If the driver declines, release them and try the next driver.
  8. If no driver accepts in any radius, the trip becomes CANCELLED.
  9. start and complete move the trip forward through guarded state transitions. Guarded means the move is allowed only from the correct previous state.
  10. complete also:
  11. Calculates the fare.
  12. Moves the driver to the drop location in the spatial index.
  13. Releases the driver so they are AVAILABLE again.

Example

// FILE: CabBookingDemo.java
import java.util.*;
import java.util.concurrent.*;
import java.util.concurrent.atomic.*;

public class CabBookingDemo {
    record Location(double x, double y) { double dist(Location o) { return Math.hypot(x - o.x, y - o.y); } }  // km on a flat grid for the demo
    enum VehicleType { AUTO, MINI, SEDAN }
    enum DriverStatus { AVAILABLE, ON_TRIP, OFFLINE }
    enum TripStatus { REQUESTED, ACCEPTED, STARTED, COMPLETED, CANCELLED }

    static final class Driver {
        final String id; final VehicleType type; volatile Location loc;
        final AtomicReference<DriverStatus> status = new AtomicReference<>(DriverStatus.AVAILABLE);
        Driver(String id, VehicleType t, Location l) { this.id = id; type = t; loc = l; }
        boolean tryReserve() { return status.compareAndSet(DriverStatus.AVAILABLE, DriverStatus.ON_TRIP); }   // atomic: no double booking
        void release() { status.set(DriverStatus.AVAILABLE); }
    }
    record Rider(String id, String name) {}

    static final class Trip {
        final String id; final Rider rider; final Location from, to; final VehicleType type;
        volatile Driver driver; volatile TripStatus status = TripStatus.REQUESTED; volatile long fareRupees;
        Trip(String id, Rider r, Location from, Location to, VehicleType t) { this.id = id; rider = r; this.from = from; this.to = to; type = t; }
        synchronized void transition(TripStatus from, TripStatus to) {          // State machine guard
            if (status != from) throw new IllegalStateException("trip " + id + " is " + status + ", not " + from);
            status = to;
        }
    }

    /** Uniform grid spatial index: cell = floor(coord / cellKm). Nearby search scans rings of cells. */
    static class DriverIndex {
        private final double cellKm; private final ConcurrentHashMap<Long, Set<Driver>> cells = new ConcurrentHashMap<>();
        private final ConcurrentHashMap<String, Long> cellOf = new ConcurrentHashMap<>();
        DriverIndex(double cellKm) { this.cellKm = cellKm; }
        private long key(int cx, int cy) { return (((long) cx) << 32) ^ (cy & 0xffffffffL); }
        private int c(double v) { return (int) Math.floor(v / cellKm); }
        void update(Driver d, Location l) {
            long k = key(c(l.x()), c(l.y()));
            Long old = cellOf.put(d.id, k);
            if (old != null && old != k) cells.getOrDefault(old, Set.of()).remove(d);
            cells.computeIfAbsent(k, x -> ConcurrentHashMap.newKeySet()).add(d);
            d.loc = l;
        }
        List<Driver> nearby(Location l, double radiusKm) {
            int r = (int) Math.ceil(radiusKm / cellKm), cx = c(l.x()), cy = c(l.y());
            List<Driver> out = new ArrayList<>();
            for (int dx = -r; dx <= r; dx++) for (int dy = -r; dy <= r; dy++)
                for (Driver d : cells.getOrDefault(key(cx + dx, cy + dy), Set.of())) if (d.loc.dist(l) <= radiusKm) out.add(d);
            return out;
        }
    }

    interface MatchingStrategy { List<Driver> rank(List<Driver> candidates, Trip t); }
    static class NearestFirst implements MatchingStrategy {
        public List<Driver> rank(List<Driver> c, Trip t) {
            return c.stream().filter(d -> d.type == t.type && d.status.get() == DriverStatus.AVAILABLE)
                    .sorted(Comparator.comparingDouble(d -> d.loc.dist(t.from))).toList();
        }
    }
    interface PricingStrategy { long fare(Trip t, double km, double minutes); }
    static class DistanceTimeSurge implements PricingStrategy {
        private final Map<VehicleType, double[]> rates = Map.of(VehicleType.AUTO, new double[]{25, 12, 1},
                VehicleType.MINI, new double[]{40, 14, 1.5}, VehicleType.SEDAN, new double[]{60, 18, 2});  // base, per km, per min
        private final double surge; DistanceTimeSurge(double surge) { this.surge = surge; }
        public long fare(Trip t, double km, double min) { double[] r = rates.get(t.type); return Math.round((r[0] + r[1] * km + r[2] * min) * surge); }
    }
    interface DriverGateway { boolean offer(Driver d, Trip t); }   // driver app accept/decline (with timeout in reality)

    static class RideService {
        private final DriverIndex index; private final MatchingStrategy matcher; private final PricingStrategy pricing; private final DriverGateway gateway;
        private final Map<String, Trip> trips = new ConcurrentHashMap<>(); private final AtomicLong seq = new AtomicLong();
        RideService(DriverIndex i, MatchingStrategy m, PricingStrategy p, DriverGateway g) { index = i; matcher = m; pricing = p; gateway = g; }

        Trip request(Rider r, Location from, Location to, VehicleType type) {
            Trip t = new Trip("TR" + seq.incrementAndGet(), r, from, to, type);
            trips.put(t.id, t);
            for (double radius : new double[]{1, 3, 5}) {                       // expanding search radius
                for (Driver d : matcher.rank(index.nearby(from, radius), t)) {
                    if (!d.tryReserve()) continue;                              // someone else got this driver
                    if (gateway.offer(d, t)) { t.driver = d; t.transition(TripStatus.REQUESTED, TripStatus.ACCEPTED); return t; }
                    d.release();                                                // declined: free the driver, try next
                }
            }
            t.transition(TripStatus.REQUESTED, TripStatus.CANCELLED);
            return t;
        }
        void start(String tripId) { trips.get(tripId).transition(TripStatus.ACCEPTED, TripStatus.STARTED); }
        long complete(String tripId, double minutes) {
            Trip t = trips.get(tripId);
            t.transition(TripStatus.STARTED, TripStatus.COMPLETED);
            t.fareRupees = pricing.fare(t, t.from.dist(t.to), minutes);
            index.update(t.driver, t.to);
            t.driver.release();
            return t.fareRupees;
        }
    }

    public static void main(String[] args) throws Exception {
        DriverIndex idx = new DriverIndex(1.0);
        List<Driver> drivers = List.of(new Driver("d1", VehicleType.MINI, new Location(0.5, 0.5)),
                new Driver("d2", VehicleType.MINI, new Location(2.5, 0.2)), new Driver("d3", VehicleType.SEDAN, new Location(0.2, 0.1)));
        drivers.forEach(d -> idx.update(d, d.loc));
        DriverGateway gw = (d, t) -> !d.id.equals("d1") || !t.rider.id().equals("r2");   // d1 declines r2 for the demo
        RideService svc = new RideService(idx, new NearestFirst(), new DistanceTimeSurge(1.2), gw);

        // Two riders request MINI at the same time: each must get a different driver
        ExecutorService pool = Executors.newFixedThreadPool(2);
        Future<Trip> a = pool.submit(() -> svc.request(new Rider("r1", "Asha"), new Location(0, 0), new Location(6, 8), VehicleType.MINI));
        Future<Trip> b = pool.submit(() -> svc.request(new Rider("r2", "Ravi"), new Location(0, 0), new Location(3, 4), VehicleType.MINI));
        Trip t1 = a.get(), t2 = b.get(); pool.shutdown();
        System.out.println(t1.rider.name() + " -> " + (t1.driver == null ? "none" : t1.driver.id) + " " + t1.status);
        System.out.println(t2.rider.name() + " -> " + (t2.driver == null ? "none" : t2.driver.id) + " " + t2.status);
        Trip done = t1.driver != null ? t1 : t2;
        svc.start(done.id);
        System.out.println("fare=" + svc.complete(done.id, 25));
    }

When would I use it?

Any dispatch and matching problem:

  • Ride-hailing.
  • Assigning food-delivery partners (13.18).
  • Assigning tasks to field-force staff.
  • Technician scheduling.
  • Geo-indexed search in general — any "find things near this point" problem.

What can go wrong?

  • A check-then-assign race. Two threads both check "is d1 free?", both see yes, and both assign. Now two riders have the same driver. This happens when there's no atomic reservation.
  • Scanning every driver for every request. This is far too slow with many drivers. Use a spatial index.
  • Offers without timeouts. If a driver never answers, the request waits forever.
  • Forgetting to release drivers who decline. They stay ON_TRIP and never get new rides.
  • Invalid trip transitions. For example, completing a trip that was already cancelled. Guard every state change.

Interview questions

Q1. How do you prevent assigning one driver to two riders? Before offering the ride, I change the driver's status atomically. In memory, that is a CAS from AVAILABLE to ON_TRIP. In a distributed system, it is a conditional UPDATE in the database (update only if status is still AVAILABLE) or a Redis SET NX (set only if the key doesn't exist). Only one request can win.

Q2. How do you find nearby drivers efficiently? I use a spatial index — a grid, geohash, H3 or quadtree — keyed by map cell. I search the rider's own cell first, then the rings of neighbouring cells, until I have enough candidates.

Q3. How would surge pricing work? Every few minutes, I calculate the demand-to-supply ratio (riders requesting vs drivers free) for each area cell. Based on that ratio, I pick a multiplier and apply it through the PricingStrategy.
