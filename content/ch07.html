7.1 How a request flows through Spring MVC

Why?

In simple words: A request does not jump straight into your controller. It passes through a fixed line of "counters" — Tomcat, filters, the DispatcherServlet, interceptors — and if you know that line, you can find where any problem happens.

Sometimes a request is slow. Sometimes it returns the wrong status code. Sometimes it skips your validation, or it never reaches your controller at all. To debug any of these, you must know every component the request passes through, and in which order.

Interviewers ask "What happens when a request hits a Spring Boot app?" to check exactly this.

What is happening internally?

HTTP request
 → Tomcat connector: accepts the socket; a worker thread from Tomcat's pool (default max 200) takes the request
 → Servlet FILTER chain (in order): CharacterEncoding, Spring Security's FilterChainProxy, your tenant/correlation filters, CORS
 → DispatcherServlet (the "front controller", one servlet for the whole app)
     1. HandlerMapping: find the handler for METHOD + PATH (RequestMappingHandlerMapping matches @GetMapping etc.)
     2. HandlerInterceptor.preHandle (each interceptor; can short-circuit)
     3. HandlerAdapter invokes the controller method:
          argument resolvers: @PathVariable, @RequestParam, @RequestHeader, @RequestBody
             (@RequestBody → HttpMessageConverter → Jackson ObjectMapper deserialises JSON)
          validation: @Valid / @Validated → Bean Validation
     4. Controller → service → repository … returns a value
     5. Return value handler: HttpMessageConverter serialises it to JSON (content negotiation via Accept)
     6. HandlerInterceptor.postHandle / afterCompletion
     7. Exceptions anywhere in 3–5 → HandlerExceptionResolvers → @ControllerAdvice @ExceptionHandler
 → back through filters → response bytes on the socket

Here is the same flow in plain steps:

  1. Tomcat (the web server inside Spring Boot) accepts the connection. It gives the request to one worker thread from its thread pool. The default maximum is 200 threads.
  2. Filters run one after another. A filter is code that runs for every request before Spring MVC sees it — for example, security checks or reading the tenant ID.
  3. The DispatcherServlet receives the request. It is the front controller — one single entry point for the whole app that sends each request to the right place.
  4. Inside it: find the controller method, run interceptors, convert JSON into Java objects, validate them, call your code, convert the result back to JSON.
  5. If anything throws an exception, your @ControllerAdvice handler turns it into an error response.
  6. The response goes back out through the filters and onto the network.

One request = one Tomcat thread for its whole life. This is true unless you use async MVC, WebFlux or virtual threads.

So every blocking call — a DB query, an HTTP call to another service — keeps that thread busy while it waits. Because of this, timeouts on outbound calls and pool sizes matter a lot. Think of a bank with 200 counters: if every clerk is stuck waiting on a phone call, new customers stand in the queue.

How does it work?

  • HandlerMapping builds its lookup table once, at startup, from all @RequestMapping methods. So if two methods map to the same URL and method, the app fails at startup — not later.
  • Content negotiation means choosing the format of the data. Spring looks at the Accept header (what the client wants back) and the Content-Type header (what the client sent). Based on these, it picks a converter. For JSON, Jackson is used by default.
  • The HTTP status code comes from one of three places:
  • the return type (ResponseEntity),
  • the @ResponseStatus annotation,
  • or an exception handler.

Example

POST /api/v1/accounts/A1/redemptions  {"points": 500, "rewardCode": "AMZ100"}
1. Tomcat thread http-nio-8080-exec-12 picks it up
2. SecurityFilterChain validates the JWT → SecurityContext set
3. TenantFilter reads X-Tenant-Id → TenantContext (ThreadLocal)
4. HandlerMapping → RedemptionController.redeem(String, String, RedeemRequest)
5. Jackson builds RedeemRequest; @Valid checks @Positive points → OK
6. Service runs in a @Transactional proxy → DB → returns RedemptionResponse
7. Jackson writes JSON, ResponseEntity sets 201 + Location
8. Filters' finally blocks clear TenantContext and MDC

Note step 8. Tomcat threads are reused for the next request. So the filters must clear TenantContext and MDC in a finally block. Otherwise the next request on that thread could see the previous tenant's data.

When would I use it?

Use this knowledge when you are:

  • Debugging a 404 (no controller matched the URL).
  • Debugging a 415 (the client sent the wrong Content-Type).
  • Debugging a 406 (the client's Accept header asks for a format you can't produce).
  • Finding out why validation did not run.
  • Fixing filter order problems — for example, auth must run before tenant resolution.
  • Planning capacity. The number of requests you can handle depends on threads × time per request.

What can go wrong?

  • Slow downstream calls use up all Tomcat threads. New requests then wait in a queue (the size is set by accept count). When that queue is full too, new connections are refused.
  • A filter forgets to call chain.doFilter, so the request stops there. Or a filter does not clean up its ThreadLocals in finally, so data leaks to the next request on the same thread.
  • Large request bodies are read fully into memory, which can cause memory pressure.

Interview questions

Q1. What happens when a request hits a Spring Boot app? Tomcat gives the request a thread from its pool. Then servlet filters run, such as security. Next the DispatcherServlet takes over: HandlerMapping finds the controller method, interceptors run, and the HandlerAdapter prepares the method arguments — Jackson turns the JSON into objects and validation runs. Then the controller runs, and a message converter writes the response as JSON. If an exception is thrown anywhere, @ControllerAdvice handles it.

Q2. What is the DispatcherServlet? It is Spring MVC's front controller — one single servlet that receives every request. It sends each request to the right handler using mappings, adapters, resolvers and converters.

7.2 REST controllers and HTTP semantics

Why?

In simple words: Your API is a promise to everyone who calls it. If you use the right URLs, HTTP methods and status codes, callers know what to expect and can safely retry. If you use the wrong ones, you get duplicate orders and confused clients.

An API is a contract. Mobile apps, partner systems and other services all depend on it.

When resources, methods and status codes are correct, the API is:

  • predictable — callers know what each call does,
  • cacheable — GET responses can be cached,
  • safe to retry — a retry does not cause damage.

When they are wrong, you get duplicate orders, broken clients and confusing support tickets.

What is happening internally?

  • Methods in a @RestController return normal Java objects. Spring converts these to JSON for you. This conversion is called serialisation.
  • ResponseEntity<T> gives you full control of the response: the status, the headers and the body.
  • Method parameters get their values from different parts of the request:
  • the URL path → @PathVariable,
  • the query string (?page=2) → @RequestParam,
  • the headers → @RequestHeader,
  • the JSON body → @RequestBody.
  • For paging, Spring can fill a Pageable object from the page, size and sort parameters.

How does it work?

First, one important word. Idempotent means: doing the same call two times has the same effect as doing it once. Deleting order 5 twice still leaves order 5 deleted. Safe means the call changes nothing at all.

Method Meaning Idempotent? Typical success status
GET Read Yes (and safe — changes nothing) 200
POST Create / action No (make it idempotent with an idempotency key) 201 + Location, or 202 for async
PUT Replace the whole resource Yes 200 / 204
PATCH Update only some fields Not guaranteed 200 / 204
DELETE Remove Yes 204

Error status codes:

  • 400 — the request is malformed or fails validation.
  • 401 — the caller is not logged in (unauthenticated).
  • 403 — the caller is logged in but not allowed (forbidden).
  • 404 — not found.
  • 409 — conflict, such as a duplicate or a version clash.
  • 422 — the input is valid, but a business rule says no.
  • 429 — too many requests (rate limited).
  • 500 — a bug on the server.
  • 502 / 503 / 504 — a service you depend on has a problem.

Example

@RestController
@RequestMapping("/api/v1/accounts/{accountId}/redemptions")
class RedemptionController {
    private final RedemptionService service;
    RedemptionController(RedemptionService service) { this.service = service; }

    @PostMapping
    ResponseEntity<RedemptionResponse> redeem(@PathVariable String accountId,
                                              @RequestHeader("Idempotency-Key") String idemKey,
                                              @Valid @RequestBody RedeemRequest req) {
        RedemptionResponse r = service.redeem(TenantContext.current(), accountId, idemKey, req.points());
        return ResponseEntity.created(URI.create("/api/v1/accounts/%s/redemptions/%s".formatted(accountId, r.id())))
                             .body(r);
    }

    @GetMapping
    List<RedemptionResponse> list(@PathVariable String accountId,
                                  @RequestParam(required = false) Long afterId,          // keyset cursor
                                  @RequestParam(defaultValue = "20") @Max(100) int size) {
        return service.list(accountId, afterId, size);
    }
}

public record RedeemRequest(@Positive long points, @NotBlank String rewardCode) {}
public record RedemptionResponse(String id, long points, String status, Instant createdAt) {}

Points to notice:

  • The POST returns 201 Created with a Location header that points to the new redemption.
  • The POST requires an Idempotency-Key header, so a retry is safe.
  • The GET uses a cursor (afterId) for paging and limits size to at most 100.
  • The request and response are small record DTOs.

When would I use it?

In every API.

Always return DTO records — small classes made only for the API. Never return JPA entities. Entities cause three problems:

  1. They leak internal fields to the outside world.
  2. They trigger lazy loading while JSON is being written.
  3. They tie your API to your database schema, so a schema change breaks clients.

What can go wrong?

  • Returning entities. While Jackson writes JSON, it touches lazy fields. This causes a LazyInitializationException, or N+1 queries (one query for the list, plus one more for each item). Two-way relationships cause infinite recursion. Internal columns get exposed.
  • Returning 200 for everything, with an "error" field in the body. Clients and monitoring tools then can't tell a failure from a success.
  • Non-idempotent POSTs retried by mobile apps. On a flaky network the app retries, and you get duplicate redemptions. Require an Idempotency-Key header (11.14).
  • Offset paging on huge tables. OFFSET 1000000 makes the DB walk past a million rows — slow. Results also shift when new rows arrive. Use keyset/cursor paging instead ("give me rows after ID X").

Interview questions

Q1. PUT vs PATCH vs POST? PUT replaces the whole resource and is idempotent — repeating it gives the same result. PATCH updates only some fields. POST creates something or triggers an action, and it is not idempotent unless you add an idempotency key.

Q2. Which status code for a business-rule failure such as insufficient points? 422 Unprocessable Entity — the input is fine but the rule says no. Use 409 if it is a conflict with the current state. 400 is for input that is malformed or invalid.

Q3. Why not return JPA entities from controllers? Because of lazy-loading exceptions, accidental N+1 queries, infinite recursion on two-way mappings, leaking internal fields, and tying the API to the database schema.

7.3 Validation

Why?

In simple words: Never trust input from outside. Put simple annotations like @NotBlank on your request class, and Spring checks every request for you — and sends back a clear 400 error if something is wrong.

Every input from outside must be checked before it reaches business logic or the database. "Outside" means mobile apps, partners, admin panels — anything.

Declarative validation means you declare the rules as annotations instead of writing if checks by hand. This has three benefits:

  • The rules live next to the DTO, so they are easy to find.
  • They are consistent and easy to test.
  • Bad input gets a clear 400 error. Without this, the bad data goes deep into the code and fails later with a confusing 500.

What is happening internally?

Spring does not validate by itself. It hands the job to Bean Validation — the standard Java validation API (Jakarta Validation). The library that actually does the work is Hibernate Validator.

The steps for a request body:

  1. Jackson converts the JSON into your object.
  2. Because the parameter has @Valid, Spring now validates the object.
  3. Each constraint annotation (like @NotBlank) has a matching ConstraintValidator class that does the check.
  4. If any check fails, Spring throws MethodArgumentNotValidException.

For @PathVariable and @RequestParam constraints, it is different. You need @Validated on the class. Failures then throw HandlerMethodValidationException (Spring 6.1+) or ConstraintViolationException.

If you put @Valid on a nested field, validation also goes inside that nested object. This is called cascading.

How does it work?

public record CreateCampaignRequest(
        @NotBlank @Size(max = 80) String name,
        @NotNull @FutureOrPresent LocalDate startDate,
        @NotNull LocalDate endDate,
        @NotEmpty List<@NotBlank String> skuCodes,          // container element constraints
        @Valid @NotNull RewardSpec reward) {                // cascade into the nested object

    @AssertTrue(message = "endDate must be after startDate")
    boolean isRangeValid() { return startDate == null || endDate == null || endDate.isAfter(startDate); }
}
public record RewardSpec(@NotNull RewardType type, @Positive long value) {}

What this shows:

  • Simple field rules: @NotBlank, @Size, @NotNull, @FutureOrPresent.
  • Rules on list items: List<@NotBlank String> checks every SKU code in the list.
  • @Valid on reward means the rules inside RewardSpec are also checked.
  • @AssertTrue on a method checks a rule that needs two fields together — the end date must be after the start date.

Example

// Custom constraint: Indian mobile number
@Target({ElementType.FIELD, ElementType.PARAMETER, ElementType.RECORD_COMPONENT})
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy = IndianMobileValidator.class)
public @interface IndianMobile {
    String message() default "must be a valid Indian mobile number";
    Class<?>[] groups() default {};
    Class<? extends Payload>[] payload() default {};
}
public class IndianMobileValidator implements ConstraintValidator<IndianMobile, String> {
    private static final Pattern P = Pattern.compile("^(\\+91)?[6-9]\\d{9}$");
    @Override public boolean isValid(String v, ConstraintValidatorContext ctx) { return v == null || P.matcher(v).matches(); }
}
public record RetailerSignup(@NotBlank String shopName, @NotNull @IndianMobile String mobile) {}

To make a custom rule, you need two pieces:

  1. An annotation (@IndianMobile) marked with @Constraint(validatedBy = …).
  2. A validator class that implements isValid.

Note that isValid returns true for null. This is the usual habit: let @NotNull handle "missing", and let the custom rule handle only "wrong format".

Validation groups (@Validated(OnCreate.class)) let one DTO have different rules for create and update. But usually it is clearer to write a separate request record for each operation.

When would I use it?

On all request DTOs, and on @ConfigurationProperties classes (so bad config fails at startup).

Keep business rules that need data in the service layer, not in annotations. For example, "points ≤ balance" needs the account's balance from the DB, so it belongs in the service.

What can go wrong?

  • Forgetting @Valid. The constraints are then silently ignored — no error, no check.
  • Validating only on the client (the app or web page). Anyone can call the API directly with curl or Postman and skip those checks.
  • Putting DB lookups inside validators. They become slow and hard to test, and they hide business logic in a place nobody looks.
  • Sending the raw validation exception text to clients. Section 7.4 shows how to shape it into a clean response.

Interview questions

Q1. How does @Valid work in Spring MVC? After Jackson turns the body into an object, Spring calls Bean Validation on it. Any broken rule throws MethodArgumentNotValidException, which you map to a 400 response.

Q2. How do you write a custom validator? Create a constraint annotation marked with @Constraint(validatedBy = …), and write a class that implements ConstraintValidator<A, T>.isValid.

Q3. Where should business-rule validation live? In the service or domain layer, because that layer has the data and context to decide. Annotations are only for checking the shape of the input.

7.4 Centralised exception handling

Why?

In simple words: Instead of every controller catching and formatting errors in its own way, you write one class that catches all exceptions. It decides the status code, builds a clean error body, and logs real bugs once.

Without one central handler, three bad things happen:

  1. Every controller catches and formats errors differently.
  2. Stack traces leak to clients.
  3. Unexpected exceptions become plain 500s with no useful information.

A single @RestControllerAdvice class fixes all of this. It maps each exception type to the right status code and a consistent body. It also logs unexpected errors exactly once.

What is happening internally?

When a controller method throws an exception, this happens:

  1. DispatcherServlet asks its HandlerExceptionResolvers to deal with it.
  2. One of them, ExceptionHandlerExceptionResolver, looks for the best matching @ExceptionHandler for that exception type.
  3. It looks first inside the controller itself. Then it looks in @ControllerAdvice beans, in the order set by @Order. It picks the most specific match.
  4. It calls that handler method.
  5. Whatever the handler returns is written out like a normal response.

Spring 6 gives you ProblemDetail. It is the standard error body format from RFC 9457. It has the fields type, title, status, detail and instance, and you can add your own extra properties.

How does it work?

@RestControllerAdvice
class GlobalExceptionHandler {
    private static final Logger log = LoggerFactory.getLogger(GlobalExceptionHandler.class);

    @ExceptionHandler(MethodArgumentNotValidException.class)
    ProblemDetail validation(MethodArgumentNotValidException ex) {
        ProblemDetail pd = ProblemDetail.forStatus(HttpStatus.BAD_REQUEST);
        pd.setTitle("Validation failed");
        pd.setProperty("errors", ex.getBindingResult().getFieldErrors().stream()
                .map(f -> Map.of("field", f.getField(), "message", String.valueOf(f.getDefaultMessage()))).toList());
        return pd;
    }

    @ExceptionHandler(InsufficientPointsException.class)
    ProblemDetail insufficient(InsufficientPointsException ex) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.UNPROCESSABLE_ENTITY, ex.getMessage());
        pd.setTitle("Insufficient points");
        pd.setType(URI.create("https://errors.example.com/insufficient-points"));
        return pd;
    }

    @ExceptionHandler({ObjectOptimisticLockingFailureException.class, DataIntegrityViolationException.class})
    ProblemDetail conflict(Exception ex) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT, "Concurrent or duplicate update, please retry");
    }

    @ExceptionHandler(Exception.class)
    ProblemDetail unexpected(Exception ex, HttpServletRequest req) {
        log.error("Unhandled error on {} {}", req.getMethod(), req.getRequestURI(), ex);   // log the stack ONCE, here
        return ProblemDetail.forStatusAndDetail(HttpStatus.INTERNAL_SERVER_ERROR, "Unexpected error");
    }
}

What each handler does:

  • Validation failure → 400, with a list of which field failed and why.
  • InsufficientPointsException (a business rule) → 422, with a clear title and a type link.
  • Optimistic lock or unique-key clash → 409, "please retry".
  • Anything else → 500 with a generic message. The full stack trace is logged here, once — and never sent to the client.

Example

HTTP/1.1 422
{ "type": "https://errors.example.com/insufficient-points", "title": "Insufficient points",
  "status": 422, "detail": "Account A1 requested 500 but has 120", "instance": "/api/v1/accounts/A1/redemptions" }

When would I use it?

In every service.

Pair it with domain exceptions — your own unchecked exceptions (1.15) such as InsufficientPointsException. Services throw them, and the advice turns them into responses. So controllers stay free of try/catch.

What can go wrong?

  • Wrong order of handlers. A catch-all handler wins over specific ones because of class order, or you have several advice classes without @Order. Then the same error gets different responses.
  • Logging and rethrowing in every layer. The same stack trace then appears five times in the logs.
  • Leaking internals in detail — SQL, class names or stack traces.
  • Exceptions thrown inside filters. Filters run before the DispatcherServlet. So @ControllerAdvice never sees these exceptions. Handle them inside the filter itself, or in Spring Security's entry points.

Interview questions

Q1. How do you handle exceptions globally in Spring? With a @RestControllerAdvice class that has @ExceptionHandler methods. Each one maps an exception type to a status code and a ProblemDetail body. Unexpected errors are logged once, there.

Q2. Why doesn't my @ControllerAdvice catch an exception thrown in a filter? Filters run before the DispatcherServlet, so Spring's exception resolvers are not involved yet. Handle it in the filter itself or in the security entry point.

7.5 Filters vs interceptors

Why?

In simple words: Both let you run code for every request. A filter sits at the building's main gate and sees everyone. An interceptor sits at the office door, after Spring already knows which controller method will handle the request.

Some logic must run for every request. Examples: authentication, finding the tenant, adding correlation IDs, request logging, rate limiting.

You can put such logic in a Servlet filter or a Spring MVC interceptor. The right choice depends on two things: what the logic needs to see, and when it must run.

What is happening internally?

  • A Filter (jakarta.servlet.Filter, usually written by extending Spring's OncePerRequestFilter) runs in the servlet container, around the DispatcherServlet.
  • It runs for every request — including static files and error pages.
  • It can wrap or replace the request and response objects.
  • It can stop the chain, so the request goes no further.
  • A HandlerInterceptor runs inside the DispatcherServlet, after the controller method has been chosen.
  • It knows which handler method will run, and can read its annotations.
  • It has three hooks: preHandle (before the controller), postHandle (after the controller) and afterCompletion (after the response is done).
Filter A → Filter B → DispatcherServlet → [Interceptor.preHandle] → Controller → [postHandle] → view/JSON → [afterCompletion] → Filter B → Filter A

How does it work?

Filter Interceptor
Level Servlet container Spring MVC
Sees Raw request/response (can wrap them) The handler method and its annotations
Runs for Everything Only requests that map to a handler
Typical use Security, tenant, correlation ID, CORS, compression, request/response logging Auth checks per endpoint based on annotations, metrics per handler, locale

Example

@Component
@Order(Ordered.HIGHEST_PRECEDENCE)
class CorrelationIdFilter extends OncePerRequestFilter {
    @Override protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        String id = Optional.ofNullable(req.getHeader("X-Request-Id")).orElse(UUID.randomUUID().toString());
        MDC.put("requestId", id);
        res.setHeader("X-Request-Id", id);
        try { chain.doFilter(req, res); }
        finally { MDC.remove("requestId"); }                   // pooled threads: always clean up
    }
}

@Retention(RetentionPolicy.RUNTIME) @Target(ElementType.METHOD) @interface RequiresFeature { String value(); }

@Component
class FeatureFlagInterceptor implements HandlerInterceptor {
    private final FeatureFlags flags;
    FeatureFlagInterceptor(FeatureFlags flags) { this.flags = flags; }
    @Override public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) throws IOException {
        if (handler instanceof HandlerMethod hm) {
            RequiresFeature rf = hm.getMethodAnnotation(RequiresFeature.class);
            if (rf != null && !flags.enabled(TenantContext.current(), rf.value())) { res.sendError(404); return false; }
        }
        return true;
    }
}
@Configuration
class WebConfig implements WebMvcConfigurer {
    private final FeatureFlagInterceptor ffi;
    WebConfig(FeatureFlagInterceptor ffi) { this.ffi = ffi; }
    @Override public void addInterceptors(InterceptorRegistry r) { r.addInterceptor(ffi).addPathPatterns("/api/**"); }
}

What the code does:

  • CorrelationIdFilter runs first for every request. It takes the X-Request-Id header, or makes a new UUID. It puts the ID in the logging context (MDC) and in the response header. In finally, it removes the ID — because Tomcat threads are reused, and the next request must not see the old ID.
  • FeatureFlagInterceptor reads the @RequiresFeature annotation on the chosen controller method. If the feature is off for this tenant, it returns 404 and stops. A filter could not do this, because a filter doesn't know which method will run.
  • WebConfig registers the interceptor for paths under /api/**.

When would I use it?

  • Use a filter for anything that must happen before Spring MVC, or for all traffic — security, tenancy, tracing.
  • Use an interceptor for logic that depends on which handler was chosen.

What can go wrong?

  • Wrong filter order. For example, tenant resolution runs before security has checked who the caller is. Or it runs after another filter that already needed the tenant.
  • Reading the request body in a filter. The body is a stream, and reading it uses it up. Then the controller gets an empty body. Wrap the request with ContentCachingRequestWrapper to fix this.
  • Expecting interceptors to run for errors or static files. They don't run for those, though you may expect them to.

Interview questions

Q1. Filter vs interceptor? A filter works at the servlet level. It runs for every request and can wrap the request and response. An interceptor works at the Spring MVC level. It runs around the chosen handler and can see its method and annotations.

Q2. Where would you put tenant resolution and why? In a filter, early in the chain. Then every later component — security rules, controllers, repositories — has the tenant context. Clear it in finally so the next request on that thread starts clean.

7.6 Calling other services: RestClient, timeouts and connection pools

Why?

In simple words: Every time your service calls another service, it can get stuck waiting. Set timeouts, reuse connections, and keep one configured client per downstream — otherwise one slow service can bring yours down too.

Microservices call each other and partners all the time — pricing, inventory, SMS, payment gateways.

Every outbound call is a risk. Your service can hang there, leak connections, or spread someone else's outage to your own callers. So configuring the HTTP client correctly is basic production hygiene. It also comes up often in SDE2 interviews.

What is happening internally?

The client options in Spring:

  • RestClient (Spring 6.1+) — the modern, synchronous client with a fluent (chained-method) style.
  • WebClient — the reactive, non-blocking client.
  • RestTemplate — the old client; it is in maintenance mode (only bug fixes).
  • HTTP interfaces (@HttpExchange) — you write an annotated interface, and Spring generates the client for you.

Connection pools: Under the hood, an HTTP library does the real work — JDK HttpClient, Apache HttpClient 5 or Reactor Netty. It keeps a connection pool for each host — a set of open connections ready to reuse.

  • Reusing a connection skips the TCP and TLS handshakes, which saves time.
  • The pool's limit caps how many calls can go to one host at the same time.

Timeouts — there are three:

  1. Connect timeout — how long to wait to open the TCP connection.
  2. Read/response timeout — how long to wait for data after connecting.
  3. Pool-acquire timeout — how long to wait for a free connection from the pool.

Without a read timeout, a stuck downstream service holds your thread forever.

How does it work?

Follow these rules:

  1. Set timeouts shorter than your own SLA (the response time you promise).
  2. Also keep them shorter than the timeout your caller uses for you. This is called a timeout budget — each hop gets a share of the total time.
  3. Add retries only for idempotent calls — calls that are safe to repeat.
  4. Add a circuit breaker for unhealthy dependencies (8.7). A circuit breaker stops calling a service that keeps failing, for a short while, like a fuse in your house.

Example

@Configuration
class ClientsConfig {
    @Bean
    RestClient pricingClient(RestClient.Builder builder) {
        var http = HttpClient.newBuilder().connectTimeout(Duration.ofMillis(500)).build();   // JDK client
        var factory = new JdkClientHttpRequestFactory(http);
        factory.setReadTimeout(Duration.ofSeconds(2));
        return builder.baseUrl("http://pricing-service")
                      .requestFactory(factory)
                      .defaultHeader("X-Caller", "loyalty-service")
                      .build();
    }
}

@Component
class PricingClient {
    private final RestClient client;
    PricingClient(RestClient pricingClient) { this.client = pricingClient; }

    Price price(String tenant, String sku) {
        return client.get().uri("/v1/prices/{sku}", sku)
                .header("X-Tenant-Id", tenant)
                .retrieve()
                .onStatus(HttpStatusCode::is4xxClientError, (req, res) -> { throw new PriceNotFoundException(sku); })
                .body(Price.class);
    }
}

// Declarative HTTP interface (Spring 6)
interface InventoryApi {
    @GetExchange("/v1/stock/{sku}") Stock stock(@PathVariable String sku);
}

What the code does:

  • One RestClient bean for the pricing service, with a 500 ms connect timeout and a 2 s read timeout.
  • PricingClient wraps it. A 4xx response from pricing becomes your own PriceNotFoundException.
  • InventoryApi shows the declarative style: Spring generates the client from the interface.

When would I use it?

For every outbound HTTP call.

Make one client bean per downstream service. Each one gets:

  • its own timeouts and pool limits — this is a bulkhead, so one slow service can't use up the connections meant for others;
  • observability — metrics, and tracing headers that pass along automatically when you build from the injected RestClient.Builder;
  • resilience policies such as retries and circuit breakers.

What can go wrong?

  • No timeouts. Your threads fill up with requests stuck on a slow dependency. Then the outage spreads to everyone who calls you.
  • Creating a new client for every request. There is no connection reuse. You pay for a TLS handshake on every call, and you can run out of ports (sockets stuck in TIME_WAIT).
  • Retrying non-idempotent POSTs. This causes duplicate payments or orders.
  • Not reading or closing response bodies. The connection never goes back to the pool, so the pool slowly leaks.
  • Calling remote services inside a DB transaction. The DB connection and its locks stay held while you wait on the network (7.12).

Interview questions

Q1. What timeouts do you configure on an HTTP client? Connect timeout, read/response timeout, and pool-acquisition timeout. All of them must fit inside the caller's latency budget.

Q2. RestTemplate vs RestClient vs WebClient? RestTemplate is the old synchronous client. RestClient is the modern synchronous client with a fluent style. WebClient is reactive and non-blocking, used with WebFlux or for high-concurrency async calls.

Q3. Why reuse HTTP clients? To reuse pooled TCP/TLS connections, avoid handshake costs and port exhaustion, and keep timeouts and limits in one central place.

7.7 JPA, Hibernate and Spring Data repositories

Why?

In simple words: You write Java classes, and the library turns them into database tables and SQL for you. With Spring Data, you only write an interface; Spring writes the code behind it.

With plain JDBC (Java's low-level database API), you do everything by hand:

  • You copy every column into every field, one by one.
  • You open and close connections and statements yourself.
  • You write the same insert, select, update and delete SQL for every table. This basic set is called CRUD (Create, Read, Update, Delete).

This is boring and easy to get wrong.

A tool that maps Java objects to database tables is called an ORM (Object-Relational Mapper). In Java:

  • JPA is the specification — a set of rules and annotations. It is like an interface.
  • Hibernate is the implementation of JPA — the real engine. It is like EF Core in .NET.

Hibernate maps Java objects to tables, generates the SQL, tracks what you changed and manages links between objects.

Spring Data JPA goes one step further. You only declare a repository interface. Spring writes the class that implements it for you.

Think of a tiffin service. You just say "veg thali, no onion" on the order slip. The kitchen knows how to cook it. You never enter the kitchen.

What is happening internally?

  • Entity: a class marked with @Entity. It maps to one table.
  • Hibernate needs a constructor with no arguments, so it can create the object itself.
  • The class and its methods must not be final. Why? Hibernate creates a subclass at runtime (a proxy) to support lazy loading. A final class cannot be subclassed.
  • EntityManager (called Session in Hibernate): the object that does the actual work with the database.
  • It holds the persistence context (7.9) — a list of the objects loaded in this transaction.
  • This pattern is called a unit of work: collect all changes, then write them together.
  • Spring does not give you a raw EntityManager. It injects a shared proxy that finds the EntityManager of the current transaction.
  • Spring Data repositories: at startup, Spring does these steps: 1. It scans for interfaces that extend Repository. 2. For each one, it creates a JDK proxy — a fake object generated at runtime that implements your interface. 3. Basic CRUD calls go to a ready-made class, SimpleJpaRepository. 4. Your own query methods get generated code. They come in a few kinds:
  • Derived queries: Spring reads the method name and builds the query. For example, findByTenantIdAndStatusOrderByCreatedAtDesc is parsed into JPQL at startup. (JPQL is SQL-like, but written against classes and fields, not tables and columns.) If you make a typo in the name, the app fails at startup. This is good — you find the bug early, not in production.
  • @Query: you write the JPQL or native SQL yourself.
  • Projections: an interface or record that selects only some columns, not the full entity.
  • Specifications: build filters at runtime, for search screens where the user picks the filters.
  • ID generation — how a new row gets its primary key:
  • IDENTITY: the database auto-increments the ID. Hibernate does not know the ID until the row is inserted. So it must insert each row immediately. Because of this, JDBC batch inserts are disabled (no sending 50 inserts in one go).
  • SEQUENCE: Hibernate fetches a block of IDs from a database sequence in advance. The block size is allocationSize. Since Hibernate already knows the IDs, it can batch inserts. This is the preferred choice on Postgres.
  • UUID: the app makes the ID itself, with no need to ask the database. Use time-ordered UUIDv7. Its values grow over time, so new rows land next to each other in the index. This is called better index locality, and it makes inserts faster.

How does it work?

@Entity
@Table(name = "ledger_entry",
       indexes = @Index(name = "ix_ledger_account_created", columnList = "account_id, created_at"),
       uniqueConstraints = @UniqueConstraint(name = "uq_ledger_idem", columnNames = {"tenant_id", "idempotency_key"}))
public class LedgerEntry {

The repository interfaces build on each other. Each level adds more methods:

Repository → CrudRepository/ListCrudRepository → PagingAndSortingRepository → JpaRepository.

JpaRepository is the top level. It adds flush, batch delete and getReferenceById.

When would I use it?

Use it for domain services that do a lot of CRUD and have clear aggregates — a main object with its child objects, saved and loaded together. Examples: accounts, orders, campaigns.

Use something else for:

  • complex reporting queries,
  • bulk operations,
  • anything where performance is critical.

For these, use native SQL, JdbcTemplate (Spring's thin JDBC helper) or jOOQ (a type-safe SQL builder). Mixing both approaches in one service is normal.

What can go wrong?

  • ORDINAL enums: the enum is saved as its position number (0, 1, 2). If someone reorders the enum values later, old rows now point to the wrong value. Your data is silently corrupted. Always use STRING.
  • IDENTITY IDs: they disable batch inserts, so bulk inserts become slow.
  • ddl-auto=update in production: Hibernate changes the schema on its own at startup. Schema changes must go through versioned migrations instead (7.16).
  • Bulk @Modifying updates: they run directly in the database and skip the persistence context. So entities you already loaded in memory now hold old values (they are stale). Fix: use clearAutomatically = true, or reload the entities.
  • Derived query names that grow silly, like findByAAndBOrCAndDOrderBy…. Nobody can read them. Switch to @Query.
  • findAll() on a big table: it loads every row into memory.

Interview questions

Q1. JPA vs Hibernate vs Spring Data JPA? JPA is the ORM specification — the rules and annotations. Hibernate is the implementation that actually does the work. Spring Data JPA sits on top of JPA and generates repository implementations from your interfaces.

Q2. How does Spring Data create a repository implementation from an interface? At startup, it creates a proxy for the interface, backed by SimpleJpaRepository for CRUD. It parses method names, or reads @Query annotations, and turns them into queries.

Q3. IDENTITY vs SEQUENCE generation? IDENTITY uses the database's auto-increment. Hibernate must insert each row immediately to learn its ID, so batching is disabled. SEQUENCE fetches IDs in advance in blocks, so Hibernate can batch the inserts.

7.8 Relationships and fetch types

Why?

In simple words: You tell JPA how your objects are linked — an order has lines, a line belongs to an order. Then you can just call order.getLines(). But each link can secretly fire extra queries, so you must control how and when it loads.

Domain objects point to each other. For example:

  • An order has many lines.
  • An order belongs to an outlet.
  • A scheme has many rules.

If you map these links, you can move from one object to another in plain Java code. This web of linked objects is called the object graph.

But every link has a cost. It can:

  • fire a hidden query,
  • cause a surprise cascade (an action on the parent spreading to children),
  • or become a performance trap.

What is happening internally?

  • Owning side vs inverse side:
  • The owning side is the side that holds the foreign key. It uses @ManyToOne with @JoinColumn. Only this side decides what gets written to the database.
  • The inverse side uses @OneToMany(mappedBy = …). It is only a mirror, so you can navigate in the other direction. Changes made only here are not saved.
  • Fetch types — when the linked data is loaded:
  • EAGER: load the link immediately, together with the parent. Hibernate uses a join or an extra query.
  • LAZY: do not load it yet. Hibernate puts a placeholder in the field instead. For a single object, the placeholder is a proxy. For a collection, it is a PersistentCollection wrapper. The data is loaded the first time you touch it.
  • Defaults: @ManyToOne and @OneToOne are EAGER. @OneToMany and @ManyToMany are LAZY.
  • Cascade: an operation on the parent (persist, merge, remove) is passed on to its children automatically.
  • orphanRemoval = true: if you remove a child from the parent's collection, Hibernate deletes that child row.

Think of a lazy proxy like a restaurant token. You get the token now. The food (the data) comes only when you go to the counter and ask for it.

How does it work?

@Entity
public class Order {
    @Id @GeneratedValue Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)       // override the EAGER default
    @JoinColumn(name = "outlet_id")
    private Outlet outlet;

    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<OrderLine> lines = new ArrayList<>();

    public void addLine(OrderLine l) { lines.add(l); l.setOrder(this); }      // keep both sides in sync
    public void removeLine(OrderLine l) { lines.remove(l); l.setOrder(null); }
}

@Entity
public class OrderLine {
    @Id @GeneratedValue Long id;
    @ManyToOne(fetch = FetchType.LAZY) @JoinColumn(name = "order_id") private Order order;   // owning side
    private String sku; private int qty;
    void setOrder(Order o) { this.order = o; }
}

Example

Order o = orderRepo.findById(7L).orElseThrow();   // SELECT order only
o.getOutlet().getId();                              // no query: the proxy already knows the FK id
o.getOutlet().getName();                            // SELECT outlet (proxy initialised)
o.getLines().size();                                // SELECT order_line WHERE order_id = 7

Sometimes a many-to-many link has its own data. For example, an outlet joins a scheme on a certain date. That joining date belongs to the link itself. In this case, do not use @ManyToMany. Make the join table its own entity instead.

When would I use it?

Map relationships inside an aggregate — for example, order → lines.

Across aggregates or across services, store only the ID (like outletId), not the object. Because of this:

  • loading stays predictable (no surprise queries), and
  • the boundaries between services stay clean.

What can go wrong?

  • EAGER @ManyToOne everywhere: every query drags in a chain of joined entities.
  • Updating only one side of a two-way link: the objects in memory disagree with each other until you reload them.
  • CascadeType.REMOVE on @ManyToMany: deleting one parent deletes children that other parents still share.
  • toString, equals, hashCode or JSON serialisation touching lazy collections: this causes extra queries, endless recursion (A prints B, B prints A …), or LazyInitializationException.

Interview questions

Q1. What are the default fetch types? ToOne links (@ManyToOne, @OneToOne) are EAGER. ToMany links are LAZY. You should set ToOne links to LAZY explicitly.

Q2. What is the owning side of a relationship? It is the side that holds the foreign key (@JoinColumn). JPA writes the relationship to the database from this side. mappedBy marks the other side, the inverse side.

Q3. When would you avoid @ManyToMany? When the link has its own data or its own lifecycle. Then model the join table as an entity, with two ManyToOne relations.

7.9 The persistence context, entity states and dirty checking

Why?

In simple words: Inside a transaction, Hibernate keeps a notebook of every object it loaded and what it looked like at load time. At the end, it compares, finds what you changed, and writes the UPDATE for you — even if you never call save().

Hibernate does more than run SQL. It keeps a unit of work — it collects changes and writes them together. In detail, it:

  • tracks every entity it loaded,
  • makes sure one database row = one Java object within a transaction,
  • groups writes into batches,
  • writes your changes to the database automatically. Sending pending changes to the database is called flushing.

If you do not understand this, you will see puzzles like:

  • "Why did this UPDATE happen? I never called save."
  • "Why is my change not saved?"
  • "Why does my batch job run out of memory?"

What is happening internally?

The persistence context is also called the first-level cache. It holds two things:

  1. A map: (EntityClass, id) → entity instance.
  2. A snapshot of each entity — a copy of its values as they were when loaded.

In Spring, the persistence context lives as long as the transaction.

Think of a library register. Every book issued is written down with its condition. When it comes back, the clerk compares it with the register and notes any damage.

An entity moves through these states:

transient (new) ──persist()──► MANAGED ──(commit / clear / close)──► DETACHED
                                  │                                       │
                               remove()                               merge() (copies state onto a managed instance)
                                  ▼
                               REMOVED ──(flush)──► DELETE
  • Transient: a new object that Hibernate does not know about yet.
  • Managed: Hibernate is tracking it.
  • Detached: Hibernate tracked it earlier, but the context is closed or cleared now.
  • Removed: marked for delete; the DELETE runs at flush.

Key behaviour:

  • find / findById first checks the persistence context. Within one transaction, the same ID always gives you the same Java object.
  • Dirty checking: an entity is dirty when its values differ from its snapshot. At flush, Hibernate compares each managed entity with its snapshot. It issues UPDATEs for the changed ones. So you do not call save() to update a managed entity.
  • When does flush happen? Before commit. Also, in the default AUTO mode, before a query that touches the affected tables — so the query sees your changes.
  • Writes wait in a queue (the action queue). At flush they run in a fixed order: inserts, then updates, then collection changes, then deletes.

How does it work?

@Transactional
public void rename(Long outletId, String newName) {
    Outlet o = outletRepo.findById(outletId).orElseThrow();   // SELECT; entity MANAGED, snapshot taken
    o.setName(newName);                                       // only changes the Java object
}                                                             // commit → flush → dirty check → UPDATE outlet SET name=? …

What save() does in Spring Data:

  • For a new entity, it calls persist.
  • For an entity with an existing ID, it calls merge. merge first runs a SELECT for that row, then copies your values onto it. That is an extra query you often do not need.

Example

// Batch job that runs out of memory: 1M entities accumulate in the persistence context
@Transactional
public void importOutlets(Stream<OutletRow> rows) {
    int i = 0;
    for (OutletRow r : (Iterable<OutletRow>) rows::iterator) {
        em.persist(new Outlet(r));
        if (++i % 500 == 0) { em.flush(); em.clear(); }     // write the batch, then forget it
    }
}
// + spring.jpa.properties.hibernate.jdbc.batch_size=500, order_inserts=true, SEQUENCE ids

Without the flush + clear, all 1 million objects (and their snapshots) stay in memory. With it, every 500 rows are written and then dropped from the context.

When would I use it?

  • Everyday updates: load the entity, change it, and let the commit flush it.
  • Read-only queries: use @Transactional(readOnly = true). Hibernate then skips the snapshots and the dirty checking, which saves memory and CPU.
  • Bulk jobs: flush and clear every few hundred rows. Or use JDBC batching or plain SQL directly.

What can go wrong?

  • Unexpected UPDATEs: some code changed a managed entity — even a setter called only "for display". Hibernate sees the change and saves it.
  • Running out of memory: a long transaction loads too many entities, and they all stay in the context.
  • Stale state: a bulk JPQL or SQL update skips the context. Entities already in memory now hold old values.
  • Detached entity confusion:
  • Changing an entity after the transaction has ended changes nothing in the database.
  • merge returns a different managed object. Keep using the returned one, not the one you passed in.
  • Flush order surprises: an error such as a unique-constraint violation may appear later, on some other query (when AUTO flush runs). It does not appear on the line where you called save.

Interview questions

Q1. What is the persistence context? It is Hibernate's first-level cache and unit of work, one per transaction. It maps IDs to managed entity objects, keeps a snapshot of each, and flushes changes at commit.

Q2. What is dirty checking? At flush, Hibernate compares each managed entity with its snapshot. For every changed entity, it generates an UPDATE automatically.

Q3. Do you need to call save() after modifying an entity? Not for a managed entity inside a transaction — the change is flushed at commit. save matters only for new or detached entities.

Q4. persist vs merge? persist makes a new object managed. merge copies a detached object's values onto a managed object (loading it first if needed) and returns that managed object.

7.10 The N+1 query problem and fetching strategies

Why?

In simple words: You load 500 orders with one query. Then, for each order, you read its outlet name — and Hibernate quietly fires one more query each time. So 1 query becomes 501.

This is the most common ORM performance bug. The code looks like one query, but it runs hundreds.

A typical story:

  • A list endpoint is fast in dev, with 10 rows.
  • In production, with 500 rows, it takes 8 seconds.
  • Why? Each row triggers more queries.

What is happening internally?

Step by step:

  1. Loading N parent rows runs 1 query.
  2. Your code touches a lazy link on each parent (for example, order.getOutlet().getName()).
  3. Each touch loads that proxy or collection with 1 more query.
  4. Total: N+1 round trips to the database.

Each query alone is cheap. But the network delay adds up: 500 × 2 ms = 1 second. And the whole time, the request holds a connection from the pool, so other requests may have to wait.

Think of a shopkeeper who walks to the godown separately for each item on your list, instead of picking all items in one trip.

SELECT * FROM orders WHERE status='OPEN'          -- 1 query, returns 500 orders
SELECT * FROM outlet WHERE id=?   (×500)           -- one per order when the DTO mapper reads order.getOutlet().getName()

How does it work?

Fixes, from most targeted to least targeted:

  1. Fetch join (JPQL): load the linked data in the same query, using join fetch.
  2. @EntityGraph: on a repository method, list which links should be loaded together with the parent.
  3. Batch fetching: set hibernate.default_batch_fetch_size=50. Hibernate then loads lazy links for many parents at once, using IN (?, ?, …). So N+1 queries become 1 + N/50.
  4. DTO projection: select exactly the columns the response needs, straight into a DTO (a plain data object). This is often the best choice for read endpoints.

Example

public interface OrderRepository extends JpaRepository<Order, Long> {
    @Query("select o from Order o join fetch o.outlet where o.status = :s")               // 1. fetch join
    List<Order> findOpenWithOutlet(@Param("s") OrderStatus s);

    @EntityGraph(attributePaths = {"outlet", "lines"})                                     // 2. entity graph
    List<Order> findByStatus(OrderStatus status);

    @Query("""
        select new com.fa.order.OrderSummary(o.id, ou.name, o.totalPaise, o.createdAt)
        from Order o join o.outlet ou where o.tenantId = :t and o.createdAt >= :since
        """)
    List<OrderSummary> summaries(@Param("t") String tenant, @Param("since") Instant since);   // 4. DTO projection
}
public record OrderSummary(Long id, String outletName, long totalPaise, Instant createdAt) {}

How to detect it:

  • In dev and tests, log the SQL: logging.level.org.hibernate.SQL=DEBUG.
  • Turn on hibernate.generate_statistics to see query counts.
  • In integration tests, assert the number of queries (for example, with datasource-proxy).
  • In production, look at APM traces (application performance monitoring). Hundreds of identical SELECTs in one request is the sign.

When would I use it?

On every list or report endpoint.

Decide what to load for each use case — a list view needs less than a detail view. Do not decide it once for the whole app by making links EAGER.

What can go wrong?

  • Fetch-joining a collection while paginating: Hibernate cannot apply the page limit in SQL. So it loads all rows and pages them in memory. You will see warning HHH90003004. Fix: first fetch only the parent IDs for the page, then fetch the links for those IDs. Or use batch fetching.
  • Fetch-joining two collections (Hibernate calls a List mapping a "bag"): you get MultipleBagFetchException, or a Cartesian product — every line row multiplied by every other row. Fix: fetch one collection per query, or use Sets, or batch fetching.
  • Making links EAGER to "fix" N+1: this does not fix it. It just moves the problem to every other place that loads the entity.

Interview questions

Q1. What is the N+1 problem? One query loads N parent rows. Then reading a lazy link on each parent fires one more query per parent. That is N+1 queries in total.

Q2. How do you fix it? Use fetch joins, @EntityGraph, batch fetching (default_batch_fetch_size), or DTO projections that select exactly what is needed. Detect it by logging and counting the SQL.

Q3. Why is join fetch with pagination dangerous? When you fetch a collection, Hibernate cannot apply LIMIT in SQL. So it loads all the rows and does the paging in memory.

7.11 Lazy loading, LazyInitializationException and Open-Session-in-View

Why?

In simple words: A lazy link can load its data only while the database session is open. If you touch it after the transaction has ended, it crashes. Spring Boot's default "fix" keeps the session open for the whole web request — which creates bigger problems.

Lazy loading is good: you do not load data you do not need. But there is a catch:

  • A lazy proxy can load only while its session (the persistence context) is still open.
  • If you touch it after the transaction ends, you get LazyInitializationException.
  • This usually happens in the controller, or while converting the object to JSON (serialisation).

By default, Spring Boot "solves" this with Open-Session-in-View (OSIV). But OSIV causes worse problems, as you will see below.

What is happening internally?

  • A lazy link is a Hibernate proxy or PersistentCollection. It keeps a reference to the session that created it.
  • On first access, it asks that session to load the data.
  • If the session is already closed, it throws LazyInitializationException: could not initialize proxy - no Session.

Think of a railway counter that closes at 5 pm. Your token is valid, but if you come at 6 pm, nobody is there to serve you.

OSIV is controlled by spring.jpa.open-in-view=true. It is on by default, and Spring prints a warning about it at startup. Here is what it does:

  1. An interceptor opens an EntityManager at the start of the web request.
  2. It closes it only after the response has been written.

So lazy loading now works in controllers and in JSON serialisers. But:

  • Queries now run in the web layer, outside your service transaction. N+1 queries can hide inside the JSON writing, where nobody looks.
  • A database connection is held for the whole request. That includes slow calls to other services and the serialisation time. Under load, this uses up the whole connection pool.

How does it work?

The correct approach has two parts:

  1. Turn OSIV off.
  2. Load everything the response needs inside the service transaction. Then convert it to DTOs before you return.
spring.jpa.open-in-view: false

Example

@Service
public class OrderQueryService {
    private final OrderRepository repo;
    OrderQueryService(OrderRepository repo) { this.repo = repo; }

    @Transactional(readOnly = true)
    public OrderDetailDto detail(Long id) {
        Order o = repo.findWithLinesAndOutletById(id).orElseThrow();   // @EntityGraph loads what we need
        return OrderDetailDto.from(o);                                  // mapping happens INSIDE the transaction
    }
}
// Controller returns OrderDetailDto (a record) — no entities, no lazy proxies cross the boundary.

When would I use it?

Always, in services that give data to controllers. Use clear fetch plans (what to load, decided per use case), and map to DTOs inside the transactional service.

What can go wrong?

  • Leaving OSIV on: the pool runs out under load, and queries hide in the web layer.
  • "Fixing" LazyInitializationException the wrong way: making links EAGER, or calling Hibernate.initialize everywhere.
  • Serialising entities directly with Jackson: lazy proxies fire queries or throw errors. Return DTOs instead.

Interview questions

Q1. What causes LazyInitializationException? Touching a lazy link that is not loaded yet, after its persistence context (session) has closed. This usually happens outside the transaction.

Q2. What is Open-Session-in-View and why disable it? It keeps the persistence context open for the whole web request, so lazy loading works in the view layer. But it hides queries outside transactions and holds a DB connection for the full request. Disable it and load data explicitly in services.

7.12 @Transactional: how it works and its rollback rules

Why?

In simple words: You put @Transactional on a method. Spring then starts a transaction before the method, and commits it after — or rolls everything back if a runtime exception escapes. You write the boundary once, not in every method.

A business operation must be atomic — all steps happen, or none do. For example:

  • debit the account,
  • and write the ledger entry,
  • and write the outbox event.

Either all three are saved, or none are.

Think of an ATM. Either the cash comes out and your account is debited, or neither happens.

Doing this by hand in every method is repetitive and easy to get wrong. You would call connection.setAutoCommit(false), then commit, then roll back on errors — every single time. @Transactional lets you declare the boundary once.

What is happening internally?

  1. Spring wraps your bean in a proxy (6.7) — a wrapper object that sits in front of it. The proxy has a TransactionInterceptor.
  2. When a call comes through the proxy, the interceptor asks the PlatformTransactionManager to begin a transaction. For JPA, this is the JpaTransactionManager. It uses the settings you gave: propagation, isolation, timeout and readOnly.
  3. The manager gets a DB connection and turns autocommit off. Then it binds the connection and the EntityManager to the current thread. It does this through TransactionSynchronizationManager, which uses a ThreadLocal (4.15) — a variable that each thread has its own copy of. Any repository called in the same thread finds this connection and reuses it.
  4. Your method runs.
  5. If the method returns normally → flush + commit. If it throws an exception → rollback, but only if the rollback rules match. Otherwise, it still commits.
  6. The connection is unbound and returned to the pool. Then after-commit callbacks (@TransactionalEventListener) run.

Default rollback rules:

  • Roll back on unchecked exceptions (RuntimeException) and Errors.
  • Commit on checked exceptions (like IOException).
  • You can change this with rollbackFor / noRollbackFor.

How does it work?

@Service
public class RedemptionService {
    private final AccountRepository accounts;
    private final LedgerRepository ledger;
    private final OutboxRepository outbox;
    // constructor omitted

    @Transactional(timeout = 5)
    public RedemptionResponse redeem(String tenant, String accountId, String idemKey, long points) {
        var prior = ledger.findByTenantIdAndIdempotencyKey(tenant, idemKey);
        if (prior.isPresent()) return RedemptionResponse.from(prior.get());           // idempotent replay

        int updated = accounts.debitIfSufficient(accountId, points);                   // atomic conditional UPDATE (7.15)
        if (updated == 0) throw new InsufficientPointsException(accountId, points, accounts.balance(accountId));

        LedgerEntry e = ledger.save(new LedgerEntry(tenant, accountId, EntryType.REDEMPTION, -points, idemKey, Instant.now()));
        outbox.save(OutboxEvent.pointsRedeemed(e));                                     // same transaction (11.15)
        return RedemptionResponse.from(e);
    }                                                                                    // commit: all three rows or none
}

A note on the "idempotent replay" line: idempotent means doing the same request twice gives the same result as doing it once. If the same idempotency key comes again, we return the old result instead of debiting again.

Example

// Checked exception → COMMITS by default (surprise!)
@Transactional
public void importFile(Path p) throws IOException {
    repo.save(new Batch(p));
    parse(p);                      // throws IOException → the Batch row is still committed
}
@Transactional(rollbackFor = Exception.class)     // roll back for checked exceptions too
public void importFileSafely(Path p) throws IOException { /* ... */ }

// Swallowed exception → COMMITS
@Transactional
public void bad() {
    try { repo.save(x); risky(); } catch (RuntimeException e) { log.warn("ignored", e); }   // no rollback
}

When would I use it?

  • Put it on service-layer methods. Each such method should be one business operation.
  • Use @Transactional(readOnly = true) on query services. It turns on read optimisations, and it can send the reads to a replica database.
  • Keep transaction boundaries out of controllers and repositories.

What can go wrong? (where @Transactional silently doesn't work)

  • Self-invocation (6.7): a method calls another method in the same class. The call does not go through the proxy, so the annotation is ignored. The same is true for private or final methods, and for objects you create with new.
  • Checked exceptions commit by default. Swallowed exceptions (caught and not rethrown) also commit.
  • Work on another thread (@Async, executors, CompletableFuture) runs outside the transaction. Why? The transaction is bound to the original thread only.
  • Multiple data sources without saying which transactionManager to use.
  • Long transactions with remote calls inside: they hold a connection and row locks while waiting on the network. Also, the remote side effect cannot be rolled back. Better: do the DB work, commit, then call out. Or use the outbox pattern.
  • UnexpectedRollbackException: this happens in three steps: 1. An inner REQUIRED method throws. This marks the shared transaction as rollback-only. 2. The outer method catches the exception. 3. The outer method tries to commit — and Spring throws this exception, because the transaction can only roll back.

Interview questions

Q1. How does @Transactional work? A proxy's TransactionInterceptor begins a transaction through the PlatformTransactionManager and binds the connection to the current thread. Then it calls the method. At the end, it commits, or rolls back according to the rollback rules.

Q2. What are the default rollback rules? Roll back on RuntimeException and Error. Commit on checked exceptions, unless rollbackFor says otherwise.

Q3. List cases where @Transactional is silently ignored. Self-invocation, private or final methods, objects not managed by Spring, work on other threads, and the wrong transaction manager. Also, it still commits when a checked exception is thrown or an exception is swallowed.

Q4. Why shouldn't you call external APIs inside a transaction? The DB connection and locks stay held while you wait on the network. This hurts throughput and risks pool exhaustion and deadlocks. Also, if the DB transaction fails, you cannot roll back the external effect.

7.13 Transaction propagation

Why?

In simple words: When one transactional method calls another, propagation decides: does the inner one join the outer transaction, start its own separate one, or insist that one already exists?

Transactional methods often call other transactional methods. So a question comes up. Should the inner method:

  • join the caller's transaction,
  • start its own transaction, or
  • require that a transaction already exists?

The propagation setting decides this. A wrong choice causes one of two problems:

  • You lose data you wanted to keep. For example, an audit record is rolled back together with the failed operation.
  • You commit half-done work that you wanted to undo.

What is happening internally?

Propagation If a transaction exists If none exists
REQUIRED (default) Join it Start a new one
REQUIRES_NEW Pause it; start a separate one (on a separate connection) Start a new one
NESTED Create a savepoint inside it; if the inner part fails, roll back only to the savepoint Start a new one
SUPPORTS Join Run without a transaction
NOT_SUPPORTED Pause it; run without a transaction Run without a transaction
MANDATORY Join Throw an error
NEVER Throw an error Run without a transaction

(Pausing a transaction is officially called suspending it. A savepoint is a bookmark inside a transaction that you can roll back to.)

With REQUIRED, the inner and outer methods share one physical transaction. So if the inner method throws an unchecked exception, the whole transaction is marked rollback-only. This happens even if the outer method catches the exception.

How does it work?

outer() @Transactional(REQUIRED)           tx#1 begins
   ├─ ledger.save(...)                     tx#1
   ├─ audit.record(...) @REQUIRES_NEW      tx#1 suspended → tx#2 begins … commits → tx#1 resumes
   └─ throws RuntimeException              tx#1 rolls back — the audit row (tx#2) STAYS committed

Example

@Service
class AuditService {
    @Transactional(propagation = Propagation.REQUIRES_NEW)     // survives the caller's rollback
    public void recordAttempt(String accountId, String action, String outcome) {
        auditRepo.save(new AuditEntry(accountId, action, outcome, Instant.now()));
    }
}

@Service
class RedemptionFacade {
    private final RedemptionService redemption; private final AuditService audit;
    // constructor omitted
    @Transactional
    public void redeemWithAudit(String acc, long pts) {
        try {
            redemption.redeem(acc, pts);
            audit.recordAttempt(acc, "REDEEM", "OK");
        } catch (InsufficientPointsException e) {
            audit.recordAttempt(acc, "REDEEM", "INSUFFICIENT");  // committed independently
            throw e;                                              // outer transaction rolls back
        }
    }
}

NESTED uses JDBC savepoints. DataSourceTransactionManager supports it. With JPA's transaction manager, it works only in limited setups. It is useful for "try this sub-step; if it fails, undo only that step and carry on".

When would I use it?

  • REQUIRED: for almost everything.
  • REQUIRES_NEW: for work that must be saved whatever happens to the outer transaction. Examples: audit logs, failure records, idempotency-key reservations, or sequence allocation.
  • MANDATORY: on repository-like methods that must never run outside a transaction.
  • SUPPORTS: for readOnly queries that work fine with or without a transaction.

What can go wrong?

  • Pool deadlock with REQUIRES_NEW: it needs a second connection while the first one is still held. Under load, with a small pool, every thread holds one connection and waits for another. Nobody can move forward.
  • REQUIRES_NEW cannot see the outer transaction's writes: the paused outer transaction has written rows but not committed them. The new transaction won't see them. It may even block, waiting on their locks.
  • Expecting a caught inner exception to be harmless: with REQUIRED, the outer transaction is already marked rollback-only. You get UnexpectedRollbackException at commit.

Interview questions

Q1. REQUIRED vs REQUIRES_NEW vs NESTED? REQUIRED joins the current transaction, or creates one; everything shares it. REQUIRES_NEW pauses the current one and runs a separate transaction that commits or rolls back on its own. NESTED creates a savepoint inside the current transaction.

Q2. When would you use REQUIRES_NEW? For work that must be saved no matter what happens to the caller, such as audit or failure logs. But remember it needs an extra connection.

Q3. Why might REQUIRES_NEW cause a deadlock? Each request holds one connection and needs a second. If such requests fill the whole pool, they all wait for each other forever.

7.14 Isolation levels and concurrency anomalies

Why?

In simple words: Many transactions touch the same rows at the same time. The isolation level decides how much one transaction can see of another's unfinished work. Too loose gives wrong data; too strict makes everything slow.

Many transactions run at the same time on the same rows. Isolation decides how much they see of each other's changes — changes that are not committed yet, or that happen in parallel.

  • Too weak: you get double redemptions and wrong balances.
  • Too strong: you get blocking, retries and lower throughput.

Choosing the level on purpose, not by accident, is a senior skill.

What is happening internally?

These are the problems (anomalies) that can happen. T1 and T2 are two transactions running at the same time.

Anomaly What happens
Dirty read T2 reads T1's change before T1 commits it; then T1 rolls back, so T2 used data that never existed
Non-repeatable read T1 reads the same row twice and gets different values, because T2 committed an update in between
Phantom read T1 runs the same range query twice and sees new or missing rows, because T2 inserted or deleted rows in between
Lost update T1 and T2 both read balance 100, and each writes its own result; one of the updates is lost
Write skew T1 and T2 read the same data, then each writes a different row based on it, and together they break a rule (two doctors both go off call, leaving nobody)
Isolation level Dirty Non-repeatable Phantom Default in
READ UNCOMMITTED possible possible possible —
READ COMMITTED prevented possible possible PostgreSQL, SQL Server, Oracle
REPEATABLE READ prevented prevented possible (prevented in Postgres's snapshot implementation; mostly prevented in InnoDB using gap locks) MySQL InnoDB
SERIALIZABLE prevented prevented prevented —

How do databases build these levels? Two main ways:

  • MVCC snapshots (multi-version concurrency control): each transaction reads a consistent snapshot of the data, as of a point in time. Used by PostgreSQL, Oracle, InnoDB, and SQL Server with snapshot isolation.
  • Locks: readers and writers block each other. SQL Server's default READ COMMITTED works this way.

More details are in 12.7.

Remember: Lost updates and write skew are not prevented by READ COMMITTED. To stop them, you need row locks, optimistic versions or atomic statements (7.15), or SERIALIZABLE.

How does it work?

@Transactional(isolation = Isolation.REPEATABLE_READ)
public Report monthlyStatement(String accountId) { /* several reads that must be consistent with each other */ }

@Transactional(isolation = Isolation.SERIALIZABLE)
public void allocateLimitedVouchers(...) { /* rare: invariant across rows; be ready to RETRY serialization failures */ }

(An invariant is a rule that must always stay true — for example, "balance never goes below zero".)

Example

Lost update under READ COMMITTED (balance = 100):
T1: SELECT balance → 100              T2: SELECT balance → 100
T1: UPDATE balance = 100 - 80 = 20    T2: UPDATE balance = 100 - 50 = 50
T1: COMMIT                            T2: COMMIT  → final 50; 130 points spent from a 100 balance
Fix: UPDATE account SET balance = balance - :p WHERE id = :id AND balance >= :p   (7.15)

When would I use it?

  • Most OLTP work (normal day-to-day transactions): keep the default, READ COMMITTED. Protect specific rules with locking or atomic statements.
  • Several reads that must agree with each other (reports, statements): use REPEATABLE READ or a snapshot.
  • Complex rules across many rows: use SERIALIZABLE, but only rarely, and with automatic retry.

What can go wrong?

  • Raising isolation for the whole app "to be safe": you get more blocking, more deadlocks and more serialisation failures.
  • Assuming a level behaves the same in every database: it does not. Postgres REPEATABLE READ is snapshot isolation; MySQL's REPEATABLE READ is not the same thing.
  • Forgetting to retry serialisation failures (SQLSTATE 40001). At SERIALIZABLE, the database cancels some transactions on purpose. You must retry them.

Interview questions

Q1. Name the isolation levels and the anomalies each prevents. Read uncommitted prevents none. Read committed prevents dirty reads. Repeatable read also prevents non-repeatable reads. Serializable also prevents phantoms and write skew.

Q2. What is a lost update and how do you prevent it? Two read-modify-write transactions overwrite each other's result. Prevent it with an atomic UPDATE statement, SELECT FOR UPDATE, or an optimistic version check.

Q3. What is the default isolation in PostgreSQL and MySQL? PostgreSQL uses READ COMMITTED. MySQL InnoDB uses REPEATABLE READ.

7.15 Optimistic locking, pessimistic locking and atomic updates

Why?

In simple words: When two requests change the same row at once, you have three choices. Check for a clash at save time (optimistic). Lock the row while reading (pessimistic). Or do the check and the change in one SQL statement (atomic update).

Many requests change the same rows at the same time. For example:

  • two redemptions from the same account,
  • two admins editing the same campaign,
  • many users booking the last seat.

You need a strategy that keeps the data correct, without killing throughput.

Think of IRCTC tatkal booking. Many people want the last seat. Only one should get it, and nobody should be charged for a seat they did not get.

What is happening internally?

1. Optimistic locking (@Version) — "assume no clash, but check at save time":

  1. No lock is taken while reading.
  2. On update, Hibernate adds WHERE id = ? AND version = ? and increases the version by one.
  3. If another transaction changed the row first, the version no longer matches. The update matches 0 rows.
  4. Hibernate throws OptimisticLockException. (Spring wraps it as ObjectOptimisticLockingFailureException.)
  5. You retry, or report a conflict to the user.

No locks are held between the read and the write.

2. Pessimistic locking — "lock first, then work":

  • SELECT … FOR UPDATE takes a row lock at read time.
  • Other writers, and other FOR UPDATE readers, wait until you commit.
  • The lock holder is sure to succeed. The cost is that others are blocked.

3. Atomic conditional update — "let the database do it in one step":

  • One SQL statement does the read, the check and the write, all inside the database: UPDATE … SET balance = balance - ? WHERE id = ? AND balance >= ?.
  • The row lock is held only for that one statement.
  • The number of affected rows tells you whether it worked: 1 = success, 0 = failed.

How does it work?

Strategy Best when Cost
Optimistic @Version Clashes are rare (editing campaigns, profiles); the user takes a long time between reading and saving Retries or 409 errors when a clash happens
Pessimistic FOR UPDATE Clashes are frequent and retries are costly; a rule across many rows inside one transaction Blocking, risk of deadlock, lower throughput
Atomic UPDATE A numeric rule on a single row (balance, stock, counters) The logic must fit in one SQL statement

Example

@Entity
class Campaign {
    @Id Long id;
    String name;
    @Version long version;                       // optimistic locking
}
// Two admins load version 3; first save → version 4; second save → UPDATE ... WHERE version=3 → 0 rows → 409 Conflict

public interface AccountRepository extends JpaRepository<Account, String> {
    @Lock(LockModeType.PESSIMISTIC_WRITE)                                         // SELECT ... FOR UPDATE
    @QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "3000"))
    @Query("select a from Account a where a.id = :id")
    Optional<Account> findByIdForUpdate(@Param("id") String id);

    @Modifying
    @Query("update Account a set a.balance = a.balance - :p where a.id = :id and a.balance >= :p")
    int debitIfSufficient(@Param("id") String id, @Param("p") long points);       // 1 = success, 0 = insufficient
}

// Optimistic retry with Spring Retry
@Retryable(retryFor = ObjectOptimisticLockingFailureException.class, maxAttempts = 3, backoff = @Backoff(delay = 50))
@Transactional
public void rename(Long id, String name) { campaignRepo.findById(id).orElseThrow().setName(name); }

Here is what happens when two redemptions run at the same time with the atomic update. The balance is 100, and both requests ask for 80:

T1: UPDATE … WHERE id='A1' AND balance >= 80 → row locked, balance 100 ≥ 80 → balance = 20, 1 row
T2: same UPDATE → waits for T1's row lock → T1 commits → re-evaluates: 20 ≥ 80 false → 0 rows → insufficient
Result: exactly one succeeds; no lost update, no application-level lock.

When would I use it?

  • Atomic updates: for balances, stock and counters — like your loyalty ledger.
  • Optimistic versions: for entities and aggregates that admins edit.
  • Pessimistic locks: for operations on many rows that must stay consistent within one transaction. Always lock rows in the same order everywhere, to avoid deadlocks (4.13 / 12.7).

What can go wrong?

  • Holding pessimistic locks while calling external services: others stay blocked for a long time, and the pool runs out.
  • Locking rows in different orders in different code paths: T1 locks A then B, T2 locks B then A. Each waits for the other — a database deadlock.
  • Optimistic retries without backoff under heavy contention: everyone retries at the same moment and clashes again. This is a retry storm. Also, retrying side effects that are not idempotent (not safe to repeat) can do them twice.
  • @Version with bulk JPQL updates: bulk updates do not increase the version, so the check is skipped.

Interview questions

Q1. Optimistic vs pessimistic locking? Optimistic finds clashes at write time with a version check. It takes no locks and retries on conflict, so it suits low contention. Pessimistic locks rows at read time (FOR UPDATE) and blocks other writers, so it suits high contention.

Q2. How would you prevent double-spending of points under concurrency? Use an atomic conditional UPDATE (balance >= amount) and check the affected row count — or use a row lock. Add an idempotency key so duplicate requests are not processed twice.

Q3. What happens when an optimistic lock check fails? The update affects zero rows, and Hibernate throws OptimisticLockException. The application then retries, or returns 409.

7.16 Connection pools, migrations and JPA performance settings

Why?

In simple words: Keep a set of ready database connections and reuse them (a pool). Change the schema only through numbered SQL scripts (migrations). And switch on a few Hibernate settings so inserts go in batches.

Three needs, three tools:

  • Pool: opening a DB connection takes milliseconds — TCP setup, TLS, login. So every app keeps a pool of open connections and reuses them.
  • Migrations: schema changes must be versioned and must run the same way in every environment. So you need migrations.
  • Settings: a few Hibernate settings make the difference between 50 and 5,000 inserts per second.

Think of an auto stand. Autos wait in a line, ready to go. You take one, finish your trip, and it comes back to the line. Nobody builds a new auto for each ride.

What is happening internally?

  • HikariCP is Spring Boot's default pool. It keeps a set of open connections. 1. A thread borrows one (getConnection). 2. It uses it for the transaction. 3. It gives it back. 4. If no connection is free, the thread waits up to connection-timeout, and then fails.
  • Pool size — more is not better. The database has limited CPU cores and disk. Beyond a point, more parallel queries just fight each other for them.
  • A common starting point is about 10–20 connections per app instance.
  • Multiply by the number of instances. The total must stay within the DB's max_connections.
  • Flyway runs numbered SQL scripts (V1__init.sql, V2__add_index.sql) in order at startup. It records which ones it has run in the flyway_schema_history table. Liquibase is the alternative, based on XML/YAML.

How does it work?

spring:
  datasource:
    hikari:
      maximum-pool-size: 20
      minimum-idle: 5
      connection-timeout: 3000        # ms to wait for a free connection before failing
      max-lifetime: 1500000           # below DB/firewall idle limits (25 min here)
      leak-detection-threshold: 20000 # log a stack trace if a connection is held > 20 s
  jpa:
    open-in-view: false
    hibernate.ddl-auto: validate      # never 'update' in production
    properties:
      hibernate.jdbc.batch_size: 50
      hibernate.order_inserts: true
      hibernate.order_updates: true
      hibernate.default_batch_fetch_size: 50
  flyway.enabled: true

Example

-- src/main/resources/db/migration/V3__ledger_account_index.sql
CREATE INDEX CONCURRENTLY IF NOT EXISTS ix_ledger_account_created ON ledger_entry (account_id, created_at DESC);
-- (PostgreSQL CONCURRENTLY can't run inside a transaction: mark this migration non-transactional in Flyway config)

Zero-downtime schema change — the expand → migrate → contract pattern. You change the schema while the app keeps running:

  1. Expand: add the new column as nullable (V4).
  2. Deploy code that writes to both the old and the new column.
  3. Migrate: fill in old rows (backfill) in small batches.
  4. Deploy code that reads from the new column.
  5. Contract: drop the old column in a later release (V5).

When would I use it?

In every service:

  • Tune the pool using its metrics (hikaricp.connections.active, pending).
  • Put every schema change in a versioned migration.
  • Turn on batching for jobs that write a lot.

What can go wrong?

  • Pool exhaustion: slow queries, long transactions, OSIV or leaked connections (borrowed and never returned). Threads get stuck in getConnection. A thread dump shows this (5.8).
  • Too many connections during autoscaling: pool size × number of pods goes above the DB's connection limit. Use PgBouncer (a connection pooler in front of Postgres), or size the pools correctly.
  • Migrations that lock big tables: for example, adding a column with a volatile default (a value computed per row, like random()), creating an index without CONCURRENTLY, or running a long backfill in one transaction.
  • Editing a migration file that has already run: Flyway stores a checksum of each file. The checksum no longer matches, so the app fails at startup.

Interview questions

Q1. How do you size a connection pool? Start small, about 10–20 per instance. Keep the total under what the DB can handle. Then tune from pool metrics and DB load. The DB's cores and I/O limit useful parallel work — not the number of app threads.

Q2. Why not use ddl-auto=update in production? It is not versioned, and it cannot do safe data migrations. It may make destructive or locking changes, and it can behave differently in each environment. Use Flyway/Liquibase migrations, and set validate.

Q3. How do you make a schema change with zero downtime? Use expand-migrate-contract. Make additive changes first, write to both old and new, backfill in batches, switch reads to the new structure, and remove the old structure in a later release.
