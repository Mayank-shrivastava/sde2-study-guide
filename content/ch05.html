At SDE2 level, JVM questions change. Juniors get "what is GC?". You will get something like: "p99 latency doubled and memory keeps climbing — walk me through what you'd do". (p99 latency means: 99% of requests finish faster than this time; it shows the slowest 1%.) This chapter gives you two things. First, a clear picture of how the JVM works inside. Second, the tools and steps to debug it in production.

5.1 Class loading

Why?

In simple words: Java does not load all your classes at startup. It loads each class from disk only when your code first needs it, and it always asks the "senior" loaders first so nobody can sneak in a fake String class.

Java loads classes lazily, at runtime. "Lazily" means only when they are first needed. It does not link everything into one big binary at build time.

This gives you useful powers:

  • Plugins can be added without rebuilding the app.
  • Frameworks like Spring can scan the classpath and discover your classes on their own.
  • Dynamic proxies (classes generated in memory while the app runs) become possible.
  • Hot reload (swapping code without a full restart) becomes possible.
  • Startup memory stays small. You only pay for the classes you actually use.

But this flexibility needs safety. Nobody should be able to replace java.lang.String with their own version. The loading design below protects against that.

What is happening internally?

A class loader is the part of the JVM that finds a class's bytes and turns them into a usable class. There are three built-in loaders. They are arranged like a chain of seniors and juniors. This arrangement is called the parent-delegation hierarchy:

Bootstrap loader (native)     → java.base: java.lang.*, java.util.* …
   ▲ parent
Platform loader               → other Java SE / JDK modules (java.sql, …)
   ▲ parent
Application (system) loader   → your classpath / module path: your code + dependency JARs
   ▲ parent
Custom loaders                → app servers, plugin systems, Spring Boot's LaunchedURLClassLoader (nested JARs)

Delegation works like this. When a loader is asked for a class, it first asks its parent. Only if the parent cannot find the class does it load the class itself. Because of this rule, core classes like String always come from the bootstrap loader. Your fake String is never even looked at.

Think of a government office. A clerk gets a file. He first sends it up to his senior. Only if the senior says "not mine" does the clerk handle it himself.

Every class goes through three stages:

  1. Loading: The JVM reads the class bytes. They can come from a JAR, a file, or be generated in memory. It then creates a Class object in Metaspace (the memory area for class information, see 5.2).
  2. Linking: This has three small steps. - Verification: check that the bytecode is well-formed and type-safe, so it cannot corrupt memory. - Preparation: create the static fields and fill them with default values (0, null, false). - Resolution: replace symbolic names (like "the method foo in class Bar") with direct memory references. This is often done lazily, only when first used.
  3. Initialisation: The JVM runs static initialiser blocks and static field assignments. This happens: - exactly once; - thread-safely (the JVM holds an init lock, so two threads can't both run it); - on the first active use of the class. Active use means: creating a new instance, calling a static method, reading a static field, using reflection on it, or initialising a subclass.

One more key point. The JVM identifies a class at runtime by two things together: (fully qualified name, defining class loader). So if two different loaders load the same class, the JVM sees two different types. They are not interchangeable.

How does it work?

Here is what happens the first time your code runs new OrderService():

  1. The application loader is asked for OrderService.
  2. It delegates up to the platform loader.
  3. The platform loader delegates up to the bootstrap loader.
  4. The bootstrap loader does not find it. The platform loader does not find it either.
  5. The request comes back down to the application loader.
  6. The application loader finds OrderService.class in your JAR.
  7. The class is loaded, then linked, then its statics are initialised.
  8. Finally, the object itself is allocated.

Example

public class LoadDemo {
    static class Lazy { static { System.out.println("Lazy initialised"); } static final int CONST = 42; static int value = 7; }
    public static void main(String[] args) throws Exception {
        System.out.println(Lazy.CONST);        // 42 — compile-time constant is INLINED: does NOT initialise Lazy
        System.out.println(Lazy.value);        // prints "Lazy initialised" then 7 — first active use
        System.out.println(String.class.getClassLoader());                 // null (bootstrap)
        System.out.println(LoadDemo.class.getClassLoader());               // app class loader
    }
}
// java -verbose:class LoadDemo   → watch every class being loaded and from where

Note the first line of output. Lazy.CONST is a compile-time constant. The compiler copies the value 42 directly into the calling code. So reading it never touches the Lazy class, and Lazy is not initialised. Reading Lazy.value is a real active use, so initialisation runs first.

When would I use it?

  • Diagnosing ClassNotFoundException and NoClassDefFoundError.
  • Fixing dependency conflicts. If two versions of a library are on the classpath, the first one found wins.
  • Understanding Spring Boot fat JARs (one JAR that contains other JARs inside it).
  • Explaining when static initialisation runs and why it is thread-safe. The holder-idiom singleton depends on this (4.6).

What can go wrong?

  • ClassNotFoundException: You asked for a class by its name (for example with Class.forName, or a framework using reflection). It is not on the classpath.
  • NoClassDefFoundError: The class was there at compile time but is missing at runtime. Or — a very common case — its static initialiser already failed earlier. Search the logs for the first ExceptionInInitializerError; that is the real cause.
  • Dependency hell: A NoSuchMethodError at runtime usually means a different version of a library won on the classpath. That version does not have the method your code expects. Check with mvn dependency:tree, and use the Spring Boot BOM (bill of materials — a managed list of compatible versions).
  • ClassCastException between "identical" classes: The same class was loaded by two different loaders. This happens in plugin systems and app servers. To the JVM they are two different types, so casting fails.
  • ClassLoader leaks: In app servers, you redeploy the app. But something still holds a reference to an old class — for example a ThreadLocal, a static registry, or a JDBC driver. That one reference keeps the whole old ClassLoader alive, along with every class it loaded. After many redeploys, Metaspace keeps growing until you get OutOfMemoryError: Metaspace.

Interview questions

Q1. Explain parent delegation. When a class loader is asked for a class, it first passes the request to its parent. It loads the class itself only if the parent cannot find it. Because of this, core classes always come from the bootstrap loader, so nobody can spoof them and there are no duplicate copies.

Q2. ClassNotFoundException vs NoClassDefFoundError? CNFE: a class that was requested dynamically by name (for example Class.forName) is not found. NCDFE: a class that was available at compile time cannot be loaded at runtime — either it is missing, or its static initialisation failed earlier.

Q3. When is a class initialised? On its first active use: creating an instance, calling a static method, reading a static field that is not a compile-time constant, using reflection, or initialising a subclass. Reading a compile-time constant does not trigger it, because the value is copied into the caller at compile time.

5.2 Runtime memory areas

Why?

In simple words: The JVM's memory is not one big bucket. It is split into several areas, each storing a different kind of data and each with its own "full" error — and the heap is only one of them.

You need this map to do three practical things:

  • size containers correctly,
  • read GC logs, and
  • understand what an OutOfMemoryError message is telling you.

For each kind of data, you should know which memory area it lives in. You should also know what happens when that area fills up.

What is happening internally?

┌──────────────────────── JVM process memory ───────────────────────────┐
│ HEAP (-Xmx)          objects & arrays; shared; GC-managed               │
│   Young gen: Eden | S0 | S1      Old gen (tenured)                      │
├────────────────────────────────────────────────────────────────────────┤
│ METASPACE (native)   class metadata, method bytecode, constant pools    │
│ CODE CACHE (native)  JIT-compiled machine code                          │
│ THREAD STACKS        one per platform thread (-Xss, ~512KB–1MB)         │
│ DIRECT BUFFERS       ByteBuffer.allocateDirect, Netty, NIO              │
│ GC / JIT internals, symbol tables, native libraries                    │
└────────────────────────────────────────────────────────────────────────┘
Per thread: JVM stack (frames: locals + operand stack), PC register, native method stack

Quick meaning of each area:

  • Heap: where all your objects and arrays live. All threads share it. The garbage collector manages it. -Xmx sets its maximum size.
  • The young generation (Eden plus two survivor spaces, S0 and S1) holds new objects.
  • The old generation (also called tenured) holds objects that have lived a long time.
  • Metaspace: information about classes — their structure, method bytecode and constant pools. It lives in native memory, meaning memory outside the heap that the JVM gets directly from the operating system.
  • Code cache: the machine code produced by the JIT compiler (5.10).
  • Thread stacks: one per platform thread. Each holds the method calls currently running in that thread. Size is set by -Xss, usually about 512 KB–1 MB.
  • Direct buffers: memory outside the heap used for fast I/O, for example by ByteBuffer.allocateDirect, Netty and NIO.
  • Other internals: the GC's and JIT's own data, symbol tables and native libraries.

Each thread also has its own small private areas: its JVM stack (made of frames — one frame per method call, holding local variables and the operand stack), a PC register (which instruction is next), and a native method stack.

Area Contains Error when exhausted
Heap All objects and arrays OutOfMemoryError: Java heap space / GC overhead limit exceeded
Metaspace Class metadata (replaced PermGen in Java 8; grows on its own as needed) OutOfMemoryError: Metaspace
Thread stack One frame per method call StackOverflowError
Native memory for threads The OS's own structures for each thread OutOfMemoryError: unable to create native thread
Direct memory Buffers outside the heap OutOfMemoryError: Direct buffer memory
Code cache JIT-compiled code Warning "CodeCache is full"; the JIT stops compiling → sudden slowdown

Why PermGen was removed: Before Java 8, class metadata and interned strings lived in PermGen. PermGen was a fixed-size part of the heap. Apps that loaded many classes kept running out of it and failed with PermGen space errors. Examples are Groovy apps, app servers and apps with many proxies.

Java 8 fixed this in two ways:

  1. Class metadata moved to Metaspace. It lives in native memory and grows as needed. You can still put a cap on it with -XX:MaxMetaspaceSize.
  2. Interned strings moved to the normal heap.

How does it work?

Here is the key formula:

Total container memory ≈ heap + metaspace + code cache + (threads × stack) + direct buffers + GC overhead.

-Xmx limits only the first item, the heap. Everything else comes on top of it. So say you set -Xmx equal to the container's memory limit. The total process will go over the limit. Kubernetes (the Linux kernel, really) then kills the pod — this is called being OOM-killed. Java itself never reports an OutOfMemoryError, because the heap was never full.

Think of a 2 BHK flat. -Xmx is the size of the hall only. If you rent a flat exactly the size of the hall, the kitchen and bedrooms don't fit.

Example

Container limit 2 GiB:
  -XX:MaxRAMPercentage=70     → heap ≈ 1.4 GiB
  metaspace ~150 MB, code cache ~50 MB, 200 threads × 1 MB = 200 MB, direct buffers ~64 MB, GC structures ~50 MB
  → ~1.9 GiB: fits. With -Xmx2g the process would exceed the limit and be killed (exit code 137, OOMKilled).

You can check the real numbers on a running JVM:

jcmd <pid> VM.native_memory summary     # requires -XX:NativeMemoryTracking=summary
jcmd <pid> GC.heap_info

When would I use it?

  • Sizing pods and choosing JVM flags.
  • Reading an OOM message and knowing which area ran out.
  • Explaining in an incident why "the JVM uses more memory than -Xmx".

What can go wrong?

  • Pods OOM-killed by the kernel with no Java error. This happens when you forget non-heap memory in your sizing.
  • Thread-per-request with thousands of threads. Each thread needs native memory for its stack and OS structures. Native memory runs out.
  • Deep recursion. Each call adds a frame to the stack until you hit StackOverflowError.
  • Metaspace growth from classes generated at runtime. Sources are proxies, lambdas in dynamically generated code, and redeploy leaks (5.1).

Interview questions

Q1. What are the JVM memory areas? The heap (young generation with Eden and two survivor spaces, plus the old generation), Metaspace, the code cache, per-thread stacks and PC registers, native method stacks, and direct memory.

Q2. What replaced PermGen and why? Metaspace, in Java 8. It lives in native memory and grows automatically, so the old fixed-size PermGen out-of-memory errors went away. Interned strings moved to the heap.

Q3. Why does a Java process use more memory than -Xmx? -Xmx limits only the heap. Metaspace, thread stacks, the code cache, direct buffers and GC data structures all come on top of it.

5.3 Object allocation and the generational heap

Why?

In simple words: Most objects are like paper tea cups — used once and thrown away within seconds. A few are like steel utensils that stay for years. So the JVM keeps the new objects in a separate small area and cleans that area very often and very cheaply.

In a server, most objects die almost immediately. Examples: request DTOs, iterators, temporary strings. A few objects live for the whole run of the app. Examples: caches, Spring beans, connection pools.

This pattern has a name: the weak generational hypothesis ("most objects die young"). Because it is true, the JVM can:

  • collect the young area — which is mostly garbage — cheaply and often, and
  • collect the old area only rarely.

What is happening internally?

1. Allocation is just a pointer bump. Each thread gets a TLAB (Thread-Local Allocation Buffer). A TLAB is a private chunk of Eden that only that thread uses. To create an object, the thread just moves a pointer forward inside its TLAB. No locking is needed, because no other thread uses that chunk. It typically takes a few nanoseconds — faster than malloc in C.

2. New objects go to Eden. When Eden fills up, a minor GC (also called a young GC) runs:

  1. Live objects in Eden and in the "from" survivor space are copied into the "to" survivor space.
  2. Each copied object's age goes up by one.
  3. Everything left behind in Eden is garbage. The JVM frees all of it at once just by resetting the pointer.

So the cost depends only on the number of live objects, not on the garbage. Garbage is free to remove.

3. Survivors get promoted. An object that survives enough minor GCs is promoted (moved) to the old generation. The limit is called the tenuring threshold. It is at most 15, and the JVM adjusts it on its own. Very large objects may go straight to old gen. In G1 they go to special humongous regions instead (5.5).

4. Old gen is cleaned rarely. The old generation is collected less often, by major or mixed collections. These are more expensive.

5. Card table / remembered sets. Sometimes an old object points to a young object. The JVM keeps a record of such links. So during a minor GC, it doesn't have to scan the whole old generation to find which young objects are still used. It just checks this record.

6. Escape analysis. Sometimes the JIT compiler can prove that an object never leaves the method that created it. Then it doesn't put the object on the heap at all. Instead, it turns the object's fields into plain local variables. This is called scalar replacement.

new Order() → TLAB in Eden
minor GC #1: Order still referenced → copied to S0 (age 1)
minor GC #2: → copied to S1 (age 2)  ... age N → promoted to Old
request DTOs: dead before the first minor GC → reclaimed for free

How does it work?

A healthy service in a steady state looks like this:

  1. Eden fills every few seconds.
  2. A minor GC runs and takes a few milliseconds.
  3. Most objects are gone after it.
  4. Old gen grows slowly with long-lived data, and gets cleaned occasionally.

Trouble starts with medium-lived objects. Examples: a response cache with a short TTL (time-to-live), or objects held while waiting on a slow downstream call. They live just long enough to be promoted to old gen. Then they die there. Now old gen fills with garbage quickly, so old-gen collections become frequent and costly. This problem is called premature promotion.

Example

GC log (G1), healthy:
[12.345s] GC(41) Pause Young (Normal) (G1 Evacuation Pause) 612M->98M(1024M) 7.812ms
             young collections frequent and short; heap after GC (98M) stable over time

GC log, leak or overload:
[901.2s] GC(880) Pause Young (Normal) 1010M->940M(1024M) 45ms
[901.9s] GC(881) Pause Full (G1 Compaction Pause) 1020M->985M(1024M) 2950ms
             heap after GC near the max and rising, full GCs taking seconds → leak or undersized heap

How to read a log line like 612M->98M(1024M) 7.812ms: heap used before GC → heap used after GC (total heap size), and the pause time. The number to watch is the "after GC" value over time.

When would I use it?

  • Reading GC logs.
  • Explaining latency spikes.
  • Tuning heap size.
  • Deciding whether to reduce allocation in hot code paths, for example by reusing objects or using primitive arrays.

What can go wrong?

  • Young gen too small. Minor GCs happen too often, and objects get promoted too early (premature promotion).
  • Huge object arrays. In G1 these become humongous allocations, which fragment the regions.
  • Allocation storms. Logging, boxing (turning int into Integer) or JSON parsing inside hot loops create huge numbers of short-lived objects.

Interview questions

Q1. Why is the heap divided into generations? Because most objects die young. Collecting a small young generation often is cheap, since only the few survivors are copied. Long-lived objects sit in the old generation, which is collected rarely.

Q2. How does an object move to old gen? By surviving a number of minor GCs — it ages each time it is copied between survivor spaces. It can also go there directly if it is too large, or if the survivor spaces overflow.

Q3. What is a TLAB? A Thread-Local Allocation Buffer: a private chunk of Eden for one thread. The thread allocates objects by just moving a pointer forward, with no synchronisation.

5.4 How garbage collection finds and frees garbage

Why?

In simple words: The garbage collector starts from a few fixed starting points, follows every reference it can reach, and treats everything it could not reach as rubbish — while your app keeps running and changing things.

In C, you manage memory by hand with malloc and free. That causes three classic bugs:

  • use-after-free — using memory that was already freed, which crashes or corrupts data;
  • double free — freeing the same memory twice;
  • leaks — forgetting to free memory.

Java frees memory automatically. But the collector has a hard job. It must decide safely which objects are dead. And it must do this while the application keeps changing references.

What is happening internally?

Reachability, not reference counting. An object is live if you can reach it by following references from GC roots. GC roots are the fixed starting points:

  • local variables and operands on thread stacks,
  • static fields,
  • JNI references (references held by native code),
  • live threads,
  • objects used as synchronisation monitors (locks).

Everything that cannot be reached is garbage. This includes cycles — objects pointing to each other but not reachable from any root. Reference counting (counting how many references point to an object) cannot free such cycles, because each object in the cycle still has a count above zero. Reachability handles them correctly.

Core algorithms:

  • Mark: start from the roots, walk all references, and mark every reachable object.
  • Sweep: free the memory of unmarked objects in place. This leaves gaps, called fragmentation.
  • Compact: slide live objects together and update all references to them. No fragmentation, but extra work.
  • Copy/evacuate: copy live objects into an empty area, then treat the old area as empty. Cost depends on the amount of live data. Used for the young gen and for G1 regions.

Stop-the-world (STW) pause. Some GC phases need all application threads to be stopped. Threads can only stop at safepoints. A safepoint is a place where the JVM knows exactly what the thread's state is — for example a method return or the jump back to the start of a loop.

Modern collectors do most of their work concurrently, meaning while the application keeps running. To do this safely they use barriers. A barrier is a small piece of code the JIT inserts wherever your code reads or writes a reference. It lets the GC track changes made during concurrent marking.

Tri-colour marking. During marking, each object has one of three colours:

  • White: not seen yet.
  • Grey: seen, but its children (the objects it points to) are not scanned yet.
  • Black: fully scanned.

During concurrent marking, the app could move a reference to a white object into a black object. The GC will never rescan the black object, so it would miss the white one and wrongly free it. Write barriers prevent this by telling the GC about such changes.

How does it work?

GC roots → A → B → C            D ⇄ E (cycle, unreachable)
mark: A, B, C marked            D, E unmarked → garbage, freed despite referencing each other

Here A, B and C are reachable from a root, so they are marked and kept. D and E point to each other, but nothing from the roots reaches them. So they stay unmarked and are freed, even though each one references the other.

Example

void handle(Request r) {
    Order o = new Order(r);       // reachable from this stack frame while handle() runs
    cache.put(o.id(), o);         // now ALSO reachable from a static cache → survives after return
}                                  // frame popped; if the cache weren't there, o would be garbage now

When would I use it?

  • To reason about leaks. The question "which path from a GC root keeps this object alive?" is exactly what heap-dump tools answer.
  • To reason about latency, because of STW pauses.
  • To explain why calling System.gc() is pointless. It is only a hint to the JVM — and a harmful one, because it can trigger an expensive full GC.

What can go wrong?

  • Long STW pauses. These come from a large live set (lots of live data to process) or from full GCs.
  • Time-to-safepoint delays. A GC pause must wait until every thread reaches a safepoint. A long counted loop with no safepoint check inside can make everyone wait for that one thread.
  • Finalizers (deprecated). A finalizer can bring an object back to life ("resurrect" it) and delays the freeing of its memory.

Interview questions

Q1. How does the JVM decide an object is garbage? If it cannot be reached from any GC root — thread stacks, static fields, JNI references, active threads — it is garbage. Unreachable cycles are collected too.

Q2. What is a stop-the-world pause and a safepoint? A stop-the-world pause is a phase where all application threads are halted so the GC can work safely. Threads stop at safepoints, which are points where the JVM knows the exact state of their stacks.

Q3. Mark-sweep vs mark-compact vs copying? Mark-sweep frees dead objects in place, which leaves fragmentation. Mark-compact moves live objects together, so there are no gaps. Copying evacuates live objects to a fresh area; its cost is proportional to the amount of live data.

5.5 The garbage collectors: Serial, Parallel, G1, ZGC

Why?

In simple words: Different apps want different things from the GC — maximum work done, shortest pauses, or least memory used. No collector wins on all three, so Java gives you several to choose from.

Each type of application cares about something different:

  • A batch job wants maximum throughput — the most total work done per hour. Pauses don't matter much.
  • A trading or ordering API wants low latency — short pauses, so no request waits long.
  • A small container wants a low footprint — little memory and CPU used by the GC itself.

No single collector is best at all three. So the JVM offers several.

What is happening internally?

Collector Flag How it works Pauses Best for
Serial -XX:+UseSerialGC One thread. Stops the app and does mark-copy for young gen and mark-compact for old gen Long Tiny heaps, 1-CPU containers
Parallel -XX:+UseParallelGC Same as Serial, but uses many threads Long but efficient Batch jobs, max throughput
G1 (default since Java 9) -XX:+UseG1GC Splits the heap into ~2048 equal regions (1–32 MB each). Young collections evacuate the young regions. Concurrent marking finds old regions that are mostly garbage. Mixed collections then evacuate the regions with the most garbage first ("Garbage First"), staying within a pause-time target (MaxGCPauseMillis, default 200 ms). Huge objects get humongous regions. Typically 10–200 ms General-purpose services, 2–32+ GB heaps
ZGC -XX:+UseZGC (+ -XX:+ZGenerational on 21; generational by default from 23) Does almost everything while the app runs, including compaction. It uses coloured pointers (extra metadata bits inside each reference) and load barriers (checks on every reference read), so objects can be moved while the app runs. If the app reads an outdated reference, it is fixed on the spot < 1 ms, no matter how big the heap is Latency-sensitive APIs, very large heaps
Shenandoah -XX:+UseShenandoahGC Compacts while the app runs, using forwarding pointers (built by Red Hat) < 10 ms Similar to ZGC
CMS removed in Java 14 Concurrent mark-sweep with no compaction → fragmentation Legacy only

How does it work?

A G1 cycle, step by step:

  1. Young pauses happen all the time, cleaning the young regions.
  2. When heap usage crosses a threshold, concurrent marking starts and runs alongside the app. This threshold is called IHOP (Initiating Heap Occupancy Percent), about 45%.
  3. Short remark and cleanup pauses finish the marking.
  4. A series of mixed pauses follows. Each one evacuates the young regions plus the old regions with the most garbage.
  5. The cycle repeats.

A full GC compacts the entire heap in one long pause. G1 does this only as a last resort, when evacuation can't keep up with the app. This is the multi-second pause you see in incidents.

ZGC's trade-off: It gives up some throughput and CPU — for the barrier checks and its concurrent GC threads. In return, pauses stay below a millisecond even with heaps of hundreds of GB.

Example

# Typical service on Java 21 in a 4 GiB pod
-XX:+UseG1GC -XX:MaxRAMPercentage=70 -XX:MaxGCPauseMillis=200
# Latency-critical API (p99 < 50 ms SLO) with large caches
-XX:+UseZGC -XX:+ZGenerational -Xmx8g

When would I use it?

  • Keep G1 unless measurements show GC pauses breaking your SLO (service level objective — your latency promise). Then try ZGC.
  • Use Parallel for offline batch jobs that need maximum throughput.
  • Tune heap size and allocation rate first. Only then touch collector flags.

What can go wrong?

  • MaxGCPauseMillis set too low. G1 then does less work per pause. It falls behind the app and ends up triggering full GCs — the opposite of what you wanted.
  • Humongous allocations. In G1, an object of at least half a region (huge arrays or Strings) gets its own humongous region. Many of these fragment the heap.
  • ZGC without enough headroom. ZGC needs extra free heap. If the app allocates faster than the concurrent collector can free memory, application threads are forced to wait. This is called an allocation stall.

Interview questions

Q1. G1 vs ZGC? G1 is region-based. It evacuates mostly during stop-the-world pauses and aims for a pause target of tens of milliseconds, giving a good balance with throughput. ZGC compacts concurrently using load barriers. Its pauses stay under a millisecond regardless of heap size, but it costs some throughput and CPU.

Q2. Why is G1 called "Garbage First"? After concurrent marking, it evacuates first the old regions that contain the most garbage. This gets back the most space for each pause.

Q3. Which collector for a batch job vs a low-latency API? Parallel for batch throughput. G1 by default for services. ZGC when pause times threaten the latency SLO.

5.6 Strong, soft, weak and phantom references

Why?

In simple words: Sometimes you want to point to an object but still let the GC throw it away. Special reference types let you say "keep this only while someone else needs it" or "tell me when it is gone".

Normally, if you hold a reference to an object, the object stays alive. But sometimes you want to refer to an object without keeping it alive. For example:

  • a cache that should give memory back when memory is short;
  • extra data attached to objects, which should disappear together with them;
  • cleanup work that should run when an object is collected.

What is happening internally?

Type Cleared by GC when Typical use
Strong (normal) Never, while it is reachable Everything
SoftReference Memory is running low (before an OOM) Memory-sensitive caches (rare now, because behaviour is unpredictable)
WeakReference At the next GC, if only weak references point to it WeakHashMap keys, listener registries, canonicalising maps (maps that keep one shared copy per value)
PhantomReference After the object has been finalised; get() always returns null Cleanup after the object is gone, via ReferenceQueue / Cleaner (for off-heap resources)

When the GC clears a reference, it can put it on a ReferenceQueue. Your code reads that queue to learn that the object is gone.

How does it work?

WeakHashMap holds its keys through weak references. Once nothing else points to a key, the GC clears it. The entry then disappears during the next operation on the map.

There is a classic gotcha. The values are held strongly. So if a value references its own key, the key stays reachable through the value. The entry is never removed.

Example

Map<Session, Metadata> meta = new WeakHashMap<>();   // metadata disappears when the Session is unreachable
Cleaner cleaner = Cleaner.create();
class OffHeapBuffer implements AutoCloseable {
    private final Cleaner.Cleanable cleanable;
    OffHeapBuffer(long address) { cleanable = cleaner.register(this, () -> freeNative(address)); }   // safety net
    public void close() { cleanable.clean(); }                                                     // preferred: explicit
}

The Cleaner here is only a safety net. The preferred way is to call close() yourself (for example with try-with-resources).

When would I use it?

Rarely in business code. You mostly need to recognise these in interviews and in library code. For caches, use Caffeine with size and time limits instead of soft references.

What can go wrong?

  • Soft-reference caches cause GC thrashing (the GC runs again and again) and unpredictable latency.
  • WeakHashMap entries never cleared, because their values reference their keys.
  • Relying on GC timing for cleanup. You don't know when the GC will run. Always provide an explicit close().

Interview questions

Q1. Weak vs soft references? A weak reference is cleared at the next GC once the object is reachable only through weak references. A soft reference is cleared only when memory is under pressure.

Q2. How does WeakHashMap work? It holds keys through weak references. When a key is no longer reachable from anywhere else, the GC clears it and the map removes that entry.

5.7 Memory leaks in a garbage-collected language

Why?

In simple words: The GC only frees objects nobody points to. If your code keeps pointing to objects it will never use again — like a register where entries are added but never struck off — memory keeps filling up. That is a leak, even in Java.

"Java has a GC, so it can't leak" is a classic wrong answer.

A Java leak is an object that is still reachable but no longer needed. The GC cannot know you won't use it again. It only knows something still points to it.

How a leak shows up, in order:

  1. The heap grows slowly.
  2. GCs become longer and more frequent.
  3. Latency spikes appear.
  4. Finally, OutOfMemoryError.

What is happening internally?

Some long-lived root holds a reference graph that keeps growing. The root can be a static field, a singleton bean, a long-lived thread or a cache. On every GC, the collector marks all of it as live. It copies or keeps it, and can never free it.

The usual suspects:

  1. Unbounded caches and static collections: for example, a static Map<String, Result> CACHE that only ever grows.
  2. Listeners and callbacks that are registered but never removed.
  3. ThreadLocals in pooled threads that are never removed. Pool threads live forever, so their ThreadLocal values do too (4.15).
  4. Inner classes and lambdas that capture a large outer object and are stored long-term (1.17).
  5. Mutable map keys whose hash changed after insertion. The map can't find the entry any more, so it can never be removed (1.12).
  6. Unclosed resources: streams, result sets, HTTP responses. These also use up connection pools and file descriptors.
  7. Unbounded queues in executors that keep growing under overload (4.3).
  8. ClassLoader leaks on redeploy, which fill Metaspace (5.1).
  9. Session or per-tenant maps with no expiry.

How does it work?

The signature in monitoring is the "sawtooth" heap graph. The heap rises as objects are created, then drops at each GC. Look at the floor — the heap level right after each GC.

  • In a healthy app, the floor stays flat.
  • In a leak, the floor rises steadily over hours or days.

Along with this, old-gen GCs become frequent, and the percentage of time spent in GC goes up.

heap used
 │      /\    /\     /\      /\
 │  /\ /  \  /  \   /  \    /  \     ← floor after each GC keeps rising = leak
 │ /  V    \/    \_/    \__/
 └──────────────────────────────── time

Example

// Leak: request-scoped results cached forever, keyed by unique request IDs
@Component
class RuleResultCache {
    private static final Map<String, RuleResult> CACHE = new ConcurrentHashMap<>();
    RuleResult get(String requestId, Supplier<RuleResult> calc) { return CACHE.computeIfAbsent(requestId, k -> calc.get()); }
}

// Fix: bounded, time-limited cache (Caffeine), keyed by something with bounded cardinality
Cache<String, RuleResult> cache = Caffeine.newBuilder()
        .maximumSize(50_000)
        .expireAfterWrite(Duration.ofMinutes(10))
        .recordStats()
        .build();

Why the first version leaks: every request has a new, unique ID. So every request adds a new entry, and nothing ever removes one. The fix limits both the size (50,000 entries) and the age (10 minutes) of entries.

When would I use it?

Every time you add a static or long-lived collection, ask two questions:

  1. What limits its size?
  2. What removes entries?

In incident reviews, use the investigation flow in 5.9.

What can go wrong?

  • Restarting pods "fixes" the symptom. It hides the leak until the next traffic peak.
  • Increasing -Xmx only delays the OOM. The leak is still there.

Interview questions

Q1. Can Java have memory leaks? Yes. A leak is an object that stays reachable but is no longer needed. Common causes: unbounded caches, static collections, listeners and ThreadLocals that are never removed, lambdas or inner classes holding outer references, and unclosed resources.

Q2. How do you recognise a leak from metrics? Heap usage right after GC rises steadily over time. GC frequency and duration grow. Eventually you get an OOM. A restart resets it, but only for a while.

5.8 Diagnosing high CPU, hangs and slow requests

Why?

In simple words: When production is slow or stuck, you don't guess. You take snapshots of what every thread is doing, find the busy or stuck ones, and follow the evidence.

Production problems rarely tell you what is wrong. You see "CPU at 100%", "requests hanging" or "p99 doubled". To handle these, you need a repeatable approach driven by evidence.

Interviewers ask "walk me through debugging this" to check exactly that: do you have a method?

What is happening internally?

Two main tools:

  • A thread dump is a snapshot of every thread: its state (running, blocked, waiting) and its stack trace (which methods it is inside right now).
  • A CPU profile samples which methods are running, many times over a period, and adds up where the time goes.

Combine them with OS tools. Together they tell you which thread is busy and what it is doing.

How does it work?

High CPU:

  1. Run top -H -p <pid>. This shows CPU use per thread. Note the thread IDs (TIDs) using the most CPU.
  2. Convert the TID to hex: printf '%x\n' 12345 → 3039. Thread dumps show IDs in hex.
  3. Run jcmd <pid> Thread.print > dump.txt. Search for nid=0x3039. That thread's stack shows the hot code.
  4. Take 3 dumps 5–10 s apart. If you see the same stack every time, you have confirmed it.
  5. Check the common culprits: - GC threads — if these are the busy ones, the real problem is memory; go to memory analysis (5.9) instead; - an infinite loop; - regex catastrophic backtracking (a badly written regex that tries millions of combinations); - huge JSON serialisation or deserialisation; - a HashMap infinite loop after unsafe use from many threads (old Java versions); - busy spin loops (a loop that keeps checking a condition without sleeping).
  6. For a full picture, use async-profiler flame graphs, or JFR (jcmd <pid> JFR.start duration=60s filename=cpu.jfr) and open the recording in JDK Mission Control.

Hangs and slow requests:

  1. Take thread dumps again. Look for these patterns: - Many threads BLOCKED and "waiting to lock" the same monitor → lock contention (threads queueing for one lock). - Threads WAITING in HikariPool.getConnection → the DB connection pool is exhausted. Causes are slow queries or leaked connections. - Threads RUNNABLE in SocketInputStream.read for minutes → a downstream call with no read timeout. The thread waits forever for a reply. - A section saying "Found one Java-level deadlock" → a deadlock (4.13).
  2. Match what you see with APM traces and metrics: pool usage, GC pauses, downstream latency.

Think of a railway reservation hall where the queue has stopped moving. You don't guess — you walk up and see what each counter clerk is doing. A thread dump is that walk.

Example

"http-nio-8080-exec-41" #87 daemon prio=5 tid=0x... nid=0x3039 waiting on condition
   java.lang.Thread.State: TIMED_WAITING (parking)
      at jdk.internal.misc.Unsafe.park(Native Method)
      at com.zaxxer.hikari.util.ConcurrentBag.borrow(ConcurrentBag.java:...)
      at com.zaxxer.hikari.pool.HikariPool.getConnection(HikariPool.java:...)
      at ...LedgerRepository.balance(...)
 → 150 of 200 Tomcat threads look like this: the DB pool (size 20) is exhausted.
   Next step: which queries hold connections? (slow query log / pg_stat_activity) — often a missing index or a
   transaction that calls an external API while holding the connection.

When would I use it?

  • On-call incidents.
  • Performance tuning.
  • Telling an interview story with a concrete diagnosis. Your ~30 s → ~10 s API improvement can be told this way: measure, find the bottleneck, fix it, verify the result.

What can go wrong?

  • Trusting a single dump. One snapshot can mislead. Take several.
  • Heavy instrumenting profilers in production. They add code to every method and change how the app behaves. Prefer sampling profilers such as JFR or async-profiler.
  • Fixing symptoms instead of causes. Bigger pools or more pods without finding the real cause just move the problem.

Interview questions

Q1. CPU is at 100% on a Java service. What do you do? Find the hot threads with top -H. Convert their TIDs to hex and match them to the nid in thread dumps taken a few seconds apart. Read their stacks. Check whether the busy threads are GC threads, which would point to a memory problem. Profile with JFR or async-profiler. Then fix the hot code path.

Q2. Requests are hanging. How do you investigate? Take thread dumps to see what the threads are waiting on — locks, connection pools, sockets without timeouts, or deadlocks. Then correlate that with traces and pool metrics.

5.9 Diagnosing memory problems: GC logs, heap dumps, JFR

Why?

In simple words: Memory problems are the most common JVM incidents. You must switch on evidence collection in advance, because when the process dies, the evidence dies with it — and then you need a clear method to read that evidence.

Leaks, GC thrashing and OOMs are the most common JVM incidents. To handle them you need two things:

  1. The right artefacts (logs, dumps, recordings), captured before the process dies.
  2. A method for reading them.

What is happening internally?

The four sources of evidence:

  • GC logs record every collection: its type, its cause, heap size before and after, and the pause time.
  • Class histogram: for each class, how many live objects exist and how many bytes they use. It is cheap and needs no full dump.
  • Heap dump (.hprof file): a copy of every object and every reference in the heap. Analysis tools compute two key things from it:
  • The dominator tree: for each object, how much memory would be freed if that object disappeared. This is its retained size.
  • The path to GC roots: the chain of references that keeps an object alive.
  • JFR (Java Flight Recorder): a recording that runs all the time with low overhead (~1%). It captures allocations, GC, locks, I/O and CPU samples.

How does it work?

# Always-on in production
-Xlog:gc*:file=/logs/gc.log:time,uptime,level,tags:filecount=5,filesize=20m
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps

# During an incident
jcmd <pid> GC.class_histogram | head -20          # take twice, 10 minutes apart: which classes grow?
jcmd <pid> GC.heap_dump /dumps/heap.hprof         # pauses the app; heap-sized file — mind disk and PII
jcmd <pid> JFR.start duration=120s filename=/dumps/rec.jfr settings=profile

Note: a heap dump pauses the app and writes a file as big as the heap. Check disk space first, and remember it contains user data (PII — personally identifiable information).

Investigation flow:

  1. Which OOM is it? Heap, Metaspace, direct buffers or native threads. Each type has a different cause (5.2).
  2. Read the GC logs. Is heap-after-GC rising over time? That is a leak. Or is it just high under load? That means the heap is too small, or there was a traffic spike.
  3. Take two class histograms some time apart. Which classes keep growing?
  4. Open the heap dump in Eclipse MAT. Run the "Leak Suspects" report. Then open the dominator tree. Follow the path to GC roots of the biggest retainers. Find the code that owns that root.
  5. Fix it, then verify using the same metrics.

Example

MAT Leak Suspects:
  One instance of "java.util.concurrent.ConcurrentHashMap" loaded by "app" occupies 1,284,331,112 (82.4%) bytes.
  Path to GC root: RuleResultCache.CACHE (static) → ConcurrentHashMap → Node[] → RuleResult …
  → The static request-keyed cache from 5.7. Fix: bounded Caffeine cache. Heap after GC drops from 85% to 40%.

Say this: "p99 latency of the reward API jumped from 300 ms to 4 s every few minutes. GC logs showed full GCs of about 3 s, and old gen never dropped below 85%. I took two class histograms ten minutes apart, and RuleResult objects were growing. The heap dump's dominator tree pointed to a static ConcurrentHashMap keyed by request ID, with no eviction. We replaced it with a Caffeine cache limited by size and TTL. Old gen settled around 40%, p99 went back under 300 ms, and we added an alert for old-gen-after-GC above 70%." Build your own version of this from a real incident you handled.

When would I use it?

  • For any OOM or memory alert.
  • Proactively before launches: run a load test and check the heap.

What can go wrong?

  • Heap dumps contain customer data (PII). Handle and store them securely.
  • Dumping a big heap hurts. A 16 GB heap dump pauses the service for a long time and needs a lot of disk. So first remove that instance from the load balancer, then take the dump.
  • No HeapDumpOnOutOfMemoryError flag. Then the evidence dies with the process.

Interview questions

Q1. How do you investigate an OutOfMemoryError? First identify the OOM type. Check the GC logs for the heap-after-GC trend. Compare class histograms taken some time apart. Analyse the heap dump's dominator tree and the paths to GC roots. Fix the reference that is holding the memory. Then verify with metrics.

Q2. What is retained size? The memory that would be freed if an object were collected. It includes the object itself and everything that is reachable only through it.

Q3. What is JFR? Java Flight Recorder. It is a built-in event recorder with low overhead. It captures CPU samples, allocations, GC, locks and I/O, and you analyse the recording in JDK Mission Control. It is safe to run in production.

5.10 JIT compilation in depth

Why?

In simple words: Java first runs your code slowly, by interpreting it, while watching what it actually does. Then it compiles only the busy parts into fast machine code, tuned to how your app really behaves.

There are two simple options, and both have problems:

  • Interpreting bytecode (running it instruction by instruction) is slow — 10–50× slower than native machine code.
  • Compiling everything ahead of time loses runtime information. For example: which branches are actually taken, and which subclass actually shows up at a call.

The JIT (just-in-time compiler) takes a middle path:

  • It compiles only hot code (code that runs a lot).
  • It uses live profiling data collected while the app runs.
  • So it can make optimistic optimisations that a normal ahead-of-time compiler cannot safely make.

What is happening internally?

Tiered compilation. Code moves up through levels:

  • Level 0: the interpreter.
  • Level 3: the C1 compiler, with profiling. It compiles quickly and collects statistics.
  • Level 4: the C2 compiler, with full optimisation. It compiles slowly but produces very fast code.
  • (Levels 1–2 are C1 variants.)

Key C2 optimisations:

  • Inlining: copying the body of a small, hot method directly into its caller. This removes the cost of the call. More importantly, it enables every other optimisation. It is the most important one.
  • Devirtualisation: An interface or virtual call normally needs a lookup to find the right implementation. If profiling sees only one implementation at a call site (monomorphic), the JIT calls it directly and can inline it. If it sees two types (bimorphic), it adds a quick type check. With more types (megamorphic), it falls back to a normal vtable call (a table lookup).
  • Escape analysis: If an object never leaves the method, it is scalar-replaced — its fields become local variables and no allocation happens. Any locks on it are removed too (lock elision).
  • Loop optimisations: unrolling (doing several iterations per loop pass), range-check elimination (removing repeated array-bounds checks), and vectorisation (SIMD — one CPU instruction working on several values at once).
  • Dead-code elimination (removing code that can never run) and constant folding (calculating constant expressions at compile time).

Deoptimisation. The JIT's optimisations rely on assumptions. Sometimes an assumption becomes false — for example, a new subclass gets loaded, or a branch that was never taken is suddenly hit. Then:

  1. The JVM throws away that compiled code at a safepoint.
  2. Execution goes back to the interpreter.
  3. Later, the JIT may compile it again with the new information.

On-stack replacement (OSR). Suppose a method is still interpreted but is stuck in a very long loop. The JVM can switch that running loop to compiled code in the middle, without waiting for the method to be called again.

How does it work?

call count / loop iterations cross thresholds → C1 compiles with profiling counters
→ profile shows hot path, receiver types, branch frequencies → C2 compiles optimised code for those
→ assumptions guarded by cheap checks; guard fails → deoptimise → interpreter → recompile

In steps:

  1. Call counts or loop iterations cross a threshold. C1 compiles the method, with profiling counters.
  2. The profile shows the hot path, the receiver types and how often each branch is taken. C2 compiles optimised code for exactly those cases.
  3. The assumptions are protected by cheap checks called guards.
  4. If a guard fails → deoptimise → back to the interpreter → recompile later.

Example

interface Fee { long of(long amt); }
final class Flat implements Fee { public long of(long a) { return 10; } }
long total(List<Long> amounts, Fee fee) {
    long s = 0;
    for (long a : amounts) s += fee.of(a);   // only Flat seen → devirtualised + inlined → s += 10
    return s;
}
// If later a PercentFee is passed here, the guard fails → deoptimisation → recompiled as a bimorphic call.

When would I use it?

  • Explaining warm-up, and how to design benchmarks correctly.
  • Explaining why hot paths should be small, monomorphic methods.
  • Explaining that final and sealed classes help readability — the JIT does not need them for speed, because profiling already tells it the real types.
  • Discussing startup options: CDS archives (pre-loaded class data), CRaC (restoring a saved, warmed-up JVM), and GraalVM native image for fast-starting CLIs and serverless functions.

What can go wrong?

  • Benchmarks without warm-up. You end up measuring the interpreter, not the real performance.
  • Megamorphic call sites in hot loops. For example, many different lambda implementations called through one interface. The JIT can't inline them.
  • A full code cache. The JIT stops compiling, and new hot code stays slow.
  • Deoptimisation storms. Repeated deoptimise-and-recompile cycles cause latency jitter.

Interview questions

Q1. What does the JIT do? It profiles running code and compiles hot methods into optimised native code, first with C1 and then C2. It uses inlining, devirtualisation, escape analysis and loop optimisations. If its assumptions break, it deoptimises.

Q2. Why do Java services need warm-up? Code starts in the interpreter. The JIT needs profiling data and time to compile the hot paths. Caches and connection pools also need time to fill up.

Q3. What is escape analysis? A JIT analysis that proves an object does not escape its method or thread. This allows the JIT to skip the allocation entirely (scalar replacement) and to remove locks on it (lock elision).

5.11 The JVM in containers and the flags that matter

Why?

In simple words: Inside a container, the JVM must size itself from the container's limits, not the whole machine's. A handful of flags control this, and getting them wrong causes OOM kills and slow, throttled services.

Your services run in Kubernetes on Azure. Imagine a JVM that ignores container limits. It looks at the host machine's RAM and CPUs instead. It then sizes its heap and thread pools for that much bigger machine. The results are OOM kills and CPU throttling (the container being slowed down for using more CPU than allowed).

Knowing a handful of flags lets you configure services sensibly and explain incidents.

What is happening internally?

Since Java 10 (also backported to 8u191), the JVM reads cgroup limits. Cgroups are the Linux feature that enforces a container's CPU and memory limits. This means:

  • availableProcessors() returns the container's CPU limit, rounded up.
  • The default maximum heap is a percentage of the container's memory. The default is 25%, which is too low for most services.
  • The CPU count also decides the number of GC threads, the size of the common ForkJoinPool, and the size of many library thread pools.

How does it work?

-XX:MaxRAMPercentage=70.0            # heap = 70% of the container limit (leave room for non-heap, 5.2)
-XX:InitialRAMPercentage=70.0        # equal initial/max avoids resize pauses (or -Xms = -Xmx)
-XX:+UseG1GC  (default)  | -XX:+UseZGC -XX:+ZGenerational (Java 21)
-XX:MaxGCPauseMillis=200
-Xss512k                             # smaller thread stacks if you run many platform threads
-XX:MaxMetaspaceSize=256m            # cap runaway class generation
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps
-XX:+ExitOnOutOfMemoryError          # die fast and let Kubernetes restart instead of limping
-Xlog:gc*:file=/logs/gc.log:time,uptime:filecount=5,filesize=20m
-XX:ActiveProcessorCount=2           # override if the CPU limit is fractional and the JVM misjudges it

Example

Take a Kubernetes pod with limits.memory: 2Gi and limits.cpu: 2:

  • MaxRAMPercentage=70 → about 1.4 GiB of heap.
  • G1 runs with 2 parallel GC threads.
  • Tomcat has max 200 threads, which reserve about 200 MB for stacks.
  • A readiness probe points at /actuator/health/readiness. So traffic arrives only after the app has warmed up.

When would I use it?

  • Writing Dockerfiles and Helm values.
  • Sizing pods.
  • Investigating OOMKilled restarts (exit code 137) and CPU throttling.

What can go wrong?

  • -Xmx equal to the container limit. Non-heap memory pushes the process over the limit → OOMKilled.
  • A very low CPU limit (e.g., 500m, meaning half a CPU). The JVM thinks it has only 1 CPU. So it picks Serial GC and tiny thread pools.
  • Requests and limits set far apart. This causes noisy, unpredictable throttling.
  • No volume for heap dumps. The dump has nowhere to go, so the evidence is lost.

Interview questions

Q1. How does the JVM behave in containers? It is container-aware. It reads the cgroup CPU and memory limits and uses them to size the heap, the GC threads and thread pools. You should set MaxRAMPercentage to about 70–75%, to leave room for non-heap memory.

Q2. A pod keeps restarting with exit code 137 but no Java OOM in the logs. Why? The kernel OOM-killed it. The total process memory — heap plus metaspace, threads and direct buffers — went over the container limit. Fix it by lowering the heap percentage or raising the limit, and check native memory usage with NMT (Native Memory Tracking).
