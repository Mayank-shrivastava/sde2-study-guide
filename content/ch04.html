This topic clearly separates SDE1 answers from SDE2 answers. You need three things:

  • The words: atomicity, visibility, happens-before.
  • The tools: executors, locks, atomics, concurrent collections, CompletableFuture and virtual threads.
  • The hands-on skill: coding the classic problems on a whiteboard.

4.1 Threads and the thread lifecycle

Why?

In simple words: A thread is one worker inside your program. With many workers, one can wait for the database while another uses the CPU, so nothing sits idle.

A server handles thousands of requests. Most of the time, each request is just waiting — for the database, the network or the disk.

If one thread did all the work one after another, the CPU would sit idle during every wait. Threads let independent pieces of work run at the same time. This is called concurrency.

With threads you get three benefits:

  • Waits overlap, so total time drops.
  • All CPU cores get used.
  • The system stays responsive.

Think of a bank with one counter versus five counters. With five counters, while one clerk waits for a printout, the others keep serving customers.

What is happening internally?

  • A process is a running program. It owns memory: the heap (where objects live) and the code.
  • Threads live inside a process. All threads share the same heap. But each thread has its own stack (its method calls and local variables) and its own program counter (which line it is on).
  • A Java platform thread is a thin wrapper around an OS thread. The OS scheduler decides which thread runs on which core. It also pauses threads and switches between them using small time slices. This is called preemption.
  • Creating a platform thread is not free. It reserves stack memory (default ~512 KB–1 MB). It also costs tens of microseconds. So you can have thousands of them, not millions.
  • Switching from one thread to another is called a context switch. The CPU saves and restores registers and stack pointers. It also spoils the CPU caches (the CPU's small, fast memory). Each switch typically costs a few microseconds.
NEW ──start()──► RUNNABLE ◄──────────────► BLOCKED        (waiting to enter a synchronized block)
                    │    ◄──────────────► WAITING        (wait(), join(), park(), take() with no timeout)
                    │    ◄──────────────► TIMED_WAITING  (sleep(ms), wait(ms), join(ms), poll(timeout))
                    ▼
               TERMINATED

RUNNABLE means "running or ready to run". Java does not separate these two.

One surprise: a thread that is blocked reading from a socket also shows as RUNNABLE in thread dumps. So RUNNABLE does not always mean "using CPU".

How does it work?

  1. new Thread(task) creates the object. The state is NEW. No OS thread exists yet.
  2. start() makes the JVM create the OS thread. That thread calls run(). The state becomes RUNNABLE.
  3. The thread may block on a lock (BLOCKED), wait for a condition (WAITING), or sleep (TIMED_WAITING). After that it returns to RUNNABLE.
  4. When run() returns or throws, the state becomes TERMINATED. A thread can't be restarted.

Interruption is the polite way to ask a thread to stop. The thread must cooperate. Here is how it works:

  1. Another thread calls t.interrupt(). This only sets a flag on t.
  2. If t is inside a blocking method (sleep, wait, join, BlockingQueue.take), that method notices the flag. It throws InterruptedException and clears the flag.
  3. If t is running normal non-blocking code, nothing happens by itself. The code must check Thread.currentThread().isInterrupted() regularly.

Example

Runnable task = () -> {
    while (!Thread.currentThread().isInterrupted()) {
        try {
            processNextBatch();
            Thread.sleep(1000);                         // TIMED_WAITING
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();         // restore the flag so the loop condition sees it
        }
    }
    System.out.println("stopped cleanly");
};
Thread worker = new Thread(task, "batch-worker");      // always name threads: readable thread dumps
worker.start();                                        // NOT run(): run() would execute on the current thread
Thread.sleep(3500);
worker.interrupt();                                    // ask it to stop
worker.join();                                         // wait until TERMINATED

Thread daemon = new Thread(this::heartbeat);
daemon.setDaemon(true);                                // daemon threads don't keep the JVM alive

When would I use it?

In application code, you should almost never create raw threads. Instead, submit tasks to an executor (4.3) or use virtual threads (4.12).

But you must understand the lifecycle for two jobs:

  • Reading thread dumps. A thread dump is a snapshot of every thread and its state. Many threads BLOCKED on one lock means contention — too many threads fighting for one lock. Many threads WAITING in getConnection means the connection pool is exhausted.
  • Writing correct shutdown logic.

What can go wrong?

  • Calling run() instead of start(). No new thread is created. The code runs on the current thread, one step after another.
  • Swallowing InterruptedException with an empty catch block. Now the thread can no longer be stopped, and shutdowns hang.
  • Unbounded thread creation — for example, one new thread per request without a pool. Memory runs out and you get OutOfMemoryError: unable to create native thread.
  • Uncaught exceptions kill the thread silently. Nobody sees the error unless you set an UncaughtExceptionHandler, or use executors and check the Futures.
  • Thread.stop() is deprecated and dangerous. It releases locks in the middle of an update. This leaves data in a corrupted, half-changed state.

Interview questions

Q1. Process vs thread? A process has its own memory space. Threads live inside a process: they share its heap, but each has its own stack and program counter. So threads are cheaper to create and to switch between. The cost is that shared data needs synchronisation.

Q2. start() vs run()? start() creates a new thread, and that new thread executes run(). If you call run() directly, it simply executes on the current thread, like a normal method call.

Q3. Explain the thread states. NEW (created, not started). RUNNABLE (running or ready to run). BLOCKED (waiting to get a monitor lock). WAITING / TIMED_WAITING (waiting for a signal, or for a signal or a timeout). TERMINATED (finished).

Q4. How do you stop a thread correctly? Cooperatively. You interrupt it (or set a volatile flag), and the task checks the flag and exits by itself. When the task catches InterruptedException, it must either restore the flag or exit.

4.2 Race conditions: atomicity, visibility and ordering

Why?

In simple words: When two threads change the same data, three different things can break: an update can get lost, a change can stay hidden from the other thread, or steps can happen in a surprising order.

As soon as two threads touch the same mutable (changeable) data, three separate problems can appear. They are independent of each other.

SDE2 candidates name these three problems precisely. That is how they explain a concurrency bug and choose the right fix.

What is happening internally?

  1. Atomicity — an operation should happen fully or not at all. But count++ is actually three machine steps: read, add, write. Two threads can mix (interleave) these steps:
count = 5
T1: read 5          T2: read 5
T1: add → 6         T2: add → 6
T1: write 6         T2: write 6       → final 6, one increment LOST

Both threads read 5, both write 6. One increment is lost.

  1. Visibility — a write by one thread should be seen by others. But each CPU core has its own caches (L1/L2). Also, the JIT compiler may keep a variable in a CPU register. So a write by thread A may stay inside A's core. Thread B may never see it. Without synchronisation, B may read an old (stale) value forever.

  2. Ordering — steps should happen in the order you wrote them. But compilers and CPUs reorder instructions to run faster. They only do this when the result looks the same to the current thread. Another thread, however, can see the changed order. For example, it may see the "ready" flag set before the data that the flag protects was written.

Two more terms:

  • A critical section is any code that reads or writes shared mutable state.
  • A data race is when two threads access the same variable without synchronisation, and at least one of them writes.

How does it work?

You fix a race with one of these strategies. They are listed best first:

  1. Don't share. Keep the data inside one thread only — local variables, per-request objects. This is called thread confinement.
  2. Don't mutate. Share only immutable objects, which can never change (1.14).
  3. Synchronise. Pick the tool that matches the problem: - Locks (synchronized, ReentrantLock) give atomicity + visibility. - volatile gives visibility only. - Atomics give atomic updates to one single variable. - Concurrent collections give safe shared data structures.

Example

class UnsafeCounter { int count; void inc() { count++; } }

UnsafeCounter c = new UnsafeCounter();
Thread[] ts = new Thread[4];
for (int i = 0; i < 4; i++) { ts[i] = new Thread(() -> { for (int j = 0; j < 100_000; j++) c.inc(); }); ts[i].start(); }
for (Thread t : ts) t.join();
System.out.println(c.count);       // expected 400000, typically prints something like 231874 — lost updates

// Check-then-act race (just as common in business code)
if (!cache.containsKey(key)) {     // T1 and T2 both see "absent"
    cache.put(key, load(key));     // both load and both put → duplicate work or overwritten state
}

When would I use it?

Use these three ideas as a checklist for diagnosis. When a bug "only happens under load", ask which of the three is broken:

  • Lost updates → atomicity is broken.
  • A flag that never seems to change → visibility is broken.
  • Objects that look half-initialised → ordering is broken.

What can go wrong?

  • Races don't happen every time. Tests pass, but production fails under load. So test with many threads and many repetitions. For low-level code, use tools like jcstress.
  • Only writes synchronised. If writes are synchronised but reads are not, visibility is still broken. The reader may see stale values.
  • Compound operations on thread-safe classes are still races. Each single call on a ConcurrentHashMap is safe. But if (!map.containsKey(k)) map.put(k, v) is two calls, and another thread can act between them. Use putIfAbsent/computeIfAbsent instead — they do both steps as one.

Interview questions

Q1. What is a race condition? It is a correctness bug where the result depends on the timing, or interleaving, of threads that use shared mutable state. A classic example is lost updates when many threads run count++ at the same time.

Q2. Atomicity vs visibility? Atomicity means other threads see an operation either fully done or not done at all — never half-done. Visibility means a write by one thread can actually be seen by other threads. Locks give both. volatile gives visibility only.

Q3. Why is count++ not thread-safe? It is a read-modify-write made of three steps. Two threads can interleave those steps, so updates get lost.

4.3 Executors and ThreadPoolExecutor

Why?

In simple words: A thread pool is a fixed team of workers with a waiting line. Tasks join the line, and free workers pick them up — so you never hire thousands of new workers when traffic jumps.

Creating one thread per task has two problems:

  • It is expensive. Each one needs an OS thread and stack memory.
  • It has no limit. A traffic spike creates thousands of threads and crashes the JVM.

A thread pool solves both. It reuses a fixed set of threads. Extra work waits in a queue.

It also gives you one single place to control three things: how many tasks run at once (concurrency), how to slow down callers when overloaded (back-pressure), and shutdown.

Think of a railway reservation office. It has a fixed number of counters and one queue. When the queue gets too long, the guard stops letting new people in.

What is happening internally?

ThreadPoolExecutor has three parts:

  • a set of worker threads,
  • a BlockingQueue of waiting tasks,
  • policies that decide what to do in each situation.

When you submit a task, it follows this decision path:

submit(task)
   │
   ├─ running threads < corePoolSize?  ──yes──► start a NEW worker with this task
   │ no
   ├─ queue.offer(task) succeeds?        ──yes──► task waits in the queue
   │ no (queue full)
   ├─ running threads < maximumPoolSize? ──yes──► start a NEW (non-core) worker
   │ no
   └─ RejectedExecutionHandler           ──► Abort / CallerRuns / Discard / DiscardOldest
Workers loop: take() a task from the queue → run it → repeat. Non-core workers idle longer than keepAliveTime exit.

Note the order: the queue is used before the pool grows to max. This is the most misunderstood detail.

The result is surprising. If the queue is unbounded (has no size limit), it never becomes full. So the pool never grows, and maximumPoolSize is never used.

How does it work?

Here is a properly configured pool:

ThreadPoolExecutor exec = new ThreadPoolExecutor(
    8,                                         // corePoolSize
    32,                                        // maximumPoolSize
    60, TimeUnit.SECONDS,                      // keepAliveTime for non-core threads
    new ArrayBlockingQueue<>(1_000),           // BOUNDED work queue
    Thread.ofPlatform().name("reward-", 0).factory(),   // named threads (Java 21 builder)
    new ThreadPoolExecutor.CallerRunsPolicy()); // when saturated, the submitting thread runs the task → natural back-pressure

When the pool and the queue are both full, the rejection policy decides what happens:

Rejection policy Behaviour Use
AbortPolicy (default) Throws RejectedExecutionException Fail fast; the caller handles it
CallerRunsPolicy The submitting thread runs the task itself Slows down producers: back-pressure
DiscardPolicy Drops the task silently Only for truly optional work (metrics samples)
DiscardOldestPolicy Drops the oldest queued task, then retries "Latest wins" workloads

The Executors factory methods and their traps:

Factory Configuration Trap
newFixedThreadPool(n) core = max = n, unbounded LinkedBlockingQueue Under overload the queue grows without limit → OutOfMemoryError
newCachedThreadPool() core 0, max Integer.MAX_VALUE, SynchronousQueue No limit on threads → thread explosion
newSingleThreadExecutor() 1 thread, unbounded queue Same queue risk
newScheduledThreadPool(n) Delayed or repeating tasks
newVirtualThreadPerTaskExecutor() One virtual thread per task (Java 21) Not for CPU-bound work

Sizing — how many threads?

  • CPU-bound work (the task mostly calculates): threads ≈ number of cores. Get it with Runtime.getRuntime().availableProcessors().
  • I/O-bound work (the task mostly waits): threads ≈ cores × (1 + wait time / compute time). Example: 8 cores, and a task that waits 90 ms on a DB and computes for 10 ms. That gives 8 × (1 + 9) = 80 threads.
  • Cross-check with Little's Law: concurrency = throughput × latency. In words: work in progress = arrival rate × time each item takes. Serving 400 req/s at 200 ms each needs ~80 workers busy at the same time.
  • The downstream system limits you too. If 80 threads share a DB pool of 20 connections, 60 of them just wait in line for the pool.

Shutdown:

exec.shutdown();                                     // stop accepting; finish queued tasks
if (!exec.awaitTermination(30, TimeUnit.SECONDS)) {
    exec.shutdownNow();                              // interrupt running tasks, return queued ones
}

Example

// Fan out reward calculation for a batch of outlets with bounded concurrency and back-pressure
List<Future<Long>> futures = new ArrayList<>();
for (String outlet : outlets) futures.add(exec.submit(() -> calculatePoints(outlet)));
long total = 0;
for (Future<Long> f : futures) total += f.get(5, TimeUnit.SECONDS);   // timeout per result

// Trace with core=2, max=3, queue=2 and 6 quick submissions while all tasks are still running:
// t1 → new core worker #1; t2 → new core worker #2; t3 → queue [t3]; t4 → queue [t3,t4];
// t5 → queue full → new non-core worker #3; t6 → queue full & max reached → REJECTED

When would I use it?

  • Background processing, such as notifications and report generation.
  • Parallel fan-out — sending many calls at once to services or DB shards.
  • Scheduled jobs, with ScheduledExecutorService.
  • Moving slow work off request threads.

In Spring, define pools as beans (ThreadPoolTaskExecutor) and inject them where needed.

What can go wrong?

  • Unbounded queues hide overload. Nothing looks wrong until the heap fills up. This is the reason Alibaba's Java guidelines ban Executors.newFixedThreadPool.
  • Thread starvation deadlock. Tasks in a pool submit subtasks to the same pool and then wait for them. Once every thread is waiting, no thread is free to run the subtasks. Everything stops.
  • Silent failures. If a task given to submit() throws, the exception is stored inside the Future. If nobody calls get(), the error simply disappears. So log inside the task, or use execute() with an uncaught exception handler.
  • ThreadLocal leakage — data from one pooled task stays on the thread and leaks into the next task (4.15).
  • Forgetting shutdown. Pool threads are non-daemon threads, so they keep the JVM alive and the app never exits.

Interview questions

Q1. Explain how ThreadPoolExecutor handles a new task. If fewer than core-size threads are running, it starts a new core thread. Otherwise it puts the task in the queue. If the queue is full, it starts a non-core thread, up to the max size. If it is already at max, it rejects the task through the rejection handler.

Q2. Why is Executors.newFixedThreadPool risky? It uses an unbounded LinkedBlockingQueue. Under overload, tasks keep piling up until you hit OutOfMemoryError. They are never rejected and the callers are never slowed down.

Q3. How do you size a thread pool? For CPU-bound work, about the number of cores. For I/O-bound work, about cores × (1 + wait/compute). Then check it with Little's Law and load tests. Finally, keep it within what downstream systems can handle, such as the DB pool size.

Q4. What is CallerRunsPolicy and why is it useful? When the pool is full, the thread that submitted the task runs it itself. That keeps the producer busy, so it slows down. You get simple back-pressure without dropping any work.

4.4 Callable, Future and their limits

Why?

In simple words: A Future is a receipt for work happening in the background. You keep the receipt, and later you use it to collect the result — or give up if it takes too long.

A Runnable cannot return a result. It also cannot throw a checked exception.

But background work usually produces a value, such as a score or a price. So you need a handle to collect the result later. You also want a timeout and a way to cancel.

Think of a restaurant token. You order, get a token number, and sit down. When the food is ready, you collect it with the token.

What is happening internally?

  1. submit(Callable<V>) wraps your task in a FutureTask.
  2. A FutureTask plays two roles. It is the Runnable that the worker thread runs. It is also the Future<V> that you hold.
  3. It stores either the result or the exception.
  4. It also tracks a state: NEW → COMPLETING → NORMAL/EXCEPTIONAL/CANCELLED.
  5. Threads that call get() are parked — put to sleep — until the state is final.

How does it work?

  • get() blocks until the task is done. get(timeout, unit) throws TimeoutException if the time runs out first.
  • If the task throws, get() rethrows the exception wrapped in ExecutionException. Call getCause() to get the original exception.
  • cancel(true) interrupts the running task. This only works if the task responds to interrupts.
  • invokeAll(tasks) waits for all tasks. invokeAny(tasks) returns the first successful result and cancels the rest.

Example

ExecutorService pool = Executors.newFixedThreadPool(4);
Future<Price> price = pool.submit(() -> pricingClient.price(sku));      // Callable<Price>
try {
    Price p = price.get(800, TimeUnit.MILLISECONDS);
} catch (TimeoutException e) {
    price.cancel(true);                                                  // stop waiting and interrupt the task
    useCachedPrice();
} catch (ExecutionException e) {
    log.error("pricing failed", e.getCause());                           // the real exception
}

When would I use it?

Use it for the simple case: "run this in the background and collect the result, with a timeout".

If you need to combine several async steps — do this, then that; combine these two; recover from a failure — use CompletableFuture (4.11).

What can go wrong?

  • get() without a timeout can block a request thread forever.
  • No chaining. You can't chain or combine Futures without blocking. That is exactly the gap CompletableFuture fills.
  • Ignored Futures swallow exceptions. If nobody calls get(), nobody sees the error.

Interview questions

Q1. Runnable vs Callable? Callable returns a value and can throw checked exceptions. Runnable returns nothing and cannot throw checked exceptions.

Q2. What are Future's limitations? get() blocks. There are no callbacks. You can't chain or combine Futures. You can't complete one manually. CompletableFuture solves all of these.

4.5 synchronized, monitors, and wait/notify

Why?

In simple words: synchronized is a lock on a door: only one thread can be inside at a time, and whoever enters next sees everything the last person changed. wait/notify let a thread sleep until someone tells it "the thing you need is ready".

You often need two guarantees for a block of code:

  • Mutual exclusion — only one thread can run it at a time.
  • Visibility — changes made inside are seen by the next thread that enters.

synchronized is Java's built-in tool for both.

wait/notify add one more ability. A thread can sleep until a condition becomes true, such as "the queue is not empty".

Think of a single-key washroom at an office. Whoever has the key goes in. Others wait outside. When the key comes back, the next person goes in.

What is happening internally?

  • Every Java object can act as a monitor — a lock plus a waiting room. The object header has a field called the mark word. It stores the object's lock state.
  • Uncontended locking is cheap. "Uncontended" means no other thread wants the lock right now. In that case the JVM uses a lightweight (thin) lock. It does one CAS (an atomic compare-and-swap, see 4.8) on the mark word. The mark word then points to a lock record on the owning thread's stack. (Biased locking, an older trick, was removed in Java 15/18.)
  • Under contention, the lock inflates. When threads start fighting for the lock, it becomes a heavyweight monitor — an ObjectMonitor. This has an entry list of BLOCKED threads and a wait set of WAITING threads. It uses OS-level parking to put threads to sleep.
  • Bytecode. A synchronized block compiles to monitorenter / monitorexit. There is also an exception path that runs monitorexit, so the lock is released even on errors. A synchronized method instead sets the ACC_SYNCHRONIZED flag.
  • Memory effects. Releasing a monitor flushes your writes to memory. Acquiring it throws away stale cached reads. In JMM terms, an unlock happens-before every later lock of the same monitor (4.6).
  • Reentrant. A thread that already holds the lock can enter other synchronized blocks on the same object. A counter tracks how deep it is.
            ┌────────── ObjectMonitor (inflated) ──────────┐
 BLOCKED →  │ entry list: T3, T4  (waiting to acquire)      │
            │ owner: T1                                     │
 WAITING →  │ wait set: T2  (called wait(); lock released)  │
            └───────────────────────────────────────────────┘
notify(): moves one thread from the wait set to the entry list; it must re-acquire the lock before continuing

How does it work?

  1. A thread holding the monitor calls wait(). It is only allowed while holding the monitor.
  2. wait() releases the lock and moves the thread into the wait set.
  3. Another thread changes the state and calls notify() or notifyAll(). This moves one waiter (or all waiters) back to compete for the lock.
  4. The woken thread reacquires the lock.
  5. It must re-check the condition in a while loop. Why? Because another thread may have changed the state in between. Also, the JVM allows spurious wakeups — a thread can wake up even when nobody called notify.

Example

public class Inventory {
    private final Object lock = new Object();                 // private lock object: outsiders can't interfere
    private final Map<String, Integer> stock = new HashMap<>();

    public boolean reserve(String sku, int qty) {
        synchronized (lock) {                                 // check-then-act made atomic
            int have = stock.getOrDefault(sku, 0);
            if (have < qty) return false;
            stock.put(sku, have - qty);
            return true;
        }
    }

    public void awaitStock(String sku, int qty) throws InterruptedException {
        synchronized (lock) {
            while (stock.getOrDefault(sku, 0) < qty) lock.wait();   // ALWAYS a while loop
        }
    }
    public void restock(String sku, int qty) {
        synchronized (lock) {
            stock.merge(sku, qty, Integer::sum);
            lock.notifyAll();                                 // wake waiters to re-check their conditions
        }
    }
}

When would I use it?

  • Simple mutual exclusion around small critical sections.
  • Classic interview problems, such as odd/even printing and producer–consumer.

For production producer–consumer code, use a BlockingQueue instead. If you need timeouts, fairness or several separate conditions, use ReentrantLock (4.7).

What can go wrong?

  • Locking on the wrong object:
  • On this in library classes — callers can lock the same object too.
  • On String literals or boxed Integers — these are shared, pooled instances used elsewhere.
  • On a non-final field — the field can change, so threads lock different objects.
  • Holding a lock during slow I/O. This kills throughput and invites deadlocks.
  • wait in an if instead of while. This causes bugs on spurious wakeups, or when another thread already used up the condition.
  • notify instead of notifyAll when there are several kinds of waiters. It can wake the wrong thread. The right thread never wakes, and the system hangs. This is called a lost wakeup.
  • wait/notify outside a synchronized block throws IllegalMonitorStateException.
  • Virtual threads (Java 21). Blocking inside synchronized pins the carrier thread — the real OS thread under the virtual thread cannot be freed (4.12).

Interview questions

Q1. What does synchronized guarantee? Two things. Mutual exclusion on the monitor: only one thread at a time. And visibility: everything written before releasing the lock is seen by the next thread that acquires it.

Q2. sleep() vs wait()? sleep is a static Thread method. It pauses the thread but does not release any locks. wait must be called while holding the monitor. It releases the monitor and waits for a notify or a timeout.

Q3. Why must wait() be called in a loop? Spurious wakeups are allowed — a thread can wake without a notify. Also, the condition may have changed between the notify and the moment the thread gets the lock back. So it must check again.

Q4. Is synchronized reentrant? Why does it matter? Yes. A thread can re-enter locks it already holds. So synchronized methods on the same object can call each other without deadlocking on themselves.

4.6 The Java Memory Model, volatile and happens-before

Why?

In simple words: The CPU and compiler shuffle and cache memory to go faster, so one thread may not see another thread's changes. The Java Memory Model is the rulebook that says when a change must be seen, and volatile is the simplest way to force it.

Modern CPUs and the JIT compiler aggressively reorder and cache memory operations. Without clear rules, you could not reason about what one thread sees of another thread's writes.

The Java Memory Model (JMM) gives these rules. It defines exactly when a write is guaranteed to be visible. It does this through a relation called happens-before. It also gives you volatile, the lightest tool to create a happens-before link.

What is happening internally?

Happens-before (HB): if action A happens-before action B, then B sees all of A's memory changes. B also sees everything that happened before A.

The main ways to get an HB link are:

  • Program order inside one thread.
  • Unlock → later lock of the same monitor.
  • Volatile write → later volatile read of the same variable.
  • Thread start and join. Thread.start() → everything in the started thread. Everything in a thread → a successful join() on it.
  • Hand-offs between threads. Submitting a task to an executor → the task running. A Future completing → get() returning. Putting into a concurrent collection → taking it out.
  • HB is transitive. If A → B and B → C, then A → C.

How volatile works:

  1. The JIT cannot cache a volatile variable in a register. Every read and write goes to memory.
  2. The CPU adds memory barriers (also called fences) around it. These stop other reads and writes from being reordered across the volatile access.
  3. So a volatile write publishes everything written before it. A thread that reads the volatile then sees all those earlier writes too.

volatile gives visibility and ordering, but not atomicity. With volatile int c; c++, updates are still lost — c++ is still three steps.

Thread A                               Thread B
data = 42;            (1)
ready = true;  (volatile write) (2) ──HB──►  if (ready)  (volatile read) (3)
                                               print(data)                (4) → guaranteed 42
Without volatile: B might loop forever on a stale `ready`, or see ready=true but data=0 (reordered).

How does it work?

Use volatile for a single variable that one thread writes and others read. Good examples: flags, and configuration references that you swap in one go. It works only when you don't need a compound read-modify-write. For anything else, use locks or atomics.

Double-checked locking (a lazy singleton) needs volatile. Here is why. instance = new X() is really three steps:

  1. Allocate memory.
  2. Run the constructor.
  3. Publish the reference into instance.

Without volatile, step 3 can be reordered before step 2 finishes. Then another thread sees a non-null reference to a half-built object, and uses it.

Example

class Poller implements Runnable {
    private volatile boolean running = true;          // without volatile the loop may never see 'false'
    public void stop() { running = false; }
    public void run() { while (running) poll(); }
}

class RuleRegistry {                                  // hot-swappable immutable config
    private volatile Map<String, Rule> rules = Map.of();
    void reload(Map<String, Rule> fresh) { rules = Map.copyOf(fresh); }   // one volatile write publishes the whole map
    Rule get(String id) { return rules.get(id); }                          // lock-free reads
}

public final class ConfigHolder {                     // double-checked locking, done right
    private static volatile ConfigHolder instance;
    public static ConfigHolder get() {
        ConfigHolder local = instance;                // one volatile read on the fast path
        if (local == null) {
            synchronized (ConfigHolder.class) {
                local = instance;
                if (local == null) instance = local = new ConfigHolder();
            }
        }
        return local;
    }
    private ConfigHolder() {}
}
// Simpler and equally lazy: the holder idiom (class init is thread-safe by JVM spec)
final class Config2 { private static class H { static final Config2 I = new Config2(); } static Config2 get() { return H.I; } }

When would I use it?

  • Stop flags and status flags.
  • Publishing immutable snapshots that many threads read — config, rule tables, feature flags.
  • Lazy initialisation patterns.

Most of the time, you get happens-before "for free" from higher-level tools: executors, concurrent collections and CompletableFuture.

What can go wrong?

  • Using volatile for counters or check-then-act. It is not atomic, so updates get lost.
  • Volatile reference, mutable object. Making the reference volatile does not protect the object behind it. For example, volatile Map plus map.put from many threads is not safe. Instead, build a new immutable object and swap the whole reference.
  • Synchronising only the writer. Readers must also synchronise (or the field must be volatile). Otherwise they may never see the write.

Interview questions

Q1. What does volatile guarantee? Visibility: writes are seen by all threads. And ordering: no reordering across the volatile access. It does not make compound operations atomic.

Q2. What is happens-before? It is the JMM's ordering guarantee: if A happens-before B, then B sees A's effects. It is created by locks, volatile, thread start/join, executor hand-offs and concurrent collections. It is also transitive.

Q3. Why does double-checked locking need volatile? Without it, the reference can be published before the constructor finishes. Another thread may then use a partly constructed object.

Q4. volatile vs synchronized vs AtomicInteger? volatile gives visibility only. synchronized gives mutual exclusion plus visibility for a whole block. AtomicInteger gives lock-free atomic operations on a single variable, with visibility.

4.7 Explicit locks: ReentrantLock, ReadWriteLock, StampedLock, Condition

Why?

In simple words: synchronized is a basic lock with no options. Explicit locks add the options real systems need: "give up if you can't get the lock in 500 ms", "let many readers in together", and "separate waiting rooms for different reasons".

synchronized has four limits:

  • It can't time out.
  • A thread waiting for it can't be interrupted.
  • It isn't fair — it doesn't serve threads in arrival order.
  • It has only one wait set.

Real systems need more:

  • "Try to get the lock for 500 ms, else fail fast." This avoids hanging requests and deadlocks.
  • "Many readers or one writer" for caches that are read much more than written.
  • Several separate wait conditions, such as "not full" and "not empty".

What is happening internally?

Most java.util.concurrent locks are built on AbstractQueuedSynchronizer (AQS). AQS has these parts:

  • An int state. For ReentrantLock, 0 means free, and n means the owner holds it n times. It is changed with CAS (atomic compare-and-swap, 4.8).
  • A FIFO wait queue of parked (sleeping) threads. It is built from CLH-style linked nodes.
  • Acquire steps: 1. Try a CAS on the state. 2. If it fails, join the queue and park (LockSupport.park). 3. Sleep until the releasing thread calls unpark on you.

Other details:

  • Fair mode hands the lock out in queue order. Nobody can jump the line (no barging). So no thread starves, but throughput is lower.
  • Non-fair mode is the default. A newly arriving thread may grab a lock that was just freed. Throughput is higher.
  • Condition objects each keep their own wait queue. await() releases the lock, just like wait().
  • ReentrantReadWriteLock splits the AQS state into two parts: a read count (high 16 bits) and a write count (low 16 bits).
  • StampedLock (Java 8) adds optimistic reads: 1. Read without taking any lock. 2. Call validate(stamp) to check that no write happened meanwhile. 3. If a write did happen, fall back to a real read lock.

This is very fast when reads dominate. But it is not reentrant.

How does it work?

lock.lock();
try { /* critical section */ }
finally { lock.unlock(); }          // ALWAYS in finally — unlike synchronized, nothing releases it for you
Feature synchronized ReentrantLock
Timed / try acquisition No tryLock(), tryLock(t, unit)
Interruptible waiting No lockInterruptibly()
Fairness No Optional
Multiple conditions One Many, via newCondition()
Auto release Yes Manual (in finally)
Virtual-thread friendly (Java 21) Pins when blocking Doesn't pin

Example

public class TransferService {
    private final ReentrantLock lock = new ReentrantLock();
    public boolean transfer(Account from, Account to, long amt) throws InterruptedException {
        if (!lock.tryLock(500, TimeUnit.MILLISECONDS)) return false;     // fail fast instead of hanging
        try {
            if (from.balance() < amt) return false;
            from.debit(amt); to.credit(amt);
            return true;
        } finally { lock.unlock(); }
    }
}

public class RuleCache {                                   // read-heavy: many concurrent readers
    private final ReadWriteLock rw = new ReentrantReadWriteLock();
    private final Map<String, Rule> rules = new HashMap<>();
    public Rule get(String id) { rw.readLock().lock();  try { return rules.get(id); } finally { rw.readLock().unlock(); } }
    public void put(String id, Rule r) { rw.writeLock().lock(); try { rules.put(id, r); } finally { rw.writeLock().unlock(); } }
}

class Point {                                              // StampedLock optimistic read
    private double x, y; private final StampedLock sl = new StampedLock();
    double distanceFromOrigin() {
        long stamp = sl.tryOptimisticRead();
        double cx = x, cy = y;
        if (!sl.validate(stamp)) {                         // a write happened: retry with a real read lock
            stamp = sl.readLock();
            try { cx = x; cy = y; } finally { sl.unlockRead(stamp); }
        }
        return Math.hypot(cx, cy);
    }
}

When would I use it?

  • tryLock with timeouts around resources that may be contended. Examples: account transfers, seat holds kept in memory.
  • Read-write locks for caches that are mostly read, when a ConcurrentHashMap doesn't fit.
  • Conditions for custom blocking structures, such as the bounded buffer in 4.14.
  • ReentrantLock instead of synchronized around blocking calls on virtual threads, because it doesn't pin.

What can go wrong?

  • Forgetting unlock() in finally. If an exception happens, the lock stays held forever. Everyone else hangs.
  • Trying to upgrade a read lock. ReadWriteLock doesn't let you upgrade a read lock to a write lock. If you try, you deadlock.
  • Writer starvation. In non-fair mode, under heavy reads, writers may wait for a very long time.
  • Fair locks are slow. They cut throughput a lot. Use them only when starvation is a real problem.
  • StampedLock traps. It isn't reentrant. And with optimistic reads, you must copy fields into local variables before you validate.

Interview questions

Q1. ReentrantLock vs synchronized? ReentrantLock adds tryLock with timeouts, interruptible acquisition, optional fairness and multiple Conditions. But you must unlock it yourself in finally. synchronized is simpler and is released automatically.

Q2. What is AQS? AbstractQueuedSynchronizer. It is the framework behind most j.u.c locks and synchronisers. It uses an int state changed by CAS, and a FIFO queue of parked threads.

Q3. When would you use a ReadWriteLock? For shared data that is read a lot and written rarely. Reads can then run at the same time, and only writes are exclusive.

Q4. Fair vs non-fair locks? A fair lock serves threads in arrival order: no starvation, but slower. A non-fair lock lets new threads jump in (barging) for higher throughput. Non-fair is the default.

4.8 Atomics and compare-and-swap (CAS)

Why?

In simple words: Instead of locking, a thread says "change this value from 5 to 6, but only if it is still 5". If someone else changed it first, the thread just tries again. Nobody ever sleeps or waits.

Sometimes you share just one variable — a counter, a sequence number, or a reference to the latest config. A lock is heavy for this. Threads get parked and unparked, and each context switch costs microseconds.

Modern CPUs offer an atomic instruction called compare-and-swap (CAS). It lets you update a variable safely without blocking any thread.

What is happening internally?

  • CAS(address, expected, new) does this in one atomic step: "If the value at this address equals expected, set it to new and report success. Otherwise, report failure." On x86 it is the LOCK CMPXCHG instruction.
  • AtomicInteger.incrementAndGet() is a loop: 1. Read the current value. 2. Try CAS(current, current+1). 3. If it fails, another thread changed the value. Go back to step 1.

This is called lock-free: at any moment, at least some thread is making progress. - Visibility. The value field is volatile, so atomics also give visibility. - Cost under contention. When many threads hit the same atomic, many CAS attempts fail and retry. The cache line also bounces between cores. LongAdder fixes this. It spreads the count across an array of cells — roughly one per contending thread, chosen by hash. On read, it adds up all the cells. So increments rarely collide. - The ABA problem. The value changes from A to B and back to A between your read and your CAS. Your CAS succeeds, even though the state did change in between. This matters for lock-free stacks and queues. The fix is a version stamp (AtomicStampedReference).

How does it work?

incrementAndGet():
  loop:
    cur = value                // volatile read
    if CAS(value, cur, cur+1)  // hardware atomic
        return cur+1
    // else someone else won the race: retry with the fresh value

Example

AtomicInteger seq = new AtomicInteger();
int id = seq.incrementAndGet();
seq.updateAndGet(x -> Math.min(x * 2, 1_000));        // arbitrary atomic update (function may run multiple times!)
boolean won = seq.compareAndSet(5, 6);                // only one of many racing threads succeeds

LongAdder requests = new LongAdder();                 // metrics counter under heavy contention
requests.increment();
long total = requests.sum();                          // not an atomic snapshot while increments continue

AtomicReference<RateCard> card = new AtomicReference<>(RateCard.initial());
card.updateAndGet(c -> c.withSurge(1.2));             // immutable object + CAS = lock-free config updates

// Exactly-once initialisation flag
AtomicBoolean started = new AtomicBoolean(false);
if (started.compareAndSet(false, true)) startScheduler();   // only the first caller starts it

When would I use it?

  • ID and sequence generators.
  • Counters and metrics (LongAdder).
  • "Only once" flags.
  • Lock-free swaps of immutable state (AtomicReference).
  • Simple rate-limiter state.

If several variables must change together, use a lock. Or put them into one immutable object inside an AtomicReference.

What can go wrong?

  • Two atomics are not atomic together. If you update them one after the other, another thread can see one changed and the other not. For example, balance and version kept as separate atomics can drift apart.
  • Update functions can run more than once. Under contention, the function passed to updateAndGet may run several times. So it must have no side effects.
  • Busy CAS loops waste CPU under extreme contention. LongAdder or a lock may be better.
  • ABA in hand-written lock-free structures.

Interview questions

Q1. What is CAS? An atomic CPU instruction. It sets a memory location to a new value only if it currently holds the expected value. It is the base of lock-free algorithms and Java atomics.

Q2. How does AtomicInteger.incrementAndGet work? With a retry loop. It reads the volatile value, tries a CAS to value+1, and retries if the CAS fails.

Q3. AtomicLong vs LongAdder? LongAdder splits (stripes) the count across several cells to reduce contention. So increments are much faster with many threads. The cost is that sum() is slower and is not an atomic snapshot.

Q4. What is the ABA problem? CAS can't detect that a value changed and then changed back. You solve it with versioned references, like AtomicStampedReference.

4.9 ConcurrentHashMap internals

Why?

In simple words: ConcurrentHashMap is a map that many threads can use at the same time safely. Readers never wait, and writers only lock the one small bucket they are changing — not the whole map.

Servers use shared maps all the time. Some examples:

  • an in-process cache (a cache inside the app's own memory),
  • a counter per tenant,
  • a set of IDs you have already seen, to skip duplicates (a de-duplication set),
  • a registry of active sessions.

A plain HashMap breaks if two threads write to it at the same time. Its internal data can get corrupted.

Hashtable and Collections.synchronizedMap are safe. But they use one lock for everything. So every reader and every writer must stand in one line, one after another.

ConcurrentHashMap (CHM) fixes this:

  • Reads take no lock at all.
  • Writes to different buckets run in parallel.

Think of a big post office with many counters. Hashtable has one counter for everyone. CHM opens a separate counter for each bucket, and anyone who only wants to look at something does not need a counter at all.

What is happening internally?

Java 7: the map was split into 16 parts called Segments. Each segment was a small hash table with its own ReentrantLock. So at most 16 threads could write at the same time.

Java 8+ (this is the version to describe in interviews): there is one Node[] table, just like HashMap. But it adds these tricks:

  • Reads take no lock. The table and each node's val and next fields are volatile. Volatile means every thread always sees the latest written value. So get just reads; it never waits.
  • Writes to an empty bin use CAS. CAS means compare-and-swap: "put my node here only if the slot is still empty", done as one atomic CPU step. The call is casTabAt(tab, i, null, newNode). This common case needs no lock.
  • Writes to a non-empty bin use synchronized on the bin's first node. Only that one bucket is locked. Writers to other buckets carry on in parallel.
  • Treeify at 8 nodes. Like HashMap, a bin with 8 nodes turns into a tree. Here it is a TreeBin, which has its own lightweight read-write locking.
  • Resizing is shared work (cooperative). It works like this: 1. A resizing thread moves bins to a new, bigger table. 2. After moving a bin, it puts a ForwardingNode in the old bin. This is a signpost saying "moved to the new table". 3. If another thread tries to write and hits a forwarding node, it does not wait. It helps transfer a range of bins. 4. If a read hits a forwarding node, it simply looks in the new table.
  • size() uses a baseCount plus a CounterCell[] array. This is the same idea as LongAdder: threads add to different cells, so no single counter becomes a hotspot. The catch: while writes are happening, size() is only an estimate.
  • No null keys or values. In a concurrent map, get returning null must clearly mean "not present". Why? Because you cannot run containsKey and get together as one atomic step. Another thread could change the map between the two calls. So null is reserved to mean "absent".
table: [ ∅ ][ A→B ][ ∅ ][ C ][ FWD ][ D→E→F ] ...
put into an empty bin  → CAS (no lock)
put into "A→B" bin      → synchronized(A) { append/replace }
bin already moved       → ForwardingNode: help resize, then retry in the new table
get(...)                → volatile reads only, never blocks

How does it work?

The real power of CHM is its atomic compound operations. A compound operation is a "check and then change" done as one step. This is what makes CHM more than just "a safe HashMap".

Each of these runs atomically per key. It holds that key's bin lock while it runs:

Method Atomic behaviour
putIfAbsent(k, v) Insert only if the key is not there yet
computeIfAbsent(k, fn) Compute and insert only if absent; fn runs at most once per key
compute(k, (k, old) -> new) Read, change and write back in one step; return null to remove the key
merge(k, v, fn) Insert v, or combine it with the existing value using fn
replace(k, old, new) CAS on the value: replace only if the current value is still old

Example

// Per-SKU request counters (hot, many threads)
ConcurrentHashMap<String, LongAdder> hits = new ConcurrentHashMap<>();
hits.computeIfAbsent(sku, k -> new LongAdder()).increment();

// Atomic stock reservation: check-then-act inside compute, under the bin lock
ConcurrentHashMap<String, Integer> stock = new ConcurrentHashMap<>(Map.of("SKU1", 10));
boolean[] reserved = {false};
stock.compute("SKU1", (k, have) -> {
    if (have == null || have < 3) return have;    // not enough: unchanged
    reserved[0] = true;
    return have - 3;
});

// WRONG — two separate calls, a race even on CHM
if (!map.containsKey(k)) map.put(k, expensiveLoad(k));
// RIGHT
map.computeIfAbsent(k, this::expensiveLoad);

// Concurrent set
Set<String> seenEventIds = ConcurrentHashMap.newKeySet();
if (!seenEventIds.add(eventId)) return;           // duplicate delivery

When would I use it?

  • In-process caches and registries shared by request threads.
  • Counters and metrics.
  • De-duplication sets (via ConcurrentHashMap.newKeySet()).
  • Per-key memoisation, which means "compute once per key and remember the result" (computeIfAbsent).
  • Connection or session registries (as in the chat design, 13.5).

If your cache needs a size limit or TTLs (time-to-live — entries expire after some time), use Caffeine instead. It is built on similar ideas.

What can go wrong?

  • Compound actions built from separate calls are races. For example, get then put, or containsKey then put. Another thread can slip in between the two calls. Use the atomic methods instead.
  • Slow or blocking functions inside compute*. The function runs while holding the bin lock. So other keys in the same bin are blocked until it finishes. Also, if you update the same map from inside computeIfAbsent (a recursive update), it can throw IllegalStateException ("Recursive update") or deadlock.
  • Iterators are weakly consistent. They never throw ConcurrentModificationException. But they may or may not show changes made while you iterate. So don't use them when you need an exact snapshot.
  • size() is approximate while other threads are writing.
  • Unbounded growth. A CHM used as a cache with no eviction (nothing ever removed) is a memory leak (5.7).

Interview questions

Q1. How does ConcurrentHashMap achieve thread safety in Java 8? Reads are lock-free because the fields are volatile. Inserting into an empty bin uses CAS. Writing to a non-empty bin uses synchronized on that bin's first node only. Resizing is cooperative — threads that hit a forwarding node help move bins. And the size is kept in striped counters, so counting is not a bottleneck.

Q2. Why doesn't it allow null keys or values? In a concurrent map, if get returned null, you could not tell "key absent" from "key mapped to null". You also cannot check both with containsKey and get atomically, because another thread may change the map in between. So null is banned and always means "absent".

Q3. HashMap vs Hashtable vs synchronizedMap vs ConcurrentHashMap? HashMap has no synchronisation, so it is unsafe for concurrent writes. Hashtable and synchronizedMap use one lock for every operation, so all access goes one at a time. ConcurrentHashMap allows reads in parallel with no lock, and writes in parallel with fine-grained, per-bucket locking.

Q4. Is map.get(k) + map.put(k, v+1) safe on ConcurrentHashMap? No. Each call on its own is atomic, but the pair is not — another thread can update between them and you lose its update. Use merge(k, 1, Integer::sum) or compute to do it in one atomic step.

4.10 Synchronizers: CountDownLatch, CyclicBarrier, Semaphore

Why?

In simple words: These are ready-made tools for making threads wait for each other. A latch says "wait until N things are done", a barrier says "wait until all N friends arrive", and a semaphore says "only N people inside at a time".

Many coordination problems are not about protecting data. They are about timing, like:

  • "wait until N things happen",
  • "let N threads start together",
  • "allow at most N calls at a time to this slow partner service".

You could build these yourself with wait/notify. But that is easy to get wrong. The JDK gives you tested building blocks instead. They are built on AQS (AbstractQueuedSynchronizer — the JDK's common base for locks and waiting queues).

What is happening internally?

Tool AQS state means Behaviour Reusable
CountDownLatch(n) How many counts are left countDown() reduces the count by one; await() blocks until it reaches 0 No (one-shot)
CyclicBarrier(n, action) Threads still to arrive (built on a lock + condition, not AQS directly) Each await() blocks until n threads arrive; then the optional action runs and all continue Yes (resets for each round, called a "generation")
Semaphore(permits) Permits available acquire() takes one (blocks when 0 are left); release() gives one back Yes
Phaser Parties and phases that can change at runtime A flexible barrier where threads can join (register) and leave (deregister) Yes

How does it work?

  • Latch: a one-way gate. Worker threads count down. The coordinator thread waits for the count to reach zero. Once open, it never closes again.
  • Barrier: threads wait for each other at a meeting point (a rendezvous). It is used for work done in phases — everyone finishes phase 1, then everyone starts phase 2.
  • Semaphore: a counter of permits. It is the classic way to limit how many threads use a resource at once. A semaphore has no owner thread, so any thread can call release(). A lock is different: only the thread that locked it can unlock it.

Think of a restaurant with 10 tables. The manager hands out 10 table tokens (permits). When all tokens are out, new guests wait. When a guest leaves, the token goes back, and the next guest gets in.

Example

// Fan out to 3 services; wait at most 2 s for all
ExecutorService io = Executors.newFixedThreadPool(3);
CountDownLatch done = new CountDownLatch(3);
Map<String, Object> results = new ConcurrentHashMap<>();
for (String svc : List.of("pricing", "stock", "schemes")) {
    io.submit(() -> {
        try { results.put(svc, call(svc)); }
        finally { done.countDown(); }              // ALWAYS count down, even on failure
    });
}
boolean allArrived = done.await(2, TimeUnit.SECONDS);

// Limit concurrent calls to a partner API that allows 10 parallel requests
Semaphore partnerSlots = new Semaphore(10);
Voucher issueVoucher(Req r) throws InterruptedException {
    if (!partnerSlots.tryAcquire(500, TimeUnit.MILLISECONDS)) throw new BusyException("partner saturated");
    try { return partner.issue(r); }
    finally { partnerSlots.release(); }
}

// Barrier: 4 workers compute a phase, then merge, then continue
CyclicBarrier barrier = new CyclicBarrier(4, () -> System.out.println("phase merged"));

When would I use it?

  • Latch:
  • start-up readiness, e.g. wait for caches to warm up before taking traffic;
  • tests that wait for async work to finish;
  • fan-out-and-wait (start many tasks, wait for all) — though CompletableFuture's allOf is usually nicer.
  • Semaphore:
  • bulkheads around a slow dependency (a bulkhead caps how many threads one dependency can take, so it can't sink the whole app);
  • limiting how many virtual threads hit the DB at the same time;
  • simple resource pools.
  • Barrier: parallel simulations and batch work done in phases.

What can go wrong?

  • Forgetting countDown() on the error path. If a task throws before counting down, await() hangs forever. Put countDown() in finally, and give await a timeout.
  • release() without a matching acquire(). This adds an extra permit, so more threads get in than you wanted. A semaphore does not track who took which permit.
  • One bad thread breaks a CyclicBarrier for everyone. If a thread fails or times out at the barrier, all waiting threads get BrokenBarrierException.

Interview questions

Q1. CountDownLatch vs CyclicBarrier? A latch lets one or more threads wait for N events, and it is one-shot — it cannot be reset. A barrier makes N threads wait for each other. It is reusable for the next round, and it can run an action once all threads arrive.

Q2. What is a Semaphore used for? It limits how many threads can use a resource at the same time. For example, at most N parallel calls to a partner API, or at most N DB-heavy jobs running together.

Q3. Semaphore vs lock? A lock has one owner and gives mutual exclusion — only one thread inside at a time. A semaphore has N permits and no owner, so any thread may release a permit.

4.11 CompletableFuture: composing asynchronous work

Why?

In simple words: CompletableFuture lets you start several slow calls at once and say "when they finish, do this next" — without making a thread sit and wait. It is Java's version of C#'s Task.

Say a recommendation API needs three things from three services: price, stock and eligible schemes.

  • If you call them one after another, the waits add up: 300 + 250 + 400 ms = 950 ms.
  • If you call them in parallel, you only wait for the slowest one: about 400 ms.

Plain Future can run them in parallel. But the only way to get the result is get(), which blocks the thread until the value is ready.

CompletableFuture (CF) is better. Without blocking any thread, it lets you:

  • chain steps ("then do this"),
  • combine results,
  • time out slow work,
  • recover from errors.

If you know C#, this is like Task with ContinueWith and WhenAll.

What is happening internally?

  • A CF has a result field. It holds the value, or a wrapper around an exception.
  • It also has a stack of dependent actions. Each one is a Completion object — "work to do when I finish".
  • thenApply(fn) adds a dependent stage to that stack. When the CF completes, the thread that completed it pops and runs the dependents. For the *Async versions, it instead hands them to an executor.
  • If the CF is already complete when you call thenApply, the function runs right away, on your calling thread.
  • supplyAsync(supplier) with no executor uses the common ForkJoinPool. This one pool is shared by the whole JVM, and its size is (CPU cores − 1).
  • Exceptions travel down the chain, wrapped in a CompletionException, until some stage handles them (exceptionally or handle).
supplyAsync(price) ─┐
supplyAsync(stock) ─┼─ thenCombine ─ thenCombine(schemes) ─ orTimeout(800ms) ─ exceptionally(fallback) ─► Recommendation
supplyAsync(schemes)┘

How does it work?

The main methods, with the C#/functional idea each one matches:

Method Analogy Use
supplyAsync(s, executor) Task.Run Start async work that returns a value
thenApply(fn) map Change the result with a normal (non-async) function
thenCompose(fn) flatMap Chain another async call that itself returns a CF (avoids ending up with CF<CF<T>>)
thenCombine(other, fn) zip Join two independent results into one
thenAccept / thenRun Use the result / just run something after; returns no result
allOf(...) / anyOf(...) WhenAll / WhenAny Fan-in: wait for all / for the first one
exceptionally(fn) catch Recover from an error by returning a value
handle((v, ex) -> ...) Look at success or failure, and return a value either way
whenComplete((v, ex) -> ...) finally Do a side effect (like logging); the original outcome passes through unchanged
orTimeout(t) / completeOnTimeout(v, t) (Java 9) After the timeout, fail / use a default value
*Async variants Run the stage on an executor instead of on the thread that completed the previous stage

Example

ExecutorService io = new ThreadPoolExecutor(16, 64, 60, TimeUnit.SECONDS,
        new ArrayBlockingQueue<>(500), Thread.ofPlatform().name("io-", 0).factory(),
        new ThreadPoolExecutor.CallerRunsPolicy());

CompletableFuture<Price> price   = CompletableFuture.supplyAsync(() -> pricing.get(sku), io);
CompletableFuture<Stock> stock   = CompletableFuture.supplyAsync(() -> inventory.get(sku), io);
CompletableFuture<List<Scheme>> schemes = CompletableFuture.supplyAsync(() -> schemeSvc.eligible(outlet, sku), io)
        .completeOnTimeout(List.of(), 300, TimeUnit.MILLISECONDS);     // optional data: default if slow

CompletableFuture<Recommendation> rec = price
        .thenCombine(stock, Partial::new)                              // both needed
        .thenCombine(schemes, (p, s) -> recommend(p, s))
        .orTimeout(800, TimeUnit.MILLISECONDS)                         // overall budget
        .exceptionally(ex -> {
            log.warn("recommendation degraded for {}", sku, ex);
            return Recommendation.fallback(sku);
        });

// thenCompose: dependent async calls (need the user before fetching their tier)
CompletableFuture<Tier> tier = CompletableFuture.supplyAsync(() -> users.find(id), io)
        .thenCompose(user -> CompletableFuture.supplyAsync(() -> loyalty.tier(user), io));

// Fan out over a list and collect all results
List<CompletableFuture<Long>> fs = outlets.stream()
        .map(o -> CompletableFuture.supplyAsync(() -> points(o), io)).toList();
List<Long> all = CompletableFuture.allOf(fs.toArray(new CompletableFuture[0]))
        .thenApply(v -> fs.stream().map(CompletableFuture::join).toList())
        .join();

When would I use it?

  • Aggregator endpoints that call several services in parallel. NOVA's recommendation flow is exactly this.
  • Async pipelines that need fallbacks.
  • Spring @Async methods that return CompletableFuture.
  • Non-blocking HTTP clients (HttpClient.sendAsync).

With Java 21, there is often a simpler option for the same fan-out: plain blocking code on virtual threads (4.12).

What can go wrong?

  • No executor means the common pool. If you do blocking I/O there, you starve parallel streams and every other CF in the whole JVM. Always pass your own I/O executor.
  • Lost exceptions. If a chain has no exceptionally/handle, and nobody calls join(), the error disappears silently.
  • Mixing up thenApply and thenCompose. Using thenApply with a function that returns a CF gives you CompletableFuture<CompletableFuture<T>>.
  • Calling join()/get() inside a stage. This blocks a pool thread while it waits. With a small pool, that can deadlock.
  • No timeout. A dependency that hangs will hold resources forever. Use orTimeout, plus timeouts on the HTTP/DB client itself.
  • ThreadLocal context does not follow. Things like MDC (the logging context) and the security context are stored per thread. They are not copied to executor threads automatically. Wrap the executor, or pass the context explicitly.

Interview questions

Q1. Future vs CompletableFuture? Future only gives you a blocking get and cancel. CompletableFuture adds non-blocking callbacks, chaining, combining results, timeouts, completing it yourself from code, and proper exception handling.

Q2. thenApply vs thenCompose vs thenCombine? thenApply transforms the value, like map. thenCompose chains a function that returns another CF and flattens the result, like flatMap. thenCombine merges the results of two independent CFs.

Q3. Which thread runs thenApply? The thread that completes the previous stage runs it. If the stage is already complete, your calling thread runs it immediately. thenApplyAsync instead runs it on the executor you pass (or the common pool if you pass none).

Q4. How do you handle errors in a CF chain? Use exceptionally to recover with a value, handle to map both success and failure, and whenComplete for side effects like logging. Remember that exceptions arrive wrapped in CompletionException.

4.12 Virtual threads (Java 21)

Why?

In simple words: Virtual threads are very cheap threads managed by the JVM. When one is waiting for the network or DB, it steps aside so the real OS thread can run someone else. So you can write simple blocking code and still handle a huge number of requests.

The thread-per-request model is easy to write and easy to debug: each request gets its own thread. The problem is that normal threads (called platform threads) are expensive:

  • each one reserves about 1 MB of stack memory,
  • each one is backed by a real OS thread.

So one server tops out at a few thousand requests at the same time.

Most requests spend most of their time waiting on I/O — for the DB, for another service. During that wait, the thread sits idle but still holds those scarce resources.

The old fix was reactive/async code (WebFlux, CompletableFuture chains). It scales well. But it is hard to write, hard to read and hard to debug.

Virtual threads give you the scalability of async code, while you keep writing plain blocking code.

What is happening internally?

  • What it is. A virtual thread is a normal Thread object, but the JVM manages it, not the OS. Its stack is stored on the heap as small chunks that can grow (starting at a few hundred bytes). That is why you can have millions of them.
  • Carrier threads. Virtual threads actually run on a small pool of real platform threads called carriers. This pool is a ForkJoinPool with one thread per CPU core.
  • Mounting and unmounting. Here is what happens when a virtual thread blocks: 1. The virtual thread calls a blocking operation that the JDK has made virtual-thread-aware. Examples: socket I/O, Thread.sleep, BlockingQueue.take, ReentrantLock, and JDBC drivers that use java.net sockets. 2. The JVM copies its stack frames to the heap and unmounts it (takes it off the carrier). 3. The carrier is now free and runs another virtual thread. 4. When the I/O finishes, the virtual thread is put back in the queue. 5. It resumes on whichever carrier is free.
  • Pinning (Java 21). Sometimes a virtual thread cannot unmount. This is called pinning. It happens:
  • inside a synchronized block or method,
  • inside a native frame (native code).

If the thread blocks while pinned, it keeps its carrier busy the whole time. There are only a few carriers, so a handful of pinned threads can stall everything. - Java 24 (JEP 491) removed pinning for synchronized. - On Java 21, prefer ReentrantLock around blocking calls. - Detect pinning with -Djdk.tracePinnedThreads=full (Java 21) or with JFR (Java Flight Recorder) events.

Think of a bank with 4 cashiers (carriers) and 1,000 customers (virtual threads). When a customer has to go fetch a missing document (I/O), they step out of the line. The cashier serves the next person. The customer comes back later to any free cashier. Pinning is a customer who goes to fetch the document but stays standing at the counter, blocking that cashier.

Carrier threads (= cores):   C1           C2
Virtual threads:          VT1 running   VT7 running
                          VT2..VT6, VT8..VT100000 parked (stacks on heap, waiting for I/O)
VT1 calls db.query() → unmount VT1 → C1 picks VT3 → DB responds → VT1 queued → resumes on C1 or C2

How does it work?

Thread.ofVirtual().name("vt-", 0).start(() -> handle(request));
try (ExecutorService exec = Executors.newVirtualThreadPerTaskExecutor()) {   // one new virtual thread per task
    ...
}                                                                            // close() waits for tasks
// Spring Boot 3.2+: spring.threads.virtual.enabled=true  → Tomcat request handling and @Async on virtual threads

Don't pool them. Virtual threads are cheap, so create a new one for each task. To limit how many tasks hit a scarce resource at once, use a Semaphore or the resource's own pool (for example the DB connection pool).

Example

// Fetch 10,000 outlet profiles from a partner API, at most 200 in flight (partner limit)
Semaphore inFlight = new Semaphore(200);
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<Profile>> fs = outletIds.stream().map(id -> exec.submit(() -> {
        inFlight.acquire();
        try { return partnerClient.fetch(id); }        // blocking HTTP call — cheap on a virtual thread
        finally { inFlight.release(); }
    })).toList();
    for (Future<Profile> f : fs) save(f.get());
}
// The same with platform threads would need a 200-thread pool; with reactive code, a much harder program.

When would I use it?

Use them for services that handle lots of requests at once and are I/O-bound (mostly waiting, not computing):

  • REST APIs that call DBs and other services,
  • fan-out to many HTTP calls,
  • message consumers that do I/O for each message.

They give little benefit for:

  • CPU-bound work — it is still limited by the number of cores;
  • apps that only have a few requests at a time.

What can go wrong?

  • Pinning in Java 21. synchronized around I/O pins the thread. This can be in your code or inside libraries (older JDBC drivers and connection pools). Check with pinning tracing and upgrade libraries.
  • Overwhelming downstream systems. A million virtual threads will happily fire a million DB queries. Now the DB connection pool and partner rate limits are your real bottleneck. Limit concurrency with semaphores.
  • Code that relies heavily on ThreadLocal. If each of a million threads holds big ThreadLocal values, memory use multiplies. Prefer passing context explicitly, or scoped values.
  • Pooling virtual threads. This is pointless and harmful. Create one per task.
  • CPU-heavy tasks. They can hog the carriers. There is no time-slicing between virtual threads, so one busy thread does not get paused to let others run.

Interview questions

Q1. What are virtual threads and how do they differ from platform threads? They are lightweight threads managed by the JVM. Their stacks live on the heap, and many of them share a few carrier OS threads. When blocked on I/O they unmount and free the carrier, so millions can exist. Platform threads, in contrast, map one-to-one to expensive OS threads.

Q2. What is pinning? Pinning is when a virtual thread cannot unmount from its carrier. In Java 21 this happens inside synchronized or native code. If it blocks there, it holds the carrier thread for the whole wait.

Q3. Do virtual threads make code faster? They increase throughput — total requests handled — for I/O-bound concurrency, because OS threads are not tied up during waits. They do not make a single request faster, and they do not speed up CPU-bound work.

Q4. Should you pool virtual threads? No. They are cheap to create, so use one per task. Limit access to scarce resources with semaphores instead.

4.13 Deadlock, livelock and starvation

Why?

In simple words: A deadlock is when two threads each hold something the other needs, so both wait forever. Once your code takes more than one lock, this can happen — so you must design it away and know how to spot it.

As soon as your code takes more than one lock (or waits on more than one resource), it can freeze forever. This usually happens under production load, and almost never in tests.

Interviewers expect you to:

  • name the conditions that cause deadlock,
  • prevent it by design,
  • diagnose it from a thread dump (a snapshot of what every thread is doing).

What is happening internally?

A deadlock needs all four Coffman conditions to be true at the same time: 1. Mutual exclusion: only one thread can hold the resource at a time. 2. Hold and wait: a thread holds one resource while waiting for another. 3. No preemption: nobody can forcibly take a resource away from a thread. 4. Circular wait: T1 waits for T2's resource, and T2 waits for T1's.

Picture two cars meeting on a narrow one-lane bridge from opposite sides. Each holds its half of the bridge and waits for the other to back up. Neither does, so both wait forever.

T1: lock(A) ──── wants B ───►┐
                             │   circular wait → both BLOCKED forever
T2: lock(B) ──── wants A ───►┘

Two related problems:

  • Livelock: the threads are not blocked. They keep reacting to each other, but no one makes progress. Example: two people in a corridor who both step aside the same way, again and again, forever. Or two transactions that keep retrying at exactly the same moments.
  • Starvation: one thread never gets the CPU or the lock, because others always win. Causes include unfair locks, thread priorities, or a flood of readers that never lets a writer in.

How does it work?

To prevent deadlock, you break one of the four conditions. Any one is enough:

Break Technique
Circular wait Global lock ordering: every thread takes locks in the same fixed order (for example, by account ID)
Hold and wait Take all locks at once, or use tryLock with a timeout and, on failure, release what you hold and back off
No preemption Timeouts that make a thread give up its attempt
Mutual exclusion Lock-free designs, immutable data, or single-writer models (actor/partition: only one thread ever owns a piece of data)

Example

// Deadlock-prone: transfer(A,B) and transfer(B,A) running together
void transferBad(Account from, Account to, long amt) {
    synchronized (from) { synchronized (to) { from.debit(amt); to.credit(amt); } }
}

// Fixed with lock ordering: both threads lock the lower ID first
void transfer(Account from, Account to, long amt) {
    Account first = from.id().compareTo(to.id()) < 0 ? from : to;
    Account second = first == from ? to : from;
    synchronized (first) { synchronized (second) { from.debit(amt); to.credit(amt); } }
}

// Or tryLock with timeout + randomised backoff (avoids livelock)
boolean transferTry(Account from, Account to, long amt) throws InterruptedException {
    for (int attempt = 0; attempt < 5; attempt++) {
        if (from.lock.tryLock(50, TimeUnit.MILLISECONDS)) {
            try {
                if (to.lock.tryLock(50, TimeUnit.MILLISECONDS)) {
                    try { from.debit(amt); to.credit(amt); return true; } finally { to.lock.unlock(); }
                }
            } finally { from.lock.unlock(); }
        }
        Thread.sleep(ThreadLocalRandom.current().nextInt(5, 50));   // jitter breaks lockstep retries
    }
    return false;
}

Diagnosing in production: take a thread dump with jcmd <pid> Thread.print (or jstack). The JVM finds lock cycles itself — for both monitors (synchronized) and ReentrantLock — and prints them like this:

Found one Java-level deadlock:
"pool-1-thread-2": waiting to lock monitor 0x... (object 0x... Account), which is held by "pool-1-thread-1"
"pool-1-thread-1": waiting to lock monitor 0x... (object 0x... Account), which is held by "pool-1-thread-2"

When would I use it?

Use these rules in any design that takes several locks or resources:

  • money or points transfers between two accounts,
  • seat booking with several seats (lock the seats in sorted order),
  • batch updates of many rows.

The same rules apply to database deadlocks too (12.7).

What can go wrong?

  • Hidden lock taking. You call an outside method (a listener, a callback) while holding a lock. That method may need the same lock, or another lock in the opposite order. This is called an "alien method" deadlock.
  • Nested locks across classes with no documented order.
  • Thread-pool starvation deadlock (4.3). Tasks in a pool wait for other tasks that can't get a thread. It is not a lock cycle, but the system freezes in the same way.
  • Retrying without jitter. If threads retry at exactly the same intervals, they collide again and again. A deadlock just becomes a livelock. Jitter means adding a small random delay.

Interview questions

Q1. What are the four conditions for deadlock? Mutual exclusion, hold and wait, no preemption, and circular wait. All four must be true at the same time for a deadlock to happen.

Q2. How do you prevent deadlocks? Break one of the conditions. The usual ways: take locks in one consistent global order, use tryLock with timeouts and backoff, take all resources at once, or use lock-free designs.

Q3. How do you detect a deadlock in a running JVM? Take a thread dump with jcmd Thread.print or jstack. The JVM reports Java-level deadlocks and names the threads and locks involved. To check from code, use JMX: ThreadMXBean.findDeadlockedThreads().

Q4. Deadlock vs livelock vs starvation? Deadlock: threads are blocked forever, each waiting on the other. Livelock: threads are active and busy, but make no progress. Starvation: one thread is always denied the resource while the others keep making progress.

4.14 Producer–consumer, BlockingQueue and classic problems

Why?

In simple words: One side makes work and puts it in a queue; the other side takes work out and does it. The queue has a fixed size, so if workers fall behind, the makers are forced to slow down instead of filling up memory.

The producer–consumer pattern separates creating work from doing it. Some examples:

  • an HTTP handler puts notifications in a queue, and worker threads send them;
  • a Kafka listener hands records to processor threads.

A bounded buffer (a queue with a maximum size) sits in the middle. It does two jobs:

  • it absorbs short bursts of work;
  • it applies back-pressure — when consumers fall behind and the queue is full, producers are made to wait. Without this, the queue keeps growing until you run out of memory.

Think of a tiffin service with a shelf that holds 20 boxes. Cooks (producers) put boxes on the shelf. Delivery boys (consumers) pick them up. If the shelf is full, cooks wait. If it is empty, delivery boys wait.

Interviewers often ask you to build one from scratch. It tests whether you understand locks and conditions.

What is happening internally?

The JDK queues work like this:

  • ArrayBlockingQueue = a circular array + one ReentrantLock + two Conditions (notFull and notEmpty). A Condition is a waiting room tied to a lock.
  • put waits on notFull when the queue is full.
  • take waits on notEmpty when the queue is empty.
  • After each put or take, it signals the other side.
  • LinkedBlockingQueue uses two separate locks, one for put and one for take. So producers and consumers don't block each other, which gives higher throughput. A size limit is optional.
  • SynchronousQueue has no capacity at all. It is a direct hand-off from producer to consumer.
  • PriorityBlockingQueue has no size limit and returns elements in priority order.
  • DelayQueue releases each element only after its delay has expired.

The four styles of method on a BlockingQueue:

Throws Returns special value Blocks Times out
add / remove offer / poll put / take offer(e, t) / poll(t)

How does it work?

This is the bounded buffer you must be able to write in 15 minutes:

import java.util.concurrent.locks.*;

public class BoundedBlockingQueue<T> {
    private final Object[] items;
    private int head, tail, count;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull = lock.newCondition();
    private final Condition notEmpty = lock.newCondition();

    public BoundedBlockingQueue(int capacity) { items = new Object[capacity]; }

    public void put(T item) throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (count == items.length) notFull.await();     // while: re-check after wakeup
            items[tail] = item;
            tail = (tail + 1) % items.length;
            count++;
            notEmpty.signal();                                  // wake one consumer
        } finally { lock.unlock(); }
    }

    @SuppressWarnings("unchecked")
    public T take() throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (count == 0) notEmpty.await();
            T item = (T) items[head];
            items[head] = null;                                 // let GC reclaim it
            head = (head + 1) % items.length;
            count--;
            notFull.signal();                                   // wake one producer
            return item;
        } finally { lock.unlock(); }
    }
}

Why two conditions instead of one shared wait set? Because producers only wake consumers, and consumers only wake producers. No thread gets woken up just to find it still can't proceed. So there are no wasted wakeups.

Example

// Production version: BlockingQueue + poison pill shutdown
record Job(int id) {}
final Job POISON = new Job(-1);
BlockingQueue<Job> q = new ArrayBlockingQueue<>(100);
int consumers = 4;

Runnable producer = () -> {
    try {
        for (int i = 0; i < 1_000; i++) q.put(new Job(i));    // blocks when full → back-pressure
        for (int i = 0; i < consumers; i++) q.put(POISON);    // one pill per consumer
    } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
};
Runnable consumer = () -> {
    try {
        for (Job j = q.take(); j != POISON; j = q.take()) process(j);
    } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
};

// Classic: two threads print 1..N alternately (odd/even)
class OddEven {
    private int n = 1; private final int max;
    OddEven(int max) { this.max = max; }
    synchronized void print(boolean odd) throws InterruptedException {
        while (n <= max) {
            while (n <= max && (n % 2 == 1) != odd) wait();
            if (n <= max) System.out.println(Thread.currentThread().getName() + " " + n++);
            notifyAll();
        }
    }
}

How the poison pill works: the producer puts one special "stop" job (the poison pill) per consumer at the end. When a consumer takes the pill, it exits its loop.

Other classic problems to practise (LeetCode's free concurrency set):

  • Print in Order,
  • FooBar Alternately,
  • Zero Even Odd,
  • Building H₂O,
  • Dining Philosophers (fix it with lock ordering, or with a semaphore of N−1 seats),
  • a thread-safe rate limiter (10.5).

When would I use it?

  • In-process work queues: notification dispatch, audit log writers, async enrichment.
  • Batching: take up to N items at once with drainTo.
  • Smoothing out producers that send work in bursts.

Across separate processes, the same idea becomes a message broker such as Kafka or RabbitMQ (11.12).

What can go wrong?

  • Unbounded queues. new LinkedBlockingQueue<>() with no size limit removes back-pressure. The queue grows until you hit OOM (OutOfMemoryError).
  • Losing in-memory work on crash or deploy. An in-process queue is not durable — if the app dies, the queued work is gone. For work that must survive, use a broker or an outbox table.
  • Shutdown. Consumers blocked in take() never exit on their own. You must interrupt them or send poison pills.
  • Exceptions in consumers. An uncaught exception kills the worker loop silently. Catch errors per item, log them, and send the failed item to a retry or dead-letter queue (a queue for items that keep failing).

Interview questions

Q1. Implement a bounded blocking queue. Use a circular array, one ReentrantLock and two Conditions (notFull and notEmpty). Wrap each await in a while loop to re-check after waking up. After each put, signal notEmpty; after each take, signal notFull (see the code above).

Q2. Why use two Conditions instead of wait/notifyAll? Producers wait on notFull and consumers wait on notEmpty. So each signal wakes only the right kind of thread, and no time is wasted waking threads that can't proceed.

Q3. How do you shut down consumers cleanly? Send poison-pill messages, one per consumer. Or interrupt the threads, and have them exit when they catch InterruptedException.

Q4. ArrayBlockingQueue vs LinkedBlockingQueue? ArrayBlockingQueue is always bounded, uses one lock, and allocates its array up front, so memory use is predictable. LinkedBlockingQueue is optionally bounded and uses separate put and take locks for higher throughput, but it allocates a new node for every element.

4.15 ThreadLocal

Why?

In simple words: A ThreadLocal is a private pocket on each thread. Each thread puts its own value in the pocket and can read it from anywhere in its code, without passing it through every method.

Some data belongs to one request or one thread. For example:

  • the current tenant ID,
  • the logged-in user,
  • a correlation ID for logs (one ID that ties together all log lines of one request),
  • the current transaction or DB connection,
  • a formatter object that is not thread-safe.

Passing these through every method signature makes the code noisy. ThreadLocal gives each thread its own copy, and any code running on that thread can reach it.

What is happening internally?

Here is how it is stored:

  1. Every Thread object has a field called threadLocals.
  2. That field is a ThreadLocalMap — an open-addressing hash table (on a collision it uses the next free slot, not a chain).
  3. The keys are weak references to the ThreadLocal object. A weak reference does not stop GC from collecting the object.
  4. The values are strong references to your data.
  5. tl.get() really does Thread.currentThread().threadLocals.get(tl).

The important consequence: the value lives as long as the thread lives. Server threads are pooled and live forever. So values stay alive from one request to the next, unless you remove them.

Thread "http-nio-8080-exec-7"
  └── threadLocals: { [weak] TENANT → "tenant-42", [weak] MDC → {requestId=...} }
       (pooled thread reused by the NEXT request → stale tenant-42 is still there unless removed)

Spring uses ThreadLocals a lot:

  • SecurityContextHolder — the current user;
  • TransactionSynchronizationManager — this is how @Transactional ties a DB connection to the current thread;
  • RequestContextHolder — the current HTTP request;
  • SLF4J's MDC — extra fields added to log lines.

How does it work?

The pattern has three steps:

  1. Set the value at the start of a unit of work (for example, at the start of a request).
  2. Read it anywhere on that thread.
  3. Always remove it in finally.

Example

public final class TenantContext {
    private static final ThreadLocal<String> CURRENT = new ThreadLocal<>();
    public static void set(String tenantId) { CURRENT.set(tenantId); }
    public static String current() {
        String t = CURRENT.get();
        if (t == null) throw new IllegalStateException("no tenant bound to this thread");
        return t;
    }
    public static void clear() { CURRENT.remove(); }
}

// Servlet filter: bind per request, ALWAYS clear (threads are pooled)
public class TenantFilter extends OncePerRequestFilter {
    @Override protected void doFilterInternal(HttpServletRequest req, HttpServletResponse res, FilterChain chain)
            throws ServletException, IOException {
        TenantContext.set(req.getHeader("X-Tenant-Id"));
        try { chain.doFilter(req, res); }
        finally { TenantContext.clear(); }
    }
}

When would I use it?

  • Request-scoped context in thread-per-request servers: tenant, user, correlation ID.
  • Framework plumbing: transactions, security.
  • Per-thread caches of expensive objects that are not thread-safe. This is rarely needed now — for example, DateTimeFormatter is already thread-safe.

What can go wrong?

  • Leaking data between requests. Threads are pooled. If you forget to clear, the next request on that thread sees the previous request's tenant or user. In a multi-tenant app this is a serious security bug — one customer could see another's data. Always call remove() in finally.
  • Memory leaks. Big values stay alive as long as the long-lived pool threads. In app servers there is a worse case: if a ThreadLocal value holds classes from an app that has been redeployed, it keeps that app's whole ClassLoader alive. This is a Metaspace leak.
  • Async boundaries. Values do not follow your work to other threads — executors, CompletableFuture, @Async or reactive code. You must pass them on explicitly, using task decorators or context-propagation libraries.
  • Virtual threads. Millions of threads × ThreadLocal values means a lot of memory. Java's newer ScopedValue (a preview feature in Java 21) is meant to replace ThreadLocal here.
  • InheritableThreadLocal surprises. It copies values into a child thread when the child is created. With pools, threads are created once and then reused, so the copied values are often stale.

Interview questions

Q1. How does ThreadLocal work internally? Each Thread holds a ThreadLocalMap. Its keys are weak references to the ThreadLocal objects, and its values are strong references to the data. get simply looks up the value in the current thread's map.

Q2. Why can ThreadLocal cause memory leaks or data leaks? Pooled threads live forever. So a value that is set and never removed stays there across tasks. This leaks memory, and can even leak one request's data into the next request.

Q3. How does Spring's @Transactional know which connection to use? TransactionSynchronizationManager binds the connection or EntityManager to the current thread using a ThreadLocal. The repositories then look it up there. That is also why a transaction does not follow your work onto other threads.

Q4. How do you pass context to async tasks? ThreadLocals don't move to other threads automatically. So capture the value before you submit the task, then set it at the start of the task and clear it at the end. A TaskDecorator or a context-propagation library can do this for you.
