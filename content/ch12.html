You already write SQL every day on SQL Server, PostgreSQL, ClickHouse and Trino. So this chapter skips the syntax basics. It focuses on what SDE2 interviews actually test:

  • How the database runs a query.
  • Why an index is used — or ignored.
  • What happens when many transactions run at the same time.
  • The SQL you are asked to write live: joins, window functions and CTEs (named sub-steps of a query).

Examples use PostgreSQL syntax. Where SQL Server is different, the difference is noted.

This sample schema is used in the whole chapter:

CREATE TABLE outlet (id BIGINT PRIMARY KEY, tenant_id INT NOT NULL, city TEXT, created_at TIMESTAMPTZ);
CREATE TABLE rep    (id BIGINT PRIMARY KEY, tenant_id INT NOT NULL, name TEXT, manager_id BIGINT REFERENCES rep(id));
CREATE TABLE orders (id BIGINT PRIMARY KEY, tenant_id INT NOT NULL, outlet_id BIGINT REFERENCES outlet(id),
                     rep_id BIGINT REFERENCES rep(id), amount NUMERIC(12,2), status TEXT, created_at TIMESTAMPTZ);

12.1 Joins and how the engine executes them

Why?

In simple words: A join stitches rows from two tables together using a matching column. Picking the right join gives the right answer. Knowing how the database runs the join tells you why the same query is fast today and slow tomorrow.

Real questions almost always need more than one table. For example:

  • "Outlets that never placed an order."
  • "Each rep with their manager."
  • "Revenue per city."

If you choose the right join type, you get the correct answer. If you also know how the engine executes the join, you can explain performance changes. The same query can be fast one day and slow the next, because the database picked a different way to run it.

What is happening internally?

There are two layers. First, the logical join type — what rows you want back:

Join Returns
INNER JOIN Only rows that have a match on both sides
LEFT JOIN All left rows; the right-side columns are NULL where there is no match
FULL OUTER JOIN All rows from both sides, with NULLs where there is no match
CROSS JOIN Every left row paired with every right row (Cartesian product)
Self join A table joined to itself (rep → manager)
Semi join (EXISTS, IN) Left rows that have at least one match — each left row appears once, not duplicated
Anti join (NOT EXISTS) Left rows that have no match at all

Second, the physical algorithm — how the database actually does the matching. A component called the query planner picks the algorithm. It decides using table statistics: stored facts like row counts and how values are spread.

Algorithm How it works Best when
Nested loop For each row on the outer side, look up the matching inner rows (ideally using an index) The outer input is small and the inner side has an index
Hash join Build a hash table from the smaller input, then check each row of the larger input against it Both inputs are large and unsorted, and the join uses equality (=)
Merge join Both inputs are sorted on the join key; walk through them side by side Both inputs are already sorted (for example, by indexes), or large range joins

Think of a nested loop like a shopkeeper checking each customer's name in a register. It is fast when there are only a few customers and the register has an alphabetical index. It is very slow for 10 lakh customers.

How does it work?

The planner works like this:

  1. It estimates how many rows each step will produce.
  2. It tries different join orders and different algorithms.
  3. It gives each option a cost.
  4. It picks the cheapest plan.

The plan is only as good as the estimates. Estimates go wrong when statistics are old (stale), or when two columns are related in a way the planner does not know (correlated columns). Then the planner makes a bad choice. The most common bad choice is a nested loop that runs over far more rows than it expected.

Example

-- Anti join: outlets that never ordered. Prefer NOT EXISTS to NOT IN (NOT IN returns nothing if the subquery yields a NULL)
SELECT o.id, o.city
FROM outlet o
WHERE NOT EXISTS (SELECT 1 FROM orders x WHERE x.outlet_id = o.id);

-- Self join: each rep with their manager (LEFT keeps reps with no manager)
SELECT r.name AS rep, m.name AS manager
FROM rep r LEFT JOIN rep m ON m.id = r.manager_id;

-- The LEFT JOIN trap: a WHERE filter on the right table turns it into an INNER JOIN
SELECT o.id, COUNT(x.id)
FROM outlet o LEFT JOIN orders x ON x.outlet_id = o.id
WHERE x.status = 'DELIVERED'            -- outlets with no orders disappear (x.status is NULL)
GROUP BY o.id;
-- Fix: move the condition into ON
SELECT o.id, COUNT(x.id)
FROM outlet o LEFT JOIN orders x ON x.outlet_id = o.id AND x.status = 'DELIVERED'
GROUP BY o.id;

When would I use it?

In every reporting query and API query that needs more than one table. Interviews often ask you to write anti joins, self joins and LEFT JOIN aggregations live, on the spot.

What can go wrong?

  • NOT IN with NULLs. If the subquery returns even one NULL, NOT IN returns no rows at all.
  • LEFT JOIN filter in WHERE. A WHERE condition on the right table quietly turns the LEFT JOIN into an INNER JOIN.
  • Accidental Cartesian product. You forget the join condition, so every row pairs with every other row.
  • Duplicate rows from a one-to-many join before aggregating. One outlet with ten orders becomes ten rows, so sums get multiplied. Aggregate first, then join.
  • Stale statistics. The planner thinks a table is small and picks a nested loop over millions of rows. Refresh statistics with ANALYZE in PostgreSQL or UPDATE STATISTICS in SQL Server.

Interview questions

Q1. Why NOT EXISTS instead of NOT IN? If the subquery returns even one NULL, NOT IN returns no rows at all. NOT EXISTS gives the correct result in that case, and the database usually runs it as an efficient anti join.

Q2. Nested loop vs hash vs merge join? Use a nested loop when the outer input is small and the inner side has an index. A hash join suits large, unsorted inputs joined on equality. A merge join is best when both inputs are already sorted on the join key.

Q3. Why does a LEFT JOIN sometimes behave like an INNER JOIN? For unmatched rows, the right table's columns are NULL. A WHERE condition on those columns removes exactly those rows. To keep them, move the condition into the ON clause.

12.2 Window functions

Why?

In simple words: A window function lets each row look at its neighbours — rows in the same group — and calculate something like a rank or a running total. Unlike GROUP BY, it does not squash the rows together; every row stays in the result.

Many questions need a result on each row that depends on other rows. For example:

  • The rank of a rep within their team.
  • A running total of sales.
  • The previous month's value.
  • The top N items in each category.

GROUP BY does not help here, because it collapses many rows into one. Self joins and correlated subqueries (a subquery that runs once per outer row) work, but they are slow and messy.

Window functions solve this. They calculate over a "window" of related rows while keeping every row. They come up again and again in live SQL rounds.

What is happening internally?

The general shape is:

function(...) OVER (PARTITION BY <group> ORDER BY <order> [ROWS|RANGE BETWEEN ... AND ...])

What the engine does:

  1. It sorts (or hashes) the rows by the partition key and the order key.
  2. For each row, it works out the frame — the set of rows the function should look at.
  3. It computes the function for that row over its frame.

When windows run: they are evaluated after WHERE, GROUP BY and HAVING, but before ORDER BY and LIMIT. Because of this, you cannot filter on a window result in the WHERE of the same query. Wrap the query in a subquery or CTE, and filter outside.

The main function families:

  • Ranking: ROW_NUMBER (1,2,3,4 — always unique), RANK (1,2,2,4 — ties share a rank, then a gap), DENSE_RANK (1,2,2,3 — ties share a rank, no gap), NTILE(n) (splits rows into n equal buckets).
  • Offsets: LAG (previous row's value), LEAD (next row's value), FIRST_VALUE, LAST_VALUE.
  • Aggregates over windows: SUM, AVG, COUNT, MIN, MAX.
  • Frame default: if you write ORDER BY but no frame, the default is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. RANGE treats rows with equal ORDER BY values (ties) as one group of "peers". So in a running total, all tied rows get the same total — which surprises people. To avoid this, write ROWS explicitly.

Think of a class result sheet. Each student's row stays on the sheet, but next to it you write their rank within their own section. That is a window function with PARTITION BY section ORDER BY marks DESC.

How does it work?

Here, R2 and R3 tie at 700. DENSE_RANK gives both rank 2, and the next rep gets 3 (no gap):

monthly_sales (tenant 7, Oct):   rep  sales   DENSE_RANK() OVER (PARTITION BY tenant, month ORDER BY sales DESC)
                                  R1   900     1
                                  R2   700     2
                                  R3   700     2
                                  R4   500     3

Example

-- 1. Top 3 reps per tenant per month (the classic)
SELECT * FROM (
  SELECT tenant_id, month, rep_id, sales,
         DENSE_RANK() OVER (PARTITION BY tenant_id, month ORDER BY sales DESC) AS r
  FROM monthly_sales) t
WHERE r <= 3;

-- 2. Running total and 7-day moving average per outlet
SELECT outlet_id, order_date, amount,
       SUM(amount) OVER (PARTITION BY outlet_id ORDER BY order_date ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS running_total,
       AVG(amount) OVER (PARTITION BY outlet_id ORDER BY order_date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)         AS avg_7d
FROM daily_outlet_sales;

-- 3. Month-over-month growth
SELECT month, revenue,
       ROUND(100.0 * (revenue - LAG(revenue) OVER (ORDER BY month))
             / NULLIF(LAG(revenue) OVER (ORDER BY month), 0), 2) AS mom_pct
FROM monthly_revenue;

-- 4. Each outlet's first order (dedupe: keep one row per group)
SELECT * FROM (
  SELECT o.*, ROW_NUMBER() OVER (PARTITION BY outlet_id ORDER BY created_at) AS rn FROM orders o) t
WHERE rn = 1;

-- 5. Share of tenant revenue per outlet (window over an aggregate)
SELECT tenant_id, outlet_id, SUM(amount) AS rev,
       100.0 * SUM(amount) / SUM(SUM(amount)) OVER (PARTITION BY tenant_id) AS pct_of_tenant
FROM orders GROUP BY tenant_id, outlet_id;

-- 6. Gaps and islands: reps who visited on 5+ consecutive days
SELECT rep_id, MIN(visit_date) AS streak_start, MAX(visit_date) AS streak_end, COUNT(*) AS days
FROM (
  SELECT rep_id, visit_date,
         visit_date - (ROW_NUMBER() OVER (PARTITION BY rep_id ORDER BY visit_date))::int AS grp
  FROM (SELECT DISTINCT rep_id, visit_date FROM visits) v
) s
GROUP BY rep_id, grp
HAVING COUNT(*) >= 5;
-- consecutive dates minus their row number give the same value → that value identifies each streak

For example 6, the trick is simple. Consecutive dates go up by one each day. Row numbers also go up by one each row. So date minus row number stays the same along a streak. When a day is missed, the value jumps. That constant value labels each streak, and you group by it.

When would I use it?

  • Leaderboards and rankings (incentive standings).
  • Deduplication — keeping one row per group.
  • Period-over-period comparisons (this month vs last month).
  • Running balances and account statements.
  • Streaks and sessionisation (grouping events into sessions).
  • Percent-of-total reports.

What can go wrong?

  • Filtering on a window column in WHERE. This is not allowed. Wrap the query in a subquery and filter outside.
  • LAST_VALUE returns the current row. This happens because the default frame ends at the current row. Set the frame to ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING.
  • RANGE vs ROWS surprises with ties. Tied rows get the same running total under RANGE.
  • Huge sorts spill to disk on big partitions. The sort no longer fits in memory and becomes slow. An index on the partition and order keys helps.

Interview questions

Q1. ROW_NUMBER vs RANK vs DENSE_RANK? ROW_NUMBER gives a unique sequence (1,2,3,4). RANK lets ties share a rank and then leaves a gap (1,2,2,4). DENSE_RANK lets ties share a rank with no gap (1,2,2,3).

Q2. How do you get the top N rows per group? In a subquery or CTE, rank rows with PARTITION BY group ORDER BY metric DESC. Then, in the outer query, keep only rows where the rank is N or less.

Q3. How do you compute a running total? Use SUM(x) OVER (PARTITION BY key ORDER BY t ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW). Write ROWS explicitly so tied values don't get the same total.

12.3 CTEs and recursive queries

Why?

In simple words: A CTE gives a name to one step of a big query, so you can read the query top to bottom like a recipe. A recursive CTE repeats a step again and again — perfect for walking down a manager → team tree.

Long queries with subqueries nested inside subqueries are hard to read and hard to debug. A common table expression (CTE) gives each step a name. Then the query reads from top to bottom, step by step.

A recursive CTE goes further. It solves hierarchy problems — manager chains, category trees, distributor networks. Without recursion, you cannot solve these in a single query, because you don't know in advance how many levels deep the tree goes.

What is happening internally?

  • A normal CTE (WITH name AS (…)) defines a named subquery that lives only for that one statement.
  • PostgreSQL 12 and later inline CTEs. This means the CTE is copied into the main query and optimised like a normal subquery. The exception is when you mark it MATERIALIZED — then it is computed once and stored.
  • SQL Server always inlines CTEs.
  • So a CTE is a readability tool, not a performance tool.
  • A recursive CTE has two parts joined by UNION ALL:
  • An anchor member — the starting rows.
  • A recursive member — a query that joins the CTE back to the table to find the next level.

The engine runs it in a loop:

  1. Run the anchor to get the first set of rows.
  2. Feed those rows into the recursive member to get the next level.
  3. Feed the new rows in again.
  4. Stop when a step returns no new rows.

Think of a family tree. You start with one grandparent (the anchor). Then you find their children, then the children's children, and so on — until a generation has no children.

How does it work?

iteration 0 (anchor):    direct reports of 42           → {7, 9}
iteration 1:             reports of {7, 9}             → {15, 16, 21}
iteration 2:             reports of {15, 16, 21}       → {}   → stop

Example

-- Readable multi-step report
WITH delivered AS (
  SELECT rep_id, date_trunc('month', created_at) AS month, SUM(amount) AS sales
  FROM orders WHERE status = 'DELIVERED' GROUP BY 1, 2
),
ranked AS (
  SELECT *, RANK() OVER (PARTITION BY month ORDER BY sales DESC) AS r FROM delivered
)
SELECT * FROM ranked WHERE r <= 10;

-- Everyone under manager 42, with depth (sales hierarchy)
WITH RECURSIVE team AS (
  SELECT id, name, manager_id, 1 AS depth FROM rep WHERE manager_id = 42          -- anchor
  UNION ALL
  SELECT r.id, r.name, r.manager_id, t.depth + 1
  FROM rep r JOIN team t ON r.manager_id = t.id                                   -- recursive step
  WHERE t.depth < 20                                                              -- guard against cycles in bad data
)
SELECT * FROM team ORDER BY depth;
-- SQL Server: identical without the RECURSIVE keyword; limit with OPTION (MAXRECURSION n)

When would I use it?

  • Breaking complex reports into named steps.
  • Organisation and sales hierarchies — for example, rolling incentives up to managers.
  • Bill-of-materials (a product made of parts, which are made of smaller parts).
  • Graph-like walks that don't go very deep.

What can go wrong?

  • Infinite recursion on cyclic data. If bad data says A manages B and B manages A, the loop never ends. Add a depth limit, or keep an array of the path already visited and stop when you see a repeat.
  • Assuming CTEs are materialised (or not). Engines behave differently. Don't assume a CTE is computed once.
  • Very deep or very wide recursion on big tables. This gets slow. For large hierarchies, consider a closure table (a table storing every ancestor–descendant pair) or a materialised path (storing the full path like /1/42/7/ on each row).

Interview questions

Q1. What is a recursive CTE? It is a CTE with two parts: an anchor query that gives the starting rows, and a recursive query that refers back to the CTE. The engine repeats the recursive part until no new rows come out. It is used for hierarchies.

Q2. Do CTEs improve performance? Usually no. Modern PostgreSQL and SQL Server inline them, so they run like normal subqueries. Their real benefit is readability. In PostgreSQL, use MATERIALIZED when you deliberately want the CTE computed once.

12.4 Classic SQL interview problems and evaluation order

Why?

In simple words: Live SQL rounds keep asking the same handful of problems. Learn the templates, and learn the order in which SQL runs each clause — then you can write them fast and explain why they work.

Live SQL rounds reuse a small set of patterns:

  • Nth highest value.
  • Finding and deleting duplicates.
  • "Did it happen in every period?" (this is called relational division).
  • Pivots — turning row values into columns.
  • Retention — who came back next month.

If you know these patterns, and the logical order in which SQL runs, you can write them quickly and explain them clearly.

What is happening internally?

Logical evaluation order — the order SQL conceptually runs each clause. It explains many alias and filter errors: FROM/JOIN → WHERE → GROUP BY → HAVING → window functions → SELECT → DISTINCT → ORDER BY → LIMIT/OFFSET

What this means in practice:

  • WHERE runs before SELECT. So WHERE cannot see the aliases you define in SELECT.
  • WHERE runs before GROUP BY. So WHERE cannot filter on aggregates like SUM. Use HAVING for that.
  • Window functions run after WHERE. So you cannot filter on a window result at the same level.

How does it work?

First, recognise which pattern the question is. Then apply that pattern's template from the examples below.

Example

-- Nth highest salary (N = 2), ties handled
SELECT DISTINCT salary FROM (
  SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) r FROM employee) t
WHERE r = 2;

-- Delete duplicate rows by business key, keeping the earliest
DELETE FROM orders o USING (
  SELECT id, ROW_NUMBER() OVER (PARTITION BY tenant_id, external_ref ORDER BY created_at) rn FROM orders) d
WHERE o.id = d.id AND d.rn > 1;

-- Outlets that ordered in every month of 2026 (relational division)
SELECT outlet_id FROM orders
WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'
GROUP BY outlet_id
HAVING COUNT(DISTINCT date_trunc('month', created_at)) = 12;

-- Pivot with conditional aggregation (works everywhere)
SELECT tenant_id,
       COUNT(*) FILTER (WHERE status = 'DELIVERED') AS delivered,      -- SQL Server: SUM(CASE WHEN status='DELIVERED' THEN 1 ELSE 0 END)
       COUNT(*) FILTER (WHERE status = 'CANCELLED') AS cancelled
FROM orders GROUP BY tenant_id;

-- Month-on-month retention: active in month M and also in M+1
WITH m AS (SELECT DISTINCT outlet_id, date_trunc('month', created_at) AS mon FROM orders)
SELECT a.mon, COUNT(*) AS active, COUNT(b.outlet_id) AS retained
FROM m a LEFT JOIN m b ON b.outlet_id = a.outlet_id AND b.mon = a.mon + interval '1 month'
GROUP BY a.mon ORDER BY a.mon;

When would I use it?

In SQL rounds, in analytics questions during system-design interviews, and in your daily reporting work.

What can go wrong?

  • Using LIMIT 1 OFFSET N-1 for Nth highest. This is wrong when there are ties. Use DENSE_RANK instead.
  • COUNT(col) vs COUNT(*) with NULLs. COUNT(col) skips NULLs; COUNT(*) counts every row.
  • Comparing dates using a function on the column. For example DATE(created_at) = …. This stops the index from being used — it is non-sargable (see 12.5).
  • Integer division in percentages. 5 / 10 gives 0 in integer maths. Multiply by 100.0 to force decimal maths.

Interview questions

Q1. WHERE vs HAVING? WHERE filters individual rows before grouping. HAVING filters whole groups after aggregation.

Q2. Why can't I use a SELECT alias in WHERE? In the logical order, WHERE runs before SELECT, so the alias doesn't exist yet. Either repeat the expression in WHERE, or wrap the query and filter outside.

12.5 How indexes work: B+ trees, clustered and covering indexes

Why?

In simple words: An index is like the index at the back of a book. Instead of reading every page to find a word, you look it up and jump straight to the right page. Without it, the database reads the whole table.

Without an index, the database must scan the whole table to find rows. The work grows with table size — O(n) disk pages. With the right index, a lookup reads only 3–4 pages, no matter how big the table is.

Most "the API takes 30 seconds" problems are really index problems. And "why isn't my index being used?" is one of the top SDE2 database questions.

What is happening internally?

Relational database indexes are B+ trees. A B+ tree is:

  • Balanced — every path from the top to the bottom has the same length.
  • Very wide — each 8 KB page holds hundreds of keys.

It has two kinds of pages:

  • Internal pages hold separator keys (signposts like "keys below 1000 go left") and pointers to child pages.
  • Leaf pages hold the actual keys in sorted order. Each leaf is linked to its neighbours. So a range scan finds the first leaf, then simply walks along the leaves in order.

Because each page fans out to about 500 children, a billion rows need only about 4 levels. The top levels are used so often that they stay in memory.

Think of a library. The signboard at the entrance tells you which floor. The floor sign tells you which shelf. The shelf has books in sorted order, and you can walk along it. Three or four steps, however big the library is.

                 [ 1000 | 5000 ]                      root (cached)
        ┌─────────────┼──────────────┐
  [200|600]       [2000|3500]     [7000|9000]          internal
   ↓   ↓   ↓        ↓    ↓   ↓      ↓    ↓   ↓
 leaf ⇄ leaf ⇄ leaf ⇄ leaf ⇄ leaf ⇄ leaf ⇄ leaf …      sorted keys + row pointers, linked for range scans

The main kinds of index:

  • Clustered index (SQL Server, MySQL InnoDB): the table rows themselves are the leaf level. Rows are stored in primary-key order. There can be only one per table.
  • Secondary indexes store the primary key, not a direct row address. So a lookup through a secondary index goes: index → primary key → row. SQL Server calls this a key lookup.
  • Random UUID primary keys land in random places. This causes page splits (a full page is split in two to make room) and fragmentation. Sequential or time-ordered keys just add to the end neatly (11.22).
  • Heap + secondary indexes (PostgreSQL): rows live in an unordered pile called the heap. Every index points to a row's physical location, called the TID.
  • Covering index: an index that contains every column the query needs. So the engine never has to visit the table at all. In PostgreSQL this is an index-only scan. In SQL Server you add extra columns with INCLUDE.
  • Other index types:
  • Hash — equality (=) only.
  • GIN — PostgreSQL JSONB, arrays and full-text search.
  • GiST/BRIN — GiST for geo data; BRIN for huge tables that are naturally in order (like append-only time data).
  • Partial — indexes only some rows, e.g. WHERE status = 'PENDING'.
  • Unique — also how you enforce idempotency keys (keys that make a repeated request safe to apply only once).

How does it work?

Composite index column order. A composite index covers several columns. It works like a phone book sorted by (last name, first name). Follow these rules:

  1. Put equality-filtered columns first (tenant_id, status).
  2. Then put the range or sort column (created_at).
  3. Leftmost-prefix rule: an index on (tenant_id, status, created_at) helps WHERE tenant_id = ? and WHERE tenant_id AND status. It does not help WHERE status = ? alone. A phone book sorted by last name can't help you find everyone with first name "Rahul".

Why an index gets ignored:

  • A function or calculation on the column. WHERE DATE(created_at) = '2026-10-01' can't use the index on created_at. Rewrite it as a range: created_at >= '2026-10-01' AND created_at < '2026-10-02'. A filter that can use an index like this is called "sargable". Or create an expression index on DATE(created_at).
  • An implicit type conversion. For example, a VARCHAR column compared to a number. In SQL Server, NVARCHAR vs VARCHAR mismatches do the same.
  • A leading wildcard. LIKE '%abc' can't use a normal index, because you don't know the start of the value. Use trigram or full-text indexes.
  • Low selectivity. If the filter matches roughly 10–20% or more of the rows, reading the whole table in order is cheaper than jumping around for many random lookups.
  • OR across different columns. Rewrite as UNION ALL, or rely on the engine's bitmap OR (combining two index results).
  • Stale statistics, or a cached plan built for different parameter values. In SQL Server, this second one is called parameter sniffing: the plan was built for the first parameter value it saw, and is bad for others.

Example

CREATE INDEX ix_orders_tenant_status_created
  ON orders (tenant_id, status, created_at DESC) INCLUDE (amount);
-- Serves: WHERE tenant_id = ? AND status = ? ORDER BY created_at DESC LIMIT 50   (no sort needed)
--         SELECT SUM(amount) … same filter                                         (index-only, no table access)
-- Doesn't serve: WHERE status = 'OPEN'  (tenant_id not constrained → leftmost prefix broken)

When would I use it?

  • On the filter, join and sort columns of every frequent query.
  • Unique indexes for business keys and idempotency.
  • Partial indexes for small "hot" subsets — for example, outbox rows not yet published, or pending payments.

What can go wrong?

  • Too many indexes. Every write must update every index. This costs storage and multiplies write work (write amplification).
  • Duplicate or unused indexes. Check the usage statistics and drop them.
  • Wrong column order in a composite index.
  • Indexing a low-cardinality column alone, like status. A column with only a few distinct values doesn't narrow things down much.
  • Random UUID keys in clustered indexes. They cause page splits and fragmentation.

Interview questions

Q1. How does a B+ tree index speed up queries? It keeps keys sorted in a tree that is shallow and very wide. So a lookup reads only about 3–4 pages. Its leaves are linked together, so range scans read them one after another.

Q2. Clustered vs non-clustered index? A clustered index stores the table rows themselves in key order, so there can be only one per table. A non-clustered index is a separate structure that points to the rows.

Q3. Why might the database not use my index? Common reasons: a function or type conversion on the column, a leading wildcard, low selectivity, the wrong composite column order, stale statistics, or a bad cached plan.

Q4. How do you choose composite index column order? Put equality filters first, then range or sort columns. Respect the leftmost-prefix rule. Add INCLUDE columns so the index covers the whole query.

12.6 Query plans and query optimisation

Why?

In simple words: A query plan is the database's step-by-step route for running your query. Reading it shows you exactly where the time went, so you fix the real problem instead of guessing.

Guessing why a query is slow can waste days. The query plan shows exactly what the database did:

  • Which indexes it used.
  • Which join algorithms it chose.
  • How many rows came out of each step.
  • Where the time went.

Reading plans is how you turn "it's slow" into a specific fix. It is also the heart of a good performance story in an interview — like your ~30 s → ~10 s API improvement.

What is happening internally?

  • EXPLAIN shows the plan the optimiser chose. It shows estimated rows and costs. It does not run the query.
  • EXPLAIN ANALYZE actually runs the query. It shows the actual rows and timings for each step.
  • BUFFERS adds how many pages were read from memory cache vs from disk.
  • In SQL Server, the equivalent is the actual execution plan, plus Query Store for history over time.

Think of Google Maps. EXPLAIN is the route it suggests before you leave. EXPLAIN ANALYZE is the record of the trip you actually took, with the time spent on each road.

How does it work?

Look for these clues in the plan:

Plan clue Meaning Usual fix
Seq Scan on a large table with a selective filter There is no index the planner can use Add a composite index that matches the filter + sort
Estimated 10 rows vs actual 500,000 Bad statistics, or columns related in a way the planner doesn't know ANALYZE, extended statistics, or rewrite the query
Nested Loop with a huge outer side Wrong join choice caused by a bad estimate Fix the estimates; index the inner side
Sort … external merge Disk The sort did not fit in memory and spilled to disk An index that already gives the order, or more work_mem
Index Scan + many heap fetches / SQL Server Key Lookup in a loop The index does not cover the query, so each row needs a trip to the table Add INCLUDE columns
Large Rows Removed by Filter The index finds rows, but most are thrown away afterwards Add the filtered column to the index

Optimisation checklist — work through it in order:

  1. Measure first. Find which query takes most of the time. Use the slow query log, pg_stat_statements, SQL Server Query Store, or APM traces.
  2. Read the plan. Compare estimated rows with actual rows.
  3. Index for the access path. Cover the filter first, then the sort, then the columns the query returns.
  4. Return less data. Select only the columns you need. Use keyset pagination (continue from the last seen key, instead of a large OFFSET). Aggregate in the database, not in Java.
  5. Remove N+1 patterns (7.10) — one query for a list, then one more query per item. Batch them with IN (...) or a join.
  6. Pre-aggregate. Use materialised views, summary tables, or ClickHouse for analytics.
  7. Partition big tables so queries skip irrelevant partitions (12.8).
  8. Cache results that don't change often. Move heavy reports to read replicas or an OLAP system.
  9. Verify the result using the same metrics after the change.

Example

EXPLAIN (ANALYZE, BUFFERS)
SELECT outlet_id, SUM(amount)
FROM orders
WHERE tenant_id = 7 AND created_at >= now() - interval '30 days'
GROUP BY outlet_id;

-- Before: Seq Scan on orders (actual rows 9,800,000 scanned, 120,000 kept) … 8,400 ms
-- Add:    CREATE INDEX CONCURRENTLY ix_orders_tenant_created ON orders (tenant_id, created_at) INCLUDE (outlet_id, amount);
-- After:  Index Only Scan using ix_orders_tenant_created (actual rows 120,000) … 95 ms

Say this: "The incentive dashboard API took ~30 seconds. APM showed 90% of the time in one aggregation query. The plan was a sequential scan over the whole orders table because we filtered on DATE(created_at). I rewrote the predicate as a range, added a composite covering index on (tenant, created_at) including the aggregated columns, and moved one heavy breakdown to a pre-aggregated table. The endpoint went to ~10 seconds and the DB CPU dropped." Adapt this to what you actually did — only claim the steps you took.

When would I use it?

  • Every slow-endpoint investigation.
  • Every new query on a big table — check its plan before you ship it.
  • Design reviews of reporting features.

What can go wrong?

  • Testing plans on tiny dev data. On production volumes, the planner chooses differently.
  • Adding indexes blindly. Each index adds write cost.
  • Running EXPLAIN ANALYZE on destructive statements in production. It really executes them — an UPDATE or DELETE will change data. Wrap it in a transaction and roll back.
  • Fixing one query while the real problem is the number of queries. For example, an N+1 pattern firing hundreds of fast queries.

Interview questions

Q1. How would you find and fix a slow query? First find it, using the slow log, Query Store or APM. Run EXPLAIN ANALYZE and compare estimated rows with actual rows. Then fix indexes or rewrite the filters, return less data, and remove N+1 patterns. If needed, pre-aggregate or partition. Finally, confirm the improvement with metrics.

Q2. EXPLAIN vs EXPLAIN ANALYZE? EXPLAIN shows the planned strategy with estimates only. EXPLAIN ANALYZE actually runs the query and reports the real rows and timings for each step.

12.7 Transactions, MVCC, locks and database deadlocks

Why?

In simple words: Many users change the same data at the same time. The database must keep them from stepping on each other — without making everyone wait in one long queue. MVCC and locks are how it does this.

Hundreds of transactions hit the same tables at the same moment. How the database keeps them apart (isolation) decides two things:

  • Correctness — no money spent twice, no update silently lost.
  • Throughput — who blocks whom, and how much work gets done per second.

Once you understand MVCC and locking, you can explain strange results (anomalies), deadlocks, and "why is this query just waiting?".

What is happening internally?

MVCC stands for multi-version concurrency control. PostgreSQL, Oracle and MySQL InnoDB use it, and so does SQL Server when snapshot isolation is on. Here is how it works:

  • An UPDATE does not overwrite the row. It writes a new version of the row. The old version stays for transactions that started earlier.
  • Each transaction reads the versions that were committed as of its snapshot — a fixed point in time. In READ COMMITTED, the snapshot is taken at the start of each statement. In REPEATABLE READ, it is taken at the start of the transaction.
  • So readers don't block writers, and writers don't block readers. But writers still block other writers on the same row.
  • PostgreSQL keeps the old versions inside the table. They are called dead tuples. VACUUM cleans them up. A long-running transaction stops this cleanup, so the table grows with junk. This is called bloat.
  • SQL Server's default READ COMMITTED uses locks, not versions. Readers take shared locks and can block writers. If you turn on READ_COMMITTED_SNAPSHOT, it uses row versions stored in tempdb instead. This is a real difference from your SQL Server experience, and worth mentioning in an interview.

Think of a bank passbook. When a new entry is written, your earlier printout still shows the old balance. Someone reading the old printout doesn't stop the clerk from writing a new entry.

Locks (simplified):

  • Shared (S) — taken for reads when the isolation level uses locking.
  • Exclusive (X) — taken for writes.
  • Update (U) — SQL Server only. Taken when you read a row you plan to update. It avoids conversion deadlocks, where two readers both try to upgrade to a write lock.
  • Intention locks — placed at table or page level to signal "someone has a lock inside here".
  • Range/gap locks — lock a range of keys, not just existing rows. Used in SERIALIZABLE in SQL Server and REPEATABLE READ in InnoDB. They prevent phantoms — new rows appearing in a range you already read.

Explicit row locks: SELECT … FOR UPDATE (PostgreSQL/MySQL) or WITH (UPDLOCK, ROWLOCK) (SQL Server). FOR UPDATE SKIP LOCKED lets many workers each take different rows from a queue table, without waiting on each other. This is used for outbox relays and job schedulers.

Lock escalation (SQL Server): if one statement holds thousands of row locks, SQL Server may swap them for a single table lock. That blocks everyone. So split big updates into smaller chunks (batches).

Deadlock: transaction A locks row 1 and waits for row 2. At the same time, transaction B locks row 2 and waits for row 1. Neither can move. The database's deadlock detector finds this cycle and aborts one of the transactions. PostgreSQL reports deadlock detected. SQL Server reports error 1205, "chosen as deadlock victim".

How does it work?

Step by step:

  1. T1 updates account A, so it locks A.
  2. T2 updates account B, so it locks B.
  3. T1 now wants B. B is locked by T2, so T1 waits.
  4. T2 now wants A. A is locked by T1, so T2 waits.
  5. Each waits for the other — a cycle. The database rolls one back.
T1: UPDATE account SET balance=balance-10 WHERE id='A'   (locks A)
T2: UPDATE account SET balance=balance-10 WHERE id='B'   (locks B)
T1: UPDATE account SET balance=balance+10 WHERE id='B'   (waits for T2)
T2: UPDATE account SET balance=balance+10 WHERE id='A'   (waits for T1) → cycle → one is rolled back
Fix: always update accounts in ascending id order (both lock A first).

Isolation anomalies (full table in 7.14):

  • Dirty read — reading data another transaction hasn't committed yet.
  • Non-repeatable read — reading the same row twice and getting different values.
  • Phantom — running the same range query twice and getting new rows.
  • Lost update — two transactions update the same row, and one update overwrites the other.
  • Write skew — two transactions read the same condition, and each writes a different row. Together they break a rule that each one alone would have kept. Example: two admins each approve "the last" budget slot, so two slots get used.

Write skew needs SERIALIZABLE isolation, or an explicit FOR UPDATE on the rows you read.

Example

-- Job queue table consumed by many workers without blocking each other
BEGIN;
SELECT id, payload FROM outbox
WHERE published_at IS NULL
ORDER BY created_at
LIMIT 100
FOR UPDATE SKIP LOCKED;          -- each worker gets a disjoint batch
-- publish to Kafka …
UPDATE outbox SET published_at = now() WHERE id = ANY(:ids);
COMMIT;

When would I use it?

  • Designing concurrent updates — balances, inventory, seat holds.
  • Job tables and outbox tables.
  • Batch updates on busy ("hot") tables.
  • Debugging blocking — "which session holds the lock?". In PostgreSQL, use pg_locks + pg_stat_activity. In SQL Server, use sys.dm_tran_locks and blocked process reports.

What can go wrong?

  • Long transactions. They hold locks longer, cause bloat, and cause replication lag.
  • Network calls inside transactions. A slow HTTP call keeps locks held the whole time.
  • Inconsistent lock ordering. Different code paths lock rows in different orders, which causes deadlocks.
  • Missing indexes. An UPDATE without a useful index scans and locks more rows than needed.
  • Not retrying deadlock victims and serialisation failures. These are normal and expected. Retry them with a small backoff (a short wait), and make the retry idempotent — safe to run twice.

Interview questions

Q1. What is MVCC? Writers create new versions of a row instead of overwriting it. Readers see a consistent snapshot. So reads and writes don't block each other. Old versions are cleaned up later.

Q2. How do database deadlocks happen and how do you handle them? Transactions wait on each other's row locks in a cycle, and the database aborts one of them. Prevent it with a consistent lock order, short transactions, good indexes and single-statement updates. Retry the victim.

Q3. What is write skew and how do you prevent it? Two concurrent transactions read overlapping data. Based on it, each writes a different row, and together they break a rule (an invariant). Prevent it with SERIALIZABLE isolation, or by locking the rows you read with FOR UPDATE.

Q4. What does FOR UPDATE SKIP LOCKED do? It locks the selected rows and skips any rows already locked by others. So parallel workers each grab different work items without blocking each other.

12.8 Data modelling: normalisation, denormalisation and table partitioning

Why?

In simple words: Normalising means storing each fact in one place, so it can't go out of sync. Denormalising means copying data on purpose to make reads faster. Partitioning means cutting one huge table into smaller pieces, usually by month.

The schema decides three things:

  • Correctness — no update anomalies (the same fact stored twice, with one copy updated and the other not).
  • Performance — how many joins each request needs.
  • Operability — how you archive or delete old data.

A senior engineer knows when to normalise, when to denormalise on purpose, and how to keep huge tables manageable.

What is happening internally?

Normal forms, one line each:

  • 1NF: each column holds a single value, and there are no repeating groups. For example, no comma-separated SKU list in one column.
  • 2NF: no column depends on only part of a composite key.
  • 3NF: no transitive dependencies — a column should not depend on another non-key column. An outlet's city belongs in outlet, not repeated in every order.
  • BCNF: every determinant (a column that decides another column's value) is a candidate key.

Denormalisation means copying data so you avoid joins or recalculation. Use it for:

  • Read-heavy paths.
  • Analytics tables.
  • Cached aggregates — for example, a balance column kept next to the ledger and checked against it (reconciled) every night.
  • Historical snapshots that must not change when master data changes. Store the price at order time on the order line. This is a correctness requirement, not just a performance trick.

Table partitioning splits a large table into child tables by a key — usually time. This is inside one database. It is different from sharding, which spreads data across servers (11.9). Benefits:

  • Queries that filter on the key touch only the relevant partitions. This is called partition pruning.
  • Dropping an old partition is instant. A huge DELETE is slow and heavy.
  • Each partition's indexes are smaller.

Think of an office that keeps one file cabinet per month. To find last week's papers, you open only this month's cabinet. To throw away 2019, you remove the 2019 cabinets — no need to pull out papers one by one.

How does it work?

CREATE TABLE ledger_entry (
  id BIGINT NOT NULL, tenant_id TEXT NOT NULL, account_id TEXT NOT NULL,
  points BIGINT NOT NULL, created_at TIMESTAMPTZ NOT NULL,
  PRIMARY KEY (id, created_at)                       -- the partition key must be part of the PK/unique keys
) PARTITION BY RANGE (created_at);

CREATE TABLE ledger_entry_2026_10 PARTITION OF ledger_entry
  FOR VALUES FROM ('2026-10-01') TO ('2026-11-01');
-- monthly job creates next month's partition; retention job detaches/drops partitions older than 7 years (or archives them)

Example

The orders table grows by 60M rows a year. You use monthly range partitions. Now:

  • Dashboard queries for "last 30 days" scan only one or two partitions.
  • GDPR or retention deletes become a simple DROP TABLE orders_2019_01.
  • Vacuum and index maintenance run per partition, which is smaller and faster.

When would I use it?

  • Normalise OLTP (transactional) schemas by default.
  • Denormalise on purpose, for read paths that are proven slow, and for history.
  • Partition tables that keep growing forever (ledgers, events, orders, logs) by time. Choose a partition key that appears in almost every query's filter.

What can go wrong?

  • Denormalised copies drift out of sync. Decide which copy is the source of truth. Decide how the copies get updated — events, triggers, or reconciliation jobs.
  • Partitioning on a key that queries don't filter by. Then every query scans every partition.
  • Too many tiny partitions. The planner spends too long just planning.
  • Unique constraints must include the partition key. You can't enforce uniqueness on id alone across partitions.

Interview questions

Q1. When would you denormalise? For read-heavy paths where joins cost too much, for analytics, for cached aggregates, and for historical snapshots such as the price at order time.

Q2. Partitioning vs sharding? Partitioning splits a table inside one database, so queries can skip partitions and old data is easy to drop. Sharding spreads data across many database servers, to get more capacity and more write throughput.

12.9 OLTP vs OLAP: where ClickHouse and Trino fit

Why?

In simple words: The database that takes orders (OLTP) is built for many tiny reads and writes. Dashboards need the opposite — a few huge scans over months of data. So analytics goes to a different kind of database (OLAP), like ClickHouse, which is built for scanning.

A dashboard that adds up months of orders across thousands of outlets will crush a transactional database. It will also slow down checkout for real users. Analytical work needs a different storage design.

Your experience with ClickHouse and Trino is a strength here. Be ready to explain why they are fast.

What is happening internally?

OLTP means online transaction processing. OLAP means online analytical processing.

OLTP (PostgreSQL, SQL Server) OLAP (ClickHouse, BigQuery, Snowflake; Trino over a lake)
Workload Many small reads and writes by key A few huge scans and aggregations
Storage Row-oriented (all columns of one row stored together) Column-oriented (each column stored separately, heavily compressed)
Indexes B+ trees for point lookups Sparse primary index + sort order; skip indexes; min/max per block
Updates Cheap and transactional Expensive or done later in the background (mutations, ReplacingMergeTree)
Joins Strong Possible but costly; prefer wide, denormalised tables

Why columnar storage is fast for analytics:

  • A query that sums amount by outlet_id reads only those two columns. It skips the rest.
  • Similar values are stored next to each other, so they compress 5–10×. Less data to read from disk.
  • Vectorised execution processes values in batches, using SIMD (one CPU instruction working on many values at once).

Think of a school register. A row store is like one file per student, with all their marks. To find the class average in Maths, you open every file. A column store is like one sheet with only the Maths marks of all students — you read just that one sheet.

ClickHouse MergeTree:

  1. Inserted data is sorted by the table's ORDER BY key.
  2. It is written as immutable (never changed) parts.
  3. Parts are merged together in the background.
  4. The sparse primary index stores one mark per granule (a block of 8,192 rows). So a query reads only the granules that can match.
  5. Materialised views keep rollups up to date at insert time.
  6. TTLs (time-to-live rules) move or drop old data automatically.

Trino is a distributed SQL query engine with no storage of its own. It federates queries — one SQL query can read from many sources: Hive/Iceberg tables on object storage, PostgreSQL, Kafka, ClickHouse. It is great for ad-hoc analysis across systems. It is not meant for low-latency serving to users.

How does it work?

The data flow:

  1. PostgreSQL holds the source of truth.
  2. CDC (change data capture — Debezium reads every change from the database log) sends changes to Kafka.
  3. ClickHouse reads from Kafka. A materialised view builds daily sales per outlet for dashboards and incentive metrics.
  4. Batch exports go to a data lake (Iceberg on Blob storage). Trino queries the lake, Postgres and ClickHouse together for ad-hoc analysis.
PostgreSQL (truth) ──CDC (Debezium)──► Kafka ──► ClickHouse (MergeTree, ORDER BY (tenant_id, outlet_id, day))
                                                    └─ materialised view: daily sales per outlet → dashboards, incentive metrics
Data lake (Iceberg on Blob) ◄── batch exports; Trino queries lake + Postgres + ClickHouse for ad-hoc analysis

Example

CREATE TABLE sales_events (
  tenant_id UInt32, outlet_id UInt64, sku LowCardinality(String), amount Decimal(12,2), event_time DateTime
) ENGINE = MergeTree
PARTITION BY toYYYYMM(event_time)
ORDER BY (tenant_id, outlet_id, event_time)
TTL event_time + INTERVAL 3 YEAR;

-- Scans only the granules for tenant 7 in the last 30 days, reading 3 columns
SELECT outlet_id, sum(amount) FROM sales_events
WHERE tenant_id = 7 AND event_time >= now() - INTERVAL 30 DAY
GROUP BY outlet_id ORDER BY sum(amount) DESC LIMIT 10;

Say this: "Transactional truth stays in PostgreSQL or SQL Server; changes stream via CDC and Kafka into ClickHouse for dashboards and incentive aggregates; Trino handles ad-hoc analysis across sources. That split keeps heavy analytics from ever hurting checkout latency."

When would I use it?

  • Dashboards and reports.
  • Incentive metric aggregation (13.14).
  • Metrics and log analytics (13.11).
  • Any query over months or years of events.

What can go wrong?

  • Using ClickHouse like an OLTP database. Frequent single-row updates and deletes, or point lookups by non-key columns, perform badly.
  • A poor ORDER BY key. Queries can't skip granules, so they read everything.
  • Too many small inserts. Each insert creates a new part. Batch your inserts.
  • Expecting strong consistency. The analytics store is fed asynchronously, so it is always slightly behind the source.

Interview questions

Q1. Row store vs column store? A row store keeps each row together, which is ideal for transactional point reads and writes. A column store keeps each column together, which is ideal for scanning and aggregating a few columns over many rows, with high compression.

Q2. Why is ClickHouse fast for aggregations? It uses columnar storage, so it reads only the needed columns. Data is heavily compressed. Data is sorted by the primary key, and a sparse index lets it skip granules. It uses vectorised execution. And materialised views pre-aggregate data at insert time.

Q3. What is Trino used for? Distributed SQL across many data sources, without storing any data itself. It is used for ad-hoc analytics across a data lake and operational databases.
